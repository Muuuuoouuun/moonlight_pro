# C레벨·Eevee Office·Agent 통합 검토와 발전 방향

> 상태: **설계 전 검토 기록 · 권장안 비교**. 이후 운영자의 “진행, 심화 설계” 및 “구현, 서브에이전트 동원”에 따라 [심화 설계](superpowers/specs/2026-09-21-eevee-office-embedded-workflow-deep-design.md)와 [구현 기록](superpowers/plans/2026-09-21-eevee-office-embedded-workflow.md)이 작성됐다. 아래의 “현재”·“구현 전”은 검토 당시 기준이다.
> 작성: 2026-09-21. 현재 체크아웃의 문서·소스 코드 기준.
> 요청: C레벨·EV·에이전트 내용을 다시 취합하고 구조·피치·기능·탭·섹션의 균형을 점검한다.
> 용어: 이번 조사에서 EV는 Eevee Office로 해석했다. 이브이(eevee, 비서실장)와 에브이(espeon, 전략총괄)는 구분한다.
> 검증 범위: 정적 구조 검토와 Office 관련 기존 테스트. 화면을 브라우저에서 관찰한 시각 QA, 운영 연결 검증, 새로운 실제 모델 평가는 수행하지 않았다.

## 1. 핵심 판단

현재는 역할 설명의 깊이에 비해 실제 업무 문맥과 결과를 이어 주는 연결이 얕다. 9인의 성격을 더 길게 쓰는 것보다 **현재 업무를 이해하고, 사용할 결과물 하나를 만들고, 그 결과를 원래 업무에서 이어 쓰는 경험**에 투자할 때다.

유지할 자산은 9인 역할, 회사/개인 범위 분리, 단일 주관, 실제 실행과 생성의 구별, 기존 명령·receipt·worker 기반이다. 조정할 것은 중복 진입점, 상시 노출되는 선택지, 과도한 능력 표현, 결과의 저장·적용 연결이다.

권장 방향은 **업무 화면에서 쓰는 도움 + 필요할 때 깊게 들어가는 Office**다. Office는 자유 요청과 복합 판단의 공간으로 남기고, 일상적인 답장·원고·주간 정리는 해당 업무 화면 곁에서 완성한다.

## 3. 현재 실제 구조

| 층 | 현재 확인한 내용 | 제품에서 보여줄 의미 |
|---|---|---|
| C레벨 9인 | 같은 Office 서비스에 선택 역할의 지침을 주입 | 책임과 판단 관점 |
| Office | 대화·초안·검토·회의, 생성 후 같은 모델의 편집 검수 | 답변·산출물 생성 |
| Office Council | 주관 포함 2~3개 관점, 단일 모델 시뮬레이션 | 복합 판단의 관점 비교 |
| 기존 Guru/브랜드 Council | 별도 서비스·ID·기억 경계 | 기존 영업 코칭·브랜드 자문 |
| Legend | Office 입력은 lens=null만 허용 | Office에서는 미연결 |
| Office 문맥 | 사용자 입력과 최근 대화; 선택 시 최근 프로젝트 최대 8개의 제한 필드 | 전체 CRM·일정·문서 자동 조회가 아님 |
| Office 기억 | 페이지 React 상태에 대화 유지, 선택적 agent_runs 기록 | 로그 저장과 대화 복원은 다름 |
| 업무 실행 | 기존 command/receipt와 별도 Codex jobs/worker가 존재 | Office의 다음 행동 텍스트와 아직 직접 연결되지 않음 |

권장 개념 정리:

```text
업무 원문·선택 대상
  → 담당 역할 1명
  → 대화 / 초안 / 검토 / 관점 비교
  → 결과물 + 근거 + 다음 행동
  → 사용자가 선택한 기존 저장·적용 경로
  → receipt 및 원장 재조회

Guru = 방법론 참조, Legend = 가치 판단 참조
Agent runtime = 실제 도구·권한·작업 상태를 가진 실행 계층
```

이 그림의 저장·적용 연결은 발전 방향이다. 현재 Office가 이 전체 흐름을 수행한다는 뜻이 아니다. 특히 C레벨 명칭이 도구 권한이나 독립 프로세스를 부여하지 않는다.

## 4. 바로 정리할 불일치

| 우선 | 발견 | 근거와 영향 | 권장 수정 |
|---|---|---|---|
| P0 | 실행 불가 규칙과 실행 약속 예시 공존 | `prompt.ts`는 도구 없음을 명시하지만 `personas.ts`에는 보관·캘린더 재배치·재연락·테스트 실행을 약속하는 예시가 있음 | 역할의 유능함을 완성된 초안·확인 절차로 표현. 능력별로 허용 문장을 분리 |
| P0 | 목표와 성과의 혼용 | C-Suite OS §5의 `1/3 절감 달성`, 100%·0% 보장 표현은 현재 평가가 입증하지 않음 | `목표`, `검증할 기준`, `관찰 결과`로 구분 |
| P0 | 문서 출력 계약과 parser 불일치 | C-Suite OS의 `meta`는 실제 `parseOfficeAnswer` 허용 키에 없음. 그대로 출력하면 거절됨 | 문서에서 후속 계약으로 표시하거나 버전 변경과 parser·schema·test를 함께 갱신 |
| P1 | 가역성 분류의 내부 불일치 | C-Suite 본문은 Type 1 비가역/Type 2 가역인데 타입 예시는 `type1_reversible/type2_irreversible` | 번호 대신 `reversible/irreversible` 사용 권장. 실행 허용은 별도 capability로 판정 |
| P1 | 회의가 고정인지 선택형인지 충돌 | 명세는 4개만 허용한다고 하지만 UI는 프리셋 뒤 참여자 변경 가능, API도 모든 유효 2~3인 조합 허용 | 현재는 `추천 조합 4개`로 설명. 제한 정책 도입은 별도 결정 |
| P1 | 챔버 선택 시 입력 대상 키가 이전 세션 | `selectChamber`가 owner/mode 변경 직후 이전 `key`로 `update` 호출 | 새 세션 키에 문맥을 전달하도록 수정하고 입력 소실·오염 검증. 현재는 정적 추론이며 브라우저 재현 전 |
| P1 | 결과와 입력보다 설정 선택이 앞섬 | Office 렌더 순서: 로스터→소개→챔버→모드→참여자→대화→입력 | 입력과 현재 결과를 우선, 전체 인물·참여자 조합은 펼침 |
| P1 | 자문·실행의 위치 혼합 | `AgentsCouncil`에 `CodexJobsPanel`과 `CouncilCoachPanel`을 함께 렌더 | 실행 작업은 작업·실행 영역, 자문은 Office/코칭으로 구분 |
| P1 | 과거 평가를 최신 프롬프트의 성과로 읽을 위험 | 품질 문서의 18개 결과 이후 persona/playbook 변경이 존재. 현재 버전 상수는 v2 | 정책·모델·평가 시각과 prompt hash를 연결. 현재 성능은 재평가 전 미확인 |
| P2 | 공통 분량 제한의 과도함 | 통합 프레임워크의 600/700자 전체 제한은 실제 산출물·코드·보고서를 훼손할 수 있음. parser answer 상한은 10,000자 | 판단 요약만 짧게, 결과물 본문은 요청 형식에 맞게 분리 |

기존 테스트 통과는 위 의미·UX 문제를 해결했다는 증거가 아니다. 특히 프롬프트에 안전 규칙이 존재하는지 검사하는 것과 실제 답이 실행을 사칭하지 않는지 평가하는 것은 다르다.

## 5. 피치 조정

### 현재 능력에 맞는 한 줄

**“내 업무를 함께 정리하고, 바로 쓸 초안과 다음 행동을 만드는 9명의 역할별 AI 오피스.”**

### 발전 목표를 포함한 설명

“고객 답장, 주간 정리, 콘텐츠, 프로젝트 판단을 각 분야 담당에게 맡긴다. 필요한 근거와 불확실성을 함께 보여주고, 선택한 결과를 기존 업무에 이어 쓸 수 있게 한다.”

두 번째 문장의 업무 연결은 구현 단계에 따라 `연결 예정`과 `사용 가능`을 구분한다. `상위 1%`, `누락 0건`, `인지 부하 1/3`은 지향점으로 유지하되 제품 능력의 실측 주장으로 쓰지 않는다.

| 표면 | 권장 카피 |
|---|---|
| Office 제목 | 이브이 오피스 |
| 설명 | 정리할 일이나 필요한 결과물을 알려주세요. |
| 담당 선택 | 담당: 이브이 · 변경 |
| 회의 모드 | 관점 비교 |
| 챔버 묶음 | 함께 검토하기 |
| 딜 클로징 챔버 | 고객 제안 검토 |
| 빌드·배포 챔버 | 기능·구현 검토 |
| 자원 배분 챔버 | 돈·시간 비교 |
| 주간 정산 챔버 | 이번 주 정리 |
| 인지 방패 Tier 3 | 오늘은 최소한만 |
| 결과 상태 | 초안 생성 · 업무 변경 없음 |

역할별 짧은 피치: 이브이는 “복잡한 요청을 다음 한 걸음으로”, 샤미드는 “끝낼 수 있는 순서와 남길 약속”, 부스터는 “고객의 다음 반응을 만드는 연락”, 님피아는 “내 생각을 내 말로 완성한 글”처럼 산출물로 설명한다. 나머지 전문 역할도 아래 책임표로 같은 방식으로 소개한다.

## 6. 9인의 균형: 동일한 노출량보다 명확한 책임

| 역할 | 책임 질문 | 대표 결과물 | 겹침을 푸는 기준 |
|---|---|---|---|
| 이브이 · 비서실장 | 이번 요청에서 무엇을 결정해야 하나 | 요청 요약·담당·추천·다음 행동 | 이미 담당이 명확하면 재접수 생략 |
| 샤미드 · 운영 | 언제 무엇을 끝내고 무엇을 기다리나 | 실행 순서·대기 조건·주간 정리 | 기능 범위는 글레이시아, 투자 선택은 에브이 |
| 부스터 · 매출 | 이 고객과 어떤 다음 접촉을 하나 | 답장·미팅 목적·연락 결과 입력안 | 금액 해석은 리피아, 독자 대상 글은 님피아 |
| 님피아 · 브랜드 | 누구에게 무엇을 어떻게 전달하나 | 원고·파생 콘텐츠·브랜드 표현 기준 | 개별 딜 협상은 부스터, 범위 결정은 글레이시아 |
| 글레이시아 · 제품 | 무엇이 되면 이번 작업이 끝나나 | 최소 흐름·수용 기준 | 일정은 샤미드, 코드는 쥬피썬더 |
| 쥬피썬더 · 기술 | 실제로 무엇이 동작하고 어디서 실패하나 | 구현 초안·진단·검증 절차 | 코드 실행·수정 결과는 연결된 worker 증거 필요 |
| 에브이 · 전략 | 무엇을 선택하고 무엇을 포기하나 | 추천·기회비용·판단 변경 조건 | 일상 순서 정렬까지 전략 회의로 만들지 않음 |
| 리피아 · 자원 | 돈·시간·유지 부담을 감당할 수 있나 | 기간별 현금·순시간·상한 비교 | 최종 투자 방향은 에브이, 고객 설득은 부스터 |
| 블래키 · 검토 | 이 주장과 약속을 믿을 근거가 있나 | 문제 위치·영향·대체 문장 | 모든 일에 별도 모델 호출을 붙이는 게이트가 아님 |

일상 노출은 이브이·샤미드·부스터·님피아 중심, 제품·기술·전략·자원은 문맥에 따라 등장시키는 것을 권장한다. 블래키의 사실 기준은 공통 품질 규칙으로 적용하되 별도 검토 호출 여부와 구분한다. 이 구분은 인물의 서열이나 능력 점수가 아니다.

말투는 정중한 기본 톤을 공유하고 관찰 지점·결론·산출물에서 차이를 만든다. 친밀한 어투, 단호함, 피로 배려가 실행 사칭·근거 없는 안심·새 과제 부과로 번지지 않게 한다. 최소 업무 모드는 사용자의 선택과 현재 입력을 따르며 정신 상태를 추정해 자동 전환하지 않는다.

## 7. 탭·섹션 배치의 권장 균형

### AI·자동화 영역의 목적 분리

최상위 사이드바를 늘리지 않고 기존 영역 안에서 목적을 정리한다.

| 목적지 | 들어갈 내용 | 비중 조정 |
|---|---|---|
| Office | 자유 요청, 역할별 초안·검토·관점 비교 | 입력과 결과 중심 |
| 작업·실행 | 기존 Orders와 Codex jobs의 구분된 보기 | 상태·실행 대상·결과·실패 처리 중심. 서로 다른 상태 모델을 억지 통합하지 않음 |
| 코칭·관점 | 기존 Guru·브랜드 Council·Legend 진입 | 목적·회사/개인·현재 서비스 표시. Office로 조용히 대체하지 않음 |
| 자동화·실행 기록 | 기존 자동화와 Runs | 연결 상태·실패 영향·재시도 조건 중심 |

새 라벨·그룹은 비교안이며 현재 내비를 변경하지 않았다. 이전 URL·로그 ID·scope 계약을 보존하는 이행이 필요하다. Office 대화 복원·산출물 보관함은 현재 기능이 아니므로 탭부터 만들지 않는다.

### Office 안의 순서

1. **요청**: 현재 범위, 목적/원문 입력, 담당 한 명. 입력만으로 요청 가능.
2. **결과**: 완성된 본문, 다음 행동, 복사/수정 요청. 실제 저장 연결 전에는 적용 완료처럼 표현하지 않음.
3. **근거와 상태**: 참조 범위·누락 자료·생성/로그 저장 여부. 핵심 실패와 미저장 상태는 접지 않음.
4. **선택 설정**: 다른 담당, 모드, 참여자, 최근 프로젝트 참고.
5. **도움 예시**: 업무별 추천 조합. 빈 상태에서만 유용한 것을 짧게 노출.

모든 회의 결과에 소개·답변·추천·근거·이견·다음 행동이 중복 서술되지 않도록, 본문은 결과물, 추천은 선택, 근거·이견은 설명이라는 역할을 나눈다. 요청 하나의 주 행동도 하나로 유지한다.

### 실제 업무 표면

| 탭/섹션 | 기본 도움 | 기본 담당 | 결과가 돌아갈 곳 |
|---|---|---|---|
| 홈의 선택 신호 | 지금 결정할 것 정리 | 이브이 | 해당 신호 상세 |
| 오늘·내 작업 | 남은 시간에 맞추기 | 샤미드 | 기존 실행 목록; 추천만으로 기한 변경 금지 |
| 주간 정리 | 회사/개인 기간별 보고 초안 | 샤미드 | 주간 카드·결과 패널 |
| 문의·고객 연락 | 선택 고객 답장 초안 | 부스터 | 고객 상세·기존 연락 기록 폼 |
| CRM 매출·수금 | 금액과 미확인 조건 설명 | 리피아 | 거래의 금액 상세 |
| CRM 지원·장애 | 처리 순서·진단 준비 | 샤미드/쥬피썬더 | 해당 문의 |
| 프로젝트 진행 | 지연·대기·다음 작업 정리 | 샤미드 | 프로젝트 작업·일정 |
| 프로젝트 기획 | 최소 범위와 완료 조건 | 글레이시아 | 해당 프로젝트의 기획·작업 |
| 프로젝트 기술 작업 | 구현 요청·실패 검토 | 쥬피썬더 | 명시된 job과 결과 |
| 메모 | 선택 원문 정리 | 이브이 | 원문 보존, 선택 결과만 task/Studio 연결 |
| 브랜드 | 독자·약속·표현 기준 정리 | 님피아 | 계속 재사용할 브랜드 기준 |
| 콘텐츠 Studio | 원문을 완성 글로 | 님피아 | 기존 후보·버전·적용·복원 흐름 |
| 기회·목표 | 선택·보류·검증 조건 | 에브이 | 기회 또는 목표의 근거 |
| 비용·자원 | 기간별 현금·순시간 | 리피아 | 근거와 가정을 구분한 비교 |
| 실행 기록·설정 | 연결·실패·재시도 설명 | 쥬피썬더 | 해당 실행·설정 |

일반 페이지에서는 기존 저장·완료 버튼이 주 행동이다. AI 도움은 선택 대상 상세 안에 기본 한 개, 나머지는 더보기로 둔다. 리스트/보드/주간 보기 전환은 같은 업무의 표시 변경이며 새 대화나 모델 호출의 계기가 아니다.

## 8. 비교 가능한 세 가지 발전안

| 안 | 범위·재사용 | 장점 | 부담·위험 |
|---|---|---|---|
| A. 현재 Office 정돈 | 기존 페이지·parser 유지, 카피·모순 예시·설정 순서·세션 전환 수정 | 가장 작은 변경, 바로 사용할 때 혼란 감소 | 업무 문맥 재입력과 결과 복사 부담은 남음 |
| **B. 업무 안의 Office — 권장** | A 이후 검증된 context adapter로 주간 카드→고객 연락→Studio 연결. 기존 저장·command·receipt 재사용 | 운영자 실제 업무에서 한 흐름을 닫고 효과를 비교 가능 | 대상·scope·revision·권한·중복 방지 계약 필요 |
| C. 중앙 오피스 작업대 | 장기적으로 요청·산출물·실행·코칭을 한 작업대에서 탐색 | 복합 업무 추적과 지속 대화에 유리 | 별도 inbox·memory·job을 중복 구축할 위험, 현재 인지 부담을 키울 수 있음 |

B를 권장한다. A를 첫 단계로 포함하고, 중앙 작업대는 실제로 여러 안건을 추적할 필요가 생긴 뒤 투자한다. 이번 검토만으로 B의 전체 구현이나 새 스키마를 확정하지 않는다.

## 9. 개발 순서와 완료 증거

| 단계 | 작업 | 완료 증거 |
|---|---|---|
| 0. 현재 약속 정합성 | 실행 사칭 예시 제거, 성과 표현 교정, 출력 계약 정렬, 정책/평가 버전 추적 | 동일 규칙의 문서·prompt·parser 대조 및 오류 사례 재평가 |
| 1. Office 사용성 | 챔버 세션 키 교정, 요청·결과 우선 배치, 선택 설정 축소 | 작성 중 모드/담당 전환·실패·복귀·scope 변경에서 입력과 결과 대상 보존 |
| 2. 주간 정리 | 명시된 기간·scope의 제한 read adapter | 월요일 개인/목요일 회사 구분, 활동/고객 수 및 수락/완료 보존, 조회 실패 명시 |
| 3. 고객 연락 | 선택 고객 근거→부스터 초안→기존 기록 흐름 | 고객 A 응답이 B에 적용되지 않음, 복사는 발송 아님, 실제 결과만 저장 |
| 4. Studio | 원문 기반 님피아 초안과 기존 후보·적용 연결 | 없는 경험 0건이라는 관찰 기준, 원문 revision 대조·복원 검증 |
| 5. 선택 결과의 업무화 | 검토한 산출물에서 구조화 명령으로 연결 | 같은 요청 재시도에 중복 없음, 영수증과 재조회로 적용 확인 |
| 6. 전문 판단·worker | 프로젝트·전략·자원 및 기술 실행 연결 | 등록 프로젝트·모드·실행 증거·실패 복구, 채팅 생성과 실행 상태 분리 |

이미 허용된 내부 작업마다 별도 승인 큐를 추가하지 않는다. 외부 발송 등은 구체적인 대상·내용·실제 권한을 확인한다. 자연어 `nextAction`을 곧바로 실행 명령으로 변환하지 않는다.

## 10. 기능의 깊이를 평가하는 기준

9명에게 같은 분량과 같은 수의 탭을 배분하지 않는다. 아래 질문을 역할별 대표 시나리오에 적용한다.

- 원문을 다시 설명하지 않아도 필요한 문맥이 전달되는가?
- 답변을 다시 요약하지 않고 사용 가능한가?
- 근거 없는 경험·수치·상태를 만들지 않는가?
- 결과를 원래 고객·프로젝트·콘텐츠에서 이어 쓸 수 있는가?
- 오류·지연·재시도 뒤에도 입력과 결과가 보존되는가?
- 피곤하거나 시간이 없을 때 실제로 업무를 줄이는가?

측정 권장: 요청부터 쓸 수 있는 결과까지 걸린 시간, 큰 수정 없이 사용한 비율, 문맥 재입력 횟수, 결과에서 실제 행동으로 이어진 비율, 미해결 후속 건수, 호출 비용. 모두 지금 자동 계측된 지표라는 뜻은 아니다. 작은 실제 사용 표본으로 기준선을 만든 뒤 목표치를 정한다.

기존 의미 평가의 **18개 생성 / 11개 기준 확인 / 7개 보완 필요**는 당시 평가 기록이다. 현재 변경된 프롬프트의 성적표로 재사용하지 않는다. 우선 기존 7개 실패 유형과 신규 사례를 함께 검토하고, 이름을 바꿔도 답변이 같은지 역할 구별도 확인한다.
