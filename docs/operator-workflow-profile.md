# Moonlight Operator Workflow Profile

> 상태: ACTIVE OPERATING SOURCE — Q1~Q115 정리 완료, 추가 인터뷰 일시 중단
> 마지막 갱신: 2026-07-13
> 근거: 운영자 인터뷰 Q1-Q115, `classinkr-web` Neo CRM 문서, Asana·monday.com 공식 도움말 확인
> 용도: Moonlight의 제품 기획, 우선순위, CRM, 캘린더, PMS, 자동화 작업 전에 읽는 운영 기준
> 후속 설계: `docs/superpowers/specs/2026-07-13-moonlight-personal-operator-os-deep-design.md`

## 1. 문서 사용 규칙

이 문서는 구현 완료 상태나 확정된 제품 사양을 뜻하지 않는다. 아래 표기를 구분해서 사용한다.

- **확정**: 운영자가 직접 설명한 현재 업무 방식 또는 명시적으로 동의한 기준
- **권장**: 인터뷰를 바탕으로 제안된 운영 규칙. 구현 전에 다시 확인할 수 있다.
- **미정**: 아직 답을 얻지 못했거나 정확한 기준이 없는 항목

향후 에이전트와 기획자는 다음 규칙을 지킨다.

1. CRM, 우선순위, 캘린더, PMS, 자동화, 첫 화면을 변경하기 전에 이 문서를 읽는다.
2. **권장** 항목을 운영자의 확정 결정처럼 표현하거나 구현하지 않는다.
3. 추가 인터뷰는 한 번에 정확하고 짧은 질문 5개씩 진행한다.
4. 추가 인터뷰는 현재 중단한다. 운영자가 요청하거나 Phase 1 실사용 결과가 생기면 `Q116`부터 재개한다.
5. 새 답변을 받을 때마다 확정·권장·미정을 분리해 이 문서를 갱신한다.
6. 최초 이관 뒤 Moonlight는 개인 업무 정본으로 사용하고, ClassIn에는 공식 객체·공식 활동 요약만 보낸다. 개인 상세 메모를 복제하지 않는다.
7. 개인 캘린더 URL, 전화번호 등 원본 개인정보는 저장소 문서에 복사하지 않는다.

## 2. Moonlight의 역할과 성공 기준

### 확정

- Moonlight는 운영자 **본인만 사용하는 개인 운영체제**다.
- 판매하거나 다중 사용자 SaaS로 만들 계획은 없다.
- 현재 회사 업무 체계 자체가 아직 정규화되어 있지 않다.
- Moonlight를 통해 달성하려는 결과는 다음 두 가지다.
  - 업무에 쓰는 인지적 에너지를 현재의 약 **1/3 수준**으로 줄인다.
  - 고객 연락과 프로젝트 후속 조치의 누락을 **0건**으로 만든다.
- 자동 기록과 등록은 적극적으로 허용할 수 있다. 개인 전용 도구이므로 캘린더와 내부 기록을 자동 생성하는 것에 거부감이 없다.

### 안전한 해석

- 자동 **등록** 허용을 고객에게 메시지를 자동 **발송**해도 된다는 뜻으로 확대 해석하지 않는다.
- 외부 발송, 결제, 계약, 삭제 등 되돌리기 어렵거나 타인에게 영향을 주는 행동은 별도 결정 전까지 초안·추천·확인 단계를 유지한다.

## 3. 현재 업무 흐름

### 확정

- 업무 확인 순서는 아직 정규화되지 않았지만 현재 생각하는 순서는 다음과 같다.
  1. 할 일
  2. 매출
  3. 메시지
  4. 기획: 프로젝트와 전략
  5. 콘텐츠
  6. 기타
- 이메일은 후순위다.
- 반복적으로 시간과 인지 에너지를 가장 많이 사용하는 일은 다음과 같다.
  - 고객 연락
  - 일정 잡기
  - 고객·매출·행사 데이터 분석
- 새로운 할 일의 주요 유입처는 다음과 같다.
  - 머릿속에서 떠오른 생각
  - Instagram DM
  - 회의
- 선호하는 캡처 방식은 상황에 따라 달라진다.
  - 기본: 짧은 텍스트 메모
  - 급하거나 손을 쓰기 귀찮을 때: 음성
  - 원문이 있을 때: 복사·붙여넣기

## 4. 첫 화면과 우선순위

### 확정

- 첫 화면과 Google Calendar가 주요 알림 표면이다.
- 휴대폰 푸시 알림은 후순위다.
- 고객 관리 용량은 대략 다음과 같다.
  - 정말 중요한 긴급 KA 미팅: 1건
  - 단순 카카오톡 이상의 집중 관리 고객: 3~5명
- 집중 고객에게 필요한 다음 행동의 예시는 다음과 같다.
  - 전화
  - 소개 자료, 리드 마그넷, 매뉴얼, PDF 등의 자료 제작
  - 프로젝트 종료일 또는 다음 단계 독촉과 알림
- 첫 화면의 다음 행동을 누르면 일반 업무는 체크리스트로 이어져야 한다.
- 콘텐츠나 데이터 입력 업무는 해당 제작·입력 화면으로 바로 이어져야 한다.

### 권장

- 첫 화면은 `긴급 KA 1건 + 집중 고객 3~5명`으로 제한한다.
- 각 할 일은 다음 정보를 한눈에 보여준다.
  - 고객명과 소속
  - 지금 해야 하는 이유
  - 정확한 다음 행동
  - 기한
  - 최근 대화 한 줄
  - 보조 정보로 거래 단계와 예상 매출
- 임시 우선순위는 다음 순서를 사용한다.
  1. 기한이 지난 고객 약속
  2. 오늘 확정된 일정
  3. 거래 종료에 가까운 고객
  4. 다음 연락 시점이 지난 고객
  5. 일반 프로젝트와 콘텐츠
- 전환 가능성은 사용자가 숫자를 직접 편집하지 않고 `집중도 높임 / 기본 / 낮춤`처럼 큰 범위만 조정한다.

### 미정

- 모든 업무를 아우르는 최종 우선순위 공식
- 프로젝트·고객·콘텐츠가 같은 날 충돌할 때의 예외 규칙

## 5. 고객·조직·거래 모델

### 확정

- 기본 고객 단위는 **사람**이다.
- 사람은 기관, 회사, 학원 같은 **조직**에 연결된다.
- 한 조직에 여러 담당자가 붙는 경우는 거의 없다.
- 한 고객이 여러 거래를 동시에 갖는 경우도 보통 없다.
- 기존 고객의 재문의는 과거 거래를 다시 열지 않고 **새 거래 기록**으로 만든다.
- ClassIn 회사 업무에서는 Account와 Opportunity 개념을 사용한다.

### 권장 모델

```text
사람(Contact)
  -> 조직(Account)
    -> 거래 건(Opportunity)
      -> 활동 기록(Activity)
        -> 다음 할 일(Task)
```

- 고객·조직과 거래를 분리한다.
- 고객은 과거 관계와 활동을 보존하고, 거래는 문의 또는 구매 시도마다 새로 만든다.

## 6. 영업 단계와 상태

### 확정

- 미팅이 잡히면 정식 리드로 취급하는 편이다.
- 실제 미팅을 마친 뒤 유효 리드인지, Account·Opportunity로 관리할 가치가 있는지 판단한다.
- `진행 중`은 가격 또는 학원 상황에 깊이 연관된 질문이 오가는 **깊은 상담 시작 시점**이다.
- 유효 리드 이후의 대표 흐름은 다음과 같다. 각 단계의 횟수는 달라질 수 있다.

```text
데모 -> 견적 -> 최종 미팅 -> 거래 종료
```

- `클로징`은 거래 종료를 뜻한다.
- 주문 예상 품목은 반복적이며 `HW / SW` 선택형이 적합하다. 주된 차이는 수량이다.

### 권장 분리

서로 다른 개념을 하나의 영업 단계에 섞지 않는다.

- 영업 단계: `잠재 리드 -> 리드 -> 유효 리드/상담 -> 데모 -> 견적 -> 최종 미팅 -> 종료`
- 종료 결과: `성공 / 실패 / 보류`
- 문의 유형: `신규 문의 / 재문의`
- 결제 상태: `미결제 / 부분 결제 / 결제 완료`
- 부분 결제와 상품 구분: `HW / SW`
- 관계 신호: `추가 구매 예정 / 재연락 필요`
- 상품 선택은 `HW / SW + 수량`을 기본으로 하고, 가격·할인 필드는 실제 견적 흐름을 확인한 뒤 추가한다.

### 미정

- 잠재 리드와 리드 사이의 예외 기준
- 거래 성공·실패·보류의 세부 정의
- 견적에서 품목과 수량 외에 반드시 관리할 정보

## 7. KA 고객과 활동 기록

### 확정

- KA 고객은 학원·기관 규모를 기준으로 하며 현재 기준은 **300명 이상**이다.
- 정확한 규모 산정은 학생·교사 수를 참고한다.
- 일반 고객은 활동 횟수와 간단한 메모가 중요하다.
- 간단한 메모에는 고객이 중요하게 생각하는 것과 대화 내용을 남긴다.
- KA 고객은 기본적으로 모든 주요 활동 기록이 필요하다.
- 주요 연락 채널은 메시지와 전화다.
- 고객 연락 할 일을 완료할 때 남겨야 하는 최소 기록은 다음과 같다.
  - 대화 요약 한 줄
  - 고객 반응
  - 다음 행동과 날짜

### 권장

- 거래가 종료되지 않았다면 다음 행동과 날짜를 비워두지 않는다.
- 정확한 날짜가 없을 때는 `기약 없음`을 명시적으로 선택한다.
- `기약 없음`은 삭제가 아니라 낮은 우선순위의 휴면 상태로 둔다.
- 클로징되지 않은 `기약 없음` 고객은 한 달 뒤 다시 확인 대상으로 올린다.

### 미정

- KA 300명 기준이 학생 수, 교사 수, 합산 규모 중 무엇인지
- `기약 없음`의 추가 하위 유형. 현재 확인된 유형은 “구매 가능성은 있지만 시점을 알 수 없음”이다.

## 8. 전환과 집중 고객

### 확정

- 현재 말하는 1차 전환 성공은 구매가 아니라 다음 행동을 고객이 수락하는 것이다.
  - 실제 미팅 또는 방문 데모 수락
  - 쇼룸 초대 수락
- 결제까지의 거래 성공률도 별도로 확인해야 한다.
- 전환 가능성이 높은 신호의 현재 우선순위는 다음과 같다.
  1. 고객이 자진해서 쇼룸 방문
  2. 방문 데모 요청
  3. 자세하고 빈도 높은 문의
  4. 자기 학원에 맞춘 구체적인 질문
  5. 세미나와 행사에 반복 참석
- 가격 질문도 관심 신호로 언급되었지만 최종 우선순위에서의 위치는 미정이다.
- “전환 가능성 수”는 날짜 기반 매출 예측보다, 가능성이 높아 지금 연락하고 집중해야 하는 고객 수를 뜻한다.

### 권장 지표

- 접촉 전환율: 잠재 리드 또는 리드 중 미팅·데모·쇼룸 방문을 수락한 비율
- 거래 성공률: 유효 리드 또는 Opportunity 중 결제 완료된 비율
- 집중 고객 수: 현재 전환 가능성이 높고 다음 행동이 필요한 고객 수
- 처음에는 최근 30일과 이전 30일을 비교하고, 실제 사용 후 기간 단위를 조정한다.

### 미정

- 접촉 전환율의 정확한 분모. 미팅이 잡힌 리드와 미팅 후 유효 리드가 모두 언급되었다.
- 전환율의 최종 기간 단위
- 집중 고객 점수의 가중치와 자동 산정 데이터 원천

## 9. 일정 관리

### 확정

- 개인 일정과 회사 일정을 하나의 Google Calendar에서 함께 관리한다.
- 일반적인 일정 확정 흐름은 다음과 같다.

```text
메시지 확인 -> 캘린더 확인 -> 가능 시간 제안 -> 확정 일정 등록
```

- 일정 제목에 고객명이나 조직명을 적어야 하지만 실제로 자주 누락한다.
- 쇼룸 예약은 별도 예약 도구가 없고, 주로 구두로 정한 뒤 캘린더에 남기는 수준이다.

### 권장

- 고객 또는 할 일에서 일정을 만들면 제목을 자동 생성한다.

```text
[조직명] 고객명 · 미팅 목적
```

- 미팅 상태는 `예정 / 일정 변경 / 취소 / 노쇼 / 완료`로 구분한다.
- 취소와 일정 변경에는 짧은 이유만 선택적으로 남긴다.

### 미정

- 일정 변경·취소·노쇼 이후 자동으로 생성할 다음 행동
- 캘린더 이벤트와 Neo CRM 고객을 매칭하는 확정 규칙

## 10. 행사와 데이터 분석

### 확정

- 분석 대상은 고객, 고객 기록, 매출, 행사별 결과다.
- 분석은 정형화된 결정보다 자잘한 고객 접근과 다음 타겟 전략에 참고하는 용도다.
- 행사는 세미나, 컨퍼런스, 프로모션 등을 포함한다.
- 보고 싶은 정보는 행사 참석 횟수, 플랫폼별 미팅 횟수, 결정 데이터다.
- 행사 참석자 데이터는 현재 스프레드시트로 마구잡이 수집한다.
- 기본 필드는 이름, 기관, 전화번호 정도이며 나머지는 주관적인 기준이 많다.

### 권장

- 행사 스프레드시트는 붙여넣기 또는 가져오기로 캡처하고, 전화번호와 조직·이름을 이용해 기존 고객에 매칭한다.
- 자동 매칭이 불확실한 행은 신규 고객을 바로 만들지 않고 검토 대상으로 둔다.
- 행사 참석은 고객 활동 기록에 누적하고, 반복 참석은 집중 고객 신호로 사용한다.

### 미정

- “플랫폼별”의 정확한 분류 체계
- 행사별 결정 데이터의 표준 필드
- 행사 데이터에서 자동 생성할 후속 조치와 기한

## 11. 자료 제작과 PMS

### 확정

- 고객을 위한 정형화된 자료 제작 체계는 아직 없다.
- 현재 활용 가능한 자료는 운영자가 만든 리드 마그넷과 회사 내부 자료다.
  - 회사 소개 자료
  - 매뉴얼
  - PDF
- 프로젝트 종료일을 관리하는 별도 체계가 없다.
- Moonlight 안에 PMS 도구와 비슷한 프로젝트 관리 흐름을 만들고 싶다.
- PMS는 고객 거래 프로젝트만이 아니라 내부 업무, 콘텐츠, 전략 등 **모든 프로젝트**를 관리한다.
- 현재 확인된 상위 프로젝트 분야는 다음과 같다.
  - 영업
  - 마케팅
  - 콘텐츠
  - IT
  - AI 기반 서드파티 개발
  - 개인 프로젝트
- 모든 프로젝트는 공통 진행 단계를 사용하고, 프로젝트 분야별 세부 단계를 추가한다.
- 공통 진행 단계는 `수집 -> 계획 -> 진행 -> 대기 -> 완료`이며, `보류 / 취소`는 별도 종료·중단 상태로 둔다.
- 유효 리드에 Opportunity가 생성되면 연결된 **영업 프로젝트 후보를 자동 생성**하고, 운영자가 확인하면 활성 프로젝트로 전환한다.
- 개인 프로젝트는 Moonlight에만 보관하며 ClassIn으로 보내지 않는다.
- 단순 활동도 관련 활동량, 빈도, 반복 징조가 시스템 기준을 넘으면 프로젝트 생성 후보가 된다.
- 프로젝트 후보의 초기 자동 감지 기준은 다음 세 가지로 시작한다. 어느 하나를 충족하면 후보가 된다.
  1. Opportunity가 생성됨
  2. 가격·견적과 관련된 구체적인 대화가 발생함
  3. 같은 고객 또는 주제로 미팅이 2회 이상 발생하거나, 14일 안에 관련 활동이 3회 이상 누적됨
- 자동 감지 결과는 프로젝트를 즉시 활성화하지 않고 **후보함의 추천**으로 보여준다.
- 관련 고객·활동 화면에서도 “프로젝트로 관리할까요?” 형태의 추천 툴팁을 표시할 수 있다.
- 프로젝트는 시스템의 자동 감지뿐 아니라 운영자가 직접 만들 수 있다.
- 거래 성공 뒤 납품·온보딩 프로젝트는 항상 만들지 않는다. 필요 여부를 운영자에게 확인하거나 운영자가 직접 생성한다.
- 종료일이 없는 프로젝트는 한 달마다 다시 검토하고, 분기 리뷰에서도 모아서 정리한다.

### 프로젝트 기본 화면

- 프로젝트 추천은 첫 화면에 요약으로 먼저 보여주고, 관련 고객 화면에서 추천 근거를 자세히 보여준다.
- 지금 해야 할 일
- 특이사항과 위험 신호
- 프로젝트 마감일과 지연 정도
- 프로젝트 내부 투두리스트
- 진척과 활동량을 보여주는 간단한 시각화

### 프로젝트 진척 계산 원칙

- 체크리스트 완료율, 완료된 작업 수, 마일스톤처럼 확인 가능한 **정량 데이터가 우선**이다.
- 고객 프로젝트에는 다음 정성 평가를 보조 지표로 붙인다.
  - 고객이 목표 상태에 얼마나 접근했는가
  - 고객이 제품이나 제안을 얼마나 이해했는가
  - 실제 도입·구매 의향이 있는가
- 정성 신호도 가능한 범위에서 관찰 가능한 데이터로 근거를 남긴다.
  - 회의 중 핵심 단어와 긍정 표현
  - 메시지 횟수
  - 전화·미팅 등 컨택 횟수
  - 가격 문의
- 초기 진척률은 **정량 데이터 70% + 고객 반응 30%**로 시작한다.
- 구체적인 세부 가중치와 트래킹 방식은 실제 데이터를 보며 조정한다.

### 음성·메시지 분석 원칙

- 회의 메모, 음성, 복사한 메시지에서 관심 신호를 추출하는 기능은 사용할 수 있다.
- 외부 AI API 비용이 발생하므로 모든 기록을 분석하는 핵심 기능으로 삼지 않는다.
- 기본 시스템은 체크리스트, 활동 횟수, 날짜, 직접 입력한 메모처럼 비용이 낮은 구조화 데이터를 우선 사용한다.
- 모든 고객 미팅을 중요한 미팅으로 간주한다.
- 고객 미팅은 음성 인식과 관심 신호 추출의 우선 대상이다.
- 중요한 미팅을 위해 음성 파일 입력, 전사, 요약, 신호 추적의 기반은 초기부터 준비한다.
- 자동 분석 결과는 사실로 확정하기 전에 운영자가 확인할 수 있어야 한다.
- 지원할 초기 입력 경로는 다음 두 가지다.
  1. Moonlight에 직접 넣는 음성 녹음
  2. 다른 녹음 도구에서 추출한 전사 텍스트 파일
- 음성 원본은 30일 뒤 삭제하고, 전체 전사문과 요약은 계속 보관한다.
- 고객 미팅 분석은 다음 결과를 만든다.
  - 요약
  - 결정사항
  - 고객 우려
  - 관심 신호
  - 다음 행동
- AI 분석은 운영자가 직접 누르는 분석 버튼으로 실행한다.
- 월별 AI 분석 비용과 사용량을 화면에서 확인할 수 있어야 한다.

### 지연 위험 표시 원칙

- 모든 프로젝트에 같은 지연 기준을 적용하지 않는다.
- 프로젝트 중요도와 위험도는 `핵심 / 중요 / 일반` 3단계로 나눈다.
- `핵심` 프로젝트는 일 단위로 확인하고 **하루 지연부터 위험**으로 표시한다.
- `일반` 프로젝트는 주 단위로 확인하고 **일주일 지연부터 `지연·관심 필요`**로 표시한다. 바로 위험으로 격상하지 않는다.
- `중요` 프로젝트의 정확한 확인 주기와 위험 전환 기준은 아직 정하지 않았다.

### 병목 분류

- 고객 응답
- 내부 작업
- 의사결정
- 자료 부족
- 외부 일정

### 월간 리뷰

- 프로젝트 전체 진척 상황
- 기준 마감일 대비 지연 정도
- 최근 활동량과 활동 진척
- 현재 상태에서 마무리될 가능성
- 막혀 있는 지점과 다음에 풀어야 할 병목

### 분기 리뷰와 클로징

다음 신호가 지속되는 프로젝트는 계속 유지하지 않고 클로징 후보로 올린다.

- 연락 빈도가 지나치게 낮음
- 미팅과 활동에서 실질적인 진척이 없음
- 고객 또는 관계자의 관심이 없음
- 학원·기관의 니즈와 해결책이 맞지 않음
- 실제 활용 가능성이 낮거나 가망이 없음

클로징된 프로젝트에 새 활동이 생기면 다음 원칙을 적용한다.

- 대부분, 운영자 추정 약 90% 이상의 새 활동은 같은 고객 아래 **새 프로젝트**로 만든다.
- 과거와 동일한 문제가 다시 발생한 경우에는 기존 프로젝트를 다시 열고 재발 기록을 추가해 기간을 연장한다.
- 새 프로젝트는 이전 프로젝트를 관련 이력으로 연결한다.

### 프로젝트 기본 정보

- 프로젝트 제목
- 분야
- 목표 결과
- 종료일 또는 `종료일 없음`
- 다음 행동
- 관련 고객. 고객과 무관한 프로젝트에서는 비워둘 수 있다.

### 미정

- 영업·마케팅·콘텐츠·IT·서드파티 개발·개인 프로젝트의 분야별 세부 단계
- 활동량·빈도 기반 프로젝트 후보 기준의 실제 운영 후 튜닝
- 프로젝트 후보를 보여줄 정확한 화면 위치와 후보 만료 규칙
- 분야별 종료 조건과 마감 자동 계산 규칙
- 고객 질문이나 거래 단계에서 어떤 자료 제작 프로젝트를 자동 추천할지
- 진척률, 활동량, 완료 가능성, 지연 위험의 계산 방식
- 회의·메시지에서 정성 신호를 추출하고 검증하는 방법
- 음성 녹음과 전사 과정의 화자 구분, 수정 흐름, 실패 시 수동 입력 방식
- 월별 API 비용 경고선과 분석 횟수 한도

### PMS 제품 레퍼런스 원칙

- **Asana 참고**
  - `My Tasks`처럼 여러 프로젝트의 개인 할 일을 오늘의 작업대로 통합한다.
  - 기한 임박·지연 규칙으로 업무를 `나중 / 예정 / 오늘`에 자동 승격한다.
  - Portfolio처럼 프로젝트의 상태, 진행률, 종료일, 위험을 한 화면에서 본다.
- **monday.com 참고**
  - 일상적인 단순 업무와 목표·작업·기한이 있는 구조화된 프로젝트를 분리한다.
  - 상위 프로젝트 현황과 프로젝트 내부 세부 작업을 분리하되 연결한다.
  - Opportunity나 활동 기준이 충족되면 템플릿 기반 프로젝트를 자동 생성한다.
  - 프로젝트 간 의존성, 기한 경고, 분야 통합 대시보드를 참고한다.

## 12. 콘텐츠 운영

콘텐츠는 초기 업무 우선순위에 포함되며, 현재는 정해진 발행 일정이나 정규화된 제작 파이프라인보다 아이디어와 몰입 시점에 따라 움직인다.

### 현재 확인된 사실

- 고객 질문과 영업 활동에서 자료 제작 필요가 발생할 수 있다.
- 현재 재사용 가능한 자산은 리드 마그넷, 회사 소개 자료, 매뉴얼, PDF 등이다.
- 콘텐츠 또는 입력 할 일은 체크리스트에서 해당 제작·입력 화면으로 바로 이어져야 한다.
- 콘텐츠 아이디어의 주요 발생 경로는 다음 두 가지다.
  1. 일상에서 문득 떠오르는 아이디어
  2. 비슷하거나 재미있는 영상을 보고 자신의 주제와 연관 지어 떠올린 아이디어
- 주요 발행 채널은 Instagram, Threads, YouTube Shorts다.
- 현재는 Threads 콘텐츠의 비중이 가장 크다.
- 실제 제작 흐름은 다음과 같다.

```text
아이디어 발생 -> 우선 저장 -> 시간 여유나 몰입이 생길 때 선택 -> 제작 -> 다듬기 -> 발행
```

- 콘텐츠 제작에서 인지 에너지를 많이 쓰는 순서는 대체로 다음과 같다.
  1. 어떤 아이디어를 만들지 결정
  2. 실제 제작
  3. 다듬기
- 확인할 성과 신호는 공유 수, 답글·문의 수, 조회 수다.
- 조회 수가 높아지면 공유와 답글·문의도 함께 증가하는 경향이 있다고 본다. 따라서 조회 수는 도달의 선행 신호로 사용하되, 공유와 문의도 별도로 추적한다.
- 떠오른 아이디어는 현재 메모장 또는 Threads 내부 임시 저장에 남긴다. 여러 곳에 흩어져 있어 효율적이지 않다고 느낀다.
- 다음 제작 아이디어는 정형화된 점수보다 운영자의 직감과 **지금 바로 만들 수 있는가**를 기준으로 고른다.
- 콘텐츠는 하나의 원본 아이디어를 여러 결과물로 재생산하는 방식을 지향한다.
  - Threads 글로 변환
  - Instagram용 재구성
  - YouTube Shorts용 영상화
  - 이미 만든 결과물을 잘라 짧은 파생 콘텐츠로 제작
  - 같은 원본을 다른 관점과 형식으로 재가공
- Threads는 하루 2~3개까지 만들 수 있다고 느끼지만, 현재는 많을 때 하루 1~2개이며 지속되지는 않는다.
- 개인 브랜드와 ClassIn 회사 콘텐츠를 나누는 절대 규칙은 없고, 최종 채널은 운영자가 선택한다.
- 다만 현재의 암묵적인 톤 기준은 다음과 같다.
  - 개인 채널: 더 강하고 편하며 러프한 표현과 제작 방식
  - 회사 채널: 기능 중심, 포멀한 설명, 공식 채널에 맞는 표현
- 모든 콘텐츠 아이디어는 Moonlight의 **단일 콘텐츠 아이디어함**으로 모은다.
- 아이디어를 저장할 때의 초기 최소 정보는 다음과 같다.
  - 아이디어 원문
  - 참고 링크
  - 떠오른 이유
  - 추천 채널
- 다음 제작 대상을 위한 복잡한 점수·분석 추천은 초기에는 필요하지 않다. 운영자의 직감과 즉시 실행 가능성이 우선이다.
- Threads는 **하루 1개**를 기본 목표로 두고, 여유와 몰입이 있을 때 추가 발행한다.
- ClassIn 회사 채널 콘텐츠는 별도 승인자가 없으며 운영자가 직접 판단하고 발행한다.

### 후속 범위

### 동기화 단계와 원칙

- 초기에는 직접 등록하거나 웹훅으로 연결한다.
- ClassIn 쪽 시스템과 연동이 완성되지 않았으므로, 초기부터 모든 세부 필드와 자동화를 완전히 맞추지 않는다.
- 시스템이 안정되면 Moonlight에서 등록할 수 있는 공식 기록을 점진적으로 자동 등록한다.
- ClassIn에서 Moonlight로 가져오는 동기화는 별도의 **동기화 버튼**으로 실행한다.
- 역방향 동기화는 Moonlight에 없는 기록만 가져오는 **missing-only import**를 기본으로 한다.
- 기존 Moonlight 기록을 ClassIn 값으로 자동 덮어쓰지 않는다.
- 양쪽에 같은 기록이 있지만 내용이 다르면 자동 병합하지 않고 **비교 대상**으로 보여준다.
- 다른 담당자가 운영자 고객에게 활동을 추가한 드문 경우를 동기화 버튼으로 보충한다.
