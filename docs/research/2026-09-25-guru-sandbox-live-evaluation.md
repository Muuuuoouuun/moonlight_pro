# Guru 샌드박스 실응답 평가 — 2026-09-25

> 범위: 격리 개발 브랜치의 Hub → Engine → Gemini 질문 생성 경로와 멘토 서가 UI. 서울 운영 DB·운영 배포는 건드리지 않았다. 질문은 모두 가상 연습 사례이며 실제 고객 성과를 뜻하지 않는다. 앞선 코드·디자인 점검은 `2026-09-25-guru-objective-evaluation.md`에 있다.

## 실행 조건과 관찰

- 로컬 Hub `127.0.0.1:3188`와 Engine `127.0.0.1:3189`를 별도 샌드박스 Supabase에 연결했다. Hub 영업 원장은 `live` 봉투로 읽혔고 Engine의 Guru 생성기는 설정된 상태였다. 모델 응답에는 `gemini-3-flash-preview`가 기록됐다. 샌드박스와 서울 운영 DB의 주소가 서로 다름을 확인했다.
- 브라우저에서 `코칭·대화 → 멘토 찾아보기 → MEDDIC → 선택한 관점으로 질문 쓰기`를 실행했다. 입력 창을 여는 것만으로 생성은 시작되지 않았고, 가상 질문을 **전송**한 뒤에만 실제 답변이 도착했다. 이른 단계의 MEDDIC 적용을 “시기상조”라고 판단했다.
- 동일한 다섯 가상 사례를 수정 전 한 번씩 생성했다: GAP 카드 선택/미선택, 제안 전 MEDDIC, 제안 후 내부 검토 MEDDIC, 계약 전 Girard. 모두 HTTP 200 `generated`였고, 응답 시간은 7.2~10.5초(중앙값 7.8초)였다. 5건 모두 `agent_runs`에 기록됐으며 각 실행의 `emitted_count`는 0, 연결된 `work_orders`는 0건이었다. 실행 시각 전후의 Guru `project_updates`도 0건이었다. `project_updates`에는 실행 ID가 없어 후자는 시간 범위 확인이다.

## 원인과 적용한 수정

1. 질문 프롬프트와 상위 멘토 지침이 함께 3단 출력을 강제했다. `open-question`은 운영자가 요청한 형식·분량을 우선하고 카드의 `써볼 때`를 먼저 대조하도록 바꿨다. 연결된 고객 기록이 **제공되지 않은 것**과 원장에 **존재하지 않는 것**을 구분하도록 했다.
2. 범위 없는 카드 질문에 ClassIn 원장 전체와 과거 Guru 생성 답변이 들어가 다른 고객·다른 카드의 내용이 현재 질문에 섞일 수 있었다. 카드에서 시작한 질문에는 원장 연결 상태만 전달하고, 일반 자유 질문에는 ClassIn 범위로 필터된 원장을 유지한다. 과거 전역 `agent_runs` 조언은 자유 질문 입력에서 제외했다.
3. 상위 지침의 업종 예시와 매번 “거장 팁”의 출처를 붙이라는 문구가 근거 없는 업종·인물 귀속을 유도할 수 있었다. 연결 고객이 없는 자유 질문의 업종 예시는 제거하고, 카드가 없으면 인물·책 출처를 새로 붙이지 않도록 했다. 카드 프레임에는 검수된 예시 질문을 함께 제공하고, 추천 상황이 Moonlight 편집 기준임을 명시했다.

| 제안 후 MEDDIC | 선택 기준을 확인하는 질문 한 개를 냈다. 다만 승인권자에게 보고하는 단계가 있다는 표현은 입력만으로 확정할 수 없어 질문 문구 개선 여지가 있다. |
| 계약 전 Girard | 계약 후 원칙을 보류했다. 자동 연락 주기나 업무 등록은 만들지 않았다. |

| 카드 없는 GAP 상황 | 가장 최근 재실행에서는 특정 업종이나 인물 출처를 새로 붙이지 않았고 관심의 배경을 묻는 질문을 냈다. |

출처의 큰 틀은 [MEDDICC 창안 경위](https://meddicc.com/resources/who-created-meddic), [Keenan의 GAP Selling 소개](https://salesgrowth.com/gap-selling-book/), [Joe Girard의 고객 관계 글](https://www.joegirard.com/posts/keep-in-touch-with-your-customers/)과 대조했다. 이 확인은 카드의 모든 응용 문구나 모델의 각 문장을 원전이 직접 보증한다는 뜻은 아니다.

수정 직후 다섯 사례의 응답 길이는 427~581자로 낮아져 모두 600자 아래였다. 맥락 입력을 더 좁힌 뒤 GAP 카드 선택/미선택을 다시 실행한 두 답변은 각각 345자·278자였다. 이후 내부 맥락 경계를 답변에 불필요하게 노출하지 않도록 지침을 조정했다. 마지막 자유 질문 재실행은 **118자, 질문 하나와 이유 한 문장**으로 응답했다. 이는 단일 생성 사례이므로 형식 준수율을 보증하지 않는다.

## 추가 연결 점검

- 마케팅·콘텐츠 카드 질문도 참조 브랜드 없이 전역 브랜드 기록을 넘기지 않도록 수정했다. 같은 가상 질문 두 건을 다시 생성한 결과 모두 HTTP 200이었고, 이전에 나오던 “원장 데이터상 실제 독자 반응 기록이 존재하지 않는다”는 전체 원장 부재 단정은 재현되지 않았다. 마케팅 답변은 먼저 고객 언어를 확인하라고 했고, 콘텐츠 답변은 입증되지 않은 수치 제목의 사용을 보류했다. 응답은 각각 314자·427자였으며, 콘텐츠의 “짧게 판단만” 요청에는 여전히 과하게 길었다.
- Hub 대화 화면에서 가상 질문을 보낸 다음 “방금 제시한 질문을 절반 길이로” 요청했다. 새 버전에서는 같은 채팅의 이전 문답만 Engine에 전달하며, 실제 두 번째 답변은 직전 질문을 줄여서 제시했다. 다른 채팅의 과거 `agent_runs`는 질문 맥락에 넣지 않는다. 대화 이력은 최대 3쌍으로 제한하고 생성 답변은 원장 사실로 취급하지 않는다.
- 대화 화면의 Guru 모델 표시는 고정된 “Gemini 3.1 Pro (Thinking)” 대신 요청 전 “요청 시 연결”, 생성 후 실제 응답 모델 ID로 바뀌었다. 환영 인사에는 태스크 등록 버튼을 보이지 않게 했다. 실제 생성 답변의 태스크 버튼은 사용자가 누를 때만 동작한다.
- 독립 코드 리뷰에서 질문이 `deal-review`로 전송될 수 있는 고객 위젯과 `open-question` 딥링크의 잘못된 모드 전환을 발견해 수정했다. 고객 카드 질문은 `open-question`으로 보낸다. 고객 ID가 있으면 정확히 일치하는 ClassIn 기록과 같은 회사 ID의 ClassIn 거래·리드만 최대 5건씩 제공하고, 회사 단위 연결을 선택 리드의 거래로 단정하지 않도록 경계를 표시한다. 카드 없이 이어 묻는 고객 질문도 같은 범위를 유지한다. 고객 ID가 없는 카드 질문은 원장을 읽지 않고 검수된 카드 출처만 사용한다. 딥링크는 카드 관점을 입력창에 준비하고 생성 없이 기다린다. 모든 Guru 자문 모드가 `project_updates`를 쓰지 않도록 Engine의 기록 경로를 끊고, 생성 이력은 `agent_runs`와 연결·실행 진단 로그에 남긴다. 실제 샌드박스 `deal-review` 1회에서 HTTP 200, 실행 ID 존재, `mentorUpdate: null`을 확인했다. 작업지시서는 명시적인 수동 태스크 동작 또는 별도 승인 흐름에서만 만든다.
- 선택한 Keenan 카드를 딥링크로 열어 가상 질문을 보낸 뒤 “방금 질문을 더 짧게”라고 물었다. 첫 답변과 후속 답변 모두 GAP Selling 관점을 유지했고, 별개 주제로 전환한 세 번째 질문에는 Keenan을 붙이지 않았다. 이전 카드 ID는 완료된 현재 채팅의 문답과 함께 제한적으로 전달하며, Hub와 Engine이 같은 명시적 참조 규칙으로 판단한다.
- Guru 위젯에서 인물 렌즈를 선택한 토의는 별도의 `persona-chat` 경로를 사용한다. 이 경로가 쓰던 홈 업데이트도 위젯의 대화 전용 요청에서는 만들지 않도록 분기했다. 고객 위젯의 인물 렌즈 질문은 화면의 선택 고객 필드만 넣고 최근 거래 15건과 전역 RAG 메모는 읽지 않는다. 카드 선택은 첫 전송 뒤 해제하고, 명시적인 후속 참조만 제한된 대화 이력에서 복원한다. 위젯에 보이던 Carnegie·Hill 렌즈도 Engine의 실제 허용·지침 목록에 연결했다. 빠른 딜 진단에서는 인물 렌즈 선택기를 숨겨 명시된 진단 모드가 일반 대화로 바뀌지 않게 했다. 일반 페르소나의 주간 보고 기록 동작은 유지한다. 이 추가 수정은 코드 테스트로 확인했으며, 별도의 실고객 인물 렌즈 생성 평가는 아직 하지 않았다.
- 샌드박스 홈의 기존 `Work` 항목 2건은 이번 Guru 질문에서 생성된 항목이 아니다. 이 항목의 삭제 범위는 운영자 확인이 필요해 그대로 두었다.
- 이번 샌드박스의 영업 원장 4개 리드·4개 거래는 모두 개인 범위로 표시되고 ClassIn 계정은 0건이다. 그래서 **고객 ID로 연결된 ClassIn 실사례 응답**은 아직 실생성으로 검증하지 못했다. ID 일치·개인 범위 차단·연결 기록만 전달하는 경로는 테스트로 검증했다.

## 판정과 다음 품질 게이트

- **개발 샌드박스 사용:** 가능. 멘토 출처 열람·명시적 질문·기록 경로는 동작하고, 확인한 다섯 실행에서 자동 업무 생성은 없었다.
- **실제 고객 판단 품질:** 미검증. 샌드박스 기록은 실고객의 단계·발언·결정 기준을 충분히 대표하지 않는다. 이번 사례는 단회 가상 생성이라 오류율이나 운영 성과를 추정할 수 없다.
- **응답 형식:** 개선됐지만 안정성은 미검증. 자유 질문 마지막 한 건은 요청한 형식을 지켰으나 콘텐츠 카드 한 건은 여전히 장황했다. 반복 생성과 길이·출처·적용 시기 검증 게이트가 필요하다. 원장에 연결된 실제 고객 사례를 평가할 때는 고객 ID·발언 원문·제안 단계의 근거를 함께 기록하고, 그 근거 밖의 주장을 결함으로 세어야 한다.
- **대화 연속성:** 같은 채팅의 후속 질문은 실화면에서 동작했다. 이력은 브라우저 세션의 현재 채팅에 한정되어 새 대화·새로고침을 넘는 영속 기억이 아니다.
- **범위 밖 자동화:** `followup-autopilot`과 `revenue/stalled-scan`은 현재 Vercel 크론 목록에 없고 저장소 내 자동 호출처도 확인되지 않았다. 다만 인증된 수동/외부 호출은 각각 Guru 후속 작업 최대 3건·5건을 승인 대기에 만들 수 있다. 별도의 콘텐츠 크론은 매일 실행 설정이 남아 있어 콘텐츠 작업 대기를 새로 만들 수 있다. Guru 조언 답변 경로를 막은 것과 전체 작업 큐를 비우는 것은 별개다.

이 결과만으로 운영 배포를 권하지 않는다. 실제 고객의 채택·무시·수정 여부를 보기 전에는 카드 조회 수나 단회 응답을 “도움이 됐다”는 지표로 취급하지 않는다.
