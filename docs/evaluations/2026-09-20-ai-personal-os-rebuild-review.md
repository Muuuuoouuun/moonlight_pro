# AI 개인 비즈니스 OS — 보강·재구축 검토

> 작성일: 2026-09-20 · 상태: **검토안 / 신규 제안은 미확정**
> 범위: 첨부 구상, 운영자 확정 기준, 현재 코드의 연결 지점을 비교한 제품 검토. 구현·배포·운영 데이터 측정 결과가 아니다.
> 관계: 기존 승인 설계와 실행 순서를 대체하지 않는다. 이번 요청의 OKR·KPI 필요성은 반영하되 목표 숫자·자동 실행 권한은 새로 확정하지 않는다.
> 조사 기준: 분리 워크트리 생성 시점 커밋 `a3b2938`. 공유 작업 공간의 미커밋 변경은 가져오지 않았다.

## 1. 판단

**기존 Moonlight를 보강해, 신뢰할 수 있는 업무 시스템 위에 교체 가능한 AI 기능을 붙이는 방향을 권장한다.**

AI를 많이 호출하는 것보다, 같은 품질의 결과를 내기 위해 사람이 입력·탐색·정리·검수하는 시간을 줄이는 것이 목표다. 사용자는 전략·창작·고객 대화에도 참여한다. “최종 승인만 하는 사람”을 강제하면 초기 사업에 필요한 현장 학습을 잃을 수 있다.

다만 AI를 마지막에 붙이는 장식 기능으로 취급해서도 안 된다. 지금부터 업무 데이터에 출처·시각·연결 대상·변경 이력·실행 결과를 남겨야 나중의 AI가 정확히 읽고 행동한다. **기록·권한·실행·측정 계약은 먼저, 추론과 자동화 수준은 점진적으로** 확장한다.

| 접근 | 장점 | 비용·한계 | 판단 |
|---|---|---|---|
| 기존 OS 보강 + 업무별 AI | 현재 원장·화면 재사용, AI 중단 시 수동 운영, 문제 위치 추적 가능 | 기존 집계·연결 결함을 먼저 교정해야 함 | 권장 |
| 에이전트 군집 중심 전면 재구축 | 탐색·기획의 자율성을 넓힐 수 있음 | 호출·검수·실패 복구 비용, 재이관 부담. 현재 병목보다 큰 작업 | 반복 업무 성과가 입증된 부분에 한정 |
| 외부 SaaS 조합으로 운영 교체 | 개별 캡처·투두 기능을 빨리 사용할 수 있음 | 개인/회사 경계와 업무 이력을 다시 연결해야 함 | 특정 입력 채널이 부족할 때만 보완 |

이 비교는 설계 판단이다. 비용·시간 절감 실측이나 공급업체 성능 비교가 아니다.

## 2. 원문에서 유지할 것과 고칠 것

| 원문 구상 | 보강 방향 |
|---|---|
| 지식·맥락 계층 | 유지. 업무별 정본, 출처, 최신 확인일, 개인/회사 범위, 사실/가설/제안을 함께 관리 |
| 다중 에이전트 군집 | 리서치·작성·검수는 먼저 **역할/단계**로 구현. 각 역할마다 상시 실행 에이전트가 필요한 것은 아님 |
| 이벤트 기반 자동화 | 유지. 한 사건의 중복 접수·실행 실패·재시도·처리 완료 근거를 먼저 정의 |
| Critic이 품질 보장 | AI 검수는 보조. 사실 출처 검사·형식 검사·수치 재계산·사람의 표본 검토를 결합 |
| 수정 차이로 프롬프트 자동 갱신 | 수정 이유를 모아 규칙 변경 **후보**를 만들고, 이전 사례 재평가 후 버전 적용·되돌리기 |
| 사람은 승인만 | 전략·고객 대화·독자적 관점 형성도 사람의 역할. 승인만으로 새 일이 끝없이 유입되지 않도록 제한 |
| 오전 15분·오후 10분 | 운영 목표로 시험하되 보장하지 않음. 건수보다 실제 검토 시간과 적체를 측정 |
| Action KPI를 채우면 결과 달성 | 행동은 결과를 만들기 위한 가설. 시장·제안 적합성, 표본 수, 전환 지연을 함께 판단 |
| 생산성 400%, 누락 0% 달성 | 400%는 검증 전 기대치. 누락 0은 기존 운영 목표이며 관측 범위와 수집 누락도 따로 검사 |
| 문의 후 48시간 내 클로징 | 최초 응대·다음 행동 확정과 계약 체결은 별개. 영업 주기를 임의로 압축하지 않음 |
| 일정 기간 무접촉이면 모두 알림 | 운영자가 선별한 고객·약속한 다음 연락일 우선. Q117의 자동 범람 방지 원칙 유지 |
| 모든 플랫폼에 동일 유지율·저장률 기준 | 채널·형식·영상 길이·관측 기간별 비교. 원문의 60%·65%·3%를 공통 합격선으로 채택하지 않음 |

MCP는 도구 호출을 연결하는 인터페이스다. 실시간 동기화, 데이터 정합성, 저장 완료를 자동으로 보장하는 계층으로 설계하면 안 된다.

## 3. 권장 작동 구조

```text
방향: 브랜드·오퍼·OKR·시간/비용 한도
                      ↓
기본 업무: 캡처 → 원장 저장 → 다음 행동 → 실행 → 결과 기록
                      ↕
AI 보조: 문맥 찾기 → 요약/초안/비교 → 근거·검수 → 후보 제시
                      ↓
실행 제어: 권한 확인 → 필요한 승인 → 작업 수행 → 결과 확인
                      ↓
학습: KPI 집계 → 병목 가설 → 다음 실험·이번 주 계획
```

### A. 방향과 자원

브랜드마다 대상, 해결 문제, 제안, 톤, 금지 표현, 좋은 결과물 예시를 짧게 정한다. 개인 사업의 오퍼에는 제공 범위·완료 조건·가격 정책·실제 납품에 드는 시간도 필요하다.

개인 사업·회사 영업·창작 브랜드를 같은 매출 목표로 재지 않는다. 브랜드 목적에 따라 유료 검증, 관계·신뢰, 창작 결과물 중 중심 결과를 선택한다. 생활·행정·유지 업무는 OKR 연결을 강제하지 않고 공통 할 일·루틴에서 처리한다.

활성 목표는 우선 개인 기준 1~2개, 목표당 KR은 2~3개를 제안한다. 이는 조직용 OKR을 복사한 기준이 아니라 1인 운영의 집중도를 위한 권장 범위다.

### B. AI 없이도 완결되는 업무 기반

- 원문을 먼저 저장하고 필요한 분류·연결은 뒤에서 보완한다.
- 메모 → 할 일, 콘텐츠 소재, 고객 활동으로 전환해도 원문 링크를 남긴다.
- 할 일, 다음 연락, 프로젝트 완료 조건과 발행 결과는 구조화된 기록으로 관리한다.
- 회사와 개인의 구분은 저장·조회·AI 문맥·지표 집계에 일관되게 적용한다.
- 검색·완료·기한·루틴·기본 리포트는 모델 응답이 없어도 작동한다.
- AI 장애 시 입력을 잃거나 모든 화면이 멈추지 않는다.

단일 정본은 모든 데이터를 한 테이블에 넣는다는 뜻이 아니다. 기존 원장의 책임을 유지하면서 연결 ID와 공통 읽기 모델을 제공한다.

### C. 작업에 필요한 문맥만 전달하는 AI

입력은 현재 업무, 관련 원문, 브랜드 기준, 최근 확정 결정, 허용 동작, 출력 형식으로 제한한다. 전체 저장소나 모든 고객 정보를 매번 전달하지 않는다.

출력은 결과물, 근거 링크, 확인할 부분, 제안된 다음 행동을 구분한다. 원문에 없는 고객명·예산·날짜·성과를 채우지 않는다. 검색/필터로 충분한 동안 벡터 DB 도입을 필수 전제로 두지 않는다.

리서치처럼 병렬 탐색이 유리한 작업에만 여러 에이전트를 검토한다. 반복 문서 초안은 단일 작성 단계와 필요한 검사부터 시작한다. Anthropic의 [에이전트 설계 안내](https://www.anthropic.com/engineering/building-effective-agents)도 단순한 구성에서 출발해 측정된 이점이 있을 때 복잡도를 높일 것을 권한다.

### D. 실행과 검토량 제어

승인 카드는 “승인할까요?”보다 **무엇이 바뀌며, 누구에게 전달되고, 근거가 무엇인지**를 먼저 보여준다. 초안 승인, 실제 전달, 전달 결과 확인은 다른 사건이다.

- 원문 보존·내부 집계·규칙 기반 알림은 자동화하기 좋다.
- 요약·초안·분류·업무 분해는 AI 후보부터 시작한다.
- 고객 메시지·발행·공식 거래 변경은 기존 확인 경계를 유지한다.
- 이미 승인된 좁은 작업은 범위 안에서 진행하며, 모든 내부 조작에 재승인을 요구하지 않는다.
- 원문·수신자·가격·내용이 달라졌으면 과거 승인을 다른 작업에 재사용하지 않는다.
- 같은 사건에는 같은 실행 키를 쓰고, 결과가 불명확하면 확인 후 재시도한다.
- 생성량·호출 비용·재시도·검수 반복에 상한을 둔다. 보류 중인 후보가 있으면 같은 초안을 계속 생산하지 않는다.

하루 검토 한도는 실측 후 정한다. 긴급 약속·실패는 빠르게, 나머지는 묶어서 보여주되 중요한 일을 한도 밖에서 숨기지 않는다.

### E. 증거를 쌓는 학습

검수 통과만으로 좋은 업무라고 판정하지 않는다. 사람이 실제 채택했는지, 얼마나 고쳤는지, 외부 결과가 무엇인지 연결한다.

“항상 짧게 써라”처럼 일회성 수정을 전역 규칙으로 즉시 바꾸지 않는다. 브랜드·채널·작업별 수정 이유를 보관하고, 변경 후보를 이전 사례에 적용해 좋아지는지 확인한다. 새 기준은 버전·적용일·되돌리기 경로를 가진다.

## 4. OKR·KPI는 지금 연결하되, 기록을 한 번만 한다

**OKR은 바꾸고 싶은 결과, KPI는 운영 상태를 보는 지표, Action KPI는 결과를 개선하기 위해 선택한 행동이다.** KPI에는 행동과 결과 지표가 모두 들어갈 수 있다. KR과 KPI를 선행/후행이라는 하나의 축으로 동일시하지 않는다. [Atlassian OKR 안내](https://www.atlassian.com/team-playbook/plays/okrs)

### 연결 모델

```text
Objective: 누구에게 어떤 가치를 주는 사업으로 성장할 것인가
  └ KR: 그 변화가 일어났다는 측정 가능한 결과
      └ 실행 가설/프로젝트: 어떤 제안과 활동으로 결과를 만들 것인가
          └ 주간 행동·오늘 할 일
              └ 실제 실행 기록 → 지표 집계 → KR 검토
```

할 일 완료율을 KR 달성률로 자동 치환하지 않는다. 콘텐츠를 발행했어도 유료 수요가 검증됐다는 뜻은 아니다. 여러 KR에 연결된 한 활동은 원본 사건으로 한 번만 세며, 목표별 연관을 모두 합쳐 실적을 부풀리지 않는다.

**설명용 예시이며 확정 목표가 아니다.**

- O: 개인 브랜드의 전문성을 유료 서비스 수요로 검증한다.
- KR 후보: 기간 안의 첫 유료 고객 수, 약속한 결과물을 수락한 고객 수.
- 실행 가설: 반복되는 고객 질문을 콘텐츠와 작은 오퍼로 만들면 적합한 상담이 생긴다.
- 주간 행동: 콘텐츠 발행, 적합한 대상에게 구체적인 제안, 약속한 후속 연락.
- 보호 지표: 납기 누락, 재작업, 운영자 작업시간.

목표 방향과 측정 정의는 지금 정한다. 새 수치 목표는 2주 동안 실제 처리량·가용 시간을 기록한 뒤 설정하는 것을 권장한다. 계약·결제처럼 주기가 긴 결과는 2주만으로 전환율을 확정하지 않는다. 기존 Threads 하루 1개 기준은 운영자 프로필에 있는 목표이며, 새 브랜드 전부에 일괄 적용하지 않는다.

### 최소 결과 지표와 행동 후보

처음부터 아래를 모두 첫 화면에 올리지 않는다. 활성 목표에 맞는 주요 결과 1~3개와 결과당 유용한 행동 1~2개를 고른다.

| 종류 | 지표 후보·정의 | 근거·집계 | 무엇을 결정하는가 / 주의 |
|---|---|---|---|
| 결과 | 개인 사업의 신규 유료 고객 수 | 해당 기간 최초 결제 근거가 확인된 고유 고객. 취소·환불은 별도 표기 | 오퍼 유료 검증. 딜 금액·계약 수를 입금으로 간주하지 않음. 현재 자동 집계 가능 여부 미확인 |
| 결과 | 회사 영업의 다음 단계 수락률 | 동일 관측 집단에서 명시적 미팅·데모 제안을 받은 고유 고객 중 수락한 고객 / 제안받은 고객 | 제안 적합성. 시도 수·미팅 실시 수와 구별하고 관측 기간과 표본 수 표시 |
| 결과 | 주간 순절감 시간 | 유사 업무량의 기준 수동 시간 − 도입 후 총 사람 투입시간. 후자는 지시·검토·수정·실패 복구·유지 시간 포함 | 자동화 유지/축소. 초기에는 자기 기록 기반 추정이며 절대 생산성 배수로 표현하지 않음 |
| 행동 | 발행 완료 수 | 채널별 고유 외부 게시물과 실제 발행일. 내부 초안·예약은 제외 | 지속 가능한 제작량. 동일 원본의 파생 수와 원본 수는 구분 |
| 행동 | 적합한 대상에게 전달한 오퍼 수 | 대상과 제공 범위·조건이 있는 실제 제안. 같은 대상·같은 오퍼 재시도 중복 제외 | 수요 검증 시도. 단순 공지나 초안 생성 건수로 대체하지 않음 |
| 행동/신뢰 | 약속한 후속 행동 기한 준수율 | 기간 내 기한 도래한 명시적 약속 중 기한 내 실행된 건 / 도래한 건 | 후속 누락 방지. 기한 없는 모든 고객을 분모에 넣지 않음 |
| 실행 보조 | 오늘 선택한 집중 작업 완료율 | 계획 시점에 선택한 집합 중 마감 시점 완료 / 선택 수 | 하루 계획의 현실성. 계획 변경은 이력으로 남기고 사후에 분모를 줄이지 않음 |
| 품질 진단 | AI 초안의 실사용 전환·수정 부담 | 채택한 고유 결과물 수와 결과물별 실제 검토·수정 시간 | 작성 단계 개선. 승인 버튼 수를 외부 발행·사업 성과로 보지 않음 |

보호 지표는 시작할 때 **후속 누락 건수**와 **AI 비용·검토시간 한도 초과 여부** 정도로 좁힌다. 품질 문제가 드러나면 해당 워크플로에 재작업률 같은 지표를 추가한다.

### 지표 카드의 최소 계약

- 이름, 단위, 개선 방향(증가/감소/범위 유지), 기간.
- 회사/개인, 브랜드·오퍼 등 적용 범위.
- 분자·분모, 실제 발생 시각, 중복 제거 키, 제외 규칙.
- 기준값·목표값·현재값과 원본으로 가는 링크.
- 수동/자동 입력 여부, 최종 수집 시각, 누락·부분 수집 여부.
- 정의·목표 변경 이력과 다음 점검일.

집계는 SQL/업무 코드로 계산하고 AI에는 숫자의 해석과 다음 행동 후보를 맡긴다. 읽기 실패나 미측정은 0이 아니다. 분모가 0이면 해당 없음, 목표가 없으면 미설정으로 보인다.

달성률은 지표별 방향을 반영한다. 매출 증가, 처리시간 감소, 누락 0건 유지에 같은 `actual / target` 공식을 쓰지 않는다. 서로 다른 KR을 한 생산성 점수로 억지 평균하지 않는다.

## 5. 우선 붙일 AI 기능

| 순서 | 업무 | AI 역할 | 완료 근거 |
|---|---|---|---|
| 1 | 주간 정리 | 실제 기록을 읽어 진척·공백·병목 가설과 다음 주 제안 작성 | 숫자별 원장 링크, 모르는 부분 표시, 운영자가 선택한 다음 행동 저장 |
| 2 | 메모의 업무 전환 | 요약, 관련 업무 찾기, 할 일·콘텐츠·고객 활동 후보 제시 | 원문 보존, 대상 확인, 선택한 결과의 저장·재조회 |
| 3 | 미팅·고객 후속 준비 | 최근 대화·약속·자료를 한 장으로 정리, 연락 문안 초안 | 근거와 상대·날짜 확인, 실제 연락 기록과 구분 |
| 4 | 콘텐츠 재가공 | 승인한 아이디어/원문을 채널별 목적에 맞게 재작성 | 브랜드 기준·사실 검사, 원본 연결, 실제 발행 결과 |
| 5 | 병목과 실험 제안 | 행동→반응→유료 결과의 약한 구간에서 다음 실험 제안 | 가설·변경점·기간·판단 기준·결과가 연결 |

주간 리포트 1순위는 Q118의 기존 선택이다. 개인 월요일 아침·회사 목요일 아침(Q119)을 유지한다. 내부 카드에서 시작하고 메시지 발송을 자동으로 추가하지 않는다.

### 하루가 작동하는 예

아침에는 오늘 약속·일정·가용 시간을 보고 집중 작업을 선택한다. AI가 준비한 고객 브리프나 콘텐츠 초안은 해당 작업 옆에서 확인한다.

미팅 뒤 짧은 메모를 저장하면 원문은 즉시 보존된다. AI가 다음 행동·날짜·고객 연결 후보를 보여준다. 모호한 “다음 주 화요일”은 실제 날짜와 연결 대상을 확인할 수 있어야 한다. 채택한 정보로 기존 업무 기록을 업데이트한다.

콘텐츠는 자신의 경험·고객 질문에서 원본을 만들고, AI가 파생 초안을 만든다. 사용자가 다듬어 발행하면 게시물 근거가 기록되고 주간 집계에 반영된다.

저녁에는 완료·미완료·재계획할 약속을 확인한다. 기존 하루 리뷰를 길게 만들지 않는다. 주간 리포트에서 어느 행동이 결과로 이어졌는지 보고 다음 실험 하나를 선택한다.

## 6. 편의 기능의 우선순위

| 우선 | 기능 | 실제로 줄이는 부담 |
|---|---|---|
| 먼저 | 전역 빠른 입력, 원문·초안 복구, 저장 확인, 관련 객체 자동 채움 | 기록을 놓치거나 두 번 입력하는 시간 |
| 먼저 | 오늘 집중 작업, 예상 소요시간, 일정 충돌 표시 | 불가능한 하루 계획과 반복 이월 |
| 먼저 | 기다리는 일·다음 연락일·다시 보기·누락된 다음 행동 | 고객과 프로젝트를 머리로 기억하는 부담 |
| 먼저 | 통합 검색과 메모→할 일/소재 전환 | 흩어진 기록을 찾고 다시 옮기는 시간 |
| 다음 | 반복 업무 템플릿, 완료 시 다음 회차, 건너뛰기·휴식 처리 | 루틴 재등록, 못한 날 누적되는 부담 |

이미 있는 기능은 새로 만들지 않고 실패·왕복·저장 복구 같은 사용 흐름을 보강한다. 모든 편의 기능을 한 번에 켜지 않는다. 모바일·음성·직접 발행은 기존 단계 경계를 유지하며 실사용 필요로 승격한다.

## 7. 콘텐츠 분석은 다음 행동을 바꿀 때 확장한다

첨부 자료의 방향은 유용하지만 “초반 이탈 = 훅 실패”, “저장률 3% = 좋은 콘텐츠”로 원인을 확정해서는 안 된다.

1. 현재 주력인 Threads의 원본·후킹 유형·게시 시각·문의/반응 기록부터 연결한다.
2. 같은 채널·형식·주제·비슷한 관측 기간끼리 비교한다. 발행 다음 날과 일주일 뒤 수치를 섞지 않는다.
3. AI는 관찰 사실과 설명 가설을 분리한다. 댓글에서 자료 요청이 보였다고 유효 영업 기회를 자동 확정하지 않는다.
4. 다음 실험은 한 가지 변경을 중심으로 잡는다. 작은 표본의 순위는 확정 규칙으로 승격하지 않는다.
5. 콘텐츠→문의는 추적 링크·문의에서 밝힌 출처·수동 연결 근거를 구분한다. 조회수와 매출의 동반 변화만으로 인과를 선언하지 않는다.

YouTube는 [Analytics 채널 리포트](https://developers.google.com/youtube/analytics/channel_reports)의 승인된 접근으로 시청 유지 데이터를 조회한다. [지표 정의](https://developers.google.com/youtube/analytics/metrics)의 `audienceWatchRatio`는 구간 반복 시청 때문에 1을 넘을 수 있어 단순 이탈 확률과 같지 않다. 공개 조회수만으로 자신의 채널과 타 채널의 내부 분석을 동일하게 얻는다고 가정하지 않는다.

Instagram/Threads의 상세 지표는 사용할 계정·권한·API 버전으로 별도 검증해야 한다. 이번에는 Meta 개발자 페이지 읽기에 실패했으며, 계정 연결·실제 응답은 점검하지 않았다. 원문의 지표 전부가 자동 수집 가능하다는 전제를 두지 않는다.

## 8. 현재 코드와 연결되는 지점

이 표는 지정 커밋의 정적 확인이며, 운영 실행 검증은 아니다.

| 항목 | 확인한 내용 | 제안 |
|---|---|---|
| 주간 리포트 | [weekly-report.js](../../apps/hub/lib/repositories/weekly-report.js)의 `getWeeklyReport`가 완료 task를 `updated_at`으로 필터 | 완료 시각 기준으로 교정. 과거 완료 task의 제목 수정이 이번 주 실적으로 잡히지 않게 함 |
| 리포트 범위·이력 | 같은 함수에서 딜만 개인/회사 필터를 적용하고, 열린 딜의 최근 수정 목록을 `movedDeals`로 계산 | 도메인별 scope 적용·실제 단계 전이 근거를 먼저 정함. “수정”을 “전환”으로 집계하지 않음 |
| 집계 상한 | tasks/outcomes/deals 300, publish logs 200 등 고정 limit | 완전 집계를 위한 서버 aggregate 또는 페이지 처리. 상한 도달을 조용히 전체값으로 표시하지 않음 |
| 목표/실적 기반 | [campaign-business-truth.js](../../apps/hub/lib/campaign-business-truth.js)에 `primaryMetric/weeklyTarget/weeklyActual`과 `buildWeeklyScorecard` 존재 | “KPI 기능이 전혀 없다”는 진단은 부정확. 기존 카드를 목표·기간·출처·이력으로 확장 |
| KPI 현재 한계 | [MCP 안내](../../packages/mcp-server/README.md)는 scorecard를 수동 현재 스냅샷으로 명시 | 기간별 추세·KR 진척·입금 집계로 오해하지 않음. 목표 0·감소형 지표도 표현할 계약 필요 |
| 초안 크론 | [followup-autopilot](../../apps/hub/app/api/cron/followup-autopilot/route.js)·[content-flywheel](../../apps/hub/app/api/cron/content-flywheel/route.js)이 각각 `followup-draft`·`content-draft`와 구조화 결과를 요구 | 기존 F-0 수리와 실패 가시성 우선 |
| Engine 모드 | [sales-mentor](../../apps/engine/app/api/ai/sales-mentor/route.ts)·[brand-mentor](../../apps/engine/app/api/ai/brand-mentor/route.ts)의 MODES에 두 모드가 없고 기본 자문 모드로 대체 | 실제 요청·응답 계약 불일치. 운영 실행은 별도 확인하되 새 자율화보다 이 결함부터 다룸 |
| 실행 확인 | [work-order-executor.js](../../apps/hub/lib/sales-os/work-order-executor.js)는 일부 외부 action 별도 처리 후 나머지를 `marked_executed`로 표시 | 수동 실행 표시를 실제 발송/발행 영수증과 구분. “모든 실행이 단순 표기”라고 일반화하지 않음 |
| MCP/worker | [09-13 연결 설계](../superpowers/specs/2026-09-13-codex-mcp-api-integration-design.md)에 공통 Agent API·명령 receipt·선택적 worker 기반 | 새 오케스트레이터부터 만들지 않고 기존 계약 확장. 실제 가동은 별도 활성화 검증 |

공유 작업 공간에는 같은 날짜의 `personal-workflow-os-three-axes-and-action-kpi-design.md` 미커밋 초안도 있었다. 방향 검토에 참고했지만 확정 사양으로 취급하지 않았다. 그 초안의 “새 테이블·마이그레이션 0”을 이번 목표 이력의 고정 제약으로 채택하지 않는다. 현재값 카드에 과거 이력을 억지로 넣는 것도 피한다.

## 9. 구축 순서와 통과 조건

기존 승인된 F-0 및 성장 계획 순서를 뒤집는 구현 지시는 아니다. 신규 OKR·AI 보강을 어디에 연결할지 제안하는 순서다.

| 단계 | 범위 | 다음 단계로 넘어갈 근거 |
|---|---|---|
| 0. 현재 루프 신뢰성 | 기존 F-0 초안 계약/실패 표시, 주간 집계 시각·scope·완전성, 메모 연결·재조회 확인 | 저장·집계가 실제 사건과 맞고 실패가 드러남 |
| 1. 목표와 측정 | 현재 카드 확장 방향 결정, OKR·지표 정의, 기간 기록, 오늘 선택과 리뷰 연결 | 원본에서 주간 수치를 재현하고 미측정/0을 구별 |
| 2. 한 업무의 AI 보조 | 주간 리포트 요약부터 시작, 필요 시 메모 정리 | 근거 정확성, 실제 채택, 검수 포함 순절감이 반복 관측됨 |
| 3. 이벤트 자동화 | 검증된 후보 생성·템플릿·재시도·실행 결과 확인 | 중복·장애·재시도에도 기록과 결과가 일치, 비용·검토량 한도 준수 |
| 4. 선택적 자율 운영 | 콘텐츠 파생·한정 리서치·회고 규칙 개선 | 단일 단계보다 품질/시간이 좋아지고 실패 시 중지·복구 가능 |

일정만 지나면 자동으로 자율성 단계를 올리지 않는다. 승인된 범위 안에서 실제 성과를 보고 확장한다.

**첫 구현 후보:** 기존 주간 리포트의 집계 신뢰성을 교정하고, 목표·실제값·근거·다음 행동을 같은 흐름에서 보는 것. 새 최상위 대시보드보다 현재 리포트와 업무 상세를 확장한다. OKR 전용 저장 구조는 기간 이력·참조 무결성 요구를 정한 뒤 최소 범위로 설계한다.

## 10. 확인 범위와 다음 설계에 남길 결정

- 첨부 3개 중 앞의 2개는 SHA-256이 일치하는 동일 본문이다. 실질적으로 두 종류의 참고 자료와 이번 사용자 메시지를 검토했다.
- 운영자 프로필과 심화 설계, 문서 지도, 관련 성장/Agent 설계를 대조했다.
- 현재 코드에서 주간 집계·수동 scorecard·초안 모드·실행 분기를 직접 확인했다.
- 운영 DB 수치, 자동화 가동 여부, 실제 시간 절감, 채널 API 응답은 측정하지 않았다.
- 기존 문서 지도의 배포·테스트 수치에는 다른 문서와 시점 차이가 있어 이번 검토의 운영 현황 증거로 사용하지 않았다.
- 이번 작업은 문서 검토다. 앱 코드·DB·자동화 설정을 변경하지 않았고 런타임 테스트도 실행하지 않았다.
- 이후 세부 설계에서 정할 것은 활성 Objective, 유료 고객/전환의 정확한 정의, 기간과 목표, 시간·AI 비용 예산이다. 추가 인터뷰 중단 원칙에 따라 이번 검토에서 새 질문을 요구하지 않는다.
