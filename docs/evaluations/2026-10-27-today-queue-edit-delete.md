## 확인한 부족과 수정

기존 구현은 집중이 찬 뒤에도 등록은 가능했지만, 오늘 화면의 나머지 목록을 레인별 5개로 제한해 더 쌓인 항목은 다른 탭으로 보내고 있었다. 오늘 목록과 집중 카드에는 항목별 편집·삭제 진입점도 없었다. 따라서 “등록은 됨”과 “오늘에서 계속 보고 관리할 수 있음” 사이에 차이가 있었다.

- 기존 `items/later` 요약 계약은 유지하고 전체 미완료·비집중 `queueItems/queueCount`를 별도로 제공한다. 오늘의 **대기 할 일**은 읽힌 전체 큐를 표시한다. 집중 3개 제한은 등록 수나 대기 수에 적용하지 않는다.
- 집중에서 해제하면 같은 ID가 대기 큐로 돌아온다. 할 일 자체 삭제는 별도 편집창의 삭제 행동이다. 임의 일일 초기화·날짜별 데이터 삭제는 추가하지 않았다.
- 대기 행과 집중 카드에 **편집** 버튼을 둔다. 공용 `EditDrawer`에서 제목·우선순위·기한·다음 행동·메모를 수정하며, 바뀐 필드만 보낸다. 다른 필드를 편집한다고 기존 시각이 있는 기한을 날짜로 덮지 않는다.
- 기존 `expectedUpdatedAt` 비교를 사용한다. 실패·충돌이면 초안을 유지하고, 명시 ACK 필드가 실제 요청값과 맞아야 창을 닫는다. 미확인 응답을 성공으로 표시하지 않는다.
- 서버의 제목 300자·다음 행동 1,000자·메모 4,000자 한계를 입력과 저장 전 검증에 반영해 조용한 잘림을 막는다. 보드용 `med/high` 표시 별칭 대신 `priorityRaw`를 편집하고 ACK 뒤 원값도 동기화한다.
- 삭제는 기존 공용 2단 확인과 **3.5초 전송 지연·되돌리기** 정책을 따른다. 창 동안 행과 집중 자리는 유지하고 변경을 잠근다. 실제 `saved` ACK 뒤에만 큐·집중 자리·집계에서 제거한다. 실패·Preview·응답 유실은 항목을 성공 삭제처럼 없애지 않는다.
- 중복 삭제는 같은 작업 promise를 공유하며 다른 할 일 변경과 직렬화한다. 느리거나 실패한 재조회에서도 ACK 투영을 유지한다. 완료된 선택의 삭제·해제와 반복 투영도 집중 분모·완료 집계·스트릭을 중복 증감하지 않는다.
- 모바일에서 이전 편집기의 결과 알림이 재진입한 편집창 하단 버튼을 가리는 경우를 재현했다. 새 편집을 열 때 이 편집기가 만든 이전 알림을 걷어 버튼 접근을 복구한다. 전역 알림 레이아웃은 바꾸지 않았다.

요청 기록도 검증했다: 등록 POST 9개·서로 다른 receipt 9개, 최종 원장 ID 7개, 집중 ID 3개, 대기 4개다. DELETE는 총 3회로 두 항목에 대응한다(대기 항목 503→성공 2회, 집중 항목 성공 1회). 취소·되돌리기로는 DELETE가 나가지 않았다. 항목 재등록이나 임의 생성 없이 같은 ID를 수정·선택·해제했다.

내 작업의 합성 auth 사전 확인은 제공하지 않아 해당 탭에서 새 요청 전송이 차단됐으며, 이를 우회하지 않았다. 그 탭에서는 리스트의 동일 7개 제목과 수정·삭제 반영을 읽기로만 확인했다. fixture의 상세 기한 버킷은 운영 분류 전체를 재현하지 않는다.

브라우저 수정 저장은 제목·우선순위 중심으로 검증했다. 날짜 입력의 양수 날짜 선택·모바일 OS 키보드 및 다음 행동/메모 저장의 실제 조작은 완료 검증으로 세지 않는다. 날짜 유지·명시 null 해제·메모/다음 행동 ACK·길이 제한·충돌·중복 callback·완료/삭제 스트릭은 실제 코드의 handler/model 회귀시험으로 확인했다.
