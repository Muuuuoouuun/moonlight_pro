# AI API 연결·사용·활용 개선 조사

> 조사일: 2026-09-22 (Asia/Seoul)
> 범위: 현재 Moonlight 체크아웃의 코드, 로컬 설정의 존재 여부, 실행 중인 Hub/Engine, 연결된 서울 Supabase의 해당 workspace, 저장된 평가 기록.
> 상태: 조사 결과와 권장안. 제품 사양·구현 승인·배포 완료를 뜻하지 않는다.

## 1. 결론

**Gemini API 키는 연결되어 있고 실제 호출 이력도 있다. 다만 최근 일상 업무 활용과 계정 전체 비용을 확인할 체계는 미완성이다.**

- 루트·Hub·Engine 로컬 설정에 같은 `GEMINI_API_KEY`가 있다. 값은 출력하거나 이 보고서에 저장하지 않았다.
- 프로젝트 로컬 설정과 현재 셸에는 `OPENAI_API_KEY`·`ANTHROPIC_API_KEY`가 없으며, 앱 소스에서도 이 두 공급자 직접 호출을 찾지 못했다. 다른 프로젝트·도구·계정 전체의 미사용을 뜻하지 않는다.
- 실행 중인 `localhost:3000` Hub와 `localhost:3001` Engine의 health는 모두 HTTP 200이며 Gemini 설정, Hub→Engine 연결, DB 연결이 정상이다.
- 현재 키로 Google의 모델 목록을 조회해 HTTP 200을 확인했다. `gemini-3.5-flash`와 `gemini-3.1-pro-preview`가 목록에 있고 `generateContent`를 지원한다. 이번 조사에서 새 생성 요청은 하지 않았으므로 생성 할당량·결제 가능 여부까지 시험한 것은 아니다.
- 기본 모델은 `gemini-3.5-flash`. 일부 구 페르소나 채팅만 `gemini-3.1-pro-preview`를 선택한다. Council/Guru라는 화면 이름만으로 Pro 사용 여부를 판단할 수 없다.

조회는 workspace로 제한했고 응답의 정확한 전체 행 수를 확인했다. `sync_runs`의 공급자·모델·토큰·시각 등 필요한 메타데이터만 읽었으며 업무 원문은 조사 결과에 복제하지 않았다.

**9월 실제 API 사용 근거가 평가·자료 조사 파일과 별도 임시 DB 검증에는 있지만 운영 DB 사용량에는 모이지 않는다.** 따라서 DB가 비었다고 최근 호출·청구가 0이라고 말할 수 없다. 일부 기능의 미기록, 별도 평가 스크립트, 다른 프로젝트의 호출도 계정 청구와 차이를 만들 수 있다. [Google 공식 안내](https://ai.google.dev/gemini-api/docs/billing)에 따르면 계정 사용량은 AI Studio의 Dashboard → Usage에서 확인한다. 이번 조사에서는 계정 청구 내역·현재 월 비용·유료 등급을 확인하지 않았다.

## 4. 효과가 큰 활용 순서 — 권장안

### 먼저: 주간 정리의 운영 연결

운영자 확정 우선순위는 **주간 리포트**, 월요일 아침 개인·목요일 아침 회사다([운영 프로필 Q118·Q119](../operator-workflow-profile.md)). 이미 화면·업무 문맥·Office 연결이 구현돼 있으므로 별도 챗봇을 늘리기보다 다음 왕복을 완성하는 것이 우선이다.

`원장 집계 → 이번 주 완료·정체·누락 요약 → 다음 행동 1~3개 → 검토한 행동을 할 일로 연결 → 다시 조회`

선행 조건은 현재 DB의 0038 준비, 최신 업무 프롬프트의 실제 평가, 생성·재조회·할 일 저장의 왕복 확인이다. 이번 조사에서 DB 적용·예약 생성·배포는 하지 않았다. 기존 Office v2 평가를 최신 E0~E4 업무 흐름의 검증으로 대체하면 안 된다([구현 기록 §9](../superpowers/plans/2026-09-21-eevee-office-embedded-workflow.md)).

### 다음: 고객 연락의 기록까지 연결

선택 고객의 최근 직접 연결 활동과 다음 행동을 사용해 카카오톡·문자 답장을 짧게 만들고, 실제 연락 뒤 `요약 / 반응 / 다음 행동 / 다음 날짜`를 남긴다. 생성·복사·채택을 실제 연락 완료로 취급하지 않는다. 이후 신규 개발은 붙여넣은 대화·전사문에서 이 네 칸의 후보 값을 추출하는 좁은 기능이 적합하다. 외부 자동 발송 제안이 아니다.

### 다음: 선택한 원문을 Threads 중심으로 재사용

원문 하나 → Threads 초안 → 필요한 경우 Instagram·Shorts 파생 초안 순으로 사용한다. 단순 다듬기·줄이기는 기존 Studio 단일 호출을 쓰고, 수치·고객 약속·복합 판단이 필요한 결과는 Office 검수 흐름에 둔다. 제작 아이디어의 복잡한 자동 점수화보다 운영자가 고른 원문을 바로 쓸 수 있게 만드는 것이 확정 운영 방식에 맞다.

이미 Codex·Claude 등에서 작성한 결과는 `save_ai_candidate`로 저장하면 Moonlight Gemini를 다시 호출하지 않는다. 클라이언트 자체의 사용량이 없다는 뜻은 아니다([기존 운영 가이드](../measurable-personal-os-operations.md)).

## 5. 비용·품질 개선 — 권장 구현 순서

1. **호출 시도별 사용량을 통일한다.** 기능·모델·시각·입력/출력/생각/캐시 토큰·지연·성공/실패·요청 ID·개발 평가/실사용 구분을 저장한다. Office는 첫 생성 뒤 파싱·검수가 실패하면 이미 발생한 사용량이 응답에서 사라진다. 실패를 0원으로 처리하지 말고 미측정으로 표시한다. 월별 비용·사용량 조회는 운영자 확정 요구다. 추정 비용과 공급자 실제 청구를 분리한다.
2. **기존 결과 재사용과 문맥 절약을 우선한다.** 과거 Guru 후속 초안 3회는 각각 약 15,100 입력 토큰에서 161~180 출력 토큰을 만들었다. 짧은 답장에 어떤 문맥이 필요한지 줄여볼 근거다. 같은 요청의 재조회·복구는 모델을 다시 부르지 않도록 기존 영속 요청 ID 구조를 확장한다.
3. **잘림·형식 실패를 정상 결과로 처리하지 않는다.** 공통 Gemini 함수는 HTTP 200만 보고 `ok:true`를 반환하며 `finishReason`을 확인하지 않는다. 브리프 768·OCR 512·패턴 분석 2048의 출력 한도와 모델별 thinking 설정을 함께 점검한다. 무조건 모든 한도를 올리기보다 빈 답변·MAX_TOKENS·차단·유효 JSON을 구분한다. Studio에는 이미 지원하는 `responseJsonSchema`를 전달해 형식 실패를 줄일 수 있다.
4. **시간 제한과 키 판정을 일치시킨다.** 명함 OCR에는 요청 시간 제한이 없고, 패턴 분석은 Hub가 30초·Engine이 45초여서 화면 실패 뒤 공급자 호출이 계속될 수 있다. Hub health의 키 별칭 지원과 OCR·메모의 실제 키 해석도 다르다. 현재 키 설정에서는 별칭 문제가 발생하지 않지만 공통 설정으로 정리할 가치가 있다.
5. **모델 선택을 업무별로 평가한다.** 같은 실제 업무 사례로 현재 Flash 단일 호출·필요한 검수·Pro 경로의 사실 오류, 바로 쓸 수 있는 비율, 지연, 비용을 비교한다. 기존 Office 검수를 근거 없이 제거하거나 화면 이름만으로 Pro를 강제하지 않는다. 입력이 짧고 수치·약속이 없는 수정 작업은 기존 단일 호출 경로부터 활용한다.

캐시는 완전히 없는 상태가 아니다. DB 기록에 `cachedContentTokenCount` 8,144가 있으며 Google은 Gemini 2.5 이후 암묵적 캐시를 기본 제공한다. 우선 변하지 않는 지침을 앞부분에 유지하고 실제 캐시 적중량을 관찰한다. 명시적 캐시는 반복량·최소 토큰·보관료를 계산한 뒤 도입한다([공식 캐시 문서](https://ai.google.dev/gemini-api/docs/generate-content/caching)).

많은 평가나 긴급하지 않은 대량 변환에는 Batch를 후순위로 검토할 수 있다. 공식 요금 문서는 Batch API의 50% 비용 절감을 안내하지만, 현재처럼 사용 기록이 적은 개인 업무에서는 먼저 운영 활용과 관측을 갖추는 편이 낫다([공식 요금표](https://ai.google.dev/gemini-api/docs/pricing)).

첫 측정은 다음 다섯 가지면 충분하다.

- 기능별 호출 수와 추정 비용; 토큰 누락은 별도 표시.
- 주간 보고서 중 실제 검토한 비율.
- 초안을 큰 수정 없이 사용한 비율 / 수정 후 사용 / 폐기.
- 제안에서 실제 다음 행동·다음 날짜 기록으로 이어진 비율.
- 기존 소요 시간 − 검토 시간 − 프롬프트·실행·재작업 시간. 값이 빠지면 미측정.

9월 Legend 파일럿에서는 지침이 늘어난 조건이 기본 조건보다 평균 점수·분량 기준을 더 잘 충족하지 못했다. 소표본·자동 판정이므로 일반화할 수는 없지만, 더 긴 페르소나 지침이 자동으로 더 좋은 업무 결과를 뜻하지 않는다는 재평가 근거다. 최신 Office 평가도 18개 중 7개가 보완 필요였다. 다음 투자는 인물·설정 확대보다 **운영자의 실제 작업에서 채택과 시간 절약을 확인하는 평가**가 적합하다.

## 7. 조사 범위의 한계

- 현재 체크아웃에는 다른 작업의 미커밋 변경이 있다. 코드는 해당 조사 시점의 로컬 상태이며 배포 상태와 동일하다고 가정하지 않았다.
- Vercel 환경·공급자 결제 대시보드·다른 프로젝트의 사용량은 이번에 재검증하지 않았다.
- 키 목록 조회는 인증 확인이며 생성·정산 시험이 아니다. 새 모델 생성, 외부 발송, DB 변경, 설정 변경, 예약, 배포는 실행하지 않았다.
- 이번 변경은 이 보고서 1개뿐이다.
