## 0. 한 줄 결론

10월의 확정 방향은 "새로 만들지 않고, 이미 가진 것을 돈으로"(OKR v3 O)이고 Moonlight는 동결(확정 12)이다.
그런데 10월 첫 7일 동안 Moonlight에 커밋 136개가 쌓였고, 새 기능(`feat`)만 27개다. **KR4(신규 개발 0건, Moonlight 포함)는
첫 주에 이미 어긋났다.** 한편 제품이 쓰이고 있는지 보여 줄 측정은 하나도 켜져 있지 않다. 지금의 병목은 기능 부족이 아니다.
병목은 셋이다. 실사용 측정 공백, 갈라진 브랜치를 합치는 비용, 판매에 쓸 시간이다.

### 1.3 누가 시작했나

대부분은 운영자 요청에서 시작됐다. 펫 1안(10/3 선택), OKR 목업 ①③④(10/1 지시), 개인 현금흐름(10/5 스펙),
디자인 감사·금액 표기·속도(10/6 요청, 이 세션)가 그렇다. 반대로 **운영자 결정 없이 들어간 것**도 있다. 상태표가
"권장 · 운영자 결정 전"으로 적은 Office 업무 나누기 H1이 그렇다. 자동 진행은 운영자가 "일부는 자동적으로"라고
요청했지만 범위는 정하지 않았다. 확인할 것은 방향만 고른 상태에서 단계 1~4가 한꺼번에 구현됐다. 동결을 깨는 손이 대부분 운영자 자신이라는 점이 OKR v3가 1번 임무로 막겠다고 한
실패 패턴("만드는 데 시간이 더 감")과 정확히 같다.

## 4. 권장 (운영자 결정 필요)

### 4.1 10/8~10/31: 동결을 실제로 건다

- 허용하는 것은 셋이다. 깨진 것 고치기, 이미 만든 것의 통합·배포, 결제 고객이 요청한 수정이다(OKR v3 §3 "유지" 칸).
- 새 기능 아이디어는 메모에 `[11월]` 태그로만 남긴다. 그 메모 수가 11월 OKR의 "만들기 압력" 실측이 된다.
- 에이전트(Claude·Codex)에게 줄 기본 규칙도 정한다. 요청이 새 화면이나 새 경로라면, 10월에는 착수 전에 "동결 중인데 진행할까요?"를
  한 번 되묻게 한다. 루트 `CLAUDE.md`·`AGENTS.md`에 한 줄을 넣는 것은 운영자 확정이 필요하다.

### 4.2 이번 주 남은 개발 시간은 통합 하나에만 쓴다

1. `codex/moonlight-sync-20261007`을 main에 합친다.
2. 나머지 7개 브랜치는 합치거나 닫는다. 이 세션 브랜치의 4커밋(감사 문서, 금액 표기, 디자인·성능)도 포함이다.
3. "권장 · 결정 전" 상태로 들어온 기능은 **운영 배포하지 않는다.** Office H1·자동 진행과 확인할 것 단계 3·4가 해당한다.
   코드는 남기되 11월 판정까지 화면에서 감추거나 배포 범위에서 뺀다.
4. 통합이 끝나면 정리 브랜치를 지운다. 브랜치가 줄어야 다음 세션들이 같은 맞추기를 반복하지 않는다.

### 4.3 실사용 측정은 코드 없이 시작한다

새 텔레메트리를 만들면 그 자체가 동결 위반이다. 이미 있는 도구로 시작한다.

- **`npm run db:usage`를 오늘 한 번, 10/14에 한 번 돌린다.** 운영자 Mac에서 `db:check`와 같은 env로 실행하며, SELECT만 보낸다.
  두 시점의 테이블별 삽입 수(`n_tup_ins`) 차이가 "그 주에 실제로 쓴 기능"이다. 대상은 `crm_activities`(연락 기록),
  `tasks`, `journal_entries`(메모), `routine_checks`, `office_requests`, `agent_runs`, `signal_outcomes` 등이다.
  행이 늘지 않은 표면이 11월에 정리할 첫 후보가 된다. 측정 방법은 [DB 감사 문서](../db-optimization-audit-2026-10-01.md)
  (`codex/moonlight-sync-20261007` 브랜치)에 있다.
- 심화 설계 §20의 이벤트 4종은 11월 개발 항목으로 넘긴다. 10월에는 하루 리뷰와 주간 메모의 자기 보고로 대신한다.
- 10/14 Office 판정은 계획대로 `[office]` 메모 수로 한다. 이번 주에 이미 만든 H1을 운영에 올릴지도 같은 날 함께 정한다.

### 4.4 판매 쪽: 저장소 밖의 숫자가 이번 주의 진짜 점검이다

이 문서로는 KR1~KR3을 볼 수 없다. 월요일 6칸(OKR v3 §5)에 아래를 적는 것이 이번 점검의 나머지 절반이다.

- KR2 1:1 가격 제시(주 2건 이상), KR3 고객 대화(주 2건 이상), KR4 신규 개발(**이번 주는 위 수치대로 0이 아니다**)
- 판매 시간 비중(60% 이상), 에너지 주 평균(3 이상)
- 마일스톤 세 가지:
  - 가격 확정(9/30)
  - 취업규칙 확인(10/2)
  - **강의 모집 오픈(10/9)**: 10/9를 넘기면 §7 규칙대로 강의는 11월로 넘기고, 10월 KR1은 소프트웨어 파일럿·대행에서 찾는다.

### 6.1 브랜치 대조 결과

워크플로(브랜치별 비교 → 반박 검증)의 결과는 아래에 적는다.

---

## 부록. 측정 명령

```bash
# 주별 고유 커밋 (전 브랜치, 병합 제외, KST)
TZ=Asia/Seoul git log --all --no-merges --since=2026-09-01 --date=format-local:%Y-%m-%d --pretty='%H %ad' \
  | sort -u -k1,1 | awk '{print $2}' | xargs -I{} date -d {} +%G-W%V | sort | uniq -c
# 10월 커밋의 종류 접두사
TZ=Asia/Seoul git log --all --no-merges --since=2026-10-01T00:00:00+09:00 --pretty='%H %s' | sort -u -k1,1 \
  | cut -d' ' -f2- | sed -E 's/^([a-z]+)(\([^)]*\))?!?:.*/\1/; t; s/^.*/(없음)/' | sort | uniq -c
```

영역별 줄 수는 커밋마다 `git show --numstat`의 경로를 키워드로 묶어 셌다(경로 이름 기준이라 경계가 겹치는 파일은 한 영역에만 들어간다).
