## 제품 변경의 근거와 범위

실험 중 확인한 별도 문제는 실패 기록이 서로 다른 원인을 합쳐 보였다는 점이다. 공급자 응답의 실제 `modelVersion`, `finishReason`, 토큰 사용량과 차단 사유가 기존 평가 trace에서 빠졌고, Office의 JSON·인용·계약 실패도 하나의 오류로 보였다. 이 정보 손실과 불완전 응답 수용 경계를 수정한다. 의미 오류를 해결한 것으로 기록하지 않는다.

공급자 `model`은 호출 시 요청한 alias로 유지해 다음 단계의 모델 고정을 보존한다. 별도 `modelVersion`은 API가 반환한 경우에만 기록한다. 응답 완료 여부와 비어 있지 않은 최종 텍스트를 확인하고, 생각 요약 part를 공개 본문에 섞지 않는다. 평가 trace에는 제한된 진단 코드·수치만 남기며, 원문 오류 메시지·키·헤더를 복사하지 않는다. Office 내부 진단 callback은 공개 API 응답이나 사용자 메시지를 바꾸지 않는다.

## 다음 판단

현재 9명 모두 70점 이상이라는 목표는 여전히 미달·미검증이다. 이 세 사례의 반복 실패를 전체 모델의 일반적 무능력으로 확대하지 않으며, 좋은 표본만 골라 통과시키지도 않는다. 보완한 진단 경계로 생성 실패를 구분한 뒤, 해당 원인을 고쳐야 전체 생성과 독립 의미 심사를 다시 할 수 있다. 기본 모델·역할 카드·평가 기준·48초 제한은 유지한다.

정확한 입력과 공급자 응답은 [시스템 전달 스크립트](system-delivery.mjs), [A/B 요청](minimal-ablation.prompts.jsonl)·[응답](minimal-ablation.responses.jsonl), [C/D 요청](output-ablation.prompts.jsonl)·[원시 응답](output-ablation.responses.jsonl), [Pro 검수·수정 호출](semantic-audit.calls.jsonl)에 있다. timeout 호출에는 실제 응답 모델 버전이나 사용량이 없으므로 추정해서 채우지 않았다.

## 보완한 진단 경계로 재현한 실패

위 23회와 별도로, 이전 v10에서 공급자 호출이 모두 성공한 뒤 거절된 세 사례를 한 번씩 다시 실행했다. [실행 journal](failure-boundary.run.jsonl)과 [검수 전후 원문](failure-boundary.provider.jsonl)에 6회 호출을 보존했다. 이브이 업무·글레이시아 종결은 생성됐고 샤미드 근거 검토는 `review_source-review`에서 실패했다. 6회 모두 실제 `gemini-3.5-flash`, `STOP`이었다. 글레이시아는 생성 성공 후에도 요청 밖 실패·중복 검증과 직접 확인 약속을 추가했으므로 품질 성공으로 기록하지 않는다.

샤미드는 서버가 제공한 정확한 운영 정책 문장을 인용했지만 검증기는 사용자/문맥만 허용해 거절했다. 따라서 유효한 현재 scope의 서버 정책만 원문 집합에 추가했다. 회사·개인 고유 규칙의 교차 인용, 누락·잘못된 scope, 초안·동료·역할 예시·임의 정책 문자열의 인용은 허용하지 않는다. 정책은 업무 원칙의 근거이며 고객 사실이나 실제 실행의 증거가 아니다.

수정 뒤 같은 사례를 새 [journal](policy-source-check.run.jsonl)·[2회 호출 원문](policy-source-check.provider.jsonl)으로 다시 확인했다. 이번에는 모델이 운영 정책 대신 검수 지시·역할 절차를 인용해 다시 `review_source-review`로 거절됐다. 첫 실패 기록을 덮어쓰거나 전체 시스템 프롬프트를 허용하지 않았다. 이 재현은 자유롭게 인용문을 생성하도록 하는 방식의 한계를 보여 주며, 허용된 원문에서 서버가 만든 후보를 선택하도록 제한하는 후속 수정의 근거다. 두 실행 모두 파일 hash 불변을 확인했다.

## Codex 실행 경로의 제한된 비교

현재 저장된 CLI 로그인으로 개발 사례 세 개를 추가 비교했다. [스크립트](codex-probe.py)·[요청과 응답](codex-probe.results.json)에 모두 보존했다. 사용자 설정을 읽지 않는 ephemeral·read-only 실행에서 원문과 A의 짧은 공통 지침, `answer/nextAction` JSON 계약만 전달했다. 실제 도구 호출은 0건이며 재시도·워크플로 활성화·운영 DB 쓰기는 없었다. 실행 방법은 [공식 비대화형 실행 문서](https://learn.chatgpt.com/docs/non-interactive-mode)와 로컬 CLI 도움말을 확인했다.

세 실행은 14.7초·7.0초·9.6초에 JSON을 반환했다. 기술 응답은 실제 저장 여부와 인증 원인을 미확인으로 유지하고 JSON 이후에도 성공 계약 검증이 필요하다고 답했다. 두 종결 응답은 짧아졌지만 불필요한 nextAction이 남았다. CLI 기본 모델을 사용했으며 이벤트에서 실제 모델 버전은 제공되지 않았으므로 특정 모델의 점수나 Gemini 대비 일반적인 우위로 기록하지 않는다. 이 호출은 제품의 전체 역할 지침·회의·검수 경로를 실행하지 않았으며 역할별 70점 심사 자료도 아니다.

현재 [Codex worker](../../../../../packages/codex-worker/README.md)는 별도 인증 홈과 등록 프로젝트·worker credential을 사용하는 비동기 작업 경로다. 기존 Office에 바로 주입할 adapter는 없고, worker 기본 600초·동시 작업 1개를 Office의 48초 HTTP 경로에 그대로 연결할 수 없다. 이후 비교를 확장하더라도 먼저 비동기 요청/결과 계약·취소·출력 schema를 연결하고 전용 worker 인증을 확인해야 한다. 이번에는 기존 기본 모델이나 인증 구성을 변경하지 않았다.

## 원문 enum의 실제 호환성 실패

서버가 원문 후보 전체를 `sourceQuotes.items.enum`으로 제공한 첫 수정은 로컬 테스트·typecheck·build를 통과했지만 실제 API에서 거절됐다. [3개 사례 실행](source-enum-check.run.jsonl)·[6회 호출](source-enum-check.provider.jsonl)에서 첫 초안 세 건은 모두 성공했고 검수 세 건은 HTTP 400이었다. 실패 검수 하나를 그대로 [재현](enum-error.json)해 `INVALID_ARGUMENT`를 확인했다. 이 구현은 성공으로 기록하지 않는다.

같은 요청의 enum만 바꾼 [분리 실험](enum-shape-probe.json)에서는 짧은 ASCII ID 목록, 짧은 한국어 한 문장, 기존 긴 한국어·개행 원문 하나가 각각 HTTP 200·`STOP`이었다. 따라서 한국어나 개행 자체가 허용되지 않는다고 볼 수 없다. 긴 원문 목록을 스키마에 누적하는 복잡도가 원인 후보이며 정확한 수치 한계는 확인하지 못했다. 후보 수만으로 원인을 확정하지도 않는다. 이 실험은 형식 수용 여부만 확인했으며 원문 선택이나 최종 답변의 의미 품질은 평가하지 않았다.

Google의 [GenerateContent 공식 제한](https://ai.google.dev/gemini-api/docs/generate-content/structured-output#limitations)은 큰 스키마가 거절될 수 있음을 설명한다. [Cloud 공식 고려사항](https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/capabilities/control-generated-output#considerations)에는 길거나 많은 enum 값이 복잡도를 높이는 요인으로 나와 있으나, 이 API의 정확한 수치 제한으로 일반화하지 않는다.

현재 입력 크기 계약 안에서도 짧은 문자열 원문 후보 수가 수천 개가 될 수 있다. 최종 수정은 모든 원문을 prompt의 번호가 붙은 목록으로 보존하고, 응답 스키마에는 최대 다섯 개의 정수 인덱스 범위만 둔다. 서버는 동일 목록에서 원문을 복원하며 범위 밖 번호·자유 인용문·역할 예시를 받아들이지 않는다. 아래 실행으로 이번 사례의 API 호환성을 확인했으며, 모든 입력 크기나 의미 품질의 보장으로 확대하지 않는다.

## 정수 원문 참조의 실제 경로 확인

최종 런타임 수정은 `4fcead3`이며 실제 실행의 파일 hash는 아래 journal에 보존했다.

[최종 journal](source-index-check.run.jsonl)·[공급자 호출 원문](source-index-check.provider.jsonl)·[집계](source-index-check.summary.json)에 새 개발 실행을 보존했다. 샤미드 근거·쥬피썬더 근거·글레이시아 종결·긴급 회의 네 사례가 모두 생성됐다. 개별 사례는 각각 2회, 회의는 역할 3회와 주관 종합 1회로 총 10회 호출했다. 전부 실제 `gemini-3.5-flash`, HTTP 200, `STOP`이며 재시도는 없었다. 요청마다 기존 48초 안에서 끝났고 실행 전후 런타임 hash도 동일했다.

원문 번호는 실제 prompt에 들어간 서버 목록에서만 선택하도록 검증한다. 역할 발언·재응답·종합과 개별 검수에 같은 계약을 적용하고, workflow의 prompt hash에도 목록을 포함한다. 수천 개의 짧은 원문이 있는 입력도 원문을 버리지 않으며 스키마에는 정수 범위만 늘어난다. 허용 번호 선택은 인용의 관련성이나 답변의 사실성을 증명하지 않는다.

이번 쥬피썬더 응답은 저장 여부를 불명으로 남기고 성공 계약을 알기 전 `showDone` 분기를 넣지 않았다. 그러나 글레이시아는 짧은 범위 확인 요청에 중복 클릭·재시도 등 별도 항목을 추가했다. 좋은 결과 하나를 일반적인 개선이나 역할별 통과 점수로 확정하지 않는다. 이 네 건은 **미채점 개발 자료**이며 전체 39건·독립 심사를 대신하지 않는다. 9명 70점 이상 목표는 여전히 미달·미검증이다.

메인에 추가된 주간 메모 분석·검색 성능 개선 커밋까지 통합한 상태에서 전체 테스트 1,968개 중 1,957개 통과·11개 건너뜀·실패 0개, typecheck 4개 작업·Hub/Engine build 2개 작업을 통과했다. 데이터베이스·배포 환경·worker 인증·기본 모델은 변경하지 않았다.
