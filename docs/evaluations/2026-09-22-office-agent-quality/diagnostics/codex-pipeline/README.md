# Codex CLI의 실제 Office 경로 비교

이 자료는 개발용 비교이며 역할별 통과 점수에 합산하지 않는다. 개별 응답의 초안·검수와 긴급 회의의 역할별 발언·종합을 기존 Office 서비스로 실행했다. 기본 모델, 운영 설정, 인증 구성, 데이터베이스는 바꾸지 않았다.

## 실행 경계

Office 런타임은 `45d932d`, 평가 전용 [CLI adapter](../../../../../scripts/office-evaluation/codex-provider.mjs)는 `21f720e`의 파일이다. 각 journal에 둘의 파일 hash, 실행 스크립트 hash, 호출별 prompt·schema hash와 실행 전후 불변 확인을 보존했다. 별도로 수행한 `scope-v1` Gemini 전체 평가와 지침이 다르므로 둘의 점수 차이를 모델 효과로 해석하지 않는다.

CLI `0.154.0`의 저장된 로그인을 정상 실행 경로로 사용했다. 인증 파일을 직접 읽거나 복사하지 않았고 사용자 설정은 읽지 않는 옵션을 사용했다. 빈 임시 디렉터리, ephemeral·read-only 실행, 웹·shell·앱·하위 에이전트 기능 비활성화를 적용했다. 감지한 도구 이벤트나 알 수 없는 이벤트는 실패로 처리하고 프로세스 그룹 종료를 기다렸다. 실행한 명령은 [baseline 스크립트](baseline.mjs)와 [low 스크립트](low.mjs)에 보존했다. 실행 당시 절대 경로를 남긴 증거 파일이며 재사용 CLI나 배포 설정이 아니다.

CLI 기본 모델을 요청했으며 실제 모델 버전은 이벤트에서 제공되지 않아 `null`이다. HTTP 상태나 Gemini의 `STOP`도 만들지 않았다. CLI의 `turn.completed`, exit 0, 유효 JSON과 Office의 계약·출처 경계를 모두 통과해야 생성 성공으로 기록했다. 원시 reasoning 본문이나 provider 오류 메시지는 adapter 결과에 보존하지 않는다.

Office 요청의 48초 공유 제한과 adapter의 호출당 45초 상한을 유지했다. adapter 재시도는 0회이며 CLI 내부 네트워크 재시도는 통제하지 못한다. `maxOutputTokens` 요청은 기록하지만 CLI에서 동일 제한을 적용했다고 주장하지 않는다. CLI의 내장 시스템 지침도 유지되므로 Gemini와 동일한 모델 입력을 비교한 실험은 아니다.

## 관측 결과

| 사례 | 기존 추론 설정 | 모든 호출 low |
| --- | --- | --- |
| 샤미드 근거 정리 | 생성, 43.9초 | 미지원 item 이벤트로 거절, 3.8초 |
| 쥬피썬더 근거 진단 | 검수 중 48초 제한 초과 | 검수 중 48초 제한 초과 |
| 블래키 짧은 문장 | 생성, 34.0초 | 생성, 28.2초 |
| 글레이시아 범위 확인 | 생성, 19.7초 | 생성, 15.1초 |
| 긴급 회의 | 종합 CLI 오류, 21.9초 | 생성, 40.6초 |

기존 설정은 초안에서 CLI 기본값, 역할 발언에서 low, 검수·종합에서 high를 요청했다. low 실행은 모든 단계의 실제 요청을 low로 바꿨으며 요청 전후 값을 공급자 기록에 함께 남겼다. 두 실행 모두 **5건 중 3건만 생성**됐다. 각각 공급자 12회 중 10회, 11회 중 9회가 완료됐다. 실패와 성공은 [baseline journal](baseline.run.jsonl)·[호출 원문](baseline.provider.jsonl), [low journal](low.run.jsonl)·[호출 원문](low.provider.jsonl)에 있다. 실패를 재생성한 답으로 대체하지 않았다.

baseline 회의의 실패한 종합을 별도 [진단 재실행](synthesis-replay.json)했을 때에는 38.0초에 완료됐다. 이는 원래 실패 원인을 확정하지 못한다. 원래 역할 발언 시간 17.5초와 단순히 합치면 48초를 넘지만, 실제 동일 요청의 총지연 측정으로 간주하지 않는다. low의 미지원 item도 원래 유형을 보존하지 못했으므로 원인을 추정하지 않는다.

완료된 글레이시아 응답은 범위를 두 문장으로 확인하고 추가 행동을 만들지 않았다. 샤미드는 활동 횟수·고유 고객·데모 수락·실시 예정·결제 미확인을 구분했다. low 긴급 회의는 실제 반론과 예상 반론을 구별하고, 현재 시각·전달 소요가 없어 18시 약속 준수를 확정할 수 없다고 남겼다. 이 관찰은 구현자의 정성 검토이며 독립 역할 점수나 전반적인 모델 우위의 증거가 아니다.

## 적용 판단

동기 공급자만 교체해서는 현재 48초 요청 계약 안에서 안정적으로 완료되지 않았다. 추론 강도를 낮추는 것만으로도 해결되지 않았다. 이 adapter는 평가 전용으로 유지하며 제품 기본 경로에는 연결하지 않는다. 이후 단일 작성 단계나 비동기 요청·결과 구조를 검토하더라도 실제 토론, 출처 경계, 취소, 결과 귀속, 전체 역할 품질 심사를 유지해야 한다. 기존 실패를 없애거나 제한 시간을 늘려 이번 실험을 통과로 바꾸지 않는다.

새 adapter의 오프라인 테스트는 실제 자식 프로세스로 원문 전달, 실패 이벤트, 도구 사용 거절, 공유 취소, TERM 이후 KILL, 파이프를 유지하는 자손 프로세스의 종료를 확인한다. 이 테스트가 CLI의 의미 품질이나 운영 연결을 검증하는 것은 아니다.

## 단일 작성 단계의 추가 분리 실험

`21f720e`의 prompt와 출처·출력 계약을 사용해 개별 응답만 한 번에 작성하는 [별도 harness](single-pass.mjs)를 실행했다. 개별 답변에도 서버의 원문 목록과 정수 인덱스 스키마를 전달하고, 원문·공개 응답 계약 검증을 모두 유지했다. 회의는 기존의 실제 역할별 호출과 종합을 그대로 사용했다. 모든 호출은 low, 요청은 48초, 호출당 상한은 45초였다. 제품 service는 변경하지 않았다. 최초 실행의 import 경로 오류는 [시작 로그](single-pass-bootstrap.log.txt)에 보존했으며 모델을 호출하기 전에 종료됐다.

[실행 journal](single-pass.run.jsonl)·[공급자 8회 호출](single-pass.provider.jsonl)에서 다음 결과를 얻었다.

| 사례 | 결과 |
| --- | --- |
| 쥬피썬더 재시도 설계 | 미지원 item 이벤트로 거절, 4.2초 |
| 쥬피썬더 성공 판정 진단 | 생성, 27.5초 |
| 부스터 지원 범위 문구 | 생성, 15.5초 |
| 글레이시아 범위 확인 | 생성, 11.0초 |
| 긴급 회의 | 종합 단계에서 48초 제한 초과 |

이번도 **5건 중 3건 생성**이며 전체 실행 중 파일 hash는 동일했다. 기술 진단은 알 수 없는 성공 계약과 인증 원인을 미확인으로 유지했고, 글레이시아는 범위 확인으로 끝냈다. 부스터는 무료 지원을 확약하지 않았으나 이미 검토 중이라고 주어진 운영 범위를 다시 확인하도록 요청했다. 짧거나 빨라진 응답만으로 실용성 통과를 선언하지 않는다.

미지원 item 때문에 끝난 기술 요청은 [진단 재실행](item-replay.json)에서 43.8초에 완료됐으며 관측된 item은 `agent_message`뿐이었다. 원래 미지원 유형은 재현되지 않았다. 확인되지 않은 유형을 허용하거나 기존 실패를 성공으로 수정하지 않았다. 로컬 SDK에는 `todo_list`·비치명 `error` 등 다른 item도 선언돼 있지만 이번 실패가 어느 유형이었는지는 알 수 없다.

## 후속 구조 검토

[읽기 전용 비동기 검토](async-review.md)는 기존 job 원장의 멱등 제출·lease·취소·상태 조회를 재사용할 수 있다고 보았다. 다만 Office 요청과 job의 원자 연결, 늦은 결과 차단, 결과 크기, actor·scope·보관 기한, 중첩 프로세스 그룹 취소를 해결할 새 계약과 마이그레이션이 필요하다. 구현·운영 준비 완료를 뜻하지 않는다.

검토자가 제안한 두 durable workflow 우선 연결은 최소 착수안일 뿐, 자유 대화·9인 역할·실제 협의·세밀한 설정과 전체 품질 심사라는 목표를 대신하지 않는다. 후속 구현에서는 그 전체 범위를 유지한다. 비동기화는 기존 HTTP 제한을 늘려 이번 평가를 통과시키는 변경과 구분해야 하며, 별도의 작업 상태·취소·완료 계약과 실제 전 역할 재평가가 필요하다. 현재 인증 파일을 복사하거나 운영 DB·worker 설정을 변경한 일은 없다.
