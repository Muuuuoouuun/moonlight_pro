# 성능 실험의 채택 조건과 기각 기록

첫 화면의 전체 동작과 오류 상태를 함께 비교한다. 한 상태의 점수만 좋아지는 변경이나 폰트 차단으로 얻은 수치는 구현 개선으로 합산하지 않는다.

## 선택한 Home의 읽기 시작 — 채택, LCP 상충 기록

통합 전 동일 소스 후보 `8de44c6a`, build `izk5oNMQaC529Gkq14SSn`을 `050e12f4`와 실제 Live 3쌍으로 비교했다. 390×844·CPU4배·150ms·200,000B/s·캐시 비움 조건에서 첫 행동 DOM 등장 중앙값은 4,025.2 → 3,484.8ms, 표준 session-window CLS는 0.228395 → 0.000357이었다. 읽기 시작은 약3.46 → 2.48초이며 두 쪽 모두 최초 요청1회다. DOM 등장은 애니메이션이 완전히 그려진 시각과 구분한다.

반면 LCP는 3,972 → 5,556ms로 악화됐다. 두 쪽 모두 SUIT는 약5.51초에 완료되지만, 후보에서는 이때 다시 그려지는 카드 제목이 가장 큰 요소로 선택됐다. 이 값을 지우거나 첫 행동 개선으로 대체하지 않는다. Preview·error도 LCP가 악화됐고, CLS 중앙값은 각각0.117758 → 0.030911, 0.093844 → 0.029005로 줄었다. 빈 결과·401은 비슷했다. 따라서 첫 행동과 화면 안정성 개선으로 채택했으며 모든 속도 지표의 개선이라고 평가하지 않는다.

Hub components 1,553개, 선택·청크 지연·이탈·3분 후 복귀·세션 폐기 검증, 상태24조건과 시각20조건이 통과했다. 오류·빈 결과를 숨기지 않고 다시 읽기와 새로고침을 확인했다. 최종 원본은 `/tmp/moonlight-quality-20261022/home-read-review.md`, 집계는 `performance-home-read-v2-summary.json`이다. 뒤의 preload-only 비교는 이 변경과 구별한다.

## 구조화된 Home 로딩 카드 — 기각

## 폰트 preload 제거 — 실제 소스 검증 후 채택

SUIT Variable 원본은 공식 v2.0.5 파일과 SHA-256이 일치한다. 폰트를 차단한 실험의 약 1초 이득은 실제 채택안이 아니다. 저우선순위 preload는 교차 반복에서 일관된 이득이 없어 기각했다.

HTML·HTTP Link·RSC의 폰트 preload를 모두 제거하고 CSS·폰트 파일·family를 그대로 둔 Preview 응답 실험 3쌍에서는 Home LCP 3568/3568/3568 → 3336/3336/3324ms, 고객 4456/4472/4460 → 4268/4224/4248ms였다. 초기 JS 전송량과 최종 화면 PNG·글꼴·내비게이션 경계는 같았으며 두 폰트가 모두 정상 전송·로드됐다. SUIT의 완료 시간은 거의 같고 Mono만 늦어졌다. Home CLS 중앙값은 0.117757로 같고 고객은 0이었다.

이는 `1x8LSkEiAY33Wr7u_kSPX`의 Preview 응답 변형 비교다. Live와 실제 소스 빌드로 확인하지 않은 단계이므로 배포된 개선으로 주장하지 않는다. 현재 CSS의 font-display: swap, 글꼴 자체 품질, 원본 문자 범위는 이 실험으로 바뀌지 않았다.

후속 실제 소스 빌드 비교를 마친 뒤 `33dd8573`으로 두 preload와 설명만 6줄 제거했다. `050e12f4` 기준 Live 3쌍에서 고객 LCP는 중앙값4,656 → 4,420ms로 3회 모두 개선됐고, Home 첫 행동 DOM은4,109.3 → 3,824.7ms로 3회 모두 앞당겨졌다. Home LCP는4,040 → 3,812ms이나 세 번째 쌍에서는188ms 느렸으므로 일관된 LCP 개선으로 표기하지 않는다.

Home 읽기 개선과의 조합도 실제 빌드3쌍으로 비교했다. 첫 행동 DOM은3,540.1 → 3,416.8ms로 매번 빨랐고, CLS 중앙값은양쪽0.005552였다. LCP 중앙값은3,760 → 3,440ms지만 세 번째 쌍에서1,984ms 악화됐다. 약5.6초의 폰트 완료 때 큰 제목이 LCP로 다시 선택되는 실행이 남아 있다.

두 실험 모두 각 경로의 JS·폰트·전체 resource 전송량은 같았다. 원본 폰트2개가 실제로 내려와 완료됐고, 최종 Home82개·고객990개 텍스트의 위치와 화면 픽셀이 일치했다. 조합 Preview·error 화면의51/52개 텍스트 위치·픽셀도 같았고 오류0건이었다. 검증은 실제 소스지만 로컬 production의 측정이며 운영 코드 배포는 하지 않았다. 상세 결과는 `performance.json`과 `/tmp/moonlight-font-preload-20261023/REPORT.md`에 있다.

## SUIT 한글 분할 — 기각

원본 624,536B를 정적 UI 문자 빈도로 분할하는 세 가지 구성을 별도 작업트리에서 비교했다. 원본 2,933개 Unicode 문자·가변 굵기·윤곽을 보존했고, 반복 생성한 42개 WOFF2 파일은 바이트가 같았다. 그러나 작은 첫 파일만으로 페이지 전체 전송 이득을 판단할 수 없었다.

실제 브라우저에서 분해된 한글(NFD)은 원본 폰트를 별도 fallback으로 남겨야 같은 글꼴로 렌더됐다. 이를 보존한 후보는 5개 굵기에서 29,370개 raster/폭 비교가 일치했지만, Live 고객 화면에서는 20개 조각과 원본 fallback·Mono를 모두 요청했다. 폰트 전송량은 기존 665,540B → 1,417,980B로 늘었다. fallback을 제외해도 조각 합계 746,440B가 원본보다 19.5% 크다.

Preview 고객의 일부 절약만으로 전체 개선을 주장하지 않고 실험을 중단했다. 소스·폰트·CSS·family 변경은 반영하지 않았으며 원본 폰트 SHA는 그대로다. 위 전송량은 최초 완료 비교의 관측값이며 3회 중앙값으로 표기하지 않는다. 전용 서버와 작업트리는 정리했고, 재현 스크립트·정적 검증·집계 보고서는 `/tmp/moonlight-font-subset-20261023/REJECTED.md`에 보존했다. 운영 레코드나 유료 API는 실험 생성 자료로 사용하지 않았다.

## 자체 호스팅 고객 JSON 압축 보정

설치된 Next16.3.8의 App Route adapter가 Content-Type을 배열로 넘기고 기본 압축기는 문자열만 인정해, 로컬 production 고객 조회201,226B가 압축되지 않았다. 최신 npm16.4.2와 upstream 경로에도 같은 처리여서 근거 없는 전체 버전 교체는 하지 않았다. `cf9a97cc`는 `/api/hub/revenue` 한 경로의 Content-Type 문자열을 next.config에서 먼저 선언해 기존 Next 압축 협상을 작동시킨다. 자체 gzip 구현·캐시 정책·응답 투영·JSON 내용·HTTP200 error 봉투는 바꾸지 않는다.

실제Next adapter+compression HTTP 회귀6건, 관련68건, source production build와 인증/협상검사가 통과했다. 무인증401을 유지하고 gzip/identity/q=0/br/헤더없음의 인증조회10개 decoded SHA가 같았다. 같은390px·150ms·1.6Mbps·CPU4배 조건의3쌍에서 첫 고객 행 DOM 중앙값6.140→4.425초, API transfer201,526→33,014B다. JS363,521B는 같고 LCP4.156→4.140초는 의미 있는 차이가 아니다.
