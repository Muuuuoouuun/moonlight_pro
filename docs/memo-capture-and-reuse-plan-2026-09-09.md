# 메모 입력과 재활용 기반 — 2026-09-09

## 이번에 구현한 범위

운영자의 여러 줄 메모·메모장·Obsidian 입력 요청과, 향후 라벨 분석·경향 파악·잊힌 메모 재활용 요청에 따른 구현이다. 아래 후속 제안은 승인된 자동 실행 정책이 아니다.

- 프로젝트 → 메모 → 새 메모 · 파일 가져오기에서 여러 줄 작성과 TXT/Markdown 단일 파일 가져오기.
- 선택 제목, 수동 라벨, 개인/회사 업무 범위. Enter는 줄바꿈, Cmd/Ctrl+Enter는 저장. 한글 조합 중 단축키 저장 방지.
- UTF-8 파일 256KB 이하, 본문 최대 100,000자. 파일이 크거나 지원하지 않는 인코딩이면 잘라 저장하지 않고 안내한다.
- 작성 중 파일을 가져오면 교체 확인. 저장 실패 시 초안 유지. 현재 탭의 sessionStorage에 임시 보관하고 새로고침 시 복원한다. 탭 종료·다른 기기 복원까지 보장하는 기능은 아니다.
- 서버 저장 응답에 이어 ID로 본문을 다시 읽어 일치하는 경우에만 초안을 비운다.
- 제목·본문·라벨·파일명 문자 검색, 저장 후 30일 이상 필터. 최신 자료 유형별 100건 안에서 검색하며 전체 자료 의미 검색은 아니다. 특정 메모 링크는 최신 목록 밖의 메모도 추가로 읽는다.

## 데이터와 저장 경계

기존 `notes` 테이블을 사용한다. 이 기능 자체에는 새 DB 마이그레이션이 필요 없다.

| 항목 | 저장 위치 / 의미 |
| --- | --- |
| 제목·작업 본문 | `notes.title`, `notes.body` |
| 저장 시점 | 기존 `notes.created_at` 기본값. 파일의 원래 작성일로 간주하지 않는다. |
| 범위·수동 라벨 | `notes.meta.memo_capture.scope`, `labels`, `labelSource: operator` |
| 출처 | `source.type`, 파일명 `source.name`, 파일 수정 시점 `source.fileModifiedAt` |
| 가져온 원문 | `originalBody`. 작성 화면에서 편집한 본문과 별도 보존한다. |
| 중복·변경 검증 | SHA-256 `contentHash`, `originalHash`, `payloadHash`와 캡처 버전 |
| 자동 분석 | `analysis: null`. 자동 AI 호출은 하지 않는다. |

원문은 텍스트로 표시하며 HTML/Markdown 내 스크립트를 실행하지 않는다. Obsidian의 링크·프런트매터는 현재 원문 텍스트로 보존할 뿐, 연결 객체로 변환하거나 포함된 지시를 실행하지 않는다. 원본 `.md` 파일 자체를 수정하지 않는다.

Hub POST는 기존 쓰기 검증을 통과한 뒤 서버 설정의 workspace ID로 덮어써 Engine에 전달한다. Engine은 기존 공유 비밀값을 검증한다. 읽기와 중복 확인 모두 workspace+ID로 제한한다. 기존 배포 인증 정책을 완화하지 않았다.

같은 workspace·기록 범위·파일명·원문·작업 본문이면 같은 저장 ID를 사용한다. 같은 파일의 제목/라벨만 다르면 덮어쓰지 않고 충돌로 알린다. 내용이 바뀌면 별도 스냅샷이다. 파일명 변경 또는 다른 경로의 동명 파일은 파일 동일성 판단에 한계가 있다. 수동 메모는 초안 ID를 재사용하므로 수정 없이 재시도하면 중복 생성되지 않지만, 다른 초안에 같은 내용을 쓰는 것은 별개 기록이다.

저장된 메모의 제목·라벨을 사후 수정하는 화면, 파일 수정본 간 계보 연결은 이번 범위에 포함하지 않았다. 전체 Vault 감시·양방향 동기화·첨부 이미지/PDF·외부 임베딩 전송도 없다. 개인 상세 메모를 ClassIn에 복제하지 않는다.

## 이후 구현 순서 — 제안

### 1. 전체 검색과 확인 기록

페이지네이션/서버 전체 검색을 먼저 추가한다. 라벨 사후 편집은 원문 수정과 분리하고 변경 이력을 남긴다. `reviewedAt`, 다시 보기 날짜, 보류 이유를 기록해야 오래된 메모와 정말 잊힌 메모를 구분할 수 있다. 현재 30일 필터는 단순 저장 경과일 필터다.

### 2. AI 라벨 제안

원문을 바꾸지 않고 별도 분석 결과로 저장한다. 제안 라벨과 운영자가 확정한 라벨을 구분한다. 분석마다 source ID, 본문 해시, 분석 버전, 모델, 실행 시점, 근거 문장을 남긴다. 본문이 바뀌면 이전 분석은 오래된 결과로 표시한다. 최초에는 사용자가 선택한 메모만 분석하고, 회사/개인 자료 혼합은 명시적으로 선택하게 한다.

라벨 예시: `고객질문`, `문제발견`, `사업아이디어`, `콘텐츠소재`, `결정근거`. 라벨을 강제로 채우게 하지 않고 수집 마찰을 낮춘다. 고객 이름 등 개인정보를 태그로 무분별하게 복제하지 않는다.

### 3. 반복 주제와 변화 분석

반복되는 고객 질문, 계속 미뤄진 아이디어, 의견이 달라진 결정 등을 근거 메모와 함께 보여준다. 주간 단위로 독립 원문 수를 세고, 재가져오기·수정 스냅샷·복사본을 독립 근거로 중복 집계하지 않도록 별도 그룹화가 필요하다. 기록량 증가와 실제 수요 증가는 다르며, 메모 주제로 운영자의 성격·정신 상태를 추론하지 않는다.

### 4. 관련 메모 다시 꺼내기

현재 프로젝트·선택한 작업을 기준으로 관련 예전 메모를 소수 제안한다. 각 제안에 ‘지금 다시 볼 이유’, 출처와 근거 문장, 이전에 보류한 이유를 표시한다. 읽음/보류/관계없음 피드백과 재노출 제한을 둔다. 단순히 무작위 오래된 메모를 매번 띄우지 않는다.

### 5. 실행과 수익 활동에 활용

| 메모에서 발견한 것 | 재사용 결과 제안 | 확인할 점 |
| --- | --- | --- |
| 반복 고객 질문 | FAQ·상담 답변·콘텐츠 초안 | 고객 정보 익명화, 실제 빈도 |
| 여러 기록에 반복되는 불편 | 서비스·상품 가설 | 메모 빈도와 지불 의사 구분 |
| 예전 아이디어 + 현재 프로젝트 | 다시 시작할 작은 실험 | 당시 중단 이유, 지금 달라진 조건 |
| 다른 분야의 비슷한 사례 | 두 아이디어를 결합한 제안 | 연결 근거와 추측을 구분 |
| 예전 결정과 지금의 차이 | 회고·의사결정 기록 | 당시 정보와 현재 정보를 분리 |

업무 생성, 고객 발송, 공개 게시, 코드 커밋은 각각 별도 실행 단계다. 메모를 썼다는 이유만으로 자동 실행하지 않는다. Agent/Council 입력에도 선택한 관련 메모와 출처만 전달하며 전체 개인 기록을 기본 포함하지 않는다.

## 검증과 운영 상태

- 실제 브라우저: 여러 줄 초안 → 새로고침 복원, Engine 중단 시 저장 실패/초안 유지 확인.
- 실제 브라우저: Markdown 가져오기 → 기존 초안 교체 확인 → 수동 라벨 → 실제 저장 → ID별 본문 재확인 → 저장 링크 재열기 → 라벨 검색 확인.
- 같은 파일·제목·라벨 재가져오기에 중복 방지 응답과 기존 ID 재사용 확인.
- 활용 제안 예시 메모 1건 저장: `aeec2e64-c4f1-5ce4-a818-d8a7852abc89`. 개인 범위이며 자동화된 기능과 제안을 본문에서 명확히 구분했다.
- 390px 모바일 작성 화면에서 가로 넘침 없음. 콘솔 error/warn 기록 없음. 화면 증거는 `artifacts/memo-capture-2026-09-09/`.
- 기존 업무 연결 기능은 `task_memo_links` 데이터 설정 미반영으로 비활성이다. 연결 여부를 ‘없음’으로 단정하지 않고 미확인으로 표시한다. 이번 메모 저장과 독립적인 제한이다.
- 검증 시점 자동 테스트 760개 통과, 계약 검사 통과, 타입검사와 Hub/Engine 빌드 통과. 이번 작업은 배포하거나 커밋하지 않았다.
