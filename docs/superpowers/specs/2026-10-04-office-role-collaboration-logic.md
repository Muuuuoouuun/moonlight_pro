# Office 역할 배정·상호 검토 로직

> 2026-10-07 통합 메모: 아래 v25 언급은 작성 당시의 기준이다. 통합본은 최신 main의 v27 역할 카드·Commander·고객 준비·요청 수신함·브랜드 연결을 보존한다. 영속 흐름은 별도 `저장 회의` 탭에 공존하며, 브랜드 결과 연결은 기존 관점 대화 흐름을 사용한다. 마이그레이션 정본은 `20261007_0069_office_meetings.sql`; 운영 DB 적용·배포·실제 모델 호출은 수행하지 않았다.

> 상태: 전용 브랜치 구현·로컬 검증, 운영 적용 전. 운영자 요청: “각자 역할, 기능 최적화, 상호 소통평가 디벨롭에 대한 로직 디벨롭”.
> 관계: 같은 날 `office-agent-evolution-design`의 영속 회의 위에 역할 배정과 검토 계약을 확장한다. `2026-09-24-agent-layer-direction`의 도구 없는 Office·명시적 운영자 적용·v25 말투 동결은 유지한다. 기존 토론 v1 저장 기록은 계속 읽는다.

## 목적과 책임

담당자는 요청한 산출물을 책임지고, 검토자는 그 산출물의 서로 다른 쟁점을 맡는다. 이브이(접수·종합), 샤미드(순서·의존성), 쥬피썬더(기술 진단), 부스터(고객 연락), 에브이(선택·기회비용), 블래키(근거·위험), 리피아(돈·시간), 글레이시아(범위·완료 조건), 님피아(독자·표현)의 기능 정본은 기존 역할 카드다. 기능 투영에는 mission·ownership·expertise·deliverables·boundaries·handoffs·deliberation만 쓰며 voice를 복제하거나 수정하지 않는다.

## 담당 추천 v2

- 주관 1명, 검토자 0~2명을 유지한다. 요청 산출물에 맞춰 주관을 고르고 서로 다른 검토 질문이 있을 때만 검토자를 붙인다.
- 기존 추천에 `plan: { ownerDeliverable, reviews: [{ reviewerId, question }] }`를 추가한다. 검토 목록은 선택한 역할과 순서까지 일치해야 하며 중복 질문은 거절한다.
- 입력은 현재 질문을 우선하고, 사용자가 적은 결정 맥락과 할 일 스냅샷을 남은 6,000자 안에 넣는다. 부가 맥락 축약은 화면에 밝히고 현재 질문 자체가 너무 길면 거절한다. 회의·질문·맥락이 달라진 추천은 적용하지 않는다.
- 계획은 추천 창에서 검토할 설명이다. 적용은 참석자 선택만 바꾸며 자동 재배정·업무 생성·외부 실행을 하지 않는다.

## 상호 검토 v2

- 첫 의견은 지금처럼 역할별 병렬 호출이다. 두 번째 라운드에서는 서버가 다음 참여자를 검토 대상으로 배정하는 순환 구조를 쓴다. 2~3인 모두 한 번 이상 검토받고, 다른 한 명을 추가 검토할 수 있다.
- `peerReviews`는 대상 역할, 첫 의견의 필드, 정확한 발췌, 동의/반론/근거 필요, 짧은 이유를 기록한다. 서버는 실제 첫 발언과 인용을 대조하고 자기 인용·없는 대상·중복·답변 대상 불일치를 거절한다. 동의나 관점 유지를 허용한다.
- 2026-10-05 실제 실패 교정: private 생성 응답은 `peerReviewsByOwner`에서 서버 발췌 목록의 `quoteIndex`를 선택한다. 필수 상대와 선택적 두 번째 상대를 키로 고정하고 서버가 원문·작성자·필드·replyTo를 붙여 위 공개 v2 계약으로 변환한다. 원문을 비슷하게 고쳐 쓰는 실패를 줄이며, 인용의 의미 타당성은 별도 평가한다.
- 서버가 `turnRef`, `sourceCheck`, `sourceCounts`를 붙인다. 유효·탈락 출처가 섞인 경우도 수치로 드러낸다. 출처 일치는 관련성이나 진실 인증이 아니다.
- 종합은 기존 한 번의 호출에서 모든 발언의 실제 반론을 `resolutions`에 연결한다. 상태는 반영(`addressed`)·남음(`open`)·해당 없음(`not_applicable`)과 이유다. 없는 참조나 중복·누락은 완전한 종합으로 받지 않는다.
- 2026-10-05 private 생성의 `resolutionsByTurn`은 실제 반론 ID를 필수 키로 가지며, 서버가 공개 배열로 변환한다. 같은 ID를 두 번 쓰고 다른 반론을 빠뜨리는 생성 실패를 줄인다. 공개 저장 형식·v1 읽기·호출 횟수·48초 제한은 유지한다. [재현·평가 기록](../../evaluations/2026-10-05-office-usability/README.md).
- 호출 수(역할 수 × 1~2라운드 + 종합 1), 공유 제한 시간, 모델 고정, 도구 금지는 유지한다. 추가 자동 재토론·자기학습·역할 성적 순위는 만들지 않는다.

## 평가와 표시

`evaluateOfficeDiscussion`은 검증된 기록으로 검토 대상 누락, 연결된 검토 수, 입장 변경 수, 출처 연결 수, 남은 반론 수를 계산한다. 의미 품질 점수를 만들지 않는다. v1의 없는 자료는 0점이나 검토 완료로 간주하지 않는다. 같은 모델의 역할 검토와 독립 평가를 구별한다.

Hub는 기존 추천 Drawer, 발언의 “근거와 반론”, “추천 근거와 남은 이견 전체”에 책임·인용·반론 처리·구조 점검을 담는다. 공통 업무 결과의 접힌 검토 기록에도 같은 정보를 표시한다. 새 상시 패널은 추가하지 않는다.

열린 반론은 최종 종합의 자유 문장 `dissent`에 빠졌더라도 결과 요약과 상세에서 보인다. 사용자가 멘토 검토를 요청하면 해당 원문도 기존 25,000자 예산과 부분 전달 표시 규칙 안에서 함께 전달한다. 다음 회의 질문에는 검증된 반론 참조·이유와 구조 점검을 제한된 assistant history로 싣는다. 운영자가 직접 적은 결정 맥락과 구별하며 자동으로 가중치·역할 카드·업무를 바꾸지 않는다.

독립 의미 평가의 인용 정책 v2는 역할 자신의 응답과 동료의 첫 발언을 쌍으로 요구한다. 갱신은 전후 발언·변경 이유·이전 요청 기록을 함께 인용하고, 원문 근거는 실제 응답 recordId와 당시 존재했던 자료에 연결한다. 이전 심사 기록은 legacy-v1로 읽히지만 새 v2 토론을 구 정책으로 채점할 수 없다. 기존 의미 점수 기준·통과선은 그대로다.

## 검증·출시 경계

계약 위조/누락/인용 불일치, v1 호환, 호출 순서/수/취소, 부분 출처 추적, 현재 질문 누락, 늦은 추천 적용, Hub 전달·복원, 업무 경로를 테스트한다. 전체 테스트·typecheck·Hub/Engine build와 독립 코드 리뷰를 완료한다. 실제 모델 품질은 별도 held-out 독립 심사로만 판단하며 이번 오프라인 테스트 통과를 v25 품질 통과로 쓰지 않는다. 새 DB 스키마는 필요 없고 배포·운영 DB 적용은 이번 구현 완료와 별개다.

v2 토론 기록은 24,000바이트, workflow 전체 결과는 기존 32,768바이트로 제한한다. 모델에 간결한 산출물을 요청하고 초과 시 인용을 잘라 통과시키지 않는다. 자유 회의 저장의 기존 결과 상한은 서비스 150,000바이트·SQL 180,000바이트다.
