# 프로젝트 시작·검증·종료 관리

> 상태: 구현됨 · 로컬 검증, 운영 배포는 별도
> 근거: 운영자 2026-09-09 요청 — 시작·종료 일정과 마무리 가능한 프로토타입을 중심에 두고 로직·디자인·UI로 구현
> 상위 정본: operator-workflow-profile.md, 개인 운영 OS 심화 설계 §11
> 관계: PMS 분류·Hub/Engine 경계 유지. 프로젝트 완료 조작은 아래의 결과물 검증 흐름으로 확장한다.

## 사용자 흐름

- 생성: 목표 결과·다음 행동과 함께 최소 결과물, 착수 예정일, 프로토타입 확인일, 목표 종료일을 입력할 수 있다. 날짜 미정은 허용한다.
- 프로젝트 첫 화면: 결과물, 세 단계의 예정일·실제일, 마무리 가능성, 완료 조건 수, 다음 행동을 먼저 보여준다. 기존 작업 진척은 보조 정보로 유지한다.
- `계획·검증`: 완료 조건, 남은 작업 시간, 종료일까지 확보한 시간, 병목, 다음 행동, 다음 버전 범위, 결과물 링크를 편집한다.
- `착수 기록`: 결과물과 완료 조건을 정한 뒤 실제 착수 시점을 기록한다.
- `프로토타입 작동 확인`: 착수한 프로젝트의 결과물 링크를 실제 확인하고 누른 시점을 기록한다. 자동 검사 통과를 의미하지 않는다.
- `검증 후 완료`: 결과물, 완료 조건 전부 확인, 작동 확인 기록, HTTP(S) 결과물 링크, 병목 해소를 검증한 뒤 저장한다. 목록의 완료 체크박스도 이 흐름을 연다. 응답 전 완료됐다고 표시하거나 행을 숨기지 않는다.
- `보류 기록`: 병목에 이유를 남기면 기존 blocked 상태와 pausedAt을 저장한다. `다시 진행`은 병목을 해결하거나 다음 버전으로 옮긴 뒤 선택한다. 일정은 자동으로 미루지 않는다.
- 마감 변경: 기존 종료일을 변경·해제할 때 이유를 입력한다. 최초 종료일과 변경 이력을 유지한다.

## 데이터 소유권

기존 projects 테이블을 사용하며 스키마 마이그레이션은 없다.

- `due_at`: 목표 종료일
- `started_at`, `completed_at`: 실제 착수·완료 시각
- `next_action`: 프로젝트 공통 다음 행동. 읽기 시 delivery.nextAction도 이 값을 사용한다.
- `meta.delivery`: deliverable, plannedStart, prototypeDate, criteria[{id,text,done}], remainingHours, availableHours, blocker, nextAction(입력 계약), nextVersion, resultUrl
- 서버 관리: originalDueAt, history[{at,from,to,reason}], prototypeVerifiedAt, pausedAt. 클라이언트가 전달해 덮어쓸 수 없다.

전달된 delivery 필드만 정규화하며 기존 meta의 org_scope·영업 연결 등 다른 정보는 보존한다. Engine은 workspace 범위에서 현재 행을 읽고 updated_at 조건으로 원자 PATCH한다. 원장을 읽지 못하거나 다른 수정과 충돌하면 쓰지 않는다. UI는 충돌 시 입력을 유지하고 최신 기록과 비교할 선택지를 제공한다.

날짜 순서는 착수 예정일 ≤ 프로토타입 확인일 ≤ 종료일이다. 일자 판단은 서울 기준이다. 결과물·완료 조건 문구·링크를 바꾸면 작동 확인을 무효화하고 다시 확인한다. 완료 시각은 중복 완료 요청으로 바뀌지 않으며 재개하면 현재 completed_at을 비운다.

새 Hub 생성 프로젝트에는 delivery 계약이 붙는다. 기존 delivery 없는 프로젝트와 다른 기존 생성 클라이언트는 자동 이관하지 않는다. 기존 API의 delivery 없는 상태 변경 호환은 유지하지만, Hub의 완료 UI는 검증 화면을 통과한다. 전면적인 DB 완료 제약은 이 변경에 포함하지 않는다.

## 마무리 가능성

확률 예측이 아니라 입력한 근거에 따른 판단이다. 시간은 운영자가 직접 적은 남은 시간이며 캘린더 가용시간을 자동 조회하지 않는다.

1. 검증을 마친 완료 상태: 완료
2. 명시적 보류: 보류 + 이유
3. 종료일 경과: 어려움 + 범위·일정 검토
4. 병목 존재: 주의 + 병목
5. 결과물·조건·종료일·시간 정보 부족: 판단 전
6. 남은 작업 > 확보 시간: 어려움 + 부족 시간
7. 프로토타입 확인일 경과·미검증: 주의
8. 그 외: 가능 + 남은 작업/확보 시간 근거

실제 착수 날짜와 예정 날짜를 구분한다. 기존 Timeline은 착수 예정일을 우선 사용하고 실제 착수일을 차선으로 사용하며, 둘 다 없으면 종료일 점만 표시한다.

## 시각·상호작용

Moonstone, 중성 서피스, 1px 경계선을 사용한다. 완료는 체크와 문구로 표현한다. 화면은 모바일 한 열, 넓은 화면 세 단계 일정을 사용한다. 저장 실패·Preview에서 입력을 보존하고, 중복 제출과 저장 중 편집을 막는다. 모바일 내비게이션은 편집 드로어 아래에 놓인다.

## 검증 경계

단위·서비스 테스트는 저장→작동 확인→완료→재개, 보류, 시간 판단, 날짜 검증, 메타데이터 보존, 충돌, 멱등 생성, 읽기 모델·Timeline을 검증한다. 브라우저 검증은 별도 테스트 데이터와 실제 Engine 서비스 함수를 연결한 메모리 저장 어댑터를 사용한다. 실제 운영 Supabase 프로젝트에 테스트 기록을 쓰지 않는다. 운영 배포 후 실제 Supabase 왕복 확인은 별도다.
