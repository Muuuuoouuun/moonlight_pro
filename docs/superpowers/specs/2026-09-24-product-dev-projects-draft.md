## 0. 한 줄 결론 (권장)

**Moonlight 안에 넣는다. 단, Jira/Linear를 다시 만들지 않는다.** 코드의 정본은 GitHub·에러 도구에 그대로 두고, Moonlight는 그 신호를 Engine으로 받아 "이 제품에 지금 무엇을 할지"를 판단하는 **제품 렌즈**만 얹는다.

**없는 것**

- "코드 제품"이라는 개념. PMS 분류는 `sns-channel` · `ka-deal` · `general` 3종뿐이다. 운영자 프로필의 `IT`·`AI 기반 서드파티 개발` 분야와 그 세부 단계는 **미정**으로 남아 있다.
- 체크리스트 **템플릿**(프로젝트·체크리스트 어느 쪽에도 없음. 템플릿은 Studio 글쓰기에만 있다 — 0044).
- CI 상태, 배포 상태, 런타임 에러 수집. Sentry·Vercel·GitHub Actions 연동 코드가 없다.
- 제품별 매출(판매·유료 사용자·구독). 딜 연결은 영업 프로젝트용이다.
- GitHub 연동의 실제 가동: 저장소 목록이 환경 변수(`GITHUB_REPOSITORIES`, `GITHUB_PROJECT_MAP`)이고, Hub에서 부르는 버튼도 cron도 없다. 결과는 프로젝트 상세의 "최근 업데이트" 한 줄로만 보인다. 폴링 요약이며 webhook이 아니다.

참고: `docs/projects-connection-inventory.md`가 로컬 Projects 폴더에서 **22개 프로젝트**를 찾았고 그중 GitHub 신호가 있는 것이 다수다. 관리 대상 후보는 이미 많다.

## 3. 두 갈래

### 갈래 A — 별도 서비스를 만들고 Moonlight에 연결

- 형태: 새 앱(예: "제품 콘솔")이 저장소·이슈·에러·매출을 소유하고, Moonlight에는 요약 webhook만 보낸다(기존 `POST /api/webhook/project` 계약).
- 좋은 점: 제품 도메인을 처음부터 깔끔하게 설계. Moonlight의 표면 예산을 건드리지 않는다. 나중에 팔거나 팀과 공유하기 쉽다.
- 나쁜 점:
  - 두 번째 로그인·DB·배포·인증 게이트·테스트 체계. 운영자 혼자 두 시스템을 유지한다.
  - 프로젝트·할 일·오늘 목록이 **두 곳**에 생긴다. "인지 에너지 1/3"·"후속 누락 0" 목표와 정면 충돌한다.
  - 수익 판단에 필요한 딜·고객·개인 매출은 Moonlight에 있어 결국 다시 끌어와야 한다.
  - 이미 있는 PMS·delivery·체크리스트·Codex·Engine intake를 재구현한다.
- 맞는 경우: 이 도구 자체를 **팔거나**, 외부 협업자가 들어와야 할 때. 운영자 프로필 §2는 "판매·다중 사용자 SaaS 계획 없음"으로 확정돼 있다.

### 갈래 B — Moonlight 안에 "제품 렌즈"로 넣는다 (권장)

- 형태: PMS에 `product` 분류를 더하고, 제품 컨테이너에 저장소·배포 URL·단계·매출 연결을 붙인다. 외부 신호(GitHub·에러·결제)는 **Engine**이 webhook으로 받는다. Hub는 판단 화면만 그린다.
- 좋은 점: 기존 자산의 약 60%를 그대로 쓴다. 오늘 화면·고객·매출과 한 루프로 묶인다(`signal → ledger → priority → action → execution → result`). 에러 → Codex 수리 작업 → PR → 해결이 한 시스템 안에서 닫힌다.
- 나쁜 점: 프로젝트 탭이 이미 무겁다(5.5천 줄). 패널을 덧붙이면 2026-09-23 "계속 붙는 것들 정리" 지시와 부딪힌다 → **새 패널이 아니라 별도 보기(탭)**로 분리하고, 본문 예산을 스펙에 적는다.
- 경계: Moonlight는 이슈 트래커가 되지 않는다. 이슈 본문 편집·코드 리뷰·스프린트 계획은 GitHub에 둔다.

### 판정

| 기준 | A 별도 서비스 | B 안에 넣기 |
| --- | --- | --- |
| 첫 결과까지 | 3~4주 | 1~2일(0단계) |
| 유지 비용 | 시스템 2개 | 1개 |
| 수익 판단 | 데이터 왕복 필요 | 이미 같은 DB |
| 발산 억제 | 새 도구 = 새 발산 | 기존 루프 안에서 WIP 제한 |
| 나중에 분리 | — | Engine webhook 경계가 있어 떼어내기 쉽다 |

B를 먼저 하고, "판매·팀 공유" 결정이 생길 때만 A로 떼어낸다.

## 4. 갈래 B 설계

### 4.1 제품 카드 (한 제품 = 한 줄)

| 필드 | 저장 위치(스키마 변경 최소) |
| --- | --- |
| 단계: 아이디어 → 검증 → MVP → 출시 → 성장 → 유지/종료 | `brands.meta.product.stage` 또는 `projects.meta.product.stage` |
| 저장소, 배포 URL | `integration_connections`(환경 변수가 아니라 UI에서 연결) |
| 수익 모델·가격 | `meta.product` |
| 다음 행동 | 기존 `next_action` |
| 점수 | 읽기 시 계산(저장하지 않음) |

### 4.2 제품 점수 (엄격, 100점, 읽기 시 계산)

| 축 | 배점 | 계산 근거 |
| --- | --- | --- |
| 돈 | 35 | 실제 매출(확정) > 파이프라인 딜 금액(권장) > 없음. 확실성은 §5.3 3값으로 표시 |
| 출시 | 25 | delivery 완료 조건 비율, 프로토타입 확인 여부, 종료일 경과 감점 |
| 코드 건강 | 20 | 기본 브랜치 CI 녹색, 24시간 에러 수, 리뷰 대기 PR, 7일 넘은 이슈 |
| 모멘텀 | 10 | 최근 7일 커밋·완료 작업 |
| 집중 비용 | 10 | 남은 작업 시간 ≤ 확보 시간이면 만점 (delivery 기존 필드) |

판단 규칙(발산 억제):

- 동시에 `MVP` 이상으로 진행하는 제품은 **최대 2~3개**(수치는 운영자 결정).
- 새 아이디어는 `아이디어` 단계에만 쌓이고, 활성 제품 하나를 `유지/종료`로 내려야 올라간다.
- 30일 동안 돈 0점 + 모멘텀 0점이면 "종료 또는 유지 전환" 결정 카드가 뜬다. 자동으로 내리지 않는다.

### 4.3 체크리스트 템플릿

기존 `tasks.meta.checklist`에 항목을 채워 넣는 방식. 템플릿 자체는 DB 행으로 둔다(0044 콘텐츠 템플릿과 같은 패턴 — 코드 하드코딩 배열은 `no-mock-data` 가드와 부딪힌다).

첫 3종 예시:

1. **MVP 검증**: 문제 한 문장, 대상 사용자 5명 확인, 가격 가설, 랜딩/대기자 페이지, 결제 의사 1건
2. **출시 전**: 도메인·HTTPS, 환경 변수 분리, 에러 수집 연결, 백업, 결제 테스트, 약관·개인정보, 분석, 롤백 방법
3. **결제 연동**: 결제사 테스트 결제, webhook 서명 검증, 환불 경로, 영수증, 매출 기록이 Moonlight에 도착하는지 확인

### 4.4 GitHub · 에러 연동 (Engine 소유)

| 신호 | 받는 방법 | Moonlight에 남는 것 |
| --- | --- | --- |
| 이슈·PR·마일스톤 | 기존 `github-sync.ts` 가동 + 저장소 목록을 UI로 | 제품 카드 요약 |
| CI 실패·PR 리뷰 요청 | GitHub webhook → `apps/engine/app/api/webhook/github`(HMAC 서명 검증) | `project_updates` + 오늘 화면 신호 |
| 런타임 에러 | Sentry(또는 Vercel 로그) webhook → Engine | 에러 묶음 1행, 급증 시에만 danger |
| 수리 | 에러·이슈 행의 "Codex에 맡기기" | 기존 Codex 작업 큐 |

규칙: 외부 발송·머지·배포는 자동으로 하지 않는다(프로필 §2 안전한 해석). 새 webhook 경로는 `route-access.js` 기본 "막힘"에서 provider secret을 가진 경로만 열린다.

## 6. 운영자 결정이 필요한 것 (미정)

1. 갈래 A와 B 중 무엇으로 갈지 (권장: B)
2. PMS 분류에 `product`(제품)를 4번째로 더할지, 아니면 `IT`·`서드파티 개발`로 나눌지
3. 동시에 진행할 제품 수 상한 (2 또는 3)
4. 에러 수집 도구 (Sentry / Vercel 로그 / 없음)
5. 첫 단계에서 연결할 제품 1~2개 (예: 인벤토리 22개 중 매출에 가장 가까운 것)
