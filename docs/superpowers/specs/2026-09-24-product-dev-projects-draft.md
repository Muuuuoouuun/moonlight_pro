## 1. 30초 요약

**제품 = 오래 사는 것, 프로젝트 = 끝나는 것.**

- **제품**(예: OMR 메이커)은 설명·대상 고객·가격·저장소를 가진 카드다. 사라지지 않고 단계만 바뀐다.
- **프로젝트**(예: "OMR 메이커 결제 붙이기")는 지금의 PMS 그대로다. 시작·검증·종료가 있고, 제품 아래에 붙는다.
- **GitHub**은 제품에 붙는다. 저장소 하나는 제품 하나에만 속한다. 개발 신호(CI 실패·PR·에러)는 Engine이 받아 제품과 프로젝트에 적는다.
- **고객 적합도**는 제품 카드의 "대상 고객·필수 조건"과 고객 기록을 대조해 **후보**만 띄운다. 운영자가 확인해야 F1 이상의 근거가 된다. 퍼센트 유사도는 쓰지 않는다.

```text
            ┌─────────────── 제품 카드 (설명·대상·필수 조건·가격·단계) ───────────────┐
            │                                                                          │
   저장소 N ─┤ GitHub 신호 → Engine → 기록        프로젝트 N (PMS, delivery)          ├─ 고객 적합도
            │                                                                          │   (후보 → 확인 → F등급)
            └──────────────────────── 제품 점수 · 다음 행동 ─────────────────────────────┘
```

### 3.1 제품 저장 위치 — 2026-09-25 운영자가 새 `products` 테이블을 골랐다

> 아래 v0.2의 권장 논리(컨테이너 재사용)는 **기록으로만** 남긴다. 운영자는 "대안(권장 안 함)"이던 새 테이블을 택했다.
> 결과: 브랜드 탭 제외 필터가 필요 없고, PMS 트리에 `제품` 폴더는 생기지 않는다. 제품은 프로젝트 탭의 `제품` 보기와
> 제품 상세 드로어에서만 보이고, 프로젝트 ↔ 제품 연결은 제품 상세 `개발` 탭에서 한다. 개발 신호는 `project_updates.product_id`에 떨어진다.

v0.2 권장 논리(대체됨):

- 좋은 점: PMS 트리·필터·컨테이너 편집·정렬이 **공짜**다. 프로젝트 탭 연결이 따로 필요 없다.
- 대가 1: 브랜드 탭(`brand-directory.js`)은 지금 카테고리를 거르지 않고 모든 컨테이너를 보여준다 → `product` 분류를 브랜드 탭에서 제외하는 필터 1개와 테스트가 필요하다.
- 대가 2: 테이블 이름이 `brands`라 코드를 읽는 사람이 헷갈린다 → 읽기 모델(`operating-ledger.js`)에서 `kind: 'product'`로 방출해 UI 코드에는 "제품"으로만 보이게 한다.
- 대안(권장 안 함): 새 `products` 테이블 + `projects.product_id`. 깔끔하지만 PMS 트리·필터·정렬을 다시 연결해야 한다. 판매·다중 사용자로 분리할 때(갈래 A 재검토) 옮기면 된다.

## 4. 제품 카드 — 제품별 설명 계약

제품이 늘어날 때마다 같은 틀로 채운다. **필수는 이름과 한 줄 설명뿐**이고 나머지는 단계가 올라갈 때 요구된다(§4.2).

| 필드 | 뜻 | 예시 | 쓰이는 곳 |
| --- | --- | --- | --- |
| 이름 · 한 줄 설명 | 무엇인가 | "학원 시험지 OMR 자동 채점" | 목록, ⌘K |
| 해결하는 문제 | 누가 무엇 때문에 괴로운가 | "수기 채점에 주 5시간" | 적합도 후보 사유 |
| 대상 고객 | 기관 유형 · 과목(12키) · 지역 · 규모 | 학원 · `math`,`english` · 전국 · 1~3관 | **적합도 L1 규칙** |
| 제공 범위 | 지금 **실제로 되는** 기능만 | "PDF 채점", "성적표 출력" | F1 판정 근거(검증된 기능) |
| 필수 조건 | 이게 안 되면 못 산다 | "스캐너 보유", "월 결제 가능" | **F2 판정 틀** |
| 가격 모델 | 월·건·일시불, 금액 | 월 29,000원 | 돈 축 |
| 단계 | 아이디어 → 검증 → MVP → 출시 → 성장 → 유지 · 종료 | MVP | 단계 게이트, WIP |
| 소속 | `personal` / `classin` | personal | **고객 경계**(§8.5) |
| 링크 | 배포 URL, 문서, 데모 | https://… | 제품 상세 |
| 제품 버전 | 설명·제공 범위가 바뀔 때 +1 | 3 | F 재평가 트리거 |

저장(구현): `products.summary` = 한 줄 설명, `products.details = { problem, target{orgTypes, subjects(리드 과목 12키), regions, size}, capabilities[{id,text,verifiedAt}], requirements[{id,text}], pricing{model: undecided|free|monthly|per_use|one_time, amount, currency: KRW}, deployUrl, links[{label,url}], nextAction }`, 단계는 `products.stage`(idea·validation·mvp·launch·growth·maintain·sunset — "유지·종료"는 두 값으로 나눴다), 이력은 `products.stage_history`. 소속은 `products.org_scope`이고 등록 뒤에는 바꾸지 않는다.

규칙:

- **제공 범위에는 확인된 기능만** 적는다. 계획 중인 기능은 `nextVersion`(delivery 필드)이나 프로젝트로 간다. 고객에게 "된다"고 말할 근거가 되는 칸이기 때문이다(리드 스펙 §5.1 "존재하지 않는 상품 기능을 정의하지 않는다").
- 제공 범위·필수 조건을 바꾸면 `version`이 오르고, 그 제품에 걸린 F 결정은 "재확인 필요"로 바뀐다(리드 스펙 §5.4).

### 4.0 카드 칸 단순화 (2026-09-25 운영자 — 위 표를 대체)

위 표의 "대상 고객: 기관 유형 · 과목(12키) · 지역 · 규모"는 쓰지 않는다. 제품이 교육인지 아닌지부터 모르고, 고정 칸은
제품을 그 분야에 가둔다. 구현된 카드: 이름·한 줄 설명(필수), **분야**(짧은 자유 서술, 예: 교육), **대상 고객**(한 줄 자유 서술),
해결하는 문제, **기능**(한 줄에 하나, 기능마다 점검 여부), 필수 조건, 가격, 배포 URL, 링크, **특이사항**(과목·지역·규모 같은 세부).
"제공 범위에는 확인된 기능만"(§4 규칙)은 "기능 목록 + 점검 완료 표시"로 바뀐다 — F1 근거는 점검을 마친 기능만이다.
L1 규칙 대조(§8.2)는 구조화된 대상 칸이 없어졌으므로 4단계 착수 전에 다시 설계한다(분야·대상 고객 문장 대조 또는 L3로).

### 4.3 전체 체크리스트와 진척률 (2026-09-25 운영자)

제품 상세 개요 맨 위. 제품 기록에서 **계산**한다(코드에 박아 둔 할 일 목록이 아니다 — `productChecklist`).

| 묶음 | 항목 | 완료 조건 |
| --- | --- | --- |
| 기획 | 한 줄 설명 · 분야 · 대상 고객 · 해결하는 문제 | 칸이 채워짐 |
| 기능 | 기능 정리 · 기능 점검 k/n | 기능 1개 이상 · 모든 기능 점검 완료(기능별 체크박스, 점검일 기록) |
| 개발 | GitHub 저장소 연결 · 프로젝트 연결 · CI 통과 | 연결 1개 이상 · 최신 CI 성공(데이터 없으면 확인 필요) |
| 출시 | 가격 정하기 · 배포 URL | 가격 모델이 미정이 아님 · URL 있음 |
| 운영 | 에러 수집 연결 · 연결된 문의 | 에러는 도구 미정(§12-6)이라 확인 필요, 문의는 건수 현황 |

진척률 = 완료 / (완료 + 할 일). "확인 필요"(원천 없음)와 "현황"(문의 건수)은 분모에서 뺀다. 목록 행에는 단계 옆에 %가 붙는다.

### 4.4 문의 ↔ 제품

문의 하나는 제품 하나에만 붙는다(`product_inquiry_links`, 0049). `inquiries`는 RPC로만 쓰이므로 열을 더하지 않았다.
문의 상세에 "어떤 제품 문의인가요" 선택 칸, 제품 상세에 `문의` 탭(연결 목록 · 최근 문의 붙이기 · 빼기). 연결 수는 체크리스트 운영 묶음에 보인다.

### 4.1 단계와 게이트

| 단계 | 들어가려면 | 체크리스트 템플릿 |
| --- | --- | --- |
| 아이디어 | 이름 + 한 줄 설명 | — |
| 검증 | 해결하는 문제 + 분야나 대상 고객 | MVP 검증 |
| MVP | 저장소 1개 연결 + 프로젝트 1개 | — |
| 출시 | 점검을 마친 기능 1개 이상 + 배포 URL + 출시 전 체크리스트 완료 | 출시 전 |
| 성장 | 확정 매출 1건 이상 | 결제 연동 |
| 유지 · 종료 | 이유 한 줄 | — |

게이트는 **막지 않고 알려준다**: 조건이 빠지면 "출시로 올리려면 배포 URL이 필요해요"처럼 빠진 칸으로 바로 데려간다.

### 4.2 발산 억제 (권장, 수치는 운영자 결정)

- 동시에 `MVP`·`출시`·`성장`인 제품은 **최대 N개**(권장 2~3).
- 넘치면 새 제품은 `아이디어`·`검증`에만 머무르고, 하나를 `유지`·`종료`로 내리라는 결정 카드가 뜬다. 자동으로 내리지 않는다.
- 30일간 돈 축 0 + 모멘텀 축 0이면 "종료 또는 유지 전환" 결정 카드.

| `status` | `connected` · `error` · `disabled` |
| `last_synced_at`, `last_error` | 가시성 |

기존 `GITHUB_REPOSITORIES`·`GITHUB_PROJECT_MAP` 환경 변수는 **읽기 폴백**으로 남기고, 테이블이 비어 있을 때만 쓴다.

### 5.2 두 경로: 폴링 요약 + webhook 이벤트

| 경로 | 무엇 | 주기 | 기존 자산 |
| --- | --- | --- | --- |
| 폴링 | 열린 이슈·PR·마일스톤 + **기본 브랜치 최신 커밋의 check 상태**, 최신 릴리스 | cron 하루 수 회 + 수동 버튼 | `github-sync.ts` 확장 |
| webhook | 아래 이벤트 즉시 | 실시간 | 새 `apps/engine/app/api/webhook/github` |

webhook 이벤트와 기록:

| GitHub 이벤트 | 조건 | Moonlight 기록 | 오늘 화면 |
| --- | --- | --- | --- |
| `workflow_run` / `check_suite` | 기본 브랜치 **실패** | `project_updates`(status `blocked`) | danger 레일 1건(red budget) |
| 같은 이벤트 | 이후 성공 | 같은 제품의 실패를 해소로 표시 | 사라짐 |
| `pull_request` | opened · review_requested · merged | `project_updates` | 리뷰 요청만 일반 행 |
| `issues` | opened/closed, 라벨 `bug` | 링크된 할 일에 상태 표시 | 없음 |
| `release` | published | 제품 `stageHistory`에 릴리스 기록 | 없음 |
| `push` | 기본 브랜치 | 모멘텀 축 입력(커밋 시각만) | 없음 |

보안·신뢰 계약:

- 서명: `X-Hub-Signature-256` HMAC 검증. 실패는 401, 기록 없음. `route-access.js`에는 **이 경로 하나만** provider secret 경로로 연다(기본 막힘 원칙).
- 멱등: `X-GitHub-Delivery`를 `webhook_events.provider_event_id`로 저장. 기존 unique 인덱스(0002)가 중복 배달을 막는다.
- 모르는 저장소의 이벤트는 저장만 하고 "연결 안 된 저장소" 표시. 제품을 추측하지 않는다.
- 토큰: 읽기 전용 fine-grained token(Contents·Issues·Pull requests·Actions: read). 쓰기 권한은 받지 않는다 — Moonlight는 GitHub에 **쓰지 않는다**.

### 5.3 프로젝트·할 일과 GitHub

- **프로젝트 ↔ 마일스톤 (선택):** `projects.meta.github = { repo, milestone }`. 연결하면 마일스톤의 열린/닫힌 이슈 수가 프로젝트 상세에 보인다. delivery 완료 조건을 자동으로 체크하지는 않는다 — "GitHub 마일스톤 닫힘 · 완료 조건을 확인할까요?"만 띄운다.
- **할 일 ↔ 이슈 (선택):** `tasks.meta.github_issue = { repo, number, url }`. 이슈가 닫히면 할 일에 "GitHub에서 닫힘" 표시와 완료 버튼. 자동 완료 금지(되돌리기 어려운 판단은 확인 단계 유지 — 프로필 §2).
- **에러 → Codex:** CI 실패·에러 행의 `Codex에 맡기기`가 기존 Codex 작업 큐(`pages/codex-jobs.jsx`)에 프로젝트·저장소·실패 로그 링크를 채운 초안을 연다. 보내기는 운영자가 누른다.

### 5.4 런타임 에러

도구는 미정(§12). 어느 쪽이든 Engine webhook → `error_logs`(기존, `source = 'sentry'` 등, `payload.product_id`)로 받고, **같은 오류 묶음은 1행**으로 센다. 오늘 화면에는 "평소보다 급증"일 때만 올라온다. 기준값은 운영 1~2주 관측 뒤 정한다.

## 8. 고객 ↔ 제품 적합도 ("누가 무엇을 살 수 있나")

### 8.1 원칙 — 유사도 퍼센트를 만들지 않는다

리드 스펙 §5는 합산 점수·100점 환산·퍼센트를 금지하고, AI 추출은 사용자가 원문과 대조해 확인하기 전까지 **후보**라고 정했다. 이 문서도 따른다. "유사도 87%" 대신 **왜 후보인지 조건별로** 보여준다.

```text
OMR 메이커 × ○○수학학원      ◇ 권장 · 후보
  ✓ 기관 유형  학원
  ✓ 과목      수학 (대상: 수학·영어)
  ? 지역      미확인
  ✓ 문의 원문  "채점이 너무 오래 걸려요" (09-12 문의)
  → [적합 확인]  [제외]
```

### 8.2 세 층

| 층 | 방법 | 입력 | 결과 | 시작 시점 |
| --- | --- | --- | --- | --- |
| **L1 규칙 대조** | 제품 대상 고객 조건 ↔ 고객 라벨을 조건별 일치/불일치/미확인 | 기관 유형, `meta.subjects`, `meta.region`, 규모 | 후보 + 조건표 | 제품 카드에 대상 고객이 채워지면 바로 |
| **L2 닮은 고객** | 이 제품을 이미 산 고객과 같은 조건을 공유하는 고객 | `deals.meta.product_id`(won) + 딜↔고객 연결 | "이 제품 고객 3명과 과목·기관 유형이 같음" | **막힘**: 라이브 `deals.lead_id` 0/22 연결(08-19 실측). 딜 연결 정비 후 |
| **L3 문장 근거 (선택)** | 문의·연락 원문에서 제품의 "해결하는 문제"와 맞는 발췌를 AI가 찾음 | `inquiries`, `crm_activities` 원문 | 발췌 + 출처 링크 | 비용 상한 결정 후. 개인 메모는 대상에서 제외 권장 |

세 층 모두 **후보만** 만든다. 후보는 기회 탐색(`discovery_records`)에 `source: product-fit`으로 들어가 기존 넛지 규칙을 따른다 — 새 알림 표면을 만들지 않는다.

### 8.3 확인 → F 등급

| 운영자 동작 | 저장 | F 등급 (리드 스펙 §5.1) |
| --- | --- | --- |
| `적합 확인` + 사용 목적 한 줄 | `product_customer_fits` status `confirmed` | **F1** — 실제 사용 목적 확인 + 제품의 검증된 제공 범위와 연결 |
| 필수 조건 대조 완료(제품 카드의 필수 조건 틀) | `requirements_checked[]` | **F2** — 미해결 필수 제약 없음 |
| 데모·시험 사용 결과 확인 | 기존 활동/일정 근거 링크 | **F3** |
| 필수 조건 불일치 확인 | status `confirmed`, grade 0 | **F0** — 자동 소멸 안 함 |
| `제외` | status `dismissed` + 이유 | 등급 없음. 같은 제품 버전에서 다시 후보로 올리지 않음 |

`product_customer_fits`(권장): `workspace_id, id, product_id, lead_id | customer_account_id (정확히 하나), status (confirmed | dismissed), grade (0–3 | null), purpose, requirements_checked jsonb, evidence_refs jsonb, product_version, policy_version, decided_at, revision`. 후보는 저장하지 않고 읽을 때 계산한다(같은 입력·버전·시각이면 같은 결과 — 리드 스펙 §4.2).

### 8.4 제품 쪽에서 보이는 것 · 고객 쪽에서 보이는 것

- 제품 상세 `고객` 탭: 확정 F2 이상 → F1 → 후보 순. 후보는 상위 5개만 본문, 나머지는 `더보기`.
- 고객 상세: `맞는 제품` 한 줄. 확정은 solid 칩, 후보는 dashed `◇ 권장`. 고객 한 명에 제품 후보가 여러 개면 가장 강한 것 1개 + "외 2".
- 연락 우선순위(리드 스펙 §8)에는 **확정 F만** 들어간다. 후보는 연락 순서를 바꾸지 않는다.

### 8.5 경계 — ClassIn 고객과 개인 제품

ClassIn은 회사 공식 객체의 정본이고, 개인 프로젝트는 ClassIn으로 보내지 않는다(프로필 §2·§11). 회사 고객에게 개인 제품을 제안하는 것은 이해 충돌이 될 수 있다.

- 권장 기본값: **같은 소속끼리만 후보를 만든다**(`personal` 제품 ↔ `personal` 고객, `classin` 제품 ↔ `classin` 고객).
- 교차 허용 여부는 운영자 결정(§12-4). 허용하더라도 ClassIn 쪽으로는 아무것도 보내지 않는다.

## 9. 제품 점수 (100점, 읽을 때 계산)

리드 점수와 달리 이것은 **내 제품의 건강 점수**다. 운영자가 원한 "철저한 점수"이므로 합계를 보이되, 축별 근거를 항상 함께 보이고 미확인은 0이 아니라 "미확인"으로 표시한다.

| 축 | 배점 | 만점 조건 | 근거 원천 |
| --- | --- | --- | --- |
| 돈 | 35 | 확정 매출 발생 (20) + 진행 중 딜 (10) + 확정 적합 고객 F≥1 3명 이상 (5) | `deals.meta.product_id`, `product_customer_fits` |
| 출시 | 25 | 소속 프로젝트의 delivery 완료 조건 비율, 프로토타입 확인, 종료일 준수 | `projects.meta.delivery` |
| 코드 건강 | 20 | 기본 브랜치 CI 녹색 (8) · 에러 급증 없음 (6) · 리뷰 대기 PR 3일 이하 (3) · 7일 넘은 bug 이슈 없음 (3) | GitHub·에러 신호 |
| 모멘텀 | 10 | 최근 7일 기본 브랜치 커밋 또는 완료 작업 | `push`, `tasks` |
| 집중 비용 | 10 | 남은 작업 시간 ≤ 확보 시간 | delivery 기존 필드 |

- 원천을 못 읽으면 그 축은 "읽기 실패"로 표시하고 합계에 "일부 데이터" `TruthBadge`를 붙인다. 0점으로 떨어뜨리지 않는다.
- 단계별로 의미 없는 축은 뺀다: `아이디어`·`검증`은 돈·코드 건강 대신 "검증 체크리스트 진척"을 본다.

| 단계 | 범위 | 스키마 | 끝나면 |
| --- | --- | --- | --- |

| **4. 고객 적합도 L1** | 조건 대조 후보 · 기회 탐색 연결 · `product_customer_fits` · 고객 상세 `맞는 제품` · 제품 `고객` 탭 | 테이블 1개 | "누가 이걸 살 수 있나"가 근거와 함께 보인다 |

각 단계는 앞 단계 없이도 쓸 가치가 있게 자른다. 1단계 끝에 운영자가 실제 제품 2~3개를 넣어 보고 카드 필드를 줄이거나 늘린다.
