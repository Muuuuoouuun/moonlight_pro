# 프로젝트 직접 실행 구조 재설계

> 상태: **직접 실행·계획 점진 노출 구현 및 로컬 검증 완료** (2026-09-23). 완료 검증 계약 변경은 제안으로 남김.
> 요청: 프로젝트에 들어가면 폴더를 하나 더 만들어야 진행되는 구조, 체크리스트 생성 팝업, 과한 `완성까지의 계획`을 재검토한다.
> 상위 정본: `docs/operator-workflow-profile.md`, `2026-07-13-moonlight-personal-operator-os-deep-design.md`, `DESIGN.md`
> 관계: `2026-09-23-project-operator-experience-and-write-trust-design.md`의 **하위 항목 우선 화면 가설과 큰 진척 카드 배치를 대체**한다. 같은 날 진척 UI 작업에서 추가한 계산 근거·기록 시점·부분 읽기 안내는 작은 진척 요약에 유지한다. `2026-09-13-pms-task-checklists.md`의 저장 모델은 재사용한다. `2026-09-09-project-delivery-lifecycle.md`의 완료 검증 규칙을 바꾸는 제안은 §5에 별도로 표시한다. 운영자의 “서브에이전트로 다른 PMS를 분석한 뒤 구조 리빌딩” 요청으로 직접 실행과 UI 점진 노출을 진행했다. §5의 서버 완료 검증 완화는 이번 구현 범위에 포함하지 않는다.

## 1. 관찰과 제품 판단

운영자가 제공한 2026-09-23 화면 세 장과 현재 `project-portfolio-workspace.jsx`, `projects.jsx`, `project-delivery.jsx`를 확인했다. 초기 진단은 제공 화면과 코드에 근거했다. 이후 구현의 브라우저·핸들러 검증 범위는 §8에 기록하며, 다수 사용자 실험 결과로 해석하지 않는다.

1. 프로젝트에 연결된 `tasks`가 이미 있으나 개요의 첫 실행 구역 제목이 `하위 프로젝트 · 마일스톤`이고 생성 버튼도 그 두 종류다. 기본 작업인 `task`를 직접 추가할 경로가 가려진다. 폴더 아이콘이 붙은 `subproject`도 독립 `projects` 레코드가 아닌 `tasks.meta.item_type`이다. 사용자에게는 프로젝트 아래 또 프로젝트를 만들어야 하는 것처럼 보인다.
2. 체크리스트 조회·체크는 항목을 펼치면 가능하지만, 새 항목 작성은 작업 상세 드로어의 체크리스트 탭으로 돌아간다. 프로젝트 안에서 생각난 일을 곧바로 한 줄로 적는 흐름이 끊긴다. 다른 프로젝트 상세 표면에는 이미 한 줄 할 일 생성 경로가 있으므로 저장 계층을 새로 만들 필요는 없다.
3. `완성까지의 계획`을 펴면 값이 없는 세 날짜와 판단 전 카드가 큰 면적을 차지한다. 편집 드로어는 결과물, 세 날짜, 완료 조건, 두 시간 추정, 병목, 다음 행동, 다음 버전, 링크를 동시에 요구하는 모양이다. 생성 계약은 이름만 필수이고 날짜는 선택인데, 화면은 계획을 먼저 완성해야 시작할 수 있다는 인상을 준다.
4. 개요의 큰 진척 수치, 바로 아래 계기판, 결과물 바, 하위 항목의 작은 게이지가 서로 경쟁한다. 사용자의 1차 질문인 “지금 무엇을 할까?”가 접힌 구역 아래로 밀린다.

**제품 원칙**: 프로젝트를 열면 바로 할 일을 적고 체크할 수 있다. 마일스톤은 필요한 때에 작업을 묶거나 중요한 결과 시점을 표시한다. 완료 기록은 실행을 막는 사전 양식이 아니라 마무리 순간에 확인한다.

## 2. 외부 제품에서 가져올 패턴과 가져오지 않을 것

| 제품의 확인된 패턴 | Moonlight 적용 |
| --- | --- |
| [Asana는 프로젝트에서 작업을 바로 추가](https://help.asana.com/s/article/structure-your-projects-clearly)하고, 하위 작업은 분해가 필요할 때 쓰며 깊은 중첩을 피하라고 안내한다 | 프로젝트 → 직접 할 일을 기본 경로로. 세부 체크는 작업 안 한 층까지만 |
| [monday.com은 그룹의 행을 입력하고 Enter로 추가](https://support.monday.com/hc/en-us/articles/115005319105-The-basics-of-items)하며 [subitem은 추가 깊이](https://support.monday.com/hc/en-us/articles/360011905480-All-about-subitems)다 | `+ 할 일` 한 줄 입력, Enter 연속 작성. 작업 묶음은 선택 사항 |
| [Linear는 프로젝트 이름만으로 시작](https://linear.app/docs/projects)하고 이슈를 직접 연결한다. [마일스톤의 날짜도 선택](https://linear.app/docs/project-milestones)이다 | 이름 → 첫 할 일까지 한 화면. 계획 날짜와 마일스톤은 필요할 때 추가 |

세 제품의 보드·권한·자동화 전체를 복제하지 않는다. 개인 운영자인 Moonlight에서는 고객 연결, 오늘/요약의 작업 원장, 월 평가와 저장 신뢰가 우선이다.

## 3. 적용한 정보 구조

```text
프로젝트
├─ 직접 할 일 N개 (기본, 체크 가능, 오늘/내 작업과 동일 task ID)
│  └─ 세부 체크 N개 (선택, 작업이 여러 단계일 때만)
├─ 마일스톤 N개 (선택, 결과 시점/묶음; 할 일의 선행 조건 아님)
├─ 작업 묶음 N개 (선택, 기존 subproject 유형의 화면 이름)
├─ 고객·기록·일정 (연결 정보)
└─ 완료 기록 (마무리 시점)
```

- **할 일**은 `project_id`가 있는 기존 `tasks` 행 하나다. 제목만으로 생성하며 기한·우선순위·메모는 나중에 더한다. 체크하면 그 행의 상태를 바꾸고 오늘/내 작업에서도 같은 결과를 본다. 프로젝트 전용 체크리스트 배열을 새로 만들지 않아 원장이 둘로 갈라지지 않는다.
- **세부 체크**는 기존 `tasks.meta.checklist`다. 작업 안에서 바로 한 줄 추가하고 체크하되, 세부 체크가 모두 끝났다고 작업 또는 프로젝트를 자동 완료하지 않는다. 드로어는 설명·기한·긴 메모를 편집할 때만 연다.
- **마일스톤**은 선택적 결과 시점이다. 새 할 일 생성에 필요하지 않다. 기존 `item_type=milestone` 레코드는 유지해 목록에 표시한다. 마일스톤과 여러 할 일의 실제 연결 관계는 현재 모델에 없으므로, `마일스톤 밑에 저장됐다`고 가장하지 않는다. 관계가 필요해질 때 명시적인 ID 연결과 집계 규칙을 별도 설계한다.
- **작업 묶음**은 현재 `item_type=subproject`의 UI 명칭이다. 폴더처럼 보일 수 있으나 독립 프로젝트는 아니다. 진짜 하위 프로젝트가 필요한 경우 별도 `projects` 관계 모델이 필요하며 이번 1차 재설계의 필수 경로에서 제외한다. 기존 데이터는 삭제·자동 변환하지 않는다.

## 4. 한 화면의 첫 30초

```text
갈무리 테스트                 진행 · 테스트 KA 학원       [···]
다음 행동  미완료 할 일 하나                  기한 없음

할 일  1/4 완료                         [진행률 25% · 계산 근거]
□ 11                               오늘 · [세부 2] [···]
□ 검토 요청 보내기                  내일          [···]
✓ 이전 회의 정리                    완료          [···]
+ 할 일 입력…   [Enter로 저장하고 다음 줄]

+ 마일스톤  ·  + 작업 묶음   (보조 메뉴)
결과·완료 기준  아직 없음 · 필요할 때 기록  [추가]
고객·기록·일정  필요할 때 펼침
```

1. **기본 상태**: 선택 프로젝트의 제목·고객·기한·실행 가능한 다음 할 일, 그리고 직접 할 일 목록이 첫 시야에 온다. 다음 행동 옆에 작은 진척 요약을 두고 계산 근거와 기록 시점을 같이 표시한다. 할 일이 0건이어도 실제 보고값이 있으면 이를 표시하고, 근거가 없으면 `—`와 추가 안내를 표시한다.
2. **한 줄 추가**: `+ 할 일`을 누르면 행 안에 커서가 들어간다. 제목 입력 후 Enter는 한 번 저장하고 다음 빈 줄을 연다. 빈 Enter는 저장하지 않고, Esc는 현재 초안만 닫는다. 블러 시 조용히 폐기하지 않으며 입력 보존 또는 명시적 취소를 제공한다. 모바일에도 동일한 입력 경로를 둔다.
3. **처리**: 행의 체크박스는 즉시 저장 상태를 표시한다. 응답 지연에는 저장 중, 실패에는 원상 복구와 같은 작업 재시도, 충돌에는 저장되지 않은 초안과 수정·재시도 경로를 남기며 최신 원장으로 다시 읽는다. 행 제목을 누르면 세부 체크와 일정·메모가 펼쳐지고, 세부 체크도 그 자리에서 한 줄 추가한다.
4. **정리**: `할 일 / 완료`의 단순 분류가 기본이다. 마일스톤과 묶음은 보조 `추가` 메뉴에서 선택한다. 기존 묶음과 마일스톤은 같은 목록 안에 유형 라벨로 읽히며, 안의 세부 체크는 펼칠 때 보인다. 기존 자료를 자동으로 평탄화하거나 복사하지 않는다.
5. **화면 밀도**: 데스크톱 작업 행은 약 40px, 모바일 탭 가능 영역은 최소 44px을 목표로 한다. 한 행의 기본 정보는 제목·기한/상태 한 줄이다. 긴 메타·보조 설명은 펼친 상태로 보내고 왼쪽 프로젝트 목록 행도 두 줄 이내로 압축한다. 키보드 포커스, 체크박스 이름, 저장 피드백은 유지한다.

## 5. `완성까지의 계획`을 결과·완료 기록으로 줄이기

**적용한 UI 조정**: 기본 화면에서 큰 계획 카드와 빈 타임라인을 제거하고 `결과·완료 기준` 요약만 둔다. 입력 전에는 경고성 `계획 필요`를 반복하지 않는다. 요약의 추가·편집으로 여는 짧은 드로어에서 결과물 한 줄·목표일 한 개·완료 기준을 입력한다. 완료 기준은 Enter로 이어 적거나 저장 시 마지막 입력까지 포함한다. 기존 긴 필드는 `자세한 계획`, 착수·링크·작동 확인·완료는 `실행·완료 기록`에 접어 유지한다. 프로젝트 완료로 진입하면 실행·완료 기록을 바로 펼친다. 시작일·프로토타입 예정일·작업/확보 시간·다음 버전은 기본 화면과 빠른 입력에서 제외한다. 사용자가 원할 때만 기록한다.

**기존 확정 완료 규칙의 변경 제안**: 현재 완료는 결과물, 전부 확인된 완료 조건, 프로토타입 작동 확인, HTTP(S) 결과물 링크, 병목 해소를 요구한다. 이는 온라인 프로토타입 프로젝트에 적합하지만, 회의·고객 관계·내부 정리 같은 프로젝트에 동일하게 적용하면 사실과 맞지 않는 링크와 프로토타입을 강요할 수 있다. 완료 조작 시 작은 검토 화면에서 (a) 실제 남긴 결과 한 줄, (b) 미완료 할 일이 있으면 그 수와 완료 후 노출 위치를 먼저 보여주고 `유지 / 옮기기 / 취소`를 명시적으로 선택, (c) 근거 링크·완료 기준은 있으면 검토하도록 **재승인할 계약**을 권장한다. `유지`를 제공하려면 완료 프로젝트의 미완료 할 일이 오늘/내 작업에 남는지 실제 쿼리로 확인하고, 남지 않으면 그 선택지를 제공하지 않는다. 결과 유형에 따라 검증이 필요한 프로젝트에는 기존 엄격한 경로를 선택할 수 있게 한다. 이 변경은 서버 완료 검증과 보고 의미까지 바꾸므로 화면만 먼저 완화했다고 완료 계약이 바뀐 것으로 표시하지 않는다.

진척과 완료는 다른 값이다. 작업 100%는 자동 프로젝트 완료가 아니고, 완료 프로젝트의 월 평가에는 완료일·결과·고객 연결을 남긴다. 진행 중 프로젝트도 해당 월의 상태 근거로 집계하되 완료 건수와 섞지 않는다.

## 6. 저장·이행 순서

| 단계 | 내용 | 합격 조건 |
| --- | --- | --- |
| P0 · 직접 실행 | 개요의 기본 섹션을 `할 일`로 변경, 기존 project task 전부 표기, 인라인 생성·완료·세부 체크 추가. 기존 `subproject`는 `작업 묶음`으로 표기 | 이름만 만든 프로젝트에서 추가 폴더/팝업 없이 Enter로 첫 할 일을 저장하고 새로고침 후 동일 ID로 보인다. 오늘/내 작업과 동기화된다 |
| P0 · 정보 밀도 | 큰 진척/빈 계획 카드 축소, 작업 목록 우선, 모바일 선택 프로젝트 우선 | 데스크톱·390px에서 첫 행동과 입력이 첫 화면에 보인다. 빈 데이터가 `미정` 카드 여러 개가 되지 않는다 |
| P1 · 계획 점진 노출 | 결과물·목표일·완료 기준의 짧은 입력, 긴 필드 접기, 변경 이유·이력 유지 | 기본 할 일 생성에 계획 입력이 필요 없고, 기존 완료 검증은 변경 전까지 그대로 작동한다 |
| 별도 결정 · 완료 계약 | §5의 프로젝트 유형별 완료 검증 재설계, 서버/API·월 평가 영향 검토 | 온라인/오프라인·고객/내부 프로젝트 모두 거짓 링크 없이 실제 결과를 기록할 수 있다. 미완료 작업 처리 선택이 남는다 |

쓰기 신뢰는 기존 task 생성의 안정적인 클라이언트 ID·중복 검사와 변경의 버전 비교를 재사용한다. 새 한 줄 입력은 한 의도에 같은 ID를 유지하고 중복 Enter/응답 유실 재시도에도 행이 하나여야 한다. 변경 요청의 응답 유실까지 강하게 멱등 처리하려면 앞선 프로젝트 저장 신뢰 스펙의 operation receipt가 추가로 필요하다. 체크 실패를 성공처럼 표시하지 않고 초안을 보존한다. 계층 변경으로 기존 `task.id`, 체크리스트 ID, 프로젝트/고객 참조, 완료 이력, 월 평가 원장을 복제하거나 소거하지 않는다.

## 7. 확인할 제품 판단

- **적용**: 첫 화면의 기본 단위를 `프로젝트 직접 할 일`로 바꾸고 하위 구조는 선택 사항으로 내린다. 이 요청의 핵심이다.
- **적용**: 현재 `하위 프로젝트`라는 이름을 `작업 묶음`으로 고친다. 실제 독립 프로젝트 관계가 생기기 전에는 폴더 안 폴더처럼 설명하지 않는다.
- **별도 승인 필요**: 완료 시 프로토타입·URL 강제를 프로젝트 유형에 따라 완화하는 서버 계약. 이는 2026-09-09 확정 스펙과 달라서 UI만으로 조용히 바꾸지 않는다.
- **실사용 후 판단**: 마일스톤에 할 일들을 실제로 연결하는 기능의 필요성. 1차에는 유형별 표시와 직접 할 일만으로 충분한지 관찰한다.

## 8. 구현·검증 기록

### 실행 화면과 입력

- `ProjectWorkList`에 모든 프로젝트 task를 바로 표시한다. 제목 입력 → Enter로 생성하고 행의 체크로 완료한다. `작업 묶음`과 `마일스톤`은 보조 추가 메뉴에서 선택한다. 레코드·ID·연결·체크리스트를 이관하거나 복제하지 않는다.
- 행 제목을 누르면 설명과 기존 세부 체크, `세부 체크 입력 후 Enter`가 같은 화면에 펼쳐진다. 완료 항목은 접어서 확인할 수 있고, 긴급 체크 딥링크는 정확한 체크에 포커스한다. 사라진 체크의 링크는 작업 제목을 펼치므로 상위 작업을 우연히 완료시키지 않는다.
- 왼쪽 프로젝트 목록 최소 높이 60px, 작업 기본 행 42px, 모바일 행 48px·주요 입력/버튼 44px 터치 영역을 적용한다. 빈 일정은 그리지 않고 실제 일정과 기록만 보조 펼침 구역에 둔다.
- 다음 행동이 실제 task 제목과 같으면 목록으로 이동한다. 자유 텍스트이면 새 할 일의 초안으로 채운 뒤 사용자가 제출한다. 300자를 넘는 원문은 잘라 저장하지 않고 줄이도록 안내한다.

### 저장 신뢰

- 생성 의도마다 클라이언트 ID를 한 번 만들고 저장 응답이 불명확한 동안 제목·프로젝트·유형을 고정한다. 중복 Enter와 재시도는 같은 ID·본문을 사용한다. 서버의 저장/중복 응답도 동일한 레코드인지 확인한다.
- 초안은 프로젝트/작업 ID별로 보관하므로 프로젝트 전환, 행 접기, 프로젝트 생성 화면 진입·취소 후에도 남는다. 결과 미확인에는 같은 의도로 재시도하고, 명확한 `invalid-input`/충돌에는 입력 다시 작성 경로를 둔다. 새로고침·탭 종료까지 복구하는 영속 초안은 이번 범위가 아니다.
- 세부 체크 추가는 고정 체크 ID와 task 버전 비교를 사용한다. 응답 유실 뒤 같은 ID·내용·초기 상태가 원장에 있으면 다시 추가하지 않는다. 50번째 항목의 응답 유실도 재시도가 가능하다. 다른 탭의 변경이나 다른 내용의 동일 ID는 덮어쓰지 않는다.
- 한글 조합 Enter는 제출하지 않는다. 성공 응답을 확인해야 저장됨을 표시한다. 완료 토글은 기존 버전 비교와 저장 계층을 재사용하며 새로운 서버 operation receipt를 도입하지 않는다.

### 결과 기록과 검증

- 큰 빈 계획 타임라인을 제거하고 짧은 결과 요약과 점진 노출 드로어를 적용했다. 결과물·완료 기준·링크 변경 시 이전 작동 확인이 무효가 되는 기존 서버 계약을 UI에도 반영한다.
- 접힌 입력에 오류가 있으면 해당 구역을 펼쳐 포커스를 옮긴다. 오류 문구는 label 밖에서 `aria-describedby`로 연결해 입력 이름이 바뀌지 않는다. 기존 완료 검증·보관 확인·고객 및 월 평가 집계 계약은 유지한다.
- `npm test`: **2,423개 / 통과 2,412 / 실패 0 / skip 11**. 저장 helper, 실제 JSX 입력 핸들러, 완료 검증, 긴급 정렬 회귀를 포함한다. `npm run check:contracts` 및 Hub production build 통과.
- 실제 Chrome에서 데스크톱과 390px 화면을 확인했다. 인라인 입력, IME, 저장 실패·같은 ID 재시도, 프로젝트 전환, 생성 화면 왕복, 체크 추가 재시도, 접힌 오류 입력 복구, 모바일 프로젝트 선택 및 가로 넘침을 점검했다. 브라우저 런타임 오류는 없었다.
- 브라우저 검증에서는 운영 원장을 읽기만 하고 **모든 API 쓰기를 차단**해 실패 경로를 재현했다. 실제 DB에 작업을 생성·완료한 검증으로 보고하지 않는다. 저장 성공·중복 응답·충돌은 helper/핸들러 테스트로 검증했다. 스크린리더 실기 테스트와 실제 운영자 연속 사용 평가는 별도다.

## 9. 할 일 편집 후속 조정 (2026-09-23)

- 운영자 요청에 따라 이름·항목 유형을 한 줄(2:1)에 배치했다. 메모는 하단에서 항상 작성할 수 있고 기존 `tasks.description`에 저장한다. 별도 메모 원장을 만들거나 기존 설명을 옮기지 않는다. 다음 행동만 선택 펼침에 남긴다.
- 목표 연결은 이 업무가 기여하는 기간 목표의 문맥 연결이다. 할 일 생성·완료나 프로젝트 진척의 필수 조건이 아니며 연결 자체로 실적이 늘어나지 않는다. 편집창에서 기본은 접힘이고 처음 펼칠 때만 읽는다. 열린 뒤에는 접거나 탭을 전환해도 연결 입력을 유지한다. 이 구역에서 AI 지원 화면까지 연쇄 노출하지 않는다.
- 목표가 없으면 정상 빈 상태와 `목표 만들기 · 새 탭`을 제공한다. 새 탭을 사용해 편집 중 메모를 유지한다. 읽기 실패는 작업공간/소속 확인과 일반 연결 오류를 구분하고, 실패를 `목표 없음`으로 처리하지 않는다.
- 반복 읽기 실패 원인은 실제 작업공간·기존 업무의 DB UUID를 목표 기능의 RFC variant 검사가 거절하는 것이었다. workspace와 연결 업무 ID만 기존 DB UUID 형식으로 검증하며 목표·지표·명령 ID의 엄격한 검증, 인증, 정확한 workspace 필터와 소속 판정은 유지한다. DB 수정·마이그레이션은 필요하지 않다.
- 실제 읽기로 기존 할 일 4건·프로젝트 4건의 목표 연결이 `live`임을 확인했다. Chrome에서 메모와 저장 본문 연결, 저장 실패 후 입력 유지, 탭 왕복, 목표 지연 조회·빈 상태, 390px 한 줄 이름/유형 배치를 검증했다. 브라우저의 API 쓰기는 모두 차단했다.

## 10. 프로젝트 선택 목록 관리 (2026-09-23)

- 운영자 요청에 따라 프로젝트 행 우클릭·`⋯`·Shift+F10에서 편집, 위/아래 이동, 삭제 확인을 연다. 삭제는 기존 `archived` 전환이며 연결된 할 일·체크리스트·고객·메모를 삭제하지 않는다. 확인창에 현재 읽은 미완료 수, 현재 월 평가에서 제외되는 점, 완료·보관에서 진행 상태로 다시 여는 방법을 알린다. 성공한 선택 프로젝트는 URL 선택을 비우고, 실패 시 확인창과 원래 행을 유지한다.
- 보관 시 `completed_at`을 null로 덮던 명령 정규화 결함을 수정했다. 기존 완료일은 보존하고, 명시적으로 진행 상태로 다시 열 때 완료일을 비우는 기존 계약은 유지한다. 보관 프로젝트의 현재 월 평가 제외 규칙은 바꾸지 않는다.
- 일반 클릭은 프로젝트 선택, 누르고 이동하거나 잠시 잡은 뒤 드래그하면 위치 변경이다. 삽입 위치를 1px 선으로 표시하고 드래그 뒤 선택 클릭을 방지한다. Esc·포인터 취소·창 포커스 이탈은 저장하지 않는다. 터치에서는 44px 손잡이로 이동하고 행 본체의 세로 스크롤을 유지한다. 메뉴의 위/아래 이동은 드래그 없이 사용할 수 있는 대안이다.
- 직접 정렬, 이름 오름/내림, 기한 빠른/늦은 순, 진척 낮은/높은 순, 최근 수정 순을 제공한다. 미정 기한·미측정/부분 진척은 방향과 관계없이 뒤에 둔다. 자동 정렬에서 드래그하거나 위/아래 이동하면 현재 화면 순서를 바탕으로 직접 정렬로 전환한다. 검색·소속 필터로 숨긴 항목의 저장 슬롯은 유지한다.
- 순서·정렬은 기존 폴더/브랜드 표시 순서처럼 브라우저 로컬 환경설정(`mlp.projectIndex.<workspace>.v1`)이다. 프로젝트 원장이나 기한을 수정하지 않으며 기기 간 동기화를 의미하지 않는다. 키보드 j/k 순회도 실제 표시 순서를 따른다. 메뉴와 확인창을 닫으면 원래 조작 위치로 포커스를 돌린다.
- 정렬·필터 슬롯 모델과 완료일 보존을 회귀 테스트로 검증했다. 브라우저에서는 우클릭/키보드 메뉴·삭제 확인과 실패·드래그/취소·새로고침 복원·정렬 전환 및 390px 터치 조작을 검증한다. 운영 원장은 읽기만 하며 삭제 요청은 차단해 실패 경로를 확인하고, 실제 운영 프로젝트를 삭제하지 않는다.
