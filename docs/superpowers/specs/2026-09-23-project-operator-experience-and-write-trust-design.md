# 프로젝트 개요의 실행성·저장 신뢰 설계

> 상태: **DRAFT · 평가와 권장안, 전체 구현 승인 아님** (2026-09-23). 선택 프로젝트의 **진척 근거 진행 바 UI만** 2026-09-23 요청으로 구현·로컬 검증했다. 나머지 흐름과 쓰기 계약은 이 문서의 권장/미정 상태를 유지한다.
> 요청: 프로젝트 화면을 실제 사용자와 PO 관점에서 평가하고 사용성·편의성·멱등성까지 설계 발전. 2026-09-23 후속 사용자 시나리오(할 일/요약/고객 → 프로젝트 → 하위 항목 체크리스트 → 고객과 함께 월 평가)를 §2·§7에 반영했다.

> 관계: `2026-09-09-project-delivery-lifecycle.md`의 완료·검증, `2026-09-21-crm-project-context-and-focus-design.md`의 목록/상세/입력 역할, `2026-09-13-pms-task-checklists.md`의 하위 프로젝트·마일스톤 저장 모델을 **유지**한다. 이 문서는 프로젝트 개요의 정보 우선순위와 쓰기 실패 복구를 구체화한다.

선택 프로젝트의 진척 영역은 근거 없는 21개 눈금과 범례 없는 두 번째 상태 막대를 제거했다. 한 진행 바에 하위 항목 완료 수 또는 보고값의 기록 위치·확인 가능한 시점을 묶고, 미집계·부분 읽기는 설명으로 표시한다. 보고값은 웹훅에서 올 수도 있어 입력 주체를 알 수 없으면 `수동`이라고 단정하지 않는다. 100%에서도 결과물 검증을 별도로 안내한다. 진척 계산식·저장 모델과 이 문서의 다른 권장안은 바꾸지 않았다.

## 1. 판단의 기준과 근거

프로젝트 화면은 일일 작업대의 복제본이 아니다. 운영자가 **할 일·요약·고객에서 발견한 신호를 프로젝트 맥락으로 연결하고, 가장 급한 하위 항목의 체크리스트를 처리한 뒤, 월말에 프로젝트와 고객의 결과를 함께 평가하는 곳**이다. `오늘/내 작업`은 프로젝트를 가로지르는 실행 목록, `프로젝트 개요`는 한 프로젝트의 목표·현재 근거·다음 행동, `목록`은 여러 프로젝트의 비교·선택을 맡는다.

2026-09-23 로컬 실데이터 화면을 데스크톱과 390×844 모바일에서 읽고, 프로젝트 선택 → `할 일·기록 열기` → 편집 → 목록에서 제거 확인창을 열어 보았다. 저장·보관은 실행하지 않았다. 코드 근거는 `project-portfolio-workspace.jsx`, `project-detail-panel.jsx`, `projects.jsx`, `pms-command-service.ts`다. 아래 관찰은 한 화면과 코드의 현 상태에 대한 것이며, 다수 사용자 실험의 결과가 아니다.

| 관찰 | 사용자에게 생기는 일 | PO 판단 |
| --- | --- | --- |
| 개요에서 `다음 행동` 문장 아래 `할 일·기록 열기`를 누르면 배경이 프로젝트 목록으로 바뀌며 상세 패널이 열린다. `개요` 토글은 그대로 선택되어 있고, 선택 사례에는 연결된 할 일이 없어 `할 일 추가`가 다시 나타난다 | “다음 행동을 실행”할 수 있을 것이라는 기대와 실제 진입점이 다르다 | **P0**: 행동의 원천과 버튼의 결과를 일치시킨다 |
| 선택 사례는 `58%`가 크게 보이나 하위 항목 0개, 기한 없음, 결과물 계획 필요, 위험 없음이 함께 보인다. 58%의 출처는 `보고된 진척`으로 표시된다 | 큰 숫자와 `위험 없음`을 검증된 상태로 오해할 수 있다 | **P0**: 출처·측정 시점·판단 가능 여부를 분리한다 |
| 모바일 첫 화면은 헤더·탭·검색·프로젝트 행이 차지하고, 선택 프로젝트의 다음 행동은 스크롤 뒤에 보인다 | 선택 후 행동까지 시야 이동이 길다 | **P1**: 모바일에서 선택 프로젝트의 요약을 먼저 보여준다 |
| 개요 상단에 `목록에서 제거`가 편집과 나란히 있고, 확인창은 보관/복구·기록 유지를 설명하며 체크를 요구한다 | 사고 방지는 되지만, 삭제·완료·보관의 뜻과 남은 할 일의 운명이 한눈에 다르지 않다 | **P1**: 관리 메뉴와 보관 전 영향 요약을 명료화한다 |
| 편집 드로어에는 이름·분류·브랜드·목표·고객·상태·우선순위·다음 행동·기한이 한 번에 노출된다. 고객 목록은 길다 | 다음 행동 하나를 고치기에도 전체 양식을 훑는다 | **P1**: 빈도가 높은 수정을 짧은 경로로 만들고 나머지는 접는다 |
| `개요/목록/백로그/Board/메모/Timeline/To-dos`가 동등한 보기로 보이고 상위 PMS 내비게이션에 Calendar/Roadmap/Rhythm도 있다 | 처음 방문한 사용자가 “개요”와 다른 보기의 역할을 학습해야 한다 | **P2**: 역할별 그룹과 명칭을 검증하되 기능을 섣불리 없애지 않는다 |

잘 작동하는 부분도 있다. 선택 프로젝트와 탐색 목록이 함께 있고, 진행 수치의 출처(`보고된 진척`)를 이미 드러내며, 제거는 실제로 보관 상태를 사용하고 복원 경로를 알려 준다. 고객 연결·할 일/기록 전환·편집의 저장 충돌 감지도 존재한다. 따라서 새 객체나 별도 대시보드를 만들기보다 이 흐름의 의미를 정확하게 만든다.

## 2. 실제 사용자 작업 시나리오

사용자가 제시한 기본 루프는 다음이다. **할 일/요약/고객에서 발견 → 프로젝트 사항·고객 맥락 확인 → 급한 하위 프로젝트·마일스톤의 체크리스트 처리 → 진행/완료 결과를 고객과 함께 월 평가에서 확인**. 프로젝트 첫 화면은 이 루프의 중간 허브여야 한다. 모든 내용을 한 번에 펼친 대시보드도, 매번 상세 편집을 여는 폼도 아니다.

| 진입 | 사용자가 알고 싶은 것 | 프로젝트 화면의 즉시 결과 | 돌아갈 곳 |
| --- | --- | --- | --- |
| `오늘/내 작업`의 할 일 | 이 일이 어떤 목표/하위 항목에 속하고 지금 뭘 체크해야 하나 | 해당 프로젝트와 하위 항목을 선택·펼치고 관련 체크 항목에 초점. 같은 task ID를 사용 | 원래 할 일 행과 필터·스크롤 |
| `요약`의 프로젝트 신호 | 왜 관심 대상으로 올라왔고 가장 급한 부분은 무엇인가 | 신호 이유, 마감/막힘, 다음 행동, 급한 하위 항목 첫째를 바로 표시 | 원래 요약 카드 |
| 고객 상세의 연결 프로젝트 | 고객 약속과 프로젝트 결과가 어떻게 이어지나 | 관련 고객 한 줄과 최근 접점, 프로젝트 진행·마일스톤·다음 행동 | 선택 고객과 상세 탭 |
| 프로젝트 목록/검색 | 어느 프로젝트를 볼까 | 선택 프로젝트의 핵심 정보와 `지금 처리할 항목` | 목록의 검색·선택 상태 |

1. **아침 20초 확인**: 위 어느 표면에서 와도 프로젝트 제목·고객·다음 행동·가장 급한 하위 항목이 첫 시야에 들어온다. 진행률만으로 우선순위를 결정하지 않는다.
2. **하위 항목 처리**: 하위 프로젝트/마일스톤은 독립 projects 레코드가 아니라 기존 task의 유형이다. 각 항목 안에 일정·상세·체크리스트를 둔다. 한 항목의 체크를 끝내도 하위 항목 상태나 상위 프로젝트의 `완료`를 자동으로 확정하지 않는다.
3. **회의 직후 30초 수정**: 다음 행동 또는 기한을 고치고 저장 결과를 확인한다. 변경하지 않은 고객·목표는 다시 보내지 않는다. 실패하면 입력이 남고 같은 의도를 재시도한다.
4. **진척 점검**: `58%`가 수동 보고인지 체크리스트 계산인지, 언제/무엇을 근거로 했는지 확인한다. 결과물 검증 상태와 별개임을 알 수 있어야 한다. 100% 수치가 자동 완료를 뜻하지 않는다.
5. **월 평가**: 완료한 프로젝트와 월말 진행 중인 프로젝트를 모두 보되 서로 다른 줄/집계로 표시한다. 고객 연결 프로젝트는 해당 고객의 평가 근거에서 다시 찾을 수 있어야 한다. 내부 프로젝트는 고객 연결 없이 프로젝트 평가에 남는다.
6. **보관**: 오래된 프로젝트를 활성 목록에서 치울 때 미완료 할 일·고객·기록의 영향을 확인한다. 완료 인증, 월 평가 포함, 보관은 서로 다른 행동이다.

## 3. 제안하는 화면 계약

### 개요: 선택한 프로젝트의 판단·한 걸음

데스크톱은 좌측 **프로젝트 선택/검색**, 우측 **선택 프로젝트**를 유지한다. 우측 상단의 시선 순서는 `제목·상태/소속 → 연결 고객의 최근 접점·다음 약속(있을 때) → 실제 다음 행동 → 지금 처리할 하위 항목 → 근거 있는 진행·기한 → 결과물/전체 마일스톤`이다. 고객 정보는 최근 접점 한 줄만 두고 전체 기록은 고객 화면으로 연결한다. 현재의 큰 진척 숫자와 계기판은 개성을 유지하되 다음 행동보다 시각적으로 앞서지 않게 면적을 줄인다. 게이지의 눈금은 데이터 해석을 돕는 경우에만 남긴다. 수치·원천·측정 시점은 같은 시각 단위에 묶고, 0건/미기록은 빈 게이지 대신 설명을 둔다.

```text
프로젝트 선택                 | Content Engine Rollout            [편집] [···]
검색 · 전체/진행/관심         | 진행 · Class.Moon · 연결 고객/최근 접점
행: 제목 / 다음 행동 유무     | 다음 행동  카드뉴스 산출물 검토   [할 일 만들기]
    기한/막힘 / 근거 있는 진척 | 지금 처리  마일스톤 A › 체크 항목  [열기/체크]
                              | 진척 58% · 수동 보고 · 측정일 확인 필요
                              | 기한 미정 · 결과물 계획 필요 · 판단 자료 부족
                              | 하위 프로젝트·마일스톤 전체  |  기록·자료
```

모바일 `개요`는 **선택 프로젝트 요약이 첫 화면에 오는 단일 열**로 권장한다. 현재의 7개 프로젝트 전체 목록은 `프로젝트 바꾸기` 검색 시트 또는 `목록`에서 연다. 프로젝트를 바꾼 뒤 같은 뷰·스크롤 문맥을 복원한다. 목록 탐색을 원하면 `목록`을 직접 선택할 수 있다. 모바일에서 게이지·하위 항목은 다음 행동 아래로 내려가고, 주요 CTA는 첫 화면에서 보인다.

`개요`와 `목록`을 1차 선택지로 설명하고, 백로그/보드/할 일은 `작업 보기`, 메모/타임라인은 프로젝트 문맥과 계획 내비게이션에 맞춰 재배치하는 **정보구조 가설**을 둔다. 실제 이용 빈도와 딥링크를 확인하기 전에는 탭을 삭제하거나 URL을 바꾸지 않는다. 상단 `Projects` 반복 표기와 전역 `New`/페이지 `Project N`의 경쟁도 같은 단계에서 정리한다.

### 다음 행동: 표시와 실행을 같은 계약으로

현재 `nextAction`은 프로젝트 텍스트, 업데이트 문구, 다음 미완료 task 제목 중 하나일 수 있다. 텍스트와 task를 같은 실행 객체처럼 보이지 않는다.

| 원천 | 기본 표시 | 1차 버튼 | 저장 원칙 |
| --- | --- | --- | --- |
| 연결된 미완료 task | 제목·기한·상태·`할 일` 출처 | `할 일 열기` | task ID로 이동, 새 task를 만들지 않음 |
| 프로젝트의 자유 텍스트 `next_action` | 문구·`프로젝트 메모` 출처·수정 시점 | `할 일로 만들기` 또는 `다음 행동 편집` | 사용자가 선택한 때에만 task 생성. 생성 후 task ID 연결/중복 방지 |
| 업데이트 기록에서 제안된 문구 | 문구·`기록에서 가져옴` 출처·기록 시점 | `확인 후 할 일로 만들기` | 자동 확정/자동 완료 금지 |
| 없음 또는 읽기 실패 | `다음 행동 미정` 또는 `일부 기록 확인 불가` | `다음 행동 입력` / `다시 읽기` | 실패를 빈 상태로 위장하지 않음 |

텍스트가 task가 아닌 경우 `할 일·기록 열기`처럼 목적지가 모호한 버튼을 쓰지 않는다. task 생성은 현재 프로젝트·고객 문맥을 이어받되 동일한 메모나 약속을 자동으로 두 번 만들지 않는다. 다음 행동을 수동으로 바꾸면 기존 task의 완료나 고객 약속을 조용히 변경하지 않는다.

### 진척·위험·결과물: 서로 다른 판단 축

- `진척`: 체크리스트/마일스톤 계산값, 명시적 수동 보고, 값 없음 중 하나다. 큰 수치 옆에 **원천과 마지막 기록 시점**을 둔다. 계획한 항목이 0건이면 `계산할 항목 없음`을 표시하고 수동 보고값을 계산값처럼 합성하지 않는다.
- `결과물 검증`: 완료 조건/프로토타입/결과물 링크를 사용하는 기존 `계획·검증` 흐름이다. 진척 100%와 프로젝트 `완료`는 별개다. 결과물 계획이 비어 있을 때는 단일 `계획 보완` 진입점을 보여주고, 동일한 경고를 여러 구역에 반복하지 않는다.
- `위험`: 현재 코드는 막힘/기한 지남이 아니면 `위험 없음`으로 표기한다. **권장**은 `막힘 또는 초과`, `현재 확인된 신호 없음`, `판단 자료 부족`의 세 상태다. 기한이 없는 프로젝트 자체를 위험으로 칠하지 않는다. 다만 명시적 검토 날짜나 충분한 근거가 없으면 안전 판정도 하지 않는다. 프로젝트 분야별 지연 임계값은 기존 확정/미정 경계를 지키며 여기서 새 수치를 확정하지 않는다.
- `월간 검토`: 기한 없는 프로젝트를 한 달마다 다시 보자는 운영 원칙은 유지한다. 검토 예정일·마지막 검토일이 없다면 `검토 미설정`으로 보여준다. 실제 알림/주기 자동화는 별도 승인 범위다.

시각적으로는 Moonstone 선택/초점, 중립 완료, 긴급 손실/실패에만 danger를 쓴다. 수치 강조는 `DESIGN.md`의 `.stat`, 소형 계기·날짜는 `.mono`를 따른다. 선은 1px 토큰, 상태는 텍스트와 아이콘/형태를 함께 쓴다. 새 색상으로 프로젝트 종류나 평상 진척을 칠하지 않는다.

### 편집·보관

- `편집`의 기본 진입은 현재 목표를 살린다. 빠른 수정은 `다음 행동` 1필드와 저장, 전체 편집은 `기본 정보 / 목표·연결 / 관리`로 접어 보여준다. 필드의 현재값과 변경 여부를 분명히 하고, 저장 중 중복 클릭을 막는다. 고객 선택은 긴 native 목록 대신 실제 검색 가능한 기존 선택기 패턴의 재사용을 검토한다.
- `완료`는 검증 절차를 통과한 상태, `보관`은 활성 목록에서 빼는 정리 행동, `영구 삭제`는 별도 정책이다. 화면 문구는 `프로젝트 보관`을 쓰고, `목록에서 제거`는 설명 문장에 둔다. 보관은 `···` 관리 메뉴에 넣어 기본 편집/실행과 시각적으로 분리한다.
- 보관 확인창은 프로젝트명, 미완료 할 일 수, 연결 고객/기록의 유지 여부, 복원 위치를 보여준다. **미완료 할 일이 남았을 때 그 할 일이 오늘/내 작업에 계속 보이는지**를 구현 전에 실제 쿼리로 확인하고, 그 결과를 확인창에 명시한다. 보이지 않게 되는 경우에는 할 일 이전/유지/취소의 명시적 선택 없이 보관하지 않는다. 복원은 같은 프로젝트 ID를 다시 활성화한다.
- 현재의 모든 보관에 대한 확인 체크박스는 안전성 대비 마찰을 검증할 대상이다. 기본은 명확한 확인 버튼과 취소이며, 미완료 할 일/연결 작업이 있는 고영향 보관에만 추가 결정을 요구하는 것을 권장한다. 영구 삭제 UI는 이 단계에 넣지 않는다.

## 4. 저장·멱등성 계약

현재 생성은 안정적인 클라이언트 ID와 같은 내용 재요청 판정이 있고, 편집/보관은 `expectedUpdatedAt` 비교와 요청 중 중복 클릭 방지가 있다. 이는 **동시 수정 보호**이지만, 첫 PATCH가 저장된 직후 응답만 유실된 경우의 안전한 재전송까지 보장하지 않는다. 성공 후 재시도는 충돌로 보일 수 있고, 사용자는 저장 여부를 알 수 없다.

**권장 최종 계약**:

1. 각 사용자 의도(프로젝트 수정, 보관, 복원, 체크리스트 항목 변경, `다음 행동 → 할 일` 전환)에 안정적인 `operationId`를 하나 발급한다. 같은 의도의 재시도는 같은 ID·같은 정규화된 payload를 사용한다. 사용자가 내용을 다시 편집하면 새 의도/새 ID다.
2. 서버는 workspace·actor·command·entity·operationId와 payload 지문을 원자적으로 기록한다. 같은 ID·같은 내용은 최초 확정 결과와 동일한 record ID/버전을 돌려주고, 같은 ID·다른 내용은 충돌시킨다. 이 기록과 프로젝트/할 일 변경·이력 부수 효과는 같은 트랜잭션 경계에 있어야 한다.
3. 최초 요청의 `expectedUpdatedAt`은 다른 사용자 수정과 충돌을 감지한다. 동일 의도의 재전송은 **작업 영수증 조회가 먼저**, 그다음 버전 검사를 한다. 따라서 저장은 한 번, 결과 조회는 여러 번 가능하다.
4. 네트워크 타임아웃은 `실패`로 단정하지 않고 `저장 결과 확인 중`으로 둔다. operationId로 결과를 조회해 `saved/duplicate/conflict/failed`로 수렴한다. 영수증 조회도 안 되면 입력을 보존하고 같은 의도로 재시도하게 한다. 단순히 새 operationId로 다시 보내지 않는다.
5. 도입 전 단계에서는 정확한 현재값·버전 재조회로 이미 반영됐는지 대조해 불확실성을 줄일 수 있지만, 마감 변경 이력/상태 부수 효과까지 포함한 강한 멱등성은 영수증 없이 주장하지 않는다. `preview`/read error를 성공 토스트로 바꾸지 않는다.

```text
사용자 저장 → pending(operationId) → 응답 saved
                         ├─ 응답 유실 → receipt 조회 → saved/duplicate → 화면 갱신
                         ├─ 다른 편집 → conflict → 최신값 비교, 초안 보존
                         └─ 연결 불가 → 결과 미확인, 같은 operationId로 재시도
```

UI는 성공 후 영속 기록과 갱신된 버전을 확인한다. 저장 성공·목록 재조회 실패는 `저장은 완료, 화면 갱신 실패`로 분리해 알린다. `duplicate`는 오류가 아니라 원래 저장의 결과다. 보관/복원, 기한 변경 이력, task 생성의 중복 부수 효과는 서비스 테스트로 고정한다.

## 6. 확정/권장/미정 경계

- **기존 확정 유지**: 개인 운영 원장, 이름만 빠른 생성, 결과물 검증 후 완료, 완료와 보관 분리, 하위 프로젝트/마일스톤의 기존 task/meta 구조, 기한 없는 프로젝트의 월간 검토 원칙, 실패 시 입력 보존.
- **이번 권장안**: 행동 원천에 따라 CTA 분기, 진척/위험의 근거 표시, 모바일 요약 우선, 급한 하위 항목과 체크리스트 직접 처리, 진입/복귀 문맥 보존, 진행·완료 프로젝트의 월 평가 집계, 보관 전 미완료 할 일 영향 확인, operationId 기반 쓰기 영수증. 구현 전 실제 데이터 경로 확인이 필요하다.
- **미정**: archived 프로젝트의 미완료 할 일이 현재 어느 작업 목록에 남는지와 그때의 원하는 운영 정책, 수동 진척의 신선도 기준, 7개 보기를 어떤 빈도로 쓰는지, 보관 체크박스를 언제 추가 요구할지, operation receipt의 보존 기간, 고객 평가의 정성·정량 가중치. 이 항목을 임의의 확정 규칙처럼 코드에 박지 않는다.

## 7. 후속 사용자 시나리오의 편의성 계약

### 한 번 찾은 맥락을 다시 찾지 않게 한다

`오늘/내 작업`, 요약, 고객 상세의 프로젝트 진입은 같은 `projectId`를 전달한다. 하위 항목에서 온 링크는 `taskId`, 특정 체크리스트에서 온 링크는 `checkId`까지 전달한다. 프로젝트 화면은 데이터를 읽은 뒤 해당 프로젝트를 선택하고 하위 항목을 펼쳐 체크 항목에 초점을 둔다. 현재 `?project=`와 `?task=` 딥링크 계약을 확장하되 기존 URL을 깨지 않는다. URL에는 내용 원문이나 고객 이름을 넣지 않는다. 권한/소속이 맞지 않거나 기록을 못 읽으면 다른 프로젝트를 임의로 선택하지 않고 이유와 안전한 돌아가기를 표시한다.

돌아가기는 링크 출처의 허용된 내부 경로, 선택한 필터·스크롤·고객 상세 탭을 복원한다. 같은 프로젝트를 여러 표면에서 별도 사본으로 편집하지 않고 원장 ID로 연결한다. 요약 카드와 고객 카드에는 프로젝트의 **이름·상태·기한/막힘·다음 행동 한 줄**만 싣고, 체크리스트 전체는 프로젝트에서 연다. 링크를 누르는 순간 읽기가 실패해도 원래 카드의 값이 “없음”으로 바뀌지 않는다.

### `지금 처리할 항목`은 하위 구조 위에 놓인 진입 레일이다

프로젝트 상단에서 `다음 행동` 아래에 최대 3개의 **실제 하위 항목**을 보여준다. 각 줄은 `하위 프로젝트/마일스톤 › 체크 항목`, 기한, 막힘 이유, 완료 여부를 담고 동일한 task/check ID의 본문으로 이동한다. 별도 할 일이나 일정 사본을 만들지 않는다. 정렬은 이미 확정된 업무 원칙처럼 실제 기한 지남/오늘을 우선하고, 그다음 막힘과 가까운 기한을 보여준다. 4건 이상이면 `외 N건 보기`로 전체 목록을 연다. 기한 없는 항목은 위험으로 칠하지 않고 일반 목록에 둔다. 급한 항목이 없으면 이 레일을 숨기고 상위 프로젝트의 다음 행동을 유지한다.

하위 항목의 본문 행은 `제목 · 상태 · 가장 가까운 기한 · 체크리스트 n/m · 다음 미완료 항목` 정도로 압축한다. 펼치면 상세와 일정, 체크리스트가 한 자리에서 보인다. 날짜가 있는 체크 항목은 해당 줄에 표시하고 접힌 `일정 N`은 모아보기만 맡는다. 마일스톤을 완료했다고 상위 프로젝트의 결과물 검증을 자동 통과시키지 않는다.

현재 개요의 체크 항목은 아이콘과 텍스트여서 완료하려면 `상세·일정 편집`을 열어야 한다. **권장**은 체크 항목 한 줄에 실제 `Checkbox`를 두고, 누르면 기존 task의 `meta.checklist`를 정확한 `updated_at` 버전으로 저장하는 것이다. 체크가 켜졌다는 표시와 `저장 중/저장됨/실패`를 구분하고, 저장 실패 시 완료로 남겨 두지 않는다. 같은 체크를 연속 눌러도 한 번의 의도로 처리하며 다른 체크·메모·날짜는 보존한다. 충돌이 나면 최신 체크리스트와 내 변경을 비교해 선택하게 하고 초안을 잃지 않는다. 체크리스트 100%와 하위 task 완료 상태는 기존 계약대로 별개다. 키보드 Space/Enter와 모바일 터치 영역을 포함한다.

### 고객과 프로젝트의 월 평가: 함께 보되 각각 한 번만 센다

월 평가의 첫 행은 **프로젝트: 이번 달 완료 N / 월말 진행 N (그중 막힘 N)**, 다음 행은 **고객: 그달의 연락·후속 현황과 연결 프로젝트**로 권장한다. 고객별 연락·후속 수치는 CRM 원장에서 정의와 기간 근거가 확인된 항목만 표시하고, 별도 고객 점수나 가중치는 여기서 만들지 않는다. 고객이 없는 내부 프로젝트도 프로젝트 집계에 포함한다. 고객 상세에서는 연결 프로젝트의 월 결과를 근거로 보여주되 고객 실적 숫자에 프로젝트 한 건을 또 더하지 않는다. 현재 프로젝트와 고객 연결은 `lead_id` 또는 `customer_account_id` 중 하나이므로 `projectId → customerRef` 한 관계를 사용하고, 미래의 다중 고객 연결을 가정해 임의 복제하지 않는다.

월 기준은 Asia/Seoul의 `[월초 00:00, 다음 월초 00:00)`이다. **이번 달 완료**는 그 기간에 완료로 전이했고 월말에도 완료 상태인 고유 프로젝트, **월말 진행**은 월말 시점에 진행/막힘이었던 고유 프로젝트다. 진행 중인 현재 달은 마감된 월말처럼 보이지 않게 `현재까지 완료/현재 진행 · 잠정`으로 표시한다. 같은 달 완료 후 다시 연 프로젝트는 월말 진행에만 넣고 `월 중 완료 후 재개` 사건을 기록으로 보여준다. 두 숫자를 더할 때 같은 프로젝트가 중복되지 않는다. 이전 달에 완료된 프로젝트는 그 완료 달의 평가에 남고 이번 달 새 완료 수에는 넣지 않는다. 보관은 완료로 세지 않는다. 진행 중 프로젝트는 평가 기준 시점의 진척 근거, 기한 대비 차이, 최근 활동, 병목, 다음 행동을 카드에 남긴다. 완료 프로젝트는 검증된 결과물과 완료일을 남긴다. `완료 가능성`은 근거가 있는 경우에만 판단하고 AI 추정을 확정 점수로 쓰지 않는다.

현재 `projects.completed_at`은 재개 시 비워지고, 체크리스트 항목에는 완료 시각이 없다. 따라서 **현재 행만으로 지난달의 완료 전이와 체크리스트 처리량을 정확하게 복원할 수 없다.** 월 평가를 영속 기능으로 만들 때는 프로젝트 상태 전이를 append-only 사건으로 남기고, 월말의 진행률/고객 연결/근거를 월별 스냅샷으로 고정해야 한다. 같은 상태 전이 재시도는 §4의 operationId 하나로 사건 한 건만 기록한다. 월 평가 생성·재실행은 `(workspace, month, projectId)`를 항목 식별자로 사용하며 동일 생성 의도는 같은 결과를 돌려준다. 확정 후 정정은 기존 값을 조용히 덮지 않고 새 revision과 이유를 남긴다. 과거 사건이 없는 달은 현 상태의 **임시 미리보기**라고 명시하고 확정 월 실적을 꾸며내지 않는다. 체크리스트의 월 처리량은 완료 시각/사건이 도입되기 전까지 표시하지 않는다.

월 평가에서 항목을 눌러 프로젝트/고객의 원본 근거로 돌아갈 수 있게 한다. 평가 입력은 `계속/보류/완료 후보` 같은 운영 판단과 한 줄 메모만 받고, 원장 상태 변경은 별도 검증 절차를 통과한 명시적 행동일 때만 한다. 월 평가를 열거나 스냅샷을 조회하는 것만으로 프로젝트·고객 기록을 바꾸지 않는다.

**추가 인수 기준**: 오늘의 task에서 체크 항목으로 들어가 한 번 체크하고 원래 할 일로 돌아오기; 고객에서 연결 프로젝트를 확인하고 같은 고객 탭으로 돌아오기; 서로 다른 하위 항목의 기한이 겹칠 때 급한 이유를 설명하기; 체크 저장 타임아웃/두 창 충돌에서도 완료를 중복 기록하지 않기; 9월 30일 23:59 KST 완료와 10월 1일 00:00 KST 완료를 다른 달로 세기; 완료 후 10월에 재개해도 9월 확정 집계가 바뀌지 않기; 한 고객에 여러 프로젝트가 있어도 프로젝트와 고객을 각각 고유 ID로 세기; 고객 미연결·보관·부분 읽기 상태에서 숫자를 허위로 채우지 않기.
