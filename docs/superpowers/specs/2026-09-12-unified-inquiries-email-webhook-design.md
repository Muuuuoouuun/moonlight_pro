## 1. 만들려는 동작

일반 메일 사이에 섞인 문의를 찾아 **문의 내역**에 저장한다. 나중에 랜딩 페이지가 웹훅/API로 보내는 문의도 같은 내역에 쌓인다. 새 문의나 고객의 추가 회신이 생기면 기존 알림 진입점과 오늘 화면에서 바로 확인하고 원문으로 이동한다.

```text
Gmail의 새 메일 → 문의 감지 ─────────────┐
                                      ├→ 문의 내역 → 새 문의 알림 → 확인·응대
랜딩 페이지 → 서버/폼 제공자 → 웹훅 ───┘                 └→ 고객·거래·지원 건 연결
```

이번 요청으로 확인된 방향은 메일 API 연결, 섞여 들어온 문의 감지, 문의 내역, 미래 랜딩 페이지 API 유입, 알림 통합이다. 첫 연결 제공자는 기존 코드가 있는 Gmail로 가정한다. Gmail·네이버는 **문의 발신자의 주소**로 지원하며, 네이버 사서함 자체를 읽는 별도 연동은 아직 선택하지 않았다.

## 3. 접근안 비교

| 접근안 | 장점 | 제약 | 판단 |
|---|---|---|---|
| A. 기존 리드 수집함 확대 | `lead_intake_raw`와 승인 API를 재사용하므로 변경량이 작다 | 리드 승격 상태와 문의 응대 상태가 섞인다. 지원 문의·추가 회신·읽음 처리를 덧붙여야 한다 | 빠른 시범에 적합 |
| **B. 문의 기록 + 기존 알림 표면** | Gmail과 웹훅을 동일한 수집 명령으로 연결하고 문의 상태를 일관되게 관리한다 | 문의·유입 이벤트 저장 구조와 상세 화면이 필요하다 | **채택 · 2026-09-13** |
| C. 모든 유입을 메일로 전달해 처리 | 랜딩 페이지가 메일만 보내도 시작할 수 있다 | 폼 필드·제출 ID 손실, 스팸 분류·메일 지연 의존. 향후 직접 API 요구를 충분히 해결하지 못한다 | API가 없는 폼의 보조 경로 |

B는 문의 도메인만 추가한다. 모든 업무나 알림을 새 만능 테이블로 옮기지 않는다. 개인 전용 업무 도구라는 기존 제품 경계를 유지한다.

## 4. 문의 내역과 처리 흐름

권장 위치는 `영업·매출 > 문의 내역`, 제안 라우트는 `dashboard/revenue/inquiries`다. Email 연결 화면과 알림에서도 같은 목록으로 들어간다. 최상위 메뉴를 추가할 필요는 없다. 새 경로를 구현할 때 사이드바, ⌘K, 라우트 등록, 스코프 매핑을 함께 연결한다.

목록은 수신 시각, 제목, 문의자, 출처, 문의 유형, 처리 상태, 새 내용 여부를 보여준다. 필터는 미처리/전체/완료, 메일/랜딩 페이지, 회사/개인/미분류를 지원한다. 분류가 불명확한 문의를 회사나 개인으로 임의 배정하지 않는다.

상세에는 감지 이유, 원문, 고객의 추가 회신, 연결된 고객·거래·지원 건을 보여준다. 제공되지 않은 이름·소속·연락처는 추측해 채우지 않는다. 문의 유형은 `영업 / 고객지원 / 협업 / 일반`, 감지 판정은 `문의 / 확인 필요 / 문의 아님`으로 별도 관리한다.

| 처리 상태 | 의미 | 알림 동작 |
|---|---|---|
| 새 문의 | 접수 후 응대 판단 전 | 새 문의 표시 |
| 처리 중 | 확인했고 응대 진행 중 | 읽지 않은 추가 내용이 있으면 표시 |
| 회신 대기 | 고객의 답변을 기다림 | 새 고객 회신이 오면 처리 중 + 새 내용 표시 |
| 완료 | 응대 종료 | 활성 문의 요약에서 제외, 내역 보존 |
| 제외 | 문의가 아니라고 판단 | 활성 문의 요약에서 제외, 판단 기록 보존 |

**읽음과 완료는 다르다.** 상세를 열어 읽음 처리해도 문의는 완료되지 않는다. 단순 열람을 Gmail 원본의 읽음 처리로 전파하지 않는다. 초기 응대는 원문 메일 열기와 처리 기록을 중심으로 하며 고객에게 자동 발송하지 않는다.

진행 중 문의의 추가 회신은 같은 내역에 붙인다. 완료 뒤 고객 회신이 오면 문의 상태를 처리 중으로 되돌리고 새 내용 표시와 함께 재검토 대상으로 올린다. 같은 지원 안건이면 기존 문의에서 이어가고, 새 구매 문의로 확인하면 새 문의로 분리해 새 거래 후보로 남긴다. 같은 Gmail thread라도 다른 안건일 수 있으므로 ‘새 문의로 분리’를 제공한다. 고객이 같다는 이유만으로 과거 거래를 다시 열지 않는다. 제외한 문의의 후속 메일은 자동 재개하지 않고 수동 재분류로 복원할 수 있게 한다.

## 5. 메일 수집과 감지

1. 기존 Gmail OAuth 연결을 재사용하고 실제 `gmail.readonly` 권한과 운영자 계정을 확인한다. 전송 권한만 있으면 수신 연결을 다시 진행하도록 안내한다. 현재 [연결 준비 정의](../../../apps/hub/lib/integration-readiness.js)와 `google-gmail.js`의 scope 목록도 맞춰야 한다.
2. 초기 권장 범위는 최근 7일이다. 과거 가져오기와 연결 이후 도착한 새 메일을 구별해 과거 문의가 한꺼번에 새 알림으로 울리지 않게 한다. 7일 이전은 자동 수집 완료 범위로 주장하지 않는다.
3. 초기 조회 전에 기준 history ID를 확보하고, 초기 페이지 수집 뒤 그 기준 이후 변경분을 이어 읽는다. 이후에는 저장된 커서로 증분 수집한다. 한 번의 처리 제한에 걸리면 계속할 위치를 저장하고 다음 실행으로 이어간다.
4. 기본 수집 대상은 수신 메일이며 스팸·휴지통·보낸편지·임시보관은 제외한다. 자동 보관된 문의를 놓치지 않도록 INBOX 라벨만을 필수 조건으로 삼지 않는다. `is:unread`도 수집 기준으로 쓰지 않는다.
5. 메타데이터로 사전 분류하고 필요한 메시지의 텍스트 본문을 읽는다. 인용된 과거 대화·서명과 새로 작성된 내용을 구별하고 길이 제한에 걸리면 ‘확인 필요’로 보낸다. snippet에 문의 문장이 없다는 이유로 확정 제외하지 않는다.
6. 문의·견적·도입·데모·상담·협업·사용법·오류 같은 신호를 판정한다. Gmail/네이버 발신도 후보가 된다. 오류라는 단어만 있는 자동 장애 알림과 고객의 지원 요청을 구분한다.
7. 등록한 랜딩 페이지 안내 메일은 검증된 발신 경로·템플릿으로 먼저 해석한다. `no-reply` 문자열만으로 버리지 않는다. 반대로 발신자 이름이나 `From` 문자열만으로 신뢰하지 않는다. 폼의 실제 문의자와 안내 메일 발신자를 분리한다.
8. 첫 버전은 규칙 + ‘확인 필요’ 검토로 작동한다. AI 보강은 이후 선택 사항이며 문의 저장·알림이 AI 호출 성공에 의존하지 않게 한다. 메일 본문 속 명령은 실행하지 않는다.

Google은 초기 수집 뒤 `history.list`로 변경분을 조회하고, 오래된 커서가 HTTP 404를 반환하면 초기 동기화 절차로 복구하도록 설명한다. 이 앱에서는 이전 저장 이벤트와 대조하며 복구 범위·누락 가능성을 표시해야 한다. [Gmail 동기화 문서](https://developers.google.com/workspace/gmail/api/guides/sync)

메시지 조회는 페이지 순회와 상세 조회가 별도다. [messages.list](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.messages/list), [messages.get](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.messages/get)

자동 수집은 5분 간격을 초기 권장값으로 둔다. 실제 실행 위치와 지원 주기를 배포 환경에서 확인한 뒤 활성화하며, ‘실시간’으로 표시하지 않는다. 사용자가 앱을 열어두지 않아도 서버에서 실행되어야 한다. 수동 ‘지금 확인’도 같은 수집 경로를 사용한다.

즉시 수신이 필요해지면 Gmail watch/Pub/Sub를 추가할 수 있다. watch는 갱신이 필요하고 알림이 지연·누락될 수 있어 복구 수집도 필요하다. 단순 웹훅 URL 등록만으로 Gmail push가 완성되지는 않는다. [Gmail push 문서](https://developers.google.com/workspace/gmail/api/guides/push)

## 6. 랜딩 페이지 API 계약

구현 경로는 Engine의 `POST /api/intake/inquiries`다. 사용자 표현의 ‘API를 열어둔다’는 외부 서비스가 정해진 계약으로 문의를 전달할 수 있게 한다는 뜻으로 해석한다. 코드는 구현됐으며 실제 배포와 출처 등록 후 외부 연동에 사용한다.

```json
{
  "eventId": "submission_example_001",
  "eventType": "inquiry.created",
  "formId": "contact-form",
  "submittedAt": "2026-09-12T10:00:00+09:00",
  "contact": { "name": "샘플 문의자", "email": "sample@example.com" },
  "subject": "서비스 도입 문의",
  "message": "도입 상담을 요청합니다.",
  "pageUrl": "https://example.com/contact"
}
```

- 랜딩 페이지의 서버 또는 폼 제공자가 호출한다. 브라우저 코드에 Engine shared secret을 넣지 않는다. 브라우저 직접 폼 제출을 원하면 사이트의 공개 폼 수신 경로가 입력·봇·속도 제한을 담당하고 서버에서 Engine으로 전달한다.
- 수신 연결별 자격 증명 또는 provider 서명을 검증한다. `workspace`, 회사/개인 범위, 허용 form/brand는 서버에 등록한 연결 정보로 결정한다. 본문의 workspace/brand 값을 신뢰해 저장 위치를 바꾸지 않는다.
- `eventId`, 허용된 `eventType`, `message`와 최소 한 가지 회신 수단(email/phone)을 필수로 한다. 이름·제목은 선택값이며 없으면 ‘제목 없는 문의’로 표시한다. 입력 길이·본문 크기·날짜·URL 스킴을 검증한다.
- `Idempotency-Key`는 재전송 시 동일하게 유지한다. 본문 `eventId`와 함께 사용한다면 일치 규칙을 고정하고 충돌을 거부한다. `pageUrl`은 저장용 메타데이터이며 서버가 자동 접속하지 않는다.
- 문의와 유입 이벤트가 원자적으로 저장된 경우에만 성공한다. 새 저장은 201 `saved`, 같은 요청의 재전송은 200 `duplicate`와 기존 inquiry ID, 같은 키의 다른 내용은 409 `conflict`, 입력 오류는 400, 인증 오류는 401/403, 저장 불가는 5xx `failed`를 반환한다.
- 5xx·네트워크 타임아웃은 같은 키로 재시도한다. 429는 재시도 시각을 따른다. 입력·인증·충돌 오류는 수정 전 자동 반복하지 않는다.

프로젝트 웹훅에 문의를 억지로 넣어 project update나 task를 만들지 않는다. 기존 Engine 검증·receipt·원자 저장 패턴을 문의 명령에 맞게 재사용한다.

## 7. 저장·중복·동시 처리

권장 저장 구조는 문의 현재 상태인 `inquiries`와 원본 유입별 기록인 `inquiry_events`다. Gmail 커서·실행 잠금·최근 성공/오류는 해당 연결의 동기화 상태로 관리한다. 정확한 SQL과 마이그레이션 번호는 구현 계획에서 정한다.

| 객체 | 최소 정보 |
|---|---|
| 문의 | workspace, 회사/개인/미분류, 유형, 감지 판정·이유, 제목, 문의자, 처리 상태, 고객/거래/지원 건 연결, 마지막 수신 순번, 읽은 순번 |
| 유입 이벤트 | inquiry ID, source, 연결 ID, 외부 event/message ID, thread ID, 수신 시각, 접수 시각, 선택한 원문 필드, 원문 참조, 내용 해시 |
| 연결 수집 상태 | 검증된 계정, 필터, 커서·계속 위치, 처리 중 lease, 최근 시도/성공, 오류, 재시도 가능 여부 |

동일한 원본 이벤트의 키는 `(workspace, source, sourceAccountKey, externalEventId)`다. 계정 재연결로 connection row가 바뀌어도 검증된 계정의 sourceAccountKey는 유지한다. 문의자 이메일은 고객 연결 힌트이며 문의 중복 키가 아니다.

랜딩 페이지가 웹훅과 안내 메일을 모두 보내는 경우 두 경로에 동일한 제출 ID를 넣도록 연동 계약을 정한다. 검증된 사이트/폼 + 제출 ID가 같으면 하나의 문의에 두 출처를 연결하고 새 알림을 한 번만 만든다. 수신 순서가 바뀌어도 같다. 공통 ID가 없으면 제목·주소·시간의 유사성은 ‘중복 후보’로만 제안하며 조용히 합치지 않는다. 이 경우 자동 중복 제거가 보장된다고 표시하지 않는다.

문의 갱신, 유입 이벤트 저장, 알림용 마지막 수신 순번 갱신은 한 트랜잭션으로 처리한다. 폼의 중복 안내 이벤트는 수신 순번을 다시 올리지 않는다. Gmail의 실제 새 고객 메시지는 올린다. 동시 스캔은 연결별 lease로 제한하고, 같은 요청의 동시 재전송은 DB unique 제약으로 방어한다.

읽음 저장은 화면에 표시된 수신 순번까지만 반영한다. 상세를 보고 있는 동안 새 회신이 오더라도 보지 못한 회신이 읽음으로 사라지지 않아야 한다. 재시도는 읽은 순번을 뒤로 되돌리지 않는다.

## 8. 기존 알림에 합치는 방식

알림의 정본은 문의 기록의 **마지막 수신 순번 > 읽은 순번**이다. 토스트나 브라우저 메모리에만 저장하지 않는다. 처리 완료·제외된 문의는 기본 활성 알림 수에서 제외한다.

- 기존 종 모양 버튼은 오늘 화면으로 이동하는 동작을 유지하며 ‘새 문의 N건’을 표시한다. N은 메시지 수가 아니라 새로운 내용이 있는 문의 수다.
- 오늘 화면은 새 문의 개수와 바로 열 수 있는 요약을 제공한다. 상세 이동은 `dashboard/revenue/inquiries?inquiry=<id>`를 사용한다.
- `getAttentionLedger`에 문의 소스 상태와 문의 요약을 추가하고 Daily Brief는 이를 재사용한다. 두 화면에서 별도 Gmail 스캔을 실행하지 않는다.
- 현행 Attention의 `lane`은 task/deal/event라는 **데이터 종류**다. 과거 설계 문서의 missed/today/waiting/inbox라는 **행동 상태**와 다르다. 구현에서는 source 종류 `inquiry`와 읽기/응대 상태를 구별하고 기존 소비자의 타입 분기를 검토한다.
- Daily Brief 신호가 상위 7개로 잘려도 문의 미확인 총수와 ‘문의 내역 열기’는 남긴다. 목록 페이지 크기로 전체 건수를 대신 계산하지 않는다.
- 새 문의라는 이유만으로 기존 긴급 KA·오늘 약속보다 높은 우선순위를 부여하지 않는다. 명시적인 기한과 중요도는 기존 우선순위 규칙을 따른다.
- ‘읽음’은 새 내용 표시만 해제한다. 처리 중 문의는 문의 내역의 미처리 목록에서 계속 확인한다. 자동 재촉 시각은 이번 기본안에서 임의 설정하지 않는다.

첫 버전의 알림 표면은 앱 내부다. 휴대폰 푸시·Slack 발송·Calendar 일정 자동 생성은 별도 필요가 확인될 때 연결한다.

## 9. 오류와 복구

| 상황 | 표시와 처리 |
|---|---|
| 연결 없음 | ‘메일 연결 필요’, 수집 성공·문의 0건으로 표현하지 않음 |
| 토큰 만료/권한 부족 | ‘메일 재연결 필요’, 기존 문의는 조회 가능 |
| 일부 메시지 fetch/저장 실패 | `partial`, 실패 수·재시도 표시. 해당 범위를 복구하기 전 커서를 건너뛰지 않음 |
| 중복 | 기존 문의 ID 반환, 오류 수에 포함하지 않음 |
| DB 저장 실패 | `failed`, 저장 완료·알림 생성으로 표시하지 않음 |
| 저장은 성공, 응답 유실 | 같은 키 재시도로 저장된 결과 복구 |
| 분류 불확실/본문 잘림 | ‘확인 필요’, 제외로 확정하지 않음 |
| Gmail 커서 만료 | 복구 동기화. 마지막 성공 이후를 복구할 수 없는 부분은 누락 가능 기간으로 명시 |
| 문의 read 실패 | Hub 규칙인 HTTP 200 + `{status:"error"}`와 재시도. `!response.ok`만 검사하지 않음 |
| 문의만 실패, 기존 업무 정상 | 문의 소스만 오류/부분 상태. 다른 업무를 빈 목록으로 지우지 않음 |

최근 수집 성공 시각은 실제 메시지 처리 완료 기준이다. 토큰 갱신 시각을 수집 성공 시각으로 사용하지 않는다. 운영 로그에는 메일 원문이나 토큰을 복제하지 않고 event ID·오류 종류·처리 수를 남긴다.

## 10. 구현 단위와 완료 기준

| 순서 | 적용 범위 | 완료를 판단할 장면 |
|---|---|---|
| 1 | 문의 저장 명령, 읽기 모델, 문의 내역, 읽음/처리 상태, Daily Brief 연결 | 합성 문의를 저장하고 새로고침 후 같은 내역·알림 수를 확인한다 |
| 2 | 기존 Gmail OAuth 수신 검증, 본문 감지, 페이지·커서·재시도, 수동/서버 자동 수집 | 회사·개인 발신자의 실제 테스트 문의가 앱을 닫은 동안에도 수집된다 |
| 3 | 문의 웹훅과 입력 계약 문서, 동일 제출 ID 중복 처리 | 같은 샘플 제출을 웹훅·메일로 반복해도 문의와 새 알림이 각각 하나다 |
| 후속 | 실제 랜딩 페이지 서버/폼 연결 | 해당 사이트에서 제출하고 문의 상세 원문까지 왕복 확인한다 |

사용자가 말한 ‘나중에’는 실제 랜딩 페이지 연결 시점에 적용한다. 수집 계약과 검증 가능한 API 준비는 앞선 구현과 함께 하되, 미연결 사이트를 연결 완료로 표시하지 않는다. Gmail push/Pub/Sub는 자동 폴링을 검증한 뒤 필요할 때 확장한다.

후속 구현은 전용 git worktree에서 진행한다. 문의 domain mutation은 Engine, Hub read는 repository, Hub write는 write guard가 있는 BFF로 나눈다. 새 UI 구현 전 `DESIGN.md` 전체를 읽고 기존 프리미티브·반응형·키보드 계약을 적용한다.

## 11. 후속 구현의 검수 시나리오

아래는 검수 기준이다. 로컬 합성·트랜잭션·화면 검증 범위는 §13에 기록하며, 실제 메일·배포 왕복은 연결 후 검증한다.

1. 개인 도메인의 견적 메일, 회사 주소의 지원 문의, 등록된 폼 안내 메일을 각각 저장한다. 뉴스레터·시스템 자동 오류 알림의 오탐도 확인한다.
2. 제목·snippet에 문의가 없고 본문에만 요청이 있는 메일을 감지한다. 서명의 ‘문의’ 한 단어만으로 확정 문의로 만들지 않는다.
3. 최근 메시지가 한 페이지를 넘고 일부 fetch가 실패해도 재시도로 모두 복구한다. 자동 보관 메일과 이미 읽은 수신 메일도 설정 범위 안에서 처리한다.
4. 동일 계정 재연결, 동시 스캔, 응답 유실 뒤 재시도에서 중복이 생기지 않는다.
5. 웹훅→메일, 메일→웹훅 순서를 모두 검증한다. 공통 제출 ID가 없는 유사 문의는 자동 병합되지 않는다.
6. 같은 키의 다른 내용은 충돌이며 원문을 덮어쓰지 않는다. 위조 workspace/form/brand로 다른 범위에 저장할 수 없다.
7. 문의 상세를 읽는 동안 새 회신이 와도 새 알림이 남는다. 읽음과 완료, 문의 분리, 고객/거래 연결을 새로고침 후 확인한다.
8. 최초 과거 수집은 새 알림 폭주를 만들지 않는다. 연결 후 도착한 문의는 초기 수집 중이어도 새 내용으로 남는다.
9. 신호 7건 제한·목록 페이지 제한을 넘겨도 문의 총수가 정확하고 상세 링크가 작동한다.
10. 권한 부족·커서 만료·DB 실패·부분 수집을 각기 구별한다. `preview`, `error`, `partial`이 문의 0건으로 위장되지 않는다.
11. 회사/개인/미분류 스코프를 전환해도 분류 불명 문의가 누락되거나 회사 공식 기록으로 복제되지 않는다.
12. 인증 없는 API 호출·과도한 본문을 거부한다. 원문 HTML을 실행하지 않고 외부 이미지를 자동 로드하지 않는다.

## 12. 운영 연결 전에 남은 설정

- 접근안 B는 구현 요청으로 채택됐다. 자동 수집은 기본 비활성이고 실제 배포 주기와 실행 성공은 운영 환경에서 확인한다.
- 첫 수신 계정은 기존 운영자 Gmail 계정 기준으로 가정했다. 다른 사서함이 대상이면 제공자·계정 연결 범위를 바꾼다. 실제 OAuth는 계정 소유자의 로그인으로 마무리한다.
- 실제 랜딩 페이지 주소, 폼 제공자, 서버 존재 여부, 메일과 공유할 제출 ID는 연결 단계에서 확인한다. 인증값을 저장소 문서에 적지 않는다.
- 감지 정확도는 합성 예시만으로 확정할 수 없다. 초기에는 후보·감지 이유·수동 교정을 제공하고 운영자가 확인한 메일 표본으로 누락과 오탐을 평가한다.
