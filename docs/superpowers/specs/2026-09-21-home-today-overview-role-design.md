## 1. 이번에 풀 문제

세 페이지의 이름은 다르지만, 신호·일정·할 일·지표를 반복해 보여주면 사용자가 매번 어디서 일해야 하는지 판단한다. 홈을 더 풍부하게 만드는 대신 **정보의 깊이와 할 수 있는 행동**을 분리한다.

| 화면 | 사용자의 질문 | 주로 머무는 방식 | 정보 단위 | 대표 동작 |
|---|---|---|---|---|
| 홈 | 지금 확인할 것이 있나, 어디서 시작하지? | 짧게 확인하고 이동 | 확인이 필요한 신호 요약, 다음 일정 1건 | 확인하기, 오늘 열기 |
| 오늘 | 오늘 무엇을 끝내야 하지? | 실행하며 여러 번 돌아옴 | 오늘 할 일·연락·일정과 완료 상태 | 완료, 결과 기록, 일정 확인 |
| 현황 | 선택한 기간에 일이 어떻게 진행됐지? | 주기적으로 점검 | 기간별 집계·추세·목표 대비 | 기간/범위 변경, 근거 열기 |

내 작업은 전체 업무 저장소다. 오늘은 그중 당일 실행 대상이며, 홈에 새 업무 목록을 하나 더 만들지 않는다.

### 비교한 두 방향

- **A. 짧은 시작 화면(권장):** 신호 요약→상세, 오늘 요약→오늘. 기존 데이터와 화면을 재사용한다. 장점은 역할 구분·작은 변경 범위, 비용은 처리 시 한 번 이동하는 것이다.
- **B. 결정 처리 화면:** 현재 홈의 신호 큐·상세 분할을 유지하고 처리에 집중한다. 장점은 신호를 연속 검토하는 속도, 비용은 적은 신호로 홈 전체가 비거나 승인·결정 화면과 역할이 겹치는 것이다.

사용자의 “발산 없이”를 기준으로 A를 구체화한다. B의 전체 큐·진행률·숫자 결정 단축키는 첫 버전 홈에서 제외한다.

## 2. 정보 소유권 — 요약은 허용하고, 편집은 한 곳에서

| 내용 | 홈 | 오늘 | 현황 / 상세 |
|---|---|---|---|
| 빠른 입력 | 공통 상단 버튼 | 입력→할 일 순서 유지 | 공통 버튼 유지 |
| 오늘 할 일 | 확인 가능한 미완료 건수만 | 목록·완료·결과 기록 | 기간 집계와 원본 근거 |
| 고객 연락 | 기한을 넘긴 약속 등 예외 신호만 | 오늘 연락 대상·다음 행동 | CRM 관계/활동 상세와 기간별 결과 |
| 일정 | 진행 중 또는 다음 일정 1건 | 오늘 전체 일정 | 일정 편집은 캘린더 |
| 미확인 문의·승인 | 요약 후 해당 화면으로 이동 | 별도 큐를 반복 배치하지 않음 | 문의/승인 화면이 처리 정본 |
| 프로젝트 | 실제 진행 장애가 있을 때 요약 | 당일 관련 작업만 | PMS가 편집 정본, 현황은 기간·상태 집계 |
| 매출·성과·주간 리포트 | 독립 KPI 타일 없음 | 장기 지표 묶음은 현황으로 이동 제안 | 현황이 요약과 비교를 소유, 자세한 매출은 매출 화면 |
| 시스템 연결 실패 | 관련 영역에 실패 표시 | 해당 실행에 미치는 영향 표시 | 상세 진단은 설정/실행 기록 |

**중복 허용 예:** 홈의 다음 일정 1건과 오늘 시간표의 같은 일정. 홈의 ‘확인할 일’ 카드 1개가 참조하는 작업을 오늘에서 실제 완료하는 것.
**중복 금지 예:** 홈·오늘에 같은 승인 큐, 주간 리포트, 전체 고객 목록을 각각 펼쳐놓기.

주의: 과거 매출 pulse 상시 노출 결정은 일괄 폐기로 간주하지 않는다. 오늘의 지표 이동은 해당 결정과 함께 재확정할 항목이며, 홈 개편의 선행조건이 아니다.

## 3. 홈의 구성 — 헤더 + 본문 두 영역

### 헤더

- 화면 이름은 **홈**. 날짜는 보조 정보.
- 한 줄 설명: “확인할 일을 살펴보고, 오늘의 작업을 시작하세요.”
- `Daily Brief`, `N건 남았습니다`, 처리 진행률을 페이지 제목으로 쓰지 않는다. 남은 신호 수를 오늘 남은 업무량으로 오해하기 쉽다.
- 기존 공통 빠른 입력을 사용한다. 홈 전용 입력창·검색창·즐겨찾기 메뉴는 추가하지 않는다.
- 정상 상태는 작은 TruthBadge로 충분하다. 실패/부분 확인만 설명을 펼친다.

### 왼쪽 / 첫 번째: 확인할 일

- **카드 최대 3개**, 카드당 제목 1개·이유 1문장·기한 또는 발생 시점·목적지 1개.
- 제목은 객체와 사건이 드러나야 한다. 이름 없는 “위험 증가”, 일반 조언, AI가 추정한 할 일은 넣지 않는다.
- 예시 형식은 `[대상] — [확인할 사건] / [왜 지금 확인하는지] / [관련 화면 열기]`. 시안의 대괄호는 구조 설명이며 실제 데이터가 아니다.
- 문의·승인처럼 기존 원장이 묶음 건수만 제공하는 경우 **묶음 카드 1개**를 허용한다. 나머지를 개별 항목처럼 만들어 채우지 않는다.
- 카드 자체는 요약·이동용이다. ‘완료·승인·보류’ 쓰기 버튼을 홈에 추가하지 않는다.
- 3개를 넘으면 같은 영역 안의 **‘추가 항목 펼치기’**를 한 번 눌러 기존 조회 결과의 나머지를 볼 수 있다. 별도 탭/새 전역 큐를 만들지 않는다. 접기를 제공하고, 펼친 채 상세에 갔다 돌아오면 상태를 복원한다.
- 더보기에는 총수를 모르면 숫자를 붙이지 않는다. 조회가 잘렸다면 ‘확인된 항목 기준’과 원본 화면 링크를 붙인다.

### 오른쪽 / 두 번째: 오늘 시작

- ‘오늘 할 일’은 오늘 페이지와 같은 원천·기준의 미완료 수만 요약한다. 전체 내 작업 수와 섞지 않는다. 상위 N개만 읽었다면 총수처럼 쓰지 않는다.
- 시간 문맥은 **진행 중 일정 우선, 없으면 다음 일정 1건**. 종료시각이 현재 이하인 일정은 제외한다. 진행 중이 여러 건이면 가장 먼저 시작한 건을 표시하고 ‘겹치는 일정 확인’으로 오늘 시간표에 연결한다.
- 같은 시각의 일정은 시작시각→안정된 이벤트 ID 순으로 선택한다. 종일 일정은 시각 일정과 섞지 않고 확인 가능한 경우 ‘종일 일정 있음’ 링크만 표시한다.
- 캘린더 미연결/실패면 ‘일정 없음’이라고 쓰지 않는다.
- 주 버튼은 **‘오늘 열기’**. 첫 작업을 자동 선택하거나 특정 업무의 착수를 자동 기록하지 않는다.
- 보조 링크는 **‘현황 보기’** 하나. 최근 프로젝트·문서·즐겨찾기를 추가 카드로 늘리지 않는다.

## 4. 확인할 일 선정·순서·수명

### 포함 조건

다음 중 하나이고, 실제 원장 상태와 열 수 있는 목적지를 갖춘 항목만 후보가 된다.

1. 원장에 기한 초과·긴급으로 이미 판정된 약속/업무 신호.
2. 미확인 문의·승인 대기처럼 사용자 확인이 필요한 상태.
3. 프로젝트 차단·실행 실패처럼 실제 처리 가능한 장애. 실행 실패는 현재 미해결임을 기존 원장에서 확인할 수 있어야 한다. 과거 실패 run이 후속 성공 뒤에도 실패 이력으로 남는 경우는 1차 후보에서 제외한다. 새 해결 상태 저장소를 만들지 않는다.

일반 오늘 할 일, 단순 활동 로그, 원장이 없는 추천 문장, 오래됐다는 이유만으로 위험을 추정한 고객은 제외한다. 기한이 있는 평범한 오늘 일정은 오늘 시작 영역에 둔다.

### 순서와 중복

- 기존 Attention의 우선순위를 재사용할 수 있는 항목은 그대로 사용한다. 홈에 새 영업 점수·위험 공식을 만들지 않는다.
- 서로 다른 원장의 점수를 비교할 수 없다면 표시 순서는 **확인된 긴급/기한 초과 → 승인·문의 → 기타 장애**로 제안한다. 그 안에서는 기존 순서 유지, 동점이면 안정된 ID로 고정한다. 이 순서는 업무 우선순위 공식 변경이 아닌 홈 표시 기본값이다.
- 같은 원장·동일 대상 ID·동일 사건의 항목만 중복 제거한다. 제목·고객 이름의 유사성으로 합치지 않는다. 전체 묶음 카드와 그 묶음의 개별 카드를 동시에 표시하지 않는다.
- 대상을 식별할 수 없는 집계 신호는 개별 사건과 중복 제거됐다고 보장할 수 없으므로 홈 1차 후보에서 제외한다. 예외는 원장이 명확한 문의/승인 묶음이다.
- 영역 제목은 ‘확인할 일’로 고정하고 서로 다른 단위의 총합 숫자는 만들지 않는다. 카드 3개는 사건 3건 또는 업무 3개를 뜻하지 않는다.

### 수명

- 클릭·탭 이동은 해결이 아니다. 현재 Home의 로컬 `resolved` Set으로 항목을 지우거나 처리율을 올리는 동작을 종료한다.
- 목적지에서 실제 처리가 저장되고 재조회 결과 조건에서 벗어났을 때만 사라진다.
- 돌아올 때·다시 활성화될 때 재조회한다. 이전 데이터가 있으면 화면을 유지하며 갱신 상태를 표시한다. 서버 실패 후 이전 항목을 현재 상태처럼 표시하지 않는다.
- ‘나중에 보기’, 읽음 처리, 알림 해제, 개인별 숨김 저장소는 이번 버전에 추가하지 않는다.

## 5. 오늘과 현황의 구체적 정리

### 오늘: 실행 순서

1. 빠른 입력. 기존 입력→할 일의 연속 흐름을 보존한다.
2. 오늘 할 일. 실제 선택/기한 데이터로 구성하며 신규 ‘AI Top 3’ 기능을 붙이지 않는다. 기존 미완료/기한 초과 구분·저장 확인·재시도 계약 유지.
3. 오늘 일정과 연락할 고객. 업무량이 많으면 기존 목록 안에서 펼친다. 상시 고정 고객 5명을 분량을 채우기 위해 보여주지 않는다.
4. 하루 마무리는 기존 하루 리뷰로 연결하는 보조 동작. 새로운 회고 원장은 만들지 않는다.

신호/문의/승인 전체 큐는 홈·각 상세로 역할을 정리한다. 단, 실제 당일 작업으로 등록된 승인 후속 작업은 오늘 목록에 남을 수 있다. 긴급 경고를 모두 홈에만 숨겨 오늘 직접 진입한 사용자가 놓치게 해서는 안 된다. 오늘에서 실행에 직접 영향을 주는 경고는 해당 작업 행에 유지한다.

### 현황: 점검 순서

1. 기존 개인/회사 범위와 7·14·30일 기간 선택.
2. 선택 기간의 핵심 집계, 비교 가능한 경우 이전 동기간 대비.
3. 업무 진행·성과의 추세와 상태 분포. 현재 시점의 재고 수치는 ‘현재’로 구분해 기간 실적처럼 표시하지 않는다.
4. 원본 근거와 도메인 상세 링크. 현황에서 새 체크리스트·승인 큐를 만들지 않는다.

목표·성과는 현재 DB/워크스페이스 호환 문제를 별도로 해결한 후 연결한다. 이 기능 준비를 홈 출시의 선행조건으로 만들지 않는다. 없는 지표는 ‘준비 필요’이고 0이 아니다.

## 6. 동선·첫 진입·시간

- 이름·경로 유지: 홈 `/dashboard/home`, 오늘 `/dashboard/daily-brief`, 현황 `/dashboard/overview`.
- 사이드바 순서와 깊이를 유지한다. 새 하위 메뉴·전체 화면 전환기는 추가하지 않는다.
- **1차는 현재 `/dashboard`→오늘 착지를 보존한다.** 홈의 역할을 실제로 확인한 뒤 홈 기본 착지를 별도 결정한다. 매번 홈을 거쳐야 하는 이동을 강제하지 않는다.
- 홈→상세는 가능한 경우 실제 객체 딥링크. 현재 `SIGNAL_TARGETS`가 목록 경로만 제공하는 종류는 목록 이동으로 라벨링한다. 객체 ID 없는 경로를 ‘상세 열기’로 표시하지 않는다.
- 뒤로 가면 원래 페이지·펼침·스크롤을 복원한다. 원장이 갱신돼 항목이 사라졌으면 다음 항목 또는 영역 제목으로 포커스를 복구한다.
- 날짜 경계는 KST. 자정을 넘긴 채 열린 탭은 날짜 및 오늘 요약을 함께 갱신한다. 시스템 날짜 표시만 바뀌고 어제 건수가 남아서는 안 된다.

## 7. 상태 계약과 배치

| 상태 | 확인할 일 | 오늘 시작 |
|---|---|---|
| 최초 로딩 | 카드 위치에 Skeleton | 숫자/일정 자리에 Skeleton |
| 연결됨·0건 | ‘현재 조회 범위에 표시할 확인 항목이 없습니다’ | 확인된 오늘 할 일 0건, 시간 일정 없으면 그 사실만 |
| 일부 확인 | 확인된 카드 + 읽지 못한 원장 이름·재시도 | 알려진 값만 표시, 합계/일정 완전성을 과장하지 않음 |
| 읽기 실패 | 실패 설명·재시도, 0건 표현 금지 | 해당 수치 대신 ‘확인 못함’, 다른 원장의 정상 값은 유지 |
| 미연결 | 연결 필요·설정 링크 | 일정 미연결과 일정 0건 구분 |

- 데스크톱: 왼쪽 확인할 일, 오른쪽 오늘 시작. 주 버튼과 최우선 항목을 같은 첫 화면에서 볼 수 있게 한다. 기존 Futura 질감·토큰·프리미티브 유지.
- 모바일: 헤더→확인할 일→오늘 시작. 별도 가로 탭 없음. 카드 이유는 최대 두 줄 요약, 목적지에서 원문 확인. 긴 제목도 버튼과 겹치지 않게 한다.
- 제안된 크기 목표: 1440×900에서 기본 3카드와 오늘 시작을 첫 화면에 표시. 390×844에서 최우선 카드의 확인 버튼이 첫 화면에, 오늘 열기는 두 번째 화면 안에 표시. 이는 향후 실측 완료 기준이며 현재 측정값이 아니다.
- 한 페이지 주 제목 1개, 행 링크/버튼의 키보드 접근과 포커스 표시, touch 44px, 로딩/오류 TruthBadge·Skeleton·EmptyState 계약 준수.
- 확인 항목이 0건이어도 최신 글·명언·홍보·AI 조언으로 빈 공간을 채우지 않는다. 오늘 시작이 남는 조용한 홈을 정상 상태로 인정한다.

## 8. 데이터 재사용과 구현 범위

현 코드 확인: `pages/home.jsx`는 daily-brief 신호와 calendar event를 읽으며 클릭 시 local resolved를 변경한다. `pages/daily-brief.jsx`는 taskToday·operatorHome·inquiries 등을 이미 받는다. `pages/overview.jsx`는 집계와 목표·성과를 구분한다. `hub-nav.js`에서 홈/오늘은 통합 범위, 현황은 범위 선택이 있는 상태다.

- **조회 범위 한계:** 현재 daily-brief는 `signals`를 최대 7개로 잘라 반환한다. 1차 선정·정렬·추가 펼치기는 응답에 포함된 후보 안에서만 적용한다. 전체 원장의 최우선 목록이나 전체 미해결 수를 보장하지 않는다. 제목은 ‘확인할 일’, 보조 설명은 ‘현재 조회 범위 기준’으로 표시한다. 적격 후보가 응답에서 누락될 수 있으며 원본 화면에서 전체 목록을 확인한다. 이 한계가 실사용에서 누락을 만들면 기존 API 내부의 후보 선정 순서를 후속 수정하고, 새 원장을 만들지 않는다.
- 1차는 `/api/hub/daily-brief`의 기존 신호·문의·오늘 할 일과 기존 캘린더 응답을 재사용한다. 데이터 계약을 확인한 종류만 연결하고, 별도 홈 원장/API는 만들지 않는다.
- 화면의 배열을 억지로 카드 수에 맞춰 채우지 않는다. 테스트는 격리한 응답으로 하고 실제 화면에는 하드코딩 업무 데이터를 넣지 않는다.
- 읽기 요청은 두 영역을 독립 처리하고, 페이지를 떠나면 취소한다. 지표 전체를 다시 읽거나 AI 요약 호출을 추가하지 않는다.
- 신호가 실제 객체로 이동할 수 있는지는 종류별로 확인한다. 새 딥링크가 필요한 항목은 기존 필터를 쓰는 목록 진입으로 우선 제한한다.

| 단계 | 구현 범위 | 통과 기준 |
|---|---|---|
| 1. 홈 역할 고정 | 제목·두 영역·최대 3카드·기존 오늘 요약·목적지 링크, 가짜 완료 상태 제거 | 신호가 없어도 오늘 진입 가능; 클릭만으로 완료되지 않음 |
| 2. 중복 조정 | 오늘의 신호/지표 묶음 이동, 현황의 기간·현재 수치 표기 정리 | 캡처→할 일 보존, 오늘 직접 진입해도 실행 가능 |
| 3. 첫 진입 판단 | 실제 사용으로 홈을 기본 착지로 바꿀지 평가 | 사용자가 홈을 거칠 이유를 설명할 수 있을 때만 변경 |

신규 AI 추천·KPI·보관함·드래그 커스터마이징·최근 방문 추적·일괄 승인·새 알림 저장소·브랜드 재설계는 범위 밖이다.

## 9. 검증 시나리오와 남은 선택

구현 전 검증용 시나리오:
1. 일반 할 일만 있는 날: 홈을 업무 목록으로 채우지 않고 오늘 진입 가능.
2. 기한 초과 약속 + 승인 + 문의: 우선순위/중복 규칙에 맞는 3카드와 각 목적지 확인.
3. 항목을 열었다 닫기: 신호가 그대로 남는다. 실제 처리 저장 후 돌아오면 재조회로 반영.
4. 동일 대상의 다른 사건: 이름이 같아도 합쳐지지 않는다. 집계와 개별 중복은 제거.
5. 읽기 실패·미연결·일부 확인: 0건과 다른 문구, 재시도, 정상 원장은 계속 사용 가능.
6. 자정·진행 중 일정·종일만 있는 날·일정 중복: 오늘 날짜와 요약이 일치.
7. 오늘/현황 직접 URL 진입 및 뒤로가기: 홈을 거치지 않아도 모든 기존 실행 가능.

남은 선택은 두 가지다. (a) 1차 사용 뒤 기본 착지를 홈으로 전환할지, (b) 기존 매출 pulse의 오늘 상시 노출을 유지할지. 둘 다 홈의 1차 구성 작업을 막지 않는다.

다음 작업은 실제 사용 상황 세 가지(출근 후 첫 접속·점심 후 재접속·퇴근 전 점검)를 이 구성에 대입해 각 상황의 첫 클릭이 어디인지 확인하는 것이다. 홈에서 업무를 모두 처리하려 하거나 오늘에서 장기 지표를 찾게 되면 역할 배치를 수정한다.

검증 상태: 코드/기존 기획 기반의 문서 설계. 새 UI 구현, 운영 DB 변경, 실사용 성능 측정은 하지 않았다. 로컬 UX 검색은 이 정보 구조에 정확히 맞는 결과를 찾지 못해 기존 DESIGN.md·원장 계약과 정보 위계의 일반 원칙을 적용했다.
