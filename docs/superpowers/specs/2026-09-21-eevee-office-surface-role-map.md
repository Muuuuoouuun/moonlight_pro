# Eevee Office — 탭·실제 기능·상황별 역할 배치

> 상태: **DRAFT · 역할 배치 권장안 / 화면·라우팅 변경 전**.
> 날짜: 2026-09-21
> 요청: “각 탭별, 역할-기능들 어떻게 배치하면 좋을지 실제 기능별-상황별-시나리오 별 역할 배정”.
> 상위 정본: [운영자 프로필](../../operator-workflow-profile.md), [문서 지도](../../README.md), [개인 운영 OS](2026-07-13-moonlight-personal-operator-os-deep-design.md).
> 관계: [9명 상세 설정](2026-09-21-eevee-office-detailed-configuration.md) §13~18을 화면과 기능 단위로 구체화한다. 직책·성격·기존 Guru/Mentor/Legend 경계를 바꾸지 않는다. 최신 내비게이션·CRM·브랜드·목표 스펙의 제품 기능을 새로 승인하거나 대체하지 않는다.
> 관찰 기준: 2026-09-21 로컬 통합 코드 `aa4329d`의 내비게이션·페이지·호출 경로를 읽었다. Office 전용 작업의 상세 설정은 별도 작업 공간에 있다. 현재 통합 작업 공간의 다른 세션이 편집 중인 `personas.ts`·`prompt.ts`는 변경하지 않았다. 브라우저 실사용·운영 DB·배포 상태를 이번 조사로 검증한 것은 아니다.
> 표의 읽는 법: **현재 기능**은 코드에서 확인한 표면이다. **담당·도움 버튼·인계**는 아래 권장안이며, 기존 기능에 Office가 이미 연결됐다는 뜻이 아니다.

## 1. 배치 원칙

**탭에는 기본 담당, 기능에는 실제 응답 담당, 업무에는 하나의 주관을 둔다.** 사용자는 “누구를 고를까”보다 “무엇을 끝낼까”를 먼저 고른다. 버튼은 `답장 초안 · 부스터`, `완료 조건 정리 · 글레이시아`처럼 행동과 담당을 함께 보여 준다.

- **탭 기본 담당:** 새 요청의 담당이 지정되지 않았을 때 추천할 역할. 그 화면의 모든 행동을 독점하지 않는다.
- **기능 담당:** 선택한 행동을 수행하는 Office 요청의 `ownerId`. “고객 메시지”와 “비용 계산”은 같은 매출 화면에서도 담당이 다르다.
- **업무 주관:** 이미 이어가던 업무의 책임은 유지한다. 다른 역할의 검토는 그 업무에 붙는 기여이며 새 프로젝트나 중복 태스크를 만들지 않는다. 주관 변경은 명시 인계다.
- **원장 담당자:** CRM/PMS의 실제 운영자 `owner_id`를 캐릭터 ID로 덮어쓰지 않는다. Office 응답 담당과 실제 업무 소유자는 별개다.
- 사용자가 역할·Guru·기존 Council을 직접 지정하면 그것을 먼저 따른다. 기능 버튼은 이번 요청의 담당을 명시하는 행동이며, 단순한 페이지 이동은 담당 변경이 아니다.
- 원래 기능이 충분하면 AI를 호출하지 않는다. 저장, 검색, 필터, 날짜 프리셋, 체크, 산술 집계에 캐릭터 대화를 의무로 끼우지 않는다.
- 보조 역할은 결과를 바꿀 구체 쟁점이 있을 때만 쓴다. 표의 보조는 상시 추가 호출 목록이 아니다.

### 선택한 배치안

| 접근 | 효과 | 판단 |
|---|---|---|
| 모든 탭에 9명 선택기 | 자유롭게 고를 수 있음 | 업무보다 역할 선택이 앞서므로 기본 배치로 쓰지 않음 |
| 각 탭에 캐릭터 한 명 고정 | 찾기 쉬움 | 매출의 고객 행동/비용, PMS의 일정/제품 판단을 구별하기 어려움 |
| **기능 버튼에 담당을 기본 배정하고 변경 가능** | 행동 중심으로 사용하며 책임도 알 수 있음 | **권장** |

## 2. 현재 표면에서 확인한 중요한 차이

1. **홈과 오늘은 현재 다른 화면이다.** `/dashboard/home`은 신호 트리아지·오늘 시간표, `/dashboard/daily-brief`는 실행 브리프·주간 리포트 등을 가진다. 기본 `/dashboard` 착지는 여전히 Daily Brief다. 과거 홈 기획의 “Home 코드 미병합” 관찰은 이번 통합 코드에는 그대로 적용되지 않는다.
2. **현황에 목표·성과가 있다.** 목표·지표·관측 근거·업무 연결과 빠른 체크를 처리한다. 프로젝트/할 일/콘텐츠 상세의 범용 AI 후보·검토 패널도 별도 경로로 존재한다.
3. **주간 리포트 카드는 이미 있다.** 월요일 개인·목요일 회사 카드가 집계를 읽는다. Office가 쓴 설명형 리포트, 외부 발송, 지정 시각의 자동 생성까지 구현됐다는 뜻은 아니다.
4. **Studio AI는 이미 초안·다듬기·축약·도입부·채널 변형과 비교/적용을 가진다.** 님피아 연결은 이 편집·버전 계약을 살리는 작업이어야 한다.
5. **고객 연락의 기존 초안은 Office 부스터가 아니다.** `personaId: sales` + `outreach-draft` + Legend lens 경로다. 전역 상담창도 Guru/기존 Council 경로다.
6. **기존 Council 화면에 Codex 작업 패널이 있다.** Office 쥬피썬더가 worker와 연결됐다는 뜻은 아니다. 기존 작업 참조를 이어야 한다.
7. **표시되는 scope와 실제 조회 범위를 다시 대조해야 한다.** 전역 필터 방향은 확정됐지만 모든 소비자가 같은 수준으로 구현된 것은 아니다. 화면에 회사라고 표시됐다는 이유만으로 데이터를 회사 자료로 재분류하지 않는다.
8. **현재 Office는 기본적으로 입력한 내용만 참고한다.** `includeProjects`의 기본값은 `false`다. 사용자가 `현재 범위의 최근 프로젝트 참고`를 선택했을 때만 최근 프로젝트 요약 최대 8개를 조회한다. 전체 CRM·일정·메모·목표를 안다고 가정하지 않는다. 아래 기능별 문맥 연결은 후속 작업이다.

### 기존 AI 진입과 새 Office 행동의 경계

| 현재 진입 | 코드에서 확인한 기존 경로 | Office 연결 시 배치 원칙 |
|---|---|---|
| 오늘의 실행 브리핑 `DailyDispatchCard` | `personaId: order` / `daily-dispatch` | 기존 브리핑 유지. 샤미드의 `남은 시간에 맞추기`와 이브이의 요약을 연결하려면 명시적 어댑터가 필요하며 같은 클릭에서 두 경로를 호출하지 않음 |
| 오늘 Rhythm의 `한 주 정리 & Council 평가` | `FloatingMentorWidget`, `agent: council`, `contextType: weekly`; `한 주 사실 요약`은 `personaId: council` / `weekly-review`, 다른 행동은 mode/lens에 따라 기존 서비스 사용 | 기존 회고·관점 경로 유지. 샤미드의 첫 주간 연결은 별도의 월/목 주간 리포트 카드에 두며 기존 평가 버튼을 바꾸지 않음 |
| Studio `방향 검토` | 기존 `FloatingMentorWidget`의 content/quick 진입. 선택한 행동·lens에 따라 기존 Council 또는 persona-chat | 님피아의 기획·원고 작업과 기존 자문을 구별. 기존 버튼 이름만 님피아로 바꾸지 않음 |
| Studio `검수 게이트 판정` | 같은 위젯의 content/critique 진입. 평가 실행은 `personaId: content` / `critique` | 블래키의 사실·약속 검토와 기존 평가 경로를 구별. 검수 화면을 열었다는 사실은 실제 판정·승인·발행을 뜻하지 않음 |
| 고객 연락의 기존 메시지 초안 | `personaId: sales` / `outreach-draft` + Legend lens | §6의 Office 초안과 기존 관점 초안 구분 적용 |

기존 경로의 요청·결과·로그 의미를 보존한 채 새 역할을 연결한다. 이름을 바꾸는 것만으로 해당 Office의 말투·정책·권한이 적용된 것으로 표시하지 않는다.

## 3. 상위 탭별 기본 배치

아래 명칭은 실제 `hub-nav.js`의 앵커와 하위 목적지를 따른다. 기본 담당은 추천값이며 고정 조직도가 아니다.

| 현재 탭 | 기본 담당 | 사용자가 주로 맡길 일 | 기능에 따라 바뀌는 담당 |
|---|---|---|---|
| **홈** | 이브이 | 지금 결정할 것 압축, 선택한 신호의 다음 행동 | 시간 충돌 샤미드, 고객 답장 부스터 |
| **오늘** | 샤미드 | 오늘 실행 순서, 남은 시간, 주간 정리 | 종합 브리핑 이브이, 고객 접촉 부스터 |
| **현황** | 이브이(집계 요약) | 변화와 확인할 지점 정리 | 목표·성과 에브이, 매출 수치 리피아, 근거 검토 블래키 |
| **내 작업** | 샤미드 | 기한·대기·작업량·마무리 | 메모 정리 이브이, 글 제작 님피아 |
| **영업·매출** | 부스터 | 문의·고객·거래의 다음 행동 | 수금·비용 리피아, CS 처리 샤미드 |
| **고객 연락** | 부스터 | 연락 순서, 카톡·전화 준비, 실제 연락 결과 정리 | 일정 샤미드, 약속·표현 검토 블래키 |
| **기회 탐색** | 에브이 | 가능성 비교, 검증, 보류·실행 연결 판단 | 자원 리피아, 최소 실험 결과물 글레이시아 |
| **프로젝트** | 샤미드(진행 관리) | 일정·병목·백로그·완료 추적 | 범위 글레이시아, 구현 쥬피썬더, 결정 에브이 |
| **브랜드** | 님피아 | 대상·약속·보이스·콘텐츠 기준 | 브랜드 간 투자 선택 에브이, 운영 리듬 샤미드 |
| **콘텐츠** | 님피아 | 소재 선택부터 원고·파생·편집 | 사실 검토 블래키, 캠페인 비용 리피아 |
| **AI·자동화** | 쥬피썬더(실행 운영) | 연결·실행·실패·재시도 진단 | Office 자유 접수 이브이, 결과 검토 블래키 |
| **설정** | 쥬피썬더 | 연결 상태와 필요한 설정 설명 | 공유 범위·권한 검토 블래키 |

브랜드와 콘텐츠는 님피아가 공통으로 맡지만 결과가 다르다. 브랜드에서는 **계속 사용할 판단 기준**, 콘텐츠에서는 **이번에 완성할 작품**을 만든다.

## 4. 홈·오늘·현황의 기능 배정

### 홈 — `/dashboard/home`

| 현재 기능·상황 | 제안 도움 행동 | 담당 / 필요 시 보조 | 결과·복귀 위치 |
|---|---|---|---|
| 선택한 신호·결정 카드 | 이 안건 정리 | 이브이 / 해당 분야 한 명 | 결정할 것·선택 근거·다음 행동 → 같은 카드 |
| 오늘 시간표 | 일정 충돌 확인 | 샤미드 | 확인된 일정 사이의 충돌·조정 제안 → Calendar |
| 고객 신호에서 연락 준비 | 답장 초안 | 부스터 | 선택 고객의 원문 기반 초안 → 고객 상세 |
| 트리아지의 처리·보류 | 기본 버튼 그대로 | 일반 UI | 현재 Home의 로컬 `resolved` 상태는 원장 업무 완료와 다름. AI가 완료로 집계하지 않음 |

홈에는 9명 카드나 새 브리핑 피드를 더하지 않는다. 선택한 신호의 상세 안에 보조 행동 하나를 둔다. 홈에서 생성한 같은 안건을 오늘 화면에서 다시 생성하도록 하지 않는다.

### 오늘 — `/dashboard/daily-brief`

| 현재 기능·상황 | 제안 도움 행동 | 담당 / 필요 시 보조 | 결과·복귀 위치 |
|---|---|---|---|
| 빠른 캡처·할 일 저장 | 기본 입력 그대로 | 일반 UI; 정리를 요청하면 이브이 | 원문 보존 → 기존 task/메모 입력 |
| 오늘 할 일·집중 실행 | 남은 시간에 맞추기 | 샤미드 | 기한·약속·가용 시간 안의 순서와 최소 결과 |
| 긴급 KA·집중 고객 | 오늘 연락 준비 | 부스터 | 선택 근거·메시지·확인할 질문 → 고객 연락 |
| 오늘 일정 | 미팅 준비 | 부스터(고객 목적) 또는 샤미드(일정 목적) | 필요한 준비와 일정 문맥; 목적에 따라 한 명 선택 |
| 개인 주간 카드 | 이번 주 정리 | 샤미드 / 이브이 | 사실·완료·막힘·다음 행동 초안; 개인 기록 유지 |
| 회사 주간 카드 | 보고 내용 정리 | 샤미드 / 블래키 | 활동·전환·정체와 미확인 항목; 공식 요약만 |
| 승인·결정 큐 | 판단 근거 확인 | 블래키 또는 안건 분야 담당 | 기존 제안의 근거 검토; 검토를 승인·실행으로 바꾸지 않음 |

주간 카드가 첫 연결 우선순위다. 읽을 기간·scope와 집계 근거를 먼저 확인하며 수정된 딜 수를 전환 수로, 활동 수를 고객 수로 바꾸지 않는다. 기존 월/목 카드의 존재와 자동 스케줄 기능은 분리한다. §2에 적은 실행 브리핑과 Rhythm의 Council 평가는 각각 기존 경로를 유지한다.

| 집계 중 매출·파이프라인 | 금액과 상태 해석 | 리피아 / 블래키(집계 근거 충돌) | 예상·계약·입금 구별, 기간·단위·빈칸 |
| 목표·성과: 새 목표 | 목표와 측정 기준 정리 | 에브이 / 글레이시아(사용 결과 정의) | 목표·기간·결과/선행 지표 제안 → 기존 목표 폼 |
| 목표·성과: 지표 빠른 체크 | 측정값·근거 입력은 기존 기능 | 일반 UI; 해석을 요청하면 에브이 | 실제 관측 저장. 측정 안 됨을 0으로 만들지 않음 |
| 목표 미달·근거 부족 | 원인과 다음 실험 검토 | 에브이 / 블래키 | 데이터로 확인한 차이·가설·작은 행동 구분 |
| 목표와 업무 연결 | 이 일이 목표에 기여하는지 | 에브이 / 샤미드(진행 계획) | 연결 이유 제안 → 기존 연결·해제 기능 |

목표·성과의 저장·지표 집계에 새 AI 원장을 만들지 않는다. 기존 목표 폼·관측·연결이 정본이다. AI 후보 채택은 목표 달성이나 업무 완료가 아니다.

### 고객 상세의 여섯 업무 축

CRM 개발 기획의 여섯 축을 **상황 분류**로 활용한다. 모두 독립 하위 탭으로 이미 구현됐다고 주장하지 않는다.

| 축 | 기본 담당 | 실제 도움 |
|---|---|---|
| 연락 | 부스터 | 이번 접촉 목적·카톡/전화 초안 |
| 미팅 내용 | 부스터 | 고객 요구·발언·약속·미확인 요약; 일정 조율은 샤미드 |
| 기록 | 부스터 | 고객 업무의 의미를 보존해 연락 결과 입력 지원. 공식 공유 검토는 블래키 |
| 매출 내용 | 리피아 | 견적·계약·예정 수금·입금과 비용의 구별; 협상 목적은 부스터 |
| 니즈 | 부스터 | 고객 원문과 해석을 분리하고 다음 확인 질문 하나 |
| 위기 | 부스터 | 고객 약속·관계 문제의 다음 대응. 허위 약속은 블래키, 장애는 쥬피썬더, 지연 일정은 샤미드 |

### 고객 연락 — `/dashboard/revenue/followups`

1. 목록의 기본 담당은 **부스터**다. `오늘 연락 순서`는 Q117의 선별 기준과 실제 기한을 함께 본다.
2. 선택 고객의 `답장 초안 · 부스터`가 첫 Office 행동이다. 고객의 최근 말·기존 약속·다음 접촉 목적만 필요한 만큼 전달한다.
3. `미팅 시간 정리 · 샤미드`는 일정이 실제 쟁점일 때만 노출한다. 캘린더를 읽지 못하면 빈 시간을 만들지 않는다.
4. `약속·표현 확인 · 블래키`는 지원 범위·성과 수치가 들어갈 때 쓴다. 모든 인사말을 검수 대기 상태로 만들지 않는다.
5. `연락 결과 기록`과 `내일/3일/다음 주`는 기존 폼·프리셋이다. 고객 답장이 없어도 운영자가 다음 연락일을 정할 수 있다.

기존 Legend 초안과 Office 초안은 한 버튼에서 몰래 교체하지 않는다. 연결 전에는 기존 기능을 유지한다. Office 연결 시에는 `Office 초안`과 `기존 영업 코칭·관점 초안`을 명시적으로 구분하고, 실제 적용한 담당·서비스·lens만 기록한다. 현재 Office의 Legend 미연결 상태도 보존한다.

## 7. 기회 탐색 — 에브이가 판단하고 실행할 곳에 넘긴다

주소: `/dashboard/discovery` 및 같은 경로의 `?scope=classin`, `?scope=personal`.

| 현재 단계·기능 | 도움 행동 | 담당 / 보조 | 결과 |
|---|---|---|---|
| 포착 `captured` | 이 가능성 한 줄로 정리 | 에브이 | 관찰한 사실·가능성 구분. 저장만 할 때는 AI 생략 |
| 발굴 `exploring` | 확인할 가정 고르기 | 에브이 | 결론을 바꿀 가정과 근거 빈칸 |
| 검증 `validating` | 작은 실험 설계 | 에브이 / 글레이시아 | 누구에게 무엇을 보여주고 무엇을 기록할지 |
| 비용·시간이 큰 검증 | 감당할 상한 비교 | 리피아 | 제안 상한·유지 부담·학습 목적 |
| 실행 연결 `connected` | 어디로 이어갈지 | 에브이 주관, 목적에 맞는 담당에 인계 | 고객/거래는 부스터, 프로젝트 범위는 글레이시아, 일정·실행은 샤미드 |
| 보류 `paused` | 다시 볼 조건 정리 | 에브이 | 날짜 또는 재개 조건; 날짜 알림은 실제 연결 전 약속하지 않음 |
| 종료 `closed` | 멈춘 이유와 배운 점 | 에브이 | 판단 이유·재사용할 근거 |

현재 실행 연결의 허용 대상은 task/project/lead/deal이며 `connected`는 task만 연결해서 충족되지 않는다. AI가 원장을 새로 만들거나 “실행 연결 완료”라고 말하기 전에 해당 기능의 실제 저장 결과를 따른다.

| Decisions `/dashboard/work/decisions` | 선택지·추천·변경 조건 | 에브이 | 결정 메모; 기록 요약은 이브이, 운영자 확정 상태 별도 |

예를 들어 기술 프로젝트의 주관이 글레이시아라면 쥬피썬더의 구현·블래키의 검토는 같은 프로젝트에 연결한 별도 작업이다. 부모 주관을 자동 교체하거나 세 프로젝트를 만들지 않는다. 단순 코딩 요청이면 처음부터 쥬피썬더에게 직접 간다.

### 콘텐츠 — 이번 결과물의 정본

주소: `/dashboard/content/queue`, `/dashboard/content/studio`, `/dashboard/content/campaigns`. 개인 별칭은 `/dashboard/brand/queue`, `/dashboard/brand/studio`, 회사 큐는 `/dashboard/classin/content`다.

| Studio: 다른 채널 변형 | 님피아 | 동일 원문을 요청 채널에 맞게 변형; 새 성과·후기 생성 금지 |

현재 Studio의 변환 경로와 범용 `AI 초안·검토` 후보 경로는 서로 다른 기능이다. 여기에 §2의 기존 `방향 검토`·`검수 게이트 판정` 자문 진입도 존재한다. 첫 적용은 Studio의 글 편집을 님피아 담당으로 연결하고 기존 비교·복원 경로를 유지한다. 같은 클릭으로 여러 생성 경로를 동시에 호출하지 않는다. 범용 패널은 목표 기여·근거 분석처럼 다른 목적이 있을 때 사용하며, 기존 자문 버튼의 변경이나 노출을 합치는 작업은 별도 UI 변경으로 검증한다.

## 11. 실제 사용 시나리오

아래 흐름의 화살표는 **필요한 업무 인계**다. 매번 여러 모델을 자동 호출하는 파이프라인을 뜻하지 않는다. 요청한 산출물이 완성되면 거기서 끝낸다.

### S01. 아침에 할 일이 많고 40분만 있다

- 시작: 오늘 또는 내 작업에서 오늘 원고 20분·내일 고객 자료 30분 선택.
- 담당: 샤미드. 이브이 접수를 다시 거칠 필요가 없다.
- 결과: 오늘 원고 20분 → 고객 자료 20분의 최소 부분 → 남은 10분 분리. 소요는 입력받은 값에 근거한다.
- 저장: 일정 변경을 명시 요청한 경우에만 기존 기능으로 연결. 추천만으로 캘린더를 바꾸지 않는다.

### S02. 고객 문의가 새로 들어왔다

- 시작: 문의 내역의 특정 문의.
- 담당: 영업 문의는 부스터. 지원·장애 문의는 샤미드, 기술 진단이 필요하면 쥬피썬더.
- 결과: 확인된 요구·현재 고객 관계·답변 초안·다음 목적.
- 기록: 기존 고객/거래 연결 기능을 사용한다. 고객 식별이 애매하면 새 고객을 자동 생성하지 않는다. 메시지 초안은 발송 기록이 아니다.

### S03. 통화를 마쳤고 다음 연락을 정해야 한다

- 시작: 고객 DB/고객 연락의 연락 결과 폼.
- 담당: 부스터는 원문을 요약·반응·다음 행동으로 정리한다. 이미 짧게 입력했으면 AI를 생략한다.
- 결과: 실제 통화에서 확인한 사실과 미정 항목. 다음 날짜는 약속·운영자 선택을 보존하거나 프리셋 제안.
- 기록: 기존 연락 결과 저장 경로 한 번. 같은 결과를 메모·활동·task에 각각 새 업무로 복제하지 않는다.

### S04. 데모 요청을 받았다

- 시작: Deals 또는 고객 상세.
- 담당: 부스터가 고객 목적·확인 질문·준비 자료를 정리한다. 시간 조율 요청은 샤미드에게 연결한다.
- 결과: 확인된 캘린더에 근거한 시간 제안, 고객/조직/목적이 포함된 일정 제목 제안.
- 완료: 수락, 일정 등록, 데모 실시, 구매는 각각 실제 근거에 맞게 기록한다. 데모 수락을 실시로 바꾸지 않는다.

### S05. 고객이 가격 때문에 망설인다

- 시작: 선택 거래의 답장 또는 제안 검토.
- 담당: 부스터. 손익 조건은 리피아, 효과·지원 약속 검토는 블래키가 필요할 때만 참여한다.
- 결과: 고객이 말한 우려를 짚는 메시지와 다음 확인 질문. 임의 할인·지원·성과 보장을 추가하지 않는다.
- 코칭 예외: “내 협상 방식을 훈련해줘”라면 Guru로 간다. 같은 초안을 Office와 Guru가 동시에 저장하지 않는다.

### S06. 메모 하나를 쓸모 있는 결과로 바꾸고 싶다

- 시작: 메모의 선택 문장.
- 담당: 정리는 이브이, 할 일은 샤미드, 원고는 님피아, 새 기회의 검증은 에브이 중 요청 목적에 맞는 한 명.
- 결과: 선택한 유형의 결과 하나와 원문 링크.
- 경계: 모든 메모에서 task·프로젝트·콘텐츠를 한꺼번에 만들지 않는다. 레퍼런스 전용 표면은 별도 기획이며 현재 탭처럼 추가하지 않는다.

### S07. Threads 한 편을 쓰고 Instagram으로 바꾸고 싶다

- 시작: 소재·제작 → 원고 작성.
- 담당: 님피아. 원문의 사실 검토가 쟁점일 때만 블래키.
- 결과: Threads 초안 → 사용자가 선택한 편집·적용 → 요청한 Instagram 변형.
- 기록: 기존 Studio 후보·선택·버전·복원 계약. “후보 채택”을 “발행”으로 표시하지 않는다.

### S08. Moonlight에 기능 하나를 만들고 싶다

- 시작: Projects 상세 또는 메모에서 기능 요청.
- 주관: 글레이시아가 사용 장면·최소 범위·완료 조건을 작성한다.
- 필요한 인계: 쥬피썬더의 구현 작업과 블래키의 증거 검토를 같은 프로젝트에 연결한다. 일정이 쟁점이면 샤미드.
- 결과: 스펙 → 코드/패치와 테스트 결과 → 수용 기준 확인. Office의 worker 미연결 상태에서는 실행 완료를 주장하지 않는다.
- 예외: 구체적인 버그 수정 요청은 쥬피썬더에게 직접 맡긴다.

### S09. 목요일 회사 주간 보고를 준비한다

- 시작: 오늘의 회사 주간 카드.
- 담당: 샤미드. 부스터는 고객 변화 해석, 블래키는 공식 공유 문구 검토가 필요할 때만 참여.
- 결과: 대상 기간·확인된 활동·상태 변화·정체·다음 행동, 확인 안 된 값은 그대로 표시.
- 경계: 개인 상세·감정·거친 평가를 제외한다. 외부 발송 채널·자동 예약이 미정이면 초안으로 끝낸다.

### S10. 월요일 개인 주간 정리에서 할 일을 줄인다

- 시작: 개인 주간 카드와 선택한 개인 기록.
- 담당: 샤미드. 방향을 재선택하는 문제만 에브이에게 넘긴다.
- 결과: 실제 완료한 것·남은 약속·부담이 큰 일·이번 주 줄일 것.
- 경계: 회사 수익을 개인 성과로 섞거나, 쉬었던 날의 콘텐츠를 밀린 의무로 계산하지 않는다.

### S11. 목표·성과가 낮아 보인다

- 시작: 현황 → 목표·성과의 지표 상세.
- 담당: 에브이. 근거의 누락·집계 단위는 블래키가 검토할 수 있다.
- 결과: 측정 안 됨인지 실제 미달인지, 확인 가능한 차이와 가설, 다음 실험 하나.
- 기록: 새 측정값은 근거와 관측 시각으로 기존 관측 기능에 기록한다. AI 설명으로 실적 수치를 덮어쓰지 않는다.

### S12. 새 아이디어가 현재 프로젝트보다 좋아 보인다

- 시작: 기회 탐색.
- 담당: 에브이, 자원 충돌이 크면 리피아, 실험 결과물 정의가 필요하면 글레이시아.
- 결과: 기존 일 계속/작게 시험/보류 중 추천 하나, 그 판단을 바꿀 근거.
- 연결: 선택된 결과만 기존 project/lead/deal/task에 잇는다. 기회 포착을 사업화 확정으로 처리하지 않는다.

### S13. 자동화 Run이 실패했다

- 시작: Runs의 해당 실행.
- 담당: 쥬피썬더. 외부 변경 여부가 불명확하면 블래키가 실행 증거 검토.
- 결과: 실패 단계·업무 영향·이미 실행된 부분·같은 요청 확인/재시도 조건.
- 경계: 타임아웃을 미실행으로 단정하지 않는다. 발송·결제·등록이 중복될 수 있는 작업은 실제 receipt와 상태를 먼저 확인한다.

### S14. 피곤해서 오늘은 아무것도 하고 싶지 않다

- 시작: 하루 리뷰 또는 이브이 대화.
- 담당: 이브이가 이미 제공된 약속과 현재 요청을 정리한다. 재배치를 요청할 때 샤미드.
- 결과: 꼭 지킬 약속과 최소 행동, 미룰 일, 멈출 지점. 새 학습 계획·콘텐츠 과제를 추가하지 않는다.
- 기억: 오늘의 상태를 영구 성격·능력 평가로 저장하지 않는다. 하루 리뷰는 개인 기록이다.

### S15. 브랜드 캠페인을 계속할지 고민한다

- 시작: Campaigns의 Pulse/Strategy.
- 담당: 현재 캠페인 메시지 개선은 님피아, 캠페인 중단·자원 재배분은 에브이.
- 보조: 비용·순시간은 리피아, 전환 귀속 근거는 블래키.
- 결과: 문구 개선안 또는 투자 판단 중 요청한 결과. 조회 증가를 매출 증가의 인과 증거로 쓰지 않는다.

## 12. 화면 안에 놓는 방법

### 기본 노출

1. **기존 생성·저장·완료 행동을 주 행동으로 유지한다.** Office는 필요한 지점의 보조 버튼이며 기존 primary 생성 버튼과 경쟁하지 않는다.
2. **상세 패널 안에서 맥락 있는 행동 1개를 먼저 보여 준다.** 나머지 1~2개는 더보기로 둔다. 매 행에 9명 아이콘을 늘어놓지 않는다.
3. **담당을 보이는 글자로 표시한다.** `답장 초안 · 부스터`, `이번 주 정리 · 샤미드`, `최소 범위 · 글레이시아`, `사실 확인 · 블래키`처럼 쓴다.
4. **결과는 현재 업무 곁에 둔다.** 긴 대화가 필요할 때만 Office 전용 화면으로 이어 간다. 원문·필터·스크롤·입력 초안은 돌아왔을 때 보존한다.
5. **일반 화면에서는 담당 변경을 접어 둔다.** 직접 역할을 고를 수는 있지만 매번 고르게 하지 않는다. 전용 Office에서는 기존 전체 로스터를 제공한다.

### 고객 연락 상세의 배치 예 — 권장 와이어프레임

```text
고객 이름 · 현재 단계 · 다음 연락일
최근 고객 발언 / 내가 한 약속

[연락 결과 기록]                    기존 주요 행동
[답장 초안 · 부스터] [더보기]        Office 보조 행동

답장 초안 패널
  담당: 부스터 · 범위: 회사 · 대상: 선택 고객
  참고한 기록: 최근 발언과 약속 / 확인 시각
  메시지 초안
  [복사] [수정 요청] [원문 보기]
  상태: 초안 생성 · 미전송
```

`저장`과 `복사`는 다른 결과다. 실제 발송 경로가 없으면 보내기 버튼을 그리지 않는다. 내부 초안을 실제 기록에 적용할 때는 기존 폼·쓰기 계약과 현재 요청의 허용 범위를 따른다.

### 공통 상호작용

- 기존 `Drawer`·`EditDrawer`·`Button`·`SegmentedControl`·`Skeleton`·상태 배지를 사용한다. 별도 떠 있는 Office 위젯을 하나 더 상시 띄우지 않는다.
- 캐릭터 원소색을 페이지·카테고리 색으로 사용하지 않는다. 이름·짧은 소개·말투로 식별한다.
- 키보드로 열고 닫고 원래 버튼으로 돌아갈 수 있어야 한다. 모바일에서는 현재 프리미티브의 반응형 계약을 따른다.
- 생성 중, 조회 실패, 자료 없음, 초안 생성, 저장 확인, 적용 완료를 구별한다. 실패 시 입력을 보존한다.
- 다른 고객·scope·문서로 이동한 뒤 이전 응답이 도착해도 새 대상에 붙이지 않는다. 자동 재생성 대신 원래 요청의 상태를 확인한다.
- 도구가 필요한데 연결되지 않았으면 확인하지 못한 범위를 짧게 밝히고, 제공한 자료로 만들 수 있는 결과를 제공한다.

UX 근거는 DESIGN.md §3·§5·§8·§11 및 UI/UX Pro Max의 공통 내비게이션·선택 정보 펼침 기준이다. 로컬 스킬 검색은 두 번 모두 이 배치에 직접 맞는 항목을 반환하지 않아 검색 결과 자체를 근거로 채택하지 않았다.

## 13. 실제 연결에 필요한 기능 계약

### 버튼이 전달해야 하는 최소 문맥 — 후속 설계

| 문맥 | 필요한 이유 |
|---|---|
| 이번 요청의 역할·행동·모드 | 페이지 키워드로 잘못된 담당이나 서비스에 보내지 않기 |
| 원래 화면·선택 대상 ID·필터·기간 | 같은 이름의 고객·다른 기간·다른 원문 혼동 방지 |
| 검증된 workspace와 scope | 회사/개인 문맥 보존; 브라우저 표시만 신뢰하지 않기 |
| 필요한 원문·출처·기준 시각·revision | 사실 보존, 오래된 초안의 잘못된 적용 방지 |
| 지금 허용된 행동과 실제 연결 능력 | 대화·초안·적용·발송·worker 구별 |
| 기존 업무·원본 산출물·요청 참조 | 인계·재시도의 중복 생성 방지 |

이것은 현재 Office API에 그대로 추가로 보내도 되는 필드 목록이 아니다. 현재 입력 계약은 엄격하므로 **서버가 검증하는 문맥 어댑터와 버전 변경**을 먼저 설계해야 한다. 고객 개인정보·본문을 URL 쿼리에 넣지 않는다. URL은 허용된 대상 참조와 복귀 위치만 표현하고 실제 접근은 서버에서 검증한다.

### 기존 능력을 살리는 연결

| 경로·능력 | 배치 원칙 |
|---|---|
| Office chat | 역할 판단·말투·초안의 전용 서비스 유지 |
| Studio transform/workflow | 님피아 연결 시 기존 원문 snapshot·후보·버전·복구 계약 유지 |
| 범용 AI 후보·검토 | 현재 tasks/projects/content_items 범위와 실제 operation을 유지. 역할·정책 적용 어댑터 없이 이름만 Office로 바꾸지 않음 |
| 목표·관측·업무 연결 | 기존 목표 원장·명령 사용. 추정과 실제 측정 분리 |
| 연락 결과 | 기존 원자 저장·다음 날짜·실제 활동 기록 계약 사용 |
| task/project/decision 쓰기 | 기존 write guard·command/receipt·revision·재조회 활용 |
| Codex worker | 기존 job ID·모드·등록 프로젝트·격리 작업·취소·결과 계약 활용 |
| Guru·기존 Council·Legend | 기존 URL·API·로그 의미 보존. 명시된 코칭/관점 요청만 인계 |

`classin`과 일부 기존 기능의 `company`, workspace의 `brand` 등은 서비스별 명시 매핑이 필요하다. 이름만 보고 미분류 데이터를 개인으로 넘기거나 company 문자열을 Office에 그대로 보내지 않는다. 현재 Office의 scope 제한과 해당 원장의 정본 판정을 모두 확인한다.

새 Hub API를 추가하게 되면 세션/검증된 서버 자격을 거치는 현재 인증 미들웨어 계약을 유지한다. Office 화면 연결 편의를 위해 공개 경로 목록에 올리지 않는다. 읽기 실패의 HTTP 200 오류 봉투도 검사한다.

## 14. 적용 우선순위와 검증

이번은 배치 기획이다. 모든 표면에 버튼을 한 번에 심는 구현 요청으로 확대하지 않는다. 앞선 상세 설정의 역할별 품질 보강과 아래 화면 연결을 작은 단위로 맞춘다.

| 순서 | 적용 묶음 | 확인할 결과 |
|---|---|---|
| 0 | 역할별 의미 오류 보강·문맥 계약 | 기존 7개 보완 사례와 담당·scope 경계. 정답을 외운 결과가 아닌지 확인 |
| 1 | **오늘 주간 카드 → 샤미드** | 확정된 다음 자동화 우선순위. 회사/개인·기간·미확인 값·상태 보존 |
| 2 | **고객 연락 상세 → 부스터** | 한 고객의 실제 근거로 초안, 기존 Guru/Legend 경로 유지 |
| 3 | **Studio 작업 → 님피아** | 기존 비교·적용·복원을 보존하며 사실·경험을 추가하지 않음 |
| 4 | **내 작업 → 샤미드 / 선택 메모 → 이브이** | 업무량 감소, 무기한 분리, 재입력·중복 task 없음 |
| 5 | **프로젝트 상세 → 글레이시아·쥬피썬더·블래키** | 요청 목적별 담당, 수용 기준·실제 코드 증거·검토 분리 |
| 6 | **기회·목표·자원 → 에브이·리피아** | 선택과 지표·기간·비용 가정 보존 |
| 7 | 나머지 탭·전역 진입 연결 | 기존 기능의 담당 덮어쓰기·중복 위젯·숨은 호출 없음 |

쥬피썬더의 실제 코딩 worker, 외부 메시지·콘텐츠 발행, 장기 기억은 관련 단계에서 연결 상태와 기존 허용 행동을 확인한다. 이미 허용된 가역적 작업은 재승인 루프를 만들지 않는다. 단순 초안을 위해 Council을 자동 소집하지 않는다.

### 단계마다 통과해야 할 시나리오

1. 같은 매출 화면에서 `답장`은 부스터, `수금 해석`은 리피아가 실제 정책과 함께 응답한다.
2. 사용자가 님피아나 Guru를 명시하면 현재 페이지의 기본 역할이 덮어쓰지 않는다.
3. 고객 A에서 요청 후 고객 B로 이동해도 결과·저장 대상은 A에 묶인다. scope 변경 시에도 누출이 없다.
4. 원문이 바뀌면 이전 초안을 새 원문에 조용히 적용하지 않는다. 비교·재조회 경로를 제공한다.
5. 조회 오류와 0건, 미측정과 0, 수락과 실시, 생성과 저장, 저장과 발송을 구별한다.
6. 같은 요청의 재시도·인계가 task·활동·후보를 중복 생성하지 않는다.
7. Guru·기존 Council·Legend·기존 worker 작업의 ID·로그·역할 의미가 유지된다.
8. 각 기능에서 화면에 표시한 담당과 실제 호출 경로·정책 버전이 일치한다.
9. 키보드·모바일·닫기·복귀·입력 보존을 확인한다. 처리하지 않은 업무가 완료처럼 사라지지 않는다.
10. 원래 검색·입력·저장 흐름은 AI 연결 실패나 모델 대기 때문에 막히지 않는다.
