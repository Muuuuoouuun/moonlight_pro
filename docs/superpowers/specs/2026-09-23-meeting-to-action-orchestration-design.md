# 회의·녹음·메모에서 실행까지 — 통합 정리와 배분 설계

> 상태: **DRAFT · 권장안 · 미구현(2026-09-23)**. 코드와 로컬 읽기 경로를 조사한 설계이며 운영 배포·실사용 품질 인증을 뜻하지 않는다.
> 상위 정본: [운영자 업무 프로필](../../operator-workflow-profile.md) §음성·메시지 분석, [개인 운영 OS 심화 설계](2026-07-13-moonlight-personal-operator-os-deep-design.md) §15, [업무 안의 Eevee Office](2026-09-21-eevee-office-embedded-workflow-deep-design.md).
> 관계: 위 문서의 확정 정책을 **대체하지 않는다**. [CRM 기록·리드 스코어링 지침](2026-09-13-crm-recording-and-lead-scoring-guidelines-design.md)의 근거 중심 방향과 [Office 품질 재기획](../plans/2026-09-23-office-agent-quality-replan.md)을 실행 입력 관점에서 연결한다. 이 문서의 UI·스키마·라우팅은 권장안이다.

## 1. 한 문장 방향과 결정 상태

한 번 입력한 회의 원문을 보존하고, **원문에 근거한 결정·미결·숫자·고객 신호·다음 행동을 검토한 뒤**, 선택한 항목만 고객·프로젝트·할 일에 연결한다. Office 역할은 판단과 배분안을 만들고, Codex는 승인된 개발 job에 쓸 수 있다. Claude는 현재 명시적으로 연결한 MCP 클라이언트의 수동 사용 경로다. 각 단계의 **제안 / 확인 / 저장 / 실제 실행** 상태를 섞지 않는다.

| 구분 | 이번 설계에서 다루는 내용 |
| --- | --- |
| 이미 확정 | 중요한 고객 미팅은 분석 우선 대상. 운영자가 `분석`을 눌러 비용을 발생시킨다. AI 결과는 확인 후 사실로 사용한다. 직접 녹음과 외부 전사 텍스트가 초기 입력 경로다. 음성 원본은 30일 뒤 삭제하고 전사·요약은 보존한다. 월별 사용량·비용을 표시한다. |
| 이미 확정 | Moonlight가 개인 업무 정본이다. ClassIn에는 승인된 공식 객체·짧은 활동 요약만 보낼 수 있고 개인 상세 메모·전사문은 복제하지 않는다. 외부 발송·공식 변경·결제·삭제는 별도 확인 경계다. |
| 이번 권장 | 기존 메모/빠른 입력에서 시작하는 단일 검토 흐름, 출처 구간을 가진 제안 원장, **한 결과의 주관 역할 하나**, 확인된 항목만 목적지별 저장, 코딩 작업에 한정한 Codex job 연결. |
| 미정 | 첫 실사용의 주 입력 비율(직접 녹음/외부 전사/붙여넣기/Drive), 화자 분리 공급자와 정확도 기준, 상세한 보관·백업 삭제 범위, Claude 자동 실행 필요성, 비용 상한액. 이 문서는 선택지를 남기고 값을 확정하지 않는다. |

## 2. 현재 되는 것과 연결되지 않은 것

2026-09-23 코드·로컬 확인 기준이다. `코드 있음`은 실제 화면 도달이나 운영 배포를 뜻하지 않는다.

| 흐름 | 현재 확인된 상태 | 결손 |
| --- | --- | --- |
| 빠른 텍스트 메모 → 할 일 | 전역 `QuickMemo`에서 텍스트 저장·AI 할 일 추출과 선택 저장 가능 (`apps/hub/components/hub/quick-memo.jsx`). | 저장 할 일에 원문 위치·담당·기한·고객/프로젝트 링크가 완결되지 않는다. |
| 메모 화면 | `Memos`는 `MemoComposer`/`MemoUseComposer`를 렌더한다 (`apps/hub/components/hub/pages/memos.jsx`). | `MemoCapture`를 렌더하지 않으므로 **현행 화면에서 음성 업로드·전사 검토에 도달할 수 없다**. |
| 짧은 미디어 분석 부품 | `memo-capture.jsx`와 `/api/hub/intake/multimodal`의 Gemini 구조화 경로가 있다. 단일 미디어 14 MiB, 요청 20 MB, 텍스트 2만 자, 45초 호출 제한 (`apps/hub/lib/multimodal-intake-core.js`). | 브라우저 직접 녹음, 긴 회의 비동기 처리, 영속 원본·전사 구간·근거 오프셋, 30일 삭제, 월 비용 원장이 없다. 테스트는 모의 공급자 응답의 계약 검증이다. |
| 메모 분석 | 선택 기록 패턴 분석 UI가 있다 (`pages/memo-pattern-panel.jsx`). | 주간 범위에 기록이 없으면 과거 20건으로 대체되고 Engine 부재 때 preview 패턴을 낼 수 있다. `preview`와 저장/분석 성공 표시를 엄격히 구별해야 한다. |
| Eevee Office | 자유 대화와 `weekly_report`·`customer_reply` 워크플로가 구현돼 있다. 역할별 의견·반론은 **같은 모델의 여러 호출**이다 (`apps/hub/lib/office/workflow-service.js`). | 회의 전사 전용 intent·원문 구간/숫자 검증·다수 작업 배분·실행 영수증 연결은 없다. 기존 source review는 인용 존재 확인이지 의미 검증이 아니다. 역할 품질도 미인증이다. |
| MCP/에이전트 API | 로컬 `npm run mcp:doctor`가 8개 core 도구 발견, Hub의 작은 읽기는 `live/supabase`로 응답했다. 점검 결과 `agentToken=false`라 쓰기 권한은 검증하지 않았다. `request_council: meeting-synthesis`와 `get_work_context` 등 부품이 있다 (`packages/mcp-server`). | 이번 로컬 주 작업공간의 `.mcp.json`에는 `eeoCRM`만 있으며 Moonlight MCP를 Codex/Claude에서 실제 등록·호출했다는 증거가 아니다. `get_work_context`는 task/project/content만 받는다. 회의·저널 원문/제안 전용 도구가 없다. `meeting-synthesis`는 Office 9인 실행이 아니다. |
| Codex/Claude 실행 | `agent_jobs`와 선택적 로컬 Codex worker는 등록 Git 프로젝트에서 읽기/초안/분리 worktree 적용을 지원한다 (`packages/codex-worker/README.md`). Claude는 수동 MCP 클라이언트 경로가 가능하다. | worker는 명시적 기동·인증이 필요하고 이 화면의 대화 맥락·업무 쓰기 권한을 자동 상속하지 않는다. Claude 자동 실행 worker는 없다. 녹음 파일을 MCP에 등록하는 것만으로 이들이 업무를 분배·실행하지 않는다. |

현재의 가장 큰 간극은 **분석 부품 → 사용자가 확인하는 화면 → 정본에 연결된 선택 저장**의 연속성이 없다는 점이다. `MemoCapture`를 그대로 표시하면 해결되지 않는다. 지금은 추출된 행동이 기본 전부 선택되고, 결과를 합친 저널 본문이 2만 자를 넘으면 저장이 거부되며, 원본 파일은 영속 저장되지 않는다.

## 3. 사용자가 거치는 하나의 흐름

`빠른 메모/메모`에서 **회의·정리 입력**을 연다. 기존 최상위 Office 탭이나 새 사이드바 앵커는 만들지 않는다. 메모 목록은 원문을 찾는 곳, 상세는 검토·연결하는 곳, Office는 필요한 전문 판단을 요청하는 곳으로 역할을 분리한다.

1. **입력·임시 보존**: M0에서 붙여넣기와 `.txt` 전사 가져오기를 연결한다. M1에서 짧은 오디오 업로드와 브라우저 직접 녹음을 녹음 중단·권한·업로드 복구까지 포함해 연다. 원문 저장 receipt를 먼저 받고 분석 여부를 묻는다. 분석 실패에도 원문이 남는다.
2. **수동 분석**: `분석` 버튼 옆에 추정 처리 비용/사용량의 표시 상태를 둔다. 실행 ID를 고정하고 진행·실패·재개를 보여준다. 긴 파일은 백그라운드 전사 후 구간 단위 구조화한다. 음성 외에도 지저분한 메모를 그대로 입력할 수 있다.
3. **근거 검토**: 왼쪽/상단에 원문·전사, 오른쪽/하단에 `요약 / 확정 결정 / 미결 / 수치·조건 / 고객 우려·관심 / 할 일` 후보를 놓는다. 각 후보는 클릭하면 근거 문장과 시각(있을 때)을 보여준다. 모델 제안·원문에 없는 해석·화자 불명은 명확히 표시한다. 운영자가 고치거나 버려도 원문은 보존한다.
4. **목적지 선택**: 후보별로 개인/회사 범위, 고객·프로젝트, 실제 담당자, 기한, 목적지(task/CRM 연락 결과/프로젝트 기록/브랜드 소재/보관)를 확인한다. 같은 이름의 고객이나 불확실한 날짜는 자동 확정하지 않는다. **Office 주관 역할**과 **실제 할 일 담당자**는 별개다.
5. **선택 저장·영수증**: 체크한 항목만 기존 정본 쓰기 경로로 보낸다. 항목마다 `저장됨 / 중복 / 충돌 / 결과 확인 필요 / 실패`를 표시하고 원문 구간·확인자·목적지 ID를 남긴다. `record_contact_outcome`은 실제 이루어진 연락에만 사용한다. 저장 성공을 발송·완료·매출 증가로 표현하지 않는다.
6. **다음 실행**: 확정된 할 일은 Today/프로젝트에 나타나고 원문으로 되돌아올 수 있다. 전문 판단이 필요하면 선택한 후보만 Office에 전달한다. 엔지니어링 티켓은 별도 승인된 Codex job을 만들 수 있다. 외부 메시지·ClassIn 공식 요약은 별도 초안/확인 흐름이다.

### 값과 판단을 보존하는 규칙

금액·수량·기한·성공 조건은 `원문 값 + 단위 + 발화자/출처 + 시점 + 확정도`를 한 묶음으로 추출한다. 예를 들어 “다음 달쯤 100개”는 확정 발주 100건이나 정해진 납기일이 아니다. 숫자 하나로 CRM 점수나 목표 관측값을 자동 가산하지 않는다. 명시적 확인 뒤 해당 정본에 기록하고, 계산 지표는 기존 지표 정의를 사용한다. 원문과 다른 수정은 수정자·시각·이전 값을 남긴다.

## 4. 데이터·권한·AI 계약

**정본은 기존 `journal_entries`와 task/CRM/project 원장을 재사용**한다. 다만 텍스트 파일럿인 M0부터 분석 run·근거 있는 후보·적용 영수증의 최소 영속 구조가 필요하다. React state나 탭의 `sessionStorage`만으로는 검토·재시도·새로고침 후 복구 계약을 만족하지 못한다. 장기 회의가 들어오는 M1에는 원본과 전사 구간을 별도로 더한다. 테이블명은 구현 시 마이그레이션과 도메인 경계를 검토할 **권장 이름**이며 승인된 스키마가 아니다.

| 자료형 | 최소 필드와 불변식 |
| --- | --- |
| `meeting_proposals` · **M0** | 종류, 제안 문장, `source_revision`, 텍스트 원문의 시작/끝 위치와 짧은 인용, 확정도(`stated/derived/unknown`), 검토 상태와 검토자/승인 버전, 선택한 scope/target/실제 담당·기한. M1에서는 전사 revision·segment ID·시각도 연결한다. 근거 없는 내용은 `inference`로 격리하며 사실 후보와 섞지 않는다. |
| `meeting_analysis_runs` · **M0** | 분석 요청 ID/입력 해시/정책 버전, provider/model, 토큰·오디오 길이 등 공급자 단위, 예상 비용과 통화/가격 버전, 실제 청구 불명 시 null, 실패·복구 상태. M1 비동기 실행에는 작업 lease·시도·checkpoint·공급자 중복 과금 방지 가능 여부를 추가한다. 월 집계는 기록된 run에서 계산하며 임의 비용을 생성하지 않는다. |
| `meeting_application_receipts` · **M0** | `(workspace, proposal, destination)` 고유키, 검토/원문 버전, 목적지의 예상 revision, stable command ID, 불변 요청 hash, 저장 결과/목적지 ID. 타임아웃 후 영수증을 조회하고 같은 ID/내용으로만 재시도한다. 기존 task command·`journal_links`와 연결하며 결과를 중복으로 정본화하지 않는다. |
| `meeting_sessions` · **M1** | `workspace_id`, 범위, 원문 종류, 저널 ID, 원본 해시, 분석 상태/버전, 원본 storage 경로·`delete_after`, 관계 ID(확인된 것만). 재분석해도 원본 정체성 유지. |
| `meeting_transcript_segments` · **M1** | 순서, 원문 텍스트, 시작/끝 ms·화자 라벨(없으면 null), 수정 이력. 전체 전사는 세그먼트를 합쳐 내보낼 수 있고 2만 자 저널 본문에 의존하지 않는다. |

원본 오디오는 private storage와 서명된 제한적 접근으로만 다룬다. 30일 만료 삭제는 재시도 가능한 정리 작업으로 만들고 **실제 삭제 receipt**를 보관한다. 삭제 작업 실패·백업 잔존 여부도 UI/운영 로그에서 거짓 완료로 보이지 않게 한다. 전사와 요약은 보존하되 민감한 개인 원문을 회사 scope·ClassIn·범용 MCP 도구에 기본 공개하지 않는다. 에이전트에는 요청한 범위의 **필요한 구간만** 전달한다. Hub read는 HTTP 200 `status:error` 봉투를 확인하고, write는 기존 guard/서버 영속화 계약을 따른다.

AI 계약은 `전사 → 출처 구간 지정 → 항목 추출 → 소스 인용 확인 → 운영자 검토 → 선택 적용`이다. 전사 모델과 구조화 모델의 결과를 구별한다. 인용 문자열이 있다는 것만으로 해석이 옳아지지 않으므로 수치·약속·고객 반응의 의미 검토는 별도 테스트와 사용자 확인이 필요하다. 긴 회의의 요약 과정에서 사라진 안건이 없도록 구간별 후보를 합치되, 중복 제거 전 원본 근거를 유지한다.

## 5. Office와 외부 에이전트 배분

이브이가 전체를 접수하고 무조건 9명에게 방송하는 방식은 사용하지 않는다. **한 후보/결과물에 주관 역할 하나**, 필요 시 반론을 줄 수 있는 보조 역할 하나를 정한다. 아래는 현재 역할 지침을 활용한 권장 라우팅이다. 역할별 별도 호출도 같은 모델이며 독립 전문가의 인증으로 표시하지 않는다.

| 결과의 성격 | 주관 | 조건부 보조 | 실제 목적지 |
| --- | --- | --- | --- |
| 흩어진 안건·결정·인계 요약 | 이브이 | 미결 기한이 크면 샤미드 | 회의 요약/검토 목록 |
| 일정·대기·후속 순서 | 샤미드 | 비용/용량 쟁점이면 리피아 | 확인 후 task/프로젝트 |
| 고객 요구·가격·반응 | 부스터 | 위험한 약속이면 블래키 | 확인 후 CRM 근거/다음 행동 |
| 목표 변경·선택지 | 에브이 | 해당 실행 담당 1명 | 확인 후 결정 기록 |
| 제품 문제·사용자 요구 | 글레이시아 | 코드 원인 분석이면 쥬피썬더 | 확인 후 제품 백로그 |
| 기술 결함·구현 작업 | 쥬피썬더 | 일정 영향이면 샤미드 | 승인된 Git 프로젝트의 Codex job 후보 |
| 비용·자원·수지 | 리피아 | 대외 조건이면 부스터 | 확인 후 재무/목표 관측 |
| 위험·민감 정보·확약 | 블래키 | 원인 영역 주관 1명 | 공개 범위/승인 조건 제안 |
| 메시지·콘텐츠 소재 | 님피아 | 사실 주장 검토는 원 분야 | 확인 후 브랜드/초안; 발행 별도 |

Office에 넘기는 입력은 전체 녹음이 아니라 `목적 + 확정 사실/미확인 + 근거 구간 + 기존 관련 기록 + 원하는 산출물`의 작고 버전 고정된 묶음이다. 현재 `weekly_report/customer_reply` 외에 `meeting_triage` 또는 이에 준하는 intent를 추가해야 한다. Office의 대화 결과를 곧바로 여러 곳에 쓰지 않고 같은 검토/receipt 경로를 거친다. 역할 점수가 재평가되기 전에는 고객 조건·재무·법적 약속을 Office만으로 확정하지 않는다.

**MCP**에는 인증된 범위에서 `get_meeting_context`(선택된 원문 구간·버전·누락 표시·cursor/hash), `save_meeting_proposal`(원본 버전·근거 참조에 묶인 제안), `get_meeting_proposal_receipt`를 먼저 제안한다. tool 이름은 설계안이다. 현재 MCP 응답 상한 128 KiB를 넘지 않도록 구간을 페이지로 나눈다. 지금의 Agent API는 단일 환경변수 bearer token에 고정된 workspace/actor/scopes를 붙이므로, Codex와 Claude를 별도 권한·감사 주체로 운영하려면 토큰 registry 또는 동등한 분리 인증, 회의 read/proposal-write scope가 선행돼야 한다. 도구를 등록하는 행위는 자동 실행·타 도구에 대한 인증·사용자 승인·업무 쓰기 권한을 만들지 않는다. 직접 저장/적용 도구는 읽기·제안 권한과 분리한다.

**Codex**는 회의에서 나온 개발 이슈가 실제 코드베이스·완료 조건·검토자가 확인된 경우에만 기존 `agent_jobs`로 읽기/초안부터 맡긴다. `apply`는 분리 worktree에서 명시적 시작·검토·테스트 후 취급한다. 고객 연락·일정 조정·재무 기록의 범용 executor로 만들지 않는다. **Claude**는 우선 명시적으로 연결한 MCP 클라이언트에서 같은 좁은 context와 제안 저장 도구를 사용하는 수동 경로다. 자동 Claude 작업이 꼭 필요하다고 검증되면 별도 worker, 인증·비용·job/receipt·중단 계약을 설계한다.

## 6. 파일 단위 구현 순서와 통과 기준

Office의 현행 48초/입력 길이 제한 안에서 검토된 짧은 구간만 전달한다. 한 결과의 주관이 하나이며 재시도해도 중복 기록되지 않는다. |
| **M3 — MCP·개발 job 연계** | `packages/mcp-server`/Agent API에 범위·revision·cursor 제한 회의 context/제안 도구와 회의별 read/proposal-write scope 추가. 각 단계는 기존 read error 봉투, same-origin/server write guard, scope/RLS, 저장 receipt를 통과해야 한다. UI 구현 전 `DESIGN.md`와 메모/CRM의 최신 스펙을 다시 읽는다. 작은 파일 인테이크 부품을 연결할 때도 실제 Gemini 호출·원문 보존·장애 회복을 별도 검증한다. Office 역할의 현재 지침 버전(v16)에 대한 **독립 의미 품질 점수는 아직 없다**. UI/계약 테스트가 통과해도 그 점수를 대신하지 않는다.

**첫 운영 출시 게이트는 M0+M1의 완료**다. 그전 텍스트 파일럿을 확정된 음성 기능의 출시로 표시하지 않는다. M2의 CRM/Office 자동 배분과 M3의 외부 에이전트 도구 연계는 추가 출시 범위이며 각각 별도 검증을 요구한다.

## 7. 검증 시나리오와 관측

- 한 회의에 고객 약속, 제품 버그, 브랜드 아이디어가 섞여도 원문에서 각각의 근거로 돌아온다.
- “아마”, “다음 달쯤”, 화자 불명, 100개/100만 원처럼 단위가 중요한 발언은 확정값으로 변하지 않는다.
- 같은 이름의 고객 두 명과 서로 다른 회사/개인 범위가 있을 때 잘못된 자동 귀속·전사 유출이 없다.
- 분석 실패, 화면 닫기, 네트워크 타임아웃, 저장 후 응답 손실, 다시 분석, 원본 삭제 실패에서 각각 복구 가능한 상태와 원본/영수증이 남는다.
- 할 일 생성, 연락 **기록**, 실제 메시지 **발송**, ClassIn 공식 요약을 서로 다른 권한·상태로 확인한다.

지표는 첫 실사용에서 기준선을 잡는다: 미팅당 검토 완료율, 전사/근거 수정률, 선택 후보의 저장 성공률, 중복·미확인 쓰기 건수, 약속 후속 누락, 입력→검토 완료까지 걸린 시간, 분석 실패·재시도율, 월별 실제/추정 API 비용. 목표 수치를 아직 임의로 만들지 않는다. 원문이나 고객명을 계측 로그에 복제하지 않는다.

## 8. 외부 기술 가능성의 범위

[Gemini 오디오 이해 공식 문서](https://ai.google.dev/gemini-api/docs/audio)는 전사·요약·시각/화자 관련 추출 가능성을 설명한다. [OpenAI 전사 공식 문서](https://developers.openai.com/api/docs/guides/speech-to-text)는 다른 공급자 선택지와 업로드 제한을 제공한다. 이는 **제품 통합의 가능성**이지 현재 Moonlight의 장시간 녹음·보관·화자 정확도 보증이 아니다. [MCP 아키텍처](https://modelcontextprotocol.io/specification/2025-11-25/architecture)의 client/server 도구 호출 모델과 [Claude Code의 MCP 공식 문서](https://code.claude.com/docs/en/mcp)는 수동 클라이언트 연결의 기반이지만, 작업 큐·승인·정본 저장은 Moonlight가 구현해야 한다.

## 9. 실제 운영 연결의 선행 조건

코드 검증과 운영 연결은 별개다. 운영 DB에 새 additive migration과 기존 Office 0038의 적용 상태를 확인하고, private storage bucket·삭제 예약 작업·Gemini 키/과금 설정·Hub/Engine 비밀키를 **배포 환경별로** 점검해야 한다. 로컬 `mcp:doctor`의 `live` 읽기는 운영 배포, Codex/Claude MCP 등록 또는 worker 기동의 증거가 아니다. 첫 출시는 저장/분석/삭제 실패를 관측할 수 있는 로그와 실제 입력 파일의 왕복 검증을 통과한 뒤 표시한다. 공급자나 모델을 바꾸면 전사 품질·비용·보관 방식·실행 제한을 다시 측정한다.
