# 프로젝트 상태·완료 행동 정리

> 상태: 운영자 승인 1~4순위 구현·로컬 검증 (2026-09-24). 운영 배포는 별도.
> 상위 정본: `docs/operator-workflow-profile.md`, `DESIGN.md`.
> 관계: `2026-09-09-project-delivery-lifecycle.md`의 착수·프로토타입·완료 필수 조건과 목록 완료 체크박스 규칙, `2026-09-23-project-direct-workflow-redesign.md` §5의 서버 완료 검증 제안을 이 문서가 대체한다. PMS 분류·장르·백로그 어휘는 변경하지 않는다.

## 목표와 화면 계약

- 프로젝트 상태는 **계획 / 진행 중 / 막힘 / 완료 / 보관**으로 표시한다. 상태 선택, 상태 칩, 목록 묶음에서 `active`는 모두 **진행 중**이다.
- 할 일 진척과 프로젝트 상태는 별개다. 할 일 4/4를 처리해도 프로젝트를 자동 완료하지 않는다. 프로젝트 개요·상세에는 `프로젝트 상태`와 `할 일 N/N 처리`를 구분해 보여준다.
- 할 일을 모두 처리했고 읽기 결과가 완전하면 기존 다음 행동 자리에 **결과 확인 → 완료 검토**를 제시한다. 프로젝트 목록의 확인 아이콘도 즉시 완료하는 체크박스가 아니라 이름이 있는 **완료 검토** 버튼이다. 완료·보관 목록에는 다시 열기 행동을 한 번만 둔다.
- `완료 검토`는 결과·완료 기준 드로어를 열며, 저장 응답을 받기 전에는 상태를 완료로 표시하지 않는다. 읽기 오류나 부분 읽기일 때는 확인된 할 일만으로 완료를 권하지 않는다.

## 서버 상태·완료 계약

- 일반 편집에서 `진행 중`으로 바꿔도 최초 착수 시각을 기록하고 현재 보류·병목을 해제한다. `막힘`에는 이유가 필요하며 보류 시각을 기록한다. `계획`으로 되돌려도 과거 착수 시각은 지우지 않는다. 직접 상태 편집과 실행 기록 버튼은 같은 규칙을 사용한다.
- 착수에는 사전 계획 입력이 필요 없다. 완료에는 **이번에 남길 결과 한 줄**, 등록한 완료 기준이 있다면 **그 기준 모두 확인**, **막힌 점 해소**가 필요하다. 프로토타입 확인일을 정했다면 실제 작동 확인도 필요하다. 결과물 URL과 별도 착수 버튼은 완료의 필수 조건이 아니다. 입력한 URL은 계속 안전성을 검증한다.
- 상태 변경은 기존 버전 비교와 원자 저장을 유지한다. 기존 완료·보관 기록의 완료 시각과 원자료는 보존한다. `create_project`를 상태 없이 호출하는 구형 클라이언트의 기본 `active` 생성은 그대로 둔다. 그 구형 경로는 `started_at`을 자동으로 쓰지 않는 호환성 경계다.

## 홀딩

5순위인 장르의 `기타`/미지정, 백로그·보관 어휘, Review 잔재, 일반 위험·기한 문구는 이번 변경에 포함하지 않는다. 각각의 의미와 실제 데이터 분포를 확인한 뒤 한 번에 정리한다.
