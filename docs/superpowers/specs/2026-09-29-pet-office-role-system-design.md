# 펫·Office 역할·프롬프트·기능 정비 설계

> 상태: APPROVED · 2026-09-29 운영자 “고고” 및 알림·다자 대화·담당 전환 요구 반영. 전용 checkout 코드·빌드 검증 완료, 데스크톱 적용·UI 검증 대기. 프롬프트 의미 평가는 아래 구현 기록을 따른다.
> 요청: 2026-09-29 운영자 — “펫들 과 에이전트, office, 프롬프트, 역할과 기능에 맞게 디벨롭, 체계적 정비”.
> 착수 조사 기준: `944fac9e`, 당시 역할 카드 `2026-09-23.v25-grounding-regression-fix`.
> 확정 방향: 기존 아홉 캐릭터와 직무를 유지하고 역할의 적용·기능 연결·검증을 정교화한다. 역할 관련 알림의 발신 펫이 바뀌고, 그 자리에서 문의·담당 전환·여러 관점의 대화로 이어지는 사용 흐름을 우선 구현한다.
> 관계: 2026-09-25 펫 즉시 대화 설계의 사용자 노출 명칭과 역할 연결을 보완한다. 2026-09-24 에이전트 계층 경계, 브랜드 Council 분리, 로컬 스킬 실행 경계는 따른다. 역할 카드의 말투 동결은 현재 버전의 독립 재평가가 끝난 뒤 증거를 근거로 해제한다.

## 1. 목표

펫에서 담당을 고를 때 보이는 설명, 이브이가 추천하는 담당, 실제 답변이 따르는 역할, 결과 뒤에 가능한 행동이 서로 일치하게 만든다. 운영자는 요청한 결과물을 받고, 실제 기록이나 실행이 필요한 경우 기존 업무 흐름으로 이어간다.

성공을 기능 개수나 캐릭터 대사 수로 판단하지 않는다. 담당 선택이 이유에 맞고, 요청에 필요한 자료가 전달되며, 결과를 다시 정리하지 않고 쓸 수 있는지를 확인한다.

## 2. 착수 당시 코드에서 확인한 상태

| 항목 | 확인된 상태 | 정비 이유 |
|---|---|---|
| 역할 지침 | Engine `role-cards.ts`에 목적·담당·전문 기준·근거·산출물·인계·말투가 있고, 생성과 검수에서 공유한다 | 이미 있는 체계를 확장한다. 개별 화면에 별도 페르소나를 만들면 기준이 갈라진다 |
| 공개 역할 정보 | `packages/agent-contracts/office.js`의 roster와 Swift `OfficeChatModels.swift`의 이름·직무를 각각 작성한다 | 현재 이름은 일치하지만 독립 변경에 취약하다. Swift 테스트도 별도 하드코딩 이름 목록과 비교한다 |
| 담당 추천 | `routing.ts`는 roster의 직함·pitch만 읽는다 | 상세 카드의 경계와 확장된 담당 범위가 추천 입력에 충분히 반영되지 않는다. 실제 오배정률은 아직 측정하지 않았다 |
| 펫의 Council | `QuickMode.council`에서 담당 한 명에게 `/api/hub/office/chat`을 호출한다. 브랜드 Council은 더보기의 별도 브라우저 이동이다 | 같은 이름이 일대일 Office 대화와 브랜드 검토를 가리킨다 |

| 펫의 근거 | 응답 계약도 `source: provided`, 프로젝트 빈 배열을 요구한다 | 입력·최근 대화·직접 가져온 텍스트는 참고하지만, 일반 대화가 오늘 일정·고객 DB 전체를 읽지는 않는다 |
| 결과 처리 | 펫의 nextAction은 텍스트다. 업무 안의 workflow 경로에는 별도의 결과·근거·제안·적용 계약이 있다 | 문장으로 제안한 행동과 실제 저장 버튼을 구분해야 한다 |
| 대화 보관 | Hub origin·담당·범위별 메모리 보관, 요청에는 최근 4왕복을 제한 전달한다 | 장기 기억·앱 종료 후 복원을 약속할 수 없다 |
| 품질 증거 | 최신 완전 독립 평가는 v10 계열의 57~71점·최종 통과 0/9. 현행 v25는 독립 재채점 전이다 | 이 점수를 현재 v25의 점수로 부르지 않는다. 생성 성공률과 의미 품질도 구분한다 |

위 표는 `944fac9e` 착수 시점의 구조와 계약 조사 결과다. 이후 [v25 고정 재평가](../../evaluations/2026-09-29-office-v25-baseline/README.md)에서 원본 36/39건 생성, 174/180항목 심사, 최종 통과 0/9명을 기록했다. 생성 실패와 심사 누락을 보존했으며, 실제 운영 성과를 평가한 결과는 아니다. 이 독립 재평가를 근거로 v26의 제한된 교정을 진행한다.

## 4. 각 계층의 역할

| 계층 | 맡는 일 | 결과 |

| Hub | 인증된 데이터 조회, 문맥 구성, 요청·결과 보관, 운영자가 선택한 적용 | 조회 상태와 실제 저장 결과 |

앱의 CRUD 기능은 버튼을 누른 운영자의 동작이다. Office 모델은 이를 스스로 실행한 것으로 말하지 않는다. 브랜드 Council은 별도 경로를 유지하고, Legend의 연결 범위도 기존 결정대로 둔다.

## 6. 정의와 프롬프트 관리

### 6.1 정본과 파생물

- 공개 역할 정보는 기존 `@com-moon/agent-contracts` 안의 버전 있는 카탈로그 한 곳에서 관리한다. ID·표시명·직무·짧은 책임·지원 요청 종류·인계 기준을 둔다.
- Engine의 역할 카드는 전문 지식·판단 절차·근거 기준·말투의 정본으로 유지하고 공개 역할 ID를 참조한다. 전체 프롬프트를 브라우저나 Swift에 복제하지 않는다.
- Swift의 표시용 정보는 공개 카탈로그에서 생성한 번들 리소스를 사용한다. 기존 색상 키와 이미지 자산의 매핑은 유지한다. 생성물 차이를 확인하는 검사를 두어 누락된 역할·오래된 직무명을 잡는다.
- 담당 추천은 같은 카탈로그의 책임·지원 요청·인계 경계를 읽는다. 긴 말투 예시나 전체 역할 카드를 추천 입력에 넣지는 않는다.
- 자동 생성 역할 지침 문서에는 역할 버전과 원본을 계속 표시한다. 코드와 문서를 따로 수정하지 않는다.

### 6.2 프롬프트 조립 순서

1. 실제 권한·자료 범위·출처·출력 계약.
2. 운영자의 현재 요청과 명시 조건.
3. 회사/개인 범위의 확정 업무 기준.
4. 선택된 역할의 전문 판단 기준.
5. 대화/초안/검토/회의와 구체 업무 의도.
6. 산출물의 독자·브랜드 문체, 그 안에서 역할의 문장 리듬.

`prompt.ts`와 `workflow-prompt.ts`의 공통 정책은 공유하되 두 API의 응답 계약은 각각 유지한다. 첫 단계에서 전체 API를 바꾸지 않는다. 역할 이름이나 프롬프트가 실제 도구 권한을 부여하지 않는다.

### 6.3 교정 후보와 증거

카드의 강한 표현과 고정된 형식이 작은 요청을 과도하게 키우는지는 현재 응답으로 확인한다. 예를 들어 모든 기능을 3단계로 고정하거나, 근거 없이 즉시 중단을 권하거나, 간단한 메모를 전원 업무 배분표로 확장하는지를 본다. 문구만 보고 현재 실패라고 단정하지 않는다.

재평가 뒤 한 번에 한 원인만 바꾸고 버전·수정 이유·전후 근거를 남긴다. 말투는 역할의 질문 방식과 강조점으로 구별하고, 고객에게 전달할 산출물에는 해당 고객·브랜드 문체를 우선한다.

## 7. 펫과 Office의 동작 연결

사용자 노출 이름은 일대일 대화를 `담당자에게 묻기`, 웹의 다자 관점 작업을 `Office 회의실`, 별도 브랜드 경로를 `브랜드 Council`로 구별하는 안을 권장한다. 내부 식별자와 저장 키를 일괄 개명하는 작업은 필요하지 않다.

선택한 펫은 기본 담당을 정한다. 이번 요청에서 직접 고른 담당·범위는 명시적으로 표시한다. 전송 중 펫 외형을 바꿔도 이미 보낸 요청의 담당은 변하지 않고, 답변에는 실제 응답 담당을 표시한다.

기능은 다음 자료 수준에 맞게 연결한다.

| 요청 | 연결 | 실패·미연결 처리 |
|---|---|---|
| 직접 질문·붙여넣은 글 검토 | 현재 Office chat 경로 | 입력과 대화를 보존하고 명시 재전송을 제공한다 |
| 현재 메모·할 일로 질문 | 사용자가 선택한 원문의 복사본을 전달 | 원본 변경과 AI 답변을 자동 동기화하지 않는다 |
| 실제 고객 답장·주간 정리 | 기존 Hub workflow의 근거 있는 업무 화면으로 연결 | 고객/기간/범위가 없으면 선택하도록 한다. 일반 chat이 조회한 듯 답하게 하지 않는다 |
| 다른 전문가 관점 | 현재 범위에 맞는 기존 Office 회의실·멘토 경로 | 회사/개인 근거를 섞지 않고 출처와 질문을 보존한다 |
| 할 일 반영·로컬 실행 | 기존 적용 또는 스킬 요청서 흐름으로 연결 | 생성·복사·저장·적용·실행 상태를 각각 실제 응답으로 표시한다 |

2026-09-29 후속 확정은 첫 개발 묶음을 다음 흐름까지 확장한다. 일반 초안/검토 모드와 영구 대화 보관은 별도 범위로 두며 기존 chat/council 계약 안에서 구현한다.

### 7.1 역할별 알림과 발신 펫

- 실제 신규 문의는 부스터, 임박한 일정은 샤미드, AI 답변 도착은 그 답변의 실제 담당자가 알린다. 현재 연결된 원천에만 적용하고 다른 직무의 알림을 임의 생성하지 않는다.
- 알림을 보여주는 동안 얼굴·발신자 이름이 담당자를 나타낸다. 이를 사용자가 저장한 기본 펫 설정에 덮어쓰지 않는다.
- 알림의 기본 행동은 담당자와 그 내용으로 대화하기다. 상세 Hub 원문을 여는 행동을 함께 유지한다. 알림 노출·클릭은 AI 자동 호출이나 외부 발송을 발생시키지 않는다.
- 문의·일정 알림은 요약 자료이며 상세 원문 미조회 상태를 문맥에 표시한다. 업무 범위가 확인되지 않으면 임의로 회사로 지정하지 않는다.

### 7.2 같은 안건에서 담당 전환과 여러 관점

- 대화는 Hub origin·업무 범위·안건별로 구분한다. 담당자를 바꾸면 같은 안건의 이전 대화·작성 중 초안·출처를 유지하며 다음 발언자만 바뀐다.
- 범위를 바꾸거나 다른 알림 안건을 열면 각각의 대화로 이동한다. 이전 대화와 초안을 보존하고 회사/개인 문맥을 자동 합치지 않는다.
- 담당 1명은 기존 chat, 담당 포함 2~3명은 기존 council API 계약을 사용한다. 여러 관점의 실제 응답·이견·추천을 펫 안에서 읽는다. 실제로 호출하지 않은 참여자의 발언은 만들지 않는다.
- 답변과 알림에는 실제 담당 및 대화 식별자를 보존한다. 답변 알림을 열면 정확한 안건으로 돌아간다.
- 전송 중에는 전송한 담당·관점·범위를 고정한다. 전환 때문에 전송을 조용히 취소하거나 입력을 잃지 않으며, 중단·실패·늦은 응답은 기존 보존 계약을 지킨다.
- 입력 상한·최근 대화 길이 제한·앱 실행 중 메모리 보관 계약을 유지한다. 알림 요약·다른 담당의 답은 사실 인증이나 실행 완료 증거로 승격하지 않는다.

UI 변경은 기존 본문과 더보기 안에서 이루어지며 기존 화면의 표면 예산을 지킨다. 구체적인 화면 구현에 들어갈 때 루트 `DESIGN.md`와 최신 펫 스펙을 읽고 그 계약 안에서 설계한다.

## 8. 검증과 개발 순서

### 묶음 0 — 현재 기준선 고정

- v25의 역할·공통 정책·생성·검수·회의·모델 설정 해시를 기록한다.
- 기존 33개 시나리오·39개 생성 범위의 실제 응답을 보존한다. 실패·종속 차단을 점수에서 지우지 않는다.
- 평가 대상의 고정된 런타임 프롬프트를 작성하지 않은 심사자가 역할 전문성·근거·말투·협의·실용성을 채점한다. 후속 구현과의 관계는 평가 기록에 공개한다.
- 기존 기준인 총점 70/100 이상, 각 축 14/20 이상, 치명 오류 0, 관찰 범위 완비를 유지한다. 이 기준을 만족해도 전체 현업 성과를 보증한다고 말하지 않는다.

완료 증거: 현재 버전의 원문·해시·점수 또는 누락 사유·역할별 개선 목록. 이 단계까지 역할 카드 본문은 동결한다.

### 묶음 1 — 역할 정의·명칭·추천 통일

- 공개 카탈로그와 Swift 파생물, 담당 추천 입력을 일치시킨다.
- 펫의 실제 일대일 대화와 Office 회의실·브랜드 Council 명칭을 구분한다.
- 명확한 단일 담당, 여러 역할이 겹치는 요청, 이미 담당을 고른 요청, 추가 업무가 불필요한 요청으로 추천을 확인한다.
- 로컬 계약 검증과 실제 UI에서 담당·범위·전송 중 변경·오류 후 초안 보존을 확인한다.

완료 증거: 9명 이름·직무 일치, 기능 경로 일치, 담당 추천의 근거, 기존 대화·기록 보존. 이 결과를 프롬프트 의미 품질 향상으로 환산하지 않는다.

### 묶음 2 — 근거가 있는 업무 연결

- 샤미드의 주간 정리, 부스터의 고객 답장, 님피아의 원문 다듬기부터 해당 업무의 실제 문맥·산출물과 연결한다.
- 업무마다 입력 원천·자료 시점·회사/개인 범위·부분 조회·결과 복귀 경로를 명시한다.
- 할 일 제안은 기존 적용 계약, 파일·코드 실행은 기존 로컬 스킬 요청서와 receipt로 이어간다.

완료 증거: 요청부터 결과·선택한 적용·재조회까지 한 업무 흐름을 확인한다. 테스트 성공·초안 생성만으로 실제 저장 성공을 표시하지 않는다.

### 묶음 3 — 평가로 확인된 역할별 프롬프트 교정

- 묶음 0에서 확인된 낮은 축과 반복 오류를 먼저 고친다. 아홉 명을 같은 문장으로 일괄 강화하지 않는다.
- 과거 오류인 미확인 가용 시간, 존재하지 않는 기능·고객 반응, 생성/저장 혼동, 허위 합의, 종결 뒤 새 업무 생성을 회귀 사례로 둔다.
- 개발 사례에서 조정한 뒤 미노출 평가 사례로 재확인한다. 결과를 보고 수정한 사례는 개발 자료로 이동한다.
- 기존 생성·workflow·회의의 공통 정책 변경은 세 경로를 모두 확인한다.

완료 증거: 역할별 변경 이유와 실제 전후 응답, 독립 재평가, 미통과·미검증 항목. UI 동작·속도·비용은 별도로 보고한다.

## 10. 승인과 적용 범위

승인된 방향은 **기존 아홉 직무 유지**, **명칭과 역할 정의 통일**, **현재 v25 평가**, **평가 후 역할별 기능·프롬프트를 순차 교정**이다. 후속 요청으로 §7.1~7.2의 역할별 알림·현장 대화·담당 전환·다자 관점을 우선 구현한다. v25 평가는 별도 고정 checkout에서 진행하며 기능 연결 작업과 병행한다.

역할 통합·재배치 또는 Office의 직접 도구 실행을 원하면 이 설계의 계층·역할 계약부터 바꾼다. 이번 개발 요청은 정비 의도로 기록하되 10월의 전체 개발 동결을 포괄적으로 해제한 결정으로 해석하지 않는다.

전용 `codex/pet-office-system` 브랜치에 다음 변경을 기록했다. 실제 데스크톱에 적용된 상태와 구분한다.

[v25 기준선](../../evaluations/2026-09-29-office-v25-baseline/README.md)은 36/39건 생성·174/180항목 심사·통과 0/9명이다. [v26 최초 미노출 평가](../../evaluations/2026-09-30-office-v26-holdout/README.md)는 8/8건 생성했지만, 미확인 가용 시간과 제품 조건을 확정하는 오류가 남았다. 생성 성공을 의미 품질 통과로 환산하지 않는다. 공개된 사례는 이후 개발 재현에 사용하며 새 미노출 평가와 분리한다.

후속 공통 지침 후보의 [분리 평가](../../evaluations/2026-09-30-office-source-state/README.md)는 공개된 사례 8/8건과 새 미노출 사례 5/5건을 모두 생성했다. 나중에 확인된 조건을 반영하고 미실행 상태를 유지한 경우도 있지만, 일부 개별 발언과 고객 초안은 미확인 조건을 여전히 확정한다. 따라서 역할 프롬프트의 의미 품질 교정은 완료되지 않았다. 최종 종합이 올바르더라도 화면에 노출되는 개별 발언의 오류를 통과로 처리하지 않는다. 후보는 전용 브랜치에 있고 운영 Engine에 적용하지 않았다.

`c6d1ca8d`에서 전체 테스트 3,445개 중 3,432개 통과·실패 0·테스트 DB가 필요한 13개 건너뜀을 확인했다. Engine 타입 검사와 생성 카탈로그 일치 검사도 통과했다. Mac 잠금 때문에 기존 실행 앱의 상태를 읽거나 새 앱으로 교체하지 못했다. 실제 창에서의 포커스·키보드·담당 전환·알림 복귀는 미검증이다. 대화는 앱 실행 중 메모리이므로 잠금 해제 후 기존 초안을 확인하고 교체한다.

처음 확인한 앱의 Hub 주소는 로컬 `http://127.0.0.1:3000`이고 데이터는 서울 운영 Supabase였다. 이후 점검에서는 3000 포트가 열려 있지 않았다. 따라서 저장된 주소만으로 현재 연결 성공을 주장하지 않는다. 연결·평가·화면 적용의 현재 기록과 남은 절차는 [구현 계획](../plans/2026-09-29-pet-office-system.md)을 따른다.
