## 1. 좋은 결과의 정의

목표는 **중요한 변화가 내 독자·업무에 주는 의미를 근거와 함께 이해하고, 쓸 만한 관점 또는 작은 실험 하나를 고르는 것**이다. 검색량·요약량·AI 호출 수는 성공 지표가 아니다.

결과물은 세 가지로 나눈다.

| 결과 | 답할 질문 | 다음 행동 |
| --- | --- | --- |
| 알아둘 변화 | 무엇이 달라졌고 왜 알아야 하는가? | 읽고 보관하거나 후속 관찰 |
| 콘텐츠 소재 | 이 브랜드 독자에게 어떤 질문·관점을 줄 수 있는가? | 중간 체크 → Studio |
| 적용·실험 후보 | 실제 업무나 제품에서 무엇을 시험할 수 있는가? | 명시 선택 후 task/project 후보 |

기사 하나가 세 결과를 모두 만들어야 할 의무는 없다. 충분한 근거가 없는 중요한 신호는 `추가 확인`으로 올리고, 제작 가능 소재와 구별한다.

## 2. 인사이트를 만드는 여섯 가지 규칙

### 2.1 브랜드별로 살아 있는 질문을 둔다

브랜드마다 이번 기간에 답할 질문 2~3개를 둔다. 기존 audience/promise/currentFocus/keywords/rules를 재사용하며 별도 브랜드 정체성 사본을 만들지 않는다.

예시 질문은 “이 분야에 무슨 뉴스가 있는가”보다 “독자가 지금 못 하는 일을 가능하게 만드는 변화는 무엇인가”에 가깝다. 이것은 질문 작성 예시이며 특정 브랜드의 확정 전략이 아니다.

질문에는 목적, 이미 아는 것, 모르는 것, 판단에 필요한 근거, 다음 검토일을 기록한다. 답을 얻거나 쓸모가 없어지면 닫는다. 오래된 질문이 검색 예산을 영구 점유하지 않게 한다.

### 2.2 기사가 아니라 실제 변경점을 추적한다

새로운 URL과 새로운 사실을 구분한다. 제품·버전·변경 종류·적용 대상·발효 시점을 묶어 사건을 식별한다. 발표, 제한적 제공, 일반 제공, 가격 변경, 철회는 별도 변화로 남긴다.

“어제도 본 발표의 새 해설”은 같은 사건의 관점 보강이다. “발표는 같지만 오늘 한국 계정에 제공”은 의사결정을 바꾸는 변경이다. 후자의 지역·조건을 버리고 둘을 중복 처리하면 안 된다.

### 2.3 의미를 인과 경로와 함께 쓴다

인사이트는 다음 순서로 작성한다.

1. **관찰:** 원문에서 실제 확인한 사실 또는 발언.
2. **변화:** 과거 상태와 비교해 달라진 점. 과거 근거가 없으면 비교 미확인.
3. **영향 경로:** 이 변화가 비용·행동·선택을 어떻게 바꿀 수 있는가.
4. **브랜드 관점:** 해당 독자에게 왜 중요한가.
5. **반대 근거·조건:** 결론을 약하게 하거나 뒤집는 사실은 무엇인가.
6. **다음 행동:** 지금 쓸 관점, 작은 실험, 또는 기다릴 확인 신호.

영향 경로와 미래 효과는 추론이다. 원문에 적힌 사실로 바꾸지 않는다. 연결 근거가 약하면 “관련 가능성”으로 남긴다. 억지로 독특한 주장을 만들거나 모든 변화에 거대한 전망을 붙이지 않는다.

### 2.4 새 소식과 과거 자료를 연결한다

[기존 레퍼런스 아카이브](../../research/2026-09-20-reference-writing/README.md)를 질문·개념으로 먼저 검색하고, 관련 자료 1~3개의 필요한 구간만 가져온다. 매번 전체 아카이브를 모델에 넣지 않는다.

기존 요약만 확보된 자료를 원문 재검증 완료로 승격하지 않는다. 공통 맥락 검색은 원자료의 유사성을 찾는 데 사용하며 서로 다른 조건의 연구·개인 경험을 합쳐 새 사실을 만들지 않는다.

사용자의 실제 경험·실험은 차별화 근거가 될 수 있다. 사용자가 명시 선택한 기록만 연결하며 개인 업무 메모를 자동으로 브랜드 자료에 넣거나 경험담을 생성하지 않는다.

### 2.5 관찰한 주장을 다시 확인한다

큰 가설에는 `현재 판단 / 지지 근거 / 반대 근거 / 다음에 관찰할 신호 / 재검토일`을 둔다. 새로운 근거는 이전 판단을 유지·수정·철회하는 데 사용한다.

초기에는 선택한 brief 안의 구조화 필드로 충분하다. 별도 지식 그래프·예측 시장·모든 기사의 가설화는 만들지 않는다. 적중 여부는 평가 조건과 시점이 정해진 가설에서만 판단한다.

### 2.6 이미 좋아하는 주제 밖에 작은 탐색 여지를 남긴다

초기 조사 시간 배분은 핵심 질문 70%, 인접 분야 20%, 새로운 출처·반대 근거 탐색 10%를 실험값으로 제안한다. 이는 콘텐츠 발행 비율이나 모든 브랜드의 고정 의무가 아니다.

놓친 중요 신호의 표본 검토에 따라 배분을 바꾼다. 정치 이슈에서 근거가 약한 주장에 형식적인 동일 비중을 주는 규칙으로 쓰지 않는다.

## 3. 수집 리듬과 출처 운영

| 흐름 | 초기 주기 제안 | 목적 |
| --- | --- | --- |
| 변화 수집 | 하루 1~2회 | 공식 발표·릴리스·업로드·정책·행사 변경 |
| 설명·연결 | 중간 체크 후 | 선택한 소재의 근거 보강·아카이브 연결·가공 |
| 주간 편집 | 주 1회 | 반복 신호·변한 판단·다음 주 행사·출처 효용 정리 |

출처별 설정: 고유 ID, 종류, URL/채널 ID, 주제, 우선도, 언어·지역, 관찰 주기, cursor, 최근 성공 시각, 저장 허용 범위, 실패 상태. 브랜드와 출처는 다대다로 연결하되 fetch는 공유한다.

- 고정 출처는 공식 RSS/Atom/API·변경 문서를 우선한다. ETag/Last-Modified를 제공하면 조건부 요청을 사용한다.
- Brave는 고정 출처 밖 발견과 특정 미확인 주장 검증에 사용한다. 공유 주제 쿼리는 한 번만 실행하고 브랜드별 렌즈를 나중에 적용한다.
- 검색 창은 이전 성공 시각과 겹치게 잡는다. 초기 72시간 겹침 + 주간 7일 보완을 제안하되 늦은 색인·피드 누락을 완전히 방지한다고 보장하지 않는다.
- 최초 연결은 최근 7일을 기준선으로 제안한다. 과거 자료 전체 수집은 별도 작업으로 분리한다.
- 기사 게시일, 수정일, 사건 발생일, 최초 발견일, 마지막 확인일을 별도로 저장한다. 모르는 날짜를 모델이 생성하지 않는다.
- 행사에는 개최일·시간대·등록 마감·온라인 여부를 구분한다. 발견만으로 캘린더에 등록하지 않는다.
- 새 정보 없음, 접근 실패, 접근 불가, 예산 때문에 미처리 상태를 구분한다.

출처 유지 여부는 채택률만으로 정하지 않는다. 드물지만 중요한 공지의 출처는 보호 목록에 둔다. 공급사의 공식 발표는 발표 내용의 원출처지만 효과·우월성의 독립 검증은 아니다.

## 4. 선별은 신뢰와 유용성을 분리한다

### 4.1 먼저 적용할 기준

- 원문 접근 수준과 실제 확인 범위를 표시한다.
- 수치·가격·날짜·인용에는 해당 근거 위치가 필요하다.
- 사실 주장과 의견·예측·적용 제안을 구분한다.
- 같은 보도자료·통신사·인터뷰를 재인용한 출처는 동일한 근거 계열로 표시한다.
- 근거가 부족한 고영향 이슈는 `긴급 확인 후보`가 될 수 있지만 `검증된 제작 소재`가 되지는 않는다.

### 4.2 통과 후보의 우선순위

브랜드 질문 관련성, 실질적 변화, 독자에게 주는 도움, 지금 활용 가능성, 시급성, 기존 발행물과의 중복을 각각 낮음/중간/높음과 한 줄 이유로 평가한다. 모델이 내놓은 자신감이나 임의의 100점 점수를 사실 정확도로 해석하지 않는다.

최종 목록은 동일 사건·공급사·주제의 과다 점유를 줄인다. 집중 브랜드에 우선권을 주되 브랜드마다 할당량을 억지로 채우지 않는다. 다음 주기에도 남겨야 할 항목과 지금 놓치면 늦는 항목을 구분한다.

초기 검토 한도는 전 브랜드 합계 5~8개다. 사용자 검토 시간이 짧으면 카드 수보다 카드의 길이와 상세 펼침을 먼저 조정한다. 미검토가 이틀 이상 쌓이면 반복 해설·새 원고 생성부터 줄이고, 공식 변경 수집과 중요한 정정 감지는 유지하는 것을 제안한다.

## 5. 중간 체크와 최종 체크의 계약

### 5.1 중간 체크: 소재와 방향 선택

카드 기본 내용은 한 줄 변화, 브랜드에 중요한 이유, 추천 관점, 근거 수준, 제가 추천하는 다음 행동이다. 상세에는 사실 3개 이내, 과거와의 차이, 반대 근거, 출처 위치, 확인할 질문을 둔다.

선택은 `제작`, `추가 조사`, `읽고 보관`, `나중에`, `제외`다. 이유는 선택 입력으로 `이미 앎 / 브랜드 안 맞음 / 근거 약함 / 지금 쓸 일 없음 / 관점 좋음` 정도를 제공한다. “나중에”와 미응답을 싫어요로 학습하지 않는다.

제작 선택은 `브랜드 + 사건 + 관점 + 선택한 brief 버전`을 고정한다. 브랜드를 바꿔도 원자료를 다시 요약할 필요는 없지만 새 브랜드의 기준으로 적합성을 다시 검토한다.

### 5.2 최종 체크: 주장과 표현 검증

- 원고의 핵심 사실이 실제 근거와 일치하는가.
- 발표·제한 제공·일반 제공, 제안·통과·시행을 구분했는가.
- 수치의 단위·비교 조건·적용 지역·확인 시점이 유지됐는가.
- 추론·의견이 사실처럼 쓰이지 않았는가.
- 반대 근거 또는 중요한 제한을 빼서 의미가 바뀌지 않았는가.
- 브랜드 보이스·독자·현재 질문에 맞는가.
- 경험·성과를 지어내지 않았고 공개 출처가 완성됐는가.

기계 검사는 누락·버전·형식을 확인하고, 의미 대조는 근거를 함께 읽는 별도 검토 단계에서 수행한다. 같은 모델의 자기평가만으로 검증 완료를 선언하지 않는다. 모델 간 동의도 독립적인 사실 근거가 아니다.

최종 확인은 `원고 버전 + 근거 버전 + 브랜드 기준 버전`에 귀속한다. 사실에 영향을 주는 근거 변경·원고 편집이 생기면 해당 확인을 stale로 표시하고 차이를 보여 준다. 철자 수정은 사실 검증과 구분하되 승인받은 정확한 원고 버전 기록은 유지한다. 발행 후 정정 신호는 수정 제안으로 올리고 외부 글을 조용히 덮어쓰지 않는다.

## 6. 실행 구조와 기존 코드 재사용

```text
공식 피드/API · Brave · YouTube · 선택한 기존 자료
  → Engine 수집 어댑터
  → 출처/버전 정리 · 중복/사건 묶기
  → 근거 추출 · 브랜드별 brief
  → Hub 중간 체크
  → 선택한 근거 packet · 기존 소재함/Studio
  → 원고와 근거 대조 · 최종 체크
  → 수동 발행 기록 또는 명시 선택한 업무 실험
```

역할은 수집·정규화·근거 추출·편집·검토로 나누되, 역할마다 장시간 에이전트를 하나씩 실행하지 않는다. 초기에는 결정론적 코드와 단계별 제한된 모델 호출로 구성한다.

| 자산 | 코드에서 확인한 것 | 적용 범위 |
| --- | --- | --- |
| 브랜드 기준 | `apps/hub/lib/brand-identity.js` | 독자·약속·주제·보이스·집중점 재사용 |
| Studio 저장 | `apps/engine/lib/content-workflow.ts` | request hash, 낙관적 버전 검사, 후보 적용·복원 계약 유지 |
| AI 후보 | `apps/engine/lib/content-transform.ts` | source snapshot, usage, unknown/unsaved 복구 패턴 참고 |
| worker | `apps/engine/lib/agent-worker.ts`, `packages/codex-worker/contracts.mjs`, migration 0033 | lease token·heartbeat·중복 요청 계약 참고 |
| 레퍼런스 packet | 09-20 레퍼런스→Studio 기획서 | 고정 출처 1~3개 전달 계약과 호환 필요. 아직 구현된 것으로 가정하지 않음 |

기존 agent_jobs는 Codex SDK 프로젝트 실행용이며 mode/runtime/context 제약이 있다. 일반 HTTP 수집·여러 모델 호출을 그대로 넣을 수 있는 범용 큐라고 가정하지 않는다. 리서치 실행은 작은 전용 stage runner로 제안하고, Codex 작업을 선택적으로 호출할 때만 기존 인증·큐를 사용한다. 실행 요약용 agent_runs를 모든 원문 저장소로 사용하지 않는다.

Hub는 읽기 repository와 검토 명령을 담당하고 Engine이 수집·모델 호출·영속 쓰기를 담당한다. 서버 간 secret, Hub write guard, workspace 검증을 유지한다. read 응답은 HTTP 200이어도 status:error를 처리한다.

운영 실행 위치는 자동화 활성화 전에 확인한다. 로컬 실행은 컴퓨터가 꺼진 동안 감지가 지연된다. 서버 실행은 환경·스케줄러·콜백 주소 설정과 실제 왕복 검증이 필요하다. 현재 배포가 실행 가능한 상태라고 가정하지 않는다.

## 7. 최소 데이터 구조 제안

아래는 신규 논리 테이블 5개 제안이다. 실제 migration과 UI 구현은 이 문서 범위가 아니다. 별도 벡터 DB나 지식 그래프는 첫 단계에서 추가하지 않는다.

| 단위 | 소유 정보 | 중복·버전 경계 |
| --- | --- | --- |
| research_sources | 출처 설정·주기·cursor·상태·저장 범위·브랜드 연결 | workspace + 정규화 source key |
| research_documents | 읽은 자료의 불변 버전, URL/외부 ID, 내용 hash, 확인 범위·시간·근거 위치 | workspace + source + external key + content hash + 추출 버전 |
| research_briefs | 사건 key, 브랜드, 관련 질문, facts/interpretations/counterevidence/action, 문서 버전 참조 | brief root + revision. 분석 결과는 새 revision으로 저장 |
| research_reviews | 중간·최종 선택, 선택자, 시각, 이유, 대상 revision, Studio ID 연결 | append-only 결정 기록. 새 결정은 이전 기록을 덮지 않음 |
| research_runs | 단계·요청 hash·상태·lease·시도·입출력 참조·비용 예약/실제 사용 | workspace + 단계 + 입력 fingerprint + 처리 버전 |

문서와 brief를 분리해 같은 자료를 여러 브랜드에서 참조한다. 하나의 brief 안에서 주장별로 문서 ID·문단/타임스탬프·확인 방법·한계를 매핑한다. 기계적 ID 연결은 사실 확인의 증거가 아니라 근거로 돌아갈 경로다.

원고의 근거는 선별 시점의 고정 snapshot을 사용한다. 수집기가 원자료 새 버전을 발견해도 원고 근거를 자동 교체하지 않는다. 변경 알림을 통해 새 근거 채택과 재검토를 선택한다.

수집 상태, 근거 수준, 편집 상태, 실행 상태는 별도 축이다. 예를 들어 수집 성공이어도 metadata_only일 수 있고, 좋은 소재여도 예산 대기로 분석이 끝나지 않았을 수 있다.

## 8. 중복 실행·실패·변경을 견디는 규칙

1. **전달은 재발생할 수 있다.** 동일 피드 항목·웹훅·스케줄의 재실행을 정상 상황으로 취급한다. source key와 content hash로 동일 입력 분석을 재사용한다. 의미 있는 URL query와 영상 ID는 보존한다.
2. **cursor는 저장 뒤에 움직인다.** 자료 저장과 후속 작업 등록이 성공한 뒤 관찰 cursor를 커밋한다. 실패한 페이지는 건너뛰지 않으며, 미완료 저장이 cursor 진전으로 영구 누락되지 않게 한다.
3. **오래된 worker는 쓰지 못한다.** claim/heartbeat/finish에는 lease token 또는 fencing version을 검사한다. lease 만료 후 돌아온 응답이 새 실행을 덮어쓰지 못한다.
4. **모델 결과 불명은 무료 재시도가 아니다.** 요청 ID·provider ID·stage checkpoint를 남긴다. 전송 후 timeout은 unknown으로 두고 결과 조회/복구를 우선한다. 멱등성을 제공하지 않는 provider에 blind retry하지 않는다. 비용은 확인 전까지 예약 상태로 유지한다.
5. **선택→소재 전달은 한 번만 효과를 낸다.** 승인 receipt, content item/variant, 전달 완료 기록을 같은 DB transaction으로 생성하는 계약을 새로 구현해야 한다. 현행 일반 소재 생성이 이미 원자적이라고 주장하지 않는다. 실패 후 같은 선택을 재시도해도 소재 하나만 생겨야 한다.
6. **부분 실패를 보인다.** 블로그 수집 실패가 유튜브 결과를 지우지 않는다. source별 최근 성공 시각·미처리 이유를 표시하고 장애를 “새 소식 없음”으로 바꾸지 않는다.
7. **변경 전파를 좁힌다.** 수정된 문서에 의존하는 주장·brief·원고만 재검토 대상으로 만든다. 모든 브랜드 원고를 재생성하지 않는다.
8. **원문은 신뢰할 수 없는 입력이다.** 수집 URL은 허용된 http(s)만 처리하며 private/loopback·redirect 우회·과대 응답을 차단한다. 문서 속 명령은 실행하지 않고 분석기의 외부 행동 권한을 제거한다.

연속 실패에는 source별 backoff와 재시도 한도를 둔다. 다른 출처의 진행을 막지 않되 실패 출처를 자동 삭제하지 않는다.

## 9. 비용과 처리 시간의 통제

### 9.1 단계별 계산량

| 단계 | 처리 | 초기 제한 제안 |
| --- | --- | --- |
| 발견·중복 | 일반 코드 | 새 문서 목록과 변경 여부. 모델 호출 없음 |
| 빠른 분류 | 규칙 + 필요한 경우 저비용 모델 | 문서별 짧은 메타, 작은 묶음으로 ID를 붙여 분류 |
| 근거 읽기 | 상위 후보의 필요한 원문 구간 | 하루 웹 문서 20개, 중요 예외는 예약 예산 안에서 |
| 의미·관점 | 공통 근거 + 짧은 브랜드 기준 | 검토 후보 5~8개 |
| 정밀 조사·초안 | 중간 체크에서 선택한 자료 | 하루 선택 소재 1~3개. 영상 직접 분석은 별도 한도 |

제한은 운영 초기의 기본값 제안이다. 긴 문서를 앞부분만 잘라 충분히 읽었다고 표시하지 않는다. 관련 절·표·조건을 추출하고 coverage를 기록한다. 중요한 제한을 확인할 수 없으면 추가 조사로 남긴다.

브랜드별 사실 요약은 공유하고 interpretation만 분기한다. 캐시는 입력 문서 버전, 브랜드 기준 버전, 질문, prompt/schema/model 버전에 묶는다. 모델을 바꿨다고 기존 모든 자료를 자동 재분석하지 않는다.

### 9.2 예산은 호출 전에 예약한다

월 비용 상한 B는 운영자 답변으로 결정한다. 활성화 전에 검색·텍스트·영상·실행 환경 비용의 포함 범위를 확정한다. 구독형 Codex의 사용량과 외부 API 청구액은 별도 지표로 기록하며 무료로 합치지 않는다.

동시에 시작하는 작업도 `실제 사용액 + 예약액 + 이번 호출 최대 추정액 ≤ B`를 만족해야 한다. workspace/청구 기간 단위 transaction lock으로 admission을 직렬화하고, token/output/영상 길이 상한으로 호출의 최대 추정 범위를 제한한다. 가격표 버전·통화·모델을 함께 남긴다. 한국 원화 한도라면 환율 기준과 여유분을 정한다.

입력 사용량·출력 사용량·영상 사용량·검색 호출·latency·재시도·실패·실제/추정/미확인 비용을 구분한다. 사용량 응답이 없으면 0으로 처리하지 않는다. 제공자가 보장하지 않는 비용 상한을 절대 보장으로 표현하지 않는다.

예산 압력이 생기면 신규 영상 분석과 폭넓은 탐색부터 줄이고 선택 소재 검증에 예산을 남긴다. 상한에서 신규 유료 요청을 멈추고 pending 이유를 보존한다. 저비용 모델로 바꿔 놓고 동일 검증 수준을 선언하지 않는다.

검색을 더 할지의 기준은 “이 결과가 제작/보류 판단을 바꿀 수 있는가”다. 최초 조사에 목표 질문과 종료 조건을 두고, 검색 두 차례에서 새 근거가 없으면 보류하거나 사용자가 선택한 심층 조사로 넘기는 것을 제안한다.

## 10. 유튜브·Brave의 현실적 경계

- 지정 채널: Atom/업로드 목록으로 시작하고 공개 callback을 운영할 수 있을 때 push를 연결한다. push는 업로드뿐 아니라 제목·설명 수정에도 발생한다. 일일 업로드 목록 대조로 누락을 보완하고 구독 갱신·실패를 관리한다.
- 개인 구독 목록: OAuth로 가져오되 구독 전체가 고비용 분석 대상이라는 뜻은 아니다. 초기에는 새 업로드의 메타데이터를 선별하고 집중 채널만 깊게 읽는다.
- 타인 영상 자막: 공식 captions.download는 영상 편집 권한을 요구한다. API 키만으로 모든 자막을 확보할 수 있다고 설계하지 않는다.
- 영상 분석: 확보 가능한 텍스트 → 필요 시 공개 영상 분석 순서. 프레임·음성이 필요한 데모/강연만 영상 처리하고 실제 입력 처리 기록·usage를 확인한다. 구간을 요청했다는 이유만으로 과금도 해당 구간에 한정됐다고 가정하지 않는다.
- 확인 상태: metadata_only / transcript_excerpt / transcript_full / video_analysis와 범위·한계를 보존한다. 자동 자막의 숫자·고유명사·직접 인용은 중요한 경우 별도 대조한다.
- Brave: Web/News로 발견하고 선택적 LLM Context를 사용한다. 반환 토큰과 URL 수를 제한할 수 있지만 snippet은 원문 전체가 아니다. 별도 Answers 재요약을 모든 결과에 중첩하지 않는다.
- 보관: Brave 검색 결과의 일부/전체 저장에는 해당 plan의 storage rights 확인이 필요하다. 허용 범위가 확인되기 전 Brave 유래 결과를 durable cache로 저장하는 경로는 활성화하지 않는다. 별도로 허용되는 publisher/RSS 수집은 분리해 운영할 수 있다. 제3자 원문 권리는 검색 API가 제공하지 않는다.
- 보존 정책: 출처별 허용 범위와 보존 기간에 따라 metadata·짧은 근거·본문을 구분한다. 삭제/갱신 의무가 있으면 파생 저장본도 추적한다. 선택 근거의 재열람 불가 상태도 기록하고 원문 전문 무기한 보관을 기본값으로 두지 않는다.

## 11. 품질을 실제로 측정하는 방법

첫 2주는 성과 보증 기간이 아니라 기준선 측정 기간이다.

| 지표 | 분모·정의 | 목적 |
| --- | --- | --- |
| 유용한 후보 비율 | 검토된 후보 중 제작/적용/읽고 보관을 선택한 수. 용도별 별도 집계 | 노이즈 조정 |
| 검토 부담 | 실제 중간 체크 시간, 미검토 잔량, 한 카드에 든 시간 | 읽기 부담 제한 |
| 채택당 비용 | 파일럿 전체 검색·분석 비용 / 실제 채택 소재 수 | 버린 자료 비용까지 포함. 채택 0이면 금액/건 계산 불가 |
| 핵심 주장 추적률 | 최종 원고 핵심 사실 중 근거 위치가 있는 수 | 연결 여부 측정. 진위 정확도와 별개 |
| 사실 오류 | 원문 대조에서 발견한 오류 건수/검토한 핵심 주장 수 | 의미·수치 왜곡 발견 |
| 중요 신호 누락 | 보호 출처 및 주간 표본에서 운영자가 중요하다고 판정한 항목 중 미노출 건수 | 확인 가능한 표본의 누락률. 전체 웹 recall이라고 부르지 않음 |
| 발견 지연 | 관찰 가능한 발표 시각부터 최초 발견까지 | 수집 주기 조정. 색인 지연과 구분 |
| 적용 가치 | 선택한 실험의 실행 여부·관찰 결과, 실제 발행 기록 | 소재 선택 이후 루프 확인 |

최소 주 1회 탈락 후보 표본을 살핀다. 낮은 채택률 때문에 특정 관점·새 출처를 영구 차단하지 않는다. 조회수만 최적화하거나 발행하지 않은 좋은 정보의 가치를 0으로 만들지 않는다.

모델/프롬프트 변경은 실제 자료의 고정 표본에서 기존 방식과 비교한다. 제목만 바뀐 업로드, 늦게 색인된 글, 같은 보도자료 5개, 반대 근거, 자막 없는 영상, 원문 정정, 비슷한 제품의 서로 다른 버전, 부분 장애, 중복 승인, 비용 응답 누락을 포함한다. 평가 자료는 실제 수집 자료 또는 로컬 전용 테스트 데이터 정책을 따른다.

## 12. 구현 순서 제안과 완료 기준

1. **설계 확정·수동 파일럿:** 브랜드·질문·출처·검토 시간·비용 상한을 정한다. 실제 자료로 brief→중간 체크→선택 소재→최종 체크를 3회 수행해 카드 효용과 누락을 본다. 이 단계는 자동화 구현을 요구하지 않는다.
2. **텍스트 반복 수집:** 공식 출처 + Brave 보완, 문서 버전·중복·출처 상태·실행/비용 기록, 하루 digest. 실패 후 재실행해도 자료·검토 목록이 중복되지 않고 실패가 보인다.
3. **선별→Studio 연결:** reference packet 경로의 실제 구현 여부를 확인하고 고정 근거 전달·중복 승인 방지·버전 확인을 구현한다. 선택 자료로 원고 3개를 저장→재열기→수정→최종 확인까지 완료한다.
4. **유튜브 확장:** 지정 채널 감지와 텍스트 분석부터 시작한다. 구독 OAuth·push·영상 분석은 실제 실행환경·한도와 함께 추가한다. 자막 없음과 수집 실패를 구분한다.
5. **주간 연결과 변경 추적:** 아카이브 연결, 가설 재검토, 근거 변경의 영향을 받는 원고 표시, 출처/질문 효용 개선. 앞 단계의 실제 반복 작업을 바탕으로 범위를 정한다.

기능·다중 파일 구현은 전용 codex worktree에서 수행한다. 앱 테스트·DB 왕복·장애 검증은 실제 변경 범위에 맞춰 별도 수행한다. 이 설계 작성에서 실행 기능·DB·자동화는 만들지 않는다.

## 13. 운영자에게 보낸 질문 5개

현재 답변 대기 중이다. 아래 미확정 항목을 AI가 브랜드 전략 또는 지출 승인으로 추정하지 않는다.

1. 먼저 적용할 브랜드 2~3개와 각 브랜드의 핵심 독자는 누구인가?
2. 콘텐츠 소재 / 업무·제품 적용 / 사업 기회 / 시야 확장·학습 중 원하는 우선순위는?
3. 중간 체크에 쓸 시간과 주기는? 예: 매일 10분 또는 주 3회 20분.
4. 우선 추적할 유튜브·블로그와 정치 이슈의 지역·주제 범위는?
5. 검색·LLM·영상 분석의 월 예산 상한은? 중요 소식 누락과 검토량 증가 중 더 피하고 싶은 것은?
