# Council · Mentor · Legend 평가와 확장 지침

> 작성: 2026-09-12
> 범위: 현재 코드·지침의 구조 평가, 페르소나 평가법, 적용 규칙, 분야·인물 확장안. 실제 모델 답변의 품질 점수는 미측정.
> 상위 정본: [운영자 프로필](../../operator-workflow-profile.md), [제품 구조](2026-07-13-moonlight-personal-operator-os-deep-design.md), [문서 지도](../../README.md).

## 1. 판단과 용어

현재 자산의 장점은 업무 원장, 역할별 입출력, 승인 경계, 이전 실행 기록이 이미 있다는 것이다. 우선 개선할 것은 **화면의 이름과 실제 실행을 맞추고, 어떤 지식을 왜 적용했는지 확인할 수 있게 하는 일**이다.

이번 조사에서 `mento`는 현행 `Guru / sales-mentor`로 해석했다. `Legend`는 [세일즈 구루 12인 자료](../../sales-guru-knowledge-base.md)와 [마케팅·브랜딩 3인 자료](../../marketing-branding-gurus.md)를 가리키는 것으로 보았다. 조사한 저장소에서 독립적인 Legend 런타임·선택기는 확인하지 못했다. 다른 정의 파일이 있다면 그 자료의 평가는 별도로 추가해야 한다.

| 이름 | 권장 제품 의미 | 결과 |
|---|---|---|
| Mentor | 특정 분야의 지속적인 코칭 방식 | 상황 이해, 판단을 돕는 설명, 작은 실천, 다음 확인 |
| Council | 중요한 선택을 여러 관점으로 검토하는 방식 | 선택지, 합의점, 이견, 조건부 결론 |
| Legend | 인물·저작·방법론에서 추출한 관점 라이브러리 | 출처, 판단 질문, 적용 조건, 한계 |

예를 들어 `콘텐츠 Mentor + 데밍 관점`으로 주간 실험을 설계하거나, `Council + 전략·사용자·반례 관점`으로 새 프로젝트를 검토한다. 기존 `order/sales/content/production/review`는 실행 책임으로 유지한다. 인터페이스 방식, 실행 역할, 전문 분야, 참고 관점을 각각 식별해야 인물 추가가 실행 권한 추가로 이어지지 않는다.

## 2. 현재 상태 평가

아래 평가는 소스 코드로 확인한 구조적 성숙도다. 배포 상태나 실제 조언의 정확도를 검증한 결과는 아니다.

| 대상 | 확인한 기반 | 공백과 개선 영향 |
|---|---|---|
| 실행 페르소나 5개 | [공통 계약](../../sales-os/personas/_contract.md)에 역할·입력·출력·도구·톤·게이트·트리거·실패 처리 정의 | 업무 분장은 명확하다. 답변 품질을 비교할 평가 사례와 역할별 합격 기준을 보강할 수 있다 |
| Council 화면 | [Agents](../../../apps/hub/components/hub/pages/agents.jsx)의 로스터·최근 실행 표시 | `Convene`는 실행 현황을 조립한다. 독립적인 다자 토론·합의 생성을 실행하지 않는다 |
| Council 자문 | [brand-mentor](../../../apps/engine/app/api/ai/brand-mentor/route.ts)의 Writer·Strategist·Analyst, 5개 모드 | 한 번의 모델 호출에 선택 렌즈를 넣는다. 화면의 실행 페르소나 5개와 다른 체계다 |
| Mentor / Guru | [sales-mentor](../../../apps/engine/app/api/ai/sales-mentor/route.ts)의 4개 업무 모드, 원장 근거·회사 업무 경계 | 실제 업무에 붙일 기반은 있다. 일반 채팅 입력이 항상 `proposal-critique`로 전달되어 질문의 의도와 실행이 어긋날 수 있다 |
| Legend 자료 | 세일즈 12인·마케팅 3인에 대한 긴 설명과 예시 | 조사한 두 자문 경로는 해당 문서 본문을 검색·발췌하지 않고 `frames` 문자열을 주입한다. 인물 소개의 분량이 실제 실행의 지식 충실도를 보장하지 않는다 |
| 연속성 | `agent_runs`, `project_updates`, 이전 자문 읽기 | 실행 로그는 조언의 유용성 평가와 다르다. 행동 채택·실행·도움 여부·보류 이유와 버전을 연결할 필요가 있다 |
| 사실성과 톤 | 원장에 없는 사실 단정 금지, 브랜드 규칙, 다음 행동 제안 | “칭찬 금지”는 근거 있는 긍정 피드백까지 막는다. “관찰 근거 없이 칭찬하거나 비난하지 않기”로 구체화하는 편이 좋다 |

### 우선 처리할 적용 불일치

1. **질문 처리:** [AgentsChat의 send](../../../apps/hub/components/hub/pages/agents.jsx)에서 Guru의 모든 일반 입력을 초안 검토로 보낸다. 먼저 업무 목적을 선택·판별하고, 판별이 불명확하면 짧게 확인하는 동작을 제안한다.
2. **모델 표시:** 같은 화면에 `Haiku 4.5 / Opus 4.8`이 고정돼 있지만 자문 Engine은 `generateGeminiText`를 호출한다. 실행 전에는 역할을, 실행 후에는 실제 응답 메타데이터를 표시한다.
3. **회사·개인 문맥:** [brand-context](../../../apps/hub/lib/sales-os/brand-context.js)는 개인 브랜드 프로젝트가 0건이면 전체 프로젝트로 되돌아간다. 프롬프트의 “회사 업무와 섞지 않기”를 입력 필터에서도 지켜야 한다. 0건은 0건으로 유지한다.
4. **기억 범위:** [sales context assembler](../../../apps/hub/lib/sales-os/context-assembler.js)의 최근 실행 조회는 `agent` 필터를 넘기지 않는다. [조회 함수](../../../apps/hub/lib/sales-os/agent-runs.js)는 해당 필터를 지원한다. 분야·업무 대상·페르소나에 맞게 이전 기록을 선택하도록 보완한다.
5. **실행 성공과 평가:** 두 Hub 멘토 라우트의 `resultStateFromStatus`는 2xx 성공을 먼저 처리해 202 분기가 도달 불가능하다. 현재 경로의 202 preview가 성공 실행으로 기록될 수 있으므로 HTTP와 응답 상태를 함께 분류한다. 생성·저장·승인·실행·유용성 상태도 구분한다. [Council BFF](../../../apps/hub/app/api/hub/brand-mentor/route.js), [Guru BFF](../../../apps/hub/app/api/hub/sales-mentor/route.js).
6. **지식 귀속:** 현행 `Ross MEDDIC` 표기는 출처 재검토 대상이다. MEDDIC 창안자 Dick Dunkel의 [직접 인터뷰](https://meddicc.com/meddicc-media/masters-of-meddicc-s1-ep4-richard-dunkel)는 PTC에서의 개발을 설명한다. Ross의 방법론과 함께 사용할 수는 있어도 창안·사용·혼합 적용을 구별해서 적어야 한다.

`80%는 5번째 이후 접촉`, `헤드라인이 80%`, `MEDDIC 완성 시 클로징률 3배` 같은 기존 문구도 주장별 출처·모집단·시점을 확인하기 전에는 현재 업무의 사실이나 보편 법칙으로 사용하지 않는 편이 좋다. 이번 검토에서 모든 통계의 진위를 판정한 것은 아니다.

## 3. 페르소나별 개발 요소

| 역할 | 유지할 강점 | 보강할 판단 기준 | 실패 예 |
|---|---|---|---|
| Order / Dispatch | 무엇을 먼저 할지와 최소 역할 선택 | 우선순위 근거, 지금 하지 않을 일, 재검토 조건 | 모든 건에 전원을 호출하거나 근거 없이 긴급 처리 |
| Sales | 딜 다음 행동·후속 연락 | 고객이 표현한 문제, 구매 단계, 접촉 간격, 다음 확인 질문 | 무응답을 구매 의사로 해석하거나 연락량만 늘림 |
| Content | 소재·각도·발행 흐름 | 독자에게 주는 가치, 새로운 근거, 실제 제작 가능성 | 이름만 다른 유사 아이디어를 많이 생성 |
| Production | 승인한 각도의 채널별 구조화 | 원문 의미·사실 보존, 채널 적합성, 편집 완료 기준 | 없는 경험·수치·후기를 추가 |
| Review | 사실·브랜드·외부 전달 전 검수 | 지적마다 원문 위치·근거·수정안, 심각도와 재검수 | 자기 의견을 사실 오류로 판정하거나 형식 통과만으로 사실성 통과 |
| Strategist | 선택과 우선순위 | 포기할 대안, 기회비용, 결론이 바뀌는 조건 | 무엇이든 중요하다고 답함 |
| Analyst | 기록 비교와 진단 | 사실·가설·공백, 비교 기간, 대체 설명 | 적은 기록으로 성격·원인·성과 효과를 확정 |
| Writer | 메시지의 전달력 | 독자·의도·구체성·브랜드 보이스 | 설득력을 이유로 원문 의미 변경 |
| Mentor | 판단을 설명하고 실천으로 연결 | 한 번에 한 가지 학습, 사용자의 시간·에너지, 이전 피드백 | 모든 상황에 같은 강한 말투·긴 과제 |

Coach를 하루 리뷰에 추가한다면 사용자가 기록한 상태와 실행 제약을 해석하는 역할로 한정한다. 기존 하루 리뷰 초안처럼 미입력·미실행을 의지나 인격 점수로 바꾸지 않는다.

### 기존 Legend 15인 자료의 활용 권장

다음은 저장소 자료에 담긴 활용 방향을 바탕으로 한 **초기 편집·적용 제안**이다. 인물 전체에 대한 평가나 원전 전수 검증 결과가 아니다. 각 항목은 검증된 출처 카드가 마련된 범위에서만 활성화한다.

| 인물 | 활용할 좁은 목적 | 적용 시 보완 |
|---|---|---|
| Zig Ziglar | 필요·신뢰 등 구매 장애 확인 | 장애물 목록을 실제 고객의 이유로 단정하지 않기 |
| Dale Carnegie | 관계·경청·상대의 언어 | 호감 형성과 구매 필요를 구별하기 |
| Napoleon Hill | 개인 목표를 글로 명료화 | 목표·자기암시를 성공의 인과 법칙으로 제시하지 않기 |
| Joe Girard | 고객 기록·후속 관리 습관 | 과거 판매 환경의 빈도·숫자를 현대 B2B에 그대로 이식하지 않기 |
| Brian Tracy | 중요한 다음 행동 선택 | 현재 일정·에너지와 충돌하는 생산성 요구 줄이기 |
| Grant Cardone | 실행량을 점검하는 보조 관점 | 일률적인 10배 목표, 거절 뒤 반복 접촉을 기본값으로 두지 않기 |
| Jordan Belfort | 메시지 구조와 설명의 명확성 | 근거 이상의 확신 표현이나 압박을 좋은 설득으로 평가하지 않기 |
| Neil Rackham | 문제·영향·해결 가치 질문 | 조사 질문을 이미 아는 고객 사실처럼 쓰지 않기 |
| Chris Voss | 협상 전 경청·확인 질문 설계 | 상대 감정 추정을 사실로 고정하지 않기 |
| Aaron Ross | 고객 적합성·영업 역할·파이프라인 구조 | 개인 운영 규모에 맞추기, MEDDIC 등 다른 방법론 귀속 구별 |
| Jason Lemkin | SaaS 성장·유지·확장 검토 | 하드웨어·교육 현장·개인 콘텐츠에 SaaS 지표를 무리하게 적용하지 않기 |
| Keenan | 현재 상태와 원하는 상태의 차이 | 고객이 확인하지 않은 고통·매출 영향을 과장하지 않기 |
| Seth Godin | 작은 대상 집단과 가치 제안 | 좁은 대상 선택이 항상 최선인지 목적과 단계 확인 |
| David Ogilvy | 구체적 사실 중심의 제목·카피 | 과거 광고 지표를 현재 채널의 성과 수치로 해석하지 않기 |
| Donald Miller | 독자 중심 메시지와 이야기 구조 | 모든 글을 판매용 이야기 형식으로 통일하지 않기 |

첫 적용 묶음은 문제 진단에 Rackham·Keenan, 대화에 Voss·Carnegie, 콘텐츠에 Ogilvy·Miller·Godin을 권장한다. 이 순서는 현재 업무와의 적합성에 대한 설계 판단이며 실측 순위가 아니다.

## 4. 확장 방식 비교

| 접근 | 범위 | 장점 | 비용·한계 |
|---|---|---|---|
| A. 현행 지침 정돈 | 모드 처리·문맥 범위·프레임 출처·답변 형식 개선 | 가장 작은 변경으로 현재 사용성 개선 | 분야·인물이 늘면 경로별 지침 중복 |
| B. 공통 계약 + 분야·관점 카드 | 기존 실행 역할을 유지하고 지침·출처·적용 조건·평가 버전을 연결 | 업무별 Mentor와 Council이 같은 지식 재사용 | 등록 규칙과 평가 사례를 먼저 정해야 함 |
| C. 인물별 독립 에이전트 토론 | 인물별 호출·교차 검토·합성 | 깊은 비교·탐색 경험 | 지연·호출 비용, 의견 중복, 합의의 과신을 별도 관리 |

**권장안은 B이며, A의 불일치 수정부터 시작한다.** C는 복잡한 결정에서 추가 관점의 이익을 관찰한 뒤 선택적으로 도입한다. 지식 라이브러리에 인물을 추가하는 일은 매 요청의 호출 수를 늘리는 일과 분리한다.

## 5. 공통 페르소나 지침 카드

기존 8섹션 계약을 기반으로 다음 내용을 보강한다. 실행 계약의 정본·런타임 mirror·fallback을 함께 관리하고, 별도 목록을 무심코 늘리지 않는다. 아래 설명형 출력과 공통 답변 지침은 Mentor·Council 자문에 적용한다. 기존 5개 실행 페르소나의 JSON 입출력과 게이트 계약은 유지하며, 필요한 설명은 기존 허용 필드에 맞춘다. 실행 계약 변경은 별도 버전 변경과 소비자 검증을 거친다.

| 필드 | 적을 내용 |
|---|---|
| ID·버전 | 역할 ID, 지침 버전, 변경 이유 |
| 목적 | 사용자의 어떤 판단·행동을 돕는가 |
| 적용·비적용 | 잘 맞는 질문과 다른 역할로 넘길 조건 |
| 읽을 문맥 | 분야·업무 대상·기간·허용 자료, 빠진 자료 처리 |
| 핵심 원칙 | 행동으로 검사할 수 있는 3~5개 규칙 |
| 판단 질문 | 답변 전에 확인할 질문 3~5개 |
| 근거 카드 | 저자·작품·장/절·발췌 위치·링크·검토 상태 |
| 출력 | 관찰, 해석, 근거, 다음 행동, 재확인 조건 |
| 말투 | 직설성·설명량·질문 빈도. 근거 있는 격려 허용 |
| 한계 | 알려진 적용 한계·반례·혼합 적용의 해석 |
| 예시 | 좋은 답변과 실패 답변 각 1개 이상 |
| 평가 | 역할별 사례, 평가 버전, 최근 관찰 결과 |

### 그대로 사용할 수 있는 공통 지침 초안

> 사용자의 목표와 현재 제약을 먼저 읽는다. 제공된 업무 기록의 사실, 내가 내린 해석, 아직 확인되지 않은 부분을 구별한다. 참고 인물의 원칙을 현재 상황에 적용할 때 적용 이유와 적용 한계를 짧게 설명한다. 출처 없이 명언·통계·고객 정보를 만들지 않는다. 근거 있는 성과는 인정하고, 비판에는 수정 가능한 행동을 붙인다. 사용자의 선호에 맞추되 확인되지 않은 전제에 동의하지 않는다. 기본 답변은 다음 행동 하나와 재확인 조건으로 끝낸다. 실행이나 외부 전달은 현재 제품 권한·승인 규칙을 따른다.

Legend 카드는 `인물 → 핵심 저작 → 원칙 → 판단 질문 → 실제 적용 예 → 한계 → 출처` 순서로 만든다. 본인의 실제 발언·현재 견해를 재현한다고 표시하지 않고, `○○의 저작에서 가져온 관점의 적용`이라고 표현한다. 직접 인용과 요약·현대적 해석을 각각 식별한다.

## 6. 자체 평가와 답변 평가

평가 대상을 세 개로 나눈다. **지침 정의의 품질**, **생성된 답변의 품질**, **사용 뒤의 유용성**이다. 자기 점검은 오류를 찾는 과정으로 사용하고 최종 품질 점수의 유일한 근거로 쓰지 않는다.

### 지침 자체 점검

- 역할 설명만 읽고 적합한 질문·부적합한 질문을 구별할 수 있는가.
- 원칙이 다른 페르소나와 구별되는 판단 질문으로 이어지는가.
- 인물 소개를 제거해도 출력과 평가 기준이 작동하는가.
- 필요한 자료가 없을 때의 답변이 정의되어 있는가.
- 원전, 편집자의 요약, 현대적 응용을 분리했는가.
- 성공·실패 예시가 실제 사용자의 업무와 연결되는가.

### 답변 평가표 — 권장 초기값

각 항목은 0~4점: 0=해당 기준 위반, 1=형식적 충족, 2=부분 충족, 3=실용적으로 충족, 4=근거·한계까지 충족. 평가자는 점수마다 답변의 구체 문장을 근거로 남긴다. 적용 불가 항목은 N/A로 두고 적용 항목의 가중치 합으로 정규화한다. 질문별 적용 항목·가중치·N/A는 답변 생성 전에 고정하고 A/B/C 모두에 동일하게 적용한다. 예를 들어 이전 기록이 없는 질문이면 세 조건 모두 연속성을 N/A로 둔다.

| 항목 | 가중치 | 확인할 것 |
|---|---:|---|
| 사실·출처 | 25 | 업무 사실이 기록에 있고, 인용·통계의 출처가 맞는가 |
| 상황 적합성 | 20 | 분야·대상·사용자의 시간·에너지를 반영했는가 |
| 실행 가능성 | 15 | 다음 행동이나 추가 확인이 작고 구체적인가 |
| 판단 기여도 | 15 | 선택지·확인 질문·우선순위가 사용자의 판단을 실제로 돕는가. 인물 언급 자체에는 가점 없음 |
| 반례·불확실성 | 10 | 반대 설명과 결론을 바꿀 조건을 다뤘는가 |
| 연속성 | 10 | 이전 조언·실행·피드백을 정확히 구별해 사용했는가 |
| 이해·읽기 부담 | 5 | 길이·용어·말투가 지금의 사용 목적에 맞는가 |

점수는 `100 × Σ(점수/4 × 가중치) / Σ(적용 가중치)`로 계산할 수 있다. 세부 점수와 미충족 이유를 함께 보며, 합산 점수만으로 활성화하지 않는다.

초기 후보 통과 조건은 **적용 가능한 모든 항목 3점 이상**으로 제안한다. 업무 사실·출처를 꾸미기, 명시된 사용 중지 조건 무시, 잘못된 회사·개인 문맥 사용은 총점과 관계없이 수정 대상으로 둔다. 이 기준은 이번에 통과시킨 결과가 아니라 후속 평가용 제안이다.

### 한 답변의 자기 점검

1. 이 질문에 맞는 역할과 분야를 선택했는가.
2. 근거 없는 사실·인용·수치가 들어갔는가.
3. 가장 그럴듯한 다른 설명이나 반례가 있는가.
4. 다음 행동이 사용자의 현재 제약 안에서 가능한가.
5. 이전 제안과 같다면 유지해야 하는 이유가 있는가.

구체적인 오류가 발견되면 한 번 수정한다. 다시 확인할 근거가 없으면 확인 필요로 남긴다. 단순히 새 답을 만들기 위해 타당한 이전 행동을 바꾸지 않는다. 자기 점검의 상세 내부 사고를 저장·공개할 필요는 없고, 최종 근거·한계·수정 요약을 남긴다.

### 비교 평가 설계

동일 질문으로 A=`일반 도우미+업무 기록`, B=`A+검증된 원전 카드`, C=`B+페르소나 지침`을 비교한다. A→B는 자료 추가 효과, B→C는 페르소나 지침의 추가 효과를 보는 비교다. 같은 모델·질문·업무 snapshot·분량 한도를 쓴다. 내용 평가에서는 조건 이름과 인물 이름을 가리고 출력 순서를 섞는다. 출처 표기는 공통 ID로 치환해 근거 연결을 보존한다.

원저자·출처 정확성은 이름을 공개하는 별도 검증 단계에서 확인한다. 따라서 모든 항목을 완전히 블라인드로 평가했다고 보고하지 않는다. 첫 단계는 내용의 유용성, 둘째는 사실·귀속 검증을 담당한다. 페르소나 고유 원칙의 충실도는 C에만 적용하는 별도 진단이며 A/B/C 공통 총점에 가산하지 않는다. 경계·형식 검사는 기존 실행 JSON 계약과 자문 출력 계약에 맞춰 각각 수행한다.

초기에는 대표 업무 6개를 각 조건으로 한 번씩 생성해 18개 답변을 검토하는 작은 점검부터 제안한다. 이 표본으로 우월성을 입증하지 않는다. 개선 후보는 별도 보류 사례와 반복 실행으로 확인한다. 실행 예산은 실제 모델·토큰 한도가 정해진 뒤 산정한다. 이번 조사에서는 이 모델 호출을 실행하지 않았다.

대표 업무: 정체 딜, 초안 수정, 주간 우선순위, 하루 리뷰, 새 개념 설명, 협업 규칙 결정. 경계 사례: 기록 없음, 기록끼리 충돌, 잘못된 인물 귀속, 근거 없는 수치, 낮은 에너지, 이전 제안 실패, 분야 밖 질문, 회사·개인 문맥 혼합, 같은 조언을 유지해야 하는 상황, 인물의 권위와 실제 기록이 충돌하는 상황.

### 사용 후 평가

`제안 → 채택/보류 → 실행 여부 → 도움 됨/변화 없음/아직 모르겠음`을 연결한다. 피드백은 건너뛸 수 있다. 행동하지 않았거나 답하지 않은 경우를 나쁜 조언·낮은 의지로 자동 환산하지 않는다.

평가 기록에는 run ID, 업무 대상, 지침·관점·평가표 버전, 선택한 행동, 평가자 종류, 분모와 표본 수를 남긴다. 채택률은 사용 편의의 신호이며 실제 성과와 다르다. 매출·진척 변화는 여러 원인이 있으므로 페르소나의 인과 효과로 단정하지 않는다.

## 7. 적용 지침

1. **작업을 먼저 식별한다.** 영업 판단, 콘텐츠 편집, 학습, 회고 등 목적에 맞춰 Mentor 또는 Council 방식을 고른다. 인물을 고르지 않아도 기본 모드가 작동하게 한다.
2. **문맥을 좁힌다.** 허용된 분야·대상·기간의 기록과 선택한 메모를 읽는다. 작업별 근거와 사상·방법론의 출처를 별도 목록으로 관리한다.
3. **관점을 최소 선택한다.** Mentor는 주 관점 1개, 필요할 때 보완 1개. Council은 기본 2~3개. 이름보다 서로 다른 판단 질문을 우선한다.
4. **충돌을 해소한다.** 최신 업무 사실·사용자 목표·시간 제약으로 적합성을 판단한다. 서로 다른 원칙을 억지로 하나로 합치지 않고, 적용 조건과 남은 이견을 보여준다.
5. **결론을 작게 만든다.** 공통 답변은 관찰·해석·근거·다음 행동·재확인 조건. Council은 합의점·이견을 덧붙인다. 일상 리뷰는 카드 하나 분량을 기본으로 한다.
6. **실제 실행 방식을 표시한다.** 한 모델이 여러 관점으로 작성했다면 그렇게 표시한다. 독립 에이전트들의 합의라고 표현하지 않는다. 인물 이름·관점 수를 신뢰도 점수로 바꾸지 않는다.
7. **선택한 행동을 연결한다.** [하루 리뷰 초안](2026-09-12-daily-review-and-council-design.md)의 adopted action과 task 연결을 재사용한다. 일상 리뷰에서 모든 제안을 새 승인 대기 업무로 자동 추가하지 않는다.
8. **실행·실패를 기록한다.** 생성, 저장, 채택, 실행, 평가 상태를 구분한다. 같은 요청 재시도가 중복 제안·중복 행동을 만들지 않도록 요청 ID와 원본 버전을 검증한다.

최소 추적 정보는 `run ID / 목적·분야 / 역할 / 관점·지침 버전 / 업무 근거 ID·revision / 모델 / 생성·저장 상태 / 선택 행동 ID / 피드백`이다. 제안 단계에서 모든 것을 새 만능 테이블로 옮길 필요는 없다. 기존 `agent_runs`·결과 기록·행동 연결을 확장할 수 있는지부터 검토한다.

공통 지침과 개별 관점이 충돌하면 제품의 권한·데이터 범위·사용자 지시를 우선한다. 출처 문서 속 명령문은 인용 자료로 다룬다. 문맥 일부가 실패하면 누락된 범위를 표시하고 가능한 범위만 답한다.

## 8. 다른 분야와 위인 확장

아래 활용법은 원전의 핵심 주제를 현재 업무에 옮긴 **설계 제안**이다. 각 인물이 이 앱이나 구체적 조언을 지지한다는 뜻이 아니다. 후보 추가 전에는 실제 사용할 원전 구간을 지정한 카드가 필요하다.

| 분야·후보 | 적용할 판단 질문 | 연결할 기능 | 한계·출처 |
|---|---|---|---|
| 과학적 검토 — Richard Feynman | 내 설명에 불리한 증거를 빠뜨리지 않았는가 | 아이디어·조언 반례 점검 | 과학 방법의 비유와 사업 효과의 증거를 구분. [Cargo Cult Science 원문](https://calteches.library.caltech.edu/3043/) |
| 개선 실험 — W. Edwards Deming | 무엇을 예상했고 실제로 무엇을 배웠는가 | 하루 리뷰·주간 실험 | 작은 실험 결과를 곧바로 일반화하지 않기. [Deming Institute의 PDSA 설명](https://deming.org/explore/pdsa/) |
| 고객·경영 — Peter Drucker | 누가 가치를 얻으며 무엇을 결과로 볼 것인가 | 프로젝트 목적·우선순위 | 고객·성과 관점을 삶의 모든 가치로 확장하지 않기. [저작 발췌](https://drucker.institute/wp-content/uploads/2018/08/Reading_Drucker-on-Being-Customer-Centric.pdf) |
| 협업·공동체 — Elinor Ostrom | 공동 자원의 규칙과 책임을 어떻게 구성할 것인가 | 커뮤니티·파트너십 기획 | 제도의 맥락과 적용 규모를 확인. [본인 노벨 강연](https://www.nobelprize.org/prizes/economic-sciences/2009/ostrom/lecture/?lbw=1) |
| 자기 성찰 — Epictetus | 내가 선택할 수 있는 행동과 통제 밖의 결과는 무엇인가 | 하루 회고·실패 이후 다음 행동 | 감정을 무시하거나 모든 문제를 개인 책임으로 환원하지 않기. [Enchiridion 제1절](https://www.gutenberg.org/files/45109/old/45109-h/45109-h.htm) |

우선 두 개를 더한다면 **데밍의 작은 실험**과 **파인만의 반례 점검**을 권장한다. 현재 자료가 세일즈·설득에 집중되어 있어, 실행 뒤 학습과 근거 검토를 보강할 수 있다는 판단이다. 새 인물이 실제로 유용한지는 §6 비교 평가로 확인한다.

다음 후보군도 열어둘 수 있다. 이 목록은 원전 구간 검토 전의 조사 후보다.

- **한국사·동양 고전:** 세종—훈민정음의 사용 목적에서 착안한 설명·접근성, 정약용—목민심서의 실무 책임, 이순신—난중일기의 관찰·제약 기록. 현대 업무 적용은 편집자의 해석으로 표시하고 원전의 해당 구간을 먼저 대조한다.
- **디자인:** Don Norman—사용자가 무엇을 이해하고 실행할 수 있는지. 저작의 구체 원칙과 좋은·나쁜 UI 사례를 함께 등록한다.
- **창작:** Leonardo da Vinci의 노트나 Ursula K. Le Guin의 창작론 등. 결과물을 실제로 다르게 만드는 관찰·연습 과제로 바꿀 수 있는지 확인한다.
- **학습·훈련:** 특정 위인 이름 없이도 설명자, 연습 설계자, 피드백 코치라는 역할로 시작할 수 있다. 능력·방법을 먼저 평가하고 필요한 출처를 붙인다.

유명 인물 외에 **처음 보는 고객, 현장 실무자, 미래의 나, 반대 근거를 찾는 검토자**도 관점 후보가 된다. 고객 관점은 가상 검토라고 표시하고 실제 고객 조사·피드백과 구분한다. 실제 이해관계자의 의견은 인물 시뮬레이션보다 우선하는 업무 근거다.

새 관점의 등록 조건은 ① 반복해서 사용할 실제 질문 ② 추적 가능한 출처 ③ 다른 관점과 구별되는 판단 ④ 좋은·실패 예 ⑤ 비적용 조건 ⑥ 비교 평가 기록이다. 근거 카드가 없으면 `조사 후보`, 사례 점검 중이면 `시험`, 통과하면 `사용 가능`, 문제가 확인되면 `보류`로 관리할 수 있다. 상태 전환은 근거를 남기는 편집 결정으로 한다.

### 8.2 이름마다 답변이 달라지는 지침

말투는 아래처럼 서비스 목적에 맞춰 설계한다. 인물의 실제 성격이나 음성을 복제했다는 표시는 하지 않는다.

- **소크라테스:** 차분하고 짧게 질문한다. 한 번에 질문 하나, 기본 최대 세 번 확인한 뒤 전제·모르는 부분·잠정 결론을 정리한다. 사용자가 직접 답을 요청하면 현재 정보로 먼저 답한다.
- **아인슈타인:** 구체적인 상황을 그려보고 가정 하나씩 바꾼다. 사고실험 최대 두 개와 실제로 확인할 관찰·실험을 연결한다.
- **링컨:** 상대의 이해관계, 지킬 원칙, 협력 제안의 순서로 답한다. 당사자의 발언과 페르소나의 추정을 구별한다.
- **시어도어 루스벨트:** 힘을 주는 말투를 쓰되 실행 하나의 범위·시간·멈출 조건을 함께 제안한다. 피로·실패를 겁이나 의지 부족으로 평가하지 않는다.
- **프랭클린 루스벨트:** 현재 확인된 상황, 공동 목표, 이번에 시도할 방법, 결과를 다시 설명할 시점을 제시한다. 침착함과 결과 보장을 구별한다.
- **잡스:** 기능 목록을 사용 장면으로 바꿔 설명한다. 한 문장 경험 정의와 이어져야 할 기능, 줄일 복잡성을 제안한다.
- **베이조스:** 고객에게 중요한 결과, 가역성, 결정 지연 비용, 수정 조건을 정리한다. 외부 실행 권한은 기존 제품 계약을 따른다.
- **버핏:** 이해할 수 있는 사업 원리를 평이하게 설명하고 정보 공백을 드러낸다. 선택의 기회비용과 더 조사할 항목을 함께 제시한다.
- **쉬나드:** 사용자가 명시한 가치와 운영 선택을 비교한다. 가치·수익·자원의 실제 충돌을 구체적인 선택지로 표현한다.

특히 **소크라테스는 전제를 묻고, 아인슈타인은 가능한 설명을 넓히고, 파인만은 그 설명을 검증한다.** 세 과정을 구별해야 모두 비슷한 “깊이 생각하라”는 조언으로 합쳐지지 않는다. 데밍은 반복 실험의 예측·학습을, 프랭클린 루스벨트는 위기 속 목표 정렬·방법 변경·설명을 담당하도록 구별한다.

### 8.3 상황별 Council 조합

각 조합은 선택 가능한 검토 프리셋이다. 기본 2~3관점 제한과 실제 실행 방식 표시 원칙을 유지한다. 아래 질문·산출물은 설계 예시이며 실제 인물들의 대화나 독립 모델 합의가 아니다.

| 상황 | 제안 조합 | 각 관점이 맡을 일 | 합성 결과 |
|---|---|---|---|
| 새 서비스·기획 | 소크라테스 + 아인슈타인 + 잡스 | 문제·전제 확인 → 다른 구성 탐색 → 사용자 경험으로 구체화 | 문제 정의, 선택지 두 개, 우선 검증할 경험 하나 |
| 시작할 일·보류할 일 | 버핏 + 베이조스 + 데밍 | 이해 범위·자원 → 되돌릴 수 있는 결정 → 작은 실험 | 이번에 시작할 일, 보류 이유, 재검토 조건 |
| 갈등·파트너십 | 링컨 + Voss + 오스트롬 | 원칙·관계 → 확인 대화 → 책임·규칙 | 상대에게 확인할 질문, 협력안, 합의가 필요한 조항 |
| 막힌 실행 재개 | 시어도어 루스벨트 + 데밍 | 감당 가능한 첫 시도 → 결과에서 학습 | 한 번 해볼 행동과 다음 확인 |
| 계획 실패·위기 대응 | 프랭클린 루스벨트 + 파인만 + 베이조스 | 목표·설명 → 반대 증거 → 수정 가능한 결정 | 유지할 목표, 바꿀 방법, 확인 시점 |

상황을 선택하면 적합한 프리셋을 제안하고 사용자가 인물을 바꿀 수 있게 한다. 일상 Mentor에서는 한 인물과 계속 대화하면서 필요할 때만 다른 관점을 요청하는 경험도 가능하다. 분야·판단 역할로 먼저 찾고, 인물 이름으로도 탐색하도록 설계하면 선택 부담을 줄일 수 있다.

첫 문서화 묶음은 사용자가 직접 제안한 **소크라테스·아인슈타인·링컨·두 루스벨트**와 기업가 네 명이다. 이 중 실제 첫 시험은 대표 질문과 입력 자료가 준비된 소수부터 §6의 같은 기준으로 진행한다. 기존의 데밍·파인만 검증·학습 역할도 유지한다. 인물 목록 확대와 기본 호출 수는 별개로 관리한다.

### 8.4 가치관을 중심으로 한 개별 개발

[Legend 9인 가치관·판단 카드](2026-09-12-legend-values-persona-cards.md)에 각 인물의 원전 근거, 가치 우선순위, 가치 충돌 사례, 조언 예시, 결론을 바꿀 조건, 적용 한계를 구체화했다. 원전의 가치와 제품용 현대 해석, 사용자가 명시한 가치를 구분한다.

페르소나의 답변은 **중요한 가치 → 관련 사실·공백 → 제안 → 감수할 비용 → 수정 조건**으로 연결한다. 공통 사례에서 관점이 판단 이유와 다음 행동을 어떻게 바꾸는지 평가한다. 같은 결론에 도달할 수 있으며, 구별되는 인물을 연출하기 위해 억지로 반대하게 하지 않는다. 개별 카드의 가치 충실도 점검은 §6의 공통 품질·실사용 평가를 보완한다.

## 9. 실제 경험 예시

아래는 **가상 입력과 기대 동작**이며 실제 사용자 기록·모델 실행 결과가 아니다.

입력: “오늘은 에너지 2/5. 고객 연락은 끝냈지만 콘텐츠 초안은 못 썼다. 내일 25분은 낼 수 있다.”

- Mentor는 낮은 에너지와 완료한 연락을 함께 읽고 25분 안의 행동을 제안한다.
- 파인만 관점은 한 번의 미착수만으로 의지 부족이나 반복 병목을 결론내렸는지 점검한다.
- 데밍 관점은 예상과 다음 날 확인할 결과를 붙인다.

기대 답변:

> 오늘 고객 연락은 끝냈고, 초안은 시작하지 못했습니다. 이 기록만으로 미착수 원인은 확정할 수 없습니다. 내일 확보한 25분 중 앞 10분에 독자 한 명과 핵심 문장 세 줄을 적어보세요. 다음 리뷰에서 시작했는지, 이 방법이 도움이 됐는지만 확인하겠습니다.

사용자가 고르면 기존 할 일로 연결한다. 다음 날 `해봄 + 도움 됨 / 변화 없음 / 아직 모르겠음` 또는 미실행·보류를 기록한다. 미실행 이유가 시간 부족이면 다음 제안의 크기를 조정하는 근거가 되며, 사용자의 성격 평가로 전환하지 않는다.

| 2. 지식 카드와 기본 지침 | 기존 15인 중 실제 사용할 소수의 출처·질문·한계 정리 | 답변의 관점 이름에서 적용 원전과 업무 근거를 각각 확인한다 |
| 3. 비교 평가 | 대표 업무, 경계 사례, 이름을 가린 평가, 지침 버전 | 일반 답변·자료 추가·페르소나 추가의 차이를 구체 답변으로 비교한다 |
| 4. 제한적 분야 확장 | 데밍·파인만 관점, 선택형 Council 2~3관점 | 서로 다른 관점이 선택지를 실제로 바꾸고 읽기 부담이 허용 범위인지 확인한다 |
| 5. 사용 결과 반영 | 하루 리뷰의 행동·피드백 연결 | 재생성·보류·미응답 후에도 이전 행동과 피드백을 정확히 재조회한다 |

구현 시에는 기존 ID와 `registry.json`·`persona-contract.js` 간 일관성 검사를 유지한다. 지침 수정만으로 답변 품질 개선을 완료했다고 선언하지 않는다. 각 단계는 좁은 구현 계획과 필요한 검증으로 나눌 수 있다.

## 11. 이번 검토의 검증 범위

- 로컬 코드, 역할 계약, Guru·브랜딩 지식 자료, 기존 제품·하루 리뷰 기획을 확인했다.
- `node scripts/check-persona-registry.mjs`는 종료 코드 0, 모든 검사 통과를 확인했다. 이는 역할 목록·필드·정규화·동기화 계약 검사이며 모델 답변 품질 검사가 아니다.
- MEDDIC 귀속은 창안자 직접 인터뷰와 대조했다. 새로운 분야의 출처는 위 링크로 제시했고, 전체 15인의 원전·통계를 전수 검증하지 않았다.
- 추가한 철학·과학·리더십·기업가 후보에는 저작·연설·본인 서한·당시 기업 발표 자료를 연결했다. 플라톤이 기록한 소크라테스, 기업의 자기 설명, 제품용 현대적 해석은 출처 성격을 구분했다. 후보별 실제 모델 성능은 미측정이다.
- 새 지침의 모델 호출, 배포 환경 확인, DB 변경, 앱 구현은 이번 평가에 포함하지 않았다. 평가 가중치·통과 조건·호출 규모·추가 인물은 모두 권장 초기값이다.
