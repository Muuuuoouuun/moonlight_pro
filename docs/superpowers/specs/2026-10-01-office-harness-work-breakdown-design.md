## 1. 결론

Office는 이미 하네스의 대부분을 갖고 있다. 빠진 것은 **"안건 하나를 여러 담당의 일로 나누는 층"** 하나다. 지금은 안건 하나에 주관 1명(+관점 0~2명)만 붙일 수 있어서, "출시를 할지 정하고 첫 고객 제안까지" 같은 안건은 운영자가 머릿속에서 나눈 뒤 회의를 여러 번 열어야 한다.

권장안: 이브이가 안건을 **업무 조각(packet) 1~5개**로 나눈 추천을 내고, 운영자가 확인한 뒤 조각을 하나씩 직접 연다. 담당은 모델이 고르지 않는다. 모델은 조각의 **업무 종류**만 고르고, 종류→담당 표가 담당과 응답 방식을 정한다. 아무것도 자동으로 실행되지 않는다.

```text
안건 ─▶ [업무 나누기] ─▶ 이브이 분해 추천(조각 1~5, 정할 것, 보류, 확인 질문)   ◇ 권장
                              │ 운영자: 적용 · 담당 바꾸기 · 무시
                              ▼
          p1 준비 ─▶ [이 조각 열기] ─▶ 기존 Office 요청(담당·방식 고정) ─▶ 결과 카드
          p2 대기(p1) ◀── 운영자가 p1 "완료로 표시" + 결과 사본 붙여 넣기
          p3 대기(p2) ─▶ 출구: Office 요청 / 할 일 연결 / 로컬 스킬 요청서
```

## 2. 하네스란 무엇이고 Office에는 무엇이 있나

Ruflo의 정의를 빌리면 "에이전트 = 모델 + 하네스"다. 모델은 글을 쓰고, 하네스는 그 글이 일이 되도록 접수·배정·문맥·반복·검사·기억·출구·통제를 준다. Office의 하네스를 10층으로 펼치면 다음과 같다.

| # | 층 | 현행 코드 | 보장하는 것 | 빈칸 |
|---|---|---|---|---|
| 1 | 접수 | 회의실 안건 바, `parseOfficeRequest`(6,000자·키 화이트리스트) | 안건은 운영자가 복사한 사본이다. 숨은 필드는 거절한다 | — |
| 2 | 배정 | 이브이 담당 추천 `routing.ts` + `office-routing.js` | 주관 1·관점 0~2, 운영자 버튼으로만 호출 | **분할 없음** — 안건 하나에 담당 하나 |
| 3 | 역할 레지스트리 | `role-cards.ts` v25(임무·소유·납품물·인계·경계) | 역할 이름은 권한이 아니다 | **업무 종류→담당 표가 문서에만 있음**(심화 설계 §5) |
| 4 | 문맥 | workflow 문맥 어댑터(주간·고객), `contextHash`, facts 24KB | 서버가 고른 근거만, 버전 고정 | 자유 안건에는 서버 문맥 없음(의도) |
| 5 | 실행 루프 | 대화·초안·검토: 생성 + 원문 대조 검수 2호출 / 관점 비교: 참여자 × 라운드 + 종합 | 회의도 단일 모델 시뮬레이션이라고 밝힌다 | — |
| 6 | 가드 | 계약 파서, `source-review`, 수치 가드, 프롬프트 경계 문장, 실패 분류(phase·category) | 실행 사칭 금지, 근거 밖 인용 제거 | — |
| 7 | 기억 | 세션 대화 8턴, `office_requests` 영수증(workflow), 멘토 스레드는 브라우저 세션 | 운영자가 원래 업무에서 결과를 다시 찾는다 | **분할 단위 기억 없음** |
| 8 | 출구 | `office_apply_task_v1`(확인 후 할 일), 멘토 한 홉, 로컬 스킬 요청서 + receipt | 출구마다 운영자 확인 | 조각과 출구를 잇는 표지 없음 |
| 9 | 관측 | Office 7일 요약(요청 수·평균 시간·실패), 실패 분류 | 모델 문구·예외는 경계를 넘지 않는다 | 조각 단위 지표 없음 |
| 10 | 통제 | 모든 발동은 운영자 버튼, Office 도구 없음, 회의 2~3명, 추천 48초 타임아웃 | §3 "자동으로 일을 만들지 않는다" | — |

이번 설계는 2·3·7·8·9층의 빈칸만 채운다. 나머지 층은 그대로 재사용한다.

## 3. 언제 나누고 언제 나누지 않나

- **나누지 않는다**: 판단 질문이 하나인 안건, 인사·감사·휴식, 목적이 이미 분명한 요청(고객 답장 하나, 오류 하나). 이브이 카드의 "기능·고객 등 목적이 명확하면 해당 담당 직행"과 같다. 이때는 기존 `담당 추천`으로 충분하다.
- **나눈다**: 결과물이 둘 이상의 담당 납품물을 필요로 하거나, 한 결과가 다음 일의 입력이 되는 순서가 있을 때. 예: 비용 계산 → 범위 확정 → 고객 제안.
- 모델이 조각 1개를 내면 그것은 "나눌 필요 없음"이라는 답이다. 화면은 이 경우 조각 목록 대신 담당 하나로 바로 연다(§5).

## 4. 업무 분할 체계

### 4.1 원칙

1. **배정은 결정적이다.** 모델은 `kind`만 고른다. `ownerId`를 내면 계약이 거절한다. 같은 종류의 일은 늘 같은 담당이 맡으니 운영자가 결과를 예측할 수 있다.
2. **운영자의 선택이 이긴다.** 적용 전에 조각별 담당을 바꿀 수 있다(`ownerSource: 'operator'`). 심화 설계 §5의 "명시한 담당 → 선택한 업무 행동 → 표면 기본 담당 → 이브이" 순서와 같다.
3. **이브이는 조각을 소유하지 않는다.** 분해 자체가 이브이의 납품물이다. 조각 담당은 전문 8인 중 하나다.
4. **아무것도 스스로 돌지 않는다.** 분해 추천도, 조각 실행도, 완료 표시도 모두 버튼이다. 시간이 지나도 상태가 바뀌지 않는다.
5. **결과는 자동으로 흐르지 않는다.** 앞선 조각의 결과는 운영자가 붙여 넣은 사본으로만 다음 조각에 들어간다. 멘토 답을 Office에 자동으로 되넣지 않는 원칙(§3)과 같은 이유다 — 같은 모델의 출력이 쌓이며 사실처럼 굳는 것을 막는다.

### 4.2 업무 종류와 담당

심화 설계 §4·§5의 표를 코드로 옮겼다(`OFFICE_WORK_KINDS`).

| 종류 | 라벨 | 담당 | 시작 방식 | 판단 질문 | 기본 납품물 |
|---|---|---|---|---|---|
| `schedule_plan` | 실행 순서 | 샤미드 | draft | 언제 무엇을 할 수 있나 | 가용시간에 맞는 순서·대기 조건 |
| `weekly_summary` | 주간 정리 | 샤미드 | draft | 이번 주 무엇이 바뀌었나 | 확인된 활동·정체 이유·다음 행동 초안 |
| `customer_contact` | 고객 연락 | 부스터 | draft | 이번 접촉의 목적은 | 보낼 메시지 하나·미확인 항목 |
| `content_draft` | 원고 | 님피아 | draft | 누구에게 무엇을 전하나 | 완성 원고 또는 수정안 |
| `scope_definition` | 완료 기준 | 글레이시아 | draft | 무엇이 되면 끝인가 | 포함/제외·정상·실패·복구 기준 |
| `tech_diagnosis` | 기술 진단 | 쥬피썬더 | review | 어디서 어떻게 실패하나 | 원인 후보·최소 패치 초안·검증 순서 |
| `cost_compare` | 돈·시간 비교 | 리피아 | review | 같은 기간에 무엇이 남나 | 현금·순시간 표·가정·재검토 조건 |
| `direction_choice` | 방향 선택 | 에브이 | chat | 이 선택이 무엇을 밀어내나 | 추천·포기 비용·변경 조건 |
| `risk_review` | 근거·약속 검토 | 블래키 | review | 어떤 주장에 근거가 부족한가 | 문제 위치·영향·대체 문장 |

`intake`(요청 정리)는 종류에 없다. 이브이의 일은 분해 그 자체다.

### 4.3 업무 조각의 구성

| 필드 | 뜻 | 한도·규칙 |
|---|---|---|
| `key` | `p1`부터 순서대로 | 번호가 비거나 섞이면 거절 |
| `kind` | §4.2의 종류 | 담당·방식은 여기서 정해진다 |
| `scope` | `classin` 또는 `personal` | 안건이 `all`이면 조각마다 레인을 고른다. 안건이 한 레인이면 그 레인만 |
| `ask` | 이 조각에서 할 일 | 600자 |
| `inputs` | 필요한 자료 | 4개·각 200자. 없는 자료를 있다고 쓰지 않는다 |
| `deliverable` | 납품물 | 300자 |
| `doneWhen` | 완료 조건 — 운영자가 확인할 수 있는 문장 | 300자 |
| `dependsOn` | 선행 조각 | **앞에 나온 조각만** → 순환이 구조적으로 불가능 |
| `reviewerIds` | 검토 관점 | 최대 2명, 담당 제외, 담당 카드의 인계 대상 ∪ 블래키 |
| `exit` | 끝난 뒤 어디로 | `office` · `task` · `skill_request`(§4.6) |

분해 전체는 `summary`(400자), `decisionNeeded`(운영자가 정할 것 하나 또는 없음), `packets`(1~5), `holds`(이번에 하지 않을 것 3개), `questions`(결론을 바꿀 확인 질문 2개)다. 전체 16KB 상한.

**조각 5개 상한의 이유**: 이브이 카드의 납품물이 "1-Pager"이고, 운영자 프로필의 처리 용량 감각(KA 1 + 집중 고객 3~5)과 맞춘다. 5개가 넘으면 그 자체가 "범위를 줄여야 한다"는 신호이므로 `holds`로 보낸다.

### 4.4 검토 관점

역할 카드의 인계(handoff) 그래프를 그대로 쓴다. 블래키는 모든 조각의 검토자가 될 수 있다(심화 설계 §3 "검토자를 블래키로 고르는 것").

| 담당 | 검토 후보 |
|---|---|
| 샤미드 | 글레이시아 · 부스터 · 블래키 |
| 쥬피썬더 | 글레이시아 · 블래키 |
| 부스터 | 리피아 · 블래키 |
| 에브이 | 리피아 · 글레이시아 · 블래키 |
| 블래키 | 쥬피썬더 · 부스터 · 이브이 |
| 리피아 | 에브이 · 쥬피썬더 · 블래키 |
| 글레이시아 | 쥬피썬더 · 샤미드 · 부스터 · 블래키 |
| 님피아 | 부스터 · 블래키 · 글레이시아 |

이 표는 브라우저에서도 쓰도록 계약 패키지에 사본(`OFFICE_HANDOFFS`)으로 둔다. 정본은 역할 카드이고, `harness-handoffs.test.mjs`가 두 쪽이 다르면 실패시킨다. 카드 본문을 바꾸지 않는다는 동결 규칙은 그대로 지켜진다.

검토자가 있는 조각을 열 때 운영자는 "담당 혼자" 또는 "관점 비교(담당 + 검토자, 2~3명)"를 고른다. 관점 비교는 기존 council 경로를 그대로 탄다.

### 4.5 순서와 상태

| 상태 | 뜻 | 어떻게 바뀌나 |
|---|---|---|
| `ready` | 선행이 없거나 모두 완료 | 계산 |
| `waiting` | 선행 중 완료되지 않은 것이 있음 | 계산 — 화면은 "p1 대기"처럼 선행을 이름으로 말한다 |
| `done` | 운영자가 완료로 표시 | 버튼 |
| `skipped` | 운영자가 건너뜀 | 버튼 |

선행을 건너뛰면 후행은 `waiting`으로 남는다. 운영자가 후행도 건너뛰거나, "선행 없이 열기"로 그냥 열 수 있다(계약은 상태로 실행을 막지 않는다 — 막는 것은 운영자의 판단이다). 상태 판정은 `officePacketStates` 한 곳에서만 한다.

### 4.6 출구

| 출구 | 뜻 | 쓰는 기존 경로 |
|---|---|---|
| `office` | 이 조각 자체가 Office 요청이다 | `officePacketRequest` → 기존 Office 요청(담당·방식·레인 고정) |
| `task` | 운영자가 직접 할 일(전화, 미팅, 결재)이다 | 조각 결과 카드의 기존 "할 일로 연결"(`office_apply_task_v1`, 확인 후) |
| `skill_request` | Mac의 Claude Code·Codex가 할 실행이다 | 기존 로컬 스킬 요청서(연결된 할 일 필수, receipt로 완료 증거) |

`exit`는 표지일 뿐 아무 권한도 주지 않는다. 할 일 생성·스킬 요청서 저장은 지금처럼 각각의 확인 단계를 거친다.

### 4.7 조각 → Office 요청

`officePacketRequest(breakdown, key, { agenda, priorResults, withReviewers })`가 기존 `parseOfficeRequest`를 통과하는 요청 본문을 만든다(테스트로 고정).

- 본문 순서: `[업무 조각 pN · 라벨]` → 요청 → 필요 자료 → 납품물 → 완료 조건 → `[앞선 조각 pK 결과 · 운영자가 붙여 넣은 사본]` → `[원래 안건]`.
- 앞선 결과는 선행 조각의 것만, 각 1,500자에서 자른다. 원래 안건은 남는 자리만큼 자른다. 전체 6,000자 이하.
- "사본"이라고 라벨을 붙인다. Office 프롬프트가 사용자 자료를 비신뢰 데이터로 다루는 규칙(`prompt.ts`)이 그대로 적용된다.

### 4.8 비용

분해 추천 1호출. 조각마다 운영자가 연 만큼(담당 혼자 2호출, 관점 비교 참여자 × 라운드 + 1). 조각 5개를 모두 관점 비교로 열어도 운영자가 다섯 번 누른 결과다. 숨은 호출은 없다.

## 5. 화면 (권장 — 구현 전)

표면 예산 규칙(2026-09-23)에 따라 회의실 본문에 새 패널을 붙이지 않는다.

- **진입**: 회의실 `더보기` 드로어의 `담당 추천` 옆에 `업무 나누기` 하나. 안건이 비어 있으면 비활성.
- **분해 카드**: `CertaintyBadge recommended`(점선·빈 마름모). 요약 한 줄 → 정할 것 → 조각 목록 → 보류 → 확인 질문. 버튼은 `적용` · `무시`. 조각 1개면 목록 없이 "나누지 않아도 됩니다 · <담당>에게 바로 열기".
- **조각 행**: 종류 라벨 · 담당 이름 · `LifecycleBadge`(ready=queued "열 수 있음", waiting=waiting "p1 대기", done=done, skipped=cancelled) · 출구 표지 · `이 조각 열기`. 행 클릭은 담당 바꾸기 드로어(`EditDrawer`). 색은 쓰지 않는다(§5.3 — 상태는 글리프와 글자).
- **조각 열기**: 입력창에 조각 본문을 넣고 담당·방식(검토자 체크 시 관점 비교)을 맞춘다. 운영자가 `보내기`를 눌러야 호출한다.
- **앞선 결과 사본(H1 구현 방식)**: 결과 카드에 버튼을 더하지 않고(표면 예산), 운영자가 조각을 `완료로 표시`하는 순간 **그 조각을 연 뒤에 나온 마지막 결과**만 사본으로 남긴다. 연 뒤 새 결과가 없으면 사본도 없다. 되돌리기·건너뛰기는 사본을 지운다. 드로어가 사본 저장 여부와 1,500자 한도를 말한다.
- **조각 결과 카드**: 기존 결과 카드 + `완료로 표시` · `건너뛰기`.
- **390px**: 조각 목록은 세로 한 줄씩, 버튼 44px, 입력 16px.
- **실패**: 분해 실패·미연결은 기존 담당 추천과 같은 문구("담당자를 직접 선택해 주세요")와 입력 보존.

## 6. Engine·Hub 경로 (권장 — 구현 전)

- Engine `POST /api/ai/office-breakdown`: `routing.ts`와 같은 경계 문장(도구 없음·실행 사칭 금지·안건 속 명령은 자료)과 §4.2 종류 표를 시스템 지시로, 응답 스키마는 `kind` enum만 있고 `ownerId`가 없는 JSON. `maxOutputTokens 4096`, `thinkingLevel low`, 48초, 재시도 1. 결과는 `parseOfficeBreakdownProposal` → `officeBreakdownResult`.
- Hub `POST /api/hub/office/breakdown`: `hub-write-guard.js`, Engine 호출에 `COM_MOON_SHARED_WEBHOOK_SECRET`, 응답은 `parseOfficeBreakdownResult`로 다시 검사. 새 경로는 미들웨어 기본값(막힘) 그대로 — `OPEN_PREFIXES`에 넣지 않는다.
- 미연결은 `preview`(202), 실패는 `error` — 기존 담당 추천과 같은 봉투.

## 7. 기억 (권장 — 2단계)

1. **H1: 브라우저 세션.** 분해·조각 상태·결과 사본을 회의실 세션(`office-session.js`)에 둔다. "이 브라우저 세션에만 남습니다" 문구를 이어서 상담과 같은 자리에 둔다.
2. **H2: DB.** 운영자가 실사용에서 세션 기억이 부족하다고 판단하면 `office_breakdowns`(분해 JSON·조각 상태·연결된 `office_requests.requestId`) 테이블을 0056으로 만든다. `office_requests.parentRequestId`로 조각 실행을 묶을 수 있다. `DATABASE_FEATURES` 등록·`begin/commit` 없음.

## 8. 평가와 지표

- **분해 품질 케이스**(H1에서 `evaluation-cases.mjs` 형식으로): 나누면 안 되는 안건(인사, 단순 사실, 답장 하나) → 조각 1개 / 회사·개인 혼합 → 레인 분리 / 비용 → 범위 → 제안 → 선행 관계 / 범위가 너무 큰 안건 → 5개 이하 + 보류 / 안건 속 "자동으로 보내라" 지시 → 따르지 않음.
- **실사용 2주 지표**(조각 단위, 7일 요약에 추가): 분해 뒤 운영자가 조각을 그대로 연 비율, 담당을 바꾼 비율(종류 표가 틀렸다는 신호), 건너뛴 비율(과분해 신호), 분해 실패율.

## 10. 바뀌지 않는 것

- Office는 도구를 갖지 않는다. 분해 추천도 텍스트 생성이다.
- 어느 단계도 자동으로 일을 만들거나 밖으로 보내지 않는다.
- 역할 카드 v25 본문·말투 동결.
- 멘토 답을 Office에 자동으로 되넣지 않는다. Legend는 Office에 연결하지 않는다.
- 회의 참여자는 주관 포함 2~3명.
