## 1. 원칙

1. **카드는 입구, 글은 주 읽기, 원문은 보존.** 한 줄 카드(검수된 요약)와 카드별 Moonlight 글(재구성 글)이 읽기의 주 경로다. 그 뒤의 바탕 문서 원문은 앱 안에서 글자 그대로 보존·열람되는 보조 읽기다. 요약·글이 원문을 없애지 않고, 원문이 검수된 글처럼 보이지도 않는다.
2. **정직한 출처 표시.** 원문에는 원전 대조가 끝나지 않은 인용·수치·사례가 남아 있다. 숨기지 않고 "원전 대조 일부 · 인용·수치는 확인 전"을 함께 보인다.
3. **추천은 저장된 사실 위에서만.** 넓은 `new/active/dormant` 구분이나 추측으로 구체 기법을 고르지 않는다. 근거가 된 사실을 운영자의 말로 함께 보인다.
4. **추천은 읽을거리.** 추천이 뜨는 것만으로는 모델 호출·업무 생성·알림·발송이 일어나지 않는다. 원문 열람과 질문은 운영자가 누를 때만.

- `scripts/build-guidance-source-library.mjs`가 다섯 문서를 줄 단위로 잘라 `packages/guru-guidance/source-library.generated.js`(항목 101개)를 만든다. CRLF를 LF로 맞춰 OS와 무관하게 같은 결과를 내고, 모든 줄이 정확히 한 항목에 들어간다(잃는 글자 없음). 문서가 바뀌면 `source-library.test.mjs`의 재생성 비교가 실패한다 — 원문 문서가 정본이다. 재생성: `npm run guidance:sources`, 확인: `npm run check:guidance-sources`.
- Hub 원문 리더(`guidance-source-reader.jsx`, 안전한 마크다운 렌더 `source-markdown.jsx`)는 필요할 때만 데이터를 불러온다(dynamic import). 머리 표시는 `참고 문서 원문 · 글자 그대로`, 출처 줄(`원문 그대로 · 문서 제목 · 줄 범위 · 글자 수`), 원전 대조 상태 표시(기준은 점검 문서의 제목), 목차, 절 접기·펴기, 카드의 출처 절로 초점 이동을 제공한다. 저장소 파일 경로는 화면에 보이지 않는다(09-25 내부 읽기 글 결정). `<h1>`·`<h2>`를 만들지 않는다(페이지당 `<h2>` 하나).
- 멘토 서가: 카드 본문을 누르면 Moonlight 글(`GuidanceDetail`)이 열린다. 원문은 주간 Legend 카드와 아틀라스 상세의 `참고 문서 원문`(ghost, 보조 행동)으로 연다. 카드가 없는 인물도 인물별 탐색에 `원문만 · 검수 카드 없음`으로 나오고 아틀라스 검색이 함께 거른다. 열람은 요청·알림·업무를 만들지 않는다.

### 2.2 AI에 넘기는 원문 (결정 ⑥)

- 운영자가 **카드를 골라** 질문하면(영업 멘토 `open-question`·브랜드 멘토 `open-question`) Engine 프롬프트에 그 카드 인물의 **장 전체 원문**과 **카드가 가리키는 절 제목**을 붙인다(`packages/guru-guidance/source-prompt.js`). 2026-09-25 기준 가장 긴 장이 5,590자라 상한 6,000자 안에 모두 들어간다. 장이 상한을 넘으면 카드의 절만 보내고, 그래도 넘으면 줄 경계에서 자르고 자른 분량을 적는다.
- 같은 블록의 가드: 원문은 참고 문서이며 원전(책·강연)이 아니다 / 인용문·수치·성과 주장·사례 문구를 답변에 옮기거나 사실처럼 말하지 않는다 / 압박식 설득·반복 접촉은 원문에 있어도 권하지 않는다 / 원문은 운영자의 기록 사실이 아니다 / 카드의 응용 범위(`source.note`).
- 모드 기본 카드(카드 없이 `deal-review` 등)는 지금처럼 짧은 프레임만 쓴다. 운영자가 고른 카드만 원문을 가져온다. Legend 주간 카드는 조언을 만들지 않으므로 원문을 붙이지 않는다.
- `source-prompt.js`는 서버 전용이다(원문 전체 데이터를 불러온다). Hub 클라이언트는 import하지 않는다.

### 2.3 Office 원문 전달

- `다른 관점으로 검토`·`이어서 상담`이 멘토에게 보내던 Office 결과는 본문 1,100자·근거와 이견 각 3개×150자·다음 행동 220자로 잘렸다. 이제 본문·주관 추천·근거와 이견 전체·다음 행동을 **그대로** 보낸다. 상한은 25,000자(Office 계약상 결과 필드 최대 23,000자 + 머리말)로 클라이언트·Hub·Engine 두 레인이 같다. 넘치면 오래된 후속 대화부터 빼고, 그래도 넘치면 가장 긴 필드를 자르며 `[원문 N자 중 M자 전달]` 표시와 드로어의 `원문 일부 전달` 배지를 남긴다. 후속 대화 기록은 4턴·질문 1,200자·답 4,000자까지(이전 200/360자).
- 이브이 담당 추천: 한글 안건 6,000자 계약이 12,000바이트 제한에 막혀(약 3,900자 초과 시 413) 있었다. Hub·Engine 바이트 상한을 계약에 맞췄다.
- 회사 레인(영업 멘토)도 개인 레인처럼 Office 출처(요청 ID·실행 ID)를 검증·기록·반환한다. **Hub와 Engine을 함께 배포해야 한다** — 이전 Engine은 출처를 돌려주지 않아 "Office 출처가 일치하지 않습니다"가 뜬다.

### 2.4 Legend 단일 원천

- 5벌(Engine 16·Hub 16·persona-chat 9·Hub 렌즈 11·주간 3)로 갈라져 Hub 툴팁과 모델이 받는 문구가 16장 중 10장에서 달랐다. `packages/guru-guidance/legend-library.ts` 하나로 모았다(모델이 실제로 받던 Engine 문구가 기준, `version`·`status`·원문 위치 `originRefs`). Engine `legend-cards.ts`와 Hub `council-legends.js`는 이 파일에서 읽는다.

## 3. 시스템에 녹은 추천 (결정 ⑦)

### 3.1 규칙 — 저장된 사실 → 원문 기법

순수 함수 `apps/hub/lib/sales-os/guru-recommendations.js`. 레코드(리드·딜·계정)당 추천은 하나이며 위가 이긴다(운영자 프로필 §4 임시 우선순위: 기한 넘긴 고객 약속 → 오늘 → 결정에 가까운 반응 → 정리).

| 규칙 | 근거 사실(모두 저장된 값) | 원문 기법(카드) | 원문 위치 | 쓰지 않는 것 |
|---|---|---|---|---|
| `quote-date-passed` | 딜 단계 견적·최종미팅 + 운영자가 정한 다음 연락일이 지남 + 그 뒤 연락 기록 없음 | MEDDIC 결정 과정 (`sales-meddic`) | 세일즈 플레이북 Aaron Ross 장 "기법 4: Qualification — MEDDIC" | "무응답"이라고 쓰지 않음(운영자 자신의 날짜), Cardone 10X·Ross 9-Touch 같은 반복 접촉 |
| `contact-due-today` | 다음 연락일이 오늘 | Hill 목적 설정 (`sales-hill-purpose`) | Napoleon Hill 장 | 시각화 루틴 등 효과 주장 |
| `positive-no-date` | 마지막 연락 반응이 긍정 + 날짜 정한 다음 단계 없음(30일 이내) | Voss 실행 조건 (`sales-voss-feasibility`) | Chris Voss 장 "Calibrated Questions" | "That's right → 클로징", Assumptive Close |
| `concern-open` | 마지막 연락 반응이 우려 + 다음 연락 미정(30일 이내) | Carnegie 경청 (`sales-carnegie-listen`) | Dale Carnegie 장 | 우려의 내용 추정·인용, Cardone 반박 스크립트 |
| `after-contract` | 딜 단계 클로징 · 리드 Customer · 계약 계정 | Girard 계약 후 관계 (`sales-girard-after-sale`) | Joe Girard 장 Step 4 | 65%·7:1 같은 수치, 현금 소개 보상 |
| `new-uncontacted` | 추적 시작 뒤 등록된 신규 리드(30일 이내) + 연락 기록 없음 | Ross 맞는 고객 (`sales-ross-fit`) | Aaron Ross 장 ICP | 전환율 수치 |

- 단계를 몰라 `potential`로 떨어진 딜은 단계 사실로 쓰지 않는다. 활동을 읽어 온 창(45일)보다 오래된 날짜는 "그 뒤 기록 없음"을 증명할 수 없어 고르지 않는다. 자동 기록(`deal`·`ai`·`update`)은 연락이 아니다(넛지 엔진과 같은 목록).
- **억제:** 최근 반응 두 번이 연속 무응답이거나 30일 안의 거절이면 지금 할 것(act)을 추천하지 않는다 — 원문에 남는 것이 압박 기법뿐이다. 기약 없음·종료·숨김 레코드도 제외. 연락 기록을 못 읽으면 연락에 관한 사실을 판정하지 않는다(단계만으로 확인되는 계약 후 관계는 예외).
- 레인: 공용 판정 `lib/sales-os/advice-scope.js`(09-25 고객 상세 판정을 옮김 — 범위·유형·브랜드가 같은 레인일 때만, 어긋나면 막음). `이 관점으로 질문`은 ClassIn으로 확인된 기록에만 열리고, 추천의 근거 사실을 그대로 질문 드로어에 싣는다(`ref` = 레코드 id). 개인·막힌 레코드는 원문 열람만.

### 3.2 위치

| 표면 | 모양 | 데이터 |
|---|---|---|
| 고객 상세 `도움 받기` | 이 고객의 추천이 있으면 순환 카드 대신 추천 카드, 없으면 기존 순환 카드. 접힌 요약줄에 `기록 기반 추천 있음` | `GET /api/hub/guru-recommendations` |
| 거래 상세 | 추천 카드. 없으면 사실만(`N일째 기록 변화가 없습니다`) — 이전의 "고객 저항 반론 점검을 추천"(정체를 반론으로 단정)은 뺐다 | 같음 |
| 오늘 | 집중 고객 카드 아래 `기록 기반 추천` 최대 3개(act만). 오늘 할 일 다음의 시간대 관점 한 줄 팁(09-25 집중 서가 스펙)과 별개 | 같음 |
| 홈 | 신호 상세 카드 안(그 신호의 딜·고객 추천) + 분류 큐 아래 목록 최대 3개 | 같음 |
| Office 결과 카드 | `안건과 맞는 원문 기법 · …` 접힌 줄(최대 2개). 근거는 운영자가 쓴 안건의 낱말(`lib/sales-os/agenda-guidance.js`) — "문제"·"어려움" 같은 넓은 말은 연결하지 않는다 | 모델 호출·기록 조회 없음 |

- 시간대로 도는 Guru 관점은 오늘에 **한 줄 팁 하나**(09-25 집중 서가 스펙)뿐이고 순환 카드는 두지 않는다. 홈에는 순환 카드·팁 모두 없다. 사실 근거 추천만 추가로 허용한다(`guru-guidance-card.test.mjs`·`guidance-inline-tip.test.mjs`가 고정).
- 추천 카드의 행동: `이 글 읽기`(서가 `?card=<id>`의 Moonlight 글 — 맥락 레일·한 줄 팁과 같은 딥링크) · `참고 원문`(보조, 제자리에서 원문 리더) · `이 관점으로 질문`(ClassIn으로 확인된 기록만). 다섯 표면 모두 같은 카드를 쓴다.
- 읽기 봉투는 허브 계약을 따른다: 읽기 실패는 `status:"error"`로 보이고 빈 목록으로 위장하지 않는다. 목록 표면은 추천이 없거나 `preview`면 아무것도 그리지 않는다(첫 화면에 빈 칸을 늘리지 않음). 한 화면 안의 여러 표면은 60초 동안 같은 결과를 나눠 쓴다.

## 4. Legend 범위 (결정 ⑧)

- Legend는 주간 카드로만 산다. 멘토 위젯·코칭 화면의 렌즈 칩에서 Legend 인물(잡스·베이조스·쉬나드·카네기·힐)을 뺐고, 대화 렌즈는 Guru 방법론(보스·오길비·고딘·랙햄·골드랫)만 남겼다. Hub `GURU_LENS_MAP`과 Engine `GURU_LENSES`의 키가 같다는 것을 테스트가 고정한다 — 다르면 고른 렌즈가 조용히 버려진다(이전 카네기·힐). Hub 라우트는 Engine이 모르는 렌즈를 넘기지도, 적용된 것처럼 기록하지도 않는다.
- 랙햄 렌즈의 "상황 → 문제 → 시사점 → 해결가치" 고정 순서를 09-24 출처 점검대로 "네 가지 질문 유형"으로 고쳤다.
- 브랜드 자문 탭(Council)의 Legend 트라이어드는 09-24 결정 ⑤(브랜드 Council은 별개 유지)에 속해 그대로 두었다. §7 "dissent → Legend 트라이어드"는 채택하지 않았다.

## 5. 함께 고친 결함

- **Guru가 엉뚱한 거래를 참조:** 오늘 화면 ✦ Guru가 고객 이름을 조회 키로 써서 이름이 겹치는 다른 거래를 끌어왔다. 이제 ClassIn으로 확인된 기록에만 뜨고 정확한 id만 넘긴다. 컨텍스트 조립은 id로만 거래를 찾고, 거래에 `lead_id`가 없을 때 연락처를 고르는 폴백도 "이름에 거래명이 든 리드"에서 "같은 회사의 리드"로 바꿨다(자동 후속 초안이 다른 고객의 연락처를 받던 경로).
- **고객 상세 Guru:** 풀리지 않는 리드·계정 id로 딜 진단을 돌리며 매 턴 `project_updates`를 쓰던 경로를 질문 드로어(`open-question`)로 바꿨다.
- **렌즈 대화의 범위 없는 컨텍스트:** 위젯에서 렌즈를 고른 대화가 컨텍스트 없이 가 Hub가 범위 없는 최근 거래 15건(개인 레인 포함)을 붙였다. 조언 경로처럼 이 레코드의 컨텍스트를 넘긴다.
- **Office:** 스킬 요청의 상태·영수증이 화면에 전혀 보이지 않던 것, 프로젝트 없는 할 일에서 `회사`를 고르면 늘 실패하던 것, 개인 레인 멘토가 과거 자문을 "사실 아님" 경고 없이 넣던 것, 새로고침 때 보내지 않은 멘토 질문이 사라지던 것.
