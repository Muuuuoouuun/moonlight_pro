> 관계: [CRM 탭 디벨롭 v0.2](2026-09-21-crm-tab-develop-design.md)의 여섯 축과 [0·1단계 계획](../plans/2026-09-21-crm-tab-develop-phase0-1.md)을 보완한다. §1은 현재 코드 재확인 결과이며, 나머지는 권장안이다. 기존 확정 스펙을 대체하지 않는다. 상충 시 운영자 프로필·최신 확정 스펙·DESIGN.md가 우선한다.

## 0. 제안의 중심

**고객을 찾고 → 지난 대화와 약속을 읽고 → 짧게 기록하고 → 다음 연락을 정하는 흐름을 한 자리에서 끝낸다.**

| 요청 축 | 개선할 경험 | 첫 적용 |
| --- | --- | --- |
| 최적화 | 과거 내역을 빠짐없이 찾고, 화면을 오가도 최신 내용이 일치함 | 검색 범위·읽기 상태 교정, 조회 분리와 캐시 갱신 |
| 편의성 | 고객·채널을 다시 고르지 않고 기록하며, 실패해도 원문이 남음 | 공통 기록창, 고객 문맥 자동 연결, 날짜 프리셋, 초안 복구 |
| UI/UX | 누가 누구인지, 무슨 이야기였는지, 무엇을 해야 하는지 바로 읽힘 | 고객 목록의 열 재구성, 상세의 읽기 우선 배치, 의미 있는 위험 표시 |

첫 결과물은 **고객 목록 + 고객 상세 + 기록창**이다. 내비게이션 전면 개편은 이 세 화면을 사용한 뒤 진행한다.

## 3. UI/UX — 읽기 화면부터 정리

### 3.1 고객 목록

기본 열을 `고객·소속 / 최근 접점 / 다음 행동·날짜 / 진행 상황` 네 묶음으로 구성한다.

- **고객·소속:** 검증된 담당자명을 우선, 조직명을 보조로. 사람이 연결되지 않았으면 조직 이름을 그대로 쓰며 사람을 만들어내지 않는다.
- **최근 접점:** 실제 활동 일자·종류·반응, 요약 한 줄. 조회 실패는 `기록 확인 못함`, 성공한 0건은 `아직 기록 없음`.
- **다음 행동:** 운영자가 작성한 문장과 날짜를 함께 표시. 이관 참고문구는 상세의 참고 영역으로 옮기고 확인 전 약속처럼 표시하지 않는다.
- **진행 상황:** 현재 검토 건의 단계, 필요한 경우 미해결 사건 한 줄. 금액은 거래 문맥에서 보조 표시하며 건강도 점수 열을 기본에서 뺀다.

행 안에 모든 활동을 펼치지 않는다. 행 선택은 상세, 보조 `기록` 버튼은 같은 고객의 기록창을 바로 연다. 목록 선택·검색·스크롤을 저장 후에도 유지한다.

동일 기관의 여러 사람, 리드와 계정이 같이 있는 경우를 이름으로 자동 병합하지 않는다. 안정된 contact ID 등 검증된 동일성만 읽기 모델에서 묶고 원본 ID는 보존한다. 판정 불가는 별도 행과 관계 라벨로 남긴다.

### 3.2 고객 상세

기존 여섯 축을 다음 순서로 배치한다. **최근 기록 미리보기는 기본 노출하고 전체 내역만 접는다.** 이는 기존 v0.2 §4.2의 기록 기본 접힘에 대한 보완 제안이다.

```text
고객명 · 소속                         [기록 남기기]
현재 검토 건 / 단계                   [연락처 보기]
─────────────────────────────────────────────────
중요하게 보는 것 · 막힌 조건            출처 보기
미해결 사건이 있을 때: 이유 + 확인할 행동
다음 약속: 내용 · 날짜                  [변경]
최근 접점: 날짜 · 채널 · 반응 · 요약
─────────────────────────────────────────────────
진행 거래: 품목·수량 / 견적 / 결제 확인 상태
최근 기록 3건                          [전체 내역]
연결 메모                              [메모 작성]
판단 근거                              [펼치기]
```

- 데스크톱은 기존 Drawer를 사용한다. 440px에 여섯 축과 입력 폼을 모두 쌓지 않고, 읽기·기록 모드를 전환한다. 폭 조정은 렌더 검증 후 결정한다.
- 상단의 고객 식별과 기록 버튼, 하단의 복귀 동작이 보이도록 한다. 상세에서 기록을 열어도 오버레이는 하나다.
- `전체 내역`은 같은 고객 문맥 안에서 기간·종류·단어 검색을 제공한다. 이전 기록으로 이동해도 작성 초안은 보존한다.
- 전화·메시지 버튼은 실제 가능한 동작만 제공한다. 번호가 없으면 복사·전화 액션을 활성화하지 않는다. 메시지 초안은 사용자가 요청할 때 생성한다.
- 회사 공통 기록은 `기관 공통 기록`으로 구분한다. 이를 특정 사람·특정 거래의 반응이나 약속으로 자동 귀속하지 않는다.

### 3.3 연락 화면

상단은 **기한 있는 약속**, 아래는 **선별한 연락 후보**로 나눈다. 약속은 실제 기한순, 나머지 후보는 Q117의 트래킹 → 날짜 도래 → 상담·견적 → 무접촉 순서를 기준으로 설계한다. 무기한 항목은 별도 렌즈에 둔다.

기존 v0.2 §4.6의 단계가 트래킹보다 앞서는 표와 ‘Q117과 정합’이라는 설명은 그대로 구현하지 않는다. 고객별 수동 트래킹과 현재 워크스페이스 컷오버가 다르므로, 수동 선택을 표현할 계약이 생기기 전에는 컷오버를 사용자의 고객별 선택처럼 설명하지 않는다.

행은 `고객 / 왜 지금 / 최근 접점 / 다음 행동·날짜 / 기록`으로 통일한다. 미래 연락 계획을 보여줄지 정하지 않은 상태에서 `이번 주` 필터만 살리지 않는다. 큐의 유입 범위와 필터가 같은 모집단을 사용해야 한다.

빈 화면에는 확인 가능한 이유와 행동을 제시한다. 초기에는 `오늘 연락 대상으로 표시된 항목이 없어요` + `고객 목록에서 다음 연락일 정하기`처럼 실제 제공하는 동작으로 연결한다. 일정 원천이 없는 큐의 `일정` 필터는 제거하거나 원천 연결 뒤 노출한다.

### 3.4 위험·색·숫자

- 점수 낮음·정보 부족·미접촉만으로 `이탈위험`을 붙이지 않는다. 미확인은 `확인 필요`다.
- 긴급함은 약속 지연, 다음 행동을 막는 확인된 조건 등 사건과 근거로 표현한다. 우려 한 번이나 다른 주제의 긍정 반응으로 위험을 자동 생성·해제하지 않는다.
- UI는 DESIGN.md의 토큰·고정 밀도·1px 선·TruthBadge/CertaintyBadge/LifecycleBadge를 따른다. 새 팔레트·밀도 토글·CRM 전용 디자인 시스템은 만들지 않는다.
- 현행 Futura 공용 컴포넌트 질감은 상속하되, Home의 큰 제목·넓은 여백을 CRM 본문에 복사하지 않는다. 표는 읽기 밀도를 유지한다.
- 모바일은 고객명·다음 약속·기록 버튼을 먼저 보여주는 세로 행. 터치 44px, 입력 16px 이상, 세그먼트는 가로 유지한다.

| 목적 | 기본 입력 | 저장이 바꾸는 것 |
| --- | --- | --- |
| 빠른 메모 | 본문 | 메모/활동 원문. 연락 완료·약속 완료로 계산하지 않음 |
| 통화·회신 결과 | 요약·고객 반응·다음 행동 상태 | 실제 연락 활동 + 명시적으로 선택한 후속 |
| 부재중 | 실제 시도 확인·다음 시도 | 연락 시도. 고객의 관심 없음·거절로 해석하지 않음 |
| 자료 전달 | 보낸 자료·시각, 후속 선택 | 전달 사실 기록. 자료 발송 자체는 하지 않음 |
| 미팅·데모·방문 | 원문·반응·결정·막힌 조건·다음 행동 | 실제 결과. 예정 일정은 자동으로 완료하지 않음 |

현재 고객·거래·채널은 진입점에서 채운다. 이름·금액·반응·날짜를 템플릿이 사실처럼 채우지 않는다. 추가 필드는 필요할 때 펼치고, 장문 붙여넣기는 한 줄 요약 때문에 잘라내지 않는다.

다음 행동은 `날짜 있음 / 기약 없음 / 후속 없음`을 명시적으로 구분한다. `후속 없음`은 이번 연락의 후속만 닫으며 다른 약속·거래를 자동 종결하지 않는다. `기약 없음`을 오늘 연락으로 자동 승격시키지 않는다.

### 4.2 반복 입력 줄이기

- 날짜는 `내일 / 3일 뒤 / 다음 주 / 직접`과 실제 날짜·요일을 함께 표시한다.
- 저장 뒤 `기록됨 · 다음 연락 날짜`를 보여주고 같은 고객 상세로 돌아온다. 연속 작업은 보조 동작 `저장 후 다음 고객`으로만 제공한다.
- `/` 검색, j/k 행 이동, e 상세 등 현행 키보드 동작을 유지한다. 고객 목록의 **N=새 고객**을 기록 단축키로 바꾸지 않는다. 기록창 내부 ⌘Enter는 한글 조합 중 작동하지 않는다.
- 새 고객은 빈 입력창에서 시작하고 저장할 때 생성한다. 닫기·취소만으로 영속 레코드를 만들지 않는다. 동명이인·동일 기관 후보는 검토 선택이며 자동 병합하지 않는다.
- 첫 버전에서 자주 쓰는 보기·정렬·접힘 상태를 기억한다. ‘사용자 정의 뷰 빌더’는 만들지 않는다.

### 4.3 저장 상태와 초안

`작성 중 → 전송 대기(되돌리기 가능) → 저장 중 → 서버 저장 확인`을 구분한다. 기존 3.5초 지연 전송을 유지한다면 기다리는 동안 `저장됨`이라고 하지 않는다.

- 입력은 서버 확인 전 초기화하지 않는다. 실패 시 같은 필드에 원문·대상·날짜를 보존하고 재시도·복사를 제공한다.
- 지연 전송은 페이지를 떠나도 유실되지 않는 공통 처리부에서 관리하거나, 전송 완료 전 이동을 명시적으로 보류한다. 컴포넌트 해제와 함께 사라지는 타이머에 저장을 맡기지 않는다.
- 서버 확인 뒤의 `되돌리기`는 별도 취소 계약이 없으면 제공하지 않는다. 저장 전 취소와 저장된 이력 수정은 다른 동작이다.
- 초안은 workspace·고객·검토 건별로 분리해 같은 탭에서 복구한다. 복구 범위는 같은 탭 새로고침까지이며 브라우저 종료 후 복구를 약속하지 않는다. 복구·복사·버리기를 제공한다.
- 재시도는 같은 요청 ID를 사용한다. 서버에서 workspace+요청 ID의 유일성을 보장하고, 같은 ID에 다른 본문은 충돌로 처리한다. 존재 여부 선조회만으로 동시 중복을 막았다고 보지 않는다.
- 다른 탭이 다음 약속을 수정했다면 조용히 덮어쓰지 않는다. 예상 버전 비교와 원문 보존이 함께 필요하다. 새 활동·다음 약속 갱신은 하나의 저장 계약으로 처리한다.

## 5. 최적화 — 완전성, 조회 비용, 화면 반응

### 5.1 검색과 조회 범위

1. 고객 목록 검색은 서버에서 수행하고 검색 결과를 페이지로 받는다. 첫 페이지 **50행은 제안값**이며 실제 사용·응답 크기로 조정한다.
2. 이름·담당자·기관·정규화 전화번호를 고객 검색 대상으로 한다. 기록 본문 검색은 고객 상세의 전체 내역과 후속 기록 렌즈에 둔다.
3. 날짜·종류·기간 필터를 적용한 후 페이지를 나눈다. 안정된 정렬키와 ID를 함께 사용해 같은 날짜의 행이 페이지 사이에서 중복·누락되지 않게 한다.
4. 단순히 limit를 늘려 ‘전체 검색’이라 하지 않는다. `표시한 수 / 전체 수 / 다음 페이지 있음 / 집계 완전성`을 구분한다. 전체 수를 검증하지 못하면 `조회된 항목`으로 표시한다.
5. 검색 정규화는 한글 Unicode NFC·공백·전화번호 표기부터 처리하고 원문은 유지한다. 초성·오타 검색은 후속 사용 결과로 결정한다.
6. 딥링크 대상이 현재 페이지에 없으면 ID로 단건 조회한다. `?customer/lead/deal`의 1회 열기 계약을 유지하고 해당 키만 소거해 scope·검색·정렬 조건을 보존한다.

고객별 최근 활동을 행마다 별도 호출하지 않는다. 현재 페이지의 검증된 ID 집합을 대상으로 묶음 조회하고, 거래·기관 기록의 귀속과 읽기 완전성을 반환한다. 활동 전체를 500개 받아 고객별 최근 기록이라고 단정하지 않는다.

### 5.2 요청과 캐시

- 고객 목록 진입에 필요 없는 Cases·매출 전체 원장을 읽지 않도록 읽기 모델을 분리한다. 공통 Supabase REST 클라이언트·read guard는 그대로 재사용한다.
- 캐시 키는 인증 문맥·workspace·scope·조회 조건을 구분한다. 동일 키의 진행 중 요청은 공유하고, 조건이 바뀌면 이전 응답을 무시하거나 취소한다.
- 저장 성공 때 해당 고객 상세·활동·연락 큐·연관 집계를 무효화한다. 통째로 화면을 비우는 대신 기존 행을 유지하면서 갱신 중임을 표시한다.
- 재검증 실패한 이전 데이터에는 `일부 데이터 · 마지막 확인 시각`을 붙인다. 확정된 다음 행동처럼 재사용하는 정책은 별도로 검증한다.
- 고객 페이지가 공유 훅 때문에 `revenue.jsx` 전체에 의존하는 구조는 공통 훅·정렬·저장 유틸로 분리한다. **번들 감소는 빌드 분석으로 확인할 목표**이며 현재 크기 감소 실측은 없다.

DB 인덱스는 실제 쿼리와 실행 계획 확인 뒤 제안한다. 새 라이브러리·전면 가상 스크롤보다 조회 범위와 왕복 횟수를 먼저 정리한다.

### 5.3 기록의 일관성

- 활동 ID 기준으로 중복 제거하며 ‘본문이 비슷하다’는 이유로 별도 사건을 합치지 않는다.
- 메모·단순 수정·AI 초안과 실제 연락을 구분한다. 마지막 연락일은 실제 사건 시각을 사용한다.
- 주간 집계는 같은 기간·timezone·scope·활동 유형·중복 규칙의 **실제 연락 부분집합**과 일치해야 한다. 메모를 포함한 모든 기록 건수와 같을 필요는 없다.
- 기관만 연결된 과거 활동은 귀속 근거가 없으면 특정 사람의 집중도·위험·주간 성과로 확정하지 않는다. 미측정·partial 사유를 표시한다.
- 다음 약속 날짜는 공통 timezone 계약을 따른다. 날짜만 지정한 항목은 그 날이 끝나기 전까지 지연으로 표시하지 않는다.

## 6. 단계별 실행 백로그

규모는 상대값이며 일정 약속이 아니다. 여러 파일을 구현할 때는 전용 worktree를 사용한다.

| 단계 | 작업 묶음 | 완료 기준 | 기존 계획과 관계 |
| --- | --- | --- | --- |
| **P0 신뢰·연결** | 로딩/empty/error 구분, 활동 read 봉투와 소비자 통일, 빠른 기록 입력 보존, 큐 item 계약·company 연결, 점수 기반 위험 표현 제거 | 실패가 0건처럼 보이지 않음. 저장 실패 후 같은 입력에서 재시도. 큐 행의 클릭·필터·최근 기록이 계약대로 작동 | 0b와 1a 일부 선반영. 주간 reader 교체는 제외 |
| **P1 읽기·기록 경험** | 목록 4묶음, 공통 상세, 공통 기록창, 새 고객 저장 시 생성, 날짜·초안·요청 ID·충돌 | 고객 문맥 확인→기록→다음 약속을 한 흐름에서 완료. 취소 시 빈 고객 0건 | 1a·1b 보강. RPC 변경·유일성 제약 필요 여부 함께 설계 |
| **P2 검색·속도** | 서버 검색·페이지 처리, 단건 딥링크, 최근 활동 묶음 조회, 캐시 무효화, 공통 훅 분리 | 상한 밖 데이터·마지막 페이지 검색 검증. 화면 간 최신 내용 일치. 아래 성능 측정 | 기존 계획에 추가. P1에서 5영업일 관찰 후 조정; 실제 누락이 확인되면 해당 항목은 P0로 승격 |
| **P3 기록 활용·탐색** | 전체 기록 렌즈, 고객·연락·기록·매출 진입점 정리, 니즈·막힌 조건의 근거 관리 | 과거 발언을 기간·단어로 찾고 고객의 해당 기록에 바로 도달 | 기존 2·3단계와 통합. 메뉴 변경은 이 단계에서 결정 |

P0의 위험 표현 제거는 중립 라벨로 교정하는 범위다. 자동 위험 판정·연락 순위 변경은 기존 미정 정책을 확정한 뒤 별도 적용한다. 외부 동기화·발송과 자동 재채점은 이 백로그에 포함하지 않는다.

## 7. 검증 기준

### 사용자 흐름 목표

다음 수치는 **개선 목표이며 현재 측정값이 아니다**. 합의된 5개 시나리오를 전후 같은 환경에서 비교한다.

| 시나리오 | 목표 |
| --- | --- |
| 고객 상세에서 다음 행동 파악 | 5초 안에 내용과 날짜를 설명 |
| 고객이 지정된 상태에서 짧은 메모 | 10초 안에 서버 저장 확인 |
| 일반 통화 결과 기록 | 20초 목표, 초기 검증 상한 30초. 요약·반응·후속 상태 포함 |
| 과거 발언 찾기 | 15초 안에 원문 기록 도달 |
| 기록 실패·재시도·새로고침 | 입력 유실 0, 동일 요청의 중복 활동 0 |

최근 실제 업무의 통화 1건·메모 1건·미팅 1건·예전 기록 찾기 1건·다음 연락 변경 1건으로 확인한다. 검증을 위해 운영 DB에 시험 기록을 만들지 않는다. 장애·중복·대량 데이터 검증은 격리된 테스트 환경에서 수행한다.

### 구현 검증

- read 200+error, preview, partial, live-empty 각각의 UI와 재시도. 활동 일부 실패가 ‘최근 연락 없음’으로 바뀌지 않는지 확인.
- 큐에 항목이 **있는 통제된 조건**에서 버킷·클릭·반응을 확인한다. 실제 큐가 0건이라고 실패시키지 않는다.
- 동일 요청 동시 저장·응답 유실 뒤 재시도·다른 본문으로 키 재사용·두 탭 약속 수정·뒤늦은 이전 응답을 검증한다.
- 120개 초과 고객·200개 초과 이력·같은 시각의 기록·한 기관의 여러 사람·재문의 새 거래·company만 연결된 이력을 검증한다.
- 390×844·1280×720·1440×900, 다크/라이트, 키보드·한글 조합·포커스 복귀·줄바꿈·reduced-motion을 확인한다.
- 변경 범위의 기능 테스트, state-usage·motion·focus-ring·no-mock-data 계약, 루트 테스트를 실행한다. 현재 기획 작성 단계에서는 코드 테스트를 실행하지 않았다.

### 성능 측정

첫 방문·캐시 재방문·고객 상세·검색·저장 확인을 분리해 요청 수, 응답 크기, 표시까지의 시간을 기록한다. 개발 첫 컴파일과 정상 요청을 섞지 않는다. 각 경로를 같은 장치·네트워크에서 반복 측정한 뒤 p50/p95를 비교한다.

권장 목표: 최초 행동 가능한 화면 p95 3초 이하(심화 설계 기존 목표), 재방문에서 목록을 통째로 비우는 구간 0회, 같은 조건의 동시 read 중복 0회. 서버 검색·상세 p95 목표는 기준선 측정 후 정한다. 지연 전송 3.5초는 네트워크 시간과 별도로 보고하며 체감 지연이 크면 유지 여부를 재검토한다.

## 8. 후속 결정과 첫 착수 단위

정책 미정은 자동 위험 판정·고객별 트래킹·매출/결제 확정 규칙·메뉴 합침 범위다. 이번 기획으로 확정 처리하지 않는다. 추가 업무 인터뷰는 재개하지 않는다.

**첫 착수 단위는 P0:** 고객 목록의 로딩/실패 상태와 빠른 기록 입력 보존을 고치고, 활동 read 계약·연락 행 계약을 맞춘다. 다음으로 P1의 고객 상세와 기록창을 함께 검증한다.

새 화면 채택 여부는 “최근 실제 고객 한 건의 이전 대화를 읽고 다음 연락을 남기는 데 화면을 몇 번 오갔는가”로 판단한다. P1 적용 뒤 5영업일 동안 탐색 횟수·기록 시간·저장 실패 복구만 간단히 관찰한다.
