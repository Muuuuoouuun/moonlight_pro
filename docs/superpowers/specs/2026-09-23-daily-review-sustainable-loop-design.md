## 1. 한 줄 결론

하루 리뷰는 **입력 폼이 모자란 게 아니라 "들어올 이유"와 "쌓였다는 감각"이 없다.** 저장·충돌·초안 복구 계약은 이미 단단하다. 고칠 것은 네 층이다.

| 층 | 질문 | 지금 | 제안 |
|---|---|---|---|
| ① 진입(Cue) | 언제·어디서 떠오르나 | 사이드바 `내 작업 › 하루 리뷰`와 ⌘K 이동뿐. 홈·오늘 어디에도 없다 | 저녁에 오늘 탭에 한 줄. 어느 화면에서든 같은 팝업이 뜬다 |
| ② 입력(Routine) | 몇 번 눌러야 끝나나 | 이동 → 기록 남기기 → 에너지 → 저장 = 최소 4단계. 오늘 3개를 이미 골랐어도 목표를 다시 친다 | 팝업 바로 열기 + 에너지 1탭 + 저장 = 2단계. 오늘 3개로 목표·진척을 **권장값**으로 채운다 |
| ③ 되돌아보기(Reward) | 쌓이는 게 보이나 | 월별 텍스트 목록. 연속 표시는 할 일 완료일만 센다 | 월 캘린더 점과 "이번 주 3/5", 에너지 추이 |
| ④ 회복(Forgiveness) | 하루 빠지면 어떻게 되나 | 아무 신호 없음. 날짜 입력으로 직접 찾아가야 한다 | 다음 날 오전에 "어제 기록 남기기" 한 줄. 연속 끊김 경고는 두지 않는다 |

"꾸준히"의 설계 원칙은 하나다. **가장 작은 기록(에너지 한 번)을 완주로 인정하고, 빠진 날을 벌하지 않고 메울 수 있게 한다.** 연속 일수가 아니라 주당 기록일(근무일 5일 기준)을 기본 지표로 둔다. 이미 주간 리포트의 `reviewDays`와 09-20 §7.2 "하루 리뷰 기록일 수(주 5)"가 같은 정의를 쓴다.

## 2. 현재 상태 — 확인한 사실

### 2.1 잘 되어 있는 것(유지)

- **저장 계약**: `save_daily_review_v1` RPC, `expectedRevision`·`requestId` 멱등, 충돌 시 두 기록 비교(`daily-review-conflict`), `sessionStorage` 초안과 `beforeunload` 보호(`daily-review-browser-store.js`), shell 마운트 때 복원(`hub-app.jsx`의 `dailyReviewDraftStore.restore()`).

- **compact Drawer**: 데스크톱 중앙 팝업과 모바일 하단 시트, ESC·포커스 처리, 저장 확인 뒤 닫힘 모션(`--dur-panel`).

## 4. 아키텍처

### 4.1 구성도

```
hub-app.jsx (shell)
 └─ DailyReviewProvider            ← 새로: useDailyReview 인스턴스 1개 + 팝업 open/close
     ├─ DailyReviewComposer        ← 기존 팝업. 페이지 로컬 state에서 shell로 승격
     ├─ pages/daily-review.jsx     ← 같은 model을 context로 소비(인스턴스 중복 없음)
     ├─ ReviewCueRow               ← 새로: 오늘(daily-brief)·홈에 한 줄
     └─ ⌘K Action "하루 리뷰 쓰기" ← 새로: 팔레트 Action 항목

lib/daily-review-rhythm.js         ← 새로: 순수 함수(시각·기록 → 신호). node --test로 고정
  reviewCue(now, timezone, todayReview, yesterdayReview) → 'none' | 'evening' | 'backfill'
  suggestFromFocus(todaySignals, focusTitles)            → { focus, progress, reason } | null
  buildReviewMonth(month, entries, todayKey)             → cells[], weekCount, energySeries

API: GET /api/hub/daily-review (기존)  — 응답에 today.focusTitles(최대 3), yesterday 요약 1개 추가
     POST (기존 그대로)
DB:  변경 없음 (Phase 1~3)
```

### 4.2 결정 사항

1. **model은 하나.** 지금은 페이지가 `useDailyReview()`를 소유하고 팝업은 그 자식이다. 팝업을 shell로 올리면서 훅 인스턴스도 Provider 하나로 옮긴다. 페이지와 팝업이 같은 초안·revision·충돌 상태를 본다. 두 인스턴스가 같은 날짜의 초안을 각자 쓰는 경쟁을 막는 게 목적이다.
2. **Provider는 지연 로드한다.** 팝업을 열거나 cue가 필요할 때만 `GET /api/hub/daily-review`를 부른다. 모든 페이지 진입마다 리뷰를 읽지 않는다. cue는 오늘 탭 자체의 기존 로드와 별개로 가벼운 한 번의 읽기(오늘·어제)만 쓴다. 필요하면 `?date=` 한 번으로 둘 다 가져오도록 응답을 확장한다(§4.4).
3. **딥링크 계약**: `?review=today` / `?review=YYYY-MM-DD`는 어느 대시보드 경로에서든 팝업을 1회 열고 쿼리를 소거한다(§8.1 `?lead=`·`?deal=` 규칙과 같은 방식). 기존 `dashboard/work/daily-review?date=`(목표·지표 링크가 쓰는 형식)는 그대로 날짜 선택으로 남긴다.
4. **순수 함수가 규칙을 소유한다.** cue 시각, 권장값 계산, 캘린더 셀 상태는 `lib/daily-review-rhythm.js`에만 두고 컴포넌트는 결과만 그린다. `task-today.js`·`weekly-report.js`처럼 테스트가 규칙을 고정한다.

### 4.3 ① 진입 — ReviewCueRow

| 조건(`reviewCue`) | 오늘 탭·홈에 보이는 한 줄 | 동작 |
|---|---|---|
| `evening` — 운영자 시간대 18:00 이후, 오늘 리뷰 없음 | `○ 하루 마무리 · 에너지 하나만 남겨도 돼요` + `남기기` | 팝업(오늘) |
| `backfill` — 다음 날 12:00 이전, 어제(근무일) 리뷰 없음, 오늘 리뷰 없음 | `○ 어제 기록이 비어 있어요` + `어제 남기기` | 팝업(어제) |
| 오늘 기록됨 | `✓ 오늘 기록함 · 에너지 4` (낮은 강조) | 팝업(오늘, 수정) |
| 그 외 | 표시 안 함 | — |

- 18:00은 §5 자동 테마가 다크로 바뀌는 시각과 같다. 운영자 기기 시계가 아니라 **워크스페이스 시간대**(`resolveRhythmTimeZone`)로 판정한다. 저장 날짜와 같은 기준이어야 자정 근처에 어긋나지 않는다.
- 색: 전부 중립. `○`/`✓`는 §5.3 lifecycle `queued`/`done` 글리프이고, 붉은색·경고색을 쓰지 않는다(§5.2 "No warning-by-default": 오늘·대기는 빨강이 아니다).
- 자리: 오늘 탭은 09-21 §5 순서의 4번(하루 마무리) — 목록 맨 아래가 아니라 저녁에는 빠른 입력 바로 아래로 올린다(권장, Q-DR2). 홈은 트리아지 큐 밖의 한 줄.
- 푸시·이메일 알림은 두지 않는다. 텔레그램 저녁 메시지는 09-20 §6.3의 봇 작업과 묶어 Phase 4 후보로만 적는다.

### 4.4 ② 입력 — 2단계 경로와 권장값

**최소 경로**: cue `남기기` → 팝업(에너지에 초기 포커스) → `1`~`5` 키 또는 탭 → `Enter`/저장. 저장 확인 뒤 닫힘(기존 계약 유지).

| 변경 | 내용 | 계약 |
|---|---|---|
| 키보드 1~5 | 팝업 포커스가 텍스트 입력 밖일 때 숫자 키로 에너지 선택. 같은 숫자는 해제(기존 토글 동작과 동일) | §8.1 단축키 조건(입력 필드 밖)과 같다 |
| 오늘 3개 권장값 | `today.focusPicked > 0`이면 목표·진척 영역 위에 **`◇ 권장` 카드**: "오늘 3개 2/3 완료 → 진척 `진행`". `적용`을 누르면 `focus`에 `오늘 3개: 제목A · 제목B · 제목C`(500자 이내로 자름), `progress`에 계산값을 넣는다. 누르기 전엔 draft를 바꾸지 않는다 | §5.3 certainty `recommended`(`CertaintyBadge`). 기본 선택값을 미리 점수로 저장하지 않는다(09-12 §4.1) |
| 진척 계산 | `done === picked` → 2 목표 달성, `done > 0` → 1 진행, `done === 0` → 0 미착수 | 09-20 §6.2 규칙. 사용자가 덮어쓸 수 있다 |
| 이미 값이 있으면 | 저장된 기록이나 초안에 focus/progress가 있으면 권장 카드를 숨긴다 | 사용자 입력을 권장값이 덮지 않는다 |
| AI 코칭 | 기본 fieldset 밖으로 옮긴다. **저장된 기록이 있을 때만** 푸터 위 ghost 버튼 `코칭 받기`. 결과는 `◇ 권장` 카드(`CertaintyBadge recommended`)이며 `메모에 추가`는 기존처럼 draft만 바꾼다 | 09-12: "AI 없이 저장·재조회, 분석은 별도 버튼". G4 부채는 `daily-review.css` 클래스, `Button`/`IconButton` primitive, 12px 이상, 이모지 제거, 복사 피드백은 toast만(raw 2000ms 타이머 제거)으로 정리 |
| 메모 placeholder | 날마다 바뀌는 한 줄 예시(잘된 일/걸린 점/기억할 일 중 하나). **필드는 늘리지 않는다** | 09-20 §6.3 "회고 질문 없음" 유지 |

API 확장(마이그레이션 없음): `readTodaySignals`가 이미 `tasks`를 `focus_dates`로 읽으므로 select에 `title`을 더해 `today.focusTitles`(최대 3, 오늘 3개 상한 `MAX_FOCUS_PER_DAY`)를 싣는다. 제목이 없으면 권장 카드는 진척만 제안하고 목표는 비운다.

### 4.5 ③ 되돌아보기 — 월 캘린더와 주간 수


- 셀 상태는 `buildReviewMonth`가 계산: `recorded` / `missed`(근무일·과거·미기록) / `rest`(주말·미기록) / `today` / `future`. 셀 클릭은 그 날짜로 팝업(`openReview(date)`). 미래는 비활성.
- 근무일은 09-20 §6.2 정의(월~금, KST 고정)를 따른다. 주말 기록은 ●로 보이되 분모에 넣지 않는다.
- **연속 일수는 표시하지 않는다.** "이번 주 k/5"는 매주 초기화되고, 하루 빠져도 그 주 안에서 회복된다. 연속 끊김 문구·빨강·애니메이션 없음(§5.3 red-budget, §9 긴급 인디케이터 무루프).
- 에너지 추이는 월 entries의 `energy`만 쓴다(null은 끊어진 선). §5.3 차트 규칙대로 Moonstone 명도, 범례 대신 직접 라벨 `에너지`.
- 주간 수는 월 경계를 넘을 수 있다. 이번 주가 전월에 걸치면 전월 entries를 한 번 더 읽는다(기존 `month` 파라미터 재사용, API 변경 없음).
- 날짜 컨트롤 정리(G8): 캘린더 헤더의 `‹ 9월 ›`가 월 이동을 맡고, `조회 월` 입력과 이전/다음 날 버튼은 캘린더로 흡수한다. 날짜 직접 입력은 접힌 보조 컨트롤로 남긴다. `TruthBadge`는 `live`일 때 숨기고 `preview`/`error`/`partial`일 때만 보인다(허브 다른 표면과 같은 "문제 있을 때만 말하기").
- 로딩은 `Skeleton`(캘린더 7×5 그리드 모양)으로 그린다. `기록을 불러오는 중…` 한 줄을 대체한다(§11).

### 4.6 ④ 회복

- `backfill` cue(§4.3)가 유일한 회복 신호다. 어제 하루만 제안한다. 그보다 오래된 빈칸은 캘린더의 `○`로만 보이고, 누르면 메울 수 있다.
- 과거 날짜를 저장할 때 팝업 제목에 `어제 · 9월 22일 화요일`처럼 날짜를 먼저 말해 오늘 기록과 헷갈리지 않게 한다. 저장 계약은 날짜 무관하게 동일하다(기존).
- 오늘 3개 권장값은 **오늘 날짜에만** 뜬다(`today.date === date` 기존 조건 유지). 과거 날짜엔 부제의 신호도 없다. 서버가 그날 신호를 읽을 수 있으면 날짜별로 확장하는 것은 Phase 4.

## 7. 측정 — 30일 뒤 볼 것

09-20 §7의 30일 관찰 항목을 그대로 쓴다. 새 계측은 추가하지 않는다.

1. **하루 리뷰 기록일 / 근무일**(주간 카드 `reviewDays`). 제안 목표 4/5(미정, 실측 뒤 확정).
2. 에너지만 남긴 날의 비율. 높아도 실패가 아니다. 최소 경로가 작동한다는 신호다.
3. `backfill`로 메운 날 수(저장 시각의 날짜 > `review_date`인 기록). 회복 층이 쓰이는지 본다. `updated_at`으로 계산 가능, 새 컬럼 없음.
4. 권장 카드 `적용` 뒤 진척을 바꾼 비율. 바꾸는 비율이 높으면 계산 규칙이 운영자 판단과 어긋난다는 뜻이다.

## 9. 운영자 결정이 필요한 것 (인터뷰 재개 시 후보)

인터뷰가 중단 상태라 질문을 던지지 않고 모아 둔다. 괄호 안은 이 문서의 권장값이다.

1. **Q-DR1 cue 시각**: 저녁 cue를 몇 시부터 띄울까? (18:00, 자동 테마 전환과 같은 시각)
2. **Q-DR2 오늘 탭 자리**: 저녁에 하루 마무리 행을 빠른 입력 바로 아래로 올릴까, 목록 맨 아래에 둘까? (저녁에만 위로)
3. **Q-DR3 주간 목표**: 하루 리뷰 기록일 목표를 주 5일로 둘까, 주 4일로 둘까? (4/5로 시작, 실측 뒤 조정)
4. **Q-DR4 권장값 적용 방식**: 오늘 3개 권장값을 버튼으로 적용할까, 기본으로 채워 두고 지우게 할까? (버튼 적용. 09-12 "기본 선택값을 미리 저장하지 않는다")
5. **Q-DR5 AI 코칭 자리**: 저장 후에만 보이게 할까, 지금처럼 입력 중에도 보일까? (저장 후)
