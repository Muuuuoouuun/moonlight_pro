## 1. 요청과 확정 입력

운영자는 사용하는 유료 제품, 고정비, 사용 기록을 수집하고 계속 추적하려고 한다. 개인 소비와 회사 청구 내역을 나눠 비교하고, Office의 CFO가 함께 검토하는 방향을 요청했다.

확정된 요청은 다음과 같다.

- 개인 현금 흐름에 구독·고정비·회사 청구를 포함한다.
- 허가된 은행·카드·간편결제 자료를 지정 기간 전체 조회하고, 출처별 관측을 대조한다.
- 같은 공급자의 서로 다른 플랜은 별도 계약으로 보존한다. 계정·가격·주기가 불명확하면 확인 대상으로 남긴다.
- Office와 재무 역할(CFO)을 통한 관리·검토를 지원한다. 자동 결제·해지·회사 제출은 별도 범위다.

상품별 자술 가격·청구 주기와 실제 초기 계약 목록은 공개 저장소에 두지 않고 비공개 금융 장부에 보관한다. 자술값은 근거가 있는 입력이지만 정규화된 약정 금액이나 실제 청구 확정액은 아니다. 청구 주기·통화·세금이 확인되지 않은 값을 월 고정비로 합산하지 않는다. 통신비와 이용권의 중복 여부도 실제 자료로 확인한다.

## 2. 현재 기능과 목표

현재 개인 `현금 흐름` 탭은 `/dashboard/revenue/overview?scope=personal`의 30일 **영업 거래 예상 유입**이다. 계좌 잔액·소비·구독료·회사 비용 환급 장부가 아니다.

거래의 예상/실제 입금과 `deals.meta.recurring`은 수입을 기록한다. 금융 지출을 가짜 영업 거래로 만들거나 회사 계약 금액을 개인 수입으로 합산하지 않는다.

설정의 AI 사용량은 Moonlight가 호출한 Gemini의 토큰과 **추정 API 비용**이다. 구독 이용량, 로컬 Codex/Claude 사용, 공급자 청구서, 이번 목록의 고정비 전체를 뜻하지 않는다.

이번 기획이 답할 질문은 다음 네 가지다.

1. 무엇을 사용하며, 약정된 다음 지출은 언제 얼마인가?
2. 실제 소비와 계좌에서 나간 돈은 각각 얼마인가?
3. 회사 관련 사용·청구·실제 회수 금액은 얼마나 다르고 무엇이 남았는가?
4. 사용을 확인할 근거가 있고, 유지·축소·재검토 판단은 무엇인가?

## 3. 정보구조와 화면 예산 — 권장

개인 스코프의 기존 다섯 번째 `현금 흐름` 탭을 `/dashboard/revenue/cashflow?scope=personal`로 연결하는 것을 권장한다. 새 사이드바 앵커나 영업·매출의 여섯 번째 탭은 추가하지 않는다.

페이지 안의 선택기 하나로 `흐름 / 구독·고정비 / 회사 청구`를 전환한다. 경로는 `?view=flow|subscriptions|claims`를 권장하며, 영업·매출 탑바 탭과는 구분한다.

| 보기 | 본문의 핵심 | 주 행동 |
|---|---|---|
| 흐름 | 확인된 실제·예정 입출금, 잔액과 누락 범위 | 기록 확인·예정 수정 |
| 구독·고정비 | 계약 목록, 다음 결제, 같은 기간의 비용·사용 근거 | 계약 상세에서 확인·검토 |
| 회사 청구 | 회사 관련 사용액, 청구/승인/실제 회수와 남은 금액 | 해당 비용의 증빙·상태 확인 |

계좌·카드 설정, 가져오기, 원본 대조, CFO 검토는 더보기 또는 선택 항목 드로어로 연다. 본문에 수집·설정·CFO 패널을 동시에 덧붙이지 않는다. 회사 청구 준비 자료는 먼저 검토 가능한 결과로 만든다.

기존 `/dashboard/revenue/overview?scope=personal`은 `개인 매출 전망`으로 ⌘K와 기존 딥링크에 보존한다. 전망 금액을 잔액으로 바꾸거나 금융 기록에 자동 복제하지 않는다.

내비 구현 시 `hub-nav.js`의 탭/역할, `hub-data.js`의 ⌘K, `hub-app.jsx`의 페이지 매핑을 함께 검토한다. 개인 금융의 사용 목적 필터는 셸의 회사/개인 workspace 접근 권한과 별개다. ClassIn 회사 스코프로 개인 금융 자료를 이동시키지 않는다.

UI 구현 전 DESIGN.md를 전부 읽는다. 이번 제안은 Futura 페이지 텍스처 확장 결정을 포함하지 않는다. 로딩·미연결·실제 빈 기록·일부 누락·읽기 실패를 구분하고, 모바일 390px의 첫 행동·44px 터치·16px 입력을 지킨다.

## 4. 최소 논리 자료구조 — 권장, DB 이름 미정

| 단위 | 저장할 최소 사실 | 연결 |
|---|---|---|
| 구독·고정비 계약 | 공급자·상품/플랜·계정 별칭, 자술 원문, 확인된 약정액/통화/주기, 다음 결제일, 시작/종료·해지 상태 | 결제 수단·실제 회차·사용 기록 |
| 원본 관측 내역 | 출처, 출처 행 ID, 관측 시각·대상 기간, 원문/금액·통화, 가져오기 배치, 검토 상태 | 한 소비 또는 결제 사건의 근거 |
| 소비와 목적 배분 | 소비 총액, 발생일, 원판매자, 취소/환불, 개인·개인사업·회사업무·미분류 배분 | 계약·원본 근거·회사 청구 |
| 계좌·결제·정산 연결 | 계좌/카드/잔액 별칭·기준 잔액, 지급 수단별 금액, 카드 회차·납부, 이체·충전·환불 현금 사건 | 소비 및 실제 은행 입출금 |
| 회사 청구 | 관련 비용·배분액, 제출액/일·상태, 승인액/일, 반려/보류 이유, 증빙 참조, 실제 회수액·일 | 원비용·부분 환급 거래 |
| 사용 근거 | 상품·계정·관측 기간, 근거 종류, 측정값/직접 메모, 취득 방식·갱신일·누락 범위 | 계약·CFO 검토의 입력 |

이는 최소 논리 구분이며 6개 테이블로 고정한 설계가 아니다. 기존 09-13 설계의 예정 일정·반복 규칙·할부·대출·가져오기 배치는 해당 단위에 연결하거나 후속 모델로 구체화한다.

각 단위는 사용자/workspace, 출처, 생성·수정 시각을 가진다. 확인된 KRW는 원 단위 정수, 미확인 값은 null과 이유를 보존한다. 서로 다른 통화를 그대로 합산하지 않는다.

자술액·약정액·실제 회차 금액은 별도 필드다. 실제 명세서 한 건의 금액을 다음 달 계획 금액으로 자동 채우지 않는다. 약정 변경은 확인 근거와 적용일을 남기고 지난 확정 회차를 바꾸지 않는다.

목적 배분 합은 원소비 금액과 맞아야 한다. 지불자와 사용 목적은 별개다. 업무용 구독이라도 실제 회사 지원 여부를 추정하지 않는다.

## 5. 신한·카드·Naver Pay 대조와 중복 방지

09-13 설계 §5의 실제/예정/전망, 카드 사용/카드대금 납부, 이체, 반복 회차, 환불 계약을 그대로 따른다.

- **원판매자와 결제 경로를 분리한다.** Naver Pay라는 표시만으로 구매 상품·플랜·회사 목적을 확정하지 않는다.
- Naver Pay 구매, 카드 승인, 신한 카드대금 출금은 한 소비와 그 정산 사건일 수 있다. 세 건의 비용으로 합산하지 않는다.
- 신용카드 사용은 비용·미결제액을 늘리고, 카드대금 납부는 계좌 현금·미결제액을 줄인다. 납부를 새 비용으로 잡지 않는다.
- 체크카드는 연결 계좌의 즉시 출금으로 연결한다. 카드 종류·연결 계좌를 모르면 현금 반영을 확정하지 않는다.
- Naver Pay 잔액 **충전**은 보관 위치 간 이동으로 기록하고 실제 구매를 소비로 잡는다. 충전과 구매를 두 번 비용 처리하지 않는다.
- 포인트·잔액·카드의 혼합 결제는 수단별 배분액을 남긴다. 포인트와 충전 잔액의 성격을 모르면 같은 현금으로 계산하지 않는다.
- 휴대폰 결제는 구매 소비와 통신사 미정산액으로 기록한다. 통신 청구서는 기본 통신료·부가서비스/구독·기타·미분해 잔여로 대조하고, 연결된 구독을 청구 총액에서 분리한다. 청구 납부는 정산·실제 현금 사건으로 한 번 기록한다. 명세 미확인 시 통신비 전액과 구독료를 비용으로 중복 합산하지 않는다.
- 취소·환불은 원구매에 연결한다. 부분 취소액·관측일·수단별 환불·실제 정산 상태와 잔여 순소비·미결제액을 보존한다. 원구매를 삭제하거나 전액 취소로 치환하지 않는다. 카드 청구 감소, Naver 잔액 복원, 은행 환입을 구분하고 환급 완료를 추측하지 않는다.
- 한 거래의 여러 원본 근거는 삭제하지 않고 연결한다. 거래 날짜·승인 날짜·계좌 출금 날짜가 다를 수 있다.
- 출처의 주문/결제 ID와 관측·변경 이벤트 ID(또는 버전·시각)를 구분한다. 같은 이벤트·배치/행 재시도만 멱등 처리하고, 같은 주문의 새 취소·상태 관측은 원구매에 연결한다. 날짜·금액·설명만 비슷하면 중복 **후보**이며 자동 삭제하지 않는다.
- 외화 원본 금액과 카드/은행에서 확인된 KRW 결제액을 보존한다. 환산 근거가 없으면 임의 환율로 합계에 넣지 않는다.

대조 상태는 `미연결 / 연결 후보 / 확인됨 / 확인 보류`를 권장한다. 연결 실패나 날짜 경과만으로 소비 완료·결제 완료·구독 유지 상태를 바꾸지 않는다.

계좌 잔액은 기준일 이후 확인된 실제 현금 사건만 반영한다. 구독 회차와 연결 카드대금 예정이 함께 있을 때 계좌 예상 유출에는 카드대금만 포함한다. 잔액 미등록을 0원으로 표시하지 않는다.

## 6. 회사 소비·청구·환급 비교

“회사 청구”가 회사에서 직접 낸 비용인지, 운영자가 선결제한 뒤 회사에 비용 처리하는 흐름인지, 별도 공식 청구 내역인지 아직 미확인이다. 아래 구조는 가능한 흐름을 보존하는 권장안이며 회사 정책을 확정한 것이 아니다.

사용 목적, 실제 지불자, 청구 상태, 실제 회수 상태를 각각 기록한다. 한 소비를 개인 기록과 회사 기록에 복제하지 않고 목적 배분과 청구 연결로 비교한다.

청구 상태는 `미확인 / 준비 / 제출 / 승인 / 일부 승인 / 반려 / 보류`, 회수 상태는 `예정 없음 / 예정 / 일부 회수 / 회수 완료`를 권장한다. 실제 회사 용어·요건을 확인한 뒤 고정한다.

| 비교 값 | 의미 |
|---|---|
| 원구매 금액·순소비 | 순소비 = 원구매 금액 − 확인된 취소/환불액. 회사 청구 여부와 별개 |
| 회사 관련 사용액 | 운영자가 확인한 회사업무 목적 배분 |
| 제출액·승인액 | 회사가 받을/승인한 것으로 확인된 각각의 금액 |
| 실제 회수액 | 입금 또는 확인된 정산 근거로 원비용에 연결된 금액 |
| 개인 현금 실부담 | 개인의 최초 지급 배분액 − 그 배분에 실제 반환된 환불 − 확인된 회사 정산액. 포인트 사용액은 별도 표시 |
| 남은 회수액 | 승인액에서 확인된 회수액을 뺀 잔여. 미승인 신청액과 구분 |

회사가 직접 지불한 비용은 사용 목적 비교에는 보일 수 있으나 개인 계좌 출금으로 만들지 않는다. 개인 선결제 환급은 비용 회수이며 급여·개인 매출로 합산하지 않는다.

부분 환급·일괄 입금은 비용별 배분을 확인한다. 과다 회수·연결되지 않은 입금은 확인 대상으로 남긴다. 신청만 했거나 승인됐다는 이유로 실제 입금이나 개인 부담 감소를 확정하지 않는다.

순소비를 계산의 시작값으로 삼을 때 이미 차감한 환불을 재차 빼지 않는다. 잔액 충전과 소비 지급 배분도 중복 차감하지 않는다. 과다 회수의 음수 잔여를 0으로 숨기지 않고 확인 대상으로 표시한다.

예정 현금 유입에는 등록된 금액·날짜와 미정산 잔여만 반영한다. 날짜 미정/기한 경과 항목을 다음 달 수입에 임의 배치하지 않는다. 금융 원문은 ClassIn에 자동 전송하지 않는다.

## 7. 사용 기록과 CFO 검토

사용은 결제 내역에서 추론할 수 없다. 공급자 이용량 화면, 운영자 직접 기록, 필요한 경우 확인된 로컬 기록에서 기간별 근거를 받는다. 상품마다 비교 가능한 단위가 달라 횟수·시간·완료 결과를 억지로 하나의 점수로 만들지 않는다.

- 사용 근거가 없으면 `사용 미확인`이다. 조회한 내역에 없다는 사실은 미사용·이용 0회·해지 완료를 뜻하지 않는다.
- 구독 기간, 금액의 기준 기간, 사용 근거의 관측 기간을 함께 표시한다. 월/연간/할인 기간을 같은 기간으로 정규화할 때 전제를 적는다.
- 공급자 약정액과 실제 결제액의 차이는 확인 대상으로 남긴다. 실제 API 사용액·추정 API 비용·구독료를 무료나 한 비용처럼 합치지 않는다.
- 첫 확인은 운영자의 사용 목적·최근 사용 근거·계속 쓸 이유를 짧게 받는 것으로 시작한다. 상세 자동 이용량 수집은 연결 가능성과 실제 필요 확인 뒤다.

리피아(`leafeon`, CFO)는 같은 기간의 현금 지출, 첫 기간/이후 설정·유지 부담, 실제 사용 근거를 검토한다. 자료가 없는 비용이나 절감 시간을 0으로 채우지 않고, 예상 시간 절감을 현금 이익으로 바꾸지 않는다.

Office 결과는 `유지 / 축소 검토 / 해지 검토 / 추가 확인`과 근거·가정·재검토 조건을 권장한다. 운영자가 실제 결정하기 전에는 계약 상태나 계획 금액이 바뀌지 않는다.

Office는 도구 없이 판단·초안·검토만 맡는다. 조회·파일 정리·자료 변환은 운영자 Mac의 Codex/Claude Code가 해당 요청 범위에서 수행한다. Moonlight는 확인된 기록·요청서·receipt를 보관한다. 어느 계층도 자동으로 회사 제출·결제·해지·외부 발송을 하지 않는다.

## 8. 수집과 확인 단계

1. **계약 목록 시작:** 위 자술 원문과 각 계약을 보존한다. 미확인 금액·주기·계정은 빈칸과 이유로 남긴다.
2. **현재 자료 조회:** 이번에는 2026-07-01~10-05의 Naver Pay 전체 결제내역과 신한 카드 내역을 병렬로 읽는다. 카드의 승인월과 명세서 청구월은 구분한다. 로그인은 운영자가 수행하며 은행 비밀번호나 전체 카드번호를 요구하지 않는다.
3. **관측 요약:** 출처·필터·조회 기간·최신/오래된 확인 날짜·읽은 페이지/범위·누락을 함께 남긴다. 검색한 결제만 본 것인지 전체 기간을 읽은 것인지 구분한다.
4. **후보 대조:** 원판매자·금액·상품·날짜·결제 수단 근거로 계약/소비/정산 연결 후보를 만든다. 구매가 확인돼도 반복 주기·플랜이 확인된 것은 아니다.
5. **확인·반영:** 계약 가격과 실제 회차의 차이, 중복 후보, 통화, 회사 목적/청구 여부를 검토 가능한 목록으로 제시하고 확인된 항목만 금융 장부에 반영한다.
6. **기간별 검토:** 같은 기간의 실제 비용·계획·회수·사용 근거를 재조회하고 CFO 검토로 이어 간다. 검토 주기와 알림은 실제 사용 후 정한다.

직접 입력과 Excel/CSV를 우선 지원하는 기존 방향은 유지한다. 파일은 열 매핑→형식/부호/통화 검증→중복 후보→반영 결과로 처리한다. 원본 행/배치 재시도, 제외 사유, 미변경 행의 가져오기 되돌리기를 보존한다. 은행별 양식을 이미 지원한다고 약속하지 않는다.

이번 Naver Pay 조회는 현재 열려 있는 자료의 정리 요청이다. 백그라운드 은행 연결·정기 브라우저 수집·자동화를 활성화하는 승인으로 확대하지 않는다.

연결은 단계적으로 추진한다. 1단계는 계약 직접 입력·명세서/영수증 가져오기와 대조, 2단계는 회사 청구·실제 회수 및 사용 근거, 3단계는 휴대폰 결제 알림을 수집 후보로 받는 전용 금융 intake와 실기 확인이다. 현재 `phone-events`는 CRM용이므로 금융 알림 지원으로 간주하지 않는다. 은행/집계 API는 이용 조건·권한·필요성이 확인된 뒤 별도 연결한다. MCP는 수집된 장부를 로컬 에이전트가 읽는 인터페이스이며 은행 조회 권한을 대신하지 않는다.

## 9. 관측 범위·개인정보·오류 계약

원본 주문번호·계좌/카드번호·배송지·연락처·상세 금융 거래·영수증 이미지는 Git 기획 문서나 테스트에 복사하지 않는다. 이 문서에는 설계만 남긴다. 사용자 자술 가격과 초기 계약 목록도 비공개 금융 장부에 남긴다. 실제 조회 결과는 비공개 작업 산출물과 접근이 통제된 운영 기록으로 분리한다.

화면에 보이는 일부 이력의 합계는 `관측한 기간/범위의 결제 합계`다. 취소·환불·다른 결제 채널·카드대금·포인트가 미확인인 합계를 전체 순지출이나 월 고정비로 부르지 않는다.

자료를 읽지 못한 경우와 읽었으나 항목이 없는 경우를 구분한다. 일부 조회는 빠진 출처와 범위를 표시하고, 빈 결과로 구독 없음·미사용을 단정하지 않는다. 값의 자술/확인/추정과 갱신 시각을 보존한다.

구현 시 Hub read는 repository와 HTTP 200 `status: error` 봉투를 따른다. 쓰기는 guard·server-write, workspace 검증, 중복 제출 키, 수정 시각 기반 충돌 검사를 적용한다. 이체·분할·정산은 원자적으로 연결한다. 저장 실패 시 입력을 유지하고 성공처럼 잔액을 바꾸지 않는다.

## 10. 검수 기준과 남은 범위

다음은 구현 검수에 사용할 요구이며 이번 문서에서 실행한 테스트 결과가 아니다.

- Claude Pro/Max를 별도 계약으로 유지하고 미확인 가격·주기를 만들지 않는다.
- Gemini/Grok의 자술 주기를 임의 월 금액으로 바꾸지 않고, 실제 결제를 향후 약정액으로 자동 복제하지 않는다.
- Naver 구매·카드 승인·신한 대금 출금이 한 비용/현금 흐름으로 연결된다.
- 잔액 충전/사용, 혼합 결제, 취소/환불이 중복 집계되지 않는다.
- 휴대폰 구독·통신사 합산 청구·카드/은행 납부가 연결되며 같은 소비를 다시 더하지 않는다.
- 같은 주문의 부분 취소 갱신을 놓치지 않고, 순소비와 개인 현금 부담에서 환불을 한 번씩만 반영한다.
- 회사 목적·지불자·신청·승인·실제 회수가 구분되고 부분 회수/일괄 입금의 배분이 유지된다.
- 회사 직접 지불과 개인 선결제 환급을 구분하며 실제 개인 부담·은행 잔액을 대사할 수 있다.
- 같은 파일/요청 재시도·중복 후보·stale 수정·저장/읽기 실패 후에도 원문과 확인 상태가 보존된다.
- 사용 미확인과 이용 0회가 다르고, 조회 기간/범위 밖 비용을 전체 고정비에 넣지 않는다.
- 금융 장부와 개인 매출 전망을 각각 열 수 있고, 개인 금융이 ClassIn 회사 기록에 복제되지 않는다.

남은 확인은 실제 청구 주기·통화/플랜, 신한 계좌/카드 구성, 회사 청구의 뜻·정책/양식, 이용 근거 취득 방식, 통신비, 검토 주기다. 자료로 확인 가능한 것은 먼저 확인하며 일반 업무 인터뷰를 재개하지 않는다.

09-13 첫 버전 범위(계좌/이체·카드/할부/대출/반복 지출·파일 가져오기·매출 수금 연결)는 여전히 전체 완료 전이다. 이번 구독·회사 청구 기획이나 부분 구현을 그 전체 범위의 완성이라고 부르지 않는다. 자동 금융 연결, 자동 해지/결제/회사 제출, 세무 신고·복식부기는 별도 후속 범위다.

최초 작성은 기획 문서와 지도만 다뤘다. 2026-10-05 운영자 `진행` 승인으로 수집 자료 등록과 검토 UI 첫 버전을 구현한다. 현재 지원·가져오기·후속 범위는 [개인 금융 원장 운영 가이드](../../guides/personal-finance-ledger.md)를 따른다. 전체 금융 기획의 완료를 뜻하지 않는다.
