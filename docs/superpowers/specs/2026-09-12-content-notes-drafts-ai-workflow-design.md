## 0. 2026-09-12 구현 범위

운영자의 “고고”에 따라 [구현 계획](../plans/2026-09-12-content-workflow.md)의 콘텐츠 제작 범위를 적용했다.

- Studio에서 원문 메모·기획 제목·결과물 제목을 분리한다. 기획 카드의 대상/목적/메시지/관점/근거/마무리와 다음 행동/막힌 이유를 저장한다.
- Threads·X·블로그·뉴스레터 텍스트, Instagram 카드, Shorts/Reels 장면 대본을 편집한다. 같은 콘텐츠에 여러 결과물을 추가하고 정확한 결과물로 돌아간다.
- 원문에서 초안 작성, 다듬기, 줄이기, 도입부 3안, 채널 변형을 제공한다. 후보를 비교하고 명시적으로 적용한다. 변경된 원문·기획에 오래된 후보를 적용할 수 없다.
- 저장/적용/복원을 원자 RPC로 처리하고 중복 요청을 기록한다. 직접 저장·AI 적용·파생 시 버전을 남긴다. 복사는 결과물만 포함한다.
- 새 DB 마이그레이션은 `20260912_0026_content_workflow.sql`이다. **운영 배포 전에 적용해야 한다.** 로컬 PostgreSQL과 로컬 Hub→Engine 연결로 검증하며 AI 응답은 테스트용 공급자를 사용한다.

일지 신설·메모 여러 건 묶기·기간 회고·콘텐츠 자동 크론 F-0 수리·외부 직접 발행은 이번 구현에 포함하지 않았다. 아래 나머지 절은 이 후속 방향까지 포함한 설계이므로, 모든 항목을 구현 완료로 해석하지 않는다.

## 1. 제안의 중심

**기록한 생각을 다시 꺼내, 전달할 메시지를 정하고, 여러 형식으로 완성하는 흐름을 만든다.**

```text
메모·일지·참고 자료
  → 쓸 부분 선택
  → 콘텐츠 기획 카드
  → 기준 초안
  → Threads / Instagram 카드뉴스 / Shorts 대본
  → 비교·수정·채택
  → 복사·내보내기·발행 기록
  → 다음 제작 때 재사용
```

메모는 공개할 필요가 없는 원문이고, 콘텐츠는 전달하려고 선택한 메시지다. 초안은 그 메시지를 표현한 버전이며, AI 변형은 새 후보를 만든다. 사용자가 원문을 다시 찾아 수정하거나 다른 관점으로 재사용할 수 있도록 관계를 남긴다.

운영자 프로필에서 확인되는 우선순위는 **무엇을 만들지 결정하는 부담**, 실제 제작, 다듬기 순서다. 따라서 첫 성과는 생성 개수가 아니라 “저장한 생각 하나를 실제로 쓸 수 있는 초안으로 끝내는가”로 본다.

## 2. 구현 전 코드에서 확인한 공백

아래는 구현 착수 전 기준의 **정적 코드 조사 기록**이다. §0에 구현한 사항도 당시 배경을 보존하기 위해 남긴다. 링크는 저장소 루트 기준 상대 경로다.

| 확인한 현재 상태 | 사용자에게 생기는 문제 | 기획에 반영할 일 |
|---|---|---|
| [Studio](../../../apps/hub/components/hub/pages/content.jsx)의 `applyToolbarAction('ai')`는 미연결 안내를 추가한다 | AI 버튼으로 초안 수정·변형을 할 수 없음 | 구체적인 작업 종류와 실행·결과 반영 계약 |
| 같은 파일의 편집 모드는 `blog`와 `carousel`이다. 다른 variant는 Blog 임시 표시 안내가 있다 | 주력인 Threads와 Shorts 작업을 해당 형식으로 이어가기 어려움 | Threads 편집을 먼저 추가하고, 대본 편집을 후속으로 확장 |
| `saveDraft`는 `sourceIdea: title`을 보내고 [저장 빌더](../../../apps/hub/lib/repositories/content-ledger.js)의 update는 `source_idea`를 다시 쓴다 | 제목을 바꾸는 경로에서 처음 생각과 제목이 섞임 | 원문·기획 제목·결과물 제목을 분리하고 미지정 원문은 유지 |
| [variant 매핑](../../../apps/hub/lib/repositories/content-ledger.js)은 `row.channel` 대신 타입으로 채널을 유도한다. `x_thread`는 X로 표시된다 | Threads와 X, Reels와 Shorts를 형식만으로 구별할 수 없음 | 저장된 채널을 우선하고 형식과 채널을 독립 선택 |
| Studio 진입은 `item`을 받고 첫 variant를 고른다. 로컬 mirror는 `item:<id>` / `active` 단위다 | 여러 결과물을 만들 때 정확한 버전으로 복귀할 계약이 부족함 | variant 딥링크·선택기·variant별 복구 키 |
| [콘텐츠 명령](../../../apps/engine/lib/content-command.ts)은 create/update draft, handoff, campaign을 지원한다. [실행 서비스](../../../apps/engine/lib/content-command-service.ts)는 중복 부모가 있는 create도 처리한다 | 내부 재사용 기반은 있으나, 화면에서 “기존 원본에 파생본 추가”를 명확히 실행하는 계약은 없음 | 기존 부모 검증을 포함한 파생본 생성 동작 명시 |
| draft update는 item·variant의 `meta`를 새 객체로 만들고 두 레코드를 순차 수정한다 | 기획·출처를 meta에 붙이기만 하면 후속 저장에서 사라지거나 반쪽 저장될 수 있음 | 선택 필드 갱신·meta 보존·필요한 원자 저장 |
| [콘텐츠 크론](../../../apps/hub/app/api/cron/content-flywheel/route.js)은 `content-draft`와 `title/body`를 기대한다. [Engine](../../../apps/engine/app/api/ai/brand-mentor/route.ts)의 모드 목록에는 그 모드가 없고 자문용 응답 경로다 | 자동 초안의 요청·응답 계약이 맞지 않음 | 기존 F-0 수리와 새 생성 기능이 같은 결과 계약을 사용 |
| 저장소의 `apps`, `packages`, `supabase/migrations` 검색에서 `journal_entries` 구현은 발견되지 않았다 | 9월 5일 일지 기획을 이미 구현된 기능으로 가정할 수 없음 | 일지 기반 작업을 별도 선행 단계로 표시 |

Supabase 원장, Studio 저장·로컬 복구, 브랜드 보이스, 승인 큐, Gemini 호출 helper는 재사용할 자산이다. 다만 이것만으로 AI 제작 흐름이 완성됐다고 판단하지 않는다.

## 3. 접근안 비교

| 접근안 | 장점 | 부담 | 판단 |
|---|---|---|---|
| **B. 원문→기획→초안→파생을 단계별 연결** | 선택과 제작의 부담을 함께 줄이고 기존 원장을 재사용 | 출처·버전·채널 계약을 먼저 정리해야 함 | **권장** |
| A. Studio에 요약·재작성 버튼부터 추가 | 좁은 범위로 효과를 빨리 볼 수 있음 | 메모를 찾고 맥락을 다시 입력하는 부담이 남음 | B의 첫 AI 단계로 포함 |
| C. 모든 메모를 읽어 콘텐츠를 자동 생산 | 장기적으로 반복 생성에 유리 | 비용·후보 범람·중복·개인 메모 혼입을 다뤄야 함 | 초기 범위에서 제외 |

아래 내용은 B를 채택할 경우의 구체적인 권장 사양이다. 모든 기능을 한 번에 구현하는 계획이 아니다.

## 4. 메모와 소재: 저장은 짧게, 선택은 나중에

### 4.1 빠른 기록

- 자유 메모는 일지의 단일 타임라인에 저장한다. 기존 프로젝트 `notes`는 프로젝트 노트로 유지한다.
- 저장 필수값은 본문 하나로 제안한다. 제목·브랜드·채널·태그를 비워도 저장한다. 이는 기존 프로필의 아이디어 입력 4항목을 모두 필수로 만들지 않기 위한 **새 권장안**이다.
- 날짜는 기본 오늘이며 변경할 수 있다. 참고 링크·떠오른 이유는 펼쳐 입력한다.
- `기록만 저장`과 `콘텐츠로 이어쓰기`를 제공한다. 전자는 AI를 호출하지 않는다.
- 직접 작성·붙여넣기·md/txt 임포트 범위는 9월 5일 확정 결정을 따른다. 임포트의 분할 미리보기와 중복 판정은 그 문서의 구현 검토 과제다.

### 4.2 메모에서 콘텐츠로

사용자가 메모 전체 또는 일부를 선택하고 `소재로 쓰기`를 누른다.

| 저장할 정보 | 의미 |
|---|---|
| 선택한 원문 | 이번 콘텐츠에 사용할 정확한 문장 |
| 출처 종류·ID·기준 수정 시각 | 어떤 기록의 어느 시점에서 가져왔는가 |
| 참고 링크 | 외부 원문으로 돌아갈 경로 |
| 쓰려는 이유 | 왜 이 문장이 콘텐츠가 될 수 있는가. 선택 입력 |
| 관련 콘텐츠 | 이미 어떤 초안에 사용했는가 |

원문은 복사 이동으로 없애지 않는다. 한 메모에서 여러 콘텐츠를 만들고, 한 콘텐츠에 여러 메모를 연결할 수 있다. 사용한 메모도 다시 쓸 수 있으며 `사용됨` 표시는 잠금이 아니다.

명시적으로 `소재로 쓰기`를 누르면 내부 기획 카드를 바로 만들 수 있다. 반면 AI가 기간 기록을 훑어 발견한 소재는 기존 `work_orders`의 제안으로 넣고, 사용자가 골랐을 때 콘텐츠가 된다. 두 경로를 같은 이중 승인 절차로 만들지 않는다.

### 4.3 여러 메모를 묶기 — 후속

선택한 메모 2~5건에 대해 `한 주제로 묶기`를 실행한다. 결과는 주제 후보 최대 3개, 각 후보의 근거 문장, 더 필요한 자료다. 단순히 같은 단어가 있다는 이유로 사실이나 인과관계를 합치지 않는다. 초기에는 운영자가 직접 선택하고, 전체 기록 자동 검색은 후속으로 둔다.

## 5. 기획 카드: 초안을 쓰기 전에 정할 것

기획 카드는 콘텐츠 원본에 속한다. 결과물마다 같은 내용을 다시 입력하지 않는다.

| 항목 | 입력 예시 | 입력 원칙 |
|---|---|---|
| 누구에게 | 수업 후 복습 설계가 어려운 강사 | 생성 시 권장, 저장 필수 아님 |
| 읽고 무엇을 얻나 | 다음 수업에서 쓸 질문 하나 | 공감 / 이해 / 행동 / 문의 중 선택 가능 |
| 핵심 한 문장 | 도구 설명보다 복습 행동을 먼저 설계하자 | 원문에서 AI가 제안하되 사용자가 고침 |
| 관점 | 경험담 / 문제 해결 / 비교 / 질문 | 한 번에 하나 선택 |
| 근거·사례 | 선택한 메모와 참고 문장 | 없으면 `근거 보강 필요` |
| 마무리 | 질문 / 실천 제안 / CTA 없음 | 모든 글에 영업 CTA를 강제하지 않음 |
| 브랜드 | 운영자가 선택한 브랜드 | 보이스·금지어·작성 예시를 읽어옴 |
| 분량·형식 | 짧은 글 / 카드뉴스 6장 / 60초 대본 | 제품 프리셋이며 플랫폼 한도로 단정하지 않음 |

`기획 제안 받기`는 최대 3개의 **관점**을 제시한다. 예를 들어 같은 메모에서 경험담, 체크리스트, 흔한 오해를 풀어주는 글을 제안하고 차이를 한 줄씩 설명한다. 세 가지 제목만 바꾼 사실상 같은 초안은 비교 가치가 낮다.

기획 카드가 비어 있어도 손으로 글을 쓸 수 있다. AI 생성 시 비어 있는 항목은 적용할 기본값을 보여주고, 누락된 사실을 지어내서 메우지 않는다.

## 6. 초안 작업대: 이어쓰기와 마무리를 돕기

기존 Studio를 사용하며, 항상 보이는 요소는 제목·본문·선택한 결과물·저장 상태다. 소재와 기획 카드는 접어서 열 수 있게 둔다.

- `기준 초안`: 현재 제작의 기준으로 지정한 variant. 별도의 master 문서 테이블을 추가하지 않는다.
- `다음에 할 일`: “도입부 다듬기”, “사례 한 문장 추가”, “촬영” 같은 한 줄. 콘텐츠를 닫았다가 돌아왔을 때 작업 위치를 알려준다.
- `막힌 이유`: 방향 미정 / 근거 부족 / 작성 중 / 촬영·디자인 필요. 필요한 경우에만 기록한다.
- `이어서 쓰기`: 해당 variant와 마지막 편집 위치로 돌아간다.
- `사용한 소재`: 원문과 선택 구간을 확인한다.
- `버전 기록`: AI 채택 직전·채택 후, 명시적 버전 저장, 내보내기 시점의 내용을 복원한다. 키 입력마다 장기 스냅샷을 만들지는 않는다.

큐에서는 `지금 고른 것`, `이어서 쓸 초안`, `마무리할 것`, `전체` 렌즈를 제안한다. 초기 선택은 수동 핀과 최근 수정 기준이다. 임의의 “바이럴 점수”나 근거 없는 제작 시간은 표시하지 않는다.

## 7. AI 변형: 버튼마다 입력과 결과를 고정

| 작업 | 사용자가 고르는 것 | 결과 | 적용 범위 | 단계 |
|---|---|---|---|---|
| **문장 다듬기** | 문장·문단 + 원하는 톤 | 의미를 유지한 수정안 1개 + 변경 요약 | 선택 구간 | 첫 AI |
| **더 짧게** | 선택 문단 + 짧게/절반 정도 | 축약안 1개 + 빠진 핵심 여부 | 선택 구간 | 첫 AI |
| **도입부 3안** | 현재 초안 + 기획 카드 | 질문형 / 장면형 / 주장형 도입 | 채택한 도입부만 | 첫 AI |
| **개요→초안** | 기획 카드 + 선택한 소재 | 제목·본문·근거 부족 목록 | 새 draft variant | 첫 AI |
| **관점 바꾸기** | 경험담/비교/체크리스트 등 | 같은 근거를 다른 구조로 구성 | 새 후보 | 후속 |
| **채널로 바꾸기** | 원본 버전 + 채널 + 형식 | 채널에 맞는 구조화 결과물 | 새 파생 variant | 채널 확장 |
| **빈 부분 찾기** | 초안 전체 | 모호한 주장·빠진 근거·확인 질문 최대 3개 | 검토 메모 | 후속 |
| **여러 메모 엮기** | 선택한 2~5건 | 관점 후보 + 근거 연결 | 기획 후보 | 메모 확장 |
| **내 톤으로** | 브랜드 + 운영자가 고른 작성 예시 | 해당 표현 습관을 반영한 후보 | 선택 구간/새 버전 | 개인화 |

`문장 다듬기`와 `관점 바꾸기`는 다른 동작이다. 전자는 의미를 유지하고, 후자는 논점의 배열을 바꾼다. 원문에 없던 수치·고객 후기·경험을 추가하는 것은 어느 동작에서도 허용하지 않는다. 설명을 위해 만든 가상 사례는 가상임을 드러낸다.

### 7.1 실행 흐름

1. 사용자가 구간 또는 원본 variant를 선택한다.
2. 작업·브랜드·채널·분량을 고른다. 기본은 후보 1개, 비교가 필요한 도입부만 3개다.
3. `사용할 자료`에 선택 원문, 기획 카드, 브랜드 규칙, 선택한 작성 예시를 보여준다.
4. `생성` 후 후보와 원문을 비교한다. 작업을 진행하는 동안 현재 편집을 계속할 수 있다.
5. `선택 부분에 적용`, `새 버전으로 저장`, `버리기`, `다시 요청` 중 고른다.
6. 적용 직전 기준 버전이 바뀌었으면 자동 덮어쓰기를 멈추고 비교 화면을 유지한다.

선택 문장 수정은 변경 전후 비교, 채널 변환은 결과물 미리보기가 적합하다. AI 결과를 닫으면 원래 글은 바뀌지 않는다. 적용 취소는 이전 내용을 새 복원 버전으로 저장해 이후 이력을 지우지 않는다.

### 7.2 결과를 믿고 고를 수 있게

결과 카드에는 결과물, 바뀐 점, 사용한 근거, 더 확인할 내용을 보여준다. 근거 표시는 “검증 완료” 판정이 아니라 원문으로 돌아가는 연결이다. 원문에 없는 사실의 진위를 모델이 스스로 보증하게 하지 않는다.

참고한 UX 패턴: Notion은 선택한 텍스트의 AI 편집 결과를 채택·폐기·재시도하는 흐름을 제공한다. Moonlight에는 선택 범위 보존과 채택 전 비교를 적용할 것을 제안한다. [Notion 공식 가이드](https://www.notion.com/help/guides/notion-ai-for-docs)

Google의 Notebook 도움말은 사용할 소스를 선택하고 인용 위치로 돌아가는 동작을 설명한다. Moonlight에는 “어떤 메모를 사용했는가”를 직접 확인하는 방식으로 적용할 것을 제안한다. [Google 공식 도움말](https://support.google.com/gemininotebook/answer/16179559)

## 8. 채널별 결과물

**저장 형식과 게시 채널을 별도 값으로 관리한다.** 기존 타입은 호환성을 유지하되 사용자에게는 실제 채널명을 보여준다.

| 채널 | 초기 저장 형식 | 결과물 구조 | 마무리 행동 |
|---|---|---|---|
| Threads | `x_thread` + `channel=threads` | 글 블록·도입·본문·마무리 질문 | 블록별/전체 복사, txt export |
| Instagram 카드뉴스 | `card_news` + `channel=instagram` | 표지→문제→핵심→예시→정리→마무리, 기본 6장 | 슬라이드 편집·미리보기, 기존 export 경로 검토 |
| YouTube Shorts | `reels_script` + `channel=youtube_shorts` | 훅·장면·대사·자막·촬영 메모·예상 길이 | 대본 복사·구조화 파일 export |
| 블로그 | `blog_insight` + `channel=blog` | 제목·소제목·본문·마무리 | 기존 편집과 미리보기 유지 |

`x_thread`를 내부 호환 타입으로 쓰더라도 Threads에 X 글자 제한을 자동 적용하지 않는다. 플랫폼 제한은 별도 최신 검증을 거쳐 채널 설정으로 제공한다. 6장·60초는 초기 작성 프리셋이며 실제 서비스 제한이나 완성 영상 길이를 보증하지 않는다.

한 원본에서 세 채널을 선택하면 독립된 파생본 세 개가 생긴다. 일부 생성이 실패하면 성공 결과는 남기고 실패한 채널만 다시 요청한다. 원본을 수정했다고 이미 만든 파생본을 자동 갱신하지 않고 `원본 변경됨`을 표시한다.

브랜드는 현재 `content_items.brand_id`가 소유한다. 다른 브랜드 버전을 만들 때는 원본 참조를 가진 별도 content item으로 분기하는 것을 권장한다. 한 파생본의 브랜드를 바꾸려다 다른 모든 결과물의 브랜드까지 바뀌는 일을 막는다.

발행 완료는 variant별로 기록한다. Threads 하나를 발행했다고 남은 카드뉴스·대본도 완료되지는 않는다. 복사·다운로드·handoff는 실제 발행과 구별한다. 초기 완료 기록은 사용자가 발행 채널·일시·URL 또는 URL 없음 사유를 남기는 방식으로 제안한다.

## 9. 실제 사용 예시

아래는 동작 설명용 가상 메모다. 실제 고객 발언이나 검증된 성과 사례가 아니다.

> 수업 도구 설명보다 수업 후 학생이 무엇을 다시 하게 만들지가 더 중요하다는 생각. 복습 질문 하나를 먼저 정해보면 어떨까.

1. **저장:** 제목 없이 메모를 남긴다. 저장 시 AI를 호출하지 않는다.
2. **소재 선택:** 해당 문장을 골라 콘텐츠로 이어쓴다. 원문 링크가 붙는다.
3. **기획:** 독자는 강사, 목적은 다음 수업에서 질문 하나를 바꾸게 하는 것, 관점은 실천 체크리스트로 정한다.
4. **초안:** Threads 글 초안을 만들고, 제시된 도입부 세 개 중 하나만 채택한다.
5. **수정:** 가운데 문단을 선택해 `더 짧게`를 적용한다. 선택하지 않은 문장은 그대로다.
6. **파생:** 카드뉴스를 요청하면 슬라이드별 문구 후보, Shorts를 요청하면 장면별 대본 후보가 생긴다.
7. **중단·복귀:** 촬영이 필요한 대본에 `촬영·디자인 필요`와 다음 행동을 남긴다. 다음 진입 시 그 대본이 열린다.
8. **발행 기록:** Threads 글을 복사해 게시한 뒤 그 결과물의 URL을 기록한다. 카드뉴스와 대본은 초안으로 남는다.

## 10. 데이터·저장 계약 초안

### 10.1 객체 역할

| 객체 | 소유하는 것 | 기존/제안 |
|---|---|---|
| `journal_entries` | 일지 원문·날짜·태그·요약 | 9월 5일 제안, 현재 구현 확인 안 됨 |
| `notes` | 프로젝트에 속한 작업 노트 | 기존 유지 |
| `content_items` | 콘텐츠 주제·선택한 소재·기획 카드·소유 브랜드 | 기존 확장 |
| `content_variants` | 편집 가능한 채널별 초안·형식·발행 상태 | 기존 확장 |
| `content_revisions` | 채택·복원·내보내기 기준 시점의 불변 스냅샷 | 좁은 신규 테이블 제안 |
| 생성 요청 receipt | 중복 호출 방지·처리 상태·입력 해시·결과 참조 | 기존 receipt 패턴을 재사용하는 별도 계약 필요 |
| `agent_runs` | 모델 실행 요약·사용량·후보 결과 참조 | 기존 확장, 현재 helper의 필드 검토 필요 |
| `work_orders` | 사용자가 아직 선택하지 않은 AI 소재·할 일 제안, 외부 실행 승인 | 기존 재사용 |

기획 단계에서는 별도의 범용 메모 테이블·브랜드 템플릿 테이블·지식 그래프를 추가하지 않는다.

### 10.2 필요한 연결

- 콘텐츠 `meta.brief`: 독자·목적·핵심 메시지·관점·마무리.
- 콘텐츠 `meta.source_refs`: 종류·ID·선택 문장·기준 시각·해시·참고 URL. 선택하지 않은 원문까지 복제하지 않는다.
- 콘텐츠 `meta.primary_variant_id`: 기준 초안 ID. 없으면 가장 최근 수정된 활성 variant, 동률은 ID로 고른다.
- 파생본 `meta.parent_variant_id`, `meta.parent_revision_id`, `meta.transform`: 원본의 정확한 버전·변형 작업·설정·모델 실행 참조.
- 생성 시 읽은 브랜드 규칙의 버전 또는 해시를 남긴다. 나중에 브랜드 규칙이 바뀌어도 과거 생성 근거를 구별한다.
- 원문은 사용자 명시 수정만 허용한다. 출처가 수정되거나 사라지면 연결 상태를 표시하고, 기존 채택 버전을 자동 재작성하지 않는다.
- source refs·생성 로그·비공개 기획 카드는 외부 복사·export payload의 기본 포함 대상이 아니다. 결과물 본문과 필요한 산출물만 내보낸다.

`meta` 확장만으로 기능이 완성되지 않는다. 현행 read projection에 원문·기획·연결 필드를 포함하고, update에서 해당 필드를 지우지 않도록 쓰기 계약을 함께 고친다. 전문 검색이나 대량 연결이 필요해지면 source refs를 별도 관계 테이블로 옮길 수 있다.

### 10.3 지켜야 할 저장 동작

1. 제목 수정이 `source_idea`를 바꾸지 않는다. 요청에 없는 필드는 보존하고 명시적으로 비울 때만 지운다.
2. 채널 값은 저장→재조회→편집→복사 흐름에서 유지한다. 레거시 채널이 없을 때만 기존 타입 매핑을 fallback으로 쓴다.
3. 기존 content item에 파생본을 추가할 때 부모 존재·workspace·소유 브랜드를 검증한다.
4. AI 선택 구간 적용은 기준 revision·본문 해시·선택 구간을 검증한다. 반복되는 동일 문장을 단순 문자열 치환하지 않는다.
5. AI 채택은 후보 채택 표시·새 revision·variant 갱신을 원자적으로 처리한다. 결과가 부분 저장됐는데 적용 완료로 알리지 않는다.
6. 로컬 mirror는 workspace/content/variant별로 분리한다. 동일 variant가 다른 탭에서 바뀌면 비교로 복구한다.
7. 현재 편집 중인 본문에 오래된 생성 응답이나 autosave 응답이 도착해도 최신 입력을 덮지 않는다.
8. 기존 `item` 딥링크를 유지하고 `variant`를 추가한다. 잘못된 부모·variant 조합은 다른 초안을 대신 열지 않고 재선택하도록 안내한다.

현재 item 상태 enum은 당장 바꾸지 않는다. “이어서 쓰기” 등의 큐 렌즈는 상태값과 별개로 계산한다. variant별 발행 수와 남은 작업을 함께 표시하고, 부모의 현재 상태값을 전체 파생본의 발행 사실로 해석하지 않는다. 새 자동 상태 집계는 별도 구현 계약으로 검토한다.

## 11. AI 실행·오류·비용

### 11.1 동일한 생성 계약

수동 버튼과 기존 F-0 자동 초안 수리는 같은 구조화 결과 계약을 쓰도록 제안한다. 새 서비스는 원문과 선택 범위를 입력받아 **후보를 만드는 일**만 담당한다. 기존 `brand-mentor` 자문 모드를 조용히 다른 목적으로 재사용하지 않는다.

| 요청 요소 | 결과 요소 |
|---|---|
| request ID, 작업, source refs, 기준 revision/hash | run ID, 입력 기준, 후보 ID |
| 선택 범위, 기획 카드, 브랜드, 채널, 형식, 분량 | 제목·본문 또는 blocks/slides/scenes |
| 운영자가 선택한 작성 예시 | 변경 요약·근거 연결·확인 필요 항목 |
| 후보 개수, 명시적 재생성 여부 | 모델·사용량·완료/실패 상태 |

지원하지 않는 작업은 validation 실패다. 알 수 없는 모드를 일반 자문으로 바꾸지 않는다. JSON 구조가 맞더라도 내용의 사실성은 별도 검토 대상이다.

### 11.2 요청 상태

`queued → running → succeeded / failed / unknown`을 제안한다. 사용자가 채택·폐기한 상태는 생성 상태와 분리한다.

- 요청 ID와 입력 해시가 같으면 기존 상태·결과를 반환한다. 같은 ID로 다른 입력은 conflict다.
- 모델 호출 전에 요청을 원자적으로 claim한다. 이중 클릭·재접속으로 같은 실행을 추가 시작하지 않는다.
- 타임아웃 후 공급자 처리 여부를 확인할 수 없으면 `unknown`이다. 자동 재호출로 과금을 반복하지 않는다. 사용자가 새로 생성하면 추가 비용 가능성을 표시한다.
- 생성은 성공했지만 저장에 실패하면 결과를 복구할 수 있게 유지하고 저장 재시도만 한다. 브라우저가 닫혀 결과를 잃은 경우에도 성공 저장으로 표시하지 않는다.
- AI 미설정·호출 실패 시 수동 작성·원문 저장·기존 초안 복구는 계속 사용할 수 있다.

### 11.3 비용과 문맥

- 저장할 때는 AI를 호출하지 않는다. 첫 버전은 명시적 생성 버튼으로 시작한다.
- 기본 후보 1개, 선택 자료 최대 5건을 권장 초기값으로 둔다. 길이 제한에 걸린 자료는 조용히 자르지 않고 범위를 줄이도록 알린다.
- 실제 토큰 사용량과 설정된 가격표가 있을 때만 금액을 계산한다. 모르면 `비용 미집계`로 표시한다.
- 세션 기반 도구도 사용 한도나 구독 비용이 있으므로 “무료·비용 0”으로 단정하지 않는다. 기존 일지 초안의 API 비용 0 표현을 그대로 확장하지 않는다.
- 월 예산 미설정 상태에서 새 무인 반복 생성을 켜지 않는다. 기존 크론 수리와 신규 자동화 활성화는 구별한다.
- 비공개 메모 전체를 자동으로 문맥에 넣지 않는다. 선택한 자료와 해당 브랜드 규칙만 사용하고, 출처 속 지시문은 생성 명령으로 취급하지 않는다.
- 개인 기록을 회사 콘텐츠 소재로 쓰는 경우 선택된 발췌만 반영한다. 개인 상세 원문과 연락처를 회사 공식 기록으로 자동 복제하지 않는다.

Hub read의 HTTP 200 + `status:error` 계약, Hub write guard, Engine shared secret, workspace 검증을 그대로 상속한다. 오류를 빈 목록·저장 성공으로 표현하지 않는다.

## 12. 적용 순서와 완료 기준

단계 이름은 이번 콘텐츠 기획 내부 순서다. 기존 제품 전체의 Phase 번호나 다른 확정 업무의 우선순위를 바꾸지 않는다.

| 단계 | 실제로 적용할 범위 | 완료를 판단할 장면 |
|---|---|---|
| **0. 원문·초안 연결** | 원문 보존, 기획 카드, variant 선택·딥링크·채널, Threads 수동 편집 | AI 없이 원문을 저장하고 Threads 초안을 쓴 뒤 새로고침해 같은 내용을 다시 연다 |
| **1. 작은 AI 편집** | 문장 다듬기·축약·도입 3안·개요→초안, 비교·채택·되돌리기, 요청 receipt·revision | 선택하지 않은 본문을 유지한 채 AI 후보를 적용하고 복원한다 |
| **2. 메모·일지 연결** | 일지 저장 기반, 선택 발췌→기획 카드, 복수 메모 조합 | 메모 2건에서 콘텐츠 1건을 만들고 두 출처로 돌아간다 |
| **3. 채널 파생** | 카드뉴스·Shorts 구조화 변형·미리보기·부분 실패 복구 | 동일 원본에서 결과물 3개가 독립 저장되고 원본 변경도 추적된다 |
| **4. 재사용 개선** | 승인한 작성 예시, 재사용한 소재 보기, 묵힌 초안 재개, 기간 회고 연결 | 반복 프롬프트 입력 없이 자기 톤을 적용하고 중단했던 초안을 다시 완성한다 |

단계 0은 일지 구현을 기다리지 않고 콘텐츠 원문 직접 입력으로 시작할 수 있다. 단계 2의 일지 기반은 9월 5일 스펙의 미확정 세부사항을 정리한 뒤 진행한다. 기존 F-0 크론 계약·실패 가시성 수리는 관련 과제로 유지하고, 단계 1 생성 계약과 중복 설계하지 않는다.

각 단계는 독립 구현 계획으로 나눈다. 채널 전체 자동 발행, 음성 전사, 성과 API, 그래프 검색, 자동 브랜드 학습은 이 단계들의 완료 요건이 아니다.

## 14. 검수 기준

아래는 **후속 구현의 검수 시나리오**이며 이번에 통과시킨 테스트 목록이 아니다.

1. 제목·채널 없이 저장한 메모가 새로고침 후 남는다. 제목 수정이 선택 원문을 바꾸지 않는다.
2. 같은 메모를 콘텐츠 두 개에 써도 메모가 남고, 두 콘텐츠의 출처가 정확하다.
3. 한 원본 아래 같은 채널의 다른 각도 초안도 독립 저장된다. `item + variant` 링크가 정확한 초안을 연다.
4. Threads 채널이 저장·재조회 후 X로 바뀌지 않는다. Shorts와 Reels도 채널을 구별한다.
5. AI 요청 도중 본문을 수정하면 오래된 결과가 자동 적용되지 않는다. 같은 문장이 반복돼도 선택하지 않은 곳은 바뀌지 않는다.
6. AI 후보를 버리면 원문·현재 초안이 그대로다. 채택 후 되돌리기도 새로고침 후 유지된다.
7. 동일 요청의 이중 클릭은 생성 요청을 하나만 claim한다. 저장 재시도가 추가 모델 호출을 만들지 않는다.
8. DB 저장 실패·모델 타임아웃·부분 채널 실패를 각각 구별하고 입력·성공 후보를 복구한다.
9. 지원하지 않는 AI 작업이나 편집 형식은 다른 모드로 조용히 전환하지 않는다.
10. 다른 workspace의 원문·variant를 연결할 수 없다. export에 비공개 기획·메모가 끼지 않는다.
11. Threads만 발행했을 때 카드뉴스·Shorts는 미완료로 남는다. 복사만 한 결과는 발행으로 집계하지 않는다.
12. 원문 부족 상황에서 꾸며낸 수치·고객 발언이 생성되는지 수동 품질 검토한다. 형식 테스트와 모델 품질 평가를 구별한다.

사용성 목표는 측정 전 가설로 둔다. 저장 10초 목표와 실제 제작 시간은 사용 전후 표본으로 비교한다. 첫 2주에는 최소 20회 저장·편집 관찰을 목표로 하고, AI 후보 채택률·다시 작성한 이유·초안 재개율을 본다. 생성 개수만으로 성공이라 하지 않는다.

## 16. 이번 문서의 검토 경계

- 기존 확정 사항과 새 권장안을 구분했다. 특히 일지 4종 범위의 확정을 전체 일지 구현 승인으로 확대하지 않았다.
- 이미 수정 중인 앱 파일과 기존 성장/MCP 기획 문서는 건드리지 않고 현재 상태를 읽었다.
- 코드에서 확인한 계약 불일치와 실제 배포 실패를 구별했다. 이번 조사에는 유료 AI 실행·DB 변경·외부 발행이 없다.
- 첫 적용 범위를 원문→기획→Threads 초안으로 좁혔고, AI 편집·일지·채널 확대는 별도 완료 기준으로 나눴다.
- 구현할 때 source 보존, meta 갱신, variant별 복구, 비용, 중복, 생성 중 편집, 부분 실패를 빠뜨리지 않도록 계약에 포함했다.
