## 1. 이번에 해결할 문제

메모를 남긴 뒤 찾으려면 현재는 최신 목록을 거슬러 올라가야 한다. 고객·프로젝트에 연결해도 해당 업무를 다시 열었을 때 관련 기록을 바로 읽는 흐름은 없다. 여러 기록을 분석하려면 어떤 기록을 읽었는지와 어떤 주장에 쓰였는지부터 고정해야 한다.

권장하는 흐름은 다음과 같다.

`업무 또는 메모 검색 → 필요한 기록 확인 → 선택한 기록과 질문으로 분석 → 근거 확인 → 후보를 할 일·콘텐츠에 적용`

작성 화면에 필수 분류를 추가하지 않는다. 메모의 양이나 작성 빈도를 성과로 평가하지 않는다. 원하는 기록을 찾아 실제 다음 작업에 다시 쓸 수 있는지가 완료 기준이다.

## 2. 접근안과 권장 순서

| 접근 | 얻는 것 | 부담·한계 | 판단 |
|---|---|---|---|
| **A. 검색·명시적 연결을 먼저 완성하고 선택 분석 추가** | 기록을 직접 찾는 기능이 먼저 작동하고 분석 입력도 검증 가능 | AI 분석까지 두 묶음이 필요 | **권장** |
| B. 선택 분석부터 구현 | 반복 주제·행동 후보를 빠르게 얻음 | 기록을 찾고 고르는 불편이 남고 입력 범위·복구 구현이 먼저 커짐 | 이미 분석할 기록을 준비한 경우 적합 |
| C. 전체 기록 자동 분류·추천 | 직접 고르는 일을 줄일 가능성 | 비용·누락·중복 근거·불필요한 제안 관리가 늘어남 | 실사용 근거가 생긴 뒤 검토 |

A를 **2A 검색·재발견**과 **2B 선택 분석·적용**으로 나눈다. 각 묶음은 별도로 구현·검수할 수 있다. 검색과 관련 메모 조회는 AI 없이 작동한다.

## 3. 2A — 메모를 다시 찾기

### 3.1 검색 범위와 동작

- 메모 화면 상단에 검색어, 기간, 기록 종류, 연결 업무, 사용 이력을 제공한다. 기본은 검색어 없음·전체 기간·모든 종류·모든 연결·전체 이력이다.
- 검색 대상은 저장된 일반 메모의 **제목·원문·보강 문장**이다. 단어가 포함된 필드를 함께 표시한다. 하루 리뷰는 기존 별도 화면을 유지한다.
- 검색어는 앞뒤 공백을 제외한 최대 200자의 문자 그대로 찾는다. `%`, `_`, `*`, 괄호를 검색 연산자로 해석하지 않는다. 여러 단어는 입력한 한 구절로 찾는다.
- Enter 또는 `찾기`로 조회한다. 입력 중인 검색어와 적용된 검색 조건을 구분한다. `초기화`는 목록 조건만 초기화한다.
- 기간은 기록 시각(`occurred_at`) 기준이다. 기본 시간대는 운영 기준인 Asia/Seoul이며 오늘·최근 7일·최근 30일·직접 지정으로 고른다. 최근 7일은 오늘을 포함한 7개 달력 날짜다.
- 직접 지정한 시작일과 종료일은 둘 다 포함한다. 서버에서는 시작일 00:00 이상, 종료일 다음 날 00:00 미만으로 변환한다. 역전된 기간은 입력 오류로 표시한다.
- 기록 종류는 기존 자유 메모·고객 대화·아이디어·배운 내용·막힌 일·결정이다. 업무 필터는 프로젝트·리드·계약 계정·브랜드 중 실제 객체 하나를 명시적으로 선택한다.
- 사용 이력은 `전체 / 사용한 메모 / 아직 사용 이력 없음`이다. `journal_links.link_kind=use`의 존재로 판단한다. 아직 쓰이지 않은 메모를 낮은 품질이나 실패로 표시하지 않는다.
- 조건들은 AND로 결합하고, 검색어는 세 텍스트 필드 중 하나에 맞으면 된다. 정렬은 기록 시각 내림차순, 같은 시각은 ID 내림차순이다.

### 3.2 목록과 편집을 함께 유지

현재 최신 40개에 대한 브라우저 내 필터링으로 끝내지 않고, 저장소 전체를 조건에 맞게 조회한다. 한 번에 40개와 `더 보기`를 반환하며 조회한 개수를 표시한다. 전체 건수를 구하지 않았으면 `전체 N개`라고 쓰지 않는다.

행에는 날짜·종류·제목 또는 첫 문장·일치한 문장·연결 이유를 표시한다. 검색어 강조는 안전한 텍스트 조각으로 렌더링한다. 제목이 없거나 보강 문장에서만 일치한 기록도 찾을 수 있어야 한다.

검색 조건은 URL에 보존한다. 기존 새 메모 복구의 `from=preview`와 충돌하지 않도록 날짜 파라미터는 `dateFrom`, `dateTo`를 쓴다. 메모를 열고 닫거나 뒤로 가도 적용된 목록 조건으로 돌아온다.

목록 조회 상태와 편집 중인 문서 상태를 분리한다. 조건 변경·더 보기·느린 검색 응답이 현재 입력, 요청 영수증, 문서의 저장 상태를 초기화하지 않는다. 필터 변경 시 이전 목록 요청과 cursor는 폐기하되 초안은 유지한다.

### 3.3 업무 화면에서 관련 메모 보기

프로젝트·고객·브랜드 상세에 `연결된 메모` 영역을 둔다. 저장된 명시적 연결이 같은 기록의 최신 3개와 `모두 보기`를 제공한다. 3개는 화면 부담을 제한하는 초기 제품값이며 효과가 입증된 수치가 아니다.

- 표시 이유는 `이 프로젝트에 연결됨`, `이 고객에 연결됨`, `이 브랜드에 연결됨`처럼 실제 연결을 설명한다.
- `모두 보기`는 해당 업무 필터가 적용된 메모 목록으로 이동한다.
- `메모 남기기`는 기존 현재 업무 연결 후보를 사용한다. 생성·수정 후 관련 목록을 갱신한다.
- 이름이 비슷하다는 이유로 다른 고객의 기록을 섞지 않는다. 리드와 계약 계정도 연결된 객체 ID 기준으로 구분한다.
- 결과 없음과 읽기 실패를 구분한다. 실패하면 해당 메모 영역 안에 재시도를 제공한다.

기회 탐색, 과거 프로젝트 업데이트/메모, 외부 문서까지 한 검색에 합치는 작업은 별도 범위다. 이번 재발견은 1차에서 저장한 일반 메모를 대상으로 한다.

## 4. 2B — 선택한 기록을 질문에 맞게 분석

### 4.1 입력을 먼저 확인

검색 결과에서 메모를 체크하고 `선택한 메모 분석`으로 들어간다. 첫 버전은 1~10개, 전달할 텍스트 총 16,000자 이내를 권장한다. 이 숫자는 초기 실행 한도이며 사용 결과에 따라 조정한다. 한도를 넘으면 범위를 줄이거나 발췌하도록 안내하고 조용히 잘라 보내지 않는다.

실행 전 선택한 메모, 기록 날짜, 원문 또는 선택 발췌, 보강 문장 포함 여부를 보여준다. 보강은 기본 제외하고 별도로 포함한다. 선택한 메모마다 분석에 쓰는 필드를 구분한다. 체크하지 않은 검색 결과나 연결 고객의 상세 데이터는 입력에 추가하지 않는다.

질문은 직접 입력하거나 다음 목적 하나에서 시작한다.

| 목적 | 기본 질문 | 결과를 쓰는 곳 |
|---|---|---|
| 반복 주제 찾기 | 이 기록들에서 반복되는 질문이나 막힘은 무엇인가? | 다음 상담·개선 실험 |
| 생각의 변화 보기 | 앞선 판단과 최근 관찰 사이에 무엇이 달라졌나? | 프로젝트 판단 근거 |
| 열린 일 찾기 | 확인이 필요한 질문이나 후속 행동 후보는 무엇인가? | 할 일 |
| 콘텐츠 소재 찾기 | 이 기록에서 근거를 갖고 전달할 메시지는 무엇인가? | Studio |

`분석하기`를 누를 때만 외부 AI를 실행한다. 검색·체크·화면 열기는 실행 요청이 아니다. 준비한 입력과 질문은 같은 탭에서 복구하며 전송 전 확정한 원문 버전을 남긴다.

### 4.2 결과 카드의 계약

결과는 최대 5개의 후보 카드로 제안한다. 각 카드에는 다음을 포함한다.

1. **관찰:** 입력에서 확인한 내용.
2. **근거:** 실제 발췌, 기록 날짜, 원문 링크.
3. **다른 사례·제약:** 설명에 맞지 않는 기록 또는 확인 범위의 한계.
4. **해석:** 관찰과 구별되는 가설.
5. **다음 행동 또는 콘텐츠 후보:** 한 번에 확인 가능한 제안 하나.
6. **확인할 결과:** 적용 뒤 무엇을 살펴볼지.

근거 발췌는 저장한 입력 snapshot의 해당 필드에 정확히 존재해야 한다. 서버가 기록 ID·버전·발췌를 검증하며 제공되지 않은 기록을 출처로 붙인 결과는 완료로 저장하지 않는다. 근거가 없는 주장에 출처를 임의로 붙여 보정하지 않는다.

단건은 `한 기록에서 나온 후보`로 표시한다. 동일 문장의 여러 기록은 독립 사례 수로 확정하지 않는다. 기록 수와 날짜 범위를 보여주되 사건의 독립성은 확인되지 않았다고 남길 수 있다. 반복 횟수를 고객 전체 비율·중요도·인과관계로 바꾸지 않는다.

검색에서 찾은 수, 분석에 선택한 수, 실제 읽은 수를 구분한다. 선택 기록 중 하나라도 읽지 못하거나 버전이 달라지면 실행 전에 이를 알려 다시 확인하게 한다. 분석이 끝난 후 바뀐 원문은 결과 카드에 `원문 변경됨`으로 표시하고 당시 발췌는 보존한다.

### 4.3 후보를 실제 작업에 적용

후보의 `할 일로` 또는 `콘텐츠로`를 누르면 제목·연결 업무·전달할 발췌를 편집하고 기존 작성 화면에서 생성한다. 그 생성 버튼이 적용 동작이며 추가 승인 팝업을 반복하지 않는다.

여러 메모를 근거로 한 결과는 선택한 각 메모와 분석 실행으로 돌아가는 출처를 가져야 한다. 기존 단일 메모 생성 계약에 여러 근거를 억지로 한 기록의 본문처럼 넣지 않는다. 분석 후보 적용을 위한 원자 명령을 별도로 추가한다.

콘텐츠로 전달할 때는 사용할 발췌를 다시 고를 수 있게 한다. 선택한 발췌와 사용자가 편집한 기획만 Studio에 넣고 결과물 본문은 빈 초안으로 시작한다. 모든 개인 기록·분석 결과를 회사 콘텐츠 문맥에 일괄 복제하지 않는다.

적용 시 참조한 메모의 버전을 다시 검증한다. 변경된 원문이 있으면 해당 후보의 새 대상 생성을 막고, 최신 메모로 재분석하거나 현재 원문에서 수동 발췌하는 경로를 제공한다. 이전 분석과 당시 발췌는 계속 읽을 수 있다.

실제 대상 생성, 사용처 링크, 요청 영수증을 하나의 트랜잭션으로 저장한다. 응답 유실은 같은 요청으로 확인하고 성공한 대상 ID를 다시 돌려준다. task 완료를 메모가 유용했다는 응답으로 대신 기록하지 않는다. 적용 결과 피드백은 이후 단계다.

## 5. 구현 경계

### 5.1 재사용할 현재 코드

- [journal repository](../../../apps/hub/lib/repositories/journal-ledger.js): workspace 확인, 상세 원문, context/use 링크와 오류 봉투.
- [메모 화면](../../../apps/hub/components/hub/pages/memos.jsx): 목록·상세 deep link, 작성 중 복구, 내 작업 내비게이션.
- [메모 편집 모델](../../../apps/hub/components/hub/pages/use-memos.js): 편집 세션 격리, 충돌 비교, 동일 요청 재확인. 검색 상태가 이 계약을 바꾸지 않도록 분리한다.
- [journal migration](../../../supabase/migrations/20260913_0027_journal_notes.sql): 원문 revision, 발췌 snapshot, 원자 생성과 사용 이력.
- [Content transform](../../../apps/engine/lib/content-transform.ts): 단일 실행 claim, 결과 검증, 응답 불명 처리, 생성 결과 저장 복구 패턴. 콘텐츠 전용 payload를 메모 분석 payload로 재사용하지 않는다.

### 5.2 2A 조회 계약

새 read 경계 `/api/hub/journal/search`에서 검색어·기간·종류·context·사용 이력·cursor를 검증한다. 조회 실패는 기존 Hub 계약인 HTTP 200 + `status:error`다. 잘못된 조건과 정상적인 결과 0개도 구분한다.

조건은 서버가 정한 workspace에만 적용한다. context 필터는 같은 workspace의 실제 객체인지 확인한다. 검색은 매개변수로 전달하는 DB read RPC에서 수행하고, 연결 필터는 `EXISTS`로 처리해 메모 한 개가 여러 연결 때문에 중복 반환되지 않게 한다.

응답은 `status`, `workspaceId`, 적용한 `filters`, `entries`, `nextCursor`를 가진다. 일반 목록은 40개, 업무 영역은 3개로 제한하고 한 행을 더 읽어 다음 페이지 유무를 확인한다. cursor에는 조건 식별값을 결합해 다른 검색의 cursor를 재사용하지 못하게 한다. 페이지 사이에 기록 시각이 수정된 경우 완전한 snapshot이라고 주장하지 않고 새로고침으로 순서를 갱신한다.

기존 `GET /api/hub/journal?note=...` 상세 조회와 쓰기 계약은 유지한다. 검색과 상세 조회의 지연 응답을 독립적으로 격리한다. 저장 후 현재 조건에 맞지 않게 된 메모는 목록에서 제외될 수 있지만 열어 둔 편집 문서는 유지한다.

### 5.3 2B 실행·저장 계약

새 `journal_analysis_runs`는 workspace, request ID/hash, 선택 원문·필드·revision snapshot, 질문·목적·prompt version·model, 실행 상태, 결과, usage, 오류를 보관한다. 메모 원문을 분석 결과로 덮어쓰지 않는다.

Hub는 쓰기 가드를 통과한 명령을 Engine에 전달한다. Engine은 실제 기록과 버전을 다시 검증한다. 선택한 원문 snapshot의 확보와 실행 claim은 하나의 DB 트랜잭션에서 처리하고, 그 claim을 얻은 실행만 AI를 호출한다. 같은 요청은 기존 결과를 반환한다. 동일 ID에 다른 질문이나 범위를 보내면 conflict다.

실행 상태는 `running / succeeded / failed / unknown`을 구분한다. 타임아웃으로 호출 결과를 모르면 자동 재호출하지 않는다. 생성은 끝났지만 저장이 실패한 경우 기존 Content transform과 같은 결과 복구 패턴으로 저장만 재시도한다. 프롬프트·원문·복구 정보는 브라우저 주소나 일반 로그에 넣지 않는다.

외부 AI 입력의 메모는 데이터로 취급한다. 본문 안의 지시를 실행하거나 참고 링크를 자동 방문하지 않는다. 새 모델은 이 기획에서 고정하지 않으며 구현 시 설정된 provider adapter의 지원 여부를 확인한다.

실행별 model·입출력 사용량과 월별 합계를 제공한다. 합계는 보고된 사용량만 더하고, 사용량을 받지 못한 실행 수와 미집계 상태를 함께 표시한다. 실제 비용이나 단가를 알 수 없으면 금액을 0원으로 표시하지 않고 `비용 미집계`로 남긴다. 모델별 단가가 검증된 경우에만 추정 비용과 적용 기준일을 표시한다.

## 6. 완료 기준과 검수

| 검수 상황 | 기대 결과 |
|---|---|
| 오래된 기록·제목 없음·보강 문장에만 검색어 존재 | 최신 40개 밖의 메모도 조건에 맞게 조회 |
| 한국어·이모지·`%`·`_`·`*`·같은 시각의 메모 | 문자 검색과 페이지 경계가 일관됨 |
| KST 날짜 경계·역전된 기간·다른 조건의 cursor | 기간이 정확하며 잘못된 요청은 명시적 오류 |
| 연결 여러 개·다른 workspace·삭제된 연결 대상 | 중복/범위 누출 없이 결과 또는 명확한 오류 |
| 검색 변경 중 미저장 입력·이전 저장 응답 지연 | 입력과 영수증 보존, 오래된 응답의 덮어쓰기 없음 |
| 업무별 관련 메모 0개·조회 실패 | 빈 상태와 오류가 다르며 모두 보기 조건 유지 |
| 선택 1개·중복 문장·한도 초과·원문 변경 | 범위/제약 표시, 자동 축약이나 근거 과장 없음 |
| 외부 AI 오류·타임아웃·결과 저장 실패 | 실패/불명 구분, 자동 과금 재시도 없음, 저장만 복구 |
| 없는 원문 ID·불일치 발췌·본문 속 지시 | 결과 검증 실패, 지시나 링크 실행 없음 |
| 다중 근거 후보 적용·생성 응답 유실·트랜잭션 오류 | 모든 출처 보존, 중복 없음, 일부 대상만 남지 않음 |

2A의 완료는 **업무를 열거나 검색한 뒤 원문을 찾아 기존 할 일/Studio 활용으로 이어지는 것**이다. 2B의 완료는 **읽은 범위가 보이고 검증 가능한 분석 후보를 실제 대상에 한 번만 적용하는 것**이다.

검증은 관련 unit/repository/route 테스트, 임시 PostgreSQL, 실제 브라우저의 새로고침·뒤로 가기·두 탭·모바일, 전체 회귀와 빌드로 수행한다. 기획 숫자의 효과나 실제 메모의 분석 품질을 구현 테스트 통과만으로 주장하지 않는다.

## 7. 이번 기획의 권장 결론

먼저 2A를 완성하고 같은 조회 결과를 2B의 입력으로 사용한다. 화면을 열었을 때 할 수 있는 일은 `다시 찾기 → 원문 확인 → 활용`으로 유지하고, 해석이 필요한 순간에 선택 분석을 추가한다. 무인 전체 분석, 의미 검색, 그래프, 재알림, 결과 피드백의 자동 수집은 이후의 별도 설계 대상이다.
