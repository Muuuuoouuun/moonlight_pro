# 스코프를 전역 필터로

> 상태: 결정됨 · 구현은 단계별 (1단계 착수 전)
> 근거: 운영자 2026-09-11 결정 — "클래스인·개인이 구분이 잘 안 된다, 없으면 공백으로"
> 상위 정본: operator-workflow-profile.md, 개인 운영 OS 심화 설계
> 관계: `2026-07-15-sidebar-second-level-and-pms-taxonomy.md`의 앵커·2레벨 구조는 유지한다.
> 이 문서는 그중 **스코프 셸의 의미와 적용 범위**만 대체한다. `2026-07-14-sidebar-consolidation-design.md`가

## 1. 무엇이 문제였나

스코프(`전체 · ClassIn · 개인`)는 필터가 아니라 **라우터**로 구현돼 있었다. 앵커를 누를 때
어느 경로로 보낼지만 정하고, 지금 보고 있는 화면의 데이터는 건드리지 않았다. 결과:

- 앵커 10개 중 5개(오늘·현황·내 작업·고객 연락·설정)는 세 스코프가 전부 같은 경로 →
  스코프를 바꿔도 **아무 일도 일어나지 않았다**.
- 영업·매출은 `?scope=personal` 쿼리로 페이지 안 툴바 필터를 시드했지만 마운트 1회만
  읽어서, 스코프를 바꿔도 목록이 그대로였다 (2026-09-11 수정 완료, §5).
- 같은 축을 고르는 컨트롤이 두 벌(사이드바 `전체/ClassIn/개인` · 페이지 툴바
  `All/Personal/Company`)이고 서로 동기화되지 않았다.
- 같은 화면을 가리키는 주소가 두 벌이다: ClassIn은 별도 라우트(`dashboard/classin/*`),
  개인은 쿼리(`?scope=personal`).

## 2. 확정 결정 (2026-09-11)

| # | 결정 | 값 |
|---|---|---|
| D1 | "개인"의 의미 | **소속** — 내 사업·브랜드 라인. ClassIn 회사 일과 대비되는 축이며, 담당자나 공개 여부가 아니다. |
| D2 | 스코프 전환의 동작 | **전역 필터**. Gmail 계정 전환처럼 화면 전체가 그 소속만 보인다. 해당 항목이 없으면 빈 화면이 정답이다. |
| D3 | 영업·매출의 개인 스코프 | **유지**. 개인 매출(코칭·자문 등)을 앞으로 여기서 관리한다. 현재 0건인 것은 거짓이 아니라 "아직 없음"이다. |
| D4 | 캘린더 소속 | **캘린더 단위로 지정**. 설정에서 캘린더별 소속을 한 번 정하면 이후 자동 적용. |
| D5 | 소속 미상 데이터 | **개인으로 귀속**(현행 백엔드 기본값 유지). 양쪽 노출·별도 미분류 칸은 채택하지 않는다. |
| D6 | URL 반영 | **모든 경로에 스코프를 남긴다**. 북마크·새로고침·딥링크가 스코프를 기억하고, "표시는 개인인데 화면은 전체"인 드리프트가 구조적으로 불가능해진다. |
| D7 | 페이지 툴바 `All/Personal/Company` | **제거**. 소속을 고르는 곳은 사이드바 한 군데로 일원화한다. |
| D8 | ClassIn 별도 라우트 | **쿼리로 통합**. `dashboard/classin/*`를 `?scope=classin`으로 흡수하고, 기존 주소는 리다이렉트로 받는다. |
| D9 | 선택 표시 | **1px 보더 추가**(조용한 강화). 색을 쓰지 않는다 — DESIGN.md §5.2 유지. |
| D10 | 구현 순서 | **내 작업 · 고객 연락 먼저**, 그다음 오늘 · 현황. |

## 3. 데이터 실사 (2026-09-11)

전역 필터가 실제로 가능한지 표면별로 확인한 결과다. 마이그레이션이 필요한 곳은 없다.

| 표면 | 소속 판정 | 근거 |
|---|---|---|
| 내 작업 | 가능 | `work-ledger`가 `brand` 보유 → org_scope 해석 |
| 현황 | 가능 | `overview-ledger`가 `brand` 보유 |
| 고객 연락 | 가능 | `followups-ledger`가 leads/deals의 `company_id`를 읽음 → 기존 판정 규칙 재사용 |
| 오늘 | 부분 | 할 일(org_scope)·딜(type)은 가능. **캘린더만 소속 정보 없음** → D4가 선행 조건 |
| 영업·매출 | 가능 | `revenue-ledger`의 `type` (`company_id ? company : personal`) |
| 프로젝트·브랜드·콘텐츠 | 이미 적용됨 | workspace prop / `?scope=` |

라이브 원장 기준(2026-09-11): 리드 117건 전부 company, 계정 25개 전부 company, 개인 0건.
즉 D3이 실현되기 전까지 영업·매출의 개인 스코프는 정상적으로 빈 화면이다.

## 4. 판정 규칙의 단일화 (구현 시 주의)

지금 소속 판정이 세 갈래로 나뉘어 있다. 전역 필터로 가면 하나로 수렴시켜야 한다.

- `revenue-ledger`: `meta.kind` → 없으면 `company_id` 유무
- `workspace-map`: 명시 workspace 태그 → `revenueTypes`(type) → brand의 org_scope → 키워드 구제
- `project-ledger-context` / `content-ledger`: `org_scope` 직접 보유

키워드 구제(`accountKeywords`)는 타입 없는 레코드를 살리는 장치인데, D7로 툴바를 없애면
사이드바 스코프 하나가 이 구제 결과를 그대로 받는다. 구제로 넘어온 행이 조용히
사라지거나 중복되지 않는지 표면별로 확인한다.

## 5. 선행 완료분 (2026-09-11)

영업·매출의 스코프 무반응 버그는 이 문서의 결정과 무관하게 틀린 동작이라 먼저 고쳤다.

- `apps/hub/lib/revenue-scope-filter.js` 신규 — "쿼리가 바뀐 순간에만 필터를 재동기화하고
  그 사이 수동 선택은 유지" 규칙 하나를 소유한다.
- `revenue.jsx`의 `useScopeFilter`로 Leads·Deals·Accounts 3표면 공통 적용.
  기존 `useState(() => window.location.search…)` 마운트 1회 초기화는 제거했다.
- Accounts 빈 상태 문구를 정직화 — 필터로 0건인데 "원장이 비어 있다"고 말하던 것을
  Leads와 같은 `필터: personal · N건 중 0건` 계약으로 맞췄다.

D7이 적용되면 이 훅의 소비자는 사라지고 사이드바 스코프가 직접 필터를 소유한다.
그때 `revenue-scope-filter.js`는 제거 대상이다.

## 6. 남은 미정

- `전체` 스코프일 때도 URL에 `?scope=all`을 붙일지(Gmail `/u/0` 방식), 아니면 전체는
  쿼리를 생략할지. 현재 가정은 **전체도 명시**(D6의 드리프트 차단 효과가 전체에서도 유지됨).
- 캘린더 소속 지정 UI의 위치. 설정 화면에 캘린더 항목이 아직 없어 새로 만들어야 한다.
- D7로 툴바를 없앤 뒤, 그 자리에 다른 축(담당·활성 등)을 둘지 여부.
