## 1. 두 관점, 같은 기록

| 관점 | 묻는 것 | 입구 |
| --- | --- | --- |
| 리드·오너 | 살릴 가치가 있나, 돈이 새는 곳은, 다음 분기에 무엇을 접나 | 포트폴리오 표, 돈 화면, 분기 결정 |
| 개발자·메인테이너 | 지금 깨진 것, 이번 릴리스에 남은 것, 이번 주 점검 기한 | 제품 페이지 개발·보수 탭, 개발·보수 체크, 오늘 화면 1줄 |

화면을 역할별로 나누지 않는다. 포트폴리오 행 → 제품 페이지로 이어진다. 운영자 한 명이라 역할 전환 스위치는 없다.

## 2. 상태 모델 — 단계와 운영 상태를 나눈다

단계(아이디어→검증→MVP→출시→성장, 구현됨)는 "얼마나 자랐나". 운영 상태는 "지금 어떤가"로 따로 둔다.

| 운영 상태 | 뜻 | 들어갈 때 남기는 것 |
| --- | --- | --- |
| 기획 | 코드 전 | — |
| 개발 중 | 실사용자 없이 만드는 중 | 목표 첫 사용일 |
| 사용 중 | 실제 사용자 있음(내부 포함) | 첫 사용일, 사용자 수 원천 |
| 일시 중지 | 배포는 살아 있으나 투자 멈춤 | 이유 한 줄, 다시 볼 날 |
| 종료 | 내렸거나 보관 | 이유, 남은 비용 정리 여부 |

표시는 글리프+글자(DESIGN §5.3 lifecycle, 색 없음). 빨강은 CI 실패·가동 중단·에러 급증·보수 기한 지남만. 적자는 "적자 N개월" 글로.

## 4. 데이터 원천 — Moonlight는 제품 시스템에 쓰지 않는다

| 알고 싶은 것 | 원천 | 방식 | 없을 때 |
| --- | --- | --- | --- |
| CI·PR·릴리스 | GitHub | webhook + 폴링 (구현됨) | — |
| 배포·가동 | Vercel 배포 이벤트, 배포 URL | Engine cron 헬스 체크 | 수동 체크 |
| 에러 | 미정(§12-6) | webhook → `error_logs`, 묶음 1행 | "도구 미정" |
| 사용자 수 | 각 제품 DB | **제품 하트비트(push)** | 월 1회 수동 입력 |
| 매출 | 토스페이먼츠·Stripe, 딜 | 결제 webhook | 월 마감 수동 |
| 비용 | Vercel·Supabase·도메인·AI API | 비용 항목 수동 + 청구 메일 후보 | — |
| 문의 | 문의함 | 문의 ↔ 제품 (구현됨) | — |

### 4.1 제품 하트비트 계약

제품이 늘어도 연동 코드를 제품마다 짜지 않도록, 모든 제품이 하루 한 번 같은 JSON을 Engine에 보낸다.

```text
POST /api/webhook/product-heartbeat
X-Moonlight-Product: <slug>
X-Moonlight-Signature: sha256=<HMAC(제품별 비밀값, body)>

{ "date": "YYYY-MM-DD", "version": "1.4.2",
  "users": { "active7d": 0, "active30d": 0, "total": 0, "paid": 0 },
  "revenue": { "currency": "KRW", "day": 0 },      // 결제 webhook이 있으면 생략
  "health": { "errors24h": 0, "p95ms": 0 } }
```

- 한 날짜 한 행, 재전송은 덮어씀. 숫자만 — 사용자 목록·이메일은 보내지 않는다.
- 제품 쪽은 cron 1개 + 쿼리 3개. 공용 스니펫은 `scripts/inventory-project-connections.mjs`가 제품 폴더에 제안한다.

## 6. 화면 (목업)

- **포트폴리오**(프로젝트 탭 → 제품): 요약 5칸(사용 중 수·주간 활성·매출·비용·순이익), 지금 볼 것, 제품 표(상태·진척·사용자·매출·비용·순익·건강·다음 행동). 390px에서는 카드.
- **제품 페이지**(`/dashboard/products/<slug>`, 드로어 대신 전용 페이지): 머리(상태·단계·버전·링크), 지표 6칸, 탭 개요·개발·보수·사용자·돈·문의.
- **개발·보수 체크**: 제품 × 점검 매트릭스(완료·임박·기한 지남·자동·해당 없음), 진행 중 릴리스, 사고 기록.
- **돈**: 6개월 매출·비용, 공급자별 비용, 제품별 손익(사용자당 비용, 손익분기 유료 수).

## 8. 정할 것

1. "사용자 수"의 정의 — 권장: 최근 7일 활성(가입·유료는 보조).
2. 운영 상태 5개로 충분한가("베타" 필요?).
3. 비용 입력 방식 — 권장: 비용 항목 한 번 등록, 달마다 확인.
4. 에러 수집 도구 — Sentry 무료 또는 당분간 없음.
5. 하트비트 push vs Moonlight가 읽기 — 권장 push(제품 DB 자격을 Moonlight에 두지 않음).
6. 보수 점검 기본 주기 — 목업의 8종(백업 복구 분기, 의존성 주간, 키·도메인 연 1회 등) 조정.
