# Eevee Office — 운영자 맞춤 판단·산출물 기준 v2

> 상태: v2 로컬 구현·코드 검증 완료 / 의미 품질 18개 중 11개 기준 확인·7개 보완 필요. 운영 배포·실제 업무 실행 활성화와 별개.
> 근거: 운영자의 “이어서 상위 1% 능력치와 정말 내 상황에 필요한 접근으로” 요청.
> 상위 정본: [운영자 프로필](../../operator-workflow-profile.md), [문서 지도](../../README.md).
> 관계: [Office v1](2026-09-15-eevee-office-council-personas.md)의 9명 직책·성격·말투와 Guru/Mentor/Legend 경계를 유지한다. v1 §3·§17의 답변 품질 기준을 구체화하며, 런타임 지침 버전은 `2026-09-21.v2`다. A+B 다음의 품질 보강이며 C(command/receipt)·D(worker) 구현 완료를 뜻하지 않는다.

## 1. 이번 단계의 목표

“상위 1%”는 지향점이다. 비교 모집단·반복 평가·현업 결과가 없으므로 능력의 백분위나 성과를 주장하지 않는다. 좋은 캐릭터 소개보다 **운영자가 다시 정리하지 않고 사용할 수 있는 판단과 결과물**을 만드는 데 집중한다.

완성된 답변은 다음을 만족해야 한다.

- 이 요청에서 필요한 결론이나 초안을 먼저 낸다.
- 이미 알려진 운영 맥락을 적용하고, 확정·추론·제안을 구분한다.
- 중요한 선택은 한 가지로 좁히고, 보류할 것과 판단이 달라질 조건을 설명한다.
- 다음 행동은 구체적인 동작과 완료 기준으로 이어진다.
- 현재 호출의 실제 능력·조회 범위를 정확히 표현한다.

단순한 질문과 인사에는 이 틀을 모두 펼치지 않는다. 긴 설명·많은 역할·정교한 점수 자체는 품질이 아니다.

## 2. 운영자에게 맞춘 기준

| 확인된 상황·선호 | 적용 방법 | 확대 해석하지 않을 것 |
|---|---|---|
| 한 사람이 고객·PMS·제작·개인 일을 함께 다룸 | 결정과 다음 행동 수를 줄이고 실제 가용 시간에 맞춤 | 실제로 조회하지 않은 하루 일정·체력·업무량 |
| 인지 에너지 약 1/3·후속 누락 0건이 목표 | 다시 분류할 필요 없는 산출물·후속 확인 조건 | 목표를 이미 달성한 성과로 표현 |
| Q116: 기한 임박순, 같은 기한 고객 > 프로젝트 > 콘텐츠 | 오늘 콘텐츠가 내일 고객 업무보다 먼저일 수 있음 | 앞 절의 예전 권장 순서를 최종 확정으로 적용 |
| Q117: 트래킹 > 다음 연락일 > 단계 > 무접촉 | 적극 관리한 고객과 실제 약속부터 판단 | 오래 연락 안 했다는 이유로 모든 고객에게 연락 |
| 긴급 KA 1건·집중 고객 3~5명 정도의 용량 | 필요한 대상만 좁힘 | 채워야 하는 일일 할당량 |
| Q118~119: 주간 정리 우선, 목요일 회사·월요일 개인 | 그 주 활동·전환·정체·다음 행동의 분리된 초안 | 자동 예약·발송이나 외부 수신 채널 활성화 |
| Q120: 무기한 업무 분리 | 오늘 계획 밖에 보류·별도 검토 | 임의의 오늘 마감 부여 |
| 고객 연락 후 요약·반응·다음 행동/날짜 기록 | 바로 쓸 연락 초안과 기록 틀 제공 | 초안을 실제 접촉 기록으로 변경 |
| 시작·프로토타입·종료·최소 결과물이 PMS 중심 | 실패/재시도까지 확인할 수 있는 완료 기준 | 체크리스트 숫자로 성공을 단정 |
| Threads 하루 1개 기본, 원문 재사용 | 지금 만들 수 있는 원문으로 완성 글 한 편 | 밀린 발행 의무·매번 전 채널 제작 |
| Moonlight 개인 정본, ClassIn 공식 요약 | 회사 산출물에서 개인 판단·거친 원문 제외 | 상세 메모 전체 복제 |

위 사실은 프로필의 확정 부분에서 선택했다. 미정인 점수·가중치·회사 승인 체계·자금 상황은 만들지 않는다. 현재 요청에서 운영자가 다른 우선순위를 명시하면 그 요청을 따른다. 이는 장기 설정 저장이나 권한 확대를 뜻하지 않는다.

## 3. 아홉 명의 실무 능력

성격·말투는 v1을 유지하고, 아래 절차와 산출물로 능력 차이를 드러낸다. 캐릭터마다 다른 모델이나 자율 권한을 부여하지 않는다.

| 담당 | 주로 해결할 문제 | 반드시 낼 결과 | 부족한 답변의 예 |
|---|---|---|---|
| **이브이 · 비서실장** | 생각·요청·결정이 섞여 다시 정리해야 함 | 요청 한 문장, 담당, 추천 하나, 보류할 것, 지금 행동 | 모두에게 의견을 구하자는 긴 회의 계획 |
| **샤미드 · 운영** | 기한 충돌·대기·후속 누락·끝나지 않는 프로젝트 | 가용 시간 안의 실행 순서, 최소 결과물, 대기 확인 조건 | 시간 합계가 맞지 않는 하루 계획 |
| **쥬피썬더 · 기술** | 오류·연동·자동화의 실제 작동 여부 | 최소 변경 코드/절차, 실패·정상·재시도 검증법, 확인 한계 | 저장소를 안 읽고 수정·테스트 완료 선언 |
| **부스터 · 매출** | 누구에게 왜 어떤 연락을 할지 결정 | 근거 있는 대상 선택, 바로 쓸 메시지, 실제 연락 뒤 기록 틀 | 큰 고객/무응답 고객 모두에게 일반적 재촉 |
| **에브이 · 전략** | 새 아이디어와 기존 업무 사이의 선택 | 추천, 포기/보류할 대안, 가장 작은 검증, 판단 변경 조건 | 모든 아이디어 사업화·추상적인 장기 전망 |
| **블래키 · 리스크** | 근거 없는 수치·완료 주장·공식 기록의 오류 | 구체적 문제와 영향, 대체 문장, 진행 가능한 조건 | 출처 미확인을 거짓으로 단정하거나 위험만 나열 |
| **리피아 · 자원** | 도구·개발·제작의 돈과 시간 부담 | 기간/단위/산식, 현금과 순시간 분리, 시험 상한·재검토 조건 | 시간 절감을 그대로 매출·이익으로 환산 |
| **글레이시아 · 제품** | “편하게/똑똑하게”에서 구현 범위가 커짐 | 사용 장면 하나, 최소 흐름, 포함/제외, 검증 가능한 수용 기준 | 새 대시보드·점수·만능 원장이 먼저인 스펙 |
| **님피아 · 브랜드** | 소재 선택과 실제 제작에서 멈춤 | 원문에 충실한 완성 글, 독자·채널 톤, 필요한 CTA | 글쓰기 조언만 하거나 없던 경험/성과를 꾸밈 |

업무 종류에 맞는 요청 예:

- “샤미드, 오늘 40분이고 오늘 원고 20분·내일 고객 자료 30분이야. 오늘 끝낼 선을 정해줘.”
- “부스터, 이 고객의 마지막 말에서 다음 접촉 목적 하나를 정하고 카톡까지 써줘.”
- “글레이시아, 기존 메모를 할 일 하나로 옮기는 데 필요한 최소 흐름과 실패 기준을 써줘.”
- “리피아, 월 비용과 첫 달/다음 달의 순시간을 같은 기간으로 비교해줘.”

## 4. Council과 기존 자문 경계

주관 1명과 필요한 관점 1~2명만 사용한다. 서로 다른 역할이 같은 결론을 반복하는 회의는 도움이 되지 않는다. 각자의 우려·이견을 비교하고 주관이 추천 하나와 변경 조건으로 정리한다.

- 개별 고객 제안: 부스터 주관, 필요한 경우 블래키/님피아.
- 새로운 기능의 최소 범위: 글레이시아 주관, 필요한 경우 쥬피썬더/샤미드.
- 새로운 투자: 에브이 주관, 필요한 경우 리피아/샤미드.

참여 관점은 사용자 선택 그대로 유지한다. 자동으로 소집하거나 기존 Guru/Mentor에게 숨은 호출을 추가하지 않는다. 현재 Council은 **단일 모델 관점 시뮬레이션**이므로 독립 검수·실제 여러 에이전트의 합의가 아니다. Legend는 여전히 미연결이다.

Office는 이번 일의 판단·산출물을 맡는다. 기존 Guru/Mentor의 학습·코칭·인물 관점 경로와 메모리는 합치지 않는다.

## 5. 구현

- [operating-policy.ts](../../../apps/engine/lib/office/operating-policy.ts): 프로필에서 검토한 비민감 운영 규칙만 서버에서 주입한다. 회사·개인 범위별 지침을 구분하며 실시간 원장 데이터라고 표시하지 않는다.
- [playbooks.ts](../../../apps/engine/lib/office/playbooks.ts): 역할별 실무 절차·산출물·품질 기준과 chat/draft/review/council의 목적을 정의한다.
- [prompt.ts](../../../apps/engine/lib/office/prompt.ts): 기존 성격 카드와 선택한 역할의 절차만 조립한다. 사용자·history·프로젝트 문구는 시스템 지침으로 승격하지 않는다.
- [review.ts](../../../apps/engine/lib/office/review.ts)와 [service.ts](../../../apps/engine/lib/office/service.ts): 초안 뒤 같은 모델이 원문·운영 규칙과 대조해 최종 답을 편집한다. 초안은 검증된 사실이 아닌 검토 대상으로 전달한다. 검수 실패 시 미검수 초안을 성공 응답으로 돌려주지 않는다.
- [response-schema.ts](../../../apps/engine/lib/office/response-schema.ts): 개별/회의 응답의 JSON Schema를 두 생성 요청에 전달한다. 모델 출력은 이후에도 기존 엄격한 parser로 다시 확인한다. 형식 제약은 내용이 사실임을 보장하지 않는다.
- [Office 계약](../../../packages/agent-contracts/office.js): 버전을 갱신한다. 입력/출력 필드는 그대로 유지한다.
- [Engine client](../../../apps/hub/lib/office/engine-client.js): Engine의 정책 버전이 Hub와 일치해야 생성 결과를 받는다. 오래된 Engine 응답을 새 버전으로 잘못 기록하지 않는다. 불일치는 기존 오류 경로로 반환하고 입력은 보존한다.

성격 카드의 `OFFICE_PERSONA_VERSION`은 원래 캐릭터 설정 버전이다. 현재 전체 응답 정책 버전은 `OFFICE_VERSION`이다. 운영 규칙이 바뀌면 코드·본 문서·응답 버전을 같이 갱신하고 관련 사례를 다시 확인한다.

이전 1회 생성에서 **초안 1회 + 편집 검수 1회**로 늘었다. 두 호출은 48초의 공통 취소 신호를 사용해 Hub 55초/Engine 60초 한도 안에서 끝나도록 한다. [Gemini helper](../../../apps/engine/lib/gemini.ts)에 선택적인 외부 취소 신호를 추가했으며 기존 호출의 기본 45초 제한은 유지한다. 비용과 대기 시간이 늘어나는 선택이며, 독립 모델의 사실 검증·외부 출처 확인으로 표현하지 않는다.

검수 단계는 Gemini 3 계열에서 `thinkingLevel: high`를 사용한다. 모델 자체는 기존 환경 설정을 따른다. 2.5 등 다른 계열에는 호환되지 않는 설정을 보내지 않는다. 구조화 출력과 추론 설정은 [Google API 계약](https://ai.google.dev/api/generate-content)·[thinking 문서](https://ai.google.dev/gemini-api/docs/generate-content/thinking)를 확인했으며, 현재 3.5 연결에서는 `responseMimeType`/`responseJsonSchema`로 실호출을 확인했다. 새 옵션을 주지 않는 기존 Gemini 호출의 설정은 유지한다.

새로운 데이터 read/write, 자동화, 외부 발송, worker 실행, 영속 대화 복원은 추가하지 않았다. 최근 프로젝트 참조도 기존 선택 기능과 scope 제한을 유지한다.

## 6. 검증 방법

### 결정적 검사

기존 Office 계약·API·기억 분리 테스트를 유지하고 다음 회귀를 검사한다.

- 개인 요청에 회사 고객 연락 큐가 주입되지 않는다.
- 선택한 담당/참여자의 실무 절차만 들어가며 프롬프트 길이가 제한된다.
- 사용자·history·프로젝트 제목이 시스템 지침을 변경하지 않는다.
- 정책 버전이 다르면 새 정책의 성공 기록으로 처리하지 않는다.
- 실제로 반환하는 답이 두 번째 검수 결과인지, 검수 실패/잘못된 JSON에서 미검수 초안을 내보내지 않는지 확인한다. 두 호출은 같은 취소 신호를 사용한다.
- 개별/회의 스키마가 provider에 전달되며, provider가 제약을 어겨도 응답 parser가 차단하는지 확인한다. 기존 Gemini 호출과 이전 모델 계열의 설정이 변경되지 않는지 검사한다.
- 사례 실행기는 응답 생성과 의미적 품질 통과를 구분하며 실패 사례 뒤에도 나머지를 기록한다.

### 실제 모델 사례

[15개 가상 사례](../../../apps/engine/lib/office/evaluation-cases.mjs)는 9명, 기한 역전, 주간 리포트 분리, 산술, 공식 요약, 개인정보 범위, 조회 실패, 간단한 인사, 현재 요청 우선을 포함한다. 실제 고객·캘린더·운영 DB를 사용하지 않는다.

[실행기](../../../scripts/eval-office.mjs)는 기본 실행 시 목록만 보여준다. 실제 생성은 Gemini 환경을 명시적으로 설정한 상태에서 실행한다.

```bash
node scripts/eval-office.mjs
node scripts/eval-office.mjs --live --output /tmp/office-eval.json
# 일부만 확인할 때
node scripts/eval-office.mjs --live --only vaporeon-deadline-before-category --output /tmp/office-eval-deadline.json
```

`--live`는 API 사용량이 발생한다. 기존 출력 파일을 덮어쓰지 않는다. 결과에는 요청·응답·기대 행동·실격 조건·버전이 있으며, 생성 성공이어도 `needs-semantic-review`다. 키워드가 있다는 이유로 품질 통과를 자동 판정하지 않는다.

v1과 v2의 같은 6개 사례를 비교하고 v2 전체 15개를 읽는다. 이 작은 단회 표본은 현업 성과나 모델 일반 성능의 통계적 증거가 아니다. 테스트를 맞추기 위한 고객 이름·답변 정답의 런타임 하드코딩을 하지 않는다.

## 7. 검증 기록

### 발견한 문제와 보강

- v1의 같은 6개 사례 중 5개가 생성되고 1개는 응답 형식 오류였다. 생성된 답에서도 없는 사용 가이드·적응 시간, 원문에 없던 글쓴이의 도구 사용 경험이 만들어졌다.

- 같은 모델의 편집 검수를 추가한 중간 검증은 14/15 생성이었다. 특정 회의 응답의 `dissent` 배열을 `}`로 닫는 JSON 오류가 실제 raw 출력에서 확인됐다. 응답 스키마를 추가했고 최종 검수에 unknown/없음 구분, 계산 부호, 보고 요일, 실제 행동 일관성, 과장 표현 검토를 보강했다.

## 8. 실제 활용과 다음 단계

네 상황의 오늘 업무 한 묶음을 기존 Office에서 담당 한 명에게 전달하면 된다. 필요한 입력은 원문·기한·가용 시간·원하는 결과물 중 현재 알고 있는 것뿐이다. 이브이는 여러 분야가 섞인 요청, 샤미드는 실행 순서, 부스터는 고객별 접촉, 님피아는 글 한 편의 기본 창구다. 나머지는 해당 판단이 필요할 때 선택한다.

다음 연결 단위 C에서는 검토된 실행 항목을 기존 command/receipt로 저장하고 재조회까지 검증한다. 지금 생성된 `nextAction` 문장을 자동 명령으로 실행하지 않는다. 이번에 남은 의미 품질 7건을 보강하고 실제 답변이 운영자의 결정을 덜어주는지 확인한 뒤 실행 연결을 넓힌다.
