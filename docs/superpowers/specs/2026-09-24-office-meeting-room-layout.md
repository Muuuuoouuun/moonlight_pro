## Problem Statement

Office는 만들어졌지만 쓰이지 않는다. 운영 DB `agent_runs`의 `office.*` 행은 0건이다(2026-09-23 확인). 운영자의 말로는 "사용성이 좀 별로이고 어떻게 써야 될지 몰라서 못 쓰고 있다". 머릿속에 그림은 있다: 안건을 올리면 여러 역할이 모여 이야기하고, 조언을 받는 회의실이다.

현재 첫 화면은 폼이다: 담당 1명 → 모드 4개(대화·초안·검토·관점 비교) → 6,000자 입력 → 접힌 "함께 검토하기". 회의 기능(관점 비교)은 엔진이 발언 단위로 만들지만, 화면은 문서 카드 한 장과 접힌 `<details>` 표로만 보여 준다. 그래서 회의처럼 보이지 않는다.

## Demand Evidence / Status Quo

- 막히면 지금은 ChatGPT·Claude 앱에 붙여넣거나, Claude Code·Codex에 묻거나, 혼자 미룬다(세 가지 모두 한다, D2).
- Office를 안 쓴 이유는 넣기 불편함, 답이 느리거나 별로, 그리고 막 만들어서 쓰는 법이 안 보임이다(D3). 이 중 **레이아웃으로 고칠 수 있는 건 "넣기"와 "쓰는 법이 안 보임"뿐이다.**
- 실사용 기록은 아직 없다. 이 문서의 가치는 전부 가설이며, 아래 과제가 첫 증거가 된다.

## Target User & Narrowest Wedge

사용자는 운영자 본인이다. 첫 장면(D4 "3-2", D5)은 **막힌 할 일 하나를 회의에 올리는 것**이고, 그다음이 회의실 토론이다. 자유 붙여넣기는 그 안건을 만드는 입력 수단이다.

## Premises (D6, 운영자 전부 동의)

1. 뼈대는 "안건 하나를 올리는 회의실"이다. 자유 채팅·⌘V·드래그는 안건을 만드는 입력 수단이며 별도 모드가 아니다.
2. 첫 안건 종류는 막힌 할 일이다. 회의실이 할 일 맥락을 읽어 운영자가 다시 타이핑하지 않게 한다.
3. 회의는 발언이 순서대로 보이는 스레드다. 이미 있는 발언 기록을 펼치는 것이라 모델 호출은 늘지 않는다.
4. 운영자는 회의 한 판이 끝난 뒤 끼어든다. 발언 도중 실시간 끼어들기와 스트리밍은 범위 밖이다.
5. 결과는 그 할 일로 돌아간다(확인 후, 자동 변경 없음). 입구는 할 일 쪽과 Office 안, 두 곳이다.
6. 답 품질·속도는 레이아웃으로 고칠 수 없다. 이미지·파일 첨부는 2단계다.

**A안은 전제 2·5를 절반만 충족한다.** 할 일은 연결된 기록이 아니라 가져온 순간의 텍스트 복사본이다. 결과를 그 할 일에 반영하지 않고, 새로고침하면 회의가 사라지며, 입구는 Office 안 한 곳뿐이다. 다음 판의 역할들은 앞 판의 역할별 발언을 기억하지 못한다. 운영자가 이 한계를 알고 A안을 선택했다(D7).

## Approaches Considered

- **A. 회의실 겉모습만** — 채택. 이유는 아래 Recommended Approach.
- B. 할 일 안건 회의실(`task_unblock` 인텐트·저장되는 라운드·할 일 반영) — 추천안이었으나 운영자가 A를 선택했다. 아래 업그레이드 조건이 충족되면 이 안으로 올린다.
- C. 할 일 드로어 안 패널 — 드로어가 좁아 회의 스레드를 담을 수 없고, 표면 예산 규칙("기존 화면에 패널을 덧붙이지 않는다")과 충돌해 기각했다.

## Recommended Approach — A. 회의실 겉모습

엔진·계약·서버 라우트는 바꾸지 않는다. `requestOffice`(`/api/hub/office/chat`)를 그대로 쓴다. 바뀌는 곳은 Office 화면, 입력 처리, 클라이언트 세션 저장소(`office-session.js`)다. 저장소 변경은 아래 "저장소 변경" 목록이 전부다.

### 용어

- **회의 한 판**: 운영자의 요청 1회와 그 응답이다. 기존 `turn` 1개에 해당한다.
- **발언 단계**: 한 판 안의 `첫 의견`(`position`)과 `상호 검토`(`response`)다. 단계 수는 설정에 따라 1~2단계다(`officeDiscussionRounds`).

### 화면 구성 (위에서 아래로)

```
┌ 안건 바 ─────────────────────────────────────────────┐
│ 안건: [할 일에서 가져옴 · 복사본] 제안서 가격 결정     │
│ 참석: 부스터(주관) · 블래키  [참석자 바꾸기] [더보기]  │
├ 회의 스레드 (오래된 판 위 → 최신 판 아래) ───────────┤
│ 나      제안서 가격을 어떻게 정할지…                  │
│ 부스터 · 첫 의견      …                               │
│ 블래키 · 상호 검토    … (반론 · 판단을 바꿀 조건)     │
│ ┌ 종합 · 부스터 ─────────────────────────────┐       │
│ │ 추천 · 남은 이견 · 다음 행동  [복사] [수정 요청]│   │
│ └──────────────────────────────────────────────┘     │
│ 나      그 안은 예산이 없어  (주관에게 이어서 묻기)   │
│ 부스터 · 답변 …                                       │
├ 입력창 (하단 고정) ──────────────────────────────────┤
│ [안건 가져오기]  이어서 묻기…  [주관에게 ▾]  ⌘↵ 보내기 │
└──────────────────────────────────────────────────────┘
```

1. **안건 바.** 현재 안건의 제목, 출처 칩, 참석자, `참석자 바꾸기`, `더보기`를 보여 준다.
   - 출처 칩은 `할 일에서 가져옴 · 복사본 · HH:MM` 또는 `직접 입력`이다.
   - 이름 바꾸기: 화면 문구의 `관점 비교`(`MODES`, 보내기 버튼)를 `회의`로 바꾼다. 보내기 버튼은 `회의 시작` / `보내기`다.
   - 제목 규칙: 할 일에서 가져왔으면 할 일 제목, 직접 입력이면 첫 요청의 첫 줄 앞 40자.
   - 첫 요청 전에는 안건 바 자리에 "안건을 올리세요 · 할 일을 가져오거나 직접 적어 주세요" 한 줄만 둔다.
   - `참석자 바꾸기`는 기존 담당 변경 `Drawer`를 **확장**한다. 지금 드로어는 주관만 고르고 고르는 즉시 닫힌다(`office-council.jsx:90,183-187`). 관점 선택은 접힘 패널에 있다(`:168-169`). 새 드로어는 주관 1명 선택과 관점 0~2명 체크를 한 곳에 두고, `완료`로 닫는다.

2. **응답 방식 결정 규칙.** 첫 화면에서 4모드 `SegmentedControl`과 "함께 검토하기" 접힘 패널을 뺀다.

   | 참석자 | `더보기`의 응답 방식 | 보내는 `mode` |
   | --- | --- | --- |
   | 주관 1명 | 대화(기본) | `chat` |
   | 주관 1명 | 초안 / 검토 | `draft` / `review` |
   | 주관 + 관점 1~2명 | (선택 불가, `회의`로 고정 표시) | `council` |

   관점을 더하면 응답 방식은 `회의`로 고정된다. 초안·검토를 고르면 관점 선택이 비활성화되고 "초안·검토는 주관 혼자 씁니다"를 표시한다. 계약상 비회의 모드는 참석자가 비어 있어야 하기 때문이다(`office.js:98`). `수정 요청`(`revise`)은 지금처럼 그 판의 참석자·방식을 되살린다.

3. **`더보기` 드로어** (`Drawer`, 이 페이지 전용). 순서대로 넣는다: 응답 방식(대화·초안·검토) → 추천 조합(`COMPARISON_PRESETS`, 참석자와 방식을 채움) → 토론 조절(`OfficeDeliberationControls`, 회의일 때만) → `현재 범위의 최근 프로젝트 참고` → `오늘은 최소한만`.

4. **회의 스레드.** 판을 시간순으로 쌓는다(현재의 최신이 위로 쌓이는 순서를 뒤집는다). 한 판은 세 부분이다.
   - 운영자 발언: 요청 원문. 3줄을 넘으면 접고 펼칠 수 있다.
   - 역할 발언(회의 판만): `discussion.turns`를 접지 않고 그린다. 각 발언은 발언자 이름·역할, 단계 라벨(`첫 의견` / `상호 검토 · 관점 수정|판단 유지`), `position` 본문으로 구성한다. `근거`·`반론`·`판단을 바꿀 조건`은 발언 아래 한 줄 요약으로 두고 펼칠 수 있다. `officeDiscussionState`가 `legacy`·`invalid`면 지금과 같은 안내 문구를 쓴다.
   - 종합 카드: 기존 `ResultTurn` 내용을 그대로 옮긴다(주관 답변, 추천 근거와 남은 이견, 다음 행동, 복사·수정 요청, 호출 기록 영수증, 참고 프로젝트).
   - 대화·초안·검토 판은 운영자 발언과 종합 카드만 그린다.
   - 발언자를 색으로 구분하지 않는다. 이름 라벨과 들여쓰기로 구분한다(DESIGN.md §5.2). 확실성은 기존대로 `CertaintyBadge recommended`와, 근거가 추적되지 않을 때 `unknown` `근거 확인 안 됨`으로 표시한다.
   - 보낸 뒤: 새 판의 운영자 발언이 스레드 보이는 영역의 위쪽에 오도록 스크롤하고(감소 모션이면 즉시) 스레드에 포커스를 준다. 지금 코드는 스레드 맨 위로 스크롤한다(`office-council.jsx:109-113`).

5. **이어서 묻기와 안건 유지.** 결과가 나오면 입력창 라벨이 `이어서 묻기`로 바뀐다. 옆의 선택은 두 가지다.
   - `주관에게`(기본): `chat` 모드, 모델 호출 1회.
   - `다시 회의`: 같은 참석자로 회의 한 판을 새로 연다. 모델 호출이 여러 번이고 60초 제한 안에 끝나야 하므로, 버튼 옆에 `역할 N명 · 발언 M단계`를 표시한다.
   - **알고 가야 할 한계:** 다음 판에 넘어가는 기록(`officeHistory`)은 최근 4판의 요청과 종합 답변이고, 각각 2,000자로 잘린다(`office-client.js:17-18`). 역할별 발언은 넘어가지 않는다. 그래서 `다시 회의`의 역할들은 앞 판의 종합만 보고 새로 의견을 낸다. 이 한계를 없애는 건 B안의 범위다.
   - **안건 고정:** 세션에 `agenda` 필드를 추가한다(`{ title, source: 'task'|'manual', taskId?, importedAt?, block }`). 안건 블록을 담은 첫 판이 최근 4판 밖으로 밀려나면, 다음 요청 `message` 앞에 블록을 다시 붙인다(블록 최대 1,500자). 이렇게 해서 안건이 기록에서 빠지지 않게 한다.
   - `새 안건`: 확인 한 번 뒤 현재 범위의 turns와 `agenda`를 비운다. 세션 저장소에 `reset(scope)`를 추가한다(`office-session.js`에는 아직 없다).

6. **입력.**
   - ⌘V 텍스트는 원래 되던 대로다. 입력창은 내용에 맞춰 최대 12줄까지 늘어난다.
   - 글자 수: 다시 붙는 안건 블록도 `messageLength`에 포함해 6,000자 초과를 기존 `tooLong` 오류로 알린다. 지금 `begin()`은 초과 시 아무 말 없이 `null`을 돌려준다(`office-session.js:41`).
   - 텍스트 드롭: `dataTransfer`의 `text/plain`만 받는다. 파일·이미지를 드롭하거나 붙여넣으면 입력을 바꾸지 않고 `이미지·파일은 아직 읽지 못합니다 · 텍스트로 붙여 넣어 주세요`를 `role="status"`로 알린다(2단계 전까지 정직하게).
   - `안건 가져오기`: `Drawer`에서 할 일을 검색해 하나 고르면, 정해진 서식의 텍스트 블록(제목·다음 행동·마감·설명)이 `agenda.block`이 되고 입력창 맨 앞에 들어간다. 원천은 기존 `GET /api/hub/tasks`다. 이 라우트는 검색·상태 필터가 없으므로 클라이언트에서 거른다.
     - 완료(`done`)가 아닌 할 일만 보인다. 제목으로 거른다.
     - 범위를 맞춘다: Office 범위 `classin` ↔ 할 일 `workspace: classin`, `personal` ↔ `brand`, `all` ↔ 전부. 프로젝트가 없어 `workspace`가 없는 할 일(`operating-ledger.js:313`)은 `all` 범위에서만 보인다. 다른 범위에서는 목록 아래에 `범위 미정 N개 · 전체 범위에서 보입니다`를 표시한다.
     - 블록에 프로젝트 줄은 넣지 않는다. 이 라우트는 프로젝트 ID만 주고 이름을 주지 않으며, A안은 추가 호출을 하지 않는다.
     - 상태 표시: `live`는 목록, `partial`은 `TruthBadge partial` + 목록, `preview`는 `TruthBadge preview`(`Preview · 연결 필요`), 로딩은 `Skeleton`으로 그린다.
     - 읽기 실패: 이 라우트는 실패 시 HTTP 502(`tasks/route.js:38`)나 500(`:67-73`)을 돌려준다. CLAUDE.md의 200 + `status: "error"` 규칙과 어긋난 별도 부채다. 소비자는 `!r.ok`와 `d.status === 'error'`를 모두 읽어 `TruthBadge error` + 다시 시도를 보이고, 빈 목록으로 위장하지 않는다.

7. **기다리는 동안.** 엔진은 모든 발언을 한 번에 돌려주므로 실시간으로 "지금 말하는 중"을 보여 줄 근거가 없다. 대신 이번 판에서 실제로 일어날 순서를 `officeDiscussionRounds(settings)`로 계산해 `Skeleton` 행으로 예고한다. 예: 1단계면 `부스터 첫 의견 · 블래키 첫 의견 → 종합`. 제목은 `순서 예고`로 달고, 진행률처럼 보이는 애니메이션은 쓰지 않는다(§5.3 truth).

8. **입구는 Office 안뿐이다.** 할 일 드로어에는 `더보기`가 없고(`더보기`는 현재 `content-studio.jsx`에만 있다), 새 버튼을 더하면 표면 예산을 어긴다. 그래서 할 일 쪽 입구와 `?task=` 딥링크는 A안에서 뺀다(Open Question 1).

9. **저장소 변경** (`office-session.js`, `office-council.jsx`). 이 목록 밖으로 저장소를 바꾸지 않는다.
   - 기본값: `blankSession`의 `reviewers: ['umbreon']`(`office-session.js:9`)을 `[]`로 바꿔 주관 혼자인 상태를 허용한다. `selectOwner`가 관점을 비우지 못하게 막는 대체 로직(`office-council.jsx:89`)도 없앤다.
   - `mode` 유도: `update()`에서 관점이 1명 이상이면 `council`로 두고, 0명이면 `chat`·`draft`·`review` 중 운영자가 고른 값으로 둔다(위 2의 표).
   - `begin(scope, id, { mode })`: `주관에게` 이어서 묻기일 때 이번 요청만 `chat`, 참석자 없음으로 보낸다. 세션에 저장된 방식은 그대로 둔다.
   - `agenda` 필드: `{ title, source: 'task'|'manual', taskId?, importedAt?, block }`. `manual`이면 `block`은 첫 요청 원문 앞 1,500자다. 다시 붙이기(위 5)는 `begin()` 안에서 한다.
   - `reset(scope)`: 현재 범위의 turns·`agenda`·draft를 비운다.

10. **그대로 두는 것.** 범위 전환, 세션 보존(다른 화면으로 이동해도 유지, 새로고침 시 사라짐), `OfficeUsageLine`, 6,000자 제한은 그대로다.
