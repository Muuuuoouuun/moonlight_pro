## 2026-09-15 로컬 통합 보정

- Windows의 소재함·브랜드 기준 편집·빠른 메모·수동 발행 기록을 기존 로컬 Studio(원문/기획·채널 변형·AI 후보·버전 복원)에 연결했다. 구 단일 파일 편집기로 되돌리지 않는다.
- Threads의 `threads_post`를 새 Studio와 Engine 검증에 연결하고, X의 기존 `x_thread`는 보존한다. `20260914_0001_content_threads_post.sql` 다음에 `20260915_0034_threads_studio_compat.sql` 적용이 필요하다. 이번 통합에서는 운영 DB를 변경하지 않았다.
- 프로젝트 생성은 로컬의 인라인/드로어 공용 폼과 접힌 선택 설정을 유지하고, Windows의 업무 분류 라벨을 적용했다. 이름 우선 생성·완료 조건 검증·저장 재시도는 유지한다.

## 1. 제안의 중심

**브랜드는 누구에게 어떤 가치를 어떤 관점으로 쌓을지 정하는 곳, 콘텐츠는 그 방향에 맞는 생각을 골라 발행 가능한 결과물로 만드는 곳으로 재정립한다.**

브랜드를 발행량 관리 대상으로만 다루면 저빈도 출판·개인 아카이브·사업 브랜드의 차이가 사라진다. 콘텐츠를 편집기·자동화 도구 중심으로 다루면 운영자가 가장 힘들어하는 “지금 무엇을 만들까”가 남는다. 두 탭의 연결 지점은 브랜드 선택 드롭다운을 넘어, 소재를 고르는 이유와 제작 기준이어야 한다.

근거의 우선순위는 `docs/README.md`를 따른다. 특히 운영자 프로필의 자연발생적 소재 수집, 지금 만들 수 있는 것 우선, Threads 중심, 원본의 다채널 재사용을 따른다. 아래는 9월 11일 제안이며 실제 구현·검증 범위는 §10을 따른다.

## 2. 현재 화면·코드에서 확인한 것

2026-09-11 로컬 Hub, 1280×720 데스크톱에서 브랜드 목록 → 브랜드 상세 → 해당 브랜드 Queue → 기존 콘텐츠 Studio를 열고, 콘텐츠 로그도 별도로 확인했다. 저장·발행 조작은 하지 않았다. 화면의 실시간 표시는 저장소 연결 상태이며 외부 SNS의 전체 발행 내역 확보를 뜻하지 않는다.

| 확인 화면/단계 | 현재 작동하는 부분 | 문제와 영향 | 판단 |
|---|---|---|---|
| 브랜드 목록 | 브랜드별 정체성·발행 요약, 범위 필터, 상세 진입 | 최상단이 목표 미달·조용함 중심. 현재 11개 모두 ‘2주 이상 조용’에 포함되지만 발행 이력 없는 항목도 집계한다 | 상태 의미부터 수정 필요 |
| 브랜드 상세 | 철학·방향·보이스·규칙을 읽고 콘텐츠로 이동 | 정체성 편집은 미제공. 철학·보이스·규칙이 채워지면 ‘정체성 확정’으로 표시해 작성 완료와 운영자 확정을 혼동 | 브랜드의 핵심 행동 보강 필요 |
| 브랜드 → Queue | 브랜드 필터와 기존 초안 열기 작동 | 선택 브랜드는 1건인데 상태 탭은 전체 4건, 주간 목표도 별도 수치로 표시. 범위가 섞여 보이며 다음 소재 선택 지원은 약함 | 선택·제작 중심 재구성 권장 |
| Queue → Studio | 저장된 원고/슬라이드와 브랜드 기준 표시 | 편집 모드는 Blog / Insight, Card News. Threads 중심 운영과 어긋남. 1280px에서 우측 패널과 상단 Publish 버튼 영역이 겹쳐 보임 | 주력 형식과 작업 공간 개선 필요 |
| 브랜드 콘텐츠 로그 | 같은 콘텐츠를 보드·리스트로 탐색하고 Studio 진입 | Queue와 작업 영역 중복. 실제 성과값 없이 ‘성과순’ 제공 | 공통 콘텐츠 보기를 재사용하도록 정리 권장 |

코드 근거:

- `apps/hub/lib/brand-directory.js`: `identityCompleteness`, `attentionRank`, `buildBrandDirectory`. 미등록 발행 이력은 `quietDays=null`이며 quiet 집계에 포함한다. cadence 권장 목표도 behind 계산에 들어간다.
- `apps/hub/components/hub/pages/brands.jsx`: 브랜드 읽기가 `/api/hub/content`에 의존. 정체성은 읽기 전용이며 콘텐츠 이동 버튼 제공.
- `apps/hub/components/hub/pages/content.jsx`: `Studio`의 blog/carousel 모드, `useContentLedger`의 기존 5분 캐시, Queue 및 Campaigns 구현.
- `apps/hub/lib/brand-content-log.js`: 기획/제작중/발행 상태 투영, 성과값은 모두 0이고 표시는 ‘—’.
- `apps/hub/app/api/hub/content/route.js`: 기록 조회와 draft/handoff/export 경로. 현재 Publish 표면은 handoff와 실제 외부 발행을 구분해 읽어야 한다.

Campaigns의 Business Truth에는 고객·문제·약속·제안이 있다. 이는 코드 검토 결과이며 해당 화면의 전체 상호작용은 이번에 점검하지 않았다. 브랜드 전략을 추가할 때 같은 정보를 별도 정본으로 중복시키지 않아야 한다.

이번 점검은 제품 역할과 대표 경로에 한정한다. 모바일, 키보드 전체 흐름, 대비 수치, 실제 발행, 응답시간 및 번들 크기는 검증하지 않았다.

## 3. 각 탭이 답해야 할 질문

| 공간 | 사용자가 답을 얻을 질문 | 핵심 결과물 |
|---|---|---|
| 브랜드 | 누구에게 무엇으로 기억될 것인가? 지금 무엇을 키울 것인가? | 편집 가능한 브랜드 기준, 현재 집중점, 대표 자산과 학습 |
| 콘텐츠 | 지금 무엇을 만들고, 어디까지 했고, 무엇을 다시 쓸 수 있는가? | 소재, 원본, 채널별 버전, 발행 기록 |
| 프로젝트·캠페인 | 특정 기간에 어떤 결과를 만들어야 하는가? | 목표·일정·산출물과 연결된 콘텐츠 |

브랜드는 채널 계정이나 프로젝트 폴더와 다른 개념이다. 기존 brands 테이블의 혼합 용도를 표시·조회 계층에서 먼저 정리한다. 기존 브랜드 이름, 소유 관계, 식별자, `projects.brand_id`를 추정으로 바꾸거나 삭제하지 않는다.

## 4. 브랜드: 핵심 기능 세 가지

### 4.1 살아 있는 브랜드 기준

한 화면에서 아래 질문의 답을 읽고 고칠 수 있게 한다. 모든 칸을 채워야 시작할 수 있는 필수 양식으로 만들지 않는다.

- **대상과 변화:** 누구의 어떤 문제·욕구를 다루고 무엇을 남길 것인가.
- **관점과 가치:** 이 브랜드가 반복해서 주장하는 생각과 제공하는 가치. 상업 브랜드는 상품·서비스, 출판·개인 기록은 작품·경험 등으로 표현한다.
- **핵심 주제:** 반복해서 다룰 소수의 주제와 다루지 않을 범위.
- **표현 기준:** 보이스·금지어·좋은 실제 예시. 기존 철학·방향·규칙을 최대한 활용한다.
- **현재 집중점:** 이번에 쌓거나 검증하려는 한 가지와 운영 상태(운영중/실험중/휴식 등).

빈칸 여부와 운영자 확인 여부를 분리한다. 자동 완성률은 ‘작성됨’, 명시적 확인은 ‘확인됨’으로 다룬다. AI는 초안을 제안하고 수정 이유를 설명할 수 있지만 기존 정체성을 조용히 덮어쓰지 않는다.

### 4.2 지금 집중할 브랜드

목록의 우선 정보는 ‘한 줄 약속 / 현재 집중점 / 이어서 할 일’이다. 집중 브랜드 고정은 운영자가 선택한다. 모든 브랜드에 매주 발행 의무를 부과하지 않는다.

권장 주기는 제안임을 유지하고, 운영자가 선택한 목표만 진행 상황에 반영한다. 발행 기록 없음, 외부 기록 미연결, 실제 기간 내 발행 없음, 휴식 상태를 구분한다. 브랜드 성격에 따라 발행 건수 외에도 대표작 완성·문의·서비스 실험 등을 선택할 수 있게 하되 성과를 추정하지 않는다.

### 4.3 쌓인 자산과 배운 점

대표 콘텐츠·작품·프로젝트·참고 자료를 브랜드에 연결하고, ‘이 표현은 맞았다 / 다음에는 이 관점을 써보자’라는 짧은 회고를 남긴다. 브랜드 상세의 콘텐츠 목록은 콘텐츠 공통 보기의 브랜드 필터를 사용한다.

## 5. 콘텐츠: 핵심 흐름 하나

**빠른 메모·참고 링크 → 소재함 → 지금 만들 것 선택 → 원본 작성 → 채널별 버전 → 발행 기록 → 재사용**

### 5.1 소재함

본문이나 링크만으로 저장한다. 브랜드·채널은 나중에 골라도 된다. ‘왜 저장했는지’는 선택 입력이다. 빠른 메모에는 명시적인 ‘콘텐츠 소재로 보내기’를 제공하고 원문 연결을 보존한다. 일반 업무 메모를 자동으로 콘텐츠나 회사 기록에 복제하지 않는다.

선택을 돕는 정보는 이어 쓰던 초안, 바로 쓸 수 있는 소재, 자료가 더 필요한 소재다. 복잡한 우선순위 점수와 필수 분류를 추가하지 않는다. 사용자가 선택한 소재에는 ‘이번에 말할 한 가지’를 붙여 제작으로 넘긴다.

### 5.2 제작중

기본 작업은 간결한 텍스트 원고다. 현재 운영 기준상 첫 번째 완결 경로는 Threads를 권장한다. 기존 Blog·Card News 초안은 보존하고 계속 열 수 있게 한다.

원고 옆에는 선택 브랜드의 핵심 기준만 요약한다. 전체 브랜드 목록·저장 기술명·자동화 설정은 작업을 방해하지 않는 위치로 옮긴다. 카드뉴스 디자인과 영상 제작은 형식에 따라 필요한 때 연다.

원본과 채널별 버전을 구분하고 원본 연결을 남긴다. Threads는 X의 thread와 별도 채널이므로 기존 타입 이름을 바꾸는 방식으로 지원했다고 처리하지 않는다. 기록 타입·Engine validation·읽기/쓰기/재열기까지 계약을 맞춰야 한다.

### 5.3 발행·재사용

첫 단계는 원고 복사/내보내기 → 외부 수동 발행 → URL과 발행일 기록으로 닫는다. 외부 자동 발행과 성과 수집은 별도 후속 범위다. 발행 요청·전달 완료·운영자 발행 확인·외부 확인을 구분한다.

발행한 글에서 ‘다른 채널 버전 만들기’와 ‘후속 소재 만들기’를 제공한다. 원본을 덮어쓰지 않는다. 초기 학습은 링크와 짧은 회고면 충분하며 성과 API가 없어도 쓸 수 있어야 한다.

## 6. 화면 구성 권장안

- 브랜드 목록 → 브랜드 상세의 **방향 / 자산·기록**. 현재 집중점은 상세 상단에 둔다.
- 콘텐츠 기본 진입 → **소재함 / 제작중 / 발행·재사용**. 카드·리스트 전환은 동일 보기 옵션이다.
- Studio → 선택한 콘텐츠의 편집 공간. 독립된 빈 편집기를 매번 먼저 선택하는 구조를 줄인다.
- 브랜드의 콘텐츠 로그 → 공통 콘텐츠 보기의 브랜드별 진입점. 기존 보드·리스트와 딥링크를 유지하며 중복 상태 계산을 제거한다.
- Campaigns → 기간·목표가 있는 묶음에서 사용. 브랜드 기준을 참조하고 캠페인에서 달라지는 대상·제안만 별도로 둔다. 기존 Business Truth의 적용 범위와 데이터를 확인한 뒤 이전을 설계한다.

이는 8월 브랜드 탭, 9월 콘텐츠 로그 확정 설계의 변경 제안이며 §10에 명시한 구현 범위에서 해당 화면 계약을 대체한다. 기존 메뉴와 딥링크, 브랜드별 색상에 관한 콘텐츠 로그 예외는 유지한다. Moonlight의 한국어 중심 문구, 다크 서피스, 문스톤 액센트와 얇은 보더를 유지한다.

## 7. 구현 순서와 완료 기준

| 순서 | 범위 | 완료 판단 |
|---|---|---|
| 1. 신뢰와 정체성 | 기록 없음 집계 수정, 작성/확인 상태 분리, 브랜드 기준 편집, 집중 상태, 성과 미연결 정렬 정리 | 기준 수정 후 재조회·새로고침에 유지. 미연결 브랜드를 발행 부진으로 판정하지 않음. 기존 프로젝트 연결 보존 |
| 2. 한 편 완성 | 소재함, 빠른 메모에서 명시적 전달, Threads 원고, 수동 발행 URL 기록 | 소재 저장→재열기→원고 수정→복사→발행 기록의 전체 경로 완주. 실패·재시도에도 중복 없이 원문 보존 |
| 3. 보기 통합·재사용 | Queue/로그 공통 상태·필터, 원본에서 채널 버전 생성, 대표 자산과 짧은 회고 | 어느 화면에서 열어도 같은 원본·상태. 채널 버전 편집이 원본과 다른 버전을 덮어쓰지 않음 |
| 4. 사용 후 확장 | 반복 템플릿, 추천 보조, 필요 채널 연동·성과 | 실제 제작 사례에서 반복되는 수고를 확인한 기능만 추가 |

첫 구현 묶음은 1과 2의 최소 범위로 잡는 것이 좋다. 목표는 ‘운영 브랜드 하나의 기준을 정리하고 소재 하나를 실제 게시물로 끝낼 수 있음’이다. 많은 탭·자동화·분석을 먼저 늘리지 않는다.

## 8. 기술 최적화: 기능 목적에 맞춰 좁게

- **데이터 의존성:** 브랜드 정체성을 읽는 데 전체 콘텐츠·asset·publish log·campaign 기록을 요구하지 않도록 조회 계약을 분리한다. Hub repository 경로를 유지하고 브랜드 기준은 콘텐츠 조회 실패와 독립적으로 표시한다.
- **기존 캐시 개선:** `useContentLedger`에는 이미 5분 캐시가 있다. 캐시 신설을 해결책으로 삼지 않고 공통 모듈로 분리해 요청 중복, 저장 후 무효화와 화면 간 최신 상태 반영을 확인한다. 지금 `brand-content-log.jsx`가 대형 페이지 모듈에서 훅을 가져오는 의존성도 정리한다.
- **범위 일치:** 선택 브랜드·상태에 따라 목록과 요약 숫자의 범위를 맞춘다. 데이터량 증가 시 서버 필터·페이지네이션·상세 본문 지연 조회를 적용한다. 먼저 payload와 전환 시간을 측정한다.
- **쓰기 계약:** Hub → Engine 인증 전달과 입력 검증, 동일 식별자 재시도, 저장 후 재조회, unknown/preview/partial/error 구분을 유지한다. 브랜드 정체성의 편집 필드 허용 범위는 기존 update_brand 계약부터 점검한다.
- **편집 공간:** 작은 화면에서 우측 기준 패널을 접거나 별도 시트로 열고, 저장·발행 행동이 가려지지 않도록 검증한다. 단순한 텍스트 제작에 카드뉴스 전체 UI를 필요로 하지 않게 구성한다.

이번 검토에서 성능 저하 수치를 측정하지 않았다. 위 항목은 확인된 의존성과 흐름에 근거한 최적화 후보이며 성능 개선 효과가 검증된 결과는 아니다.

## 9. 실사용 검증과 남은 결정

출발 기준은 ‘무엇을 만들지 고르기까지 걸린 시간’, ‘소재에서 발행까지 완주한 사례’, ‘같은 원본을 재사용한 사례’, ‘기록 유실·중복 여부’다. 초기 사용에서 기준선을 얻고 목표치를 정한다. 모든 브랜드의 주당 게시물 수를 성공 지표로 고정하지 않는다.

구현 전에 남은 결정은 집중할 첫 브랜드, 브랜드별 핵심 약속의 실제 내용, 기존 캠페인 전략의 소유 범위다. 사용자 답변을 대신 만들어 저장하지 않는다. Threads 우선과 위 메뉴 구성은 기존 운영 기준을 바탕으로 한 권장안이다.

## 10. 2026-09-14 구현 및 검증

운영자 요청: “진행 ㄱㄱ. 구현, 서브 에이전트 동원”. 브랜드·콘텐츠 백엔드·콘텐츠 UI를 3개 하위 작업으로 나눠 구현하고, 빠른 메모 연결과 통합 검증을 수행했다.

- 브랜드: 독립 `GET /api/hub/brands` → 브랜드 repository. 기준 편집, 운영자 확인, 운영 상태, 집중점·고정. Engine `update_brand_identity`가 기존 meta와 프로젝트 연결을 보존하며 `updated_at` 충돌을 검사한다. 응답 후 재조회로 저장 내용을 확인한다.
- 상태: 작성 여부와 운영자 확인 분리. 발행 기록 없음·휴식·권장 목표를 발행 부진으로 계산하지 않는다. 브랜드 정체성 목록은 콘텐츠 조회와 독립적이다.
- 소재: 브랜드 없는 본문·링크 입력과 개인/회사 범위. 빠른 메모의 ‘콘텐츠 소재로 보내기’는 note 저장·재조회 후 콘텐츠를 생성하며 원문과 연결 ID를 보존한다. 응답 불명 시 같은 식별자로 재시도한다.
- 원고: `threads_post`를 X와 구분. Threads 작성·저장·재열기·복사, 기존 Blog/Card News 유지. 미지원 형식은 읽기 전용. 원본 소재·공개 범위·기존 브랜드 연결을 보존한다.
- 발행: 외부 수동 게시 뒤 URL·일시 기록. `operator_confirmed` 출처의 로그와 콘텐츠·버전 상태를 모두 재조회해 확인한다. 빈 일시·미래 일시·잘못된 URL은 쓰기 전에 안내한다. 외부 SNS 게시 요청은 하지 않는다.
- 공통 보기: 브랜드 필터와 요약 수치 범위 일치, 성과 미연결 정렬 제거. 공유 캐시의 요청 중복 제거·저장 후 무효화·오래된 응답 덮어쓰기 방지. 모바일에서는 편집기 보조 패널을 아래로 배치한다.

검증 결과:

- Node 24.19.0 전체 자동 테스트 **814/814 통과**, 계약 검사 통과.
- Hub·Engine 프로덕션 빌드 통과. Engine TypeScript 검사 통과.
- 로컬 Hub 3100, Chrome headless, 1440×1000 및 390×844. Browser plugin이 없어 번들 Playwright를 사용했다. API 응답과 쓰기를 격리된 메모리 fixture로 대체해 운영 데이터를 변경하지 않았다.
- 브랜드 수정 충돌 시 입력 유지 → 저장 → 새로고침, 소재 → Threads 수정·저장·재열기 → 복사 → 수동 발행 기록, 빈 발행 일시 오류 복구, 빠른 메모의 부분 실패 → 새로고침 → 동일 ID 재시도, 모바일 드로어·포커스·가로 넘침을 확인했다. 해당 흐름에서 페이지 런타임 오류가 없었다.
- 실제 Supabase 저장 및 외부 SNS 발행은 이번 브라우저 검증의 범위가 아니다. 스크린샷·임시 테스트 스크립트는 저장소 밖에 보관했다.

운영 적용 제한:

`supabase/migrations/20260914_0001_content_threads_post.sql`은 기존 형식을 보존하면서 `threads_post`만 허용 목록에 추가한다. 이 파일만 지정해 `scripts/apply-migrations.mjs`로 적용을 시도했으나 Supabase 관리 API가 **401 Unauthorized**를 반환했다. 유효한 `SUPABASE_ACCESS_TOKEN`으로 갱신 후 해당 파일을 적용해야 운영 DB에 Threads 소재·원고를 저장할 수 있다. 적용되지 않은 상태는 Engine에서 `threads-contract-migration-required`로 반환하며 UI는 성공 처리하지 않고 입력을 유지한다. Engine과 Hub 코드의 운영 배포도 별도다.

아직 포함하지 않은 범위: 자동 다채널 파생 생성, 대표 자산·회고 편집, Campaigns 정보 이전, 외부 SNS 직접 발행·성과 수집. 기존 데이터와 메뉴를 보존한 첫 구현 범위다.
