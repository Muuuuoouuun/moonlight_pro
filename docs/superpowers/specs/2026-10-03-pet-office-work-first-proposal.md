# 펫 Office 기능 기획 A — 작업을 먼저 보는 창

상태: **검토용 제안 · 미선택 · 미구현**

기준일: 2026-10-03 · 대상: Mac 네이티브 펫

## 해결할 문제

펫의 Office 모드는 현재 Hub를 여는 진입 화면이다. 운영자가 이미 요청한 Office 작업의 상태와 결과를 확인하려면 브라우저로 이동해야 한다. 이 안은 펫에서 최근 요청을 찾고 결과를 읽는 흐름을 우선한다.

여기서 ‘작업’은 Office의 생성 요청과 결과를 뜻한다. 업무 할 일, Codex 실행, 외부 전송의 완료 기록을 대신하지 않는다.

## 핵심 화면과 동작

Office 진입 → 최근 요청 목록 → 한 요청 선택 → 결과 읽기 → 같은 창에서 목록으로 돌아오기.

| 표면 | 내용 | 예산 |
| --- | --- | --- |
| 상단 | Office, 개인/회사 범위 선택, 닫기 | 한 줄 |
| 모드 | 작업 / 대화 | 두 항목 |
| 본문 | 최근 요청의 제목·담당자·상태·출처 기간 | 첫 화면 최대 세 행 |
| 선택 영역 | 선택한 요청의 짧은 결과 미리보기 | 두 줄 |
| 주 행동 | 결과 읽기 | 하나 |
| 보조 행동 | Hub에서 이어서 | 텍스트 링크 하나 |

첫 화면에는 검색창, 담당자별 카드, 진행률, 미확인 숫자, 자동화 버튼을 추가하지 않는다. 더 오래된 요청은 목록 하단에서 명시적으로 불러온다. 필터의 추가 조건은 범위 메뉴의 더보기로 보낸다.

결과를 열면 목록 영역이 결과 본문으로 교체되고 ‘뒤로’가 나타난다. 결과 본문은 읽기와 복사까지만 제공한다. 업무 반영·저장·보내기·로컬 스킬 요청은 해당 Hub 화면에서 명시적으로 진행한다.

## 대표 사용 흐름

1. 펫의 Office를 연다. 마지막으로 선택한 개인/회사 범위의 최근 요청을 조회한다.
2. ‘결과 도착’ 요청을 선택한다. 원본 요청의 담당자와 출처를 확인하고 결과를 읽는다.
3. 필요하면 대화 탭으로 이동해 후속 질문을 작성한다. 결과의 복사본을 대화 맥락에 넣는 것은 운영자가 누를 때만 한다.
4. 실제 업무 반영이 필요하면 ‘Hub에서 이어서’로 원본 요청을 연다. 펫 창에서 확인한 것만으로 적용되지는 않는다.

주간 정리와 고객 답장 초안이 최초 지원 대상이다. 일반 Office 대화는 현재 저장된 요청 목록과 다른 계약이므로, 이 화면에서 영구 작업처럼 표시하지 않는다.

## 상태 문구

| 실제 상태 | 표시와 가능한 행동 |
| --- | --- |
| running | 생성 중 · 결과 읽기 비활성 |
| generated | 결과 도착 · 결과 읽기 가능 |
| unknown / error | 확인 필요 · 상세 설명, Hub에서 확인 |
| expired | 본문 보관 종료 · 메타데이터만 표시 |
| 읽기 실패 | 목록을 불러오지 못했어요 · 다시 불러오기 |
| 인증 필요 | Hub 연결 필요 · 같은 창에서 로그인 |
| 실제 빈 목록 | 아직 Office 요청이 없어요 · 대화로 이동 |
| preview | 연결된 업무 데이터 없음 · 실제 빈 목록과 구분 |

결과 생성, 기록 저장, 업무 반영은 서로 다른 상태다. 체크 표시나 ‘업무 완료’로 합치지 않는다. HTTP 200이어도 봉투의 status/source가 error이면 실패로 처리한다.

## 데이터와 개발 범위

확인한 기존 자산:

- Office의 영속 요청 정본은 office_requests다. 주간 정리·고객 답장의 요청/결과, actor, workspace, scope, origin이 저장된다.
- 기존 GET /api/hub/office/requests와 office_request_list_v1은 특정 intent·scope·originRef를 요구한다. 전체 최근 요청을 모으는 API가 아니다.
- 요청별 receipt와 결과 투영, 만료 시 본문 삭제 계약은 재사용한다.
- Mac의 OfficeChatStore와 공용 Hub 연결 서비스를 대화 탭과 인증에 재사용한다.

새로 필요한 범위:

1. 서버에서 검증된 actor/workspace와 선택 scope를 기준으로 최근 요청 메타데이터만 읽는 요약 조회.
2. 기존 테이블 권한은 그대로 닫아둔다. 새로운 제한 RPC와 필요한 색인을 검토한다. 브라우저/native에 테이블 접근 권한이나 서비스 키를 주지 않는다.
3. 요약에는 요청 ID·담당자·intent·scope·최소 출처 식별자·상태·생성 시각·만료 여부만 포함한다. 입력 스냅샷, 결과 본문, 실행 토큰은 목록에서 제외한다.
4. 최대 20개와 안정적인 시간/ID 커서를 사용한다. 상세 본문은 항목을 열 때 요청별 receipt로 읽는다.
5. 새 Hub read 라우트는 기존 미들웨어 인증을 그대로 통과한다. OPEN 예외를 추가하지 않으며 실패는 HTTP 200 + error 봉투를 따른다.
6. RPC가 추가되면 최신 번호를 확인해 마이그레이션을 만들고 db:check 기능 목록에도 등록한다. 별도 업무 정본 테이블은 만들지 않는다.

소비자의 scope나 actor 입력을 신원으로 신뢰하지 않는다. 다른 요청 ID·회사/개인 전환·만료 결과에 대해서도 서버에서 권한과 본문 노출을 확인한다.

## 창·연결·읽음 계약

- 기존 단일 companion 창의 모드를 바꾼다. 빠른 입력 창이나 별도 Office 팝오버를 만들지 않는다.
- 제안 크기는 본문 424×584pt + 펫 perch 54pt다. 현재 Office 높이와 다르므로 선택 후 실기 조정한다.
- 크기 변경 시 화면의 기존 상단/우측 앵커를 유지하고 작업 영역 안으로 제한한다.
- Mac clear glass, 흰색 계열 글자, 얇은 중립 테두리를 유지한다. 담당자와 상태 때문에 창 전체 색을 바꾸지 않는다.
- 네이티브 Hub 연결은 배포 Hub 주소와 자체 운영자 세션을 쓴다. Electron 쿠키를 복사하거나 인증을 우회하지 않는다.
- 범위 전환 시 이전 조회 응답은 폐기한다. 오프라인에서는 마지막 조회 시각을 표시하고 이전 항목을 현재 상태라고 주장하지 않는다.
- 결과를 실제로 연 요청만 ‘읽음’으로 취급한다. 이 앱의 읽음 표시를 업무 완료나 서버 반영 상태로 저장하지 않는다.

## 검증 기준

- Office ↔ 다른 펫 모드 ↔ 빠른 입력 요청을 반복해도 companion 창은 하나만 보인다.
- 401, HTTP 200/error, 빈 결과, preview, 만료, 범위 변경 중 늦은 응답이 각각 올바른 상태로 보인다.
- 다른 actor/workspace의 ID를 상세 조회하거나 커서를 바꿔도 데이터가 노출되지 않는다.
- 생성 중에는 결과 행동이 열리지 않고, 결과 도착 뒤에도 업무 완료라고 표시되지 않는다.
- 결과를 읽고 복사해도 새 업무·외부 전송·스킬 실행이 생기지 않는다.
- 생산 데이터와 모형 데이터를 섞지 않는다. 이미지의 예시 문구는 디자인 설명에만 존재한다.

## 장점·비용·우선순위

장점은 여러 요청을 다시 찾기 쉽고, Office가 무엇을 만들고 있는지 한눈에 확인할 수 있다는 점이다. 비용은 새 요약 조회·DB 계약·목록 상태 관리가 필요하다는 점이다.

출시 순서는 인증/요약 조회 → 목록과 상세 → 대화 연결을 제안한다. Hub의 API와 Mac 패키지는 버전 호환을 확인해 함께 배포해야 한다. Windows는 별도 Acrylic 설계와 실기 검증 뒤 진행한다.
