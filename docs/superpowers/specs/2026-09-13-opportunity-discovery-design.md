# 기회 탐색 — 가능성을 발견하고 실제 일로 연결하기

> 상태: **방향·1차 구현 승인 / 구현 및 로컬 검증 완료**. 2026-09-13 운영 DB 적용 및 생성·재시도 검증 완료. 화면 배포는 Vercel 무료 요금제의 문의 동기화 주기 제한으로 대기 중이다.
> 작성일: 2026-09-13 (Asia/Seoul)
> 결정 근거: 운영자 요청 “신규 사업, 신규 프로젝트, 신규 리드, 보이지 않는 기회 포착이나 진행” 및 선택 “3번째 기회 탐색으로 가자”.
> 상위 정본: [운영자 프로필](../../operator-workflow-profile.md), [개인 운영 OS](2026-07-13-moonlight-personal-operator-os-deep-design.md).
> 관계: 기존 CRM Opportunity와 PMS를 유지하면서 탐색 영역을 보완한다. 기존 프로젝트 생성·후보 규칙을 대체하지 않는다. [사이드바 스펙](2026-07-15-sidebar-second-level-and-pms-taxonomy.md)의 앵커 배치는 아직 변경하지 않는다. [메모 활용 설계](2026-09-12-memo-writing-reuse-and-analysis-design.md)는 연결 가능한 후속 제안이며 구현 의존성을 확정하지 않는다.

## 1. 확정된 방향

- 명칭은 **기회 탐색**이다.
- 프로젝트의 단계 추가나 CRM의 영업 기회 확장 대신 별도 영역으로 다룬다.
- 신규 사업·프로젝트·리드와 아직 구체화되지 않은 가능성을 포괄한다.
- 구체화된 기회는 기존 리드·거래·프로젝트 흐름에 연결한다.

2026-09-13 운영자의 “구현” 요청으로 §7의 1차 흐름을 구현했다. 구체적인 구현 계약은 §9와 실행 기록을 따른다. AI·외부 탐색은 후속 제안으로 유지한다.

## 2. 권장하는 운영 흐름

**포착·발굴 → 가설 정리 → 작은 검증 → 결과 판단 → 실행 연결 또는 보류·종료**

포착은 대화·메모·문의·콘텐츠 반응에서 가능성을 발견하는 일이다. 발굴은 관심 분야와 궁금한 문제를 정하고 조사·인터뷰·작은 제안으로 새 신호를 만드는 일이다. 두 입구는 같은 탐색 기록으로 이어진다.

처음부터 고객·예산·마감일·예상 매출을 요구하지 않는다. 기회 하나의 진척은 완료율보다 확인한 사실, 남은 불확실성, 다음 검증 행동으로 설명한다. 가능성이 낮다는 근거를 얻어 종료한 경우도 학습 결과로 남긴다.

## 3. 기존 영역과의 경계

| 영역 | 역할 | 기회 탐색과의 연결 |
|---|---|---|
| 메모 | 관찰·생각·원문 보존 | 선택한 기록을 출처로 연결. 모든 메모를 기회로 바꾸지 않음 |
| 기회 탐색 | 가치가 있을 가능성과 검증 과정 관리 | 고객이나 실행 프로젝트가 없어도 시작 가능 |
| 리드·거래 | 구체적인 상대와 영업 과정 관리 | 상대가 확인되면 기존 고객을 찾아 연결하거나 적절한 생성 흐름으로 이동 |
| 프로젝트 | 정한 결과를 위한 실행 관리 | 운영자가 실행 범위와 결과를 정했을 때 연결 또는 생성 |
| 내 작업 | 날짜가 있는 개인 행동 실행 | 탐색의 다음 행동을 기존 할 일로 연결 |
| 브랜드 | 지속적으로 운영하는 정체성과 활동 문맥 | 관련 브랜드를 선택적으로 연결 |

CRM의 기존 `Opportunity`와 탐색 기록은 같은 개념으로 취급하지 않는다. DB 이름과 관계 구현은 구현 전 기존 스키마를 확인해서 결정한다.

기회 하나에서 리드 여러 명과 프로젝트 여러 개가 파생될 수 있다. 실행 연결 후에도 탐색 원문과 근거를 보존한다. 연결된 프로젝트의 완료가 기회의 종료를 자동으로 뜻하지 않는다. 기존 리드·프로젝트 직접 생성 경로도 유지한다.

## 4. 최소 기록과 진행 상태 제안

최초 저장은 **가능성 한 줄**만 필수로 한다. 다음 정보는 검토하면서 채운다.

- 발견 근거: 원문·링크·대화 참조 또는 직접 관찰. 근거가 없는 생각은 가설로 표시.
- 가치 가설: 누구의 어떤 문제를 어떻게 풀 수 있을지.
- 다음 검증: 확인할 질문과 가장 작은 행동.
- 검토 날짜: 다시 판단할 날짜. 실행 마감일과 구분.
- 결과 기록: 실제 반응·관찰과 운영자의 해석, 다음 결정.
- 연결 대상: 고객·브랜드·거래·프로젝트·할 일.

권장 상태는 `포착 / 탐색 중 / 검증 중 / 실행 연결 / 보류 / 종료`다. 순차 통과를 강제하지 않으며 근거를 추가하고 이전 상태로 돌아갈 수 있다. 실행 연결 상태에는 실제 대상 연결이 있어야 한다. 보류에는 재검토 날짜 또는 재개 조건을 남기고, 종료에는 판단 이유를 남긴다.

다음 행동은 별도의 복제 투두로 관리하지 않고 기존 할 일에 연결하는 방향을 권장한다. 할 일을 완료하면 검증 결과와 다음 판단을 기록할 수 있게 한다. 행동 완료 자체로 가설이 검증됐다고 처리하지 않는다.

## 5. 일상에서 열어볼 이유

기회 탐색에서는 다음 세 묶음을 우선 확인하도록 제안한다.

1. 새로 포착해 아직 판단하지 않은 가능성.
2. 지금 확인할 행동이 있는 기회.
3. 결과를 판단하거나 다시 볼 시점이 된 기회.

관심 분야를 정해 직접 조사하는 행동도 같은 흐름에 넣는다. 기존 기록을 기다리는 수집함으로만 만들지 않는다. 홈·내 작업에는 날짜가 정해진 실제 행동을 연결하고 기존 업무 우선순위를 존중한다. 별도 자동 알림과 반복 일정은 이번 선택으로 승인된 것이 아니다.

## 6. AI의 후속 역할 제안

운영자가 선택한 기록이나 범위를 대상으로 반복 문제·미충족 요구·연결 가능한 자산을 찾아 기회 후보를 제안한다. 후보마다 출처와 가설, 확인할 질문을 함께 제공한다. 분석 범위 밖의 시장을 조사했다고 표현하지 않는다.

AI 제안과 확인된 사실을 구분한다. 후보가 검토 없이 실제 리드·거래·프로젝트로 생성되거나 고객 메시지로 발송되지 않는다. 사용자의 후보 수정·기각과 검증 결과는 보존한다. 같은 근거의 반복 제안을 줄이는 방식과 외부 정보 수집은 후속 설계에서 정한다.

## 7. 권장 구현 순서와 완료 기준

**1차 제안: 수동으로 시작해 한 기회를 끝까지 진행할 수 있는 흐름.**

- 기회 한 줄 저장·목록·상세·수정·재조회.
- 근거·가설·검증 결과·보류 또는 종료 이유 기록.
- 다음 행동 및 기존 리드·거래·프로젝트와 연결.
- 새 실행 대상이 필요하면 기존 생성 경로를 재사용하고 성공한 실제 레코드만 연결.

검수 시 한 줄 저장 후 새로고침 유지, 검증 결과 보존, 기존 대상 연결과 탐색 원문 유지, 보류·재개·종료를 확인한다. 중복 저장과 연결 재시도로 대상이 중복 생성되지 않아야 한다. 저장 실패 시 입력을 보존하고 실패한 실행 연결을 성공으로 표시하지 않는다. read 실패는 기존 HTTP 200 오류 봉투를 해석하며 빈 목록과 구분한다. 미연결 환경에는 preview를 명시한다.

**후속 제안:** 메모 등에서 선택해 기회로 연결하는 입구, 요청형 AI 후보 발견, 관심 분야 기반 외부 탐색. 외부 탐색의 출처·수집 주기·비용은 별도 결정한다.

UI 위치와 상세 레이아웃, 스키마·API·권한 및 원자성 계약은 기존 구현을 확인한 뒤 설계한다. 현재 문서는 제품 방향과 운영 흐름 초안이며 구현 계획을 대신하지 않는다.

## 8. 가상 사용 예시

“원장들이 운영 문제를 반복해서 말한다”는 관찰을 남긴다. 운영 진단 서비스라는 가설을 세우고 고객에게 현재 해결 방식과 불편을 묻는 할 일을 연결한다. 반응을 기록한 뒤 유료 파일럿을 논의할 상대를 기존 고객과 연결하고, 실행하기로 한 파일럿은 프로젝트로 관리한다. 반응이 약하면 이유를 남겨 보류하거나 종료한다.

이 예시는 실제 고객 데이터나 수요 확인 결과가 아니다.


## 9. 1차 구현 계약 (2026-09-13)

- 독립 사이드바 앵커 `기회 탐색`은 고객 연락 다음·프로젝트 앞이다. 경로 `/dashboard/discovery`와 ⌘K 카탈로그를 추가했다. 이 앵커 추가에 한해 07-15 사이드바 스펙의 primary 8개를 9개로 확장한다.
- 회사/개인 명시 구분, 포착/직접 발굴, 6단계 상태를 사용한다. 최초 입력은 제목 한 줄만 필수다.
- 탐색·검증 본문과 검토 날짜, 보류 조건·종료 이유, 실제 할 일/리드/거래/프로젝트 연결을 저장한다. `실행 연결`에는 리드·거래·프로젝트 중 하나가 있어야 한다.
- 새 실행 대상은 기존 생성 화면을 새 창으로 열어 저장한 뒤 검색해서 연결한다. 기회 저장 시 존재하는 동일 workspace 대상만 원자적으로 검증한다. 영업 레코드의 자동 생성은 추가하지 않았다.
- 수정에는 revision 비교와 request receipt를 적용한다. 클라이언트가 새 기회 ID를 먼저 배정하여 불확실한 저장 뒤 내용 수정도 중복 생성 대신 충돌 검토로 연결한다.
- 충돌 시 날짜·분류·본문·판단 이유·연결 대상을 모두 비교할 수 있다. 내 입력 전체 유지 또는 저장된 기록 사용을 명시적으로 선택한다.
- 저장마다 전체 snapshot 이력이 남는다. 목록 200건·이력 100건 단위 더 보기를 지원하고 불러온 범위의 현황임을 표시한다.
- GET `/api/hub/discovery`는 오류도 HTTP 200 봉투로 반환한다. POST는 Hub guard → repository → 공유 REST RPC로 저장한다. 탐색 read는 공유 클라이언트의 선택적 `strictRows`로 잘못된 JSON 응답을 빈 원장과 구분한다.
- DB 테이블은 service_role SELECT만 허용하고 저장 RPC에만 EXECUTE를 허용한다. 기존 Supabase 기본 권한을 먼저 회수하여 직접 쓰기 우회를 차단한다.
- N 생성, ESC/오버레이 닫기·미저장 변경 확인, `?new=discovery`, `?discovery=<uuid>` 딥링크, 모바일 가로 세그먼트를 지원한다.

검증과 운영 적용 명령은 [실행 기록](../plans/2026-09-13-opportunity-discovery.md)을 따른다. 개발용 임시 DB와 REST 어댑터에서 브라우저 저장을 검증했으며 실제 Supabase 운영 원장에 테스트 데이터를 쓰지 않았다.
