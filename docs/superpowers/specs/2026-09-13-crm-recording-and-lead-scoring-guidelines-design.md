## 0. 결정 상태와 한 문장 방향

**고객을 평가하기 위해 기록을 더 시키는 CRM이 아니라, 짧게 남긴 실제 대화에서 근거를 찾아 다음 약속을 놓치지 않게 하는 CRM.**

| --- | --- |

새 수치·등급 경계·시간 기준·알림 빈도는 아래에 구체적으로 제안하되 모두 승인 전 정책 후보다. 기존 권장 사항인 ‘기약 없음 한 달 뒤 재확인’도 Q120의 무기한 별도 렌즈를 넘어 오늘 연락으로 강제 승격시키지 않는다.

## 1. 해결할 문제와 성공 기준

현재 필요한 흐름은 **입력 → 저장된 원문 → 확인된 신호 → 고객 판단 → 다음 행동 → 실제 결과**다. 점수부터 채우게 하거나, 기록을 남겼다는 이유만으로 ‘고객 관심 상승’을 만들지 않는다.

사용자가 체감할 즐거움은 다음 네 가지다.

- 고객 화면을 열면 마지막 약속이 보여서 이전 기록을 다시 뒤지지 않는다.
- 자주 하는 기록은 버튼과 짧은 문장으로 끝나고, 긴 원문도 손실 없이 붙여넣을 수 있다.
- 저장된 내용이 타임라인에 조용히 붙고, 다음 연락일이 이어져 따로 할 일을 옮겨 적지 않는다.
- ‘왜 지금 이 고객인가’에 한 줄로 답하며, 틀리면 근거를 고치거나 추천을 쉽게 내려놓을 수 있다.

목표치 후보는 빠른 메모 10초 이내, 일반 연락 결과 30초 이내, 고객의 최근 약속 찾기 5초 이내다. 실사용 측정 전 성능 보장이 아니며, 긴 상담을 짧게 줄이도록 강요하지 않는다. 입력 속도보다 저장 누락·중복·오판 방지가 선행한다.

## 2. 접근안과 범위

| 안 | 장점 | 비용·한계 | 판단 |
| --- | --- | --- | --- |
| A. 모든 신호를 100점으로 합산 | 익숙하고 한 줄 정렬이 쉬움 | 미확인·활동량·관심·긴급도가 한 숫자에 섞임. 가중치가 아직 검증되지 않음 | 현행 점수 확대는 보류 |
| B. 세 축 등급 + 행동 우선순위 분리 | 무엇을 알고 무엇을 모르는지 설명 가능. 사용자는 점수를 입력하지 않음 | 근거와 상품 맥락 연결이 필요 | **권장** |
| C. AI 구매확률 예측 | 충분한 학습·검증 데이터가 있으면 복합 패턴 탐색 가능 | 현재 전환 정의·표본·평가 조건이 불충분, 과신 위험 | 후속 검토 |

이번 설계 범위는 기존 CRM·고객 연락·메모·홈의 연결 규칙이다. 새 범용 CRM, 별도 영업 기록, 대규모 스키마 교체, 메시지 자동 발송, 음성 녹음·전사, 전 고객 상시 AI 분석은 범위 밖이다. 기존 기록·쓰기 가드·receipt 패턴을 우선 재사용하되 CRM에 이미 모든 계약이 구현돼 있다고 가정하지 않는다.

## 3. 입력 지침: 하나의 기록창, 두 가지 저장 목적

### 3.1 빠른 메모와 연락 결과

| 목적 | 필수 입력 | 저장의 의미 | 하지 않는 것 |
| --- | --- | --- | --- |
| 메모 남기기 | 원문. 고객 화면이면 고객 연결은 자동 | 생각·관찰·붙여넣은 원문을 보관 | 연락 완료, 거래 단계 변경, 점수 상승, 새 연락 할 일 생성 |
| 연락 결과 남기기 | 한 줄 요약, 실제 반응, 다음 행동+날짜 / 기약 없음 / 후속 없음 중 명시적 선택 | 발생한 활동과 후속 계획을 기록 | 예정된 미팅을 완료로 간주, 고객 반응 추측, 실제 발송 |

제목·태그·상품 정보·예산·직책을 빠른 메모의 필수 필드로 만들지 않는다. 긴 원문과 목록용 요약은 별개이며 요약을 고쳐도 원문을 덮어쓰지 않는다. 업무 연결을 모르면 우선 메모로 저장하고, 잘못된 고객에 자동 귀속시키지 않는다.

‘연락 결과’ 저장도 모든 고객 할 일을 완료하는 명령이 아니다. 기존 할 일에서 진입했을 때만 해당 할 일 ID를 명시적으로 연결하며, 자유 기록은 다른 할 일을 닫지 않는다. 부재중 기록은 ‘연락 시도’의 결과이고 미팅·상담 완료의 증거가 아니다.

후속 계획은 세 상태로 구분한다. 날짜 있음은 약속/재검토 실행, 기약 없음은 다음 검토 필요는 있지만 날짜 미정, **후속 없음은 이번 연락에서 더 할 일이 없음을 명시**하는 상태다. 마지막 상태는 최종 거절·요청 처리 완료 등 이유를 짧게 남기는 이번 권장 예외이며 새 할 일·기약 없음 렌즈·날짜 넛지를 만들지 않는다. 해당 연락의 후속 종료이지 고객/거래 전체의 자동 종결 명령은 아니다. 이미 남은 다른 약속은 별도로 보존한다.

### 3.2 빠른 버튼 4개

| 버튼 | 미리 채울 것 | 사용자가 확인할 것 |
| --- | --- | --- |
| 통화 기록 | 현재 고객, 전화 채널, 현재 시각 후보 | 실제 통화 시각·요약·반응 |
| 부재중 | 현재 고객, 연락 시도 유형, ‘연결 안 됨’ 반응 후보 | 실제 시도 여부, 다음 시도 계획 |
| 자료 전달 기록 | 현재 고객, 자료 유형 선택 | 이미 보낸 사실·시각·자료. 버튼 자체는 전송하지 않음 |
| 데모·방문 기록 | 현재 고객, 연결 가능한 예정 일정 후보 | 예정/완료/취소/노쇼, 실제 참석자·결과 |

버튼 클릭은 입력 초안을 만들 뿐 활동이나 점수 근거를 생성하지 않는다. 일정이 지나면 ‘미팅은 진행됐나요?’라고 확인하며 자동 완료하지 않는다. ‘SW 관심·가격 우려·내부 논의’ 칩은 선택 후 편집 가능한 **관찰 문장 후보**다. 미리 선택된 긍정 반응을 저장하게 하지 않는다.

### 3.3 작은 템플릿 3개와 내 패턴

- 통화: 무슨 이야기였나 / 고객이 실제로 한 말 / 내가 약속한 다음 행동.
- 데모·방문: 보여준 것 / 관심·막힌 지점 / 다음 검토에 필요한 것.
- 견적 상담: 요청 품목·수량 / 고객이 확인하거나 걱정한 조건 / 누가 무엇을 언제 확인할지.

세 템플릿은 질문 틀이다. ‘예산 확보·결정권자 확인·반응 좋음’을 사실처럼 채우지 않는다. 모르는 답은 미확인으로 남기고, 템플릿 전환·닫기·고객 이동 시 작성 원문을 보존한다.

‘내 패턴으로 저장’은 사용자가 명시적으로 누른 경우만 만든다. 질문 구조·자주 쓰는 중립 문장·선호 채널만 저장하고 고객명·금액·날짜·고객 반응·과거 약속은 제외한다. 패턴 적용은 빈 칸에 제안하는 방식이며 기존 문장을 덮어쓰지 않는다. 즐겨찾기 순서는 사용자가 고정하며 자동 재배열하지 않는다.

### 3.4 저장 신뢰 계약

1. 화면에 먼저 나타나는 낙관적 카드는 ‘저장 중’이다. 서버 성공 receipt 뒤에만 ‘저장됨’으로 바뀐다. preview와 read error는 저장 성공·빈 데이터로 위장하지 않는다.
2. 초안은 업무·고객·탭 범위로 격리한다. 같은 탭 새로고침 복구와 브라우저/탭 종료 후 복구는 다른 보장이다. 후자를 보장하려면 별도 영속 초안 설계·민감정보 보관 정책이 필요하며 1차에서는 약속하지 않는다.
3. 보내기 전 요청 ID와 불변 payload를 보관한다. 재시도는 같은 ID, 새 기록은 새 ID를 사용한다. 저장 결과를 모르겠으면 조회·재시도로 확인하며 입력을 버리지 않는다.
4. 실패 시 원문·고객 연결·다음 날짜를 유지하고 재시도·복사를 제공한다. 저장소 용량 초과와 오프라인도 ‘복구됨’으로 거짓 표시하지 않는다.
5. 동시에 고친 기록은 버전 충돌을 보여주고 두 내용을 보존한다. 마지막 응답으로 새 입력을 덮지 않는다.
6. 연락 활동·해당 연락 할 일 완료·선택한 후속 계획 저장은 하나의 논리적 명령과 재시도 계약으로 묶는다. 날짜 있는 다음 행동일 때만 실행 할 일을 만들며, 기약 없음은 재검토 상태, 후속 없음은 신규 후속 생성 없음으로 처리한다. 거래 단계 변경이나 일정 확정은 별도 명시적 선택이다. 저장 실패 때 일부만 완료되는 상태는 허용하지 않는다.
7. 되돌리기 역시 서버 상태를 확인한다. 원문 저장과 점수 근거 정정 이력을 남기며, 외부 발송을 이미 취소한 것처럼 표시하지 않는다.

현재 CRM에서 2~6이 전부 충족된 상태는 아니다. §11의 구현 차이를 해소하기 전 ‘안전하게 연결 완료’라고 표시하거나 점수 자동 반영을 켜지 않는다.

## 4. 판단 단위와 근거 계약

### 4.1 누구의 무엇을 평가하는가

평가 단위는 **본인 담당 고객의 현재 도입·재구매·확장 검토 건**이다. 조직은 관계의 묶음, 사람은 발화·참석 주체, 상품은 적합성 판단 대상이다. 이미 기회가 있으면 그 ID를 쓰고, 미팅 전 문의는 문의/리드에 붙은 임시 검토 문맥을 사용한다. 점수를 만들려고 공식 리드·Opportunity를 조기 생성하지 않는다.

같은 기관의 새 문의는 기존 계약과 분리한다. 고객 성공·장애 대응·교육·갱신 관리도 신규 구매 관심과 합산하지 않는다. 계약 성공은 해당 영업 건의 결과이지 그 고객의 영구 고득점 근거가 아니다. 기존 ID에서 정식 기회 ID로 옮길 때 근거를 복사 가산하지 않고 동일 근거의 연결만 승계한다.

소유권 미확인은 담당 확인 대상으로 두며 내 집중 고객 자동 추천에서 제외한다. 이름 유사성만으로 사람·조직·영업 건을 자동 합치지 않는다. 여러 기회 중 대상이 모호하면 고객 수준 메모로 남기고 해당 기회의 점수에는 반영하지 않는다.

### 4.2 근거 한 건의 최소 계약

다음은 논리 데이터 계약이며 새 테이블을 만들라는 지시가 아니다. 기존 활동·메모 revision·일정·거래 ID로 표현할 수 있는 범위를 구현 계획에서 먼저 확인한다.

| 항목 | 규칙 |
| --- | --- |
| 식별 | workspace, 고유 evidence ID, 출처 객체 ID+revision, 실제 사건을 묶는 event group ID |
| 연결 | 조직·사람·현재 검토 건·상품. 모호한 연결은 미확인 |
| 주체 | 고객 / 운영자 / 시스템. 내가 보낸 메시지와 고객이 보낸 메시지를 구별 |
| 내용 | 신호 종류, 짧은 근거 발췌 또는 구조화 사실, 출처로 돌아가는 링크 |
| 시간 | 실제 발생 시각과 기록 시각 분리. 날짜만 아는지·시각까지 아는지도 보존 |
| 확정도 | 관찰 사실 / 고객 발언 / 운영자 해석 / AI 후보. 출처 확인 상태를 별도로 표시 |
| 유효성 | 현행 / 대체됨 / 철회됨 / 충돌 / 재확인 필요. 정정 근거와 이력 유지 |
| 계산 | 정책 버전, 기준 시각 as-of, 입력 근거 버전, 데이터 읽기 상태. 같은 입력·버전·시각이면 같은 결과 |

고객 발언은 ‘그렇게 말했다’는 사실이다. “예산은 확보했어요”를 재무 검증 사실로 표시하지 않고 고객 진술로 보존한다. 내부 해석·AI 추출은 후보이며 사용자가 원문과 대조해 확인하기 전 자동 점수 근거가 아니다. 자동 반영은 actor·사건·대상이 검증된 구조화 사실과 사용자가 확인한 근거로 한정한다.

영업 판단에 불필요한 개인 민감정보·성별·연령·출신에 대한 추정은 평가 특성으로 사용하지 않는다. 원문 보존은 무기한 보관을 강제한다는 뜻이 아니다. 기존 접근·삭제 정책을 상속하고, 원문 삭제/접근 철회로 확인할 수 없어진 근거는 현재 평가에서 제외한다. 감사 이력에 삭제된 원문 전체를 다시 복제하지 않는다.

### 4.3 중복·상충·정정

- 같은 통화의 메모·활동·일정은 한 사건이다. 메모 복제·템플릿 클릭·저장 재시도·중복 동기화는 새 신호가 아니다.
- 요청 → 일정 수락 → 실제 참석은 같은 여정의 서로 다른 상태다. 횟수 가산하지 않고 현재 확인된 가장 강한 상태를 사용한다.
- 한 번의 대화가 관심과 준비도 각각의 근거가 될 수는 있다. 단, 합산 총점은 없고 각 축에서 같은 사실을 중복 가산하지 않는다.
- 원문 정정·연결 변경·철회 시 해당 revision에 의존한 판단을 다시 계산한다. 타 고객에게 잘못 붙은 점수를 남기지 않는다.
- 동일 안건에 새 명시적 거절이 들어오면 과거 긍정만 계속 유지하지 않는다. 같은 주체·범위의 명확한 정정은 대체, 서로 다른 이해관계자의 상반된 말은 충돌로 표시하고 자동 결론을 멈춘다.
- 단순 수정 시각은 최근 연락일이 아니다. 미래 일정도 실제 접촉 이력이 아니며, 읽기 실패는 ‘접촉 없음’이 아니다.

## 5. 리드 스코어링: 합산하지 않는 세 축

표시는 **적합도 F / 고객 주도 관심 I / 도입 준비도 R**로 구분한다. 숫자는 서열형 등급이지 확률이나 등간격 점수가 아니다. 합계·평균·100점 환산·퍼센트·상중하 임의 총평을 만들지 않는다. 정렬에 쓰기 전 §8의 명시적 행동 조건을 먼저 적용한다.

각 축은 값 외에 미확인·충돌·재확인 필요·읽기 오류 상태를 가진다. **미확인(null)은 0점이 아니다.** 고객 카드 기본 화면에는 세 숫자 대신 가장 유용한 근거와 다음 약속을 보여주고, 상세에서 평가 근거를 펼친다.

### 5.1 F — 상품·업무 적합도, 0~3 또는 미확인

| 등급 | 충족할 관찰 조건 | 구분해야 할 것 |
| --- | --- | --- |
| 미확인 | 평가 상품이나 고객의 사용 목적을 모르거나, 검증된 상품 제공 범위와 연결하지 못함 | 규모·지역·연락처만으로 적합 판정 불가. 필수 조건 미확인은 F1에서 별도 표시 가능 |
| F0 · 현재 부적합 | 고객이 필수라고 확인한 조건을 현재 제안 상품이 충족하지 못함 | 확인된 충돌 조건과 상품 근거 필수. 가격 문의·무응답은 해당 안 됨 |
| F1 · 적용 가능성 | 고객의 실제 사용 목적 하나 이상을 확인했고, 현재 상품의 검증된 기능/제공 범위와 연결됨 | 기관 유형만 맞거나 웹사이트만 본 경우 미확인 유지 |
| F2 · 요구 조건 확인 | F1 + 고객이 확인한 필수 조건과 실제 제공 가능 여부를 모두 대조했으며 미해결 필수 제약이 없음 | 필수 조건 확인 전 ‘특별한 문제 없음’으로 승격 금지 |
| F3 · 적용 검증 | F2 + 해당 고객의 실제 사용 조건에서 데모·시험 사용 결과와 적합 피드백을 확인 | 데모 일정만 있거나 참석만 한 것은 부족 |

HW/SW·혼합 제안의 기능·설치/운영 제약·가격 권한은 승인된 상품 자료를 출처로 둔다. 이 문서는 존재하지 않는 상품 기능·판매 조건을 정의하지 않는다. 상품별 필수 조건 확인 틀이 준비되지 않으면 F2/F3 자동 산정을 열지 않는다. 규모와 KA 여부는 별도 사업 맥락이며 그 자체로 F를 올리지 않는다.

### 5.2 I — 고객 주도 관심 신호, 0~5 또는 미확인

아래 양의 신호 순서는 기존 프로필의 확정 순위를 유지한다. **숫자 매핑과 구체 경계는 이번 제안**이다. 여러 신호를 더하지 않고 유효한 가장 강한 신호 하나와 보조 근거를 보여준다.

| 등급 | 확인할 고객 행동 | 판정 경계 |
| --- | --- | --- |
| 미확인 | 아직 확인된 해당 상품 관심 신호가 없음 | 무응답·정보 부족·연락처 없음은 0이 아님 |
| I0 · 관심 없음 확인 | 고객이 해당 도입 건에 관심/필요가 없다고 명시 | 보류·시점 미정·가격 걱정과 구분 |
| I1 · 반복 탐색 | 서로 다른 관련 행사에 실제로 2회 이상 참석 | 신청·중복 체크인·한 행사의 여러 기록 제외 |
| I2 · 기관 맞춤 질문 | 자기 기관의 수업·운영 조건에 맞춘 구체 질문 | 단순 인사·자료 수신 확인·일반 가격표 요청 제외 |
| I3 · 깊은 문의 | I2 + 서로 다른 도입 판단 항목에 관한 추가 질문, 또는 이전 답변을 검토한 구체 후속 질문 | 문장 길이·메시지 수가 아니라 원문에서 확인되는 판단 내용 기준 |
| I4 · 방문 데모 요청 | 고객이 본인의 검토 필요에 따라 방문 데모/쇼룸 방문을 먼저 요청 | 내가 초대하고 고객이 수락한 것과 구분. 아직 실제 방문은 아님 |
| I5 · 자발적 쇼룸 방문 | 고객 주도 방문 의사와 실제 쇼룸 방문 완료 모두 확인 | 일정 경과·예약·내 초대로 참석한 사실만으로 승격 금지 |

내 초대의 수락도 중요한 1차 전환이다. 다만 고객 주도 관심의 순위를 임의로 만들지 않고 별도 전환 사건과 R에 반영한다. 가격 질문은 원문·검토 맥락·우려 항목을 저장하되 단독 등급을 부여하지 않는다. 기관 조건에 따른 구체 가격 비교라면 질문의 내용으로 I2/I3를 판단할 수 있고 ‘가격’ 단어 자체는 근거가 아니다.

통화 시도·발송 횟수, 내가 작성한 메모 수, 프로필 완성도, 검색 결과, 유입 채널, 담당자 확인, 기존 매출은 I의 가산 항목이 아니다. ‘연결 안 됨’은 고객의 거절이 아니며 반복 시도도 자동 감점하지 않는다.

### 5.3 R — 현재 검토 건의 도입 준비도, 0~3 또는 미확인

| 등급 | 확인할 사실 | 경계 |
| --- | --- | --- |
| 미확인 | 고객이 수락한 구체적인 다음 검토 단계가 없고 진행 불가 여부도 확인하지 못함 | 시점만 모르는 R1과 구분. 운영자의 일방적 다음 연락 계획은 고객 수락이 아님 |
| R0 · 진행 불가 확인 | 고객이 현재 도입을 중단했거나, 명시적 차단 조건으로 진행할 수 없다고 확인 | ‘좀 더 검토’·무응답·예산 미확인은 해당 안 됨 |
| R1 · 다음 검토 수락 | 고객이 미팅·데모·내부 검토·자료 검토 등 구체 다음 단계를 명시적으로 수락 | “네, 감사합니다”만으로 수락 추론 금지. 시점 미확인은 별도 표시 |
| R2 · 검토 경로 확인 | R1 + 고객이 밝힌 검토 담당/결정 절차와 다음 검토 시점이 확인됨 | 원장·대표 직함만 보고 구매 결정권 추정 금지 |
| R3 · 도입 조건 협의 | R2 + 대상 상품·범위/수량·목표 시점·견적/결재 다음 단계가 고객과 구체화됨 | 내 견적 발송만으로 부족. 합의되지 않은 필수 조건은 명시하고 승격 보류 |

예산·권한·시점을 한 번에 모두 물어야 기록이 저장되는 BANT 양식으로 만들지 않는다. 준비도는 대화에서 확인된 만큼만 보강한다. R3도 거래 성사·결제 완료·구매확률 90%를 뜻하지 않으며 거래 단계는 별도 기록의 사실을 따른다.

### 5.4 시간과 현재성

첫 정책에서는 임의의 일별 감점이나 무응답 횟수 감점을 넣지 않는다. 대신 근거의 현재성을 별도로 관리한다.

- I/R의 양의 신호는 **근거별 발생 시각**으로 현재성을 판단한다. 30일 경과한 근거는 ‘재확인 필요’로 분리한 뒤, 남은 현행 근거만으로 현재 등급을 선택한다. 현행 근거가 없으면 현재 등급을 보류하고 과거 등급·날짜만 보여준다. **30일은 검증 전 기본값 후보**다.
- 예를 들어 90일 전 I5와 오늘 I2가 있으면 현재 I2, 과거 최고 I5다. 오늘의 약한 신호·프로필 수정·메모 추가로 옛 I5를 갱신하지 않는다. 반복 참석·후속 질문 같은 복합 신호의 발생 시각은 그 조건을 새로 충족한 실제 사건의 시각이며 단순 기록 편집으로 바뀌지 않는다.
- I0/R0·필수 조건 불일치·명시적 연락 거절은 30일 뒤 자동 소멸시키지 않는다. 현재 적용 범위에 대한 새 확인·명시적 정정이 있어야 해제한다. 오래됐다는 이유로 다시 연락할 수 있다고 추정하지 않는다.
- 아직 유효한 고객의 구체적 미래 약속은 단순 30일 경과로 지우지 않는다. 해당 약속에 한해 약속 시점까지 유효하며 다른 관심 근거를 함께 연장하지 않는다.
- F는 상품 버전·고객 필수 조건 변경 시 재평가한다. 초기에는 단순 나이만으로 자동 강등하지 않는다. 근거 날짜는 항상 표시한다.
- 발생 날짜를 모르면 현재성 미확인이다. 기록 날짜로 대체해 ‘오늘의 관심’으로 승격하지 않는다.
- 충돌·필수 데이터 읽기 실패·조회 잘림이 있으면 영향을 받는 축의 현재 평가를 보류한다. 마지막 정상 평가가 있으면 시각과 ‘갱신 실패’를 붙여 참고로만 보여주고 새 추천의 근거로 쓰지 않는다.
- 취소·명시적 거절·요구 변경은 날짜 경과보다 우선하는 새로운 사실이다. 취소는 과거 수락 기록을 지우지 않되 현재 준비도와 다음 약속을 다시 확인하게 한다.

## 6. 등급보다 중요한 화면 구성

### 6.1 디자인의 판단 순서 — 2026-09-14 보강

먼저 볼 정보 → 바로 할 행동 → 입력 부담 → 피드백·복구 → 시각 완성도를 함께 설계한다. 편의성·가독성·저장 신뢰·접근성은 하나의 UX 기준이다. 디자인 우선은 저장 안전을 생략하거나 정보가 없는 자리를 장식으로 채우라는 뜻이 아니다.

기본 시각 방향은 기존 Moonstone Command Deck을 유지한다. 다크·쿨 실버, SUIT/JetBrains Mono, 중립 상태 라벨, 1px 경계, 일정한 밀도와 기존 모션 토큰을 사용한다. 신규 폰트·범용 대시보드 팔레트·밀도 전환기를 도입하지 않는다. 밝기·여백·정렬·문장 위계로 중요도를 만들고, 점수나 일상 단계를 여러 색으로 칠하지 않는다.

### 6.2 먼저 설계할 세 화면

CRM은 ‘관리 중 / 전체 고객 / 기약 없음’ 렌즈와 공통 고객 상세를 중심으로 한다. 고객 연락 탭은 실행 큐, 홈은 제한된 집중 대상, CRM은 관계 맥락의 정본이다. 각 표면에 다른 점수 엔진을 만들지 않는다.

| 화면 | 처음 보여줄 내용 | 핵심 동작·이동 계약 |
| --- | --- | --- |
| 고객 목록 | 고객명, 최근 대화 한 줄, 다음 행동·날짜. 검색과 관리 렌즈를 가까이 둠 | 행을 열어 상세 확인, 보조 빠른 기록. 기존 고객 생성/N 계약 유지. 목록 위치·검색·필터·정렬을 보존 |
| 고객 상세 | 중요한 요구/우려, 지난 약속, 최근 기록, 연결 거래. 평가 숫자는 전면에 크게 내세우지 않음 | ‘기록 남기기’를 중심 행동으로 두고 고객 정보 편집·전체 근거는 보조로 펼침 |
| 빠른 기록 | 누구의 기록인지, 원문 입력, 상황 버튼, 선택한 목적. 필요한 다음 행동만 순차 공개 | 메모는 짧게 저장, 연락 결과는 후속 계획까지 연결. 상세에서 진입하면 같은 Drawer의 기록 모드로 전환하고 돌아갈 위치를 보존 |

세 화면은 서로 다른 양식을 만들지 않고 같은 고객 문맥과 공통 기록 흐름을 사용한다. 상세 위에 편집창과 기록창을 겹겹이 쌓지 않는다. 목록에서 직접 진입하는 빠른 기록은 기존 compact Drawer 패턴을 사용한다. 어떤 경로든 활성 오버레이는 하나이며 닫을 때 초안·포커스·이전 위치를 복원한다. 화면/드로어마다 시각적으로 강한 주요 버튼은 하나로 제한한다.

큰 매출·점수 카드와 차트를 첫 화면의 기본 요소로 추가하지 않는다. 첫 시안은 적은 고객·긴 기관명·여러 약속·기록 없음·정보 일부 누락 등 다양한 합성 사례로 확인하고, ‘디자인 검토용 예시’임을 명시한다. 예시를 실제 운영 목록에 섞지 않는다.

### 6.3 점수와 넛지도 먼저 경험을 설계

고객 카드의 기본 문장은 예를 들어 **‘고객이 방문 데모 요청 · 도입 시점 미확인 · 목요일 11시 일정 제안 약속’**이다. 허구 예시이며 실제 고객 데이터가 아니다. 세 문구는 각각 I 근거·R의 빈칸·내 다음 행동이며 하나의 점수로 합치지 않는다.

상세의 읽는 순서는 중요한 요구/막힌 조건 → 최근 대화와 약속 → 연결 거래·일정·할 일 → 전체 원문·평가 근거다. ‘왜 이렇게 판단했나요?’를 열면 축별 근거 1~3개, 출처, 발생 날짜, 미확인 항목, 이전 판단과 달라진 이유를 보여준다.

‘데이터가 없음’, ‘고객 관심이 낮음’, ‘이탈 위험’, ‘연락이 급함’은 각각 다른 의미다. 신규 도입 점수가 낮다고 기존 고객에게 이탈 위험 라벨을 붙이지 않는다. 단일 총점의 색상·배지로 이 네 상태를 대신하지 않는다.

재미와 손맛은 선택한 칩의 분명한 상태, 고정된 내 패턴, 지난 약속의 짧은 상기, 서버 확인 뒤 조용히 추가되는 타임라인에서 만든다. 관심 점수 획득·연속 기록 배지·튀는 축하 모션으로 만들지 않는다. 신호를 지우거나 잘못된 해석을 고치는 동작도 시안에 포함한다.

### 6.4 시안에 반드시 포함할 상태

- 정상 읽기, 긴 기록, 기록 없음, 검색 결과 없음, 일부 데이터, preview, 읽기 오류.
- 작성 중, 저장 중, 서버 저장 확인, 실패 후 재시도, 버전 충돌, 초안 복구.
- 날짜 있음, 기약 없음, 후속 없음, 종료된 거래에 남은 실제 약속.
- 평가 미확인·현재 근거·과거 강한 근거·충돌, 추천 숨김·미루기·해제.
- 모바일 키보드가 열린 상태, 긴 한글 문장, 좁은 화면, 키보드 포커스, reduced-motion.

빈 상태에서는 다음 유용한 행동을 안내하고, 오류에서는 보존된 입력과 복구 경로를 보여준다. 저장 성공은 서버 확인 뒤에만 표현한다. 프로토타입의 모의 저장과 실제 저장은 별도로 표시한다.

## 7. 기록에서 스코어로 이어지는 확인 흐름

1. 사용자가 원문을 저장한다. 이 단계만으로 점수는 변하지 않는다.
2. 연락 결과의 구조화 사실 또는 선택적 분석에서 신호 후보를 만든다. 원문 발췌·누가 한 말인지·어느 도입 건인지 함께 보여준다.
3. 사용자가 후보를 확인·수정·제외한다. 구조화된 실제 사건은 같은 저장 확인에 포함할 수 있어 중복 확인을 강요하지 않는다.
4. 확인된 근거 집합으로 세 축을 결정한다. ‘새 점수 획득’ 대신 ‘방문 데모 요청이 기록에 반영됨’처럼 사실 변화를 알린다.
5. 다음 행동이 있으면 기존 할 일·일정과 연결하고, §8 자격 조건에 따라 해당 표면에 표시한다. 점수 상승만으로 할 일·알림을 무더기 생성하지 않는다.

AI는 기록 저장의 선행 조건이 아니다. 분석 실패·비용 제한·모델 미연결이어도 원문 저장과 수동 연락 결과는 작동한다. 개인 원문은 기본적으로 ClassIn에 복제하지 않고, 회사 전송 대상 요약은 기존 공식 기록 경계를 따른다.

## 8. 연락 우선순위: 자격 → 약속 → 선택

### 8.1 먼저 어떤 표면에 들어갈 수 있는지 결정

- **영업 평가/새 자동 집중 후보**는 본인 담당·현재 검토 건·유효 데이터·허용된 연락 범위를 확인한다. **약속 실행**은 이 조건과 분리한다. 종료된 영업 건이나 현재 검토 건이 없는 기존 고객도 확인된 미완료 의무가 있으면 홈·내 작업에 남긴다. 연락이 필요한 허용된 약속은 고객 연락의 기한 있는 약속 영역에도 표시한다.
- 명시적 연락 거절은 발신 추천에서 제외하지만 환불 처리·자료 준비 같은 내부 이행 의무까지 삭제하지 않는다. 금지 범위는 사람/조직/검토 건·채널·출처와 함께 기록한다. 적용 범위가 모호하면 자동 발신 추천을 보류하고 확인 대상으로 둔다. 이행 의무가 있다는 이유로 거절된 채널의 연락을 자동 허용하지 않는다.
- 고객 연락의 유입 근거는 Q117을 유지한다. 트래킹 시작, 날짜 도래, 상담·견적 단계, 무접촉 재검토를 각각 식별해 보여준다. 낮은 계층이 빈 화면을 채우려고 자동으로 쏟아져 들어오지 않는다.
- 다음 연락일이 미래면 날짜 도래 전 ‘오늘 연락’에 넣지 않는다. 단, 별개의 오늘 기한 약속이 있으면 그 약속을 보여준다.
- 기약 없음·무기한은 별도 렌즈다. 30일 재확인 후보도 그 렌즈 안에서 보여주고 새 연락일은 운영자가 정한다.
- 종료된 기회를 휴면 일수만으로 다시 열지 않는다. 새 인바운드·재구매 필요가 확인되면 별도 검토 건 후보로 연결한다.

### 8.2 표면마다 다른 정렬 목적을 명시

**홈·내 작업의 오늘 실행:** 실행 자격이 있는 기한 있는 항목만 기한 임박순으로 정렬한다. 동일 기한은 고객 > 프로젝트 > 콘텐츠(Q116), 그 뒤 수동 집중도, 안정된 ID 순이다. 점수·금액·채널·KA 여부가 약속 시각을 뒤집지 않는다. 날짜만 있는 약속과 시각이 있는 약속의 동순위 처리는 구현 전 공통 날짜 계약으로 고정한다. 임의 자정 마감으로 표시하지 않는다.

**고객 연락 탭:** 트래킹 / 날짜 도래 / 단계 / 무접촉을 유입 근거로 유지하면서, ‘기한 있는 약속’은 별도 상단 영역에서 기한순으로 보인다. 같은 날짜의 실행에서는 위 시간 규칙을 적용한다. 나머지 선별 후보는 Q117 계층순, 계층 안에서 수동 집중도순, 그 뒤 안정된 ID순이다. 이 ‘유입 계층과 약속 실행 분리’는 Q116·Q117을 함께 만족시키기 위한 **이번 권장 해석**이며 승인 전 현행 큐를 교체하지 않는다.

**CRM의 검토 후보:** 기본은 사용자가 고른 정렬을 보존한다. F/I/R 중 한 축으로 정렬할 수 있으나 미확인은 ‘낮음’에 끼워 넣지 않고 별도로 묶는다. 재확인 필요·충돌·오류는 현행 근거와 분리한다.

### 8.3 집중 고객 후보 조건 — 제안

수동 트래킹 고객과 실제 약속을 먼저 챙긴다. 자동으로 새 집중 후보를 제안하려면 아래 조건을 모두 만족시키는 안을 사용한다.

- 현재 미종결 검토 건이며 담당·연락 가능 여부가 확인됨.
- 구체적인 다음 행동과 도래한 날짜가 있음. 명시적 거절·진행 중단·필수 조건 불일치가 없음.
- 현행 근거로 F1 이상, 그리고 I3 이상 또는 R2 이상. 필요한 축이 미확인·오류·재확인 필요이면 자동 추천을 보류하되 직접 관리에서 숨기지 않음.

이는 **새 자동 후보를 좁히는 조건**이지 낮은 점수 고객의 실제 약속을 버리는 필터가 아니다. 그 조건을 통과한 후보끼리도 오늘 약속 시각을 먼저 지킨다. 임의 종합점수로 마지막 순서를 만들지 않는다.

집중도 높임/낮춤은 운영자의 선택이며 F/I/R 사실을 바꾸지 않는다. ‘낮춤’은 자동 집중 추천을 줄이지만 미완료 약속을 지우지 않는다. 긴급 KA 별도 표시도 최대 1건을 유지하며 규모 분모 미확인으로 KA를 새 자동 판정하지 않는다. 위험과 긴급함은 근거를 가진 별도 판단이어야 한다.

## 9. 넛지 지침: 기억을 돕고, 입력을 재촉하지 않기

모든 넛지는 대상·발생 이유·실제 근거·한 가지 행동·그만 보기/미루기를 가진다. 한 위치에는 하나만 보여주며 화면을 덮는 팝업을 기본으로 쓰지 않는다.

| 계기 | 표현 예시 | 하지 않는 것 |
| --- | --- | --- |
| 전송 실패/미확인 | ‘아직 저장 확인이 안 됐어요. 다시 확인할까요?’ | 성공 애니메이션, 입력 초기화 |
| 해당 고객 기록 시작 | ‘지난번에는 견적 비교표를 보내기로 했어요.’ | 다른 기회의 약속 섞기 |
| 다음 행동은 있는데 날짜가 없음 | ‘언제 다시 볼까요? 내일 · 3일 · 다음 주 · 기약 없음’ | 양식 전체를 빨간 필수 오류로 만들기. 명시적 후속 없음에 날짜 요구 |
| 예정 미팅 종료 시각 경과 | ‘예정했던 미팅은 진행됐나요?’ | 참석·긍정 반응 자동 기록 |
| 확인된 기록에 유용한 빈칸 | ‘도입 시점을 이야기했다면 한 줄만 남겨둘까요?’ | 점수를 올리려면 예산·권한을 채우라는 요구 |
| 기약 없음 재확인 | ‘다시 볼 시점을 정할까요?’ | 날짜를 임의 지정해 오늘 연락에 넣기 |

첫 적용의 빈도 제한 후보는 같은 사건·같은 누락에 같은 세션 1회다. 사용자가 닫으면 해당 계기는 다시 보이지 않는다. 새 사건·새로 합의한 날짜 등 의미 있는 변화 때만 새 계기를 만든다. 미루기는 사용자가 고른 재노출 날짜를 따르며 활동 기한 자체를 몰래 바꾸지 않는다. 초안 보관·저장 오류 표시는 안전 상태이므로 추천 숨김과 분리한다.

계기 ID는 업무 범위·대상·사건·넛지 종류로 안정적으로 식별하며 단순 재조회/화면 이동으로 바꾸지 않는다. 닫기·미루기 상태는 세션을 넘어 보존하고 같은 대상의 다른 탭에도 반영한다. 이 보존 계약을 갖추기 전 반복 노출 넛지를 자동 활성화하지 않는다. 날짜 프리셋은 선택 시 실제 날짜·요일을 함께 보여준다.

한 위치에서 겹치면 저장 실패 → 현재 기록의 다음 행동/날짜 → 지난 약속 → 선택적 정보 보강 순으로 제안한다. 미확인 필드를 매번 모두 묻지 않는다. 관심 신호가 없다는 이유로 질문을 반복하지 않는다.

디자인은 기존 [DESIGN.md](../../../DESIGN.md)의 토큰·프리미티브·모션 계약을 따른다. 칩·조용한 타임라인 삽입·마지막 약속 표시를 활용하되 배지 수집·연속 기록 점수·고객 온도 상승 애니메이션은 쓰지 않는다. 터치 영역은 44px 이상을 목표로 하고 색상만으로 상태를 전달하지 않는다. 기존 N 생성 단축키를 메모 전용으로 바꾸지 않으며 ⌘Enter 저장은 한글 조합 중 오발동을 막는다.

## 12. 도입 순서와 검증 게이트

### 단계 1 — UX 시나리오와 우선순위

핵심 시나리오는 ‘연락 전 마지막 약속 확인’, ‘통화 직후 짧은 기록’, ‘다음 약속 설정’, ‘나중에 맥락 다시 찾기’, ‘판단 근거 확인·수정’이다. 각 시나리오의 시작 위치·먼저 볼 정보·중심 행동·종료 상태를 정의한다. 저장 실패·기약 없음·후속 없음도 함께 다룬다.

완료 기준은 사용자가 해야 할 일을 화면 흐름으로 설명할 수 있고, 불필요한 필수 입력과 중복 기록이 제거된 설계안이 있는 것이다. 기존 기준을 재인터뷰하는 단계가 아니며, 화면 설계에 필요한 미결정만 좁힌다.

### 단계 2 — 정보 구조와 화면 골격

§6의 고객 목록·상세·빠른 기록을 먼저 설계한다. 데스크톱과 모바일에서 같은 고객 문맥을 유지하고, 상세를 닫았을 때 목록 위치·검색·필터가 남게 한다. 기본 노출과 펼쳐 볼 정보를 구분한다. 리드 스코어링은 숫자 배치뿐 아니라 판단 이유·미확인·수정 경로까지 화면 골격에 넣는다.

완료 기준은 세 화면을 오가며 다음 행동이 눈에 띄고, 어느 화면에서 무엇을 저장하는지 헷갈리지 않는 구조를 운영자가 선택한 것이다. 이 선택 전 실제 앱 레이아웃을 일괄 교체하지 않는다.

### 단계 3 — 시각·인터랙션 시안과 UX 확인

선택된 골격에 기존 디자인 토큰·컴포넌트를 적용하고, 버튼·칩·템플릿·타임라인·보강 넛지의 위계와 여백을 다듬는다. 선택된 시각안을 바탕으로 연결 가능한 프로토타입을 만들며, §6.4 상태를 처음부터 포함한다. 새 서비스나 운영 기록을 만들지 않고 검토용 데이터/동작임을 구분한다.

프로토타입을 사용해 설명 없이 마지막 약속을 찾고, 기록을 남기고, 다음 날짜 또는 후속 없음을 선택하고, 틀린 신호를 수정할 수 있는지 확인한다. 모바일 터치·가상 키보드·한글 조합·탭 순서·대비·모션 감소를 함께 검사한다. §1의 5초/10초/30초는 검토 목표이지 측정 전 합격 주장으로 쓰지 않는다.

**디자인 게이트:** 정상 화면만 예쁘게 완성했다고 통과하지 않는다. 핵심 흐름의 혼동·가려진 주요 행동·오입력·복구 경로 누락이 해소되고 운영자가 시안을 검토한 뒤 실제 기능 연결로 넘어간다. 현재는 시안 제작·프로토타입 검증 전이다.

### 단계 4 — 검토된 경험을 실제 기록에 연결

공통 기록창·네 버튼·세 템플릿·명시적 내 패턴·초안 복구·저장 receipt·다음 행동 명령을 검토된 화면에 연결한다. 기존 메모와 연락 활동을 중복 저장하지 않는 연결 규칙을 정한다. 구현 편의 때문에 화면 위계·상태 문구·필수 입력을 임의로 바꾸지 않고, 제약이 생기면 해당 흐름만 설계로 되돌려 확인한다.

첫 운영 적용 묶음은 이 단계의 기록·후속 행동까지다. 입력 유실·중복·잘못된 고객 연결이 재현되면 적용을 보류한다. 프로토타입에서 보인 복구 동작이 실제 서버에서도 성립하는지 별도로 검증하고 점수 자동화를 열지 않는다.

### 단계 5 — 근거 기반 스코어링과 제한된 추천

#### 5A. 실제 순서를 바꾸지 않는 비교 평가

승인된 상품별 조건표, actor/사건/기회 연결, 수정·충돌·읽기 오류 계약을 갖춘 뒤 세 축을 운영 순서와 분리해 계산한다. 기존 점수를 덮거나 실제 연락 순서를 바꾸지 않고 운영자 판단과 나란히 비교한다. 근거 확인에 AI가 필수인 구조로 만들지 않는다.

파일럿 제안은 **2주 동안 20~30개 검토 건**이며 표본을 못 채우면 기간보다 실제 사례를 우선한다. 모든 고객을 재인터뷰하지 않고 기존 기록과 새 실사용 기록으로 검토한다. 이는 통계적으로 구매확률을 검증하는 실험이 아니라 일상 판단과 설명의 오류를 찾는 단계다.

- 같은 시점의 근거로 운영자와 시스템이 판단한 이유를 비교한다. 나중에 성사된 결과를 과거 판단 입력에 섞지 않는다.
- 1차 수락과 결제 결과는 분리한다. 분모·관찰 기간이 확정되기 전 전환율 개선이나 정확도 수치를 발표하지 않는다.
- 입력 시간, 저장 실패 후 복구, 이전 약속 회수 시간, 잘못된 추천 사유, 불필요한 넛지 닫기를 관찰한다. 기약 없음/미확인 고객이 자동 추천에서 빠지는 편향도 직접 살핀다.

#### 5B. 검증 뒤 추천에 연결

§13의 안전 시나리오가 모두 통과하고, 파일럿에서 중대한 잘못된 귀속·저장 누락·금지 연락 추천이 0건이며, 운영자가 정책 버전과 남은 비차단 오판 목록을 검토해 승인한 뒤에만 추천에 연결한다. 홈/고객 연락/CRM이 같은 근거 버전을 쓰는지 확인한다. 초기에는 자동 실행이 아니라 이유를 보여주는 제안으로 제한한다.

적용 시 정책 버전·적용 시각·대상 범위·이전 버전을 남긴다. 롤백은 새 추천 소비를 끄고 마지막 안정된 표면으로 돌아가는 방식이다. 원문·실제 약속·수동 선택·새로 저장된 활동은 되돌리지 않는다. 구 writer 비활성화, 데이터 백필, 운영 배포는 각각 별도 검증·명시적 실행 절차가 필요하다.

## 14. 승인할 정책 묶음과 보류 사항

운영자에게 기존 업무 인터뷰를 반복하지 않는다. 아래 다섯 묶음이 이 초안에서 새로 제안하는 결정 단위다.

1. **점수 표현:** 총점 대신 F/I/R과 미확인·현재성, 기본 화면에는 근거 한 줄을 사용한다.
2. **입력 계약:** 원문 메모와 연락 결과를 분리하고 네 버튼·세 템플릿·명시적 패턴을 공통 기록창에 둔다.
3. **근거 규칙:** 고객 행동만 관심 근거로 인정하고 중복·추측·정보 충실도 가산을 제외한다. §5 등급 경계는 그림자 평가에서 먼저 확인한다.
4. **노출 정책:** 약속을 점수보다 먼저 지키고, 무기한 별도 렌즈·수동 집중도·§8.2 큐 분리를 유지한다. 30일 현재성·자동 후보 조건·넛지 빈도는 파일럿용 기본값으로 검토한다.
5. **적용 게이트:** UX 시나리오 → 화면 구조 → 시각·인터랙션 확인 → 실제 기록 연결 → 근거 평가·제한 추천 순서. 라이브 재채점·백필·외부 발송은 이번 문서 승인과 별개다.

KA 규모 분모, 상품별 필수 조건표의 담당/정본, 가격 질문 단독 순위, 전환율 분모·기간은 여전히 미정이다. 미정인 부분은 평가 미확인 또는 기능 비활성으로 처리하고 임의 수치로 메우지 않는다. 상세 저장 스키마·날짜 동순위 계약·기존 writer 전환 계획은 승인 후 구현 계획에서 확정한다.

## 15. 참고와 검증 기록

- 운영 기준은 §0의 저장소 정본과 프로필 §7·§8·Q116~Q121이다. 7월 이관 계획의 고객 수·적용 상태는 당시 이력이며 현재 운영 수치를 뜻하지 않는다.
- HubSpot은 적합도와 참여도를 별도 평가 축으로 구분하고 사건 빈도·기간·감쇠 등을 구성하는 방식을 제공한다. 이 문서의 세 축·등급·기한 우선 규칙은 그 제품의 정답이나 검증된 가중치를 가져온 것이 아니라 Moonlight 업무 기준에 맞춘 제안이다. [공식 점수 도구 설명](https://knowledge.hubspot.com/scoring/understand-the-lead-scoring-tool)
- 입력창은 자주 쓰는 핵심 입력을 먼저, 드문 세부 입력을 나중에 펼치는 점진적 공개 원칙을 참고한다. [Nielsen Norman Group](https://www.nngroup.com/articles/progressive-disclosure/)
- 2026-09-13 로컬 기준선: lead-enrichment.test.mjs 6개 테스트, check-followup-scoring.mjs 20개 점검, journal-browser-store.test.mjs와 journal-client.test.mjs 12개 테스트 통과. **현행 계산식과 메모 저장 패턴의 테스트**이며 새 정책 정확성·CRM 저장 신뢰·운영 DB 연결 검증이 아니다. 문서 전용 변경으로 앱 의존성 재설치·전체 빌드·운영 API 호출은 하지 않았다.
- v0.1 독립 문서 리뷰 3회: 정책 경계 3건(후속 없음, 종료 후 이행 의무, 근거별 현재성)과 인수 조건 문구 1건을 수정했다. 최종 완전성·일관성·명확성·범위·실현 가능성 PASS, 리뷰어 평가 9/10, 남은 지적 없음. 이 평가는 v0.2 추가분의 독립 검토·운영자 승인·앱 검증을 뜻하지 않는다.
