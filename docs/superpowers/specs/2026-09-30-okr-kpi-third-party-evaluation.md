# OKR·KPI 제3자 평가 — YC 관점 · a16z 관점, 그리고 쪼개기 설계 (2026-09-30)

> 상태: **평가 + 권장안(DRAFT).** 확정 아님. 운영자가 고르기 전까지 §6의 결정 항목은 모두 `권장`이다.
> 대상: 10월 개인 사업 OKR(목표 `cb625959-…`, [v3 스펙](2026-09-24-personal-business-okr-kpi-design.md))과 그것을 담는 OKR·KPI 화면(`work/goals`).
> 방법: 공개된 원칙(YC의 "one metric · talk to users · do things that don't scale", a16z의 초기 지표·퍼널·수익 품질 관점)을 렌즈로 삼아 **가상의 외부 심사**를 한다. 실제 두 곳의 의견이 아니다. 근거 수치는 운영 화면에서 읽은 것(10/1 시작 전이라 관측 0)과 v3 스펙의 숫자이며, 아래 계산의 가정은 그렇다고 표시했다.

## 0. 한 장 결론

| | 한 줄 평가 |

## 1. YC 렌즈

YC가 초기 창업자에게 반복하는 것: **하나의 숫자, 주간 리듬, 사람 이름, 배우는 속도.**

### 1.1 잘한 것
- **팔 수 있는 것을 지금 판다.** 이미 만든 소프트웨어 2종·강의·대행을 "만들기 금지" 하에 그대로 판다는 O는 *do things that don't scale*의 개인 사업판이다.
- **KR4(신규 개발 0)는 안티 골이다.** 창업자가 가장 자주 빠지는 함정("만드는 게 더 편하다")을 지표로 잡았다. 운영자 본인이 진단한 실패 패턴과 KR이 1:1로 대응한다 — 이런 자기 진단이 있는 OKR은 드물다.
- **결과 1개 + 행동 2개.** 결과(결제)만 두면 통제할 수 없고, 행동만 두면 바쁘기만 하다. 이 조합이 맞다.

### 1.2 지적
1. **"One metric that matters"가 없다.** 지금 화면은 KR 3개를 동등하게 보여 준다. 사업 전(pre-revenue) 단계의 YC식 단일 지표는 *주간 유료 결제 또는 주간 고객 대화 수*다. 결제는 월 1건이라 주간 신호가 되지 못하므로 **행동 KR 하나(가격 제시)를 주간 북극성으로 못 박는 편이 맞다**. (권장: KR2 = 주간 북극성)
2. **월 단위 하나의 약속선은 피드백이 너무 느리다.** YC는 주간 목표와 주간 성장률로 말한다. 월말에 "6건 중 2건"을 보면 이미 늦다. → §5.1 주간 페이스로 해결.
3. **사람 이름이 없다.** "가격 제시 6건"은 게시글·일반 안내 등으로 부풀릴 수 있는 숫자다. YC는 "첫 10명의 고객을 이름으로 안다"를 요구한다. 세는 단위를 *이름 있는 상대 1명*으로 내려야 한다(§4 최소 단위).
4. **추적이 일이 된다.** 관측 저장에는 근거 이름·안전한 주소·근거 발생 일시가 필요하다(완료 관측). 주 6시간 중 판매가 3.5~4시간인 사람에게 기록 1건이 2~3분이면, 주 10회 기록만으로 판매 시간의 10%가 추적으로 샌다. 추적은 **팔고 난 부산물로 자동 집계**되어야 한다(§5.4).
5. **배움의 자리가 없다.** 결제 0인 달의 진짜 산출물은 "왜 안 샀나"다. 스펙 §7 결정 규칙은 있지만 사유를 남길 곳이 KR에 없다(§4 학습 1줄).
6. **가격이 아직 없다.** 9/30(오늘)이 강의 가격·정원·대행 최소 단가 확정일이다. YC 관점에서 가격 미정은 판매를 시작할 수 없다는 뜻이므로, **모든 KR의 선행 마일스톤**이다. 그런데 앱에는 마일스톤 개념이 없다(§4).

### 1.3 YC식 한 줄 처방
"이번 주 가격을 말한 사람 이름 두 명은?" 이 질문에 앱이 매일 답해 줄 수 있어야 한다.

## 2. a16z 렌즈

a16z가 초기 지표에서 보는 것: **퍼널 전환율, 단위 경제(시간·비용 대비 매출), 수익의 품질과 반복성, 유통(어디서 오는가), 집중 위험.**

### 2.1 잘한 것
- **시간이라는 자본을 예산으로 삼았다.** 주 5~10시간을 판매 60% 이상 / 납품 30% 이하 / 유지 10% 이하로 나눈 것은 단위 경제의 출발점이다.
- **킬 기준을 미리 적었다.** 분기 결정 질문과 "결제 0 + 제시 6건 이상 → 오퍼·가격·고객군 중 하나만 바꾼다"는 규칙은 실험 설계에 가깝다.
- **회사 경계 위험을 지표로 올렸다**(회사 고객 대상 개인 판매 = 0).

### 2.2 지적
1. **KPI가 성과 지표가 아니라 제약 조건이다.** 현재 KPI 4개(판매 시간 비중, 회사 고객 개인 판매, 신규 개발, 에너지)는 모두 *지킬 선*이다. a16z식 KPI는 엔진의 성능이다.
   - 퍼널: 접점 → 대화 → 가격 제시 → 결제 각 단계 전환율
   - 효율: **시간당 매출**(1시간 투입당 얻은 계약금)과 오퍼별 회수 시간
   - 유통: 채널(구독자) → 대기 명단 → 결제 전환
   - 품질: 재구매·추천 비율(G2·G3 통과 조건)

   지금은 이 비율을 스펙 §7이 손으로 계산하도록 적어 두었을 뿐 앱이 보여 주지 않는다.
2. **수익 품질 구분이 없다.** 강의 일회 매출과 소프트웨어 반복 결제(G3의 핵심)가 같은 "결제 1건"으로 센다. 500만 원 방향(G3)은 *반복 매출 비중*이 관건인데 10월 지표로는 알 수 없다. (10월엔 불필요하나 11월 KR에서 필요)
3. **오퍼별 배분 판단 근거가 없다.** 3개 오퍼(강의·소프트웨어·대행) 중 어디에 시간을 더 쓸지가 사업의 핵심 결정인데 오퍼별로 시간·매출을 나눠 보는 단위가 없다.
4. **유통 귀속이 빠졌다**(스펙 v3가 의도적으로 10월 기록에서 뺐다). 한 줄이면 된다 — 결제·제시 기록에 "어디서 왔나" 하나. 비용은 낮고 정보는 크다.
5. **위험 게이트가 월말 자기 점검이다.** 취업규칙 확인(10/2)은 소프트웨어 판매 여부를 좌우하는 *존재 위협* 게이트인데 KPI 자리(월말, 0 유지)에 있다. a16z는 이를 **이진 게이트 KR**(날짜·완료/미완료)로 두라고 할 것이다.
6. **용량 검증(capacity check).** 시간 예산이 KR을 감당하는지 계산해 두면 좋다. 아래 가정으로 계산하면:

| 활동 | 월 건수(약속선) | 건당 시간 가정 | 월 시간 |
|---|---|---|---|
| 고객 대화 | 8 | 30분(준비 포함) | 4.0h |
| 가격 제시 | 6 | 45분 | 4.5h |
| 강의 모집·후속 | — | 월 3h 가정 | 3.0h |
| **합계** | | | **11.5h** |

주 6시간 기준 판매 60% = 월 약 15.6시간. 약속선은 가능하다(여유 약 4시간). 천장(대화 15·제시 12)은 합계 ≈ 19h로 **5~6시간 주에선 불가능**하다 → 천장은 10시간 주에만 유효한 조건부 목표다. (건당 시간은 가정이며 11월 실측으로 바꾼다.)

## 3. 두 관점이 만나는 곳 — 쪼개기의 원칙

1. **세는 단위를 가장 작은 실행 단위로 내린다.** 월 → 주 → 하루 → *이름 있는 사람 1명 + 다음 행동 1개*.
2. **KR은 목표, KPI는 엔진 상태.** 서로 점수 체계가 다르다(KR=약속선 대비 0~1, KPI=선 안·밖과 추이).
3. **추적은 부산물이다.** 팔면서 남는 기록(연락 기록·거래)이 자동으로 지표가 되게 한다.
4. **하루가 끝나면 배움 1줄.** 세지 못하는 것(왜 거절했나)이 다음 달 오퍼를 바꾼다.
5. **위협은 게이트로, 습관은 KPI로.** 한 번에 판가름 나는 것과 계속 지켜볼 것을 섞지 않는다.

## 4. 쪼개기 설계 — 6층 구조

```
방향   12개월 게이트 G0~G3 (월매출 기준)                     ← 스펙 §8, 바꾸지 않음
 └ O   월 목표 1개                                          ← 화면: 목표 카드
    ├ KR   약속선 있는 결과·행동 지표 3개 이하              ← 화면: 결과 KR / 선행 KR
    │  └ 주간 페이스  KR ÷ 주 수 (계산, 저장 안 함)         ← ★ 이번에 구현
    │     └ 일 단위  "오늘 가격 말할 사람 1명" 다음 행동    ← 권장(§5.2)
    │        └ 최소 단위  이름 있는 상대 1명 + 일시 + 결과  ← 권장(§5.3, 연락 기록 재사용)
    ├ 마일스톤  날짜 있는 한 번짜리 사건 (가격 9/30 · 규칙 10/2 · 모집 10/9)  ← 권장(§5.5)
    ├ 참고 지표  약속선 없이 기록만 (매출·대기 명단·발행)    ← 이번에 분리(구현됨)
    └ KPI  ┬ 지킬 선(가드레일)  선 안·밖 + 추이              ← 구현됨
           └ 엔진 지표(파생)   전환율 · 시간당 매출          ← 권장(§5.6, 스키마 필요)
배움   주 1줄 "왜 안 샀나 / 무엇이 통했나"                   ← 권장(§5.7)
```

**10월 목표의 실제 분해 예 (현재 데이터, 계산 결과)**

| KR | 월 약속선 | 주 페이스(자동 계산) | 하루 환산(주 5일) |
|---|---|---|---|
| 유료 결제 | 1건 | 주 기준 없음(0.23/주) → "기간 안 1건" | — |
| 가격 제시(1:1) | 6건 | 주 2건 | 이틀에 1건 |
| 고객 대화 | 8건 | 주 2건 | 이틀에 1건 |

결제는 주 단위로 쪼개면 의미가 없다(0.23건). 그래서 화면은 "기간 안 1건"으로만 말하고, **주 신호는 행동 KR(대화·제시)이 맡는다.** 이것이 §1.2의 "북극성은 행동 KR" 권장과 같은 결론이다.

## 5. 디벨롭 — 무엇을 어떻게

### 5.1 구현됨 — 월 KR의 주간 분해 (2026-09-30)
- 규칙(`lib/goal-concepts.js` `keyResultPace`, 단위 테스트 4개): 기대 진행선 = 기준값 + (목표 − 기준값) × 기간 경과율, 주간 페이스 = (목표 − 기준값) ÷ 기간의 주 수, 이번 주 몫 = 지금 값 − 이번 주 월요일 이전 마지막 확인 관측값(없으면 기준값).
- 판정: 목표의 10% 허용 범위 밖이면 "기준선보다 늦음/앞섬", 안이면 "비슷함", 측정 전이면 판정 없음.
- 화면: KR 행 아래 한 줄 `지금쯤 3.2건 · 기준선보다 늦음 · 이번 주 0/2건`. 시작 전엔 `시작하면 주 2건 페이스`.
- 늦음은 **글로만** 말한다(경고색·빨강 없음, DESIGN.md §5.2 no warning-by-default). 가장 크게 늦은 KR 하나만 카드 제안 한 줄로 올라오고 구조 제안보다 우선한다.
- 늘리기 KR만 대상. 줄이기·범위형은 "지금쯤 얼마"가 뜻이 없어 제외.
- 저장·마이그레이션 없음. 한계: 주 시작(월요일)·기간은 서울 기준 달력이고, 관측 이력이 기간 누적값이어야 이번 주 몫이 정확하다(현행 기록 규칙과 같다).

### 5.2 권장 — "오늘 할 한 가지" (마이그레이션 없음)
- 카드의 제안 한 줄을 오늘 화면(Home/오늘)의 한 줄로도 노출: "가격 제시 이번 주 0/2 — 오늘 1명". 기존 `SuggestionTip` 재사용, 새 패널 없음(표면 예산).
- 클릭하면 `오늘 연락`(revenue/followups)으로 이동. 저장 없음.

### 5.3 권장 — 세는 단위를 이름 있는 사람으로 (KR 자동 집계)
- 고객 대화 KR은 `contacts_recorded`(기록한 고객 연락) 자동 원천으로 새로 만들면 **기록 마찰이 0**이 되고 근거도 실제 연락 기록이 된다. 단 `source_key`는 만든 뒤 바꿀 수 없어 11월 목표부터 적용하거나 지표를 보관하고 새로 만든다.
- 가격 제시(1:1)는 연락 기록의 결과 종류에 "가격 제시" 표식이 있어야 자동 집계 가능 → 스키마 없이는 불가. **결정 필요**(§6-2).

### 5.4 권장 — 추적 마찰 낮추기
- 현행: 완료 관측 = 값 + 근거 이름 + 안전한 주소 + 일시. 서버가 강제(`invalid-evidence`)라 화면만으로 못 바꾼다.
- 대안 A(마이그레이션 없음): `최근 근거 불러오기`를 기본 켜기, 근거 주소 기본값을 가장 최근 것으로 채움 → 입력 3칸 → 1탭.
- 대안 B(스키마): 원천이 자동인 지표는 근거 입력을 아예 요구하지 않음. 이미 자동 원천은 이렇게 동작한다 — KR을 자동 원천으로 옮기는 것이 근본 해결.
- 주의: 근거를 가짜 자기 참조 주소로 자동 채우는 방식은 근거의 의미를 훼손하므로 채택하지 않는다.

### 5.5 권장 — 마일스톤 (한 번짜리 사건)
- 9/30 가격 확정 · 10/2 취업규칙 확인 · 10/9 강의 모집 오픈은 지금 스펙 문서에만 있다. 앱에서는 **목표에 연결한 할 일(기한 포함)**로 두면 스키마 없이 가능하다(목표↔업무 연결은 이미 있음).
- 카드에 "다음 마일스톤: 10/2 취업규칙 확인 · D-2" 한 줄(연결된 할 일 중 기한 가장 가까운 것). 연결된 할 일의 기한 값이 목표 읽기 모델에 실려 있는지 확인이 필요하다(§6-3).
- 존재 위협 게이트(취업규칙)는 KPI가 아니라 마일스톤이다. 결과가 "걸림"이면 KR1 구성이 바뀐다는 스펙 §6.1의 갈래를 마일스톤 완료 시 표시.

### 5.6 권장 — KPI 두 층: 지킬 선 + 엔진 지표
- 지금 KPI 화면 = 지킬 선. 여기에 **엔진 지표(파생, 저장 안 함)** 층을 더한다: 대화→제시 전환(제시÷대화), 제시→결제 전환(결제÷제시), 시간당 매출(매출÷판매 시간).
- 계산은 쉽다. 문제는 어떤 지표가 분자·분모인지 알아야 한다는 것 — 이름 매칭은 취약하다. **`metric.role`에 `funnel` 표식이나 지표 메타 키가 필요**하다 → 스키마 결정(§6-2).
- 샘플이 작을 때(n<10) 전환율은 소수 이벤트의 잡음이다. 표시는 "1/6" 분수와 "표본 작음"을 같이 보이고 %는 n≥10에서만.

### 5.7 권장 — 배움 1줄
- 관측 메모(`note`)와 연락 기록 메모를 재사용한다. 새 입력을 만들지 않고, 주간 실측(`GoalWeeklyActuals`) 화면 상단에 "이번 주 배운 것 1줄" 자리를 두는 안이 가장 작다. 저장은 하루 리뷰 `journal_entries`로. 결정 필요(§6-4).
