## 1. 문제

작업·실행 > 작업 지시 화면과 홈 첫 화면의 “승인 대기” 카드가 무엇을 위해 있는지 불분명하다. 실제로 쓸모가 있는지도 확인되지 않았다.

- 홈 트리아지는 오늘 2칸이다(`0/2`). 그중 1칸을 “승인 대기 12건” 카드가 차지한다.
- 그 카드의 “승인 큐 확인”을 누르면 작업 지시 목록으로 간다. 그런데 목록 위쪽에는 `dismissed` 행만 보인다.
- 목록 상단에는 개발자용 스키마 문자열(`세일즈 · { next_action, objection, followups[] }` …)이 노출돼 있다.

### 3.1 핵심 발견 — 게이트가 지키는 문이 사실상 없다

UI에서 호출되는 **자동 외부 실행 경로는 0개**다.
- 실행기를 부르는 곳이 0곳이다.
- 이메일 발송 API(`api/email/send`)는 승인된 `email_send` 주문을 요구한다. 하지만 이 API를 부르는 UI가 없고, 09-11 Q4에서 **삭제로 확정**됐다(`2026-09-11-integration-utilization-audit-and-plan.md:159`, 미실행).
- 카톡·전화는 운영자가 직접 복사해서 보낸다.

즉 운영자가 복사해서 보내는 행위 자체가 이미 사람 확인이다. 그 앞에 승인 단계를 하나 더 두면 게이트가 두 번이 된다.

### 3.2 연락 기록도 멈춰 있다

`crm_activities`는 115건이다. 그중 112건이 7월에 생성됐고, 마지막 생성은 **8/6 13:10**이다(서울 DB 기준). 이 데이터로 알 수 있는 것과 없는 것은 다음과 같다.
- **알 수 있는 것:** 최근 7주 동안 Moonlight에 남은 연락 기록이 0건이다.
- **추정:** 실제 후속 연락은 Moonlight 밖(카톡·전화·ClassIn)에서 일어나고 있을 수 있다. 이것은 운영자 확인이 필요한 추정이다.

B를 설계할 때 가장 큰 위험이 여기서 나온다(§8 Q1).

## 4. 확정 결정과 충돌하는 곳

1. **보류 표면이 첫 화면을 차지한다.** 사이드바(`hub-nav.js:125-133`)와 README(:216-225)는 이 페이지를 보류('준비 중')로 둔다. 그런데 홈 트리아지의 첫 결정이 이 페이지로 보낸다(`signal-targets.js:26`).
2. **09-23 지침 3과 맞지 않는다.** 이 지침은 첫 화면을 “긴급 KA 1 + 집중 고객 3–5 + Top 3”로 제한한다. 승인 카드는 셋 중 어디에도 해당하지 않는다.
3. **자문만 받는 기본값이 UI에서 지켜지지 않는다.** 09-09 계획 :77과 09-21 Eevee :382는 “자문만 받기”가 기본이라고 정했다. 그런데 Council을 UI에서 호출하면 기본값으로 큐 행이 생긴다. MCP 호출만 `false`가 기본이다.
4. **자동 범람 반대(Q117)와 충돌한다.** 정체 N일 자동 후속 제안이 이 결정과 맞지 않는다(09-20 세 축 기획 :64에 이미 “충돌”로 적혀 있다).
5. **“보류”가 실제로는 종결이다.** 버튼 이름은 “보류”지만 `dismissed`로 저장되고, 이 상태는 되돌릴 수 없다. 또 두 크론은 `proposed`만 중복 검사하므로, 보류한 딜이나 아이디어에 다음 날 같은 초안이 다시 제안된다.

## 7. 추천 설계

### A. 정리 + 삭제·되돌리기 (먼저)

**A0. 범위 — 인박스 캡처는 건드리지 않는다**
- A의 모든 변경은 **`source <> 'inbox'`인 행에만** 적용한다. 목록·건수·삭제·다시 열기 모두 해당한다.
- 인박스 캡처는 운영자 본인의 메모다. 정본 표면은 메모 > 받은함(`memo-ledger.js:51-56`)이다.
- 작업 지시 보기는 인박스 캡처를 목록에서 빼고, 목록 위에 한 줄로 안내한다: “캡처 메모는 메모 > 받은함에서 정리합니다”.
- **구현 위치:** GET `/api/hub/work-orders`에 **선택형** 쿼리 `scope=proposals`를 추가한다.
  - 이 값을 쓰는 곳은 세 군데다.
    - 작업 지시 보기
    - 데일리 브리프 카드
    - 데일리 브리프 “보조 정보” 요약. 서버 라우트 안에서 건수 함수(A3)를 `scope: "proposals"`로 직접 부른다.
  - 기본 동작은 바꾸지 않는다. 그래서 MCP `list_work_orders`(`legacy-tools.js:119-132`)는 인박스 행을 계속 받는다.
- DELETE API는 필터에 `source <> 'inbox'`를 건다. 인박스 행은 **오류로 거부되는 것이 아니라 필터에 걸려 지워지지 않는다**.

**A1. 공급 차단**
- `/api/hub/brand-mentor`의 기본값을 UI 호출까지 포함해 `createWorkOrder: false`로 바꾼다.
- 조언을 업무로 바꾸는 경로는 두 가지가 이미 있다. 09-21 Eevee의 “업무에 연결”은 아직 코드에 없으므로 B2에서 다룬다.
  - 떠 있는 멘토 위젯의 “할 일로 등록”(`floating-mentor-widget.jsx:852`)
  - 코칭·대화 화면의 “태스크로 등록”(`agents.jsx:347`)
- **공백 하나:** 브랜드 자문(Council) 패널(`agents.jsx:587-792`)에는 할 일 등록 버튼이 없다. A1 이후 이 패널에서 받은 `nextAction`을 할 일로 남기려면 “코칭·대화에서 이어가기”를 거쳐 위 대화 화면의 “태스크로 등록”을 써야 한다. 이 공백은 B2가 메운다.
- **테스트:**
  - `advisor-routes.test.mjs:63`(`true`면 행 생성)은 그대로 둔다.
  - `:70`의 실패 경로(`createWorkOrder: true` + 주문 생성 실패)도 유지한다.
  - “기본값이면 행이 생기지 않는다” 케이스를 새로 추가한다.
- **Engine 프롬프트 문구는 A에서 바꾸지 않는다(판단).** 대상은 “work_orders 승인 큐에 올릴 액션” 문구다(`brand-mentor/route.ts:89`, `sales-mentor/route.ts:72`, `advisor-directives.ts:77/89/107`, `advisor-guardrails.ts:224/230`).
  - 미커밋 수정이 있는 파일은 `advisor-directives.ts` 하나뿐이다. 나머지는 깨끗해서 A에서 고칠 수도 있다.
  - 그래도 운영자가 이 프롬프트 계열을 오늘도 튜닝하고 있어서(v17·v18 커밋), 일부 파일만 먼저 고치면 모드마다 안내가 어긋난다.

**A4. 삭제** (운영자 요구 = 확정, 방식 = 권장)
- **API:** `DELETE /api/hub/work-orders`
  - `hub-write-guard`를 거친다.
  - `workspace_id` 범위로 제한하고, `source <> 'inbox'`인 행만 지운다.
  - 본문은 `{ ids: [...] }`, 최대 50건(권장).
  - `ids`는 서버에서 UUID 형식을 검증한다. `inFilter`가 값을 따옴표로 감싸지 않기 때문이다(`supabase-rest/index.js:70-77`).
  - 삭제는 `deleteSupabaseRecord`(:488)로 한다. 필터(`id in (...)` · workspace · `source <> 'inbox'`)를 건 **한 문장**이므로 부분 실패가 없다.
- **응답 규칙:**
  - 입력 검증 실패는 HTTP 400이다.
  - 성공하면 `{ ok: true, status: "ok", deletedIds }`를 돌려준다.
  - 지울 행이 하나도 없으면 `deleteSupabaseRecord`가 `reason: "no-matching-row"`를 돌려준다(:512-514). 다른 탭에서 이미 지웠거나 모두 인박스 행인 경우다. 이것은 **오류가 아니라** `{ ok: true, status: "ok", deletedIds: [] }`로 바꿔 돌려준다.
  - 저장 실패는 HTTP 200 + `{ ok: false, status: "error", reason }`이다. 리터럴 `{ status: 502 }`는 쓰지 않는다. `state-usage.test.mjs:80`이 이 파일에서 금지한다.
- **UI:**
  - 행마다 **중립 휴지통 `IconButton`**(`aria-label="제안 삭제"`)을 둔다.
  - danger 색은 일괄 삭제 버튼 “선택 삭제 N건” 하나에만 쓴다. §5.3 red 예산 때문이다. 저장소 선례도 danger는 확인 단계에만 쓴다(`customers.jsx:400`, `projects.jsx:2766`).
  - 행 선택은 `Checkbox(label)`로 한다.
  - “이 목록 모두 선택”은 현재 필터에서 **최대 50건**까지만 고르고, “한 번에 50건까지”를 표시한다. API 상한과 같다.
  - 지연 쓰기가 걸려 잠긴 행(A5)은 선택에서 빠진다.
- **지연 쓰기 + 되돌리기:** Revenue 삭제와 같은 계약이다.
  1. 행을 목록에서 먼저 뺀다(낙관 제거).
  2. `useUndoableAction` 3.5초 창을 연다.
  3. 창이 닫히면 실제로 DELETE를 보낸다. 페이지를 떠나거나(`pagehide`) 언마운트되면 훅이 즉시 실행한다.
  4. 결과를 처리한다.
     - `ok: true`면 행을 뺀 상태로 두고 건수를 다시 읽는다. `deletedIds`가 비어 있어도 되살리지 않는다.
     - `ok: false`일 때만 행을 복원하고 오류를 표시한다.
- **기본은 영구 삭제(권장).** 기록 보존 여부는 §8 Q2.
- **메모 링크 연쇄는 A에서 문제가 되지 않는다.** `task_memo_links`는 `on delete cascade`지만(0025), 링크는 인박스 캡처에만 생긴다(`link_memo_task_v1`). 인박스는 A0에서 제외되므로 별도 링크 수 조회는 두지 않는다.

**A5. 되돌리기** (운영자 요구 = 확정, 방식 = 권장)
- **즉시 되돌리기:** 작업 지시 보기의 승인·보류·완료·삭제에 모두 3.5초 창을 둔다. 지금은 홈 카드의 보류에만 있다(`daily-brief.jsx:988-1008`). 작업 지시 보기의 보류는 즉시 확정된다(`agents.jsx:1059`).
- **행 잠금:** 한 행에 지연 쓰기가 걸려 있는 동안 그 행의 다른 동작은 비활성화한다.
  - 같은 key로 다시 예약하면 이전 쓰기가 조용히 버려진다(`use-undoable-action.js:43-52`).
  - key를 다르게 하면 승인 직후 3.5초 안에 “완료로 표시”를 눌렀을 때 `proposed→executed`가 전송돼 400이 난다.
- **다시 열기:**
  - `TERMINAL_STATUSES`(`work-orders.js:12`)에서 `dismissed`를 뺀다.
  - `isAllowedTransition`에 `dismissed → proposed`, `approved → proposed`를 추가한다.
  - 다시 열 때 이렇게 기록한다.
    - `decided_at`을 비운다.
    - `proposed_at`을 지금 시각으로 바꾼다. B8 만료 기준이 “마지막으로 열린 시각”이기 때문이다.
    - 처음 제안 시각은 `body.firstProposedAt`에 한 번만 남긴다. 이미 있으면 덮어쓰지 않는다.
  - `executed`는 종결 상태로 유지한다. 실행된 것을 되돌린 척하지 않기 위해서다.
  - `executing`에서도 다시 열 수 없다(`work-orders.js:210`). 그래서 버튼 “다시 열기”는 **`approved`·`dismissed` 행에만** 표시한다. ‘실행 전’ 필터 안의 `executing` 행에는 버튼이 없다.
  - 호출은 기존 POST 결정 라우트에 `status: 'proposed'`를 보낸다.
  - `work-orders.test.mjs:114`(dismissed 종결 단언)를 새 규칙으로 고친다.
- **충돌 처리:** `followup`을 다시 열면 0017 부분 유니크 인덱스를 위반할 수 있다. 이때는 `reason: "open-followup-exists"`를 돌려주고 “같은 딜에 열린 후속 제안이 이미 있습니다”를 표시한다.
- **마이그레이션 불필요.** DB에는 상태값 CHECK만 있다(0011:51, 0012:9). 전이 규칙은 JS에만 있다(`work-orders.js:206-212`).

- **B5. `work_orders`는 출처·감사 기록으로 바뀐다.** 운영자가 비워야 하는 대기열이 아니다. 작업 지시 보기는 “제안 기록”으로 축소하거나 자동화 Runs에 흡수한다(§8 Q5). 코드 작업 보기(09-21 확정)는 유지한다.
- **B6. 학습 루프를 복구한다.** 성과 연결은 `crm_activities`를 기준으로 한다. 09-23 계획 1단계 2번과 같은 정본이다. UI에서 읽는 곳이 없는 `outreach_outcomes`는 쓰지 않는다. MCP `decide_work_order`의 성과 기능도 이때 실제 동작으로 되살린다.
- **B7. 공급 위치를 정한다.** 크론 3개를 Vercel 구성, 로컬 예약, 수동 버튼 중 어디서 돌릴지 정해야 한다. Vercel 배포 환경 변수가 0개라 지금은 어디서도 돌지 않는다. 페르소나를 어디서 돌릴지(deep-config :77-83 미정)는 별개의 질문이다.
- **B8. 만료** (A에서 이동)
  - 공급이 다시 살아나면 쌓임을 막기 위해 “만료”를 도입한다. 상수 하나, 읽을 때 계산한다.
  - 기준 시각은 **마지막으로 열린 시각**이다. A5가 다시 열 때 `proposed_at`을 지금 시각으로 바꾸므로(처음 시각은 `body.firstProposedAt`), 이 기준은 곧 `proposed_at`이다. 그래서 다시 연 제안이 곧바로 만료되지 않고, 건수 쿼리에도 그대로 필터로 걸 수 있다.
  - 만료 판정은 서버 조회 함수(`getWorkOrders`·`getQueueSummary`)와 MCP 조회가 같은 순수 모듈을 쓴다.
- **B9. 인박스 캡처의 리드 승격을 되살린다.** 사라진 `promoteCaptureToLead`를 메모 > 받은함에 복구한다. 8/4 병합에서 빠진 회귀다.
- **B10. Engine 프롬프트 문구를 정렬한다.** 운영자 작업이 커밋된 뒤, “work_orders 승인 큐에 올릴 액션” 문구를 B의 흐름(업무에 연결·대상 위 초안)에 맞춘다(A1 참조).

## 8. 열린 질문

1. **B1의 전제가 성립하는가.** B1은 운영자가 Moonlight에서 연락을 기록한다고 가정한다. 그런데 서울 DB에서 `crm_activities`의 마지막 생성은 8/6이다(§3.2). 이 가정이 틀리면 B1의 위치(딜 행)도 쓰이지 않는다. 아래 “과제”의 관찰 결과로 정한다.
2. **삭제는 영구 삭제인가, 기록 보존인가.** A는 영구 삭제를 권장한다. 다만 B5에서 `work_orders`를 출처 기록으로 쓰려면 보존(숨김 표시)이 나을 수 있다.
3. **AI가 구조화한 내부 등록을 자동으로 할지, 그 자리에서 1클릭으로 확인할지.** 프로필 :37(확정)은 자동 등록을 허용한다. 09-23 지침 1(초안)은 1클릭 승인을 요구한다. 둘 다 “모아 두는 큐 없음”과는 양립한다.
4. **`email_send` 삭제(Q4 확정·미실행)를 A에 넣을지, 별도 작업으로 둘지.**
5. **작업 지시 보기의 최종 형태.** “제안 기록”으로 둘지, 자동화 Runs에 흡수할지.
6. **만료 일수(B8).** 권장값은 7일이다. 후속 초안은 시효가 짧다.
