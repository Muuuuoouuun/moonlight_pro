# 저장 레퍼런스 → 내 관점 → Studio 초안

> 작성: 2026-09-20 · 상태: **DRAFT / 권장안 · 구현 미착수**
>
> 2026-09-21 우선순위 변경: 운영자가 사용성·편의성, 레퍼런스 모아보기와 편한 입력을 첫 구현으로 지정했다. **첫 구현 순서는 [입력·모아보기 기획](2026-09-21-reference-capture-and-browse-usability-design.md)이 우선**하며, 아래 Studio 연결·고정 packet은 후속 제안이다. 자료 자체의 편집은 허용하고 생성 당시 근거를 별도 보존하는 방향으로 후속 계약을 재검토한다.
>
> 요청: Instagram·YouTube 정리 자료의 활용 가치 평가, 원본에 근거한 인사이트 정리, 개인 글쓰기 연결. 후속 요청은 **“커밋, 기획”**이다. 자료 보관과 기획서 커밋은 요청 범위이며, 아래 제품 확장은 구현 승인이나 운영 적용 완료를 뜻하지 않는다.
>
> 관계: [2026-09-12 콘텐츠·Studio 설계](2026-09-12-content-notes-drafts-ai-workflow-design.md)와 [2026-09-11 브랜드·콘텐츠 설계](2026-09-11-brand-content-refocus-proposal.md)의 **외부 자료 입력 경로를 보완하는 제안**이다. 기존 저장·AI 후보·분기·복원 계약을 대체하지 않는다. 전체 운영 전제는 [개인 운영 OS 기준선](2026-07-13-moonlight-personal-operator-os-deep-design.md), 사용자 업무 근거는 [운영자 프로필 §12](../../operator-workflow-profile.md)을 따른다.

## 1. 판단과 목표

**활용 가치가 있다. 다만 가치는 저장량보다 “지금 쓰고 싶은 질문에 맞는 출처를 찾고, 내 생각을 보태 초안으로 만드는 것”에 있다.** 저장한 콘텐츠를 사용자가 동의하는 주장이나 사용자의 문체로 간주하지 않는다. 이번 조사로 발행 성과나 시간 절약 효과가 입증된 것은 아니다.

운영자는 흥미로운 영상과 일상 생각을 먼저 저장하고, 쓸 수 있을 때 골라 제작한다. 무엇을 쓸지 정하는 데 가장 많은 에너지가 든다. 따라서 전체 자료 보관과 지금 쓸 소재를 구분하고, 기존 소재함·Studio에 소수의 선별 자료를 연결한다. Threads를 첫 초안 형식으로 제안하되 개인/회사 범위와 브랜드는 사용자가 선택한다.

목표 행동은 하나다. **질문 하나와 출처 1–3개를 골라, 내 주장과 실제 경험을 구분해 기록하고, 근거를 다시 확인할 수 있는 초안 하나를 만든다.**

## 2. 이번에 확보한 자료와 한계

재현 가능한 정리본은 [레퍼런스 아카이브](../../research/2026-09-20-reference-writing/README.md)에 있다. 상세 분모·확인 방법은 [coverage.json](../../research/2026-09-20-reference-writing/coverage.json), 인사이트와 예시 초안은 [writing-kit.md](../../research/2026-09-20-reference-writing/writing-kit.md)를 따른다.

| 항목 | 확보 범위 | 해석 시 주의 |
| --- | --- | --- |
| 통합 콘텐츠 목록 | 370건: YouTube 영상 265, Instagram 게시물 103, Facebook 1, YouTube 커뮤니티 1 | 전체 원문을 이번 작업에서 재확인한 수가 아니다 |
| YouTube | 재생목록 소속 296건 → 고유 영상 265건, 요약 264건 | 자막 기반 요약 194건과 기존 영상 분석 70건을 구분한다. 멤버십 제한 1건은 미확보다 |
| Instagram | 저장 85건 + DM 공유 18건 | DM 외부 링크 2건은 위 통합 목록에 별도 플랫폼으로 포함한다. 전체 저장 컬렉션·전체 DM 수집을 뜻하지 않는다 |
| 선별 인사이트 | YouTube 14 + Instagram 12 = 26개 | 새로 확인한 원자료는 자막 구간 10개·공개 캡션 12개다. 나머지 YouTube 4개는 기존 영상 분석 응답 검토다 |
| Threads 보충 | 공유된 프로필 2개, 프로필 탐색에서 발견한 공개 글 5개 | 프로필은 370건에 합산하지 않는다. 발견한 글을 사용자가 공유한 원글로 표시하지 않는다 |

캡션 열람은 영상 전체·음성 확인과 다르다. 출처에서 주장을 확인한 것과 그 주장이 사실인지 독립 검증한 것도 다르다. 수치·건강·심리·성과 주장은 확인 수준을 유지하며, 편집자의 적용 제안을 원저자의 발언으로 바꾸지 않는다.

## 3. 사용자 흐름과 선택한 접근

| 접근 | 얻는 것 | 한계 | 판단 |
| --- | --- | --- | --- |
| A. 문서 아카이브와 수동 붙여넣기 | 지금 바로 전체 목록·26개 인사이트·예시 초안을 사용 | 출처와 확인 수준을 매번 옮겨야 함 | P0에서 제공 |
| B. 선별 출처를 기존 소재함·Studio에 연결 | 출처·내 관점·AI 입력이 같은 소재에 남음 | 최초 선별과 발췌는 직접 수행 | **다음 구현 권장** |
| C. 별도 레퍼런스 DB·자동 수집·추천 | 대규모 검색과 반복 수집 가능 | 수집 제약·중복·확인 수준·운영 비용까지 관리 필요 | 반복 사용 결과를 보고 후속 결정 |

권장 흐름:

1. 아카이브에서 주제·질문을 보고 자료를 고른다. 첫 후보는 설명과 이해 확인, 기존 해결방식 관찰, 위임의 맥락과 결정 범위다.
2. 기존 소재 입력에서 **레퍼런스 추가**를 펼쳐 URL, 핵심 내용, 확인한 부분을 입력한다. 한 소재에 1–3개를 연결한다.
3. “이걸 보고 쓰고 싶은 질문”을 적는다. 주장과 경험은 선택 입력이며, 비워 둔 경험은 AI가 채우지 않는다.
4. 소재를 저장하고 Studio에서 독자·메시지·관점을 다듬는다. 선별 출처는 펼쳐 읽고 원본으로 돌아갈 수 있다.
5. AI 초안 후보를 요청하면 저장된 자료와 내 기획만 전달한다. 근거가 부족한 부분은 기존 `missing`에 표시한다.
6. 사용자가 후보를 비교·적용·수정한다. 복사와 내보내기는 현재 원고 본문만 대상으로 한다.

예를 들어 “설명을 더 해야 하나?”라는 질문에 이해 확인 관련 자료를 연결하고, “상대가 자기 상황에 적용해 말할 수 있는지 확인하자”라는 관점을 적는다. 실제 수업·영업 경험을 입력하지 않았다면 “내가 해 보니 전환율이 올랐다” 같은 경험담은 생성하지 않는다. 이 예시는 제품에 넣을 업무 데이터가 아니다.

## 5. P1 데이터 계약 — 권장안

새 테이블 없이 `content_items.meta.reference_packet`에 **소재를 만들 때 선별한 외부 자료의 고정 사본**을 저장한다. variant 메타에 중복하지 않는다. 내 관점은 기존 `source_idea`와 `meta.brief`가 정본이며 packet에 다시 넣지 않는다.

| 위치 | 내용·규칙 |
| --- | --- |
| packet `schema_version` | `1` |
| packet `selected_at` | 서버가 기록하는 선별 저장 시각. 원문 확인 시각을 대신하지 않음 |
| packet `sources` | 1–3개. 각 소재 내 `[R1]`–`[R3]` 식별자를 서버가 부여 |
| source 식별 | `source_id`, `platform`, `kind`(video/post/profile/article), `url`, `title`, 선택 `creator` |
| source 관찰 | `observed_claim`(출처에서 확인한 핵심 내용), `locator`(타임스탬프·슬라이드·캡션 위치), `coverage`(실제 읽은 범위) |
| source 확인 방법 | `evidence_level`: `transcript_excerpt` / `caption` / `slide` / `video_analysis` / `metadata_only` |
| source 한계 | `limitations`, 선택 `reviewed_at`(모르면 비움), `claim_verification`: 기본 `not_independently_checked` |
| 활용 의도 | `use_as`: `idea` / `structure` / `attributed_claim`. 출처를 곧바로 입증된 사실로 승격하지 않음 |
| `source_idea` | 내가 쓰고 싶은 질문과 저장 이유. 외부 요약 전체를 복제하지 않음 |
| `meta.brief` | 기존 `audience/purpose/message/angle/evidence/ending` 사용. 경험은 사용자가 제공한 것만 `evidence`에 기록 |
| `content_variants.body` | 출처 연결 경로의 첫 생성은 빈 문자열. 이후 사람이 쓰거나 후보를 적용한 실제 원고 |

검증 한도 제안: 출처별 핵심 내용 1,200자, 확인 범위·한계 각각 600자, locator 200자, 제목 200자, URL 2,048자, packet 전체 UTF-8 24KiB 이하. URL은 HTTP(S), 사용자명·비밀번호 없는 형식만 허용한다. 한도 초과는 필드를 짚어 고치도록 하고 조용히 잘라내지 않는다. AI 전체 컨텍스트의 기존 한도는 별도로 유지한다.

`metadata_only`와 `kind: profile`은 글의 내용 근거로 사용하지 않는다. 외부 주장에 사용하는 출처는 핵심 내용·확인 범위를 요구한다. 원자료 사실 검증을 수행한 추가 근거가 없으면 기본 검증 상태를 바꾸지 않는다. 플랫폼 종류나 “자막 있음”만으로 신뢰 점수를 부여하지 않는다.

**P1에서는 저장 후 packet을 읽기 전용으로 둔다.** 저장 전에 출처 입력을 검토하게 하고 이 제약을 알린다. 수정이 필요하면 새 소재에 자료를 다시 입력한다. P1은 자동 복제 기능을 포함하지 않으므로 질문·brief·작성 중 원고의 이관은 수동 복사이며, 새 소재의 첫 원고는 여전히 빈 상태다. 기존 소재와 원고는 그대로 남는다. 이 부담이 반복되면 P2에서 출처 수정·스냅샷 버전 관리를 먼저 검토한다. 자동 동기화나 원문 수정 추적은 제공하지 않는다. 일반 Studio 저장과 구형 수정 경로에서 packet을 보존하며, 구형 경로로 이를 덮어쓰는 요청은 거부한다. 내 질문·brief·원고는 기존 편집 경로를 유지한다.

## 6. 화면 범위

새 사이드바나 전체 라이브러리 화면을 추가하지 않는다. 기존 소재 입력에 접힌 **레퍼런스 추가**, Studio 상세에 읽기 전용 **참고한 자료**를 둔다. 사용자가 원시 JSON을 입력할 필요는 없다. 기본 필드는 URL·핵심 내용·확인 범위이며, 제목·확인 방법·한계는 같은 출처 카드에서 보강한다. URL만으로 읽은 상태나 요약 완료 상태를 만들지 않는다.

자료 카드에는 원본 열기, 실제 확인 방법·범위, 한계를 함께 표시한다. 프로필은 프로필이라고 명시한다. 내 질문과 외부 주장을 별도 입력란에 두며, 아직 내 주장이 없으면 질문만 저장할 수 있다. 출처 저장 직후에는 빈 원고와 “초안 작성” 행동을 보여 준다.

[DESIGN.md](../../../DESIGN.md)의 토큰·프리미티브·모션·상태 계약을 따른다. `Button`, `EmptyState`, 적절한 `TruthBadge/CertaintyBadge` 등을 기존 규약에 맞춰 재사용하고, 자료의 확인 수준을 성공 색으로 과장하지 않는다. 모바일 390px과 데스크톱 1440px에서 URL·긴 한국어 내용·카드 펼침을 확인한다. 기존 일반 소재 입력의 본문 보존 동작은 유지한다.

## 7. AI 생성·출처 추적

AI 입력은 브라우저가 보낸 임의 자료가 아니라 DB에서 읽은 item의 packet을 재검증해 조립한다. 저장되지 않은 기획 변경은 기존 저장·생성 순서를 따른다. 기존 지침인 자료 속 명령 무시, URL fetch 금지, 경험·수치 날조 금지와 `missing` 응답을 유지한다.

출처의 관찰된 주장, 사용자의 해석, 사용자가 제공한 경험을 구분해 전달한다. 외부 주장을 사용하면 원고에서 필요한 귀속 표현과 `[R1]` 같은 식별자를 제안할 수 있으나, 원고의 모든 문장에 기계적으로 인용을 붙이지 않는다. 제공되지 않은 출처 ID는 후보 검증에서 거부하고 복구 가능한 오류로 남긴다. `[R1]`은 내부 추적용이며 그 자체로 공개 인용을 완성하지 않는다. 외부 주장을 인용한 원고에는 작성자·자료명·원본 링크로 연결되는 표현을 제안하고, 복사 시 식별자만 남아 있으면 출처 보완 안내를 표시한다. 자동 치환으로 본문을 바꾸지 않으며 최종 공개 인용 표현은 사용자가 편집한다.

생성 당시 `source_snapshot`에 크기가 제한된 `reference_packet`, `source_idea`, 허용된 brief 필드를 추가해 기록한다. 기존 item·variant 버전도 함께 남긴다. 이것은 생성에 사용한 입력의 기록이며 원고 revision 복원 기능과는 별개다. 내 기획이나 원고가 바뀌면 기존 stale 판정과 적용 시 버전 검사를 계속 따른다.

개인 메모·한계 메타데이터가 복사 버튼으로 함께 나가지 않도록 현재 **본문만 복사** 계약을 유지한다. 본문에 적용된 인용 표현은 본문 일부로 남는다. 원자료 전체 자막·캡션을 매번 모델에 보내거나 대량 재요약하지 않는다.

## 8. 저장·실패·재시도

소재 생성의 현행 item·variant 순차 insert와 보상 삭제는 단일 DB 트랜잭션이 아니다. P1은 이를 트랜잭션이라고 문서화하지 않으며, 두 레코드 readback까지 확인되어야 저장 완료를 표시한다. 같은 ID의 다른 입력은 충돌로 처리한다.

현행 캡처의 `useRef` 요청 보존은 새로고침 복구를 보장하지 않는다. 출처 입력 경로는 전송 전에 item/variant ID와 정규화된 요청을 **현재 탭의 sessionStorage**에 보관하고, 응답 불명·새로고침 후 같은 요청을 재시도한다. 저장 공간을 사용할 수 없으면 복구 가능한 안내와 입력 보존 상태에서 전송을 멈춘다. 성공 readback 후 요청을 지우며, 탭 종료·브라우저 데이터 삭제 후 복구까지 약속하지 않는다. 이 장치는 기존 Studio 저장 큐의 범위와 구분한다.

Studio 저장은 현재 request ID·요청 해시 기반 RPC replay를 유지한다. AI `unknown`은 같은 요청 상태 확인, `unsaved`는 저장 복구로 처리하며 새 모델 호출을 자동 반복하지 않는다. 원문 링크가 사라져도 선별 당시의 내용·한계는 남고, 링크가 지금 열리는지는 별도 사실이다.

Hub 인증 미들웨어와 write guard, Engine 인증을 계속 사용한다. read 실패는 HTTP 200의 `status: error` 봉투도 검사해 오류로 보여 준다. 조회 실패를 “참고 자료 없음”으로 표시하지 않는다.

## 9. 단계와 완료 조건

| 단계 | 범위 | 완료 판단 |
| --- | --- | --- |
| P0 — 이번 작업 | 전체 목록·원본 조사 사본·26개 인사이트·글쓰기 예시·검증·본 기획서를 저장소에 보관 | 내부 링크·건수·원본 해시·재생성 검증 통과 후 커밋. DB 입력 없음 |
| P1 — 다음 구현 권장 | 출처 1–3개 입력, 고정 packet, 내 기획, 기존 Studio·AI 연결, 재시도 복구 | §10 검증 + 실제 선택 자료로 초안 3개를 만들어 효용 점검. 자동 발행 없음 |
| P2 — 필요가 드러나면 | 원자료 객체와 글쓰기 소재 분리, 전체 검색·필터·선별 목록·스냅샷 | 아카이브 검색·반복 입력의 구체적 불편을 확인한 뒤 별도 설계 |
| P3 — 반복 수집이 필요하면 | 승인한 출처·컬렉션의 증분 수집, 실패·중복·확인 범위 기록 | 수집 대상·주기·실행 비용 상한·알림 조건을 정한 뒤 활성화 |

P2에서 전체 라이브러리를 만들 경우 현재 content 조회의 item 80·variant 160 제한을 늘려 전체 보관함처럼 사용하는 방식은 피한다. 원자료에 대한 서버 검색·페이지네이션과 소재 연결을 별도 계약으로 설계한다. 공유 프로필과 실제 게시물, 재생목록 소속과 고유 영상을 구분한 이번 분모를 유지한다.

P1의 효용 점검은 사용자가 글 3개를 만든 후 “쓰고 싶은 질문을 빨리 찾았는가, 출처를 다시 열 수 있었는가, 내 생각을 덧붙였는가, 반복 입력이 부담이었는가”를 보는 것이다. 조회 수나 전환율 상승을 완료 조건으로 두지 않는다. 외부 인터뷰나 고정 설문을 새로 시작하지 않는다.

## 10. 구현 단위와 검증 계획

후속 구현은 전용 `codex/*` worktree에서 진행한다. 아래는 구현 순서 제안이며, 이 문서 커밋에서 코드를 수정하지 않는다.

1. **생성·보존 계약:** Hub 빌더·Engine 정규화에 동일 packet 계약을 적용한다. item만 저장, 기존 메타·Journal 출처·variant 계보 보존, packet 덮어쓰기 금지, 출처 경로의 빈 첫 원고를 검증한다.
2. **입력·상세·복구:** 소재 캡처와 Studio 출처 표시를 연결한다. 오류 시 입력 유지, 같은 요청 재시도, 탭 새로고침 복구, 기존 일반 캡처 동작을 검증한다.
3. **AI 연결:** 저장된 packet 투영과 생성 입력 snapshot을 추가한다. 미확인 출처·가짜 경험 배제, 존재하지 않는 출처 ID 거부, 복사 시 내부 식별자만 남은 인용 안내, stale 후보·unknown/unsaved 복구를 검증한다.
4. **통합 확인:** 실제 선택 자료로 저장→조회→AI 후보→적용→수정→복사까지 확인한다. 원고 복원·분기 이후에도 출처가 보이고 일반 소재·Journal 활용 경로가 유지되는지 확인한다.

## 11. 범위 결정 요약

- **요청되어 수행한 것:** 원본 조사 결과 보관, 통합 정리, 활용 판단, 기획 문서화와 커밋.
- **권장하는 다음 구현:** 별도 라이브러리 제품을 먼저 만들지 않고, 기존 소재함에 선별 출처를 붙여 Studio까지 연결하는 P1.
- **이 기획서에서 확정하지 않은 것:** 전체 자료의 DB 이관, 자동 수집 대상·일정, 새 사이드바, 새 브랜드, 자동 발행, 성과 개선 목표.
- **P1의 명시적 한계:** 수동 선별·발췌, 저장 후 출처 묶음 수정 불가, URL 자동 열람 없음, 원고 복원과 기획·출처 복원은 별개.
