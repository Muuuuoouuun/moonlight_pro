# 메모를 잘 남기고, 다시 찾아 쓰고, 분석을 행동에 연결하기

> 상태: **1차 묶음 승인·구현(2026-09-13) · 후속 분석/피드백 DRAFT**. 운영자의 “이어서”에 따라 빠른 메모·선택 보강·업무 연결·할 일/콘텐츠 활용을 구현했다. [구현 계획과 검증](../plans/2026-09-13-memo-workflow.md)을 따른다. 운영 적용 완료를 뜻하지 않는다.
> 작성일: 2026-09-12 (Asia/Seoul)
> 요청: 메모를 더 잘 쓰도록 돕고, 쌓인 메모를 활용·분석·적용할 방안을 찾는다.
> 근거: 로컬 코드·운영자 프로필·기존 일지/하루 리뷰/콘텐츠 설계. 실제 개인 메모를 분석하지 않았으며 아래 사례는 가상 예시다.
> 관계: [09-05 일지 설계](2026-09-05-journal-timeline-and-ai-digest.md)의 단일 타임라인·선택적 AI 정리를 상속한다. [하루 리뷰](2026-09-12-daily-review-and-council-design.md) R0와 [콘텐츠 Studio](2026-09-12-content-notes-drafts-ai-workflow-design.md)의 저장·출처·적용 흐름을 연결하는 후속 제안이다. 기존 확정 범위와 운영 배포 상태를 바꾸지 않는다.

## 0. 1차에 반영한 범위

`내 작업 → 메모`에서 제목 없이 기록하고, 저장 뒤 한 가지 보강 질문에 선택적으로 답한다. 프로젝트·고객(리드/계정)·브랜드를 명시적으로 연결하며 해당 업무 화면에서도 기록을 시작한다. 원문에서 선택한 발췌만 할 일이나 Studio에 보내고 원문·당시 버전·사용처를 함께 보존한다. 콘텐츠 결과물은 빈 초안으로 시작하며 AI 변형은 기존 Studio에서 명시적으로 실행한다.

미저장 입력과 요청은 탭별로 격리해 새로고침·같은 탭 이동에서 복구한다. 저장 응답이 유실되면 같은 요청으로 결과를 확인하고, 다른 창과 충돌하면 두 입력을 비교한다. 탭을 닫은 뒤 미저장 복구는 보장하지 않으며 저장 공간 실패 시 복사를 제공한다.

아래의 메모 본문·기간 검색, 문맥별 재발견, 여러 메모의 묶음 분석, 요청형 AI 정리, 결과 피드백은 후속 제안으로 남는다. 1차 목록은 최신 40개와 더 보기이며 업무 객체 검색만 포함한다.

## 1. 권장하는 경험

**생각이 생기면 짧게 남기고, 쓸 일이 생기면 관련 기록을 다시 꺼내며, 선택한 기록을 실제 행동과 결과로 연결한다.**

`빠르게 남기기 → 맥락 한 줄 보강 → 필요한 순간 다시 보기 → 행동/콘텐츠/판단에 사용 → 결과 기록`

운영자 프로필에서 확인되는 조건은 짧은 텍스트 우선, 필요할 때 음성·붙여넣기, 인지 부담 감소, 직감과 바로 만들 수 있는 정도를 기준으로 한 콘텐츠 선택이다. 저장 시 필수 분류나 긴 양식을 요구하지 않는다. 작성·검색·직접 연결은 AI 없이 작동하고, 해석이 필요한 정리는 명시적으로 요청한다.

## 2. 현재 기반과 추가할 부분

| 로컬에서 확인한 기반 | 이번 후속 기획에서 필요한 연결 |
|---|---|
| [하루 리뷰 migration](../../../supabase/migrations/20260912_0025_daily_review_journal.sql)에 `journal_entries`와 `entry_kind='note'/'daily_review'`가 정의됨 | 일반 메모 작성·목록·검색·수정 경로. 하루 여러 메모와 하루 한 리뷰를 구분 |
| [하루 리뷰 원장](../../../apps/hub/lib/repositories/daily-review-ledger.js)은 `daily_review`만 날짜별 조회·저장 | 일반 메모를 리뷰 한 칸에 계속 덧붙이지 않고 같은 타임라인에서 별도 기록으로 연결 |
| [Studio](../../../apps/hub/components/hub/pages/content-studio.jsx)에 원문·기획 카드·결과물·AI 후보 적용·복원 구현 | 메모를 고르고 발췌해 Studio로 보내는 입구와 여러 메모의 출처 연결 |
| [Studio 클라이언트](../../../apps/hub/lib/content-workflow-client.js)는 결과물의 출처 정보를 읽고, [AI 문맥](../../../apps/engine/lib/content-transform.ts)은 콘텐츠 항목의 원문·기획을 사용 | 메모 발췌와 결과물 계보의 참조 형식을 맞추고, 선택한 발췌만 AI 문맥으로 전달 |
| 빠른 캡처 입력에 note 힌트가 존재함 | 기존 입구에서 일반 메모 정본으로 가는 명시적인 저장 경로와 문맥 연결 |

이는 코드·스키마 파일의 존재에 대한 확인이다. 운영 DB에 모든 구조가 활성화됐다는 뜻은 아니다.

## 3. 접근안 비교

| 접근 | 얻는 것 | 부담·한계 | 판단 |
|---|---|---|---|
| **B. 짧은 작성 보조 + 문맥에 맞는 재발견 + 바로 활용** | 기록과 실제 업무·제작이 이어짐. 기존 Studio·할 일·프로젝트 재사용 | 일반 메모 API와 출처 연결 필요 | **우선 권장** |
| A. 템플릿·작성 질문을 풍부하게 제공 | 무엇을 적을지 막힐 때 도움 | 입력 항목이 많아지면 캡처 부담이 늘고 활용 연결은 별도로 필요 | B의 선택 기능으로 작게 포함 |
| C. 모든 메모를 상시 분석하는 대화·대시보드 | 넓은 주제 탐색과 기간별 비교 | 비용, 근거 추적, 중복 분석, 확인할 제안이 늘어남 | 선택한 메모·기간을 분석하는 후속 단계로 제한 |

## 4. 잘 쓰도록 돕기

### 4.1 원문 한 줄로 저장

- 첫 화면은 입력창과 저장 동작이 중심이다. 제목·태그·용도는 선택 사항이다.
- 날짜는 기본 현재 시각이다. 과거 기록을 붙여넣을 때 기록 대상 날짜를 확인할 수 있게 한다.
- 프로젝트·고객·브랜드 화면에서 시작하면 그 문맥을 연결 후보로 보여준다. 사용자가 제거하거나 바꿀 수 있다.
- 입력은 먼저 보존한다. 저장 실패·새로고침 복구·중복 요청 처리는 기존 Studio/하루 리뷰의 계약을 따른다.
- 붙여넣기·파일 입력은 원본 출처를 유지한다. 분할은 규칙과 미리보기를 우선하고 AI 분할은 별도 선택이다.

### 4.2 보강 질문은 하나만 선택적으로 제시

기록 종류 또는 현재 화면으로 기본 질문을 고른다. 매번 AI를 호출하지 않는다. 질문을 건너뛰어도 저장은 끝나 있다.

| 상황 | 질문 예 | 보강되는 정보 |
|---|---|---|
| 고객 대화 | “상대가 실제로 한 말 중 기억할 문장은?” | 관찰·직접 인용 |
| 아이디어 | “어떤 장면을 보고 이 생각이 들었나요?” | 계기와 구체적인 사례 |
| 배운 내용 | “내 일에서 어디에 한번 써볼 수 있나요?” | 적용 맥락 |
| 막힌 일 | “어느 단계에서 멈췄나요?” | 다음 행동을 정할 단서 |
| 결정 | “다른 선택지 대신 이것을 고른 이유는?” | 판단 근거 |

‘한 줄 보강’은 원문 옆에 덧붙인다. 직접 인용과 나의 해석을 구분할 수 있게 하며, AI가 제안한 해석은 제안 표시를 유지한다. 초안 문장을 자동으로 더 길고 단정적인 문장으로 바꾸지 않는다.

### 4.3 요청형 정리 도구

메모를 쓴 뒤 필요할 때만 `한 줄 요지`, `관찰·해석 나누기`, `더 생각할 질문`, `다음 행동 찾기`를 실행한다. 출력마다 원문의 해당 부분을 같이 보여준다. 없는 날짜·고객 반응·근거는 확인할 항목으로 남긴다.

## 5. 다시 찾고 활용하기

### 5.1 할 일을 시작하는 곳에서 관련 메모 보여주기

- 고객 화면: 연결된 최근 대화, 미확인 질문, 지난번 약속.
- 프로젝트 화면: 해당 프로젝트의 관찰·결정 근거·아직 해결되지 않은 문제.
- 콘텐츠 Studio: 선택한 주제와 관련된 메모·참고 링크·과거 발췌.
- 개인 주간 리뷰: 해당 기간의 기록 중 다시 보고 싶은 것과 실제로 사용한 기록.

첫 버전은 명시적 연결과 기간·본문 검색으로 찾는다. 추천 카드에는 “이 프로젝트에 연결됨”처럼 표시 이유를 붙인다. 관련 자료가 부족한 경우를 확인한 뒤 의미 검색을 추가한다.

### 5.2 다시 볼 메모를 작게 제시

개인 메모 화면을 열었을 때 사용자가 지정한 ‘다시 볼 날짜’와 연결된 현재 작업을 기준으로 최대 3개를 제시하는 기본값을 권장한다. 수량은 제품 설계 가정이며 효과가 입증된 기준은 아니다.

`지금 사용`, `나중에`, `다시 제안하지 않기`를 제공한다. 무응답을 관심 없음이나 실패로 간주하지 않는다. 이번 기획만으로 예약 실행이나 알림을 생성하지 않는다.

### 5.3 선택한 메모를 실제 객체로 연결

| 동작 | 생성·연결할 내용 | 완료의 기준 |
|---|---|---|
| 할 일로 | 동작이 분명한 제목, 선택한 기한, 출처 발췌 | 기존 task 생성 경로의 저장 확인 |
| 콘텐츠로 | 선택한 발췌, 떠오른 이유, 전달할 메시지 후보 | Studio 기획 카드와 source reference 저장 확인 |
| 프로젝트 판단에 연결 | 배경, 대안, 선택 이유, 다시 볼 조건 | 기존 프로젝트/결정 기록에 연결 확인 |
| 다음 미팅 준비에 사용 | 확인할 질문, 지난 약속, 관련 근거 | 준비 문서 또는 선택한 작업에 연결 확인 |

사용자가 `할 일로 만들기`를 누르는 것이 해당 생성의 선택이다. 같은 작업을 추가 승인 단계에서 다시 선택하게 하지 않는다. 분석을 실행한 것만으로 할 일이나 외부 메시지가 자동 생성되지는 않는다.

## 6. 여러 메모를 분석하는 방법

‘모든 기록 분석’보다 **선택한 기록 또는 기간 + 알고 싶은 질문**으로 시작한다. 예를 들어 “최근 상담에서 사람들이 망설인 이유를 정리해줘”라고 요청하면 분석 범위를 먼저 표시한다.

| 분석 질문 | 결과물 | 실제 적용 |
|---|---|---|
| 무엇이 반복되나? | 반복 주제, 근거 발췌, 서로 다른 날짜·사건 수 | 다음에 확인할 질문 또는 개선 실험 |
| 생각이 어떻게 바뀌었나? | 이전 판단 → 새 관찰 → 달라진 판단 | 프로젝트 결정 근거 갱신 |
| 무엇이 아직 열려 있나? | 미해결 질문, 후속 약속 후보 | 선택한 후보를 task에 연결 |
| 어떤 콘텐츠가 될 수 있나? | 주제 하나, 사용할 발췌, 메시지 후보, 부족한 근거 | 기존 Studio에서 기획·초안 작성 |
| 실제로 도움이 된 것은 무엇인가? | 적용한 행동과 관찰한 결과 | 개인 작업 원칙의 후보로 저장 |

### 6.1 분석 카드 형식

1. **관찰:** 선택 범위에서 무엇이 나타났는지.
2. **근거:** 원문 발췌와 날짜, 기록으로 돌아가는 링크.
3. **다른 사례:** 같은 설명에 맞지 않는 기록이나 조건 차이.
4. **해석:** 사실과 구별되는 가설.
5. **다음에 해볼 것:** 작고 구체적인 행동 후보 최대 1개.
6. **다시 볼 조건:** 언제, 어떤 결과를 확인할지.

단건에서 나온 생각과 여러 독립 사건에서 반복된 관찰을 구분한다. 같은 원문을 여러 번 붙여넣은 기록이나 파생 초안은 독립된 근거로 중복 집계하지 않는다. 기록 빈도를 중요도·고객 전체의 비율·성격·인과관계로 바꾸지 않는다.

분석에는 읽은 기록 수, 기간, 제외된 기록·잘린 범위가 함께 표시된다. 읽지 못한 원장을 ‘문제 없음’으로 요약하지 않는다. 자료가 한 건이면 그 한 건에서 확인할 수 있는 범위만 제시한다.

### 6.2 학습용 메모의 별도 활용

배운 내용을 저장한 메모에는 선택적으로 ‘원문을 보기 전 핵심을 먼저 떠올리기’를 제공할 수 있다. [Karpicke·Blunt의 학습 연구](https://pubmed.ncbi.nlm.nih.gov/21252317/)는 인출 연습을 학습 전략으로 다뤘다. 이를 메모 기능에 옮기는 것은 제품 가설이며, 업무 실행률이나 콘텐츠 성과가 좋아진다고 보장하는 근거는 아니다. 초기 필수 기능으로 넣기보다 사용자가 학습 메모에 선택하는 후속 기능으로 둔다.

## 7. 분석을 결과까지 이어가기

메모에서 연결한 task나 콘텐츠에는 원문으로 돌아가는 출처가 남는다. 원래 메모에는 어디에 사용됐는지가 보인다. AI가 후보를 만들기만 한 상태와 실제 객체에 저장·적용된 상태를 구분한다.

사용자가 지정한 시점에 `해봤음 / 보류`와 `도움 됨 / 변화 없음 / 아직 모름`을 선택적으로 남긴다. task가 끝났다는 사실만으로 효과가 좋았다고 판단하지 않는다. 기존 하루 리뷰의 후속 확인에 붙여 같은 내용을 반복 입력시키지 않는다.

여러 번 적용하고 사용자가 확인한 사례는 ‘내 작업 원칙’의 후보가 된다. 예: “신규 도입 상담에서는 기능 목록 전에 첫 주 운영 흐름을 보여주기.” 원칙에는 적용 상황, 근거, 다른 사례, 마지막 확인일이 붙는다. 사용자가 채택한 규칙과 AI가 추정한 패턴을 구분하고 이후 반례에 따라 수정할 수 있게 한다.

## 8. 가상 사용 예

**처음 메모:** “오늘 상담은 기능 설명보다 시작이 어렵다는 얘기가 남았다.”

**선택 질문:** “시작이 어렵다고 느낀 구체적인 장면은?”

**사용자가 덧붙임:** “첫 수업 준비를 누가 도와주는지 두 번 물었다. 도입 지원이 걱정인 것 같다.”

여기서 ‘두 번 물었다’는 관찰이고 ‘도입 지원이 걱정’은 해석이다. AI가 이를 ‘구매 의사 확정’이나 ‘가격은 중요하지 않음’으로 바꾸지 않는다.

다른 상담 메모 두 건을 함께 선택해 분석하면:

- 관찰 후보: 선택한 세 상담에서 초기 운영 준비에 관한 질문이 있었다. 각 원문과 날짜를 표시한다.
- 확인할 점: 같은 걱정인지, 담당자·기관 상황이 다른지 다음 상담에서 확인한다.
- 행동 후보: 첫 주 준비 흐름을 한 장으로 만들어 다음 상담에 써본다.
- 콘텐츠 후보: “도입 전에 확인할 첫 주 운영 질문”이라는 주제로, 공개 가능한 발췌를 선택해 Studio로 보낸다.
- 결과 기록: 자료를 사용했는지, 어떤 추가 질문이 나왔는지 다음 리뷰에 남긴다.

원문, 행동, 콘텐츠, 결과가 연결되어 다음 상담과 제작의 재료가 된다.

## 9. 저장·출처·AI 실행 계약

- 일반 메모는 기존 `journal_entries.entry_kind='note'` 기반을 확장한다. 하루 리뷰의 날짜별 1건 제약을 일반 메모에 적용하지 않는다.
- 현재 note 제약은 `review_data={}`를 요구한다. 1차에 선택 보강 정보를 담는 `note_meta`, 업무 연결과 발췌를 보존하는 `journal_links`, `journal_note_revisions`와 요청 영수증을 구현했다. 분석 입력 버전과 후보를 보존할 `journal_analysis_runs`는 후속 제안이다. 리뷰 응답 필드는 기존 계약을 유지한다.
- 출처 참조는 종류·ID·버전/해시·선택 발췌를 가져야 한다. 개인 메모 전체와 고객 개인 정보를 회사 콘텐츠 문맥에 자동으로 전달하지 않는다. 공개·회사 활용은 사용자가 선택한 발췌를 기준으로 한다.
- 내용이 수정된 메모를 근거로 한 예전 분석은 ‘원문 변경됨’으로 표시한다. 근거 발췌가 맞지 않으면 재분석 또는 발췌 재선택이 필요하다.
- 실제 task/콘텐츠 생성과 출처 연결은 중복 요청에 안전해야 한다. 생성 응답이 유실되면 같은 요청으로 확인하며, 연결이 실패했는데 ‘활용 완료’로 표시하지 않는다.
- 재수입된 같은 원본과 서로 다른 날의 독립된 기록을 구분한다. 같은 문장이라는 이유만으로 발생일이 다른 수동 메모를 합치지 않는다.
- 분석 실행 기록은 선택 범위·질문·원문 버전·후보·채택 상태를 보존한다. 본문이 같은데 기획 질문·문맥이 달라진 경우를 같은 분석으로 재사용하지 않는다.
- 원문은 데이터다. 붙여넣은 문서 속 지시를 시스템 지시로 수행하거나 링크를 자동으로 따라가지 않는다.
- 저장은 즉시 처리한다. AI는 요청형이며 결과 저장 실패 시 재생성 없이 저장만 복구할 수 있는 경로를 둔다.

## 10. 적용 순서와 완료 기준

| 단계 | 묶어서 구현할 범위 | 완료 기준 |
|---|---|---|
| **1. 남기고 바로 쓰기** | 일반 메모 작성/조회/수정, 선택 질문 하나, 현재 문맥 연결, 발췌를 할 일·Studio로 연결 | 제목·태그 없이 저장·재조회 가능. 하루 여러 메모 보존. 원문 링크를 가진 task/콘텐츠 생성과 중복 복구 확인 |
| **2. 다시 꺼내고 묶어 보기** | 본문·기간·연결 검색, 관련 메모 소량 노출, 선택한 메모 분석 | 표시 이유와 읽은 범위가 보임. 근거 발췌·다른 사례·행동 후보가 연결됨. 한 건/중복/원문 수정/읽기 실패 처리 확인 |
| **3. 결과를 다음 판단에 반영** | 적용 결과 피드백, 개인 주간 리뷰 연결, 작업 원칙 후보 | 실제 적용과 효과의 응답을 구분. 무응답 제외. 회사 리포트에 개인 상세 메모가 자동 포함되지 않음 |

첫 구현 묶음인 **빠른 메모 + 한 줄 보강 + 문맥 연결 + 할 일/콘텐츠로 보내기**는 2026-09-13 승인·구현했다. 범용 분석 챗봇, 전체 기록 상시 분석, 관계 그래프 시각화, 음성 녹음 수집은 첫 묶음의 필수 조건으로 잡지 않는다.

## 11. 효과를 확인할 지표

- **작성 부담:** 원문만 저장하기까지 걸리는 시간, 보강 질문을 건너뛰는 비율. 오래 켜 둔 편집기를 작성 시간으로 그대로 집계하지 않는다.
- **재발견의 유용성:** 다시 제시된 메모 중 사용자가 유용하다고 답했거나 실제 작업에 연결한 기록. 응답 수와 노출 수를 함께 표시한다.
- **실제 활용:** 같은 생성 시기와 관찰 기간의 메모 중 task·콘텐츠·결정 기록에 연결된 고유 메모 수. 한 메모의 여러 결과물을 여러 메모로 세지 않는다.
- **실행과 결과:** 연결 행동의 완료, 사용자가 답한 도움 여부, 아직 확인되지 않은 결과. AI가 생성한 수만으로 효과를 평가하지 않는다.

숫자 목표는 실사용 기준선 없이 확정하지 않는다. 초기에는 “지난주 메모 중 이번 주 실제로 다시 쓴 것이 무엇인가”를 근거 링크와 함께 확인한다.
