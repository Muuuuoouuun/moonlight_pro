# 회의 텍스트 검토 M0 — 구현 범위와 운영 전 확인

> 상태: **M0 코드 구현·전용 테스트 통과 / 운영 DB 적용·배포·실사용 검증 전 (2026-09-23)**. 텍스트 파일럿의 구현 기록이며 음성 분석 출시나 Office·외부 에이전트 통합 완료를 뜻하지 않는다.
> 상위 정본: [운영자 업무 프로필](../../operator-workflow-profile.md) §음성·메시지 분석 원칙, [개인 운영 OS 심화 설계](../specs/2026-07-13-moonlight-personal-operator-os-deep-design.md) §15, [회의·녹음·메모에서 실행까지](../specs/2026-09-23-meeting-to-action-orchestration-design.md).
> 관계: 통합 설계의 M0 텍스트 범위를 실제 코드에 맞춰 기록한다. 해당 설계의 M1~M3와 운영자의 직접 녹음·30일 원본 삭제·월 비용 표시 요구를 대체하거나 완료 처리하지 않는다. 그 설계의 권장 테이블명 대신 기존 저널 원장과 `meeting_review_*` 테이블·함수를 선택했다.

## 범위와 사용 흐름

메모 작성창(`apps/hub/components/hub/pages/memo-composer.jsx`)에서 원문을 붙여넣거나 UTF-8 전사 `.txt` 파일을 가져온다. 파일은 클라이언트에서 읽어 메모 초안에 채우며, 이미 원문이 있으면 교체를 확인한다. 2만 자를 넘는 텍스트·빈 파일·바이너리 텍스트는 거절한다. 이 단계는 **원문 저장**과 **AI 분석**을 분리한다. 저장된 `journal_entries` 메모에서만 `회의 내용 AI 정리 · 근거 검토`를 열고, 운영자가 `AI 분석 실행`을 눌러 Gemini 호출을 시작한다. 입력 초안이나 변경 중인 메모는 분석할 수 없다.

텍스트 추출기(`apps/hub/lib/meeting-review-extractor.js`)는 요약과 `결정 / 미결 / 수치·조건 / 고객 우려 / 고객 신호 / 다음 행동` 후보를 요청한다. 각 후보에는 원문 인용과 UTF-16 문자 구간, `stated / derived / unknown` 표시가 붙는다. 인용이 원문에 정확히 한 번 나타나지 않거나 문자 경계가 깨진 경우, 근거 없는 날짜·숫자·단위 또는 명백히 뒤집힌 확정·부정 표현이 있는 경우 그 후보를 버린다. 인용의 존재가 의미적 참을 보장하지는 않으므로, 화면은 원문과 인용 맥락을 나란히 보여주고 사용자가 후보를 수정·확인·제외한다. 여러 구간을 합친 **요약은 단일 인용 근거가 없는 AI 해석**으로 표시한다.

사용자가 확인한 `다음 행동` 후보만 개별 `할 일 등록` 버튼으로 `journal_workflow_v1`의 기존 `create_task` 경로에 보낸다. 할 일 제목은 확인·수정한 문장이고, 메모 ID·revision·원문 발췌를 함께 검증한다. **제안 날짜는 할 일 기한에 자동 반영하지 않고, 실제 담당자·프로젝트도 자동 지정하지 않는다.** 다른 종류의 후보는 이번 범위에서 검토 기록만 남기며 CRM, 목표값, 프로젝트 기록, 외부 발송에 쓰지 않는다. ClassIn에는 전사나 개인 상세 메모를 보내지 않는다.

## 영속화와 영수증

`20260923_0045_meeting_text_review.sql`은 `meeting_review_runs`와 `meeting_review_proposals`를 추가한다. `journal_entries`가 원문 정본이다. 분석 run은 요청 UUID, workspace·저널 ID, 분석 시점의 `note_revision`과 원문 스냅샷, 상태(`generating / ready / error`), 모델, 공급자가 실제로 준 토큰 사용량을 기록한다. 공급자 사용량이 없으면 알 수 없음으로 남기며 금액을 만들어 내지 않는다. 동일 요청 UUID를 다시 받으면 기존 run을 조회하고 모델을 재호출하지 않는다. 시간 초과 또는 응답 단절은 완료로 추정하지 않고 결과 확인 필요 상태로 둔다. 다시 분석하면 별도 요청이므로 추가 API 비용이 생길 수 있음을 화면에 알린다.

후보는 run에 속한 별도 행으로 저장하고, 인용·문자 위치·확정도·제안 날짜·검토 상태·수정 문장을 보존한다. 원문을 수정하면 이전 run은 stale로 표시하며 그 버전의 후보를 현 원문에서 확정할 수 없다. 읽기 projection은 `source_body` 전체를 응답에 싣지 않는다. 기존 메모에서 이미 노출되는 원문과 후보의 짧은 인용만 화면에 보여준다. 이 스냅샷에는 과거 개인 원문이 남을 수 있으므로, 후속 보존·삭제 정책에서는 원본 메모와 함께 취급해야 한다.

할 일 적용에는 **새 `meeting_application_receipts` 테이블을 만들지 않았다.** 확인된 후보 ID를 안정된 명령 UUID로 사용하고, 기존 `journal_workflow_receipts`·`journal_links`와 실제 task를 대조한다. 검토 상태·확정 제목·원문 인용·revision·대상 작업·연결 기록이 모두 일치할 때만 `저장됨`으로 돌려주며, 영수증만 남고 검증이 실패하면 `결과 확인 필요`로 둔다. 응답이 끊기면 먼저 같은 후보의 서버 결과를 재조회하고, 재전송하더라도 같은 명령 UUID를 써 중복 작업을 막는다. 메모 read API는 저장소 오류를 HTTP 200의 `status: error`로 표시하는 기존 Hub 계약을 따르고, write API는 `hub-write-guard`를 통과한다. `preview`와 HTTP 응답만으로는 저장 성공을 선언하지 않는다.

## 구현 선택과 미완료 범위

이 M0는 기존 `memo-capture.jsx`를 화면에 연결하거나 `multimodal-intake-core.js`를 바꾸지 않고, **저장된 텍스트 메모 전용 검토 경로**를 만들었다. 전역 QuickMemo의 AI 할 일 추출은 별도이며 이 영수증 흐름으로 합쳐지지 않았다. `memo-pattern-panel.jsx`의 preview/저장 판정 개선도 이번 변경에 포함되지 않는다. 새 입력 흐름은 `MemoComposer` 안에 있고 Office의 회의 triage나 MCP 도구를 호출하지 않는다.

분석 run의 입력 해시·정책 버전·금액/가격 버전, 후보 검토자의 별도 ID, 여러 분석 run의 화면 내 이력 선택도 아직 없다. 현재 화면은 같은 메모의 **최신 run 하나**를 보여주며 이전 run 행은 DB에 남는다. 이 상태를 비용 원장이나 다중 담당자 감사 기록으로 해석하지 않는다.

M0에서 구현하지 않은 운영자 확정 요구와 확장 범위는 다음 순서로 남는다.

| 단계 | 남은 작업 | 완료 판단에 필요한 근거 |
| --- | --- | --- |
| **M1 · 첫 음성 운영 출시 기반** | Moonlight 직접 녹음·오디오 업로드, 긴 전사 텍스트와 비동기 분할 처리, private storage와 원본 30일 삭제·실패 재시도, 전사 구간·화자/시각(확인 가능할 때), 월별 분석 횟수와 비용·사용량 화면. | 실제 길이의 음성/외부 전사 입력 왕복, 삭제 영수증과 전사·요약 보존, 공급자 사용량 누락 시 미확인 표시. M0의 `.txt` 가져오기만으로 M1을 완료했다고 할 수 없다. |
| **M2 · 근거 있는 업무 배분** | 후보별 고객·프로젝트·실제 담당·기한 확인, 목적지별 검토·저장 영수증, Office 회의 triage의 짧은 근거 묶음과 역할 라우팅. | 후보→운영자 확인→각 정본 저장→실행 결과가 분리되고, 미확정 숫자·고객 신호가 자동 CRM 사실이나 점수가 되지 않음. |
| **M3 · MCP와 개발 job** | 회의 구간 read/제안 도구, 클라이언트별 최소 권한과 감사 주체, 승인된 개발 작업의 Codex job 연결, Claude 수동/자동 경로의 별도 검증. | 실제 클라이언트 인증·범위 밖 읽기 차단·제안 영수증, Codex worker 미기동과 실행 완료를 구분한 상태. MCP 등록만으로 실행 완료로 보지 않음. |

## 현재 검증과 운영 적용 경계

2026-09-23 로컬 전용 점검에서 extractor·client·service·API route 테스트 **18건**, UI 컨트롤러 비동기 상태 테스트 **5건**, 별도 opt-in PostgreSQL 통합 테스트 **1건**이 모두 통과했다. 정확한 Unicode 원문 구간, 근거 없는 후보 제거, 수동 분석 요청 UUID 재조회, 저장소 preview/오류 봉투, 타임아웃 뒤 영수증 복구, 원문 revision과 task 영수증·권한을 검증했다. 루트 `npm test`는 **2,404 tests · 통과 2,392 · 실패 0 · 건너뜀 12**였고 Hub production build 및 루트 typecheck도 통과했다. 건너뜀에는 별도 opt-in으로 통과시킨 PostgreSQL 테스트가 포함된다. 이 검증의 공급자 응답은 모의 응답이며, 실제 Gemini 응답 품질·브라우저 실사용·장시간 전사·월 비용·운영 배포는 입증하지 않는다.

운영 서울 Supabase에 **0045 마이그레이션을 적용하지 않았고**, 새 Hub 코드도 운영 배포로 확인하지 않았다. 적용 전에는 migration 이력·RLS와 서비스 전용 RPC 권한, `db:check`, 배포 환경의 Supabase/Gemini 설정, 개인 원문의 접근 범위, 실제 텍스트 입력의 저장→분석→검토→할 일 적용→새로고침 왕복을 확인해야 한다. 기존 [통합 설계](../specs/2026-09-23-meeting-to-action-orchestration-design.md)의 첫 음성 운영 출시는 M0와 M1을 모두 통과한 뒤 별도로 판단한다.
