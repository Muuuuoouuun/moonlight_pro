# Office 역할 품질·토론 조절 구현 및 검증

- 상태: 역할 지침·개별 회의 호출·설정 UI 구현 및 로컬 UI QA 완료. 실제 모델 평가·개선 진행 중이며 실패가 남아 있어 **9명 각각의 70점 이상 의미 품질 인증은 대기**다.
- 기준선: `212c093`, 전용 브랜치 `codex/office-agent-quality`.
- 관계: 2026-09-21 Office 역할·말투·운영 품질 스펙을 실행 지침과 검증 절차로 구체화한다. [9명 역할 지침](../specs/2026-09-22-office-agent-role-instructions.md)은 코드에서 생성한 사본이다. [업무 내장 심화 설계](../specs/2026-09-21-eevee-office-embedded-workflow-deep-design.md)의 Hub 권한·원장·실행 승인·보관 경계와 [운영자 기준](../../operator-workflow-profile.md)의 확정·권장 구분은 유지한다.
- 요청: 각 역할의 전문성, 근거, 자연스러운 대응, 상황별 토론, 실제 산출물을 개선하고 실응답으로 평가한다.
- 이 문서의 완료 표기는 로컬 구현·검증 범위다. 운영 배포나 0038의 운영 DB 적용을 뜻하지 않는다.

## 실행 경로와 경계

```text
회의 설정 + 원문
  → Hub 요청 정규화·기존 인증/쓰기 가드
  → Engine 공통 48초 제한
     → 역할별 첫 의견 (2~3개 병렬, 자신의 역할 지침)
     → 공개 의견에 대한 재검토 (선택, 2~3개 병렬)
     → 주관 종합 (1회, 원문과 공개 의견 대조)
  → 서버가 원문 인용·화자·단계·호출 수·요청 설정을 검증
  → Hub 결과·설정 저장 및 복구 → 사용자 검토
```

빠른 결정(깊이 1) 또는 반론 0은 첫 의견과 종합만 수행한다. 전체 최대 7회, 단계 내 최대 3회 병렬이다. 한 역할이 실패하면 진행 중인 같은 단계 호출을 취소하고 불완전한 회의를 성공으로 보이지 않는다. 모든 단계는 Engine 48초, Hub 55초, 브라우저 60초 안에서 동작한다. 워크플로 DB의 60초 claim 기한을 넘기는 제한 연장은 하지 않는다.

텍스트 생성에 검색·발송·예약·업무 쓰기 도구를 추가하지 않는다. 각 역할의 발언은 비신뢰 자료이며 다른 역할의 확신은 사실이나 운영자 승인 근거가 아니다. 기존 `deliberation` 없는 요청의 정규화 형태를 유지해 과거 요청 해시·복구와 호환한다. 새 설정이 있는 요청은 같은 ID에서 설정 변경을 허용하지 않는다.

## 조절 설정과 UI 보존

| 상황 프리셋 | 반론 | 깊이 | 말투 온도 | 수렴 |
| --- | ---: | ---: | ---: | ---: |
| 균형 `balanced` | 2 | 2 | 2 | 2 |
| 빠른 결정 `urgent` | 1 | 1 | 1 | 3 |
| 가능성 탐색 `explore` | 1 | 3 | 2 | 0 |
| 엄밀한 검토 `scrutiny` | 3 | 3 | 1 | 2 |

고급 펼침에서 프리셋과 각 값을 조절한다. 반론·온도·수렴은 0~3, 깊이는 1~3, 선택한 각 참여자의 관점 비중은 1~3이다. 프리셋 선택은 요청 본문을 자동으로 채우지 않는다. 최종 숫자 설정이 호출 단계와 역할별·종합 프롬프트에 전달된다. 비중은 먼저 해결할 쟁점의 우선순위이며 검증된 사실·기한·권한·치명적 결함을 표결로 바꾸지 않는다. 단계 수·병렬 수·처리 시간은 서버 정책으로 제한한다.

전송 시 정규화한 설정을 요청 스냅샷으로 고정한다. 처리 중에는 해당 요청의 조절을 잠그고, 수정 요청·이력 복구에는 결과의 `discussion.settings`를 우선 사용한다. 결과가 없는 오류·만료 기록은 검증된 `receipt.deliberation`으로 선택을 복원한다. 자유 Office의 scope와 업무 패널의 origin별로 입력·선택·결과를 분리해 고객 A의 늦은 응답이 고객 B를 덮지 않게 한다.

새 회의 결과는 설정과 발언 기록이 요청과 일치해야 수용한다. 화면에는 **같은 모델의 역할별 개별 검토**와 실제 공개 발언을 종합 본문과 나눠 표시한다. `discussion`이 없는 과거 저장 기록은 **이전 관점 시뮬레이션 · 역할별 발언 기록 없음**으로 표시하며, 새 요청의 누락·불완전 기록을 과거 결과로 위장하지 않는다. 실패 시 입력을 보존하고 허위 회의 기록을 추가하지 않는다.

## Source review의 범위

단독 대화·초안은 첫 생성 뒤 같은 모델의 검수 호출을 거친다. 회의에서는 각 역할의 발언 호출과 주관 종합 호출 안에서 서버 원문 목록(`sourceCatalog`)의 번호(`sourceIndexes`)를 선택하고 구체 교정 메모(`corrections`)를 먼저 작성하도록 한다. 이는 별도의 독립 심사자를 추가하는 구조가 아니다.

서버는 현재 호출의 원문 목록에 존재하는 정수 번호만 받아 원문으로 복원하고, 제공 문맥·현재 요청·이전 사용자 발언 또는 현재 범위에 서버가 제공한 운영자 확정 기준에 실제 문자열로 존재하는지 확인한다. 모델이 임의로 만든 인용문이나 원문 목록은 거절하며 검수용 필드는 공개 답변에서 제거한다. 긴 원문 enum이 실제 API에서 거절돼 원문은 prompt에 두고 schema에는 번호 범위만 둔다. 정책은 회사/개인 범위에 맞는 고정 규칙만 허용하며 실제 고객·실행·성과의 증거로 취급하지 않는다. 전체 시스템 프롬프트나 역할 예시는 인용 원문으로 허용하지 않는다. AI 초안·동료 주장을 사실 근거로 승격하지 않도록 지시하지만, 인용의 관련성·주장의 진위·교정의 충분함을 자동으로 증명하지는 못한다. **같은 모델의 편집 보조를 독립 검증이나 품질 보증으로 표시하지 않는다.** 실제 출력에 남은 실패는 별도의 의미 평가에서 판단한다.

## 고정 품질 기준

각 역할을 다섯 영역 × 네 세부 항목으로 평가한다. 항목당 0~5점이며 상세 앵커는 `scripts/office-evaluation/rubric.mjs`가 정본이다.

| 영역 | 확인할 행동 |
| --- | --- |
| 역할 전문성 | 담당 관점, 전문 원칙, 판단 순서, 인계·경계 |
| 지식·근거 | 사실과 미확인 구별, 계산, 출처, 과장·오류 교정 |
| 성격·말투 | 자연스러움, 역할 차이, 피로·상황 대응, 독자에 맞는 문장 |
| 토론·조절 | 쟁점 응답, 설정 반영, 새 근거에 따른 수정, 남은 이견 |
| 실행 실용성 | 바로 쓸 산출물, 우선순위·자원, 구체 행동, 확인·중단 조건 |

통과에는 **총점 70/100 이상 + 각 영역 14/20 이상 + 중대 실패 0건 + 필수 상황의 실제 응답**이 모두 필요하다. 인용 가능한 관측이 없으면 미입증이다. 성공한 호출만 골라 실패를 숨기거나 프롬프트 문구의 존재를 내용 점수로 삼지 않는다. 내부 평가 결과는 이 사례·모델·버전의 관측이며 보편적 전문가 인증이 아니다.

## 통합 검증과 의미 평가 범위

최종 통합 코드 검사(2026-09-22): 전체 테스트 **1,916개 중 1,905 통과·11 skip·실패 0**, 타입 검사 **4/4 통과**, Hub·Engine 빌드 **2/2 통과**. 이 결과는 의미 품질 인증과 별개이며, 아래 실제 모델 평가를 대체하지 않는다.

- 계약: 잘못된 값·대상·화자·단계·순서·설정 변경·불완전 기록·크기 초과 거부.
- 실행: 라운드·병렬·모델 유지·공통 기한·중간 실패 취소·근거 없는 완료 표시 차단.
- 복구: 요청 설정 고정, 과거 기록 호환, 재시도·이력·ID 충돌, 새 결과의 회의 기록 필수.
- UI: 기본 설정, 세부 조절, 역할 비중, 모바일 레이아웃, 보존된 요청·오류·이전 결과 표시.

- 회귀: 전체 테스트·타입 검사는 위 결과를 따르고, 빌드·계약·diff 결과는 최종 통합 기록에서 확인한다.

## 의미 품질 인증 상태와 다음 순서

기존 v2 평가는 일부 사례의 기준 충족 관찰이며 현재 9명 각각의 70점 근거가 아니다. 이번 실제 모델 실행에서도 실패가 관찰되어 수정·재평가가 진행 중이다. 생성 성공률, UI QA, source review 통과를 의미 점수로 바꾸거나 아직 없는 점수를 기입하지 않는다. 결과·원문 인용·판정 한계는 [2026-09-22 평가 기록](../../evaluations/2026-09-22-office-agent-quality/README.md)에 보존했다. v10 전체 39건 중 생성 28·오류 8·종속 차단 3이며, 9명 70점 이상 목표는 미달·미검증이다. Pro 집중 비교에서도 오류와 의미 결함이 남아 기본 모델은 바꾸지 않았다.

후속 `scope-v1`은 정수 원문 참조 기반과 범위·종결 지침 정리 뒤 전체 39건을 모두 생성했다. 135회 공급자 호출이 정상 완료됐고 새 독립 심사자의 180개 항목을 검증했다. 총점 57~71점, 최종 통과 0/9명이다. 리피아는 총점 71점이어도 협의·실용성 축과 탐색 대조가 미달이다. 미제공 작업 용량·검증 시간·제품 기능을 사실화하는 문제가 남았으며 전 역할 품질 인증은 계속 대기다. [최신 점수와 원문](../../evaluations/2026-09-22-office-agent-quality/scorecard-scope-v1.json)을 따른다.

평가용 Codex CLI adapter는 원문 전달·완료·취소·프로세스 종료를 검증했으나, 실제 기존 Office 경로 비교에서는 두 추론 설정 모두 5건 중 3건만 생성했다. 48초 제한 초과와 CLI 실패를 그대로 보존했으며 기본 모델·인증·운영 DB를 바꾸지 않았다. [호출 원문과 적용 한계](../../evaluations/2026-09-22-office-agent-quality/diagnostics/codex-pipeline/README.md)를 먼저 확인한다.

`fbb371d`는 HTTP wrapper의 48초 제한을 보존하며 취소 가능한 Office 코어를 분리했다. 새 평가 전용 경로의 [전체 개발 기록](../../evaluations/2026-09-22-office-agent-quality/diagnostics/codex-async-core/README.md)은 39건 중 생성 33·오류 5·종속 차단 1이며 미채점이다. 실패한 공급자 호출과 누락된 역할·회의 관찰이 있어 전 역할 인증이나 운영 비동기 연결의 근거가 되지 않는다.

후속 [경계 분리 진단](../../evaluations/2026-09-22-office-agent-quality/diagnostics/boundary/README.md)은 지침 미전달 가설을 반증했으며 최소 지침·출력 형식 변경·별도 Pro 오류 검수에서도 의미 실패가 남았다. 이 결과를 제품 프롬프트 개정이나 모델 교체로 승격하지 않는다. 공급자 완료 상태·실제 모델 버전과 Office JSON/인용/계약 실패 단계를 보존해 다음 수정의 근거부터 명확히 한다.

1. 최종 런타임·역할 지침·모델 설정·rubric·시나리오와 파일 해시를 고정한다. 실행 도중 변경된 정책의 결과를 같은 버전으로 합치지 않는다.
2. **33개 시나리오·39개 Office 생성**의 전체 범위를 실행한다. 9명 각각의 전문 업무·근거 부족/충돌·사회적 대응, 회의의 최초 판단→새 사실→종결, 같은 문제의 urgent/explore/관점 비중 대조를 포함한다. 실패·blocked·미실행도 원문과 함께 보존한다.
3. 구현에 참여하지 않은 독립 심사자들에게 역할별 dossier와 제공 자료를 배정한다. 실제 인용으로 20개 항목·5축·중대 실패·관찰 범위를 판단하고 심사자·모델·독립성 설명을 기록한다. 논쟁적 판정은 별도 심사로 재검토하며, 같은 모델의 생성 중 검수를 이 독립 심사로 대체하지 않는다.
4. 실패를 수정하면 새 파일·새 fingerprint로 필요한 회귀와 전체 평가를 수행한다. 조정에 사용한 사례는 development로 표시하고, 최종 검증에는 구현 조정에 쓰지 않은 독립 후속 사례를 사용한다. 사전 작성한 3개 회의 질문도 사용·노출 이력에 맞게 분류하며 미사용이라고 추정하지 않는다.
5. 역할별 5축·총점·중대 실패·coverage·대조 결과·원문 링크를 함께 공개한다. 통과 조건을 모두 충족한 역할만 해당 표본의 통과로 기록하고, 70 미만·미평가·실패는 그대로 남긴다. 운영 적용 전제는 별도 확인한다.

[문서 상태 지도](../../README.md)의 Phase 1B·1C 잔여 범위를 이 작업으로 완료 처리하지 않는다. 마이그레이션 0038은 임시 PostgreSQL 검증만 완료했고 운영 DB에는 미적용이며, 운영 배포·보관 정리 예약도 완료로 기록하지 않는다.
