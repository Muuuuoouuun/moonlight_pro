# 프로젝트 실행 백로그 구현 계획

> 요청: 프로젝트 탭을 Jira 같은 PMS의 기능 중심으로 발전시키되 Moonlight 핵심 방향에 맞춘다.
> 정본: operator-workflow-profile.md §11·Q116·Q120, 07-13 심화 설계 §11, 07-17 프로젝트 설계 §3, DESIGN.md.

**Goal:** 수집한 작업을 계획·진행·완료로 옮기고, 프로젝트별 다음 행동·병목·기한을 한 원장에서 관리한다.

**Architecture:** 기존 tasks와 Hub → Engine PMS command를 재사용한다. 백로그와 보드는 같은 필터·작업 모델을 사용한다. tasks.next_action을 읽기·편집 경로에 노출하며 스키마를 추가하지 않는다. 수정에는 기존 updated_at 비교 계약을 tasks로 확장한다.

**Tech Stack:** Next.js, React, JavaScript/TypeScript, Node test, Supabase REST.

## 범위와 선택

Jira의 [백로그에서 계획으로 이동하는 패턴](https://support.atlassian.com/jira-software-cloud/docs/use-your-kanban-backlog/)을 참고한다. 기존 체크리스트만 보강하면 다중 작업 정리가 남고, 스프린트·스토리 포인트·팀 배정까지 도입하면 개인 업무의 판단 비용이 늘어난다. 이번에는 실행 백로그를 추가하고 기존 보드·할 일·프로젝트 상세와 연결한다. 새로운 자동 점수, 외부 Jira 동기화, 다중 사용자 권한은 이 변경에 포함하지 않는다.

## 구현 순서

- [x] 순수 작업 모델: 프로젝트·우선순위·실행 렌즈, 서울 날짜 기준 기한 정렬과 무기한 분리, 필터 URL 왕복, 저장 응답 병합. 동명 프로젝트는 ID로 구분한다.
- [x] 쓰기 계약: 작업 nextAction PATCH 및 정확한 expectedUpdatedAt 조건, 저장·충돌·preview·부분 실패의 회귀 테스트. 기존 상태만 보내는 소비자는 호환한다.
- [x] 실행 백로그: 상태별 그룹, 필터, 행 편집, 상태·우선순위 즉시 변경, 선택 작업의 상태·기한 일괄 저장. 성공 항목만 선택 해제하고 실패 항목과 원인을 남긴다. 전체 선택은 현재 보이는 작업에 한정한다.
- [x] 탭 연결: 백로그/보드/할 일 필터 공유, 프로젝트 상세에서 해당 작업으로 이동, 다음 행동 노출, 생성 문맥 유지. partial/error/preview는 데이터가 없다는 뜻으로 표시하지 않는다.
- [ ] 검증: `npm test`, `npm run check:contracts`, `npm run typecheck`, `npm run build`; Playwright로 백로그 → 필터 → 선택 변경 → 실패 재시도 → 새로고침과 데스크톱/모바일을 확인한다.
- [ ] 검증 후 현재 통합 브랜치에 변경을 병합하고 전용 worktree를 정리한다. 기존 사용자의 미커밋 변경은 보존한다.

## 완료 기준

- 상태·기한·다음 행동의 저장 결과가 새로고침 후에도 유지된다.
- 프로젝트 ID·원장 스코프가 일치하며 다른 프로젝트 작업을 섞지 않는다.
- 기한 없는 작업은 날짜 정렬의 마지막에 위치하고 전용 렌즈로 조회한다.
- 저장 실패·409 충돌·미연결에서는 성공 안내를 표시하지 않는다.
- 부분 원장은 확인된 범위라고 명시하고 재시도를 제공한다.
- 새로운 UI는 기존 토큰·Checkbox·SegmentedControl·EditDrawer·TruthBadge를 사용한다.

## 구현 검증 기록

- 독립 브랜치 전체 테스트: 928개 중 925개 통과, 기존 3개 건너뜀, 실패 0. 계약 검사 통과.
- Playwright: 데스크톱 1440px·모바일 390px에서 21개 흐름 통과. 프로젝트 범위 선택, 부분 실패 후 재시도, 저장 중 중복 조작 차단, 상태·기한 변경 및 해제, 완료·다시 열기, 충돌 시 입력 보존, 생성 문맥, 새로고침, partial/error/preview를 확인했다. API fixture를 사용했으며 운영 데이터에는 쓰지 않았다.
- 리뷰 회귀 보강: 할 일 구간 내 사용자 정렬 유지, 프로젝트 조직 범위 우선, 새 작업의 DB updated_at 반환 및 직후 버전 비교. 생성 → 수정은 Engine 라우트와 공통 Supabase 클라이언트까지 연결한 테스트로 확인했다.
- 다음 단계: 최신 통합 브랜치와 합친 결과에서 전체 테스트·타입 검사·빌드·계약 검사를 실행한다.
