# Eevee Office 9역할 품질 재진단과 재기획

> 상태: **DRAFT · 평가 근거에 따른 권장안** (2026-09-23). 이 문서는 역할 지침이나 운영 권한을 변경하지 않는다.
> 범위: `c5e4fd8`의 v14 역할 카드와 그 이전의 독립 평가를 대조했다. **v11~v14의 실제 응답은 아직 독립 채점되지 않았다.** 뒤이어 들어온 `829f45d` 메모 기능 커밋은 Office 역할 품질을 바꾸지 않는다.
> 상위 경계: [운영자 업무 기준](../../operator-workflow-profile.md), [업무 내장 설계](../specs/2026-09-21-eevee-office-embedded-workflow-deep-design.md), [현행 평가](../../evaluations/2026-09-22-office-agent-quality/README.md). 탭 배치는 [역할 배치 DRAFT](../specs/2026-09-21-eevee-office-surface-role-map.md)를 참고하되 구현 완료로 간주하지 않는다.

## 1. 결론과 증거의 시점

"점수가 안 오른다"는 두 현상을 분리해야 한다. **최근 v11~v14는 점수가 오르지 않은 것으로 측정된 것이 아니라, 측정 자체가 아직 없다.** 최신 완전 심사는 v10 계열 Office 런타임 `21f720e`의 `scope-v1` 39/39건에 매긴 57~71점, 최종 통과 0/9명이다. 심사 독립성은 역할별 심사자의 선언과 원문 대조에 근거하며 기계적으로 증명된 속성은 아니다. 그 뒤 Codex 평가 전용 코어는 33/39건 생성에 그쳐 미채점이다. `617732c`(v11)·`ad2a5b0`(v12)·`10ae0af`(v13)은 `role-cards.ts`와 그 자동 생성 읽기 사본의 버전 표기·말투 필드만 고쳤다. `c5e4fd8`(v14)은 이브이의 판단 순서·토론 지침·말투·예시까지 고쳤다. 따라서 57~71점을 v14의 결과라고 부르거나, v14 때문에 점수가 하락했다고 주장할 근거가 없다.

| 대상 | 확인된 사실 | 품질 해석 |
|---|---|---|
| `scope-v1`, 런타임 `21f720e` | Gemini 3.5 Flash 39/39 생성, 독립 20항목 심사 완료 | 9명 총점 57~71, **최종 통과 0/9**. 이 표본의 진단 기준선 |
| `fbb371d` 이후 Codex CLI 평가 코어 | 33/39 생성·5 오류·1 종속 차단 | 빠진 역할·회의·설정 대조가 있어 **점수 없음**. 생성 성공률과 의미 품질은 별개 |
| v11→v13, `10ae0af` | 세 커밋 모두 역할 카드의 버전 표기·`voice`와 생성 문서만 수정 | 새 버전의 의미 품질·말투 변화 모두 **미측정** |
| v14, `c5e4fd8` | 이브이의 질문·결정 변경·토론 절충 규칙, 말투 예시와 생성 문서 수정 | 판단 변화까지 있으나 실제 답변·의미 점수는 **미측정** |

Git에는 작성자와 변경 파일은 남지만 사용한 편집기 이름은 남지 않는다. 저장소에서 확인한 Antigravity 언급은 MCP 사용 설명·후보 작성 도구 선택지이며, 이 역할 카드가 **Google Antigravity에서 작성됐다는 출처 증명은 아니다**. 별도의 Antigravity 세션·Drive 문서가 있다면 이 검토 범위에 아직 포함되지 않았다. 현재의 [9명 역할 지침](../specs/2026-09-22-office-agent-role-instructions.md)은 `role-cards.ts`에서 생성한 사본이므로 독립적인 두 번째 설계·심사 문서로 세지 않는다.

## 2. 점수가 낮았던 원인: 캐릭터보다 판단의 사실 경계

완전 심사의 평균 축 점수(각 20점)는 **전문성 14.6 / 근거 9.6 / 말투 14.1 / 협의 11.1 / 실용성 13.1**이다. 근거가 가장 낮고, 협의·실용성이 그다음이다. 중대 게이트는 사실 창작 `fabrication` 5명, 핵심 오판 `material-error` 3명이 실패했다. 총점만 70을 넘어선 리피아도 협의 12·실용성 13과 탐색 설정 대조 실패로 불합격이다. 모든 말투 점수만 20으로 올린다고 가정해도 기존 응답의 나머지 점수를 고정하면 이브이·샤미드·쥬피썬더·부스터·에브이·님피아 여섯 명은 70에 못 미친다. 이는 **옛 표본의 반사실 계산**이지 새 지침의 예측 점수가 아니다.

| 실패 묶음 | 실제 심사에서 관찰한 사례 | 바꿔야 할 판단 습관 |
|---|---|---|
| 기한→가용시간 비약 | 이브이·샤미드·쥬피썬더가 내일로 연장된 마감을 내일 오전 버퍼 확보로 해석. 재조회가 5분/몇 분이라는 미제공 시간까지 추가 | **마감 변경 ≠ 작업 시간 확보**. 시간·소요·회신은 각각 출처 또는 명시적 추정 필요 |
| 성과 수치만 빼고 새 약속 창작 | 부스터·블래키·님피아가 미측정 18%를 제거한 뒤 미제공 기능, 한 화면 완료, 고객 반응·편의성으로 대체 | 외부 문구의 **기능·효과·고객 반응 각 주장**에 독립 근거 요구. 삭제 후 교체 문장도 다시 대조 |
| 합의·결론 왜곡 | 에브이는 근거 없는 40분 제약을 세웠고, 일부 회의에서는 역할 간 이견이 최종 합의로 바뀜 | 공개 발언의 반대·조건·입장 변경을 주관 합성까지 보존 |
| 사용자가 요청한 결과 이탈 | 리피아는 탐색 설정에도 단일안으로 조기 수렴, 글레이시아는 범위 확인을 새 기능 스펙으로 확장 | 강도/탐색/종결 설정은 분량보다 **실제 대안·질문 크기·최종 결과**에서 관찰 가능해야 함 |

현재 서버의 `source-review.ts`는 인용 인덱스가 실제 원문 발췌에 들어 있는지를 확인한다. **인용이 결론을 함의하는지는 판정하지 않는다**([코드](../../../apps/engine/lib/office/source-review.ts)). `review.ts`는 같은 모델의 두 번째 편집이며 독립 사실 검증이 아니다. `deliberation.ts`는 개별 발언 뒤 합성 호출을 하지만, 최종 합의가 실제 공개 발언과 일치하는지를 기계적으로 보장하지 않는다. 형식·출처 존재 검사가 통과해도 위 의미 오류가 남을 수 있는 구조다.

먼저 문서의 역할과 상태를 분리한다. 제목의 “정본”이나 “완료”는 현재 모델 품질 통과를 뜻하지 않는다.

| 문서 묶음 | 지금 읽는 방식 | 재기획에서의 조치 |
|---|---|---|
| [C-Suite OS](../specs/2026-09-21-eevee-office-c-suite-operating-system.md)·[Moonlight 전문화 9인](../specs/2026-09-21-eevee-office-moonlight-specialized-roles.md) | 역할·업무 배치의 설계 기준. “상위 1%”, “100% 직결”은 목표 언어이며 실측 품질이 아니다 | 제품 피치와 품질 성과 문구를 분리 |

| [성격·말투 심화 설계 v4](../specs/2026-09-21-eevee-office-voice-and-personality-deep-design.md)·[운영 품질 v2](../specs/2026-09-21-eevee-office-operating-quality.md) | 당시 설계·로컬 검증 기록. 현재 프롬프트의 문구와 버전이 다를 수 있음 | 현행 코드를 우선해 모순·낡은 예시 감사 |

v11~v13에서 기존 역할의 `mission`·`expertise`·`decisionProcess`·`evidence`·`boundaries`·`handoffs`는 그대로이고 `voice.character/texture/avoid/examples`가 바뀌었다. v14는 이브이의 `decisionProcess`와 `deliberation.contribution`도 수정했다. 캐릭터 구분은 커졌지만 낮은 축에 직접 대응하는 변화는 작다. 특히 예시는 단순 문서 장식이 아니다. `renderOfficeRolePersona()`가 예시를 실행 지침에 포함하고, 초안·검수·회의에 이 지침이 전달된다. 예시가 실제 요청의 사실은 아니라는 문장도 있지만, 반복되는 구체 대사는 사실·수행 상태 혼동의 위험을 만든다. **아래는 코드상의 충돌·위험 진단이며 v14 출력에서 오류가 발생했다는 관찰은 아니다.**

| 역할/현행 예시 | 평가 |
|---|---|
| 이브이: “긴급 건은 제가 챙겨둘”, “오늘 5시 계약 마감”, “수정 조항으로 막고 발송 즉시 추진” | 지속 감시 도구가 없고, 가상의 마감·조항·발송 가능성을 예시가 단정한다. v14의 1~2문장 `입니다·습니다` 의도는 공통 persona와 마지막 검수의 “편안한 해요체” 지시와 충돌한다. 초기 모호함마다 2지선다를 요구하거나 이견마다 “최적 절충안 1개”를 내라는 새 규칙은 불필요한 재질문·허위 합의를 유도할 수 있다. |
| 샤미드: “캘린더 비워두겠습니다” | 일정 변경을 실행하지 않는 경계와 충돌한다. 기존 마감→가용시간 오판을 더 쉽게 재현할 수 있다. |
| 쥬피썬더: “세션 미들웨어 에러”, “최소 패치 띄우고” | 로그·계약 없이 원인을 특정하고 실제 패치를 예고한다. 이전 심사의 기술 오판을 겨냥한 반증 예시가 필요하다. |
| 부스터·님피아: “대박” 고객 반응, “클릭 한 번으로 어제 매출 확인” | 고객의 반응·지원 기능·사용 편의가 확인되지 않았을 때 외부 문장으로 전염될 수 있다. 기존 18% 대체 창작 실패와 같은 방향의 위험이다. |
| 에브이·리피아: “이번 달 첫 결제 전환”, “이번 주 내내 피곤”, “오늘 6시” | 현재 요청에 없을 수 있는 목표·시간·에너지 상태를 예시에서 사실처럼 말한다. 근거 있는 대안 비교/산식 예시가 우선이다. |
| 블래키: “제5조 손해배상 무제한”, “수정안 달아뒀다” | 실제 계약 조항·수정 수행을 가정한 대사다. 까칠한 캐릭터는 가능하나 사실 검토자에게 가장 위험한 모범 문장이다. |
| 글레이시아: “개발 착수 못 올립니다” | 검토자가 독단적 승인권을 가진 듯한 표현이다. 실제 초안의 완료 조건과 미확인 사항을 구분하는 편이 유용하다. |

역할별 격차도 균일하지 않다. 이브이·샤미드·쥬피썬더는 시간/상태 추론과 실행 가능성, 부스터·블래키·님피아는 외부 주장 검증, 에브이·리피아·글레이시아는 대안·수렴·완료 조건이 우선이다. 전체 9명에게 동일한 “더 자연스럽게” 수정만 반복하면 가장 낮은 축을 건드리지 못한다.

## 4. 접근안과 선택

| 접근 | 얻는 것 | 한계/판단 |
|---|---|---|
| A. 말투 예시만 다시 다듬고 같은 프롬프트 유지 | 도구 실행 사칭과 어조 충돌을 작게 줄일 수 있음 | 필수 P0이지만, 내일 용량·지원 기능 창작이나 허위 합의를 막는 충분조건은 아님 |
| **B. 주장 근거 계약 → 역할별 판단 → 회의 합성 검증 → 독립 평가** | 낮은 근거·협의·실용성 축을 직접 겨냥하고 실패 위치를 분리 가능 | 단계별 구현·호출 비용이 있다. **권장** |
| C. 모델/공급자만 교체 | 속도 또는 표현 차이를 탐색 가능 | 기존 Pro·3.8 Flash·Codex 진단은 완전 범위·의미 개선을 증명하지 못했다. B의 대체가 아닌 후순위 비교 |

**권장 방향 B:** 9명의 역할 캐릭터는 유지하되, 캐릭터는 주장·도구·출처 경계 뒤에 둔다. “더 센 개성”이 아니라 **같은 근거에서 더 정확한 결론, 실제 이견을 보존한 협의, 요청 크기에 맞는 결과물**이 다음 버전의 피치다. Office가 전체 업무를 아는 C레벨 임원인 듯 소개하기보다, 제공된 문맥에서 초안을 만들고 판단을 돕는 전문 관점으로 설명한다.

## 5. 구현 순서와 통과 조건

### P0 — 지침 모순 제거와 실행 범위 표시

1. `role-cards.ts`의 구체적 실행 완료·예약·미확인 제품/고객 사실 예시를 **조건부·출처 있는 대사**로 교체한다. 이를 자동 생성 문서에 다시 export한다. 역할의 성격은 판단 차이와 문장 리듬으로 남긴다.
2. 말투 우선순위를 한 곳에 둔다: 사용자·고객 문체 > 역할별 음색 > 공통 내부 기본값. 이브이의 합쇼체와 `renderOfficeRolePersona`/`review.ts`의 해요체 충돌을 없앤다. 가벼운 종결은 한두 문장, 업무 산출물은 필요한 길이를 허용한다.
3. v14의 “초기 모호함→2지선다”는 결정에 꼭 필요한 정보가 없을 때로, “중대 리스크→1회 확인”은 실제 근거와 권한 경계가 있을 때로 제한한다. 이미 허가된 가역 작업의 수행을 형식적 재승인 질문으로 멈추지 않는다. 토론의 “절충안 1개”보다 해결되지 않은 실질 이견을 먼저 보존한다.
4. 현행 역할 버전·프롬프트/검수/회의 해시·모델을 평가 journal에 동결한다. v14 점수를 주장하지 않는다. 형식 테스트는 모순·금지 대사 유입을 검사하되 의미 점수로 환산하지 않는다.

### P1 — 주장과 근거를 답변 전에 분리

1. 요청·조회 문맥을 `사용자가 말했다/요청했다 / 검증된 원장·제품 사실 / 계산(식·입력) / 추정(가정) / 제안 / 미확인 / 실제 수행 receipt`로 정리한다. 원문 발췌의 위치·시각·scope를 붙인다. 사용자 원문에 효용·기능 주장이 들어 있어도 **그렇게 말한 사실**과 실제 제품 기능·성과의 검증은 별개다. **부재와 미조회, 마감과 가용시간, 초안과 발송, 요청과 기능 존재**를 서로 전환하지 않는다.
2. 최종 답의 구체 주장마다 내부 `claim` 항목(`문장`, `종류`, `근거 인덱스 또는 계산 입력·식`, `확정/조건부 표현`, `외부 공개 여부`)을 만들고, 근거가 없는 확정 사실은 조건부 표현·확인 질문·삭제 중 하나로 바꾼다. 원문에 인용이 있다는 사실만으로 `기한→가용시간`이나 `문의→기능 존재`를 허용하지 않는다. 같은 모델이 작성한 근거표는 **의미 검증 완료의 증거가 아니므로**, 고위험 고객/공식 문구·저장 성공 판정은 근거 인덱스와 상태 계약이 없으면 확정 표현을 반환하지 않는 방식으로 닫는다. 수정된 문장에도 같은 검사를 다시 적용한다.
3. 비교 기간·단위·작업량 합계와 알려지지 않은 시간은 결정 전에 계산·검증한다. 관련 없는 모든 응답에 표나 체크리스트를 붙이지 않는다.

### P2 — 역할 협의와 결과의 일치

1. 회의의 공개 발언마다 `turnId / 입장 / 근거 / 이견 / 새 정보로 바뀐 점 / 남은 조건`을 유지한다. 주관 합성의 `recommendation`과 `dissent`가 각 이견을 **해결(근거 포함) / 보류 / 유지** 중 어디에 두었는지 턴 ID와 함께 대응표로 만든다. 서버는 참조 ID·역할·입장 변경 선언의 구조적 일치를 확인하고 불일치 시 재작성 또는 실패 처리한다. ID만 붙인 허위 합의까지 자동으로 증명할 수는 없으므로 의미 대조는 독립 평가 항목으로 남긴다.
2. `urgent`는 필요한 한 동작과 중단 조건, `explore`는 실제로 다른 대안과 작은 반증 실험, 비중 변경은 **쟁점 우선순위**만 조절한다. 근거의 신뢰도나 권한은 비중으로 바꾸지 않는다.
3. 이브이는 주관 한 명과 결과 하나를 유지한다. 전문가는 결과를 바꿀 구체 쟁점이 있을 때만 참여한다. 탭별 9인 호출·고정 회의를 만들지 않는다.

### P3 — 독립 재평가와 출시 판정

1. P0/P1/P2 각 단계에서 과거 실패의 **음성 회귀 세트**를 먼저 돌린다: 내일 마감/미확인 용량, 미측정 18%/미제공 기능, 202 수락/저장 완료, 고객 반응/외부 카피, 반론 후 합성, 탐색·긴급·비중 변경, 종결 뒤 새 업무. 최소 사례 통과는 개발 피드백일 뿐 인증이 아니다.
2. 변경 파일과 평가 조건을 고정한 뒤 기존 33시나리오·39생성의 전체 범위를 재실행한다. 실패·blocked를 제외하지 않는다. 구현에 참여하지 않은 심사자가 9역할의 20항목·5축, 원문 인용, 치명 게이트 및 설정 대조를 채점한다. v14의 새 2지선다·리스크 제동·절충 지침은 별도 개발 반례로 먼저 시험하되 기존 고정 세트의 점수와 혼합하지 않는다.
3. **통과 기준은 총점 ≥70/100, 각 축 ≥14/20, 치명 오류 0, 필수 역할·회의 턴·설정 대조 완비**다. 개발 세트에서 조정한 뒤에는 아직 쓰지 않은 holdout에서도 같은 9역할·20항목·게이트·설정 대조를 충족해야 한다. holdout 결과를 보고 지침을 다시 고치면 그 세트는 개발 자료로 이동하고 새 미노출 holdout이 필요하다. 9명 모두 통과하기 전에는 “상위 70점 인증” 또는 운영 적용 완료로 표기하지 않는다. 생성률·테스트·UI QA는 별도 지표다.

### P4 — 기능·탭 연결의 균형 조정 (품질 게이트 뒤)

현재의 업무 내장 E0~E4와 기존 저장·승인·원장 경계를 유지한다. 기본 화면에는 **행동 하나와 담당 하나**를 보여 주고, 보조 역할은 반론이 결과를 바꿀 때만 붙인다. 우선 연결은 오늘/주간 정리(샤미드), 고객 답장(부스터), Studio 원고(님피아)처럼 이미 문맥 계약이 있는 곳이다. 홈/현황/프로젝트/브랜드의 확대는 각 표면의 source·scope·저장 복귀 경로를 확인한 뒤 개별로 진행한다. 기존 Guru·브랜드 Council·Legend 경로는 이름만 Office로 바꾸지 않는다. 고객 발송, 캘린더 변경, 코드 실행, 회사 공식 기록은 텍스트 초안과 분리된 승인·receipt가 있을 때만 완료로 말한다. 운영 DB 0038 적용·배포도 기존 잔여로 남긴다.

## 6. 판단해야 할 결과물

- **품질:** 역할별 총점과 5축, 중대 게이트, 필요한 턴·설정 비교를 같은 버전의 원문으로 제시한다. 가장 낮은 근거 축이 실제로 개선됐는지 확인한다.
- **실무:** 외부로 보낼 문장에 미확인 기능·효과 0건, 일정/시간 계획에 없는 버퍼 0건, 회의 합성에 공개 발언과 다른 합의 0건이어야 한다. 이 세 기준은 표본의 치명 실패를 직접 막는 품질 게이트다.
- **제품:** 업무 화면에서 나온 초안은 원문과 scope로 돌아갈 수 있어야 하고, 저장·발송·실행은 별도 receipt로 구별된다. 품질 인증 전에는 사용 범위를 제한하고 AI의 추천을 실제 처리 완료로 표시하지 않는다.
