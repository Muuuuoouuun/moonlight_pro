# Design: Moonlight Brand and Efficiency Operating Model

Mode: Builder / Operator

## Problem Statement

Moonlight should become the private operating system for growing a personal brand and
running work with much less manual coordination. The target is not "more dashboard".
The target is a daily machine that turns signals into decisions, decisions into content
and revenue actions, and every action into a logged feedback loop.

The current repo already points in this direction:

- `apps/hub` is the private decision surface at `/dashboard`.
- `apps/engine` is the intake and execution layer for webhooks, AI briefs, syncs, and logs.
- Supabase is the source of truth for content, revenue, work, automation, and decisions.
- The active product direction is `external signal -> Engine -> Supabase ledger -> Hub`.

## Premises

1. Brand growth and work efficiency should not be separate systems. The same decisions,
   client conversations, project updates, and content drafts should feed both.
2. Moonlight wins if the operator can answer "what matters now?" in under 5 seconds.
3. The content system should produce variants from one source idea: newsletter, blog,
   card news, X thread, and reels script.
4. Revenue follow-up should be driven by stale deals, new leads, and content attribution,
   not memory.
5. Automation is only useful if failures are visible. A hidden broken automation is worse
   than no automation.

## Approaches Considered

### Approach A: Daily Command Ritual

Use the existing Hub surfaces every morning and evening. The operator manually checks
Daily Brief, Work, Content, Revenue, and Automations, then writes one decision and three
next actions.

Effort: S
Risk: Low

Pros:
- Works with the current product immediately.
- Builds the right habit before adding more code.
- Exposes which parts of the ledger are actually useful.

Cons:
- Still depends on discipline.
- Weak leverage until intake and handoff automations are fully live.

### Approach B: Supabase-first Brand OS

Make Supabase the living memory. Every relevant external signal gets normalized into
one of the ledgers: content, work, revenue, automations, decisions, or project updates.
Hub becomes the command deck. Engine becomes the intake and dispatch layer.

Effort: M
Risk: Medium

Pros:
- Matches the current architecture.
- Creates compounding memory across brand, sales, and operations.
- Makes AI briefs and automation logs trustworthy because they read from one ledger.

Cons:
- Requires env, provider, and Supabase discipline.
- Needs clear rules for preview vs live data.

### Approach C: Public Proof Engine

Use Moonlight not only to operate the work, but to publish proof of the work. Selected
decisions, case studies, content packages, and build logs become public-facing assets.

Effort: M/L
Risk: Medium

Pros:
- Turns actual execution into brand material.
- Makes the brand more credible because it shows how the work gets done.
- Creates a repeatable case-study pipeline.

Cons:
- Needs a publishing boundary so private client/work data never leaks.
- Requires editorial taste. Raw logs are not content.

## Recommended Approach

Choose Approach B first, with Approach C as the growth layer.

Moonlight should be used as a private operating ledger first. Once the data and rituals
are reliable, the best brand assets can be exported from the same system. This avoids
the common trap: building a shiny public brand while the private work machine is still
chaotic.

## Operating Loops

### 1. Daily Signal Loop

Every morning, open `Daily Brief` first.

The screen should answer:

- What changed overnight?
- What is late, stale, or risky?
- Which one action protects revenue?
- Which one action grows brand?
- Which one action clears operational drag?

Target metric: decision latency under 5 minutes.

### 2. Content Factory Loop

Use `Content Studio` as the source-idea workshop. Do not start each channel from blank.

One source idea should become:

- Newsletter
- Blog / Insight
- Card News
- X Thread
- Reels Script

Use `Queue` as the next-action board, not a passive list. The ideal lanes are:

```text
Inbox -> Drafting -> Ready -> Handed off -> Watch
```

Target metric: one source idea creates 3 to 5 publishable variants.

### 3. Revenue Follow-up Loop

Use `Revenue` to protect money already in motion.

The highest-leverage questions are:

- Which deal is stale?
- Which lead has not been classified?
- Which account needs a next touch?
- Which content piece created revenue intent?

Target metric: zero qualified leads untouched for more than 24 hours.

### 4. Work and Decision Loop

Use `Work -> Decisions` as the memory of why choices were made.

Every meaningful decision should record:

- Context
- Choice
- Reason
- Review date

This turns brand into authority. Public content can later be derived from real decisions,
not generic advice.

Target metric: at least 5 decision records per week.

### 5. Automation Reliability Loop

Use `Automations -> Runs` as a failure board.

Every flow should have:

- Last run
- Success rate
- Failure reason
- Retry or next action

Target metric: no failed critical automation remains unreviewed for more than 24 hours.

## 400% Definition

"400%" should be measured as four separate multipliers:

1. Content output: one source idea becomes 4 channel assets.
2. Decision speed: daily priority selection drops from 30 minutes to under 5 minutes.
3. Follow-up speed: revenue/account follow-up happens within 24 hours instead of several days.
4. Rework reduction: repeated manual tasks move into logged automations.

The real target is not working 4x harder. It is making one unit of thinking produce
four units of output.

## 30-day Plan

Week 1: Make the daily ritual real.

- Use Daily Brief every morning.
- Record one decision per day.
- Track stale deals and unfinished content manually if needed.

Week 2: Make Content Studio the source of truth.

- Put all brand ideas into Content.
- Convert each serious idea into at least three variants.
- Keep local mirror and Supabase save states visible.

Week 3: Connect revenue and content.

- Tag every lead by source.
- Attach content/campaign context to deals where possible.
- Review stale deals every weekday.

Week 4: Automate the boring edges.

- Gmail -> lead tagging
- Newsletter/card-news handoff -> n8n
- Failed automation -> run log review
- AI brief -> project update

## Development Priorities

### P0: Live Data Trust

Goal: remove the places where Hub looks usable but the operator cannot trust the data yet.

Build:

- Make every main Hub page show a clear `live`, `preview`, or `mock` state.
- Finish Supabase env and seed workflow so Content, Revenue, Work, and Automations can be
  exercised with real ledger data.
- Add one smoke command that checks Hub health, Engine health, Supabase read/write, shared
  webhook secret, and core table availability.
- Keep preview data visually distinct from live data. Never mix them in the same metric.

Why this comes first:

If the operator doubts the data, they will go back to Notion, Gmail, Calendar, and memory.
That kills the operating-system behavior.

### P1: Daily Brief as Command Surface

Goal: make Daily Brief the first screen of the day, not a passive summary.

Build:

- Pull signals from Work, Content, Revenue, Automations, and recent Engine logs.
- Rank signals by urgency: stale deal, failed automation, overdue content, blocked task,
  upcoming meeting, missing decision.
- Give each signal one primary action: write draft, follow up, retry flow, create task,
  record decision, schedule focus block.
- Log dismissed/accepted actions so the brief improves over time.

Why this matters:

This is the screen that creates the 5-minute decision loop. Without it, Moonlight is still
five dashboards instead of one operator brain.

### P2: Content Handoff and Variant Engine

Goal: make one source idea reliably become multiple publishable assets.

Build:

- Treat `content_items` as the master idea and `content_variants` as channel outputs.
- Add variant completeness checks for newsletter, blog/insight, card news, X thread,
  and reels script.
- Add n8n handoff from Studio/Queue with `handoff_requested`, `handoff_success`, and
  `handoff_failed` records in `publish_logs`.
- Add Google Drive upload metadata for card-news exports when available.
- Keep IndexedDB local mirror as recovery, but make Supabase the default source.

Why this matters:

Brand leverage comes from multiplying one real insight across channels. This is the main
400% output multiplier.

### P3: Revenue Memory and Follow-up Engine

Goal: make Moonlight protect money and opportunities automatically.

Build:

- Connect Gmail/Calendar/GitHub/OpenClaw signals to leads, deals, accounts, and cases.
- Add stale-deal rules by stage, value, and last touch.
- Add source attribution from content/campaign to lead/deal where possible.
- Generate follow-up drafts from deal context and previous touches.
- Add a daily "money at risk" strip to Daily Brief.

Why this matters:

The highest ROI workflow is not more analytics. It is preventing warm leads and live deals
from quietly decaying.

### P4: Decision-to-Content Proof Engine

Goal: turn actual operating decisions into public brand authority.

Build:

- Add a decision template: context, choice, reason, rejected options, review date.
- Link decisions to project, content, deal, or automation records.
- Add "turn into content" actions for blog, thread, newsletter, and card news.
- Add privacy labels so private client details never leak into public drafts.
- Add a case-study builder from project updates, decisions, and outcomes.

Why this matters:

The best brand asset is not generic advice. It is proof that the operator makes good
decisions in real situations.

### P5: Automation Reliability and Retry UX

Goal: make automations observable, retryable, and boring in the best way.

Build:

- Normalize provider adapters so each webhook/sync path writes consistent
  `correlation_id`, `provider_event_id`, status, and error fields.
- Add retry candidates and manual retry actions for failed runs.
- Add run detail drawer with payload summary, error, linked project/content/deal, and next action.
- Add failure notifications only for high-impact flows.
- Add contract tests for the core webhook and handoff payloads.

Why this matters:

Automation without observability creates hidden debt. Reliability is what lets the operator
trust the system enough to stop checking everything manually.

## Recommended Build Order

1. P0 Live Data Trust
2. P1 Daily Brief as Command Surface
3. P2 Content Handoff and Variant Engine
4. P3 Revenue Memory and Follow-up Engine
5. P5 Automation Reliability and Retry UX
6. P4 Decision-to-Content Proof Engine

P4 is strategically powerful, but it should wait until the private ledger is trustworthy.
Public proof built on messy private data becomes editorial cleanup work.

## Success Criteria

After 30 days, Moonlight is working if:

- You open Hub before opening random tools.
- Every active project has a next action.
- Every publishable idea has channel variants.
- Every qualified lead has a next touch.
- Every important automation has visible logs.
- Weekly review can be written from the ledger, not memory.

## The Assignment

For the next 7 days, do not add a major new feature first.

Use Moonlight as the daily operating system and write down every friction point:

- "I had to leave Hub to do this."
- "This signal was missing."
- "This action was obvious but not one-click."
- "This data was mock when I needed live."

At the end of the week, build only the top 3 fixes. That is how this becomes an actual
400% system instead of another beautiful dashboard.
