## P1 - Today Actions Read Model

**What:** Add an `attention_items` or `today_actions` read model/repository contract for cross-lane ranking.

**Why:** Hub cannot answer "what matters now?" by letting every page fetch its own tables and invent priority locally. That becomes dashboard coupling at 10x data.

## P1 - Route Response Taxonomy

**What:** Standardize route response states across Hub and Engine: `preview`, `saved`/`accepted`, `partial`, `failed`, `duplicate`, and `degraded`.

**Why:** Today some failed persistence paths return `202 preview`, which can look like acceptable non-live mode. Live write failures need to be visibly different from missing-config preview.

**Pros:** Makes Hub states honest and testable.

**Cons:** Requires touching several routes and client render states.

**Context:** Start with `apps/hub/app/api/hub/content/route.js`, `apps/engine/lib/project-webhook.ts`, `apps/engine/lib/supabase-rest.ts`, and Hub badges that show live/preview/degraded state. Include `durableRecordIds`, `failedWrites`, `retryable`, and `correlationId` where useful.

**Effort:** M human / S with CC+gstack
**Priority:** P1
**Depends on:** Behavioral test harness

## P1 - Production Write Auth Boundary

**What:** Require a real operator/session boundary or server write secret for Hub writes, and constrain open webhook mode to local environments only.

**Why:** Same-origin checks are not enough authorization for production browser writes. `COM_MOON_ALLOW_OPEN_WEBHOOKS=true` also needs a production guard so local smoke-test mode cannot leak into deployment.

**Pros:** Closes a real attack surface before more write routes are added.

**Cons:** Requires deciding the current operator auth/session mechanism.

**Context:** Start with `apps/hub/lib/hub-write-guard.js` and `apps/engine/lib/shared-webhook.ts`. Add contract tests for production + open mode refusal.

**Effort:** M human / S with CC+gstack
**Priority:** P1
**Depends on:** Auth/session decision

## P1 - Behavioral Test Harness

**What:** Add a real behavioral test framework for Engine routes, Hub API routes, and core repository helpers.

**Why:** Current CI has contract checks, typecheck, build, and audit. That catches wiring mistakes, but not branch behavior: duplicate webhooks, partial Supabase writes, preview/live separation, failed provider calls, or Content Studio autosave recovery.

**Pros:** Gives 2am confidence for the command loop. Prevents regressions in security, persistence, and user-visible state.

**Cons:** Adds test framework setup and fixture maintenance.

**Context:** Start with `apps/engine/lib/project-webhook.ts`, `apps/engine/lib/run.ts`, `apps/hub/app/api/hub/content/route.js`, and `apps/hub/lib/repositories/content-ledger.js`. Match the test plan artifact written by autoplan.

**Priority:** P1
**Depends on:** Plan approval

## P1 - Content Variant Schema Contract

**What:** Make content variant types one schema-backed source of truth.

**Why:** Code currently plans variants like `blog_insight`, `x_thread`, and `reels_script`, while the base schema constraint still lists older values like `blog`, `social_post`, and `landing_copy`. Live saves can fail and be misread as preview.

**Pros:** Prevents Content Studio from silently failing live persistence.

**Cons:** Needs migration and contract update.

**Context:** Compare `apps/hub/lib/repositories/content-ledger.js` with `supabase/schema.sql` and active migrations. Add a contract check that every repository variant type is allowed by the schema/migration.

**Effort:** S human / S with CC+gstack
**Priority:** P1

## P2 - AI Prompt And Data Boundary

**What:** Add explicit AI boundary rules for brief generation and future AI proposals.

**Why:** AI brief routes send ledger snapshots to Gemini and persist model output. That output must be treated as a proposal, not trusted fact or automatic execution.

## P2 - Idempotency Key For Nil Provider Event IDs

**What:** Require or derive idempotency keys for public provider routes when `provider_event_id` is missing.

**Why:** The unique index only protects events with stable provider IDs. Retries without IDs can create duplicate project updates.

**Pros:** Protects ledger integrity at provider scale.

**Cons:** Deriving a safe hash requires careful field selection to avoid false duplicates.

**Context:** Start with `apps/engine/lib/project-webhook.ts` and shared webhook payload builders. Prefer provider-native IDs; otherwise support an `Idempotency-Key` header or a provider/source/entity/timestamp hash.

**Effort:** M human / S with CC+gstack
**Priority:** P2
**Depends on:** Route response taxonomy
